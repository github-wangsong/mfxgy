# 04 · 前端工具选择面板

> 所属：阶段 6 · 工具调用
> 本篇覆盖：在画布页 `apps/web/app/apps/[id]/page.tsx` 的 **llm 节点检查器**里新增「工具」复选框——页面加载时 `GET /tools` 拿**能力目录**，用返回的 `ToolDefinition[]` **动态渲染**；勾选 / 取消写入 `llm.data.tools`，**全部取消时删除该键**；调试运行面板把 `tool_call` / `tool_result` 两类**工具事件**与 `node_started` / `token` / `node_finished` 等**节点事件**分开呈现。
> **本篇首次教学**：**「能力目录」驱动 UI**（后端声明能力、前端只负责呈现）· **多选状态与 `data.tools` 的同步**（**不存在的键 = 未启用**）· **工具清单拉取失败要静默降级**（不阻塞画布编辑）· **运行面板区分「节点事件」与「工具事件」**（`round + toolName` 区分同轮多工具、长结果截断 200 字符）· **为什么工具执行过程在前端不可见**（只看到 `tool_call` → `tool_result` 两个事件，实际执行在后端）
> 工具契约 / `ToolDefinition` / 内置工具与安全边界见本阶段 `01-工具契约与内置工具.md`；后端 ReAct 循环与条件边见 `02-NestJS-ReAct循环与条件边.md`、`03-Python工具与ReAct对齐.md`；端到端验收见 `05-验收.md`。SSE 客户端（`fetch` + `getReader`、手动分帧、React 批处理）见 `04-执行引擎/06-前端SSE客户端与运行面板.md`；受控表单 / 复选框 / `useMemo` 见 `02-应用管理/06-前端应用列表页.md`——本篇**直接使用、不重讲**。

## 1. 本篇目标

做完这一篇，你能：

- 选中画布里的 **llm 节点**，在检查器里看到「工具」区：**三个复选框**（`calculator` / `get_current_time` / `http_get`），每项带工具名与描述。
- 勾选 `calculator`、点「保存草稿」，再读 `GET /apps/{id}/graph`，看到该 llm 节点的 `data.tools` 为 `["calculator"]`。
- 取消勾选（全不选）、保存，再读图，确认 **`tools` 键被删除**（不是 `[]`）。
- 打开「调试运行」，运行一个启用了工具的图，在**事件日志**里看到：
  - `tool_call`：`第 1 轮 · 调用 calculator · {"expression":"2+3*4"}`
  - `tool_result`：`第 1 轮 · calculator 返回 14 · 耗时 0 ms`
  - 随后的 `token` 逐段累加，最终输出 `answer: 14`。
- 讲清楚：为什么工具列表要**从后端拉**而不是前端写死、**可选字段的「键不存在」语义**、拉取失败为何要静默、`round` 与 `toolName` 如何区分同一轮的多个工具、以及**工具执行过程为什么前端看不到**。

**验收标准（对齐总纲 §6 阶段 6）**

> 画布上可为 `llm` 节点选择工具；调试面板能看到工具调用与结果。

具体化为可执行层面：

| # | 检查项 | 预期 |
| --- | --- | --- |
| 1 | 选中 llm 节点 | 检查器出现「工具」区，列出 `GET /tools` 返回的**全部**工具（本例 3 个） |
| 2 | 勾选 `calculator` 并保存 | `GET /apps/{id}/graph` 里该节点 `data.tools` = `["calculator"]` |
| 3 | 取消全部勾选并保存 | `GET /apps/{id}/graph` 里该节点 `data` **没有** `tools` 键 |
| 4 | 运行启用 `calculator` 的图 | 日志出现 `tool_call` / `tool_result`（带 `第 N 轮`），随后 `token` 逐段、`run_finished` |
| 5 | 工具清单拉取失败 | 只显示「（工具清单不可用）」，**画布仍可编辑 / 保存 / 运行** |
| 6 | 多轮 / 同轮多工具 | 日志中 `round` 递增；同一 `round` 出现多条 `tool_call` / `tool_result`，靠 `toolName` 区分 |

/** token 事件的 payload 摘要（`节点id · "文本"`），其余事件直接用原始 data 文本。 */
function summarizeFrame(name: string, data: string): string {
  if (name === 'token') {
    try {
      const parsed = JSON.parse(data) as { nodeId?: string; text?: string }
      return `${parsed.nodeId ?? ''} · ${JSON.stringify(parsed.text ?? '')}`
    } catch {
      return data
    }
  }
  // tool_call：`第 N 轮 · 调用 <toolName>` + 紧凑 JSON 参数。
  if (name === 'tool_call') {
    try {
      const parsed = JSON.parse(data) as {
        toolName?: string
        args?: unknown
        round?: number
      }
      return `第 ${parsed.round ?? '?'} 轮 · 调用 ${parsed.toolName ?? ''} · ${JSON.stringify(parsed.args ?? {})}`
    } catch {
      return data
    }
  }
  // tool_result：`第 N 轮 · <toolName> 返回` + 结果（截断 200 字符）+ 耗时。
  if (name === 'tool_result') {
    try {
      const parsed = JSON.parse(data) as {
        toolName?: string
        result?: unknown
        elapsedMs?: number
        round?: number
      }
      const text = typeof parsed.result === 'string' ? parsed.result : JSON.stringify(parsed.result ?? '')
      const result = text.length > 200 ? `${text.slice(0, 200)}…` : text
      return `第 ${parsed.round ?? '?'} 轮 · ${parsed.toolName ?? ''} 返回 ${result} · 耗时 ${parsed.elapsedMs ?? 0} ms`
    } catch {
      return data
    }
  }
  return data.length > 300 ? `${data.slice(0, 300)}…` : data
}

      nds.map((node) => {
        if (node.id !== id) return node
        const current = Array.isArray(node.data.tools) ? (node.data.tools as string[]) : []

          ? current.filter((name) => name !== toolName)
          : [...current, toolName]

        if (next.length === 0) {
          delete nextData.tools
        } else {
          nextData.tools = next
        }
        return { ...node, data: nextData }

   * 编辑 llm 数字字段（temperature / maxTokens）：
   * 非空且可解析为数字时写入 `data[field]`（number）；留空或非法则移除该字段（不留字段即不发送）。
   */
  function changeLlmNumber(
    id: string,
    field: 'temperature' | 'maxTokens',
    raw: string,
    setText: (value: string) => void,
  ): void {
    setText(raw)
    const trimmed = raw.trim()
    if (trimmed === '' || Number.isNaN(Number(trimmed))) {
      setNodes((nds) =>
        nds.map((node) => {
          if (node.id !== id) return node
          const nextData = { ...node.data }
          delete nextData[field]
          return { ...node, data: nextData }
        }),
      )
      return
    }
    updateNodeData(id, { [field]: Number(trimmed) })
  }

    setNodes((nds) => nds.filter((node) => node.id !== id))
    setEdges((eds) => eds.filter((edge) => edge.source !== id && edge.target !== id))
    setSelectedNodeId((cur) => (cur === id ? null : cur))
  }

        id: node.id,

        data: node.data,

      edges: edges.map((edge) => ({
        id: edge.id,

    },

  )

        return

      setError(err instanceof Error ? err.message : String(err))
    } finally {
      setBusy(false)
    }
  }

      router.replace('/login')
      return

    setError(null)
    setMessage(null)
    setBusy(true)
    try {
      const err = await putDraft(token)
      if (err !== null) {
        setError(err)
        return
      }
      const res = await fetch(`${API_BASE}/apps/${appId}/graph/publish`, {
        method: 'POST',
        headers: { Authorization: `Bearer ${token}` },
      })
      if (!res.ok) {
        if (res.status === 401) {
          router.replace('/login')
          return
        }
        const body = (await res.json().catch(() => null)) as { message?: string } | null
        setError(body?.message ?? `HTTP ${res.status}`)
        return
      }
      const data = (await res.json()) as PublishResponse
      setMessage(`已发布 · ${data.publishedAt}`)
    } catch (err: unknown) {
      setError(err instanceof Error ? err.message : String(err))
    } finally {
      setBusy(false)
    }

        return

        } else if (frame.event === 'run_finished') {

            nodeId?: string
            nodeType?: string

              nodeId: parsed.nodeId ?? '',
              promptTokens: usage.promptTokens ?? 0,

        await yieldToPaint()
      }
    } catch (err: unknown) {
      setRunError(err instanceof Error ? err.message : String(err))
    } finally {
      setRunning(false)
    }

### 5.1 「能力目录」驱动 UI：后端声明能力，前端只负责呈现

**问题**：前端怎么知道有哪些工具？如果像这样写死，会怎样？

```tsx
// ❌ 写死：后端新增一个工具，前端必须改代码、重新发版
const tools = [
  { name: 'calculator', description: '...' },
  { name: 'get_current_time', description: '...' },
  { name: 'http_get', description: '...' },
]
```

写死的**直接后果**是「**能力目录漂移**」：后端注册表加了 `web_search`，前端列表里没有；后端删了某个工具，前端还在显示；两端的工具描述也可能对不上。更根本的问题是——**哪些工具存在、叫什么、参数是什么，是后端的知识，不是前端的知识**。

**本项目的做法：能力目录（capability catalog）由后端提供。**

```ts
// 契约：packages/contract/src/index.ts
export interface ToolDefinition {
  name: string
  description: string
  /** JSON Schema 形状（作为 OpenAI function calling 的 `parameters`） */
  parameters: Record<string, unknown>
}
```

**这段在干什么**：声明能力目录的**条目形状**——`name` 给程序分派、`description` 给模型 / 人读、`parameters` 给模型当函数签名。

`GET /tools` 返回：

```json
{
  "items": [
    { "name": "calculator", "description": "安全地计算一个四则运算表达式……", "parameters": { "type": "object", "properties": { "expression": { "type": "string" } }, "required": ["expression"], "additionalProperties": false } },
    { "name": "get_current_time", "description": "返回当前 UTC 时间……", "parameters": { "type": "object", "properties": {}, "additionalProperties": false } },
    { "name": "http_get", "description": "对给定 URL 发起 HTTP GET……", "parameters": { "type": "object", "properties": { "url": { "type": "string" } }, "required": ["url"], "additionalProperties": false } }
  ]
}
```

**这段在干什么**：这是 `GET /tools` 的**实际响应**——三条声明，不含任何执行逻辑；前端拿到的就是「有哪些工具、叫什么、怎么描述」。

前端只做两件事：**拉目录**、**照着目录渲染**。

```tsx
const [tools, setTools] = useState<ToolDefinition[]>([])

useEffect(() => {
  const token = localStorage.getItem('accessToken')
  if (token === null) return
  let cancelled = false
  fetch(`${API_BASE}/tools`, { headers: { Authorization: `Bearer ${token}` } })
    .then((res) => {
      if (!res.ok) return null
      return res.json() as Promise<{ items?: ToolDefinition[] }>
    })
    .then((body) => {
      if (cancelled || body === null) return
      setTools(Array.isArray(body.items) ? body.items : [])
    })
    .catch(() => {
      // 静默降级：工具清单不可用时只是不显示勾选项。
    })
  return () => {
    cancelled = true
  }
}, [])
```

**这段在干什么**：页面挂载时拉一次 `/tools`，把 `items` 存进 `tools`；`cancelled` 防止组件卸载后 `setState`。

```tsx
{tools.map((tool) => (
  <label key={tool.name} style={{ display: 'flex', gap: 6, alignItems: 'flex-start', fontSize: 12 }}>
    <input
      type="checkbox"
      checked={selectedTools.includes(tool.name)}
      onChange={() => toggleLlmTool(selectedNode.id, tool.name)}
      style={{ marginTop: 2 }}
    />
    <span>
      <code>{tool.name}</code>
      <span style={{ display: 'block', color: '#888' }}>{tool.description}</span>
    </span>
  </label>
))}
```

**这段在干什么**：`useEffect` 在页面挂载时拉一次 `/tools`，把 `items` 存进 `tools`；渲染时 `tools.map(...)` 生成每个复选框，**不出现任何工具名常量**。`key` 用 `tool.name`（工具名在目录里唯一），而不是数组下标——目录顺序变化时 React 仍能正确复用节点。

**为什么这样更好**

| 维度 | 前端写死 | 能力目录驱动 |
| --- | --- | --- |
| 新增工具 | 改前端 + 发版 | **前端零改动**，后端注册表 + `/tools` 即可 |
| 删除 / 改名 | 前端残留旧项 | 目录一变，UI 跟着变 |
| 描述文案 | 两处维护，容易漂移 | **唯一真源**在后端注册表 |
| 权限 / 安全 | 前端可伪造工具名 | UI 只是「请求」，**执行与否由后端决定** |
| 多端复用 | 每端各写一份 | 任何客户端都用同一份目录 |

**`ToolDefinition` 三要素分别给谁看**

- `name`：**程序**用它分派执行、前端用它做 `key` 与勾选值；
- `description`：**模型**用它判断「这个工具能干什么」；前端也顺手展示给人看；
- `parameters`：**模型**看的「函数签名」（JSON Schema），OpenAI function calling 的 `parameters` 就是它。前端**不需要**用它渲染表单——本阶段的工具参数由模型生成，不是人填。

> **一句话**：**能力目录把「有哪些工具」从 UI 里抽出来，放到后端注册表；前端退化成「目录的投影」。** 加工具不用改前端，正是这种分工的直接收益。

### 5.2 多选状态与 `data.tools` 的同步：不存在的键 = 未启用

**问题**：复选框的「已选集合」存在哪？取消到空时，`data.tools` 应该写 `[]` 还是删掉键？

**本项目的选择：`data.tools` 是可选字段；全部取消时删除键。**

```ts
/** 当前 llm 节点已启用的工具名（`data.tools` 缺失或非数组时视为未启用）。 */
const selectedTools = useMemo<string[]>(() => {
  const raw = selectedNode?.data.tools
  return Array.isArray(raw) ? (raw as string[]) : []
}, [selectedNode])
```

**这段在干什么**：把节点里的 `data.tools` **归一**成 UI 可用的 `string[]`——缺失、`null`、非数组一律视为「未启用」。

```ts
/**
 * 勾选 / 取消勾选 llm 节点的工具：写入 `data.tools` 数组；
 * 全部取消时**删除该键**（空数组等于启用但无工具，语义不同）。
 */
function toggleLlmTool(id: string, toolName: string): void {
  setNodes((nds) =>
    nds.map((node) => {
      if (node.id !== id) return node
      const current = Array.isArray(node.data.tools) ? (node.data.tools as string[]) : []
      const next = current.includes(toolName)
        ? current.filter((name) => name !== toolName)
        : [...current, toolName]
      const nextData = { ...node.data }
      if (next.length === 0) {
        delete nextData.tools
      } else {
        nextData.tools = next
      }
      return { ...node, data: nextData }
    }),
  )
}
```

**这段在干什么**：`selectedTools` 把「节点里存的」翻译成「UI 需要的数组」——缺失 / 非数组一律当空。`toggleLlmTool` 做三件事：① 取当前数组；② 已存在就 `filter` 掉，不存在就 `[...current, toolName]`（**不可变更新**，不原地 `push`）；③ **`next.length === 0` 时 `delete nextData.tools`**，否则写入新数组。最后用 `{ ...node, data: nextData }` 返回新的 node，ReactFlow 才会重渲染。

**为什么「空数组」和「不存在」要区分**

| 写法 | JSON | 语义 | 问题 |
| --- | --- | --- | --- |
| 删除键 | `{}`（`data` 里无 `tools`） | **未启用工具** | —— |
| 留空数组 | `{"tools":[]}` | 「显式声明：启用工具，但一个都不选」 | 与「未启用」**语义不同**，却让契约读者要多想一层 |

- 契约里 `tools?: string[]` 是**可选字段**（`packages/contract/src/index.ts` 的 `LlmNodeData.tools?`）。可选字段的通用语义是：**键不存在 = 未提供 / 未启用**；空数组是「提供了，但为空」。两者在**当前引擎**里行为相同（都当没工具），但在**契约层面**是不同的图。
- 留着 `[]` 会让每次保存的图都多一个无意义的键，**diff 噪声**变大；未来若给 `tools` 加「显式启用但空」的新语义，历史数据就会歧义。
- 所以 UI 层就把它**归一**：**只要没有选中项，就不写这个键**。这也是「**可选字段的语义：不存在的键 = 未启用**」的落地方式。

**实测（真实浏览器 + 后端）**：

```
勾选 calculator → 保存 → GET /apps/{id}/graph → "tools":["calculator"]
再取消 calculator → 保存 → GET /apps/{id}/graph → 该节点 data 里没有 "tools" 键
```

> 注意：勾选后必须点「**保存草稿**」，`data.tools` 才会经 `PUT /apps/{id}/graph` 落库；`/run` 用的是**库里的草稿图**，不是浏览器内存里的节点。只勾选不保存，运行不会带工具。

### 5.3 拉取失败要静默降级：工具列表不是画布的关键路径

**问题**：`GET /tools` 失败（后端 500、网络抖动、令牌过期、接口还没部署）时，画布要不要报错 / 白屏 / 禁止保存？

**答案：不要。工具是「可选增强」，不是画布编辑的关键路径。**

```ts
fetch(`${API_BASE}/tools`, { headers: { Authorization: `Bearer ${token}` } })
  .then((res) => {
    if (!res.ok) return null          // 401/404/500 一律当「没有目录」
    return res.json() as Promise<{ items?: ToolDefinition[] }>
  })
  .then((body) => {
    if (cancelled || body === null) return
    setTools(Array.isArray(body.items) ? body.items : [])
  })
  .catch(() => {
    // 静默降级：工具清单不可用时只是不显示勾选项。
  })
```

**这段在干什么**：任何失败（非 2xx / 网络异常）都不抛到 UI，只让 `tools` 保持空；「失败」在这里被翻译成「没有目录」，而不是「页面错误」。

```tsx
{tools.length === 0 && (
  <p style={{ fontSize: 12, color: '#888', margin: 0 }}>（工具清单不可用）</p>
)}
```

**这段在干什么**：非 2xx 返回 `null`（不走 `res.json()`，避免解析 HTML 错误页抛错）；网络异常被 `.catch` 吞掉；两种情况都只让 `tools` 保持 `[]`。UI 因此只显示一行灰色提示「（工具清单不可用）」，**不设置 `error`、不阻塞保存 / 运行**。

**为什么必须静默**

- 画布的**关键路径**是「读图 → 编辑 → 保存 / 运行」；`/tools` 只是给检查器**加一栏复选框**。为了一个可选目录让整页报错，是把「增强」当成了「依赖」。
- **已有的 `data.tools` 不会因为目录拉取失败而丢失**：`selectedTools` 是从节点 `data` 读的，不是从 `tools` 目录读的；保存时 `buildGraph()` 原样带上 `data`。所以即使目录不可用，用户仍能保存一张**带工具**的图（只是看不到复选框、无法在这里改选）。
- 若令牌真的过期，`/apps/{id}/graph` 的 401 处理会先跳登录（阶段 2 · 06）；`/tools` 无需重复承担这个职责。

> **一句话**：**关键路径失败要报错，增强路径失败要降级。** 工具目录属于后者。

### 5.4 运行面板区分「节点事件」与「工具事件」

**问题**：运行日志里现在多了 `tool_call` / `tool_result`。它们和 `node_started` / `token` / `node_finished` 混在一起，怎么让人一眼看懂「第几轮、谁被调用、结果是什么」？

**契约里的工具事件**（`packages/contract/sse-events.md` §2 / §3.1）：

| 事件 | payload | 含义 |
| --- | --- | --- |
| `tool_call` | `nodeId` / `toolName` / `args`(object) / `round`(number) | llm 节点决定调用某个工具 |
| `tool_result` | `nodeId` / `toolName` / `result`(string) / `elapsedMs`(number) / `round`(number) | 该工具执行完成 |

`round` 从 **1** 开始；**同一轮的多个工具调用属于同一个 `round`**。工具轮次发生在 **llm 节点内部**，所以 `node_started(llm)` / `node_finished(llm)` **各只发一次**：

```
node_started(llm)
  token*                 ← 本轮模型流式文本
  tool_call(round 1)
  tool_result(round 1)
  token*
  tool_call(round 2)
  tool_result(round 2)
  …
  token*                 ← 最后一轮（无 tool_calls）的文本
node_finished(llm)
```

**这段在干什么**：这是契约规定的**工具事件顺序**——节点事件只包在外层，`tool_call` / `tool_result` 按轮次成对出现在中间；`round` 是轮次，`toolName` 是同一轮里的区分。

**前端只加两个摘要分支**：

```ts
// tool_call：`第 N 轮 · 调用 <toolName>` + 紧凑 JSON 参数。
if (name === 'tool_call') {
  try {
    const parsed = JSON.parse(data) as {
      toolName?: string
      args?: unknown
      round?: number
    }
    return `第 ${parsed.round ?? '?'} 轮 · 调用 ${parsed.toolName ?? ''} · ${JSON.stringify(parsed.args ?? {})}`
  } catch {
    return data
  }
}
// tool_result：`第 N 轮 · <toolName> 返回` + 结果（截断 200 字符）+ 耗时。
if (name === 'tool_result') {
  try {
    const parsed = JSON.parse(data) as {
      toolName?: string
      result?: unknown
      elapsedMs?: number
      round?: number
    }
    const text = typeof parsed.result === 'string' ? parsed.result : JSON.stringify(parsed.result ?? '')
    const result = text.length > 200 ? `${text.slice(0, 200)}…` : text
    return `第 ${parsed.round ?? '?'} 轮 · ${parsed.toolName ?? ''} 返回 ${result} · 耗时 ${parsed.elapsedMs ?? 0} ms`
  } catch {
    return data
  }
}
```

**这段在干什么**：`summarizeFrame` 按事件名分流。`token` 仍是「节点 id · "文本"」；`tool_call` 额外拼上 **`round` + `toolName` + 参数**；`tool_result` 额外拼上 **`round` + `toolName` + 结果 + 耗时**。其余事件（`run_started` / `node_started` / `node_finished` / `run_finished` / `run_failed`）继续走最后的「原文，超 300 字截断」。

**为什么用 `round + toolName` 区分**

- 同一 `llm` 节点可能**多轮**调用工具：`round` 1、2、3……靠它区分「第几轮」。
- **同一轮**也可能有**多个**工具（并行调用）：只看 `round` 不够，还要看 `toolName`。例如同一轮同时调 `calculator` 和 `get_current_time`，日志会是：
  ```
  第 1 轮 · 调用 calculator · {"expression":"6*7"}
  第 1 轮 · calculator 返回 42 · 耗时 0 ms
  第 1 轮 · 调用 get_current_time · {}
  第 1 轮 · get_current_time 返回 2026-10-20T16:15:57.595Z · 耗时 0 ms
  ```
- **`result` 一律是字符串**（契约规定）：工具返回值被序列化成字符串（紧凑 JSON，不转义非 ASCII）。所以前端先判断 `typeof result === 'string'`，不是字符串才 `JSON.stringify` 兜底。

**为什么截断 200 字符**

- 工具结果可能很长（`http_get` 最多 64KB）。日志区只有 200px 高，把 64KB 塞进 DOM 会卡顿、也看不清。
- 截断只影响**日志展示**，**不影响** `tool_result.result` 的原始值，也不影响模型拿到的 `ToolMessage`——后端照旧使用完整结果。
- 200 是「够看清开头 + 不撑爆 UI」的经验值；`token` 的 300 字符截断同理。

**实测日志（真实浏览器）**：

```
第 1 轮 · 调用 calculator · {"expression":"2+3*4"}
第 1 轮 · calculator 返回 14 · 耗时 0 ms
```

### 5.5 为什么工具执行在前端「不可见过程」

**问题**：前端能看到 `tool_call` 和 `tool_result`，但看不到工具**内部**——不知道 `calculator` 怎么解析表达式、`http_get` 请求了哪个 IP、耗时花在哪。为什么？

**答案：工具执行发生在后端，前端只收到「开始调用」和「执行完成」两个事件。**

```
前端（浏览器）                     后端（NestJS / FastAPI）
    │  POST /apps/{id}/run              │
    │ ─────────────────────────────────>│
    │                                    │  llm 节点：模型返回 tool_calls
    │ <── tool_call(round, name, args) ──│  ← 执行前
    │                                    │  executeTool(name, args)
    │                                    │  （解析 / HTTP / 计时，全在后端）
    │ <── tool_result(result, elapsed) ──│  ← 执行后
    │                                    │  结果作为 ToolMessage 回填，下一轮模型
    │ <── token ... ─────────────────────│
    │ <── node_finished(llm) ────────────│
    │ <── run_finished ──────────────────│
```

**为什么这样设计**

1. **安全边界**：工具是后端能力（`http_get` 能发网络请求、`calculator` 能执行解析器）。把执行放前端，等于把「能访问内网的 HTTP 客户端」交给浏览器，且无法统一做超时 / 体积 / 协议白名单。前端只发「请求」，**执行权在后端**。
2. **模型只出意图，程序负责执行**：Function Calling 的分工是「模型输出 `tool_calls`（意图 + 参数），程序校验并执行」。执行器必须在可信侧（后端），前端只是**观察者**。
3. **契约简单、两端可逐字节比对**：事件协议只定义 `tool_call` / `tool_result` 两个**边界事件**，不定义工具内部的进度。这样 TS / Python 两套实现只要在边界上一致，内部怎么写都行（`http_get` 用 `fetch` 还是 `httpx` 不影响协议）。
4. **过程不可见是「有意的抽象」**：前端不需要知道 `calculator` 的递归下降、`http_get` 的重定向跟随；它只需要知道「调了什么、返回什么、花了多久」。`elapsedMs` 就是给观察者的**唯一过程指标**。

**代价与边界**

- 调试时看不到工具内部的中间步骤；如果将来需要「工具执行进度」（如长任务分片），必须**新增事件类型**（例如 `tool_progress`），而不是让前端猜。
- `tool_result` 只在**成功**时发；工具失败时发 `run_failed`（`nodeId` 为该 llm 节点），**没有** `tool_result`，也**没有** `node_finished`（见 `error-messages.md` §6.2）。
- 同轮多个工具由后端**按调用顺序依次执行**（当前实现不是真并发），所以 `tool_call` / `tool_result` 成对出现、顺序稳定；未来若真并发，协议仍用 `round + toolName` 区分，但顺序保证要重新定义。

> **一句话**：**前端看到的是「调用 → 结果」这条边界，不是工具的内心戏。** 这不是信息缺失，而是把执行过程留在可信侧、把契约收敛到两个事件的**设计选择**。

### 5.6 若干配套点（简讲）

- **受控复选框**：`checked={selectedTools.includes(tool.name)}` + `onChange={() => toggleLlmTool(...)}`，是标准的受控组件（阶段 2 · 06 的受控表单，只引用）。不要用 `defaultChecked`——它只在首次挂载生效，节点切换后不会同步。
- **`key={tool.name}`**：工具名在目录里唯一，适合做 React `key`；用数组下标会在目录顺序变化时把「选中态」错配到别的工具（虽然 `checked` 由名字决定，但 DOM 复用仍建议稳定 key）。
- **`Array.isArray` 守卫**：`data.tools` 来自 JSON，可能是 `undefined`、`null`、字符串或对象。`Array.isArray` 是运行期最可靠的「是不是数组」判断（`typeof [] === 'object'`，不能用）。
- **不可变更新**：`setNodes(nds => nds.map(...))` 返回新数组、新 node、新 `data`；ReactFlow 依赖引用变化重渲染。直接 `node.data.tools.push(...)` 不会触发更新。
- **工具目录只拉一次**：`useEffect(..., [])` 空依赖，页面挂载拉一次。工具注册表在进程启动时固定，运行中不会变；需要热更新时刷新页面即可。
- **没有新增依赖 / 样式**：复选框是原生 `<input type="checkbox">`，布局沿用内联 `style`（项目未配置 Tailwind，阶段 4 · 06 已说明）。

## 7. 常见坑

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **全不选时留 `tools: []`** | 图里出现空数组，和「未启用」混在一起 | 可选字段的语义是「键不存在 = 未启用」。`next.length === 0` 时 `delete nextData.tools`（第 5.2 节） |
| 2 | **前端写死工具列表** | 后端新增工具后前端看不到 | 用 `GET /tools` 目录动态渲染；加工具只改后端注册表（第 5.1 节） |
| 3 | **`/tools` 失败就整页报错 / 禁止保存** | 后端稍有抖动就无法编辑画布 | 工具是增强路径，失败**静默降级**为「（工具清单不可用）」（第 5.3 节） |
| 4 | **用数组下标做 `key`** | 目录顺序变化时选中态 / DOM 复用错乱 | 用 `key={tool.name}`（第 5.1 / 5.6 节） |
| 5 | **勾选后没保存就运行** | 运行没有工具事件 | `/run` 读的是**库里的草稿图**；勾选后必须「保存草稿」 |
| 6 | **把 `tool_result.result` 当对象** | `result` 显示 `[object Object]` 或渲染报错 | 契约规定 `result` **一律为字符串**；非字符串才 `JSON.stringify` 兜底（第 5.4 节） |
| 7 | **长结果不截断** | 64KB 结果把日志区撑爆 / 卡顿 | 展示层截断 200 字符；原始值不变（第 5.4 节） |
| 8 | **以为工具过程会流式显示** | 等不到「工具内部进度」 | 契约只有 `tool_call` / `tool_result` 两个边界事件，执行在后端（第 5.5 节） |
| 9 | **认为同轮多工具是「并行执行」** | 以为 `tool_result` 顺序不确定 | 当前后端按调用顺序**依次执行**，同轮仍用 `round + toolName` 区分；顺序保证以协议为准 |
| 10 | **用 `defaultChecked`** | 切换节点后复选框不跟随 | 必须受控：`checked={selectedTools.includes(tool.name)}`（第 5.6 节） |
| 11 | **忘记 401 处理** | 令牌过期时目录静默为空，画布也读不到 | 画布图的 `fetch` 已有 401 → `/login`（阶段 2 · 06）；`/tools` 只降级 |
| 12 | **mock 不返回工具调用** | 勾了工具却只有 echo | mock 只有收到 `tools` + prompt 里的 `[[call:...]]` 标记才返回 `tool_calls`；真实模型则由模型自行决定（`05-验收.md`） |

## 8. 本篇复盘与知识点

**一句话总结本篇**：工具选择面板是**能力目录的投影**——页面 `GET /tools` 拿 `ToolDefinition[]`，用 `name` 渲染复选框、用 `description` 辅助人读、把 `parameters` 留给模型；勾选写入 `llm.data.tools`，**全不选删除键**（不存在的键 = 未启用）；目录拉取失败**静默降级**，不阻塞画布；运行面板把 `tool_call` / `tool_result` 与节点事件分开摘要，用 `round + toolName` 区分轮次与同轮多工具，长结果截断 200 字符——而工具的**真正执行**始终在后端，前端只看得到「调用 → 结果」这条边界。

**本篇学到的工程要点**

1. **能力目录驱动 UI**：后端声明 `name / description / parameters`，前端只呈现；加工具不用改前端。
2. **可选字段语义**：`tools?` 的「键不存在」= 未启用；全不选时 `delete`，不留 `[]`。
3. **增强路径失败要降级**：`/tools` 挂了只少一栏复选框，画布编辑 / 保存 / 运行照旧。
4. **事件分层**：节点事件（`node_started` / `token` / `node_finished`）与工具事件（`tool_call` / `tool_result`）是两层；工具轮次在 llm 节点内部，节点事件只发首 / 末各一次。
5. **`round + toolName`**：多轮靠 `round`，同轮多工具靠 `toolName`；`result` 是字符串，展示时截断。
6. **执行在后端**：前端看到的是两个边界事件，不是工具内心戏——这是安全边界与协议简化的结果。

**遗留 / 后续**

- 工具执行进度（长任务分片）未定义事件；需要时新增 `tool_progress` 之类的协议事件。
- 工具参数表单未做「人手填」——本阶段参数由模型生成；若未来支持「手动测试工具」，可用 `parameters`（JSON Schema）驱动表单。
- 工具目录的缓存 / 版本号未做；当前每次进页面拉一次。
- 真并发执行同轮多个工具尚未实现（当前顺序执行）；协议已用 `round + toolName` 预留区分能力。
