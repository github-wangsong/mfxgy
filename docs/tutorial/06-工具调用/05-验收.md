## 1. 本篇目标

做完这一篇，你能：

- 沿**依赖顺序**逐层验收阶段 6：契约 `0.6.0` → `GET /tools` 两端逐字段一致 → **单工具 ReAct**（`tool_call` → `tool_result` → token → `node_finished`）→ **多轮 / 并行** → **4 组工具错误两端一致** → **阶段 4 / 5 回归**。
- 用**可直接复制的命令**证明两套后端在「工具调用」上**行为一致**：事件名序列一致、`tool_call` / `tool_result` 的 payload 键集合一致、`tool_result.result` 一致、`run_final` / `run_failed` 一致（除 `runId` / `elapsedMs` / 动态时间戳外逐字节相同）。
- 讲清楚**阶段 6 补齐的是什么**：从「**单次模型调用**」到「**模型能自主决定调用工具、并多轮推理**」——这是 **Agent 的雏形**。
- 讲清楚**为什么「不加 Agent 节点」**：复用既有 `llm` 节点 + 条件边，图模型更简单，学习重点落在**循环机制**本身。
- 讲清楚**条件边 vs 普通边**的本质差异，以及**环**在 LangGraph 里为什么是**一等公民**（为将来 checkpoint / 中断恢复铺路）。
- 讲清楚**工具是攻击面**：`calculator` 禁 `eval`、`http_get` 防 SSRF、超时与体积上限——「工具调用必须做安全边界」。

**验收标准（对齐总纲 §6 阶段 6）**

> `llm` 节点能自主调用内置工具并多轮推理；工具错误可读。

具体化为本文第 3 节**每条命令的「预期输出」都命中**：

| # | 检查层 | 预期 |
| --- | --- | --- |
| L1 | 契约 | `pnpm run build:contract` 成功；`CONTRACT_VERSION` = **`0.6.0`**；`ToolDefinition` / `LlmNodeData.tools?` 就位 |
| L2 | **能力目录** | 两端 `GET /tools` 均 **200**、均返回 **3 个**定义，**解析后的 JSON 逐字段相等**；无 token → **401 `Missing bearer token`** |
| L3 | **单工具 ReAct** | 两端同一张图：`tool_call`(round 1) → `tool_result` → `token` × 2 → `node_finished`；`tool_result.result = "14"`、`node_finished.output.text = "answer: 14"`、`usage = 60 / 10 / 70` |
| L4 | **多轮 / 并行** | 多轮：`round` **1 → 2**；并行：**同一 `round`** 两个工具（`calculator` `6*7` → `42`、`get_current_time` → ISO-8601 UTC 时间） |
| L5 | **工具错误 4 组** | 两端 `message` **逐字节一致**：未知工具（400）/ `invalid arguments` / `rounds exceeded` / `not allowed` |
| L6 | **回归（阶段 4 / 5）** | 不配 `tools` 时 token 序列 `["echo:"," Hell","o min","i-dif","y"]`、usage `15 / 21 / 36`；阶段 4 的 400 / 401 / 404 与阶段 5 的 LLM 错误映射不变 |

## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序（先契约与目录、后单工具、再多轮 / 并行、最后错误与回归）

```
L1 契约编译(0.6.0)   L2 GET /tools 两端一致
        ↓                     ↓
L3 单工具 ReAct（tool_call → tool_result → token → node_finished）
        ↓
L4 多轮 / 并行（round 1→2；同轮多工具）
        ↓
L5 工具错误 4 组一致 → L6 回归（阶段 4 / 5）
```

**为什么按这个顺序**：契约不编译 / `ToolDefinition` 不存在，工具目录无从谈起；目录不一致，前端与模型的「可用工具」就会漂移；单工具跑通后，才谈多轮 / 并行；最后用错误与回归证明「新能力没有破坏旧行为」。

### 3.3 L3 —— 单工具 ReAct：完整事件序列 + 结果 + usage（两端各跑）

**在哪执行**：任意目录
**目的**：证明「模型只出意图、程序执行工具、结果回填、模型继续推理」这条 ReAct 闭环在两端**事件级一致**。

**建一个应用并保存一张 `start → llm → end` 的图**（llm 启用 `calculator`；prompt 里的 `[[call:...]]` 是 mock 的**脚本化工具调用标记**，真实模型不需要它）：

```bash
APP_ID=$(curl -s -X POST http://127.0.0.1:3001/apps \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"tool-demo","mode":"workflow"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['id'])")

curl -s -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"start_1","type":"start","position":{"x":0,"y":0},
         "data":{"title":"开始","inputs":[]}},
        {"id":"llm_1","type":"llm","position":{"x":0,"y":160},
         "data":{"title":"LLM","model":"mock-model",
                 "prompt":"[[call:calculator:{\"expression\":\"2+3*4\"}]] 请帮我计算这个表达式的结果吧！",
                 "tools":["calculator"]}},
        {"id":"end_1","type":"end","position":{"x":0,"y":320},
         "data":{"title":"结束","outputs":[{"name":"result","value":"{{ llm_1.text }}"}]}}
      ],"edges":[
        {"id":"e1","source":"start_1","target":"llm_1","sourceHandle":null,"targetHandle":null},
        {"id":"e2","source":"llm_1","target":"end_1","sourceHandle":null,"targetHandle":null}
      ]}' > /dev/null
```

> prompt 共 **58** 个字符（标记 42 + 空格 1 + 中文 15）。这不是随手写的：mock 的 `prompt_tokens` 按消息字符数算，58 + 工具结果 `"14"` 的 2 个字符 = **60**，正好对上 L3 的 `usage 60 / 10 / 70`（见下方解析）。

**两端各发一次运行请求，抓原始流到文件**：

```bash
curl -s -N -X POST http://127.0.0.1:3001/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{}}' > ts.sse
curl -s -N -X POST http://127.0.0.1:8000/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{}}' > py.sse

# 事件名序列逐项比对
grep '^event:' ts.sse | sed 's/^event: //' > ts.names
grep '^event:' py.sse | sed 's/^event: //' > py.names
diff ts.names py.names && echo "SEQUENCE IDENTICAL"

# 归一后整帧比对（抹掉 runId / elapsedMs）
sed -E 's/"runId":"[^"]*"/"runId":"X"/g; s/"elapsedMs":[0-9]+/"elapsedMs":N/g' ts.sse > ts.norm
sed -E 's/"runId":"[^"]*"/"runId":"X"/g; s/"elapsedMs":[0-9]+/"elapsedMs":N/g' py.sse > py.norm
diff ts.norm py.norm && echo "FRAMES IDENTICAL"

# 只看工具事件
grep -E '^event: (tool_call|tool_result)$' -A1 ts.sse
```

**预期输出（实测·两端相同）**

```
SEQUENCE IDENTICAL
FRAMES IDENTICAL
event: tool_call
data: {"nodeId":"llm_1","toolName":"calculator","args":{"expression":"2+3*4"},"round":1}
event: tool_result
data: {"nodeId":"llm_1","toolName":"calculator","result":"14","elapsedMs":0,"round":1}
```

**事件名序列（两端一致）**

```
run_started
node_started        (start_1)
node_finished       (start_1)
node_started        (llm_1)        ← 只发一次
tool_call           (round 1)
tool_result         (round 1)
token               ("answe")
token               ("r: 14")
node_finished       (llm_1)        ← 只在最后一轮发一次
node_started        (end_1)
node_finished       (end_1)
run_finished
```

**关键 payload（两端一致）**

```json
{"nodeId":"llm_1","toolName":"calculator","args":{"expression":"2+3*4"},"round":1}
{"nodeId":"llm_1","toolName":"calculator","result":"14","elapsedMs":0,"round":1}
{"nodeId":"llm_1","text":"answe"}
{"nodeId":"llm_1","text":"r: 14"}
```

`node_finished(llm_1).output`：

```json
{"text":"answer: 14","model":"mock-model","usage":{"promptTokens":60,"completionTokens":10,"totalTokens":70}}
```

`run_finished.outputs`：

```json
{"result":"answer: 14"}
```

**结果解读（四个关键点）**：

- **`tool_call` 在 `tool_result` 之前，且都带 `round`**：`tool_call` 是「模型决定调用」的**意图事件**，`tool_result` 是「程序执行完成」的**结果事件**。两者之间才是真正的工具执行（后端内部，前端不可见——`04` §5.5）。
- **`tool_result.result` 恒为字符串**：`calculator` 返回数值 `14`，但契约要求序列化成字符串 `"14"`（紧凑 JSON、不转义非 ASCII）。前端与模型拿到的都是字符串。
- **`node_started` / `node_finished` 各只一次**：工具轮次发生在 **llm 节点内部**，不重复发节点事件（`sse-events.md` §3.1）。这正是「不加 Agent 节点、把循环藏在节点里」的直接体现。
- **`usage` 来自最后一轮**：mock 第一轮（工具调用）发 `content: null`，没有 `token`；工具结果 `"14"` 回填后，第二轮 messages = user(58) + assistant(0) + tool(2) = **60** 个字符，最终文本 `"answer: 14"` 共 **10** 个字符 → `60 / 10 / 70`。`usage` 是**最后一轮**的用量，不是各轮累加（契约只定义输出形状，不定义累计口径；两端一致即可）。
- **帧比对口径**：本例工具事件的键顺序两端一致，所以归一后 `diff` 通过；**通用口径仍是「解析后的 JSON 相等」**（`sse-events.md` §1）——若某端键顺序不同，raw `diff` 会误报，应逐帧 `JSON.parse` 后比较。

### 3.4 L4 —— 多轮 / 并行：`round` 递增与同轮多工具

#### 4.1 多轮：`round` 1 → 2

**换一张 prompt 含两批标记的图**（`[[next]]` 分隔轮次）：

```bash
curl -s -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"start_1","type":"start","position":{"x":0,"y":0},
         "data":{"title":"开始","inputs":[]}},
        {"id":"llm_1","type":"llm","position":{"x":0,"y":160},
         "data":{"title":"LLM","model":"mock-model",
                 "prompt":"[[call:calculator:{\"expression\":\"2+3*4\"}]] [[next]] [[call:calculator:{\"expression\":\"6*7\"}]]",
                 "tools":["calculator"]}},
        {"id":"end_1","type":"end","position":{"x":0,"y":320},
         "data":{"title":"结束","outputs":[{"name":"result","value":"{{ llm_1.text }}"}]}}
      ],"edges":[
        {"id":"e1","source":"start_1","target":"llm_1"},
        {"id":"e2","source":"llm_1","target":"end_1"}
      ]}' > /dev/null
```

**两端运行并只看工具事件**：

```bash
curl -s -N -X POST http://127.0.0.1:3001/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{}}' | grep -E '^event: (tool_call|tool_result)$' -A1
```

**预期输出（实测·两端一致）**

```
event: tool_call
data: {"nodeId":"llm_1","toolName":"calculator","args":{"expression":"2+3*4"},"round":1}
event: tool_result
data: {"nodeId":"llm_1","toolName":"calculator","result":"14","elapsedMs":0,"round":1}
event: tool_call

```

最终 `node_finished(llm_1).output.text = "answer: 42"`（mock 用**最后一个**工具结果作答）。

**换一张 prompt 在同一批写两个标记的图**：

```bash
        {"id":"end_1","type":"end","position":{"x":0,"y":320},
         "data":{"title":"结束","outputs":[{"name":"result","value":"{{ llm_1.text }}"}]}}
```

```bash

  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
```

**预期输出（实测·两端一致；时间戳为各自运行时刻，不要求两端相等）**

```

data: {"nodeId":"llm_1","toolName":"calculator","args":{"expression":"6*7"},"round":1}
event: tool_result
data: {"nodeId":"llm_1","toolName":"calculator","result":"42","elapsedMs":0,"round":1}
event: tool_call
data: {"nodeId":"llm_1","toolName":"get_current_time","args":{},"round":1}
event: tool_result

```

**结果解读（三个关键点）**：

- **多轮靠 `round` 递增**：1 → 2；每一轮都是「模型返回 `tool_calls` → 内部工具节点执行 → 结果回填 → 回到 llm」。**节点事件不重复**。
- **并行是「同一 `round` 的多个调用」**：两个 `tool_call` 都 `round: 1`，靠 **`toolName`** 区分；`tool_call` / `tool_result` **按调用顺序一一对应**（当前实现顺序执行，不是真并发）。
- **动态结果不做跨端逐字节比较**：`get_current_time` 返回各自运行时刻（实测样例 `2026-10-20T16:15:57.595Z`，24 字符 ISO-8601 UTC、毫秒、`Z` 结尾）。契约只要求**形状与工具行为**一致，不要求两个进程的时钟相同；比对时应把时间戳归一或按正则 `<ISO-Z>` 校验。`calculator` 的 `42` 是确定值，可逐字节比。

## 4. 【技术讨论 1】阶段 6 补上了什么：Agent 的雏形

**问题**：阶段 5 已经能调用真实模型并流式输出，阶段 6 的 `tools` 到底「新」在哪？

**答案的一句话**：**阶段 5 是「单次模型调用」；阶段 6 是「模型能自主决定调用工具、观察结果、再继续推理」——这就是 Agent 的最小闭环。**

| 层 | 阶段 5 | 阶段 6 |
| --- | --- | --- |
| 模型输出 | 一段文本 | 文本 **或** `tool_calls`（意图 + 参数） |
| 程序角色 | 调一次模型、转发 token | **执行工具**、把结果回填、**再调模型** |
| 轮次 | 固定 1 轮 | **可变多轮**（`round` 1…N，受 `MAX_TOOL_ROUNDS` 限制） |
| 输入给模型 | system + user | system + user + assistant(`tool_calls`) + **`ToolMessage`** |
| 事件 | `token` / `node_finished` | **+ `tool_call` / `tool_result`** |
| 失败面 | provider 错误 | **+ 工具错误**（参数 / 超时 / 协议 / 轮次） |

**ReAct 循环（Reason + Act）**

```
        ┌──────────────────────────────┐
        │   llm：Reason（推理 + 决定）   │
        └──────────────┬───────────────┘
              有 tool_calls? ──否──> 输出最终文本 → node_finished
                       │是
                       ▼
        ┌──────────────────────────────┐
        │ tools：Act（执行工具）         │
        │ 发 tool_call → 执行 → tool_result │
        └──────────────┬───────────────┘
                       │ 结果作为 ToolMessage 回填
                       └──────────────> 回到 llm（下一轮）
```

- **Reason**：模型看「用户问题 + 之前的工具结果」，决定「还要不要调工具、调哪个、参数是什么」。
- **Act**：程序**不替模型决定**，只负责校验参数、执行、把结果原样回填。
- **Observation**：`ToolMessage` 就是观察结果；模型下一轮基于它继续推理。
- **终止**：某一轮模型不再返回 `tool_calls`（或达到轮次上限 → `run_failed`）。

**为什么说这是「雏形」而不是「完整 Agent」**

| 能力 | 本阶段 | 完整 Agent 常见能力 |
| --- | --- | --- |
| 工具选择 | ✅ 模型自主选择 | ✅ |
| 多轮推理 | ✅ 有上限的循环 | ✅（可能更长 / 带规划） |
| 记忆 | 仅**单个 llm 节点**的消息数组 | 跨会话 / 长期记忆 |
| 规划 | 隐式（模型每轮决定） | 显式计划 / 子任务分解 |
| 人工介入 | ❌ | HITL / 审批 / 中断恢复 |
| 工具发现 | 静态目录（`GET /tools`） | 动态注册 / 权限化工具市场 |
| 并发 | 顺序执行同轮工具 | 真并发 / 并行分支 |

> **一句话**：**阶段 6 把「模型说一句话」升级成「模型做一件事、看结果、再做下一件」——Agent 的核心循环已经在了，剩下的是记忆、规划、人工介入与工程化。**

## 5. 【技术讨论 2】为什么「不加 Agent 节点」

**问题**：既然阶段 6 引入了 Agent 循环，为什么不新增一个 `agent` 节点类型，把「思考 + 工具 + 循环」都封装进去？这样画布上不是更直观吗？

**答案的一句话**：**总纲的设计约束是「复用既有节点 + 条件边」——图模型更简单，学习重点落在循环机制本身，而不是又一个节点类型的配置面板。**

**如果加一个 `agent` 节点，会发生什么**

- **重复**：`agent` 节点需要自己的 `model` / `prompt` / `system` / `temperature` / `maxTokens` / `tools` 配置，和 `llm` 节点几乎一样；契约、前端检查器、两套后端都要再实现一遍。
- **隐藏**：循环被封装进一个黑盒节点，画布上看不到「llm → tools → llm」的边；学习者只能看到「一个 Agent 节点进去、一个结果出来」，**循环机制被藏起来了**。
- **分裂**：`llm` 与 `agent` 两套节点行为不同，事件协议要分叉，前端运行面板要分叉，验收要分叉。
- **过早抽象**：本阶段要教的是「**条件边 + 环**」这个通用能力；一旦有了 Agent 节点，学习者会以为「循环是 Agent 节点的魔法」，而不是「图的能力」。

**本项目的做法**

| 设计 | 说明 |
| --- | --- |
| **不新增节点类型** | 契约里 `GraphNode.type` 仍是 `start` / `end` / `llm`（`sse-events.md` §2） |
| **`llm.data.tools` 声明工具** | 启用工具只是给既有 llm 节点加一个可选字段 |
| **内部节点 `<llmId>__tools`** | 引擎在编译期**额外加**一个内部节点，用户画布上看不到 |
| **条件边 + 环** | `llm` 有 `tool_calls` → 走 `__tools`；`__tools` → 回到 `llm`；无 `tool_calls` → 走原图下游 |
| **事件仍只围绕 llm** | `node_started` / `node_finished` 各一次；工具事件在中间 |

**代价与收益**

- **代价**：画布上看不到工具循环的「边」；工具轮次只能通过事件日志观察；`llm` 节点承担了「单次调用」与「ReAct 循环」两种行为，节点内部逻辑更复杂。
- **收益**：契约稳定（不新增节点类型）、前端画布零改动（只加复选框）、两套后端的事件协议不分叉、学习重点集中在**条件边与环**这个可迁移的 LangGraph 能力上。
- **未来**：如果要做「显式 Agent 节点」，它可以是**对既有能力的组合**（llm + tools + 条件边），而不是另起一套配置；本阶段的实现已经为它铺好了路。

> **一句话**：**不是「不能加 Agent 节点」，而是「这一阶段不该加」——先把循环机制教透，再谈更高层的封装。** 复用既有节点 + 条件边，是**用图的能力表达 Agent**，而不是**用节点类型隐藏 Agent**。

## 6. 【技术讨论 3】条件边 vs 普通边；环为什么是一等公民

**问题**：ReactFlow 里画的是「普通边」，LangGraph 里却要 `addConditionalEdges`。两者到底差在哪？为什么说「环」在 LangGraph 里是一等公民？

**答案的一句话**：**普通边是「无条件、总会走」；条件边是「由路由器函数决定走哪条」；环就是「条件边指回自己」——LangGraph 的 `StateGraph` 天生支持环，每次回到节点就是一次新的 superstep。**

**普通边 vs 条件边**

| 维度 | 普通边 `addEdge(a, b)` | 条件边 `addConditionalEdges(a, router, mapping)` |
| --- | --- | --- |
| 触发 | 节点 a 执行完，**必然**走 b | 节点 a 执行完，调 `router(state)` 返回**分支 key** |
| 目标 | **固定**一个 | 由 `mapping[key]` **动态**决定（可以是不同节点 / `END`） |
| 表达力 | 线性 / DAG | **分支 + 循环** |
| 本例 | `start → llm`、`llm → end`（不启用工具时） | 启用工具的 `llm`：有 `tool_calls` → `__tools`，否则 → `end` |

```ts
// TS：条件边 + 环
builder.addConditionalEdges(
  node.id,
  (state) => ((state.toolCalls[node.id] ?? []).length > 0 ? 'tools' : 'continue'),
  { tools: `${node.id}__tools`, continue: downstream },
)
builder.addEdge(`${node.id}__tools`, node.id)   // ← 环：工具节点回到 llm
```

```py
# Python：同一结构
builder.add_conditional_edges(
    node_id,
    lambda state, nid=node_id: "tools" if (state["tool_calls"].get(nid) or []) else "continue",
    {"tools": f"{node_id}__tools", "continue": downstream},
)
builder.add_edge(f"{node_id}__tools", node_id)   # ← 环
```

**「跳过原普通边」的陷阱（重点）**

- 在 LangGraph 里，**同一个节点可以同时有普通边和条件边**；如果两者都保留，节点执行完会**同时**触发两条出边（普通边 + 条件边的选中分支），造成「既去下游、又去工具」的冲突 / 重复执行。
- 所以引擎在编译时**跳过**「启用了工具的 llm 节点」的**普通出边**：

```ts
for (const edge of graph.edges) {
  // 启用了工具的 llm 节点改由条件边分派，跳过其普通出边（否则两者冲突）
  if (toolNodes.some((node) => node.id === edge.source)) {
    continue
  }
  builder.addEdge(edge.source, edge.target)
}
```

- 然后由条件边的 `continue` 分支**接管**原来那条普通边：`continue: downstream`（多条下游时取**第一条**，`firstDownstream`）。这样「不调工具时」仍然能走到原图下游，「调工具时」走环。

**环为什么是一等公民**

- **`StateGraph` 的节点不是「一次性执行」**：每次有边指向它，它就再执行一次；环就是「边指回已执行过的节点」。LangGraph 用 **superstep** 调度，天然允许环，不需要 `while` 循环或递归。
- **状态在环上累积**：`messages[nodeId]` 逐轮追加 assistant / `ToolMessage`，`rounds[nodeId]` 递增；每一轮都是**同一个节点的新一次执行**，但状态是延续的。
- **需要显式上限**：环不能无限转——`MAX_TOOL_ROUNDS`（默认 5）在工具节点里检查，超过即 `run_failed`；同时把 LangGraph 的 `recursionLimit` 调高（`max(25, maxRounds*2 + nodes*2 + 10)`），避免默认 25 步先触发、掩盖真正的业务错误。
- **为 checkpoint / 中断恢复铺路**：环 + 显式状态是「可暂停、可恢复」的前提。将来接入 LangGraph 的 checkpointer，可以在「工具执行前 / 后」保存状态、人工审批、断点续跑——**这正是阶段 11（HITL）/ 后续 checkpoint 的扩展点**。如果没有环，Agent 的「多轮」就只能写死在节点内部，无法在轮次之间暂停。

> **一句话**：**普通边是「流程」，条件边是「选择」，环是「重复」；LangGraph 把这三件事都建模成图，所以 Agent 循环不需要额外的运行时魔法。**

## 7. 【技术讨论 4】工具是攻击面：工具调用必须做安全边界

**问题**：工具让模型「能做事」，但也让模型「能闯祸」。本阶段的内置工具做了哪些安全约束？为什么这些约束必须在**工具实现层**，而不是靠提示词？

**答案的一句话**：**模型的输出是不可信输入。** 工具是模型与真实世界之间的**执行边界**，必须在代码里做**最小权限、白名单、超时、体积上限、固定错误分类**——提示词只能「建议」，不能「保证」。

**`calculator`：禁 `eval` / `Function`，手写解析器**

- `eval` / `new Function` 会把**模型生成的字符串当代码执行**——模型（或提示词注入）可以构造 `process.exit()`、读文件、发网络请求。**绝不能**把模型输出直接喂给 `eval`。
- 本项目用**手写递归下降解析器**，只接受 `+ - * /`、括号、小数、一元正负号；文法之外的字符（如 `process`、`;`、`require`）一律 `invalid arguments`；除零、`2+` 这类不完整表达式同样拒绝。
- 结果是**白名单文法**：能算的只有四则运算，**不能**变成任意代码执行。

**`http_get`：协议白名单 + 超时 + 体积上限**

| 约束 | 实现 | 防的是什么 |
| --- | --- | --- |
| **协议白名单** | 只允许 `http:` / `https:`；`file:`、`ftp:`、`data:` 等 → `not allowed` | 本地文件读取、非预期协议 |
| **超时** | 5s（TS `AbortController` / Py `httpx.Timeout`）→ `timeout` | 慢响应拖死执行、连接堆积 |
| **体积上限** | 64KB，读取过程中超限即 `cancel` → `too large` | 大响应撑爆内存 / 前端 |
| **错误归一** | `ToolError(reason)` → `tool {name} failed: {reason}` | 不透出内部 URL / 堆栈 / 库细节 |

**SSRF（Server-Side Request Forgery）是什么**

- 攻击者让**服务器**去请求「服务器能访问、但攻击者不该访问」的地址，例如 `http://127.0.0.1:...`、云厂商元数据 `http://169.254.169.254/...`、内网服务。
- **协议白名单是 SSRF 的第一道防线**（挡住 `file:` 等），但**不是全部**：`http://127.0.0.1` 仍然是 `http:`。更严格的实现需要**目标地址黑名单 / 域名白名单 / DNS 解析后校验私网 IP**。
- 本阶段的内置工具是**教学用最小实现**：协议白名单 + 超时不等于「完整 SSRF 防护」；这一点必须诚实说明。生产环境还应限制出站网络（egress firewall）、禁止访问私网 / 元数据地址。

**为什么不能靠提示词**

- 提示词可以写「不要调用危险 URL」，但模型可能被**提示词注入**绕过；工具参数是**模型生成的不可信输入**，必须在执行前**程序校验**。
- 同理，工具名必须在**预检**阶段校验（未知工具 → 400），不能等模型「自觉」只调已注册的工具。

**工具错误为什么要固定分类**

- 工具失败的原因很多（参数、超时、协议、体积、其它），但**对外只暴露 5 个固定 `reason`**：`invalid arguments` / `timeout` / `not allowed` / `too large` / `error`。
- 好处：① 两端**逐字节一致**；② 不透出内部实现（URL、堆栈、库版本）；③ 调用方可以按 `reason` 做稳定处理（重试 / 提示 / 终止）。
- 形态：`tool {name} failed: {reason}`；轮次超限单独一条 `tool call rounds exceeded: {max}`。

> **一句话**：**工具是「模型的手」，手必须有边界：能做什么（白名单）、做多久（超时）、拿多少（体积）、失败了怎么说（固定分类）。** 这些边界只能由**代码**保证，不能由提示词保证。

## 8. 常见坑汇总（跨阶段 6）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **以为真实模型也会按 `[[call:...]]` 调工具** | 换成真实 provider 后行为完全不同 | `[[call:...]]` 是 **mock 的脚本标记**；真实模型由 function calling 自主决定。mock 只是确定性自测（`05-LLM节点/04`） |
| 2 | **勾了工具但没保存** | 运行没有 `tool_call` | `/run` 读**库里的草稿图**；勾选后必须「保存草稿」（`04` §5.2） |
| 3 | **`MAX_TOOL_ROUNDS` 改了没生效** | G3 仍按 5 轮跑 / 不报错 | 改完**必须重启**。**曾经** api-py 直接读 `os.environ`、不读 `.env`（pydantic-settings 不回写进程环境）；**现已修复**：`_max_tool_rounds()` 经 `Settings.max_tool_rounds` 读 `.env`。通用原则：读配置走 `Settings`，别直接读 `os.environ`（§3.5 · G3） |
| 4 | **比对整帧时忘了归一 `elapsedMs`** | 两端 `tool_result` diff 不一致 | 工具耗时天然不同；归一 `runId` 与**所有** `elapsedMs`（sed 的 `g` 标志） |
| 5 | **拿 `get_current_time` 做跨端逐字节比较** | 两个进程时间不同，diff 失败 | 动态值只比**形状**（24 字符 ISO-8601 UTC、毫秒、`Z`），不比具体时刻 |
| 6 | **未知工具的 nodeId 写错** | 文案对不上 | 文案里的 `{nodeId}` 是**图里的 llm 节点 id**（G1 用 `llm1`，就报 `llm node llm1 ...`） |
| 7 | **以为工具失败还有 `tool_result` / `node_finished`** | 等不到，以为卡住 | 工具失败 → 直接 `run_failed`；**没有** `tool_result`，**没有** `node_finished`（`error-messages.md` §6.2） |
| 8 | **以为第一轮工具调用会先有 token** | 事件序列对不上 | mock 的工具调用轮 `content: null`，**不发 token**；token 出现在**最后一轮**（或无工具的单轮） |
| 9 | **把 `usage` 当各轮累加** | 数值对不上 | 本阶段 `usage` 取**最后一轮**的用量（60/10/70）；契约只定义形状，不定义累计口径 |
| 10 | **同轮多工具以为顺序不确定** | 以为 `tool_call` / `tool_result` 会交错 | 当前实现**按调用顺序依次执行**，一对一对齐；`round + toolName` 用于区分 |
| 11 | **条件边和普通边都留着** | 节点既去工具又去下游 / 重复执行 | 启用工具的 llm 节点要**跳过原普通出边**，由条件边的 `continue` 接管（§6） |
| 12 | **`recursionLimit` 没调高** | 多轮工具还没到 `MAX_TOOL_ROUNDS` 就报 LangGraph 递归上限 | 环每轮消耗 superstep；按 `maxRounds*2 + nodes*2 + 10` 留余量（§6） |
| 13 | **把模型输出直接 `eval`** | 代码注入 / 任意执行 | `calculator` 用手写解析器；任何工具都**不得**把模型参数当代码 / SQL / shell（§7） |
| 14 | **以为协议白名单 = 完整 SSRF 防护** | `http://127.0.0.1` 仍可访问 | 协议白名单只挡 `file:` 等；生产还需私网 / 元数据地址黑名单与出站限制（§7） |
| 15 | **`tools: []` 与「没有 tools」混用** | 图 JSON 语义不清 | 可选字段：**键不存在 = 未启用**；全不选时删键（`04` §5.2） |

## 9. 本篇复盘与知识点

**一句话总结阶段 6**：在既有 `llm` 节点上加一个可选字段 `data.tools`，用「**LLM + 内部工具节点 + 条件边 + 环**」实现 ReAct——模型输出 `tool_calls`（意图），程序执行工具并回填 `ToolMessage`，模型继续下一轮；事件层新增 `tool_call` / `tool_result`（带 `round`），节点事件仍只发首 / 末各一次；两套后端在**事件序列、工具结果、4 组错误文案**上逐字节一致；工具实现守住「禁 `eval`、协议白名单、超时、体积上限、固定错误分类」的安全边界。

**本篇学到的工程 / 架构要点**

1. **阶段 6 补上「Agent 的雏形」**：从「单次模型调用」到「自主决定调用工具、多轮推理」；ReAct = Reason（模型）→ Act（程序）→ Observation（`ToolMessage`）→ 再 Reason。
2. **不加 Agent 节点**：复用既有 `llm` 节点 + 条件边，图模型更简单，学习重点落在**循环机制**；代价是循环在画布上不可见、节点内部更复杂。
3. **条件边 vs 普通边**：普通边无条件必走；条件边由 `router(state)` 决定分支。**环**是 `StateGraph` 的一等公民（superstep 调度），为 checkpoint / 中断恢复铺路；启用工具的节点必须**跳过原普通边**，否则冲突。
4. **工具是攻击面**：模型输出不可信；`calculator` 禁 `eval` + 手写解析器；`http_get` 协议白名单（SSRF 第一道防线）+ 5s 超时 + 64KB 上限；错误固定分类。
5. **分层验收**：契约 → 能力目录 → 单工具 ReAct → 多轮 / 并行 → 4 组错误 → 回归，逐层自证；归一 `runId` / `elapsedMs`、动态时间戳只比形状。
6. **前后端分工**：能力目录驱动 UI（`GET /tools`），前端只呈现；工具执行在后端，前端只看到 `tool_call` → `tool_result` 两个边界事件。

**遗留到下阶段**

- 工具级别的**权限 / 域名白名单**（当前只有协议白名单，SSRF 防护不完整）。
- 真并发执行同轮多个工具（当前顺序执行）。
- 工具执行进度 / 长任务事件（当前只有 `tool_call` / `tool_result`）。
- 显式 Agent 节点 / 规划 / 记忆 / 人工介入（HITL）——留给后续阶段。
- 把本文 L2~L5 固化成 CI 断言（目录一致、事件序列、错误文案）。

**基础技术要点**：Function Calling 分工 · `ToolDefinition` 三要素 · JSON Schema 签名 · `GET /tools` 能力目录 · ReAct 循环 · `addConditionalEdges` / `add_conditional_edges` 与环 · 按节点隔离状态（`messages` / `rounds` / `toolCalls`）· `ToolMessage` · `MAX_TOOL_ROUNDS` · `bindTools` / `bind_tools` · 工具安全（禁 `eval`、SSRF、超时、体积）· 工具错误固定分类。
