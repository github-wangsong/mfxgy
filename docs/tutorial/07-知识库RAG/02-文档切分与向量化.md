## 0. 定位：RAG 的「入口」只有两步

阶段 7 的知识库，本质是把「文件」变成「可检索的向量」，再把「问题」变成「一串相似 chunk」。**切分与向量化就是这条流水线的入口**，后面 `knowledge` 节点、检索接口、前端引用展示，全都只是在消费这里产出的数据。

```text
上传（本篇）
  文件字节
    │ decode
    ▼
  UTF-8 文本 ──splitText──▶ chunk[] ──embedTexts──▶ vector[][]
                                                       │
                                                       ▼
                                   documents(1) + chunks(N, embedding vector(1536))

检索（本篇只到分数，接口细节见本阶段 01 篇）
  query ──embedTexts([query])──▶ vector
                                   │
                                   ▼
             SELECT 1 - (embedding <=> :v) AS score ... ORDER BY embedding <=> :v LIMIT topK
```

这里有两个**容易被低估**的事实：

1. **切分决定了检索的「最小单位」**。检索永远只能返回整块，块切坏了，后面什么模型都救不回来。
2. **向量化决定了「什么叫相似」**。本项目验收用的是 mock 的**词袋哈希**向量，它衡量的是「共享字符多不多」，不是「意思像不像」。这不是偷懒，而是为了**无密钥、可复现**地把整条管道跑通并逐字节对比。

### 0.1 术语先立住（首次出现，一句话解释）

| 术语 | 一句话解释 |
| --- | --- |
| **RAG** | Retrieval-Augmented Generation：先从知识库**检索**相关片段，再把片段塞进 prompt 让模型回答，而不是只靠模型参数记忆。 |
| **chunk（分块）** | 文档被切分后的一小段文本，是**检索与引用的最小单位**；本项目存在 `chunks` 表里，`chunk_index` 从 0 开始。 |
| **`chunkSize`** | 单块长度上限。本项目按**字符数**（更准确地说：TS 是 UTF-16 码元数、Python 是码点数）计，不是 token 数。 |
| **`chunkOverlap`** | 相邻块之间**尽量**保留的重叠长度；目的是让被切断的句子在至少一块里保持完整上下文。 |
| **separator（分隔符）** | 切分时优先尝试切断的位置，如段落 `\n\n`、换行 `\n`、句号 `。`。顺序代表「多想在这里切」。 |
| **embedding（嵌入 / 向量化）** | 把一段文本映射成一个定长浮点数组；语义相近的文本，向量方向相近。 |
| **余弦相似度（cosine similarity）** | 两个向量夹角的余弦：`dot(a,b) / (|a|·|b|)`，取值 `[-1,1]`，越大越相似。 |
| **pgvector** | PostgreSQL 的向量扩展，提供 `vector(N)` 列类型与 `<=>`（余弦距离）等运算符。 |
| **HNSW** | 一种近似最近邻索引结构；本项目 `chunks_embedding_hnsw` 用它加速 `<=>` 检索。 |
| **tiktoken** | OpenAI 的本地分词库；`langchain-openai` 在 Python 侧默认用它把文本换成 token id 再发请求。 |
| **FNV-1a** | 一种极快的非加密 32 位哈希算法，逐字节「异或 + 乘质数」；mock 用它把 token 映射到向量桶。 |
| **L2 归一化** | 把向量除以它的欧氏长度（范数），使其长度为 1；这样余弦相似度就退化成点积。 |

## 3. 先看清要做什么

### 3.1 一次上传的七个阶段

| 阶段 | TS（`kb.service.ts`） | Python（`service.py`） | 失败时 |
| --- | --- | --- | --- |
| ① 归属校验 | `findOwned()` | `_find_owned()` | 404 `Knowledge base not found` |
| ② 文件存在 / 类型 / 大小 | `file === undefined`、`isSupportedDocument`、`MAX_DOCUMENT_BYTES` | 同左 | 400 |
| ③ 字节 → 文本 | `file.buffer.toString('utf8')` | `raw.decode("utf-8", errors="replace")` | 空文本 → 400 |
| ④ 切分 + 去空白块 | `splitText()` + `.filter(...)` | `split_text()` + 列表推导过滤 | 无块 → 400 |
| ⑤ 批量嵌入 | `embedOrBadRequest(chunks)` | `_embed_or_bad_request(chunks)` | 400（普通 JSON 接口） |
| ⑥ 写 `documents` + `chunks` | `$transaction` + 原生 SQL | `db.add/flush` + 原生 SQL + `commit` | 数据库错误（500） |
| ⑦ 回填 `chunkCount` 并返回 | `document.update` + `toDocumentResponse` | `document.chunk_count = len(chunks)` | — |

**顺序上的关键点**：**⑤ 在 ⑥ 之前**。嵌入失败时数据库里一行都没写，不会留下「有文档、没向量」的半成品。这是两端的共同设计，也是「宁可失败也不要写入错误向量」的第一层保障。

### 3.2 为什么两端 chunk 能逐字节相同

这不是巧合，而是四个条件同时成立：

| 条件 | TS | Python |
| --- | --- | --- |
| **同一份输入字节** | 同一个文件，经 HTTP multipart 原样到达 | 同左 |
| **同一套解码规则** | `buffer.toString('utf8')`，非法字节 → U+FFFD | `decode("utf-8", errors="replace")`，同样 → U+FFFD |
| **同一组参数** | `chunkSize=500`、`chunkOverlap=80`、8 个 `separators`、`keepSeparator=true` | 同左（snake_case） |
| **同一套算法** | `RecursiveCharacterTextSplitter`（LangChain TS 版） | `RecursiveCharacterTextSplitter`（LangChain Python 版） |
| **同一套空块过滤** | `chunk.trim() !== ''` | `chunk.strip() != ""` |

> 注意第 4 条的说法：**「同一个库」指的是 LangChain 这一套算法在两个语言里的移植实现**，不是「同一份代码」。两边的分隔符保留手法甚至不同（TS 用正则前瞻，Python 用捕获组再拼），但结果都是「分隔符归到下一段的开头」。§11.1 会逐条对齐。

**所以「参数是契约的一部分」**：`chunkSize` / `chunkOverlap` / `separators` / `keepSeparator` 虽然不出现在 `openapi.yaml`（客户端根本看不到 chunk 的边界），但它们是**两套后端之间的跨实现契约**。只改一边，同一份文档会切出不同的块，检索命中与 `score` 立刻分叉。两个源码文件顶部都用注释写明了「修改这里必须同步另一端」，原因就在这。

### 3.3 写进数据库的形状

```text
documents  1 ──── N chunks
  id                 id
  knowledge_base_id  document_id
  name               knowledge_base_id   ← 冗余一份，检索时不用 JOIN 也能按库过滤
  mime_type          chunk_index         ← 0,1,2…，同一文档内唯一
  size_bytes         content             ← 切分后的文本（检索返回的就是它）
  status='ready'     embedding vector(1536) ← pgvector 列，ORM 无法映射
  chunk_count=2      created_at
```

`chunks.embedding` 在 Prisma 里是 `Unsupported("vector(1536)")?`——两个 ORM 都不支持 pgvector 类型，所以**向量读写一律走原生 SQL**（本阶段 01 篇已讲，本篇直接使用）。

## 5. 【技术教学 · 首次】为什么要切分

### 5.1 三个理由，缺一不可

**① 上下文窗口有限。** 把 5 万字的员工手册整篇塞进 prompt，既超模型窗口，也把 token 预算一次性烧光。切分后只把 topK 个最相关片段（本项目默认 4 块 × 500 字）送进模型。

**② 检索粒度越细越准。** 检索的单位就是 chunk。整篇文档只有一个向量时，命中就是「整篇命中」，你无法只把「退款那一节」交给模型。块越小，定位越精确；但太小又会丢上下文（§12.1 的权衡）。

**③ 长文直接 embedding 会「语义被平均掉」。** 一个 embedding 是**定长**向量（本项目 1536 个数）。一篇文档若同时讲退款、配送、发票，它的向量会落在这些主题的「质心」附近——与任何一个具体问题的相似度都不高。直觉类比：把十本书各写一句摘要再合成一句话，这句话对查「某本书第 3 章」几乎没有帮助。

```text
整篇（多主题）→ 一个向量 → 与「退款」的相似度 0.31（示意值，被其它主题拉平）
切块后：
  refund#0（只讲退款）  → 与「退款」的相似度 0.59  ← 命中
  invoice#0（只讲发票） → 与「退款」的相似度 0.13
```

### 5.2 `chunkSize` 与 `chunkOverlap`

**`chunkSize`**：单块长度上限。本项目的「长度」是**字符数**：
- TS：`text.length` → UTF-16 码元数（BMP 汉字 1 个；emoji 2 个）；
- Python：`len(str)` → Unicode 码点数（emoji 1 个）。

**`chunkOverlap`**：切下一块时，从上一块尾部「回退」保留多少长度。为什么需要它：

```text
原文：……请在下单后 7 天内提交退款申请，逾期不予受理。审核通过后原路退回。
不重叠切（边界恰好落在「申请」后）：
  chunk0 = ……请在下单后 7 天内提交退款申请
  chunk1 = ，逾期不予受理。审核通过后原路退回。
        ↑ chunk1 一开头就是「，逾期」，读者（和模型）不知道在说什么
带 overlap：
  chunk1 = 提交退款申请，逾期不予受理。审核通过后原路退回。
        ↑ 上一句的尾巴被带进来了，上下文完整
```

**重要认知：`chunkOverlap` 是「尽量保留」，不是「精确 80 字符」。** 它只能按**已有的分片单位**回退，不能把一个分片再切碎。例如按句号切分、每句 40 字、`overlap=80`，最多回退两句（80 字）；如果下一句有 120 字，为了让这块不超 `chunkSize`，可能一句都回退不了，实际重叠变成 0。§11.2 会把这个 `while` 循环拆开讲。

**参数怎么选**（本项目的 `500 / 80`）：

| 取值 | 后果 |
| --- | --- |
| `chunkSize` 太小（如 100） | 一句话被切成两半，向量只表达半句；`topK` 里全是碎片 |
| `chunkSize` 太大（如 2000） | 召回仍可能命中，但一块里混了多个主题，向量被平均、上下文被稀释（§12.1） |
| `chunkOverlap` 为 0 | 句子在边界处断裂且无法补救 |
| `chunkOverlap` 接近 `chunkSize` | 相邻块几乎重复，写入量与检索噪声翻倍；TS 侧还会直接报错（§12.2） |

### 5.3 `RecursiveCharacterTextSplitter` 的递归策略

它的名字就是策略：**按分隔符列表从「最想切」到「最不想切」依次尝试**。本项目列表：

**完整文件路径：`apps/api-ts/src/rag/splitter.ts`（第 11 行，`separators`）**

```ts
separators: ['\n\n', '\n', '。', '！', '？', '. ', ' ', ''],
```

| 顺序 | 分隔符 | 语义 | 说明 |
| --- | --- | --- | --- |
| 1 | `\n\n` | 段落 | 最希望在这里断，语义边界最完整 |
| 2 | `\n` | 行 | 次优 |
| 3–5 | `。` / `！` / `？` | 中文句子 | 中英混排时优先保句子 |
| 6 | `. `（点 + 空格） | 英文句子 | 注意带空格，避免把 `3.14` 当句号 |
| 7 | ` `（空格） | 词边界 | 实在不行才在词间断 |
| 8 | `''`（空串） | 字符 | **兜底**：逐字符切，保证任何文本都能压到 `chunkSize` 以内 |

**算法（两端同构）**：

```text
_split_text(text, separators):
  1. 从 separators 里找到「第一个在 text 中出现」的分隔符 sep，
     并记下它后面的候选 newSeparators（更不想用的那些）。
     若遇到空串 ""，直接选它（兜底）。
  2. 用 sep 把 text 切开（keepSeparator=true 时，sep 留在后一段开头）。
  3. 遍历每个小片 s：
       - len(s) < chunkSize  → 先攒进 goodSplits
       - len(s) >= chunkSize → 先把攒着的 goodSplits「合并成块」；
                               若还有更细的 newSeparators，就递归切 s；
                               否则 s 原样成块（可能超长）。
  4. 收尾：把剩下的 goodSplits 合并成块。
```

「合并成块」= `merge_splits`：贪心往当前块里塞小片，塞不下就先落盘，再从**队头**弹出小片，直到剩余长度 ≤ `chunkOverlap`——这就是重叠的来源。

**一个小例子**（`chunkSize=6`、`chunkOverlap=2`、`separators=['。','']`、`keepSeparator=true`）：

```text
text = 第一段。第二段。第三段。
按「。」切成： ["第一段", "。第二段", "。第三段"]   （长度 3 / 4 / 4）
                 ↑ 分隔符「。」归到**后一段的开头**（两端实现一致）
merge：3 + 4 > 6 → 落盘「第一段」；回退时 3 > 2，弹出唯一一片 → 重叠为 0
      4 + 4 > 6 → 落盘「。第二段」；同样回退到 0
      → 最终 3 块，块间无重叠
```

这个例子说明两件事：

1. **块可能以分隔符开头**（例如 `。第二段`）。这是 `keepSeparator=true` 的正常结果，不是 bug；两端都这样，所以仍然逐字节相同。
2. **当分片单位本身较大时，overlap 可能退化**。真正能产生稳定重叠的，是「句子远短于 overlap」的普通中文段落。

```ts
// 完整文件路径：apps/api-ts/src/rag/splitter.ts
import { RecursiveCharacterTextSplitter } from '@langchain/textsplitters' // ← 递归字符切分器（LangChain 的 TS 包）

/**
 * 文档切分配置（**两端必须同参数**，见阶段 7 笔记）。
 * 作为导出常量供文档/笔记引用；修改这里必须同步 Python 侧。
 */
export const SPLITTER_CONFIG = {                                              // ← 导出常量：这是「跨实现契约」，不是随手写的默认值
  chunkSize: 500,                                                             // ← 单块最多 500 个长度单位（默认 text.length）
  chunkOverlap: 80,                                                           // ← 相邻块目标重叠 80（是上限/近似，见 §5.2）
  separators: ['\n\n', '\n', '。', '！', '？', '. ', ' ', ''],                  // ← 从「最想切」到「最不想切」；最后的 '' 是逐字符兜底
  keepSeparator: true,                                                        // ← 分隔符保留在块内，避免句号/换行被吞掉
} as const                                                                    // ← as const：字面量只读类型，防止运行期被意外改写

/** 按 `SPLITTER_CONFIG` 把文本切成若干块（保持原顺序）。 */
export async function splitText(text: string): Promise<string[]> {            // ← 返回 Promise：TS 版 splitText 是 async
  const splitter = new RecursiveCharacterTextSplitter({                       // ← 每调用一次构造一个切分器（无状态，可在并发请求里各自持有）
    chunkSize: SPLITTER_CONFIG.chunkSize,                                     // ← 展开成具体字段：构造函数只认 chunkSize/chunkOverlap
    chunkOverlap: SPLITTER_CONFIG.chunkOverlap,
    separators: [...SPLITTER_CONFIG.separators],                              // ← 必须复制：as const 给的是 readonly 元组，这里要可变 string[]
    keepSeparator: SPLITTER_CONFIG.keepSeparator,
  })
  return splitter.splitText(text)                                             // ← 输出 string[]，顺序与原文一致；不返回 start/end 位置
}
```

**这段在干什么**（按执行顺序）：

1. 从 `@langchain/textsplitters` 引入递归切分器（注意：不是 `langchain/text_splitter`，那是 Python 的旧路径）。
2. 把四个参数集中成 `SPLITTER_CONFIG` 并导出，使它能被测试和笔记直接引用；`as const` 让 `separators` 成为只读元组。
3. `splitText` 每次调用都 `new` 一个切分器：切分器内部只读这几个参数，不持有跨请求状态，所以并发上传互不影响。
4. 用 `[...]` 复制分隔符数组，因为构造函数要求可变的 `string[]`，而 `as const` 推断出的是 `readonly ['\n\n', ...]`。
5. 调 `splitText(text)`，得到块数组。它**不做**去空白块、不落库、不嵌入——纯粹「文本进、字符串数组出」。

```python
# 完整文件路径：apps/api-py/app/rag/splitter.py（去掉模块顶部注释后的逐行版）
from langchain_text_splitters import RecursiveCharacterTextSplitter  # ← 同一个算法，Python 的独立发行包

SPLITTER_CONFIG = {                                                  # ← 与 TS 的 SPLITTER_CONFIG 一一对应（键名改成 snake_case）

    "keep_separator": True,                                          # ← TS: keepSeparator
}


def split_text(text: str) -> list[str]:                              # ← 同步函数：Python 版 split_text 不是 async
    """按 `SPLITTER_CONFIG` 把文本切成若干块（保持原顺序）。"""
    splitter = RecursiveCharacterTextSplitter(**SPLITTER_CONFIG)     # ← ** 展开字典：键必须与构造参数名完全一致
    return splitter.split_text(text)                                 # ← 返回 list[str]，顺序与原文一致
```

**这段在干什么**：

1. 从 `langchain_text_splitters` 引入同名类（Python 侧从 LangChain 主包里拆出来的独立包）。
2. 配置字典用 snake_case 命名，四个键与 TS 完全对应；`**SPLITTER_CONFIG` 直接把字典当关键字参数传入，**键名拼错会在构造时立刻 `TypeError`**（不会静默用默认值）。
3. `split_text` 是普通同步函数；FastAPI 的 `upload_document` 是 `async`，调用它时直接 `for` 遍历（切分是纯 CPU、毫秒级，不需要线程池）。
4. 返回 `list[str]`，后续 `if chunk.strip() != ""` 过滤空白块。

**两端逐字节相同的「算法级」证据**（读安装包源码得到，位置仅作参考）：

| 步骤 | TS `@langchain/textsplitters/dist/text_splitter.js` | Python `langchain_text_splitters/character.py` |
| --- | --- | --- |
| 选分隔符 | 遍历 `separators`，`text.includes(s)` 命中即选，空串直接选（169–184 行） | `re.search(escape(s), text)`，空串直接选（110–129 行） |
| 保留分隔符 | `text.split(new RegExp('(?=sep)'))`，分隔符落在**后一段开头**（25–33 行） | `re.split('(sep)', text)` 后按奇偶重组，同样落在**后一段开头**（64–88 行） |
| 大块递归 | `newSeparators` 存在则 `_splitText(s, newSeparators)`（169–206 行） | 同样逻辑（134–150 行） |
| 合并与回退 | `mergeSplits` 的 `while (total > chunkOverlap || ...)`（96–120 行） | `_merge_splits` 的 `while total > chunk_overlap or (...)`（167–209 行） |

> 结论：**实现细节不同，行为等价**。所以「同一组参数 + 同一份输入」才能得到同一串 chunk。

## 7. 【技术教学 · 首次】Embedding：文本 → 定长向量

### 7.1 它到底做了什么

`embedTexts(texts)` 对每条文本调用 provider 的 `POST /embeddings`，得到 `data[i].embedding`（一个浮点数组）。本项目要求**每条恰好 1536 个浮点数**。

```text
"退款怎么申请"  ──▶  [0.0123, -0.0456, …, 0.0789]   （1536 个数）
"7 天内可申请退款" ──▶  [0.0119, -0.0441, …, 0.0771]   ← 方向接近 → 余弦相似度高
"发票抬头怎么填"  ──▶  [0.0901,  0.0330, …, -0.0112]   ← 方向不同 → 相似度低
```

检索时 `score = 1 - cosine_distance`，所以**分数越大越相关**；`<=>` 返回的是距离（`1 - 相似度`），SQL 里按距离升序排，就是按分数降序取 topK。

### 7.2 TS：`embedding.service.ts`

**完整文件路径：`apps/api-ts/src/rag/embedding.service.ts`**

```ts
// 完整文件路径：apps/api-ts/src/rag/embedding.service.ts
import { OpenAIEmbeddings } from '@langchain/openai'   // ← LangChain 对 OpenAI /v1/embeddings 的封装

import { RunError } from '../engine/events'            // ← 复用引擎的 RunError：同一条规范文案在 JSON 接口和 SSE 里都能用

/** 向量维度**固定 1536**：必须与 `chunks.embedding vector(1536)` 及 HNSW 索引一致。 */
export const EMBEDDING_DIMENSIONS = 1536               // ← 硬契约：改这里必须同时改迁移、索引、schema 与 Python 侧

/** 默认嵌入模型（可用环境变量 `EMBEDDING_MODEL` 覆盖）。 */
const DEFAULT_EMBEDDING_MODEL = 'text-embedding-3-small'  // ← OpenAI 的 1536 维默认模型

export async function embedTexts(texts: string[]): Promise<number[][]> {   // ← 批量入口：一次可传多条
  if (texts.length === 0) {                                                // ← 空数组直接返回，避免发一次无意义请求
    return []
  }
  const apiKey = process.env.LLM_API_KEY ?? ''                             // ← 复用 LLM 的密钥（不单独引入 EMBEDDING_API_KEY）
  if (apiKey === '') {                                                     // ← 未配置时给**契约文案**，不是库的原始报错
    throw new RunError('embedding provider not configured: LLM_API_KEY')
  }

  const client = new OpenAIEmbeddings({                                    // ← 构造客户端（每次调用新建，参数来自环境变量）
    apiKey,                                                                // ← 顶层 apiKey
    model: process.env.EMBEDDING_MODEL ?? DEFAULT_EMBEDDING_MODEL,         // ← 模型名可由 EMBEDDING_MODEL 覆盖
    configuration: {                                                       // ← ⚠️ baseURL / maxRetries 必须放在 configuration 里（SDK 选项）
      baseURL: process.env.LLM_BASE_URL ?? 'https://api.openai.com/v1',     // ← 复用 LLM 的 provider 地址（含 /v1）
      maxRetries: 0,                                                       // ← 与阶段 5 对齐：不重试，快速失败
    },
    timeout: Number(process.env.LLM_TIMEOUT_MS ?? 60000),                  // ← 顶层 timeout，单位**毫秒**
  })

  let vectors: number[][]                                                  // ← 先声明，便于把 try 的范围压到最小
  try {
    vectors = await client.embedDocuments(texts)                           // ← 真正发请求：内部按 batchSize=512 分批
  } catch (error) {
    throw new RunError(mapEmbeddingError(error))                           // ← 任何异常 → 规范文案，绝不透出库的原始 message
  }

  for (const vector of vectors) {                                          // ← 逐条校验（不是只看第一条）
    if (!Array.isArray(vector) || vector.length !== EMBEDDING_DIMENSIONS) { // ← 必须恰好 1536
      // eslint-disable-next-line no-console
      console.error(                                                       // ← 只在服务端日志里保留诊断信息
        `embedding dimension mismatch: expected ${EMBEDDING_DIMENSIONS}, got ${Array.isArray(vector) ? vector.length : 'non-array'}; ` +
          `check EMBEDDING_MODEL / provider output (vector(1536) is fixed in migrations)`,
      )
      throw new RunError('embedding request failed: unknown')              // ← 对外仍是规范文案：unknown
    }
  }
  return vectors                                                           // ← 顺序与入参 texts 一一对应
}
```

**这段在干什么**：

1. 空数组短路：上传空文档时上层已经拦了，但检索/节点调用也可能传空，函数自己也要安全。
2. 从 `LLM_API_KEY` 取密钥；没有就抛**契约文案** `embedding provider not configured: LLM_API_KEY`（`error-messages.md` §7.3 第一条）。
3. 新建 `OpenAIEmbeddings`：`apiKey`、`model` 在顶层；`baseURL` / `maxRetries` 在 `configuration` 里（这是 JS SDK 的嵌套结构）；`timeout` 在顶层且单位是毫秒。
4. `embedDocuments(texts)` 发批量请求；内部把文本按 `batchSize=512` 分批，每批一个 HTTP 请求。
5. 捕获一切异常，用 `mapEmbeddingError` 归一（HTTP 状态码优先 → 超时 → `unknown`）。
6. 逐条检查维度；不合规时先写一行 `console.error` 便于排障，再抛 `unknown`。
7. 返回与入参同序的二维数组。

### 7.3 Python：`embedding.py`

**完整文件路径：`apps/api-py/app/rag/embedding.py`**

```python
# 完整文件路径：apps/api-py/app/rag/embedding.py（去掉模块顶部注释后的逐行版）
from langchain_openai import OpenAIEmbeddings          # ← TS: @langchain/openai 的 OpenAIEmbeddings

from app.config import settings                        # ← 配置统一走 Settings（pydantic-settings 读 .env）
from app.engine.events import RunError                 # ← 同一个 RunError，保证文案一致

EMBEDDING_DIMENSIONS = 1536                            # ← 与 TS / 迁移 / HNSW 完全一致
DEFAULT_EMBEDDING_MODEL = "text-embedding-3-small"     # ← 默认模型


async def embed_texts(texts: list[str]) -> list[list[float]]:   # ← 异步入口（调用方 await）
    """批量文本向量化；失败抛 `RunError`（规范文案见 error-messages.md §7.3）。"""
    if not texts:                                                # ← 空列表短路（Python 的空列表为假）
        return []
    api_key = settings.llm_api_key                               # ← 经 Settings 读取，不直接读 os.environ
    if not api_key:                                              # ← 空串同样视为未配置
        raise RunError("embedding provider not configured: LLM_API_KEY")

    client = OpenAIEmbeddings(                                   # ← 构造客户端
        api_key=api_key,
        model=settings.embedding_model or DEFAULT_EMBEDDING_MODEL,  # ← 空串时回退默认模型
        base_url=settings.llm_base_url,                          # ← Python 侧是**顶层** base_url（跟 TS 的嵌套不同）
        timeout=settings.llm_timeout_ms / 1000,                  # ← ⚠️ 单位是**秒**：毫秒配置要 /1000
        max_retries=0,                                           # ← 与 TS 的 maxRetries: 0 对齐
        check_embedding_ctx_length=False,                        # ← 关键：不做 tiktoken 本地分词，直接发原文
    )

    try:
        vectors = await client.aembed_documents(texts)           # ← 异步批量请求（a 前缀 = async）
    except Exception as error:  # noqa: BLE001 - 任何嵌入错误都归一为规范文案
        raise RunError(map_embedding_error(error)) from error    # ← from：保留底层异常因果链

    for vector in vectors:                                       # ← 逐条校验
        if not isinstance(vector, list) or len(vector) != EMBEDDING_DIMENSIONS:
            # 维度不符时按 unknown 处理（与 api-ts 一致）
            raise RunError("embedding request failed: unknown")
    return vectors
```

**这段在干什么**：

1. `if not texts` 短路空列表。
2. **经 `settings.llm_api_key` 读配置**——不能直接 `os.environ.get("LLM_API_KEY")`：pydantic-settings 只把 `.env` 读进 `Settings`，不回写进程环境（阶段 6 的已知遗留）。
3. 构造 `OpenAIEmbeddings`：`base_url` / `max_retries` 是**顶层**参数；`timeout` 是**秒**，所以毫秒配置除以 1000。
4. `check_embedding_ctx_length=False`：关掉 tiktoken 本地分词（§11.5）。
5. `await aembed_documents(texts)` 发异步请求；异常统一转 `RunError`。
6. 逐条校验维度；不合规直接抛 `unknown`（Python 侧不额外打日志，保持与 TS 的对外行为一致）。
7. 返回 `list[list[float]]`，顺序与入参一致。

### 7.4 维度校验：为什么是两层

**第一层（应用层）**：两端的循环检查，失败 → `embedding request failed: unknown`。

**第二层（数据库）**：`chunks.embedding` 是 `vector(1536)`。即使应用层检查被绕过，`INSERT` 也会被 pgvector 拒绝：

```text
ERROR:  expected 1536 dimensions, not 1024
```

**为什么宁可失败也不写入错误维度**：

- 向量空间维度不同，**余弦相似度没有定义**；混进去的 1024 维向量要么插入报错，要么（如果列改成无维度 `vector`）在 `<=>` 时直接报错。
- 维度错误往往意味着「模型换了但迁移没做」。此时**静默补零/截断**会得到一个语法上合法、语义上完全错误的向量，检索结果看起来「能跑」，实际全是噪声——这比直接失败危险得多。
- 失败发生在写库之前，数据库里不会留下半成品文档（§3.1）。

### 7.5 批处理：一次请求多条文本

两端都支持 `input: string[]`：

- TS：`embedDocuments(texts)` → 按 `batchSize = 512` 分批，每批 `{ model, input: batch }`；
- Python：`aembed_documents(texts)` → `chunk_size = 1000` 条一批，并且还受单请求 token 上限约束（`MAX_TOKENS_PER_REQUEST`），超了就再拆。

本项目的文档切出来一般 1–10 块，**一次 HTTP 往返就够了**。好处：减少连接建立与 TLS 开销、降低限流概率；坏处：单条超长文本会拖慢整批，所以先切分再嵌入（顺序不能反）。

### 7.6 错误映射的归属

`mapEmbeddingError` / `map_embedding_error` 的规则与阶段 5 的 `mapLlmError` 完全同构，只是前缀换成 `embedding`。**本篇不重讲**规则本身，见 `05-LLM节点/03-LLM错误映射.md`；文案表见 `packages/contract/error-messages.md` §7.3。

两端各有一个「取状态码」的差异点：

| 关注点 | TS | Python |
| --- | --- | --- |
| 状态码字段 | `error.status`（OpenAI JS SDK 的 `APIError`） | `error.status_code`，再退 `error.status` |
| 超时判定 | `name` 为 `APIConnectionTimeoutError` / `TimeoutError` / `AbortError`，或 message 匹配 `timeout` | 类名为 `APITimeoutError` / `TimeoutError` / `APIConnectionTimeoutError`，或消息含 `timeout` |

### 8.1 TS：`kb.service.ts` 的 `upload`

**完整文件路径：`apps/api-ts/src/rag/kb.service.ts`（`upload` 方法，行 95–151）**

```ts
// 完整文件路径：apps/api-ts/src/rag/kb.service.ts
  /**
   * 上传并处理：校验类型/大小/空 → 切分 → 批量嵌入 → 事务写 `documents` + `chunks` → 更新 `chunkCount`。
   *
   * 嵌入失败（含未配置密钥）映射为 400 规范文案（见 error-messages.md §7）。
   */
  async upload(
    ownerId: string,
    knowledgeBaseId: string,
    file: UploadedDocument | undefined,
  ): Promise<DocumentResponse> {
    await this.findOwned(ownerId, knowledgeBaseId)                        // ← ① 归属校验：不是自己的 → 404
    if (file === undefined) {                                             // ← ② 没带 file 字段
      throw new BadRequestException('Document is empty')
    }
    const mimeType = file.mimetype && file.mimetype !== '' ? file.mimetype : 'application/octet-stream'  // ← 缺省 MIME
    if (!isSupportedDocument(file.originalname, mimeType)) {               // ← 扩展名 .txt/.md/.markdown 或 text/*
      throw new BadRequestException(`Unsupported document type: ${mimeType}`)
    }
    if (file.size > MAX_DOCUMENT_BYTES) {                                 // ← 1MB 上限（控制器 multer 已挡一层）
      throw new BadRequestException('Document too large')
    }
    const content = file.buffer.toString('utf8')                          // ← ③ 字节 → 文本；非法字节替换为 U+FFFD
    if (content.trim() === '') {                                          // ← 全是空白也算空文档
      throw new BadRequestException('Document is empty')
    }

    const chunks = (await splitText(content)).filter((chunk) => chunk.trim() !== '')  // ← ④ 切分并丢弃纯空白块
    if (chunks.length === 0) {
      throw new BadRequestException('Document is empty')
    }
    const vectors = await embedOrBadRequest(chunks)                       // ← ⑤ 批量嵌入；失败 → 400 规范文案

    const documentId = randomUUID()                                       // ← 先定 id，后续 chunk 行才能引用
    await this.prisma.$transaction(async (tx) => {                        // ← ⑥ 文档 + 全部 chunk 在一个事务里
      await tx.document.create({
        data: {
          id: documentId,
          knowledgeBaseId,
          name: file.originalname,
          mimeType,
          sizeBytes: file.size,
          status: 'ready',                                                // ← 同步处理完成即为 ready（没有异步队列）
        },
      })
      for (let index = 0; index < chunks.length; index += 1) {            // ← 按原顺序逐块插入
        // 向量写入只能走原生 SQL（Prisma 不支持 vector 类型）；字符串字面量再 ::vector。
        await tx.$executeRaw`
          INSERT INTO chunks (id, document_id, knowledge_base_id, chunk_index, content, embedding, created_at)
          VALUES (${randomUUID()}, ${documentId}, ${knowledgeBaseId}, ${index}, ${chunks[index]}, ${toVectorLiteral(vectors[index])}::vector, now())
        `
      }
      await tx.document.update({ where: { id: documentId }, data: { chunkCount: chunks.length } })  // ← ⑦ 回填块数
    })

    const document = await this.prisma.document.findUniqueOrThrow({ where: { id: documentId } })   // ← 取回完整行做映射
    return toDocumentResponse(document)
  }
```

**这段在干什么**（按执行顺序）：

1. `findOwned` 先查知识库归属；不存在或不属于当前用户一律 404（与 `/apps` 同一惯例）。
2. 校验 `file` 存在、类型受支持（扩展名优先，其次 `content-type: text/*`）、大小 ≤ 1MB。
3. `buffer.toString('utf8')` 把 multipart 的原始字节解码；`trim()` 为空则 400。
4. 切分，并**过滤纯空白块**——这一步必须两端一致，否则 `chunk_index` 会错位。
5. 批量嵌入；`embedOrBadRequest` 把 `RunError` 的规范文案转成 `BadRequestException`（普通 JSON 接口用 400，而不是 SSE 的 `run_failed`）。
6. 开事务：插 `documents` → 逐块原生 `INSERT`（`toVectorLiteral(...)::vector`）→ 更新 `chunkCount`。
7. 事务提交后重新查一次文档行，映射成契约里的 `DocumentResponse` 返回。

**为什么嵌入在事务外**：嵌入可能要几百毫秒到几秒。若先开事务再嵌入，会长时间占用连接/锁；更重要的是，嵌入失败时事务里已经有文档行，回滚虽然能兜住，但不如「先算完再写」干净。

### 8.2 Python：`service.py` 的 `upload_document`

**完整文件路径：`apps/api-py/app/rag/service.py`（`upload_document`，行 100–165）**

```python
# 完整文件路径：apps/api-py/app/rag/service.py
async def upload_document(
    db: Session, owner_id: str, kb_id: str, file: UploadFile | None
) -> dict[str, Any]:
    """上传并处理：校验类型/大小/空 → 切分 → 批量嵌入 → 写 documents + chunks → 更新 chunkCount。"""
    _find_owned(db, owner_id, kb_id)                                  # ← ① 归属校验（404）
    if file is None:                                                  # ← ② 没带文件
        raise _bad_request("Document is empty")

    filename = file.filename or ""                                    # ← 文件名可能为 None
    mime_type = file.content_type or ""                               # ← content_type 也可能为空
    if mime_type == "":
        mime_type = "application/octet-stream"                        # ← 与 TS 的缺省值一致
    if not _is_supported_document(filename, mime_type):               # ← 扩展名或 text/* 才放行
        raise _bad_request(f"Unsupported document type: {mime_type}")

    raw = await file.read()                                           # ← 异步读入全部字节
    size_bytes = len(raw)                                             # ← ★ 用实际字节数，而不是 UploadFile.size（可能为 None）
    if size_bytes > MAX_DOCUMENT_BYTES:                               # ← 1MB
        raise _bad_request("Document too large")

    # Node 的 buffer.toString('utf8') 对非法字节用 U+FFFD 替换；Python 用 errors="replace" 对齐
    content = raw.decode("utf-8", errors="replace")                   # ← ③ 同一套解码规则
    if content.strip() == "":                                         # ← 全空白 → 400
        raise _bad_request("Document is empty")

    chunks = [chunk for chunk in split_text(content) if chunk.strip() != ""]  # ← ④ 切分 + 过滤空白块（与 TS 同序）
    if not chunks:
        raise _bad_request("Document is empty")
    vectors = await _embed_or_bad_request(chunks)                     # ← ⑤ 批量嵌入；RunError → 400

    document_id = str(uuid.uuid4())                                   # ← 先定 id
    document = Document(                                              # ← 构造 ORM 对象
        id=document_id,
        knowledge_base_id=kb_id,
        name=filename,
        mime_type=mime_type,
        size_bytes=size_bytes,                                        # ← 与 TS 的 file.size 同口径（字节）
        status="ready",
        chunk_count=0,                                                # ← 先 0，插完块再回填
    )
    db.add(document)
    db.flush()                                                        # ← flush 发出 INSERT，但**不提交**；拿得到行、可被后续 SQL 引用

    insert_sql = text(                                                # ← 预编译一次 SQL，循环里复用
        """
        INSERT INTO chunks (id, document_id, knowledge_base_id, chunk_index, content, embedding, created_at)
        VALUES (:id, :document_id, :knowledge_base_id, :chunk_index, :content,
                CAST(:embedding AS vector), now())
        """
    )
    for index, chunk in enumerate(chunks):                            # ← 按原顺序逐块插入
        db.execute(
            insert_sql,
            {
                "id": str(uuid.uuid4()),
                "document_id": document_id,
                "knowledge_base_id": kb_id,
                "chunk_index": index,
                "content": chunk,
                "embedding": to_vector_literal(vectors[index]),      # ← 字符串字面量，再由 CAST 转 vector
            },
        )
    document.chunk_count = len(chunks)                                # ← ⑦ 回填块数（ORM 会在 commit 时 UPDATE）
    db.commit()                                                       # ← ⑥ 一次性提交文档 + 所有块
    db.refresh(document)                                              # ← 重新读回数据库生成的值
    return _to_document_response(document)
```

**这段在干什么**：

1. `_find_owned` 查归属（连文档数一起查），不符 → 404。
2. `filename` / `content_type` 可能为 `None`，统一兜底成空串 / `application/octet-stream`。
3. `await file.read()` 读全量字节；`size_bytes = len(raw)` 用**实际字节数**，与 TS 的 `file.size` 同口径。
4. `decode("utf-8", errors="replace")` 与 Node 的 `toString('utf8')` 行为对齐（非法字节 → U+FFFD）。
5. 切分、过滤空白块、批量嵌入；`_embed_or_bad_request` 把 `RunError` 转 400。
6. `db.add` + `db.flush`（不提交）→ 循环执行同一条参数化 `INSERT`（`CAST(:embedding AS vector)`）→ 回填 `chunk_count` → `db.commit()`。
7. `db.refresh` 取回数据库默认值后映射返回。

**事务语义对照**：

| 关注点 | TS（Prisma） | Python（SQLAlchemy） |
| --- | --- | --- |
| 事务边界 | `this.prisma.$transaction(async (tx) => …)` 显式包裹 | `Session` 隐含事务，`commit()` 收尾 |
| 先拿 id | 业务层 `randomUUID()` | 业务层 `str(uuid.uuid4())` |
| 中间态 | 事务内不可见 | `flush()` 后本会话可见、其他会话不可见 |
| 失败回滚 | 回调抛错自动回滚 | 未 `commit` 时 `close()` 回滚；异常路径由 `get_db` 兜底 |

### 8.3 向量字面量与存储精度

两端都把向量拼成 `[0.1,0.2,...]` 文本，再转成 `vector`：

```ts
// apps/api-ts/src/rag/kb.service.ts
export function toVectorLiteral(vector: number[]): string {
  return `[${vector.join(',')}]`      // ← JS 数字的「最短往返」字符串
}
```

```python
# apps/api-py/app/rag/service.py
def to_vector_literal(vector: list[float]) -> str:
    return "[" + ",".join(str(value) for value in vector) + "]"   # ← Python str(float)
```

两边的字符串**不保证逐字符相同**（例如 `0.0` 在 JS 里是 `"0"`、Python 里是 `"0.0"`；极小值可能一个用 `1e-05`、一个用 `0.00001`）。但 pgvector 解析后写入的是 **float4**（单精度），这些差异在存储时就被抹平；再加上同一份文本、同一个 mock 算法，最终列里的向量逐位相同。**不要**为了「字面量一致」去手写格式化——真正要保证的是数值一致。

## 9. 【技术教学 · 首次】mock 的哈希向量器

### 9.1 为什么需要它

验收需要回答一个问题：**「切分 → 向量 → 存储 → 检索 → 排序」这条管道是否两端一致？** 如果依赖真实 OpenAI embedding：

- 需要密钥与网络；
- 同一文本的向量可能随模型版本微调；
- 浮点结果难以逐位比对，验收只能写成「大致相近」。

mock 的做法是**用文本本身确定性构造一个向量**：同样的文本永远得到同样的 1536 个数，不需要密钥，可以离线跑，分数还能精确比对。代价是它**不懂语义**（§9.6）。

### 9.2 分词：空白分词 + CJK 逐字

**完整文件路径：`tools/mock-llm/server.mjs`（`tokenizeForEmbedding`，行 142–168）**

```js
// 完整文件路径：tools/mock-llm/server.mjs
/** 分词：小写后按空白切词；每个 CJK 字符单独成一个 token，其余连续字符合成一个 token。 */
function tokenizeForEmbedding(text) {
  const tokens = []                              // ← 输出的 token 列表（保留重复，重复次数 = 权重）
  for (const word of text.toLowerCase().split(/\s+/)) {   // ← ① 转小写，按任意空白切词
    let buffer = ''                              // ← 积累「非 CJK 的连续字符」
    for (const char of word) {                   // ← ② 按 Unicode 码点遍历（for…of 不会拆开代理对）
      if (isCjk(char)) {                         // ← ③ 汉字/兼容表意文字
        if (buffer !== '') {                     // ← 先冲刷已攒的英文/数字
          tokens.push(buffer)
          buffer = ''
        }
        tokens.push(char)                        // ← 每个汉字单独成 token
      } else {
        buffer += char                           // ← 英文、数字、标点继续攒
      }
    }
    if (buffer !== '') {                         // ← 词尾冲刷
      tokens.push(buffer)
    }
  }
  return tokens
}

/** CJK 统一表意文字（含扩展 A 与兼容表意文字）。 */
function isCjk(char) {
  return /[\u3400-\u4dbf\u4e00-\u9fff\uf900-\ufaff]/.test(char)   // ← 四个区段，够用即可
}
```

**这段在干什么**：

1. 先 `toLowerCase()`，让大小写不影响相似度；再 `split(/\s+/)` 按空白切成「词」。
2. 对每个词逐字符扫描：遇到 CJK 字符就把缓冲区里的非 CJK 片段先推出，再把自己单独推出；非 CJK 字符持续累积。
3. 于是 `"退款怎么申请"` → `["退","款","怎","么","申","请"]`；`"refund policy"` → `["refund","policy"]`；`"退款 policy"` → `["退","款","policy"]`。

**为什么必须单独处理 CJK**：`"退款怎么申请".split(/\s+/)` 只会得到 **一个** 词——中文不靠空格分词。如果照搬英文的空白分词，整句中文会变成 1 个 token，任何两句中文只要不完全相同就毫无共享 token，检索分数全为 0，验收毫无意义。**逐字成 token** 是「够用就好」的近似：它近似的是「共享汉字越多越相似」，不是真正的语义。

### 9.3 FNV-1a：把 token 映射到桶

**完整文件路径：`tools/mock-llm/server.mjs`（`fnv1a32`，行 170–178）**

```js
// 完整文件路径：tools/mock-llm/server.mjs
/** FNV-1a 32 位哈希（返回无符号整数）。 */
function fnv1a32(text) {
  let hash = 0x811c9dc5                          // ← FNV 的 32 位 offset basis（固定初值）
  for (let index = 0; index < text.length; index += 1) {   // ← 逐 UTF-16 码元
    hash ^= text.charCodeAt(index)               // ← ① 异或当前码元
    hash = Math.imul(hash, 0x01000193) >>> 0     // ← ② 乘 FNV 质数，并强制回 32 位无符号
  }
  return hash >>> 0                              // ← ③ 保证返回值在 [0, 2^32)
}
```

**这段在干什么**：

1. 以固定初值 `0x811c9dc5` 开始。
2. 每个码元先异或进 `hash`，再乘以质数 `0x01000193`。
3. `Math.imul` 保证是 **32 位整数乘法**（普通 `*` 会溢出到 2^53 以上，低位丢失）；`>>> 0` 把有符号结果转回无符号。
4. 返回稳定的 32 位无符号整数：同一个 token 永远得到同一个值。

> **为什么不用 `hash * prime`**：JS 的 `Number` 是双精度浮点，`0x811c9dc5 * 0x01000193 ≈ 2.2e16` 已超过 2^53，低位会被舍入，导致哈希不稳定且与标准 FNV 不一致。这是 mock 实现里最容易写错的一行。

### 9.4 桶累加 + L2 归一化

**完整文件路径：`tools/mock-llm/server.mjs`（`hashVector`，行 180–195）**

```js
// 完整文件路径：tools/mock-llm/server.mjs
/** 词袋哈希向量 + L2 归一化；无 token 时返回全 0 向量。 */
function hashVector(tokens) {
  const vector = new Array(EMBEDDING_DIMENSIONS).fill(0)   // ← 1536 个桶，初值 0
  for (const token of tokens) {
    vector[fnv1a32(token) % EMBEDDING_DIMENSIONS] += 1     // ← ① 哈希取模定位桶，计数 +1
  }
  let squareSum = 0
  for (const value of vector) {
    squareSum += value * value                             // ← ② 平方和
  }
  const norm = Math.sqrt(squareSum)                        // ← ③ L2 范数
  if (norm === 0) {                                        // ← ④ 无 token（空串/纯空白）→ 全 0
    return vector
  }
  return vector.map((value) => value / norm)               // ← ⑤ 每个分量除以范数，长度变 1
}
```

**这段在干什么**：

1. 建 1536 维全 0 数组。
2. 每个 token 经 FNV-1a 后对 1536 取模，落到一个桶，计数 +1（**词袋模型**：只看出现次数，不看顺序）。
3. 求平方和 → 开方得范数。
4. 范数为 0（没有任何 token）直接返回全 0，避免除零。
5. 所有分量除以范数，得到单位向量。

**为什么要归一化**：不归一化时，长文本 token 多、分量大，点积天然更大，余弦相似度会被「长度」污染。归一化后 `cos(a,b) = a · b`，只反映方向（词的分布），不反映文本长短。

### 9.5 为什么「共享词越多 → 余弦相似度越高」

设 query 的 token 多重集为 `Q`、chunk 的为 `C`，两边的计数向量为 `v_Q`、`v_C`（归一化后）：

```text
cos(v_Q, v_C) = Σ_bucket (v_Q[bucket] × v_C[bucket])
              = Σ_token (count_Q(token) × count_C(token)) / (|Q|·|C|)
```

分子只在**两边都出现的 token（含哈希碰撞）**上非零。所以：

- 共享的汉字/词越多，分子越大 → 分数越高；
- 两篇毫无共享字符的文档，分数接近 0；
- 所有分量非负，所以分数落在 `[0,1]`。

这正好让验收「有意义」：`query = "退款怎么申请"` 与 `refund.txt` 的块共享「退、款、申、请」，分数 0.588；与 `invoice.txt` 的块只共享很少的字，分数 0.133。**命中顺序是可解释的，不是碰运气。**

**如果换成随机向量会怎样**：随机向量与文本无关，任意两段的期望余弦都≈0、方差却很大；topK 顺序由噪声决定，每次运行（若用时间做种子）还可能不同。这样「两端 score 相同」即使成立也毫无意义——它只证明了两边都调用了随机数生成器。哈希向量器把「文本 → 向量」变成**纯函数**，才让逐字节/全精度比对成为有效验收。

### 9.6 它的边界：不是语义向量

- 同义不同字（「退款」vs「退钱」）**不会**相似；
- 哈希碰撞会把无关 token 混进同一个桶（1536 个桶，碰撞率可接受，但确实是噪声）；
- 只有字面重叠能被衡量。

所以它只用于**管道验收与无密钥自测**；生产环境应把 `EMBEDDING_MODEL` 换成真实模型（并保持维度 1536，如 `text-embedding-3-small`）。**换模型不需要改切分参数**，但必须确认输出维度；维度不符会被 §7.4 的两层防护拦下。

### 9.7 `/v1/embeddings` 的请求/响应形状

**完整文件路径：`tools/mock-llm/server.mjs`（`handleEmbeddings`，行 116–140）**

```js
// 完整文件路径：tools/mock-llm/server.mjs
/** 嵌入维度：**必须与 Prisma 迁移里的 `chunks.embedding vector(1536)` 一致**。 */
const EMBEDDING_DIMENSIONS = 1536                                // ← 与两端常量同值

function handleEmbeddings(res, payload) {
  const inputs = Array.isArray(payload.input) ? payload.input : [payload.input ?? '']  // ← 兼容 string 与 string[]
  const model = payload.model || 'mock-embedding'                // ← 原样回显模型名
  let promptTokens = 0
  const data = inputs.map((text, index) => {
    const tokens = tokenizeForEmbedding(String(text))            // ← 分词
    promptTokens += tokens.length                                // ← usage 用 token 数
    return { object: 'embedding', index, embedding: hashVector(tokens) }  // ← 顺序与 input 一致
  })
  return sendJson(res, 200, {
    object: 'list',
    data,
    model,
    usage: { prompt_tokens: promptTokens, total_tokens: promptTokens },
  })
}
```

**这段在干什么**：

1. `input` 既接受单条字符串，也接受数组（OpenAI 两种都支持；两端批量调用传数组）。
2. 逐条分词、构造 1536 维向量，`index` 保持与输入同序。
3. 返回 OpenAI 兼容的 `{ object: "list", data: [...], model, usage }`；客户端只关心 `data[i].embedding`。
4. `model` 原样回显，所以 `EMBEDDING_MODEL=mock-embedding` 也能「正常」工作——这正是检验 Python 侧 `check_embedding_ctx_length=False` 的场景。

## 10. 【加厚】与 TS 侧的对照

> 本篇同时覆盖两端，这一节讲**差异**本身，不只列名字。

| 关注点 | TS（`@langchain/textsplitters` / `@langchain/openai`） | Python（`langchain-text-splitters` / `langchain-openai`） | 机制差异与影响 |
| --- | --- | --- | --- |
| 切分类 | `RecursiveCharacterTextSplitter` | 同名类 | 算法同构，实现不同（前瞻 vs 捕获组），输出相同 |
| 参数命名 | `chunkSize` / `chunkOverlap` / `keepSeparator` | `chunk_size` / `chunk_overlap` / `keep_separator` | 只是命名；配置文件必须逐键同步 |
| 长度函数 | 默认 `text.length` → **UTF-16 码元** | 默认 `len(str)` → **码点** | BMP 汉字相同；emoji 会不同（§12.6） |
| `chunkOverlap` 边界 | `chunkOverlap >= chunkSize` 抛 `Cannot have chunkOverlap >= chunkSize` | 只在 `chunk_overlap > chunk_size` 抛错 | **相等时 Python 不报错**，行为还会退化；这是真实的不对称（§12.2） |
| 分隔符保留 | 正则前瞻 `(?=sep)`，分隔符落在后段开头 | 捕获组切分后按奇偶重组，同样落在后段开头 | 结果一致，代码完全两套 |
| 切分同步/异步 | `splitText` 返回 `Promise` | `split_text` 同步返回 | TS 必须 `await`；Python 直接 `for` |
| 嵌入类构造 | `new OpenAIEmbeddings({ apiKey, model, configuration: { baseURL, maxRetries }, timeout })` | `OpenAIEmbeddings(api_key=…, model=…, base_url=…, max_retries=0, timeout=…, check_embedding_ctx_length=False)` | `baseURL`/`maxRetries` 在 TS 是**嵌套**的 `configuration`；Python 是**顶层**参数 |
| 超时单位 | 毫秒 | **秒** | Python 必须 `/1000`；写成 `60000` 会等 16 小时 |
| 本地分词 | 不做（JS 版始终发原文） | 默认用 tiktoken 分词，**必须关** | 见 §11.5；这是两端最大的行为不对称 |
| 换行处理 | **默认 `stripNewLines = true`**：`\n` → 空格 | 默认不改（仅模型名以 `001` 结尾时才替换） | 真实模型下向量可能有细微差异；mock 按空白分词，结果不变（§12.6） |
| 批大小 | `batchSize = 512` 条/请求 | `chunk_size = 1000` 条/批，还受 token 上限约束 | 小批量上传都是一次请求 |
| 状态码来源 | `error.status` | `error.status_code`（再退 `status`） | 都要兼容 SDK 的异常形状 |
| 写入事务 | `$transaction` 回调 | `Session` + `flush` + `commit` | 语义等价，失败都不留半成品 |
| 向量字面量 | `vector.join(',')` | `str(value)` 拼接 | 文本可能不同，pgvector 解析成 float4 后相同 |

### 10.1 三个值得记住的「不对称」

**① `check_embedding_ctx_length` 只存在于 Python。** JS 版 `embedDocuments` 只做两件事：`stripNewLines` 与分批，然后 `input: batch` 直接发原文。Python 版默认会用 tiktoken 把文本变成 token 数组。所以「同一份文本、同一个 provider」在两端发出去的**请求体可能不同**。本项目靠关掉这个开关来对齐。

**② `stripNewLines` 只存在于 TS，且默认为 `true`。** `apps/api-ts` 的 `embedTexts` 没有显式设置它，因此上传时 chunk 里的 `\n\n` 会被替换成空格再发给 provider。Python 侧不改换行。对 mock 没影响（它按空白分词，换行和空格都是分隔符），对真实模型则可能产生微小差异。**注意：query 是单行文本，两端都不受影响，所以检索排序仍稳定。**

**③ overlap 的边界校验不等价。** 见上表与 §12.2。写文档/写测试时不要假设「两边都会拒绝 `overlap == size`」。

## 11. 【加厚】本篇首次出现的机制

### 11.1 `RecursiveCharacterTextSplitter` 的递归与 `keepSeparator`

**是什么**：一个「按分隔符优先级递归切分」的切分器。它先找最想切的分隔符把文本切开；对仍然超长的小片，用剩下的分隔符继续递归；对不超长的小片，尽量合并成接近 `chunkSize` 的块。

**TS 里对应什么**：`@langchain/textsplitters` 的同名类。`keepSeparator=true` 时用 `split(/(?=sep)/)`（前瞻），分隔符留在后一段开头。

**这里为什么这么写**：

- 中文没有空格分词，必须先按段落/句子切；直接按字符切会让每块都是半句话。
- `keepSeparator: true` 保证块里保留 `。`、`\n` 等，拼回去仍是原文（不会丢标点）；这也让「检索结果直接展示给用户」时更好读。
- 最后的 `''` 是**兜底**：没有它，一段没有任何分隔符的超长文本会被整段保留，可能远超 `chunkSize`。
- 顺序即优先级：`'\n\n'` 在 `'\n'` 前，保证优先在段落边界断，而不是先断行。

### 11.2 `chunkOverlap` 的「回退窗口」

**是什么**：`merge_splits` 在落盘一块后，从队头弹出分片，直到剩余长度 ≤ `chunkOverlap`；这些剩余分片就是下一块的开头。

**TS 里对应什么**：

```js
// @langchain/textsplitters/dist/text_splitter.js（mergeSplits）
while (total > this.chunkOverlap ||
       total + _len + currentDoc.length * separator.length > this.chunkSize && total > 0) {
  total -= await this.lengthFunction(currentDoc[0])
  currentDoc.shift()
}
```

Python 的 `base.py` 是同一逻辑（多减一个分隔符长度，本项目分隔符为 `""`，故为 0）。

**这里为什么这么写（也是你必须知道的限制）**：

- 回退单位是**整个分片**，不是字符。所以 `chunkOverlap` 是「目标上限」，不是「精确值」。
- 若下一片本身就很大（例如一整段 300 字），为了让下一块不超过 `chunkSize`，可能把回退窗口清空 → 实际重叠为 0。
- 本项目按 `。` 切分，中文句子通常 20–50 字，`overlap=80` 大致能带回 2–3 句，符合「不让句子失去上下文」的目标。

### 11.3 `OpenAIEmbeddings` 的 `configuration` 嵌套 vs 顶层参数

**是什么**：`@langchain/openai` 的 JS 客户端把「OpenAI SDK 的构造选项」放在 `configuration` 下（`baseURL`、`maxRetries`、`organization` 等），把 LangChain 自己的选项放在顶层（`model`、`timeout`、`batchSize`、`dimensions`）。

**TS 里对应什么**：就是本篇的 `embedding.service.ts`：`configuration: { baseURL, maxRetries: 0 }`。

**这里为什么这么写**：

- 把 `baseURL` 写在顶层不会报错，但会被忽略——客户端仍连 `api.openai.com`，mock 永远收不到请求。这是「配置漂移」型 bug，症状是「明明配了 LLM_BASE_URL，却还是请求 OpenAI」。
- Python 侧恰好相反：`base_url` / `max_retries` 是顶层。**照抄另一边的写法必错**。

### 11.4 `maxRetries: 0` 与超时单位

**是什么**：`maxRetries` 控制 SDK 对可重试错误（429/5xx/连接错误）的自动重试次数；`timeout` 控制单次请求超时。

**TS 里对应什么**：`configuration.maxRetries = 0`；`timeout`（毫秒）在顶层。Python：`max_retries=0` 顶层；`timeout` 单位为**秒**。

**这里为什么这么写**：

- 与阶段 5 的 LLM 调用保持一致：**快速失败**，把错误立刻归一成契约文案（`embedding request timed out` / `embedding request failed: 500`），而不是让上传请求挂几分钟。
- 上传是同步接口，长时间挂起对用户体验最差；重试交给调用方（或后续异步任务），不在请求内偷偷重试。
- 单位错误很隐蔽：Python 写 `timeout=60000` 不会报错，只是几乎永不超时；TS 写 `timeout=60` 则是 60 毫秒，几乎必超时。

### 11.5 `check_embedding_ctx_length=False`

**是什么**：`langchain-openai` Python 的布尔开关，默认 `True`。为 `True` 时，它会用 **tiktoken** 在本地把文本切成 token id，按 `embedding_ctx_length` 分片，然后把 **token 数组**作为 `input` 发给 provider；为 `False` 时，直接把原始字符串发出去。

**TS 里对应什么**：**没有对应开关**。JS 版从不在本地分词，始终发字符串（只做 `stripNewLines`）。所以这是 Python 侧独有的「必须显式关闭」项。

**这里为什么这么写**：

- 本项目允许任何 OpenAI 兼容 provider（mock、Ollama、vLLM、各类中转）。它们通常**只接受字符串输入**，不认识 OpenAI 的 token 数组。
- tiktoken 只为 OpenAI 模型准备编码表；自定义模型名（`mock-embedding`、`bge-m3` 等）可能让 `encoding_for_model` 失败（本仓库安装的版本会回退 `cl100k_base`，但更早/其它配置下会直接抛错），也可能因为离线拉不到编码文件而失败。
- 关掉后还有一个好处：**分片逻辑回到我们手里**。我们已经按 `chunkSize=500` 切好了，不需要库再按 8191 token 二次切分（否则一个 chunk 可能被悄悄拆成多条向量，条目数对不上）。

### 11.6 维度常量与 `vector(1536)`

**是什么**：`EMBEDDING_DIMENSIONS = 1536` 是应用层常量；`chunks.embedding vector(1536)` 是数据库列；HNSW 索引也按这个维度建。

**TS 里对应什么**：`embedding.service.ts` 的导出常量；Python 侧 `embedding.py` 的同名常量；Prisma schema 里的 `Unsupported("vector(1536)")`。

**这里为什么这么写**：

- 1536 是 `text-embedding-3-small` 的默认维度，也是本项目唯一写进迁移的维度。
- 改维度不是「改一个常量」：要改迁移（`ALTER COLUMN ... TYPE vector(N)`）、重算所有向量、重建 HNSW 索引。schema 注释已经写明这一点。
- 应用层检查的作用不是「防 provider」，而是**在写库前把错误变成契约文案**；数据库检查则是最后一道闸，防止任何绕过路径写入坏数据。

### 11.7 批量嵌入（`input: string[]`）

**是什么**：一次 HTTP 请求携带多条文本，响应按 `index` 返回多个向量。

**TS 里对应什么**：`embedDocuments(texts)` 内部 `chunkArray(texts, 512)`；Python：`aembed_documents(texts)` 内部按 `chunk_size=1000` 与 token 上限分批。

**这里为什么这么写**：

- 一篇文档 2 块、一次上传 1 篇，若逐条请求就是 2 次往返；批量后 1 次。
- 响应顺序必须与入参一致，否则 `chunks[i]` 会配错向量——两端的 `embedDocuments` 都保证这一点，所以上传代码可以直接按下标取 `vectors[index]`。
- 批量不是无上限：provider 有单请求条数与 token 上限，所以库内部还会再分批。

### 11.8 mock 哈希向量器（FNV-1a → 桶累加 → L2）

**是什么**：把 token 列表变成定长计数的词袋向量，再做 L2 归一化。详见 §9。

**TS 里对应什么**：它本身就是 TS/JS 写的（`tools/mock-llm/server.mjs`），没有 Python 版；两端都通过 HTTP 调它，所以**只有一份实现**。

**这里为什么这么写**：

- 需求是「确定性 + 无密钥 + 可解释的分数」，不是「语义准确」。
- 纯函数（文本 → 向量）使两端请求同一份文本必然得到同一串数，才可能做到「score 全精度相同」。
- 词袋 + 余弦让「共享字多 → 分高」可被手算验证，验收断言才有意义。

### 11.9 CJK 逐字分词

**是什么**：遇到 CJK 字符就单独成 token，非 CJK 连续字符合成一个 token。

**TS 里对应什么**：同样是 mock 自己的 JS 实现；两端共享。

**这里为什么这么写**：

- 空白分词对中文完全失效（整句一个 token）。
- 逐字是最小可用近似：不需要词典、不分词库、无外部依赖，却能让共享汉字产生相似度。
- 代价是同义不同字不匹配、单字歧义（「的」「了」等高频字贡献噪声）。教学项目接受这个代价，生产环境换真实 embedding 即可。

### 11.10 `RunError` 在 RAG 里的复用

**是什么**：`RunError` 本来是执行引擎的运行期错误（阶段 5），用于 SSE 的 `run_failed`。

**TS 里对应什么**：`apps/api-ts/src/engine/events.ts` 的 `RunError`；Python `app/engine/events.py` 的同名类。

**这里为什么这么写**：

- 同一条嵌入错误既可能发生在**普通 JSON 接口**（上传/检索 → 400），也可能发生在 **`knowledge` 节点的 SSE 流**（→ `run_failed`）。
- 用同一个错误类型承载**规范文案**，两个入口各自决定「怎么呈现」，文案只写一次、两端一致。
- `kb.service.ts` 的 `embedOrBadRequest` 和 `service.py` 的 `_embed_or_bad_request` 就是这层转换：`RunError` → 400。

## 12. 【加厚】写错会怎样

### 12.1 `chunkSize` 过大 → 召回但上下文被冲淡

**现象**：上传成功、`chunkCount` 变少（一篇长文只有 1 块）；检索确实能命中（因为整篇都在这一块里），但：

- 返回的 `content` 很长，前端引用面板被一大段文字淹没；
- 塞进 prompt 后，真正相关的一两句被大量无关内容稀释，模型答非所问或忽略关键约束；
- 多个主题混在一块，向量落在「质心」，与具体问题的分数整体下降。

**原因**：块是检索与引用的最小单位。`chunkSize=2000` 时，一块平均包含 4–5 个主题；`score` 反映的是「整块与 query 的平均接近程度」。

**正解**：中文文档用 300–800；本项目取 500，配合 `overlap=80`。判断标准不是「能不能召回」，而是「召回的这一块里，有多少比例是答案需要的」。

### 12.2 `chunkOverlap >= chunkSize` → 两端行为不一样

**现象**：

- TS 侧启动/上传直接 500（构造切分器时抛异常），日志：`Cannot have chunkOverlap >= chunkSize`；
- Python 侧**相等时不报错**，但切出来的块几乎没有重叠，甚至块长超过 `chunkSize`。

**原因（源码级）**：

```js
// @langchain/textsplitters/dist/text_splitter.js:20
if (this.chunkOverlap >= this.chunkSize) throw new Error("Cannot have chunkOverlap >= chunkSize");
```

```python
# langchain_text_splitters/base.py:94
if chunk_overlap > chunk_size:          # ← 注意是 >，不是 >=
    raise ValueError(
        f"Got a larger chunk overlap ({chunk_overlap}) than chunk size "
        f"({chunk_size}), should be smaller."
    )
```

Python 相等时为何退化：`merge_splits` 的 `while total > chunk_overlap or (...)` 在 `total == chunk_size == chunk_overlap` 时，第一项为假，只能靠第二项「下一片放不下」把窗口清空，结果往往是 0 重叠。

**正解**：始终保证 `chunkOverlap < chunkSize`（本项目 80 < 500）。不要写「相等也行」，更不要只在一端改参数。

### 12.3 维度不是 1536 → 插入失败

**现象**：

- 若应用层检查还在：上传 400 / `knowledge` 节点 `run_failed`，文案 `embedding request failed: unknown`；
- 若绕过应用层（例如直接调 provider 写库、或把检查删了）：数据库报

```text
ERROR:  expected 1536 dimensions, not 1024
```

上传接口变成 500，且原始数据库错误可能透给调用方（不符合契约）。

**原因**：`chunks.embedding` 是 `vector(1536)`，pgvector 对维度做严格校验；HNSW 索引也是按 1536 建的距离计算。

**正解**：

1. 换模型前先确认输出维度；`text-embedding-3-small` 是 1536。
2. 保留应用层逐条检查（它保证错误发生在写库前、且是契约文案）。
3. 真要换维度，按 schema 注释做完整迁移：改列 → 重算全部已有向量 → 重建 HNSW 索引 → 同步两端常量。**绝不截断/补零**凑成 1536。

### 12.4 忘记 `check_embedding_ctx_length=False` → tiktoken 报错 / provider 不认

**现象**（Python 侧）：

- 上传 400/500 或 `run_failed`，最终文案 `embedding request failed: unknown`；
- 服务端日志里能看到 `tiktoken` 相关异常（编码表下载失败、未知模型名），或 provider 返回 400（因为收到的 `input` 是嵌套的 token id 数组）；
- 更隐蔽的情况：provider「接受」了数组但返回语义不对的向量，维度可能还不对。
- **特别提醒（本项目 mock）**：`handleEmbeddings` 对每条输入做 `String(text)`，token 数组会被字符串化成 `"123,456"` 再分词——于是**根本不报错**，只是向量与 TS 完全不同，表现为「两端 `chunkCount` 相同、`score` 却不一样」。这种静默不一致比报错更难查。

**原因**：默认 `True` 时，`langchain-openai` 在本地用 tiktoken 分词，`input` 变成 `[[1234, 5678, ...], ...]`。非 OpenAI provider 按字符串处理，要么报错，要么把数组当别的东西。自定义模型名还会让 `encoding_for_model` 找不到编码（本仓库版本回退 `cl100k_base`，但并非所有版本/环境都如此）。

**正解**：

```python
client = OpenAIEmbeddings(
    api_key=settings.llm_api_key,
    model=settings.embedding_model or DEFAULT_EMBEDDING_MODEL,
    base_url=settings.llm_base_url,
    max_retries=0,
    check_embedding_ctx_length=False,   # ← 必需
)
```

同时确认 TS 侧**不需要**这个参数（JS 版不本地分词）；两边都指向同一个 mock 时，实际发出的 `input` 才都是字符串。

### 12.5 两端参数不一致 → chunk 文本不同 → 检索结果不同

**现象**：

- 同一份文件，两端 `chunkCount` 相同或不同；
- SQL 比对 `content` 的 `sha256` 从某一块的中间开始分叉；
- 同一 query 的 `score` 不同（因为向量来自不同文本），甚至命中顺序不同；
- 更隐蔽：前半段相同、后半段不同，肉眼对比容易漏掉。

**原因**：切分是**上下文相关**的——任何一块的边界变化，都会让后续所有块的起点和重叠窗口变化（蝴蝶效应）。改一个参数（哪怕只是 `separators` 里把 `。` 放到 `！` 后面）就足以让整篇错位。

**正解**：

1. 参数只在一处定义、两处引用（本项目的做法：两个 `SPLITTER_CONFIG` 常量 + 顶部注释）。
2. 改完必须跑 §15.4 的逐块比对，**不要只看 chunkCount**。
3. 验收脚本按 `(文档名, chunk_index)` 排序后比较 `octet_length` 与 `sha256`，而不是比较整段文本的哈希。

### 12.6 其它三个常见误写

| 误写 | 现象 | 原因 / 正解 |
| --- | --- | --- |
| 过滤空块的规则不同（TS 用 `.filter(trim!=='')`，Python 忘了过滤） | `chunk_index` 整体错位，向量也对不上 | 切分器在特殊文本（连续空行、全空白行）下可能产出空白块；两端必须都过滤（§8.1 / §8.2） |
| 用字符长度比较两端 chunk | 含 emoji 的文档长度不同（TS 按 UTF-16 码元，Python 按码点） | 比对用 **UTF-8 字节长度**（`octet_length`）或 sha256，不用 `length()`/`len` 的字符数 |
| 以为 TS 发的是原文、Python 发的也是原文 | 真实模型下同名 chunk 的向量略有差异 | TS 默认 `stripNewLines=true`（`\n`→空格）；mock 下无影响，真实 provider 下需自行对齐（或接受微小差异） |

### 13.1 `apps/api-ts/src/rag/splitter.ts`

**完整文件路径：`apps/api-ts/src/rag/splitter.ts`**

```ts
import { RecursiveCharacterTextSplitter } from '@langchain/textsplitters'

/**
 * 文档切分配置（**两端必须同参数**，见阶段 7 笔记）。
 *
 * 作为导出常量供文档/笔记引用；修改这里必须同步 Python 侧。
 */
export const SPLITTER_CONFIG = {
  chunkSize: 500,
  chunkOverlap: 80,
  separators: ['\n\n', '\n', '。', '！', '？', '. ', ' ', ''],
  keepSeparator: true,
} as const

/** 按 `SPLITTER_CONFIG` 把文本切成若干块（保持原顺序）。 */
export async function splitText(text: string): Promise<string[]> {
  const splitter = new RecursiveCharacterTextSplitter({
    chunkSize: SPLITTER_CONFIG.chunkSize,
    chunkOverlap: SPLITTER_CONFIG.chunkOverlap,
    separators: [...SPLITTER_CONFIG.separators],
    keepSeparator: SPLITTER_CONFIG.keepSeparator,
  })
  return splitter.splitText(text)
}
```

### 13.2 `apps/api-py/app/rag/splitter.py`

**完整文件路径：`apps/api-py/app/rag/splitter.py`**

```python
"""文档切分（阶段 7）。

**参数必须与 api-ts 的 `apps/api-ts/src/rag/splitter.ts` 完全一致**：
`chunk_size=500`、`chunk_overlap=80`、
`separators=["\\n\\n", "\\n", "。", "！", "？", ". ", " ", ""]`、`keep_separator=True`。
修改这里必须同步 TS 侧，否则两端 chunk 无法逐字节一致。
"""
```

```ts
/** 默认嵌入模型（可用环境变量 `EMBEDDING_MODEL` 覆盖）。 */
const DEFAULT_EMBEDDING_MODEL = 'text-embedding-3-small'

/**
 * 批量文本向量化（阶段 7）。
 *
 * 复用 LLM 的 provider 配置：`LLM_API_KEY` / `LLM_BASE_URL`；
 * 模型取 `EMBEDDING_MODEL`，缺省 `text-embedding-3-small`。
 * `maxRetries: 0` 与阶段 5 的 LLM 调用对齐（避免 5xx / 超时长时间挂起）。
 *
 * 错误一律经 `mapEmbeddingError` 归一为规范文案（见 error-messages.md §7），
 * 不透出库的原始 message；返回向量维度不是 1536 时也按 `unknown` 处理。
 */
export async function embedTexts(texts: string[]): Promise<number[][]> {
  if (texts.length === 0) {
    return []
  }
  const apiKey = process.env.LLM_API_KEY ?? ''
  if (apiKey === '') {
    throw new RunError('embedding provider not configured: LLM_API_KEY')
  }

  const client = new OpenAIEmbeddings({
    apiKey,
    model: process.env.EMBEDDING_MODEL ?? DEFAULT_EMBEDDING_MODEL,
    configuration: {
      baseURL: process.env.LLM_BASE_URL ?? 'https://api.openai.com/v1',
      maxRetries: 0,
    },
    timeout: Number(process.env.LLM_TIMEOUT_MS ?? 60000),
  })

  let vectors: number[][]
  try {
    vectors = await client.embedDocuments(texts)
  } catch (error) {
    throw new RunError(mapEmbeddingError(error))
  }

  for (const vector of vectors) {
    if (!Array.isArray(vector) || vector.length !== EMBEDDING_DIMENSIONS) {
      // eslint-disable-next-line no-console
      console.error(
        `embedding dimension mismatch: expected ${EMBEDDING_DIMENSIONS}, got ${Array.isArray(vector) ? vector.length : 'non-array'}; ` +
          `check EMBEDDING_MODEL / provider output (vector(1536) is fixed in migrations)`,
      )
      throw new RunError('embedding request failed: unknown')
    }
  }
  return vectors
}

/**
 * 把嵌入调用异常映射为规范文案（规则与 `mapLlmError` 一致，前缀改为 `embedding`）。
 * HTTP 状态码优先，其次超时，最后归入 unknown。
 */
export function mapEmbeddingError(error: unknown): string {
  const status = statusCodeOf(error)
  if (status !== null) {
    if (status === 401 || status === 403) {
      return 'embedding request unauthorized'
    }
    if (status === 429) {
      return 'embedding rate limited'
    }
    return `embedding request failed: ${status}`
  }
  if (isTimeout(error)) {
    return 'embedding request timed out'
  }
  return 'embedding request failed: unknown'
}

/** 取异常的 HTTP 状态码（OpenAI SDK 的 APIError 带 `status`）。 */
function statusCodeOf(error: unknown): number | null {
  if (typeof error === 'object' && error !== null) {
    const status = (error as { status?: unknown }).status
    if (typeof status === 'number') {
      return status
    }
  }
  return null
}

/** 判定是否为超时（`APIConnectionTimeoutError` / AbortError，或消息含 timeout）。 */
function isTimeout(error: unknown): boolean {
  if (typeof error !== 'object' || error === null) {
    return false
  }
  const name = (error as { name?: unknown }).name
  if (name === 'APIConnectionTimeoutError' || name === 'TimeoutError' || name === 'AbortError') {
    return true
  }
  const message = (error as { message?: unknown }).message
  return typeof message === 'string' && /timed? ?out|timeout/i.test(message)
}
```

```python
from app.config import settings
from app.engine.events import RunError

# 向量维度**固定 1536**：必须与 `chunks.embedding vector(1536)` 及 HNSW 索引一致
EMBEDDING_DIMENSIONS = 1536

# 默认嵌入模型（可用环境变量 `EMBEDDING_MODEL` 覆盖）
DEFAULT_EMBEDDING_MODEL = "text-embedding-3-small"


async def embed_texts(texts: list[str]) -> list[list[float]]:
    """批量文本向量化；失败抛 `RunError`（规范文案见 error-messages.md §7.3）。"""
    if not texts:
        return []
    api_key = settings.llm_api_key
    if not api_key:
        raise RunError("embedding provider not configured: LLM_API_KEY")

    client = OpenAIEmbeddings(
        api_key=api_key,
        model=settings.embedding_model or DEFAULT_EMBEDDING_MODEL,
        base_url=settings.llm_base_url,
        timeout=settings.llm_timeout_ms / 1000,
        # 不重试（与 api-ts 的 maxRetries: 0 对齐）
        max_retries=0,
        # 关键：不做 tiktoken 本地分词（非 OpenAI 官方模型会因此报错）
        check_embedding_ctx_length=False,
    )

    try:
        vectors = await client.aembed_documents(texts)
    except Exception as error:  # noqa: BLE001 - 任何嵌入错误都归一为规范文案
        raise RunError(map_embedding_error(error)) from error

    for vector in vectors:
        if not isinstance(vector, list) or len(vector) != EMBEDDING_DIMENSIONS:
            # 维度不符时按 unknown 处理（与 api-ts 一致）
            raise RunError("embedding request failed: unknown")
    return vectors


def map_embedding_error(error: Exception) -> str:
    """把嵌入调用异常映射为规范文案（规则与 `map_llm_error` 一致，前缀改为 `embedding`）。"""
    status = _status_code(error)
    if status is not None:
        if status in (401, 403):
            return "embedding request unauthorized"
        if status == 429:
            return "embedding rate limited"
        return f"embedding request failed: {status}"
    if _is_timeout(error):
        return "embedding request timed out"
    return "embedding request failed: unknown"


def _status_code(error: Exception) -> int | None:
    """取异常的 HTTP 状态码（Python openai SDK 的 APIStatusError 带 `status_code`）。"""
    for attr in ("status_code", "status"):
        value = getattr(error, attr, None)
        if isinstance(value, int):
            return value
    return None


def _is_timeout(error: Exception) -> bool:
    """判定是否为超时（`APITimeoutError` / `TimeoutError`，或消息含 timeout）。"""
    if type(error).__name__ in ("APITimeoutError", "TimeoutError", "APIConnectionTimeoutError"):
        return True
    message = str(error).lower()
    return "timed out" in message or "timeout" in message
```

```js
/** 嵌入维度：**必须与 Prisma 迁移里的 `chunks.embedding vector(1536)` 一致**。 */
const EMBEDDING_DIMENSIONS = 1536

/**
 * `POST /v1/embeddings`：按「哈希向量器」产出确定性向量。
 *
 * 请求 `{ model, input: string | string[] }`；
 * 响应 `{ object: "list", data: [{ object: "embedding", index, embedding }], model, usage }`。
 */
function handleEmbeddings(res, payload) {
  const inputs = Array.isArray(payload.input) ? payload.input : [payload.input ?? '']
  const model = payload.model || 'mock-embedding'
  let promptTokens = 0
  const data = inputs.map((text, index) => {
    const tokens = tokenizeForEmbedding(String(text))
    promptTokens += tokens.length
    return { object: 'embedding', index, embedding: hashVector(tokens) }
  })
  return sendJson(res, 200, {
    object: 'list',
    data,
    model,
    usage: { prompt_tokens: promptTokens, total_tokens: promptTokens },
  })
}

/** 分词：小写后按空白切词；每个 CJK 字符单独成一个 token，其余连续字符合成一个 token。 */
function tokenizeForEmbedding(text) {
  const tokens = []
  for (const word of text.toLowerCase().split(/\s+/)) {
    let buffer = ''
    for (const char of word) {
      if (isCjk(char)) {
        if (buffer !== '') {
          tokens.push(buffer)
          buffer = ''
        }
        tokens.push(char)
      } else {
        buffer += char
      }
    }
    if (buffer !== '') {
      tokens.push(buffer)
    }
  }
  return tokens
}

/** CJK 统一表意文字（含扩展 A 与兼容表意文字）。 */
function isCjk(char) {
  return /[\u3400-\u4dbf\u4e00-\u9fff\uf900-\ufaff]/.test(char)
}

/** FNV-1a 32 位哈希（返回无符号整数）。 */
function fnv1a32(text) {
  let hash = 0x811c9dc5
  for (let index = 0; index < text.length; index += 1) {
    hash ^= text.charCodeAt(index)
    hash = Math.imul(hash, 0x01000193) >>> 0
  }
  return hash >>> 0
}

/** 词袋哈希向量 + L2 归一化；无 token 时返回全 0 向量。 */
function hashVector(tokens) {
  const vector = new Array(EMBEDDING_DIMENSIONS).fill(0)
  for (const token of tokens) {
    vector[fnv1a32(token) % EMBEDDING_DIMENSIONS] += 1
  }
  let squareSum = 0
  for (const value of vector) {
    squareSum += value * value
  }
  const norm = Math.sqrt(squareSum)
  if (norm === 0) {
    return vector
  }
  return vector.map((value) => value / norm)
}
```

> 环境：mock provider（`LLM_BASE_URL=http://127.0.0.1:11435/v1`、`EMBEDDING_MODEL=mock-embedding`），两端连同一个 PostgreSQL，各建一个知识库，上传**同一份**三篇文档。

### 14.1 切分：chunkCount 与逐字节相等

**先做一个不依赖上传的最小验证**：`t = '第一段。' * 200`（共 800 字），用两端各自的 `splitText` 跑：

```text

Python : 2 块，长度 [499, 381]，第 2 块开头 。第一段。第一段。第一段
```

块数、长度、开头文本完全一致——这是「同参数 + 同算法」最直接的证据（复现命令见 §15.6）。

**再测真实文档**：两端每篇文档均为 `chunkCount = 2`（共 6 块）。SQL 直查 `chunks.content`、按 `chunk_index` 排序后：

| 文档#chunk_index | len（UTF-8 字节） | sha256（截断） | TS = Python |
| --- | --- | --- | --- |
| `delivery.txt#0` | 1227 | `89039c92…` | ✅ |
| `refund.txt#1` | 813 | `5e6c981e…` | ✅ |
| 其余 4 行（`delivery#1`、`refund#0`、`invoice#0`、`invoice#1`） | — | 逐项相等 | ✅ |

**结论：chunk 逐字节相等 = `True`。**

> 关于 `len`：表中 `1227 > chunkSize=500`，说明这里记录的是 **UTF-8 字节长度**（中文 1 字 = 3 字节），不是字符数。换算成字符约 400 上下，仍在 500 以内。验收时建议同时查 `octet_length(content)`（字节）和 `length(content)`（字符），以字节/哈希为准。

| rank | 命中 | score（两端全精度相同） |

### 15.3 建库 + 两端各上传一遍

```powershell
# 登录（换成你已注册的账号）
$TOKEN = (curl.exe -s -X POST http://localhost:3001/auth/login `
  -H "Content-Type: application/json" `
  -d '{"email":"demo@example.com","password":"Password123"}' | ConvertFrom-Json).accessToken

# 在 TS 侧建库
$KB_TS = (curl.exe -s -X POST http://localhost:3001/knowledge-bases `
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" `
  -d '{"name":"ts-kb"}' | ConvertFrom-Json).id

# 在 Python 侧建库
$KB_PY = (curl.exe -s -X POST http://localhost:8000/knowledge-bases `
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" `
  -d '{"name":"py-kb"}' | ConvertFrom-Json).id

# 两端各上传同一份三篇
foreach ($kb in @($KB_TS, $KB_PY)) {
  $port = if ($kb -eq $KB_TS) { 3001 } else { 8000 }
  foreach ($name in @('refund.txt','delivery.txt','invoice.txt')) {
    curl.exe -s -X POST "http://localhost:$port/knowledge-bases/$kb/documents" `
      -H "Authorization: Bearer $TOKEN" `
      -F "file=@$PWD\$name;type=text/plain"
    ""
  }
}
```

预期：每个响应都是 `201`，含 `"status":"ready"`；`chunkCount` 取决于你的文本长度（上面的样例通常为 1），但**两端必须相同**。

### 15.4 SQL 直查：逐块比较

```powershell
$sql = @"
SELECT d.name AS doc,
       left(d.id, 8) AS doc_id,
       c.chunk_index,
       octet_length(c.content) AS len_bytes,
       length(c.content) AS len_chars,
       left(encode(sha256(c.content::bytea), 'hex'), 16) AS sha256_16
FROM chunks c
JOIN documents d ON d.id = c.document_id
WHERE c.knowledge_base_id IN ('$KB_TS', '$KB_PY')
ORDER BY d.name, c.chunk_index, d.id;
"@
docker exec -i mini-dify-db psql -U postgres -d minidify -c $sql
```

**判定**：同一 `doc`、同一 `chunk_index` 下，`len_bytes` 与 `sha256_16` 必须**两两相等**（TS 的一行与 Python 的一行）。不要只比 `chunkCount`。

> 若 `sha256(...)` 函数不存在，改用 `encode(digest(c.content, 'sha256'), 'hex')` 并先 `CREATE EXTENSION IF NOT EXISTS pgcrypto;`；或把 content 导出到本地用 `Get-FileHash` 计算。

## 16. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 上传后 `chunkCount=1`，检索「能命中但答非所问」 | `chunkSize` 过大，整篇一个向量 | 降到 300–800；检查 `EMBEDDING_MODEL` 与文本长度 |
| TS 上传 500：`Cannot have chunkOverlap >= chunkSize` | `chunkOverlap` 调到了 ≥ `chunkSize` | 保持 80 < 500；改参数时两端同步 |
| Python 同样参数却不报错，块还变长 | Python 只在 `>` 时报错，`==` 会退化 | 不要把「相等能跑」当成约定；以 `chunkOverlap < chunkSize` 为硬规则 |
| 400 `embedding request failed: unknown`，日志有 `expected 1536` | 模型维度不是 1536，或应用层检查被绕过 | 换回 1536 维模型；不要把向量截断/补零 |
| Python 上传 400/500，日志有 tiktoken 或 provider 400 | 忘了 `check_embedding_ctx_length=False`，发的是 token 数组 | 加上该参数并重启 |
| 明明配了 `LLM_BASE_URL`，TS 仍请求 `api.openai.com` | `baseURL` 写在了顶层而不是 `configuration` 里 | 放到 `configuration: { baseURL, maxRetries }` |
| Python 超时几乎不触发 | `timeout` 单位是秒，却填了毫秒 | `settings.llm_timeout_ms / 1000` |
| 两端 `chunkCount` 相同但 `score` 不同 | 块边界不同（某个参数只改了一边），或一端 `EMBEDDING_MODEL` 不同 | 逐块比对 `sha256`；确认两端 `.env` 同值 |
| 两端块内容相同，真实模型下 `score` 仍有细微差异 | TS `stripNewLines` 把 `\n` 换成空格；真实 embedding 对空白敏感 | mock 验收无影响；生产环境可接受微小差异，或显式关掉 `stripNewLines` |
| 含 emoji 的文档两端块长不同 | 长度函数不同：UTF-16 码元 vs 码点 | 用 `octet_length` / sha256 比对；必要时避免在这些文档上做逐字节验收 |
| 检索分数全是 0 或 NaN | query 只有标点/空白 → 全 0 向量；或知识库没有 chunk | 用正常自然语言 query；确认上传成功且 `chunkCount > 0` |
| 改了切分参数，旧文档不受影响 | 已入库的 chunk 是持久化结果，不会自动重算 | 删除文档重新上传（或写重建脚本） |
