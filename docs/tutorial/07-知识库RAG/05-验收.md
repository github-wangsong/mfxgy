## 1. 本篇目标

做完这一篇，你能：

- 沿**依赖顺序**逐层验收阶段 7：契约 `0.7.0` → **迁移与索引** → KB CRUD → **上传与切分** → **chunk 逐字节一致** → **检索分数全精度一致** → **图运行 + 9 组错误 + 回归**。
- 用可直接复制的命令证明：
  - `chunks.embedding` 真的是 `vector(1536)`，HNSW 索引真的是 `hnsw (embedding vector_cosine_ops)`；
  - 同一份文档在 `api-ts` 与 `api-py` 上传后，每篇 `chunkCount=2`，且 6 个 chunk 的 `len + sha256` **逐项相同**；
  - 同一 `query / topK` 在两端返回的 `hits` 的 `documentName` / `chunkIndex` / `score` **全精度相同**（`0.5884331464767456` / `0.4971181748579854` / `0.13314714930687654`）；
  - `knowledge` 节点的 SSE 里有且只有一次 `retrieval`，`context` 两端**逐字节相等**（`len=1211`）；
  - 9 组错误（名字空 / `.exe` / 空文件 / >1MB / 缺 kbId / 未知库 / topK 99 / 无密钥 / B 访问 A 的库）两端文案**逐字一致**；
  - 阶段 5 的 token 序列与 usage、阶段 6 的工具事件**没有被破坏**。
- 讲清 **参数即契约**：切分参数（500 / 80 / 分隔符）与向量维度（1536）任意一处不一致，chunk 与检索结果必然分叉。
- 讲清 **HNSW 索引与 Prisma 迁移的冲突**：`prisma migrate dev` 会生成 `DROP INDEX "chunks_embedding_hnsw"`，必须删除该自动迁移并手工重建。

**验收标准（对齐总纲 §6 阶段 7）**

> 能上传文档、切分并向量化；`knowledge` 节点能检索并在运行面板看到引用。

## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序（先契约与库结构、后数据、最后运行与回归）

```
L1 契约编译(0.7.0) ──> L2 迁移与索引(vector(1536) + HNSW)
                              │
                              ▼
                    L3 KB CRUD（201/200/204/404）
                              │
                              ▼
              L4 上传与切分（两端各 3 篇 → 各 2 chunk）
                              │
                              ▼
           L5 chunk 逐字节一致（6 行 len + sha256）
                              │
                              ▼
        L6 检索一致（topK 3，score 全精度相同）
                              │
                              ▼
   L7 图运行(retrieval/context) → 9 组错误 → 阶段 5/6 回归
```

**为什么按这个顺序**：契约不编译，类型与路由无从谈起；库结构不对（维度 / 索引），后面所有写入与检索都是错的；KB 与上传是检索的前置；**先证明「同一份原文切出同一堆 chunk」，再证明「同一堆 chunk 查出同一堆分数」**；最后用错误与回归证明「新能力没有破坏旧行为」。

### 3.4 L4 —— 上传与切分：两端每篇 `chunkCount=2`

**在哪执行**：任意目录
**目的**：证明同一份原文在两端都按同一组参数切分，且落库的 `chunkCount` 一致。

**用 `api-ts` 上传三篇到 `TS_KB`**：

```bash
for f in delivery.txt refund.txt invoice.txt; do
  curl -s -X POST http://127.0.0.1:3001/knowledge-bases/$TS_KB/documents \
    -H "Authorization: Bearer $TS_TOKEN" \
    -F "file=@$f;type=text/plain" \
    | python -c "import sys,json;d=json.load(sys.stdin);print(d['name'],d['chunkCount'],d['status'])"
done
```

**用 `api-py` 上传同样三篇到 `PY_KB`**：

```bash
for f in delivery.txt refund.txt invoice.txt; do
  curl -s -X POST http://127.0.0.1:8000/knowledge-bases/$PY_KB/documents \
    -H "Authorization: Bearer $TS_TOKEN" \
    -F "file=@$f;type=text/plain" \
    | python -c "import sys,json;d=json.load(sys.stdin);print(d['name'],d['chunkCount'],d['status'])"
done
```

**预期输出（实测·两端相同）**

```
delivery.txt 2 ready
refund.txt 2 ready
invoice.txt 2 ready
```

**再经两端各查一次文档列表**（证明**同一个库**被两套后端读出的形状一致）：

```bash
curl -s http://127.0.0.1:3001/knowledge-bases/$TS_KB/documents \
  -H "Authorization: Bearer $TS_TOKEN" > ts.docs.json
curl -s http://127.0.0.1:8000/knowledge-bases/$TS_KB/documents \
  -H "Authorization: Bearer $TS_TOKEN" > py.docs.json

python -c "import json;a=json.load(open('ts.docs.json'));b=json.load(open('py.docs.json'));print('DOCS IDENTICAL' if a==b else 'DOCS DIFFERENT');print([(d['name'],d['chunkCount']) for d in a['items']])"
```

**预期输出（实测）**

```
DOCS IDENTICAL
[('delivery.txt', 2), ('refund.txt', 2), ('invoice.txt', 2)]
```

**结果解读**：

- **`chunkCount=2`**：三篇文档的长度都落在「500 字符一块、80 重叠」的参数下切出两块——多于或少于 2，说明切分参数漂移或原文不同。
- **`status=ready`**：上传是同步完成的（切分 → 嵌入 → 写库），没有后台任务，所以返回时已经 ready。
- **同一数据库、两套后端**：`GET /documents` 只是读同一批行，形状一致证明**出参映射**（字段名、时间、`null`）也对齐。

### 3.5 L5 —— 两端 chunk 逐字节一致（6 行 `len` + `sha256`）

**在哪执行**：仓库根
**目的**：这是阶段 7 最重要的**值级**验收——同一份原文，两端切出的每一块长度与哈希都必须相同。

**取 `TS_KB` 与 `PY_KB` 的 chunk 摘要**（用 api-py 的虚拟环境，已装 `psycopg`）：

```bash
cat > _p7_chunks.py <<'PY'
import hashlib, sys
import psycopg

kb_id = sys.argv[1]
conn = psycopg.connect("postgresql://postgres:difyai123456@localhost:5432/minidify")
rows = conn.execute(
    """
    SELECT d.name, c.chunk_index, c.content
    FROM chunks c JOIN documents d ON d.id = c.document_id
    WHERE c.knowledge_base_id = %s
    ORDER BY d.name, c.chunk_index
    """,
    (kb_id,),
).fetchall()
for name, index, content in rows:
    raw = content.encode("utf-8")
    digest = hashlib.sha256(raw).hexdigest()[:8]
    print(f"{name.removesuffix('.txt')}#{index} len={len(raw)} sha256={digest}")
PY

uv run --directory apps/api-py python ../../_p7_chunks.py $TS_KB > ts.chunks
uv run --directory apps/api-py python ../../_p7_chunks.py $PY_KB > py.chunks
diff ts.chunks py.chunks && echo "CHUNKS IDENTICAL"
cat ts.chunks
```

**预期输出（实测）**

```

delivery#1 len=...
invoice#0 len=...
invoice#1 len=...
refund#0 len=...
refund#1 len=813 sha256=5e6c981e
```

（上表中 `delivery#0` 与 `refund#1` 的 `len / sha256` 是实测值；其余四行的哈希按同一条命令输出，`diff` 为空是判定标准。`len` 是 **UTF-8 字节数**，不是字符数——中文一个字 3 字节，所以 500 字符左右的块会有 1000+ 字节。）

**结果解读**：

- **`len` 相同** ⇒ 两端的切分边界完全一致（含 `keep_separator` 的标点归属）。
- **`sha256` 相同** ⇒ 块内容**逐字节**相同（不是「看起来一样」）。
- 任意一个参数（`chunk_size` / `chunk_overlap` / `separators` 顺序 / `keep_separator`）在某一端不同，这 6 行至少会有一半对不上——这就是「**参数即契约**」的验收方式。
- 解码也必须一致：两端都对非法 UTF-8 用 U+FFFD 替换（TS `buffer.toString('utf8')` / Py `errors="replace"`），否则同一份二进制文档会切出不同文本。

### 3.6 L6 —— 检索一致：`score` 全精度相同

**在哪执行**：任意目录
**目的**：证明「同一堆 chunk + 同一个 query」在两端得到**逐条同序、同分**的命中。

```bash

python -c "import json;a=json.load(open('ts.search.json'));b=json.load(open('py.search.json'));print('SEARCH IDENTICAL' if a==b else 'SEARCH DIFFERENT');[print(h['documentName'],h['chunkIndex'],repr(h['score'])) for h in a['hits']]"
```

**预期输出（实测）**

```
SEARCH IDENTICAL
refund.txt 0 0.5884331464767456
refund.txt 1 0.4971181748579854
invoice.txt 0 0.13314714930687654
```

> 三行文档名与 `02-文档切分与向量化.md` / `03-NestJS检索与检索节点.md` 的实测一致。**判定标准是两端的 `hits` 逐条相等**（文档名、分块号、`score`），而不是某个固定文件名。

**结果解读（四个关键点）**：

- **同序**：两端都按 `ORDER BY embedding <=> query` 升序（= `score` 降序），所以 `hits` 的顺序一致；这比「集合相等」更强。
- **同分到浮点末位**：`0.5884331464767456` 这类值不是「四舍五入后相等」，而是**同一个浮点数**。它要求：同一份原文 → 同一堆 chunk → 同一个嵌入向量（mock 是确定性哈希）→ 同一个 SQL 表达式 → 同一种数值类型转换（`Number()` / `float()`）。
- **`score` 的范围**：mock 向量的分量非负且已 L2 归一化，余弦相似度落在 `[0,1]`；真实模型可能略小于 0（负相关），前端只展示 3 位小数（`04` §7.5）。
- **`documentName` 来自 JOIN**：`chunks` 只存 `document_id`，名称在 `documents` 表；两端都用 `JOIN documents d ON d.id = c.document_id`，所以「文档名 + 分块号」是稳定的引用标识。

> 若 `SEARCH DIFFERENT`，先 diff 两边的 `content`：内容不同 ⇒ 切分 / 解码漂移；内容相同但 `score` 不同 ⇒ 嵌入模型 / 维度 / SQL 表达式 / 数值转换漂移。

## 4. 【技术讨论 1】阶段 7 补上了什么：先检索你的私有资料，再回答

**问题**：阶段 5/6 已经能调用真实模型、能自主用工具，阶段 7 的「知识库」到底新在哪？

**答案的一句话**：**阶段 6 是「模型用自己的知识回答，必要时查工具」；阶段 7 是「先从你的私有资料里检索出相关片段，再把片段交给模型回答」。**

| 层 | 阶段 6 | 阶段 7 |
| --- | --- | --- |
| 知识来源 | 模型参数里的**世界知识** + 工具返回值 | **你的文档**（上传 → 切分 → 向量化 → 检索） |
| 上下文 | system + user + 工具结果 | **+ `knowledge.context`**（检索到的原文片段） |
| 回答依据 | 模型「记得」 | **可引用的原文**（`documentName` / `chunkIndex` / `score`） |
| 新失败面 | provider、工具 | provider、工具、**嵌入**、**检索质量** |
| 新事件 | `tool_call` / `tool_result` | **`retrieval`** |
| 新数据 | 无 | `knowledge_bases` / `documents` / `chunks`（含 `vector(1536)`） |

**RAG（Retrieval-Augmented Generation）的最小闭环**

```
上传文档 → 切分 chunk → 嵌入成向量 → 写入 pgvector
                                          │
用户问题 → 嵌入成向量 ──> 余弦相似度 topK ──┘
                              │
                         context（原文片段）
                              │
                       LLM 基于 context 生成答案
                              │
                    运行面板展示 retrieval 引用
```

**阶段 7 真正带来的三个能力**

1. **私有知识**：模型没见过的内部文档、政策、FAQ，可以「现查现答」，不需要微调。
2. **可更新**：改文档、加文档，下一次检索立刻生效；模型参数不用动。
3. **可解释**：答案能追溯到「哪篇文档、第几块、分数多少」——`retrieval` 事件就是引用来源。

**它没有解决什么（必须诚实）**

- **检索质量**：没有 rerank、没有混合检索（关键词 + 向量）、没有 query 改写；召回不好，模型再强也答不对。
- **切分质量**：固定 500/80 是教学参数，不适用于所有文档类型。
- **权限粒度**：只到「知识库归属用户」，没有文档级 / 片段级权限。
- **多轮对话记忆**：`knowledge` 节点每次独立检索，不看上一轮。
- **引用进输出**：引用只在运行面板展示，没有写进 `run_finished.outputs`。

> **一句话**：**阶段 6 让模型「会用工具」，阶段 7 让模型「先读你的资料」——这是从「通用助手」走向「企业知识助手」的关键一步。**

## 5. 【技术讨论 2】参数即契约：切分参数与向量维度

**问题**：为什么验收要细到「6 行 chunk 的 `sha256`」和「`score` 的浮点末位」？差一点点会怎样？

**答案的一句话**：**在 RAG 里，「切分参数」和「向量维度」不是实现细节，而是契约的一部分——它们一变，chunk 集合就变，检索结果必然分叉，后面所有「逐字节一致」都不再成立。**

**必须两端完全一致的参数**

| 类别 | 参数 | 本项目值 | 改了会怎样 |
| --- | --- | --- | --- |
| 切分 | `chunk_size` | 500（**字符**，不是 token） | 块数、边界变 → `chunkCount` / `sha256` / `context` 全变 |
| 切分 | `chunk_overlap` | 80 | 相邻块的重叠变 → 内容变 |
| 切分 | `separators` 及**顺序** | `["\n\n","\n","。","！","？",". "," ",""]` | 断句位置变 → 内容变 |
| 切分 | `keep_separator` | `True` | 标点归属变 → 内容变 |
| 编码 | 解码策略 | UTF-8 + `errors="replace"` | 非法字节的替换结果不同 → 文本不同 |
| 向量 | 维度 | **1536** | 与 `vector(1536)` / HNSW 不一致 → 插入报错 |
| 向量 | 模型 | `EMBEDDING_MODEL` 同值 | 向量不同 → `score` 不同 |
| 检索 | `score` 公式 | `1 - (embedding <=> query)` | 排序方向 / 数值全变 |
| 检索 | 排序 | 距离**升序** | 取到最不相关的块 |
| 检索 | 过滤 | `WHERE knowledge_base_id = :kb` | 跨库召回（越权） |
| 返回 | `context` 拼接 | `"\n\n"` | 长度 / 哈希变 |

**为什么「看起来一样」不够**

- 两个切分器可能切出**数量相同、内容相似**的块，但标点归属差一个字符——人眼看不出，`sha256` 立刻不同，模型看到的 context 也不同。
- 浮点分数可能只差 `1e-16`，但 `JSON.stringify` 后就是不同的字符串；验收必须比较**解析后的数值**（`json.load` 后的 `float` 直接 `==`）。
- `len` 必须明确是**字符数**还是**字节数**：本节的 `len=1227` 是 **UTF-8 字节数**；中文一个字 3 字节，用字符数会得到完全不同的值。

**如果要改参数，正确的顺序**

1. 先改**契约 / 文档**（说明为什么改，记录新值）。
2. **两端同时改**（TS `splitter.ts` 与 Py `splitter.py`），并同步版本号。
3. **重建所有 chunk**（旧向量与旧 chunk 不能混用）：删文档重传，或写迁移清空 `chunks`。
4. 重跑 L5（6 行 `len + sha256`）与 L6（`score` 全精度）；两者都过才算改完。
5. 若改维度：必须新写迁移 `ALTER COLUMN ... TYPE vector(N)` + 重建向量 + **重建 HNSW 索引**，不能只改代码里的 `Vector(1536)`。

**为什么验收要卡在 `sha256` 与浮点末位**

- `sha256` 是「内容逐字节相同」的最强证据，不受编码 / 换行 / 空白差异影响。
- 浮点末位相同，说明「同一条 SQL、同一种数值转换」；只要有一端用了 `ROUND` / `toFixed` / `float32`，末位就会变。

> **一句话**：**RAG 的一致性不是「接口形状一致」，而是「同一份原文 → 同一堆 chunk → 同一堆向量 → 同一堆分数」；参数就是这条链的契约。**

## 6. 【技术讨论 3】Prisma vs SQLAlchemy 的 pgvector 支持差异

**问题**：同一张 `chunks` 表，为什么 TS 侧到处是 `$queryRaw`，Python 侧却能写 `Vector(1536)`？

**答案的一句话**：**Prisma 的 schema 语言没有「向量」这个类型，只能用 `Unsupported(...)` 声明「这个列存在但我不认识」；SQLAlchemy 通过 `pgvector` 插件获得了原生类型 `Vector(n)`。**

| 能力 | Prisma | SQLAlchemy + pgvector |
| --- | --- | --- |
| 在 schema / 模型里声明列 | `Unsupported("vector(1536)")?` | `mapped_column(Vector(1536))` |
| 生成的 Client 是否含该字段 | ❌（被排除） | ✅ |
| ORM 读 / 写该列 | ❌ | ✅（可绑定 `list[float]`） |
| ORM 按距离排序 | ❌ | ✅（`cosine_distance` 等） |
| 原生 SQL 逃生舱 | `$queryRaw` / `$executeRaw` | `text()` + `db.execute` |
| 类型安全 | 弱（`unknown[]`，自己声明） | 强（`Mapped[list[float]]`） |
| 迁移 | Prisma 迁移（手写 `vector(1536)` + HNSW） | **不产生 DDL**（只映射） |

**Prisma 侧的真实约束**

- `Unsupported` 字段**不会出现在 Prisma Client 的类型里**：`prisma.chunk.findMany()` 返回的对象没有 `embedding` 属性。
- 不能用 `where` / `orderBy` / `select` 操作它；所有向量读写都必须走 `$queryRaw` / `$executeRaw`。
- `$queryRaw` 返回 `unknown[]`，需要自己写行类型；`score` 是 `number`（驱动转的），要 `Number(row.score)` 兜底。
- 迁移里必须**手写** `vector(1536)` 与 HNSW 索引——Prisma 不会从 `Unsupported` 自动推导出它们。

**Python 侧的真实便利**

- `Vector(1536)` 让模型「知道」列类型，读出来就是 `list[float]`；理论上可以用 ORM 的 `cosine_distance` 排序。
- 但本项目**仍然用原生 SQL**：为了与 TS 的 SQL 逐项同构（`1 - (embedding <=> :emb)`、`CAST(... AS vector)`），也为了避免两套 ORM 在浮点序列化上的差异。

**为什么不让 Python 产生 DDL**

- 迁移所有权在 Prisma（`01-账号与认证/04`）：两套迁移系统同时改表，必然冲突。
- Python 的 `Base.metadata` 只用于映射；**绝不** `create_all()`。
- 这也意味着：**改表结构只能改 Prisma schema + 写迁移**，Python 侧同步改模型即可。

> **一句话**：**Prisma 的 `Unsupported` 是「承认自己不认识」；SQLAlchemy 的 `Vector` 是「真的认识」。但为了两端行为一致，读写都走原生 SQL——类型只影响「能不能用 ORM」，不影响「最终 SQL 长什么样」。**

## 7. 【技术讨论 4】HNSW 索引与 Prisma 迁移的冲突（真实坑）

**问题**：`chunks_embedding_hnsw` 是手写 SQL 建的，Prisma schema 里**没有**它。下一次 `prisma migrate dev` 会发生什么？

**答案：Prisma 会认为「数据库里有一个 schema 没描述的索引」，于是生成一条 `DROP INDEX "chunks_embedding_hnsw"` 的迁移。**

**现象**

```bash
pnpm --filter @mini-dify/api-ts db:migrate   # = prisma migrate dev
```

生成的新迁移目录里出现：

```sql
-- DropIndex
DROP INDEX "chunks_embedding_hnsw";
```

应用后：

```bash
docker exec mini-dify-db psql -U postgres -d minidify -c "\di+ chunks_embedding_hnsw"
# → Did not find any relation named "chunks_embedding_hnsw".
```

检索仍然**正确**（顺序扫描），但数据量一大就慢；更糟的是，这个「隐形的性能退化」不会报错，容易被忽略。

**为什么 Prisma 不认识它**

- Prisma schema 的 `@@index` 只支持 btree 等常规索引，**没有 `USING hnsw` 的表达方式**。
- 迁移引擎按「schema ↔ 数据库」做 diff；数据库里多出来的索引被视为「drift」，默认动作是删除。
- `Unsupported("vector(1536)")` 只描述**列类型**，不描述**索引类型**。

**正确处置（本项目采用）**

1. **每次 `migrate dev` 后先看生成的 `migration.sql`**：
   - 若出现 `DROP INDEX "chunks_embedding_hnsw"`，**删除整个自动生成的迁移目录**（不要应用）。
2. **手工重建索引**（幂等）：

```bash
docker exec mini-dify-db psql -U postgres -d minidify -c \
  "CREATE INDEX IF NOT EXISTS chunks_embedding_hnsw ON chunks USING hnsw (embedding vector_cosine_ops);"
```

3. **确认索引还在**（每次迁移后都做）：

```bash
docker exec mini-dify-db psql -U postgres -d minidify -c "\di+ chunks_embedding_hnsw"
docker exec mini-dify-db psql -U postgres -d minidify -c \
  "SELECT indexdef FROM pg_indexes WHERE indexname = 'chunks_embedding_hnsw';"
```

**替代方案与取舍**

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| **删自动迁移 + 手工重建**（本项目） | 每次迁移后检查、重建 | 简单直接；依赖人记得检查 |
| `migrate dev --create-only` + 编辑 | 生成迁移但不应用，手工把 `DROP` 改成 `CREATE INDEX IF NOT EXISTS` | 迁移历史里保留索引；仍需人工审查 |
| 把索引放进独立 SQL 脚本 | 启动 / 部署时执行 `CREATE INDEX IF NOT EXISTS` | 与 Prisma 迁移解耦；多一步部署动作 |
| 换 ORM（如 Drizzle / TypeORM） | 支持自定义索引类型 | 工程量大，不适合本教学项目 |

**为什么不在 Prisma schema 里「假装」有这个索引**

- 写不进去：schema 语言没有 HNSW 语法。
- 即使能写，`migrate dev` 也可能因为「表达式 / 算子类」不被支持而反复 drift。
- 所以「**以数据库为准，迁移后检查**」是当前最稳的做法。

> **一句话**：**Prisma 管得了表与列，管不了 HNSW；每一次迁移之后，都要用 `\di` 确认索引还在——这不是可选的「优化」，而是 RAG 性能的生命线。**

## 8. 【技术讨论 5】mock 的哈希向量器：无密钥也能验证「语义相近 → 分数更高」

**问题**：验收环境没有真实嵌入 API 的密钥，怎么证明「检索真的在工作」，而不是「随便返回几条」？

**答案：mock-LLM 提供一个**确定性哈希向量器**——同一段文本永远得到同一个 1536 维向量，共享词越多、余弦相似度越高。**

**算法（`tools/mock-llm/server.mjs`）**

```
1. text.toLowerCase() 后按空白切词；
2. 每个 CJK 字符单独作为一个 token（中文没有空格）；
3. 每个 token 用 FNV-1a 32 位哈希 → bucket = hash % 1536；
4. vec[bucket] += 1（词袋计数）；
5. L2 归一化（除以范数；范数为 0 返回全 0 向量）。
```

```js
function hashVector(tokens) {
  const vector = new Array(1536).fill(0)
  for (const token of tokens) {
    vector[fnv1a32(token) % 1536] += 1
  }
  const norm = Math.sqrt(vector.reduce((sum, v) => sum + v * v, 0))
  return norm === 0 ? vector : vector.map((v) => v / norm)
}
```

**这段在干什么**：把文本变成「1536 维的词袋直方图」，再归一化成长度为 1 的向量。归一化后，**余弦相似度 = 点积**，计算简单且稳定。

**为什么它能验证「语义相近 → 分数更高」**

- 「退款怎么申请」与退款文档共享 `退款` / `申请` 等 token → 命中相同的 bucket → 点积大 → `score` 高。
- 与配送文档共享的词少 → 点积小 → `score` 低。
- 这不是**语义**理解（同义词「退货」与「退款」不共享 token，分数不会高），而是**词面**相似；但足以证明「检索链路按相似度排序」这件事是对的。

**实测分数的含义（L6）**

```
0.5884331464767456   ← 「退款怎么申请」与 refund#0：共享词最多
0.4971181748579854   ← 与 refund#1：共享词次之
0.13314714930687654  ← 与 delivery#1：几乎不共享
```

分数依次下降，说明排序方向与相似度计算都正确；如果顺序反了，先查 `ORDER BY` 是否写成 `DESC`。

**为什么必须确定性**

- 两端的 `score` 要**逐位相同**：哈希 + 取模 + L2 归一化都是确定性的，只要输入文本相同，输出向量就相同。
- 不需要密钥、不依赖网络、不受 provider 版本影响——CI / 本地都能跑。
- 维度固定 1536，与 `vector(1536)` / HNSW 完全对齐。

**局限（必须知道）**

- **没有语义**：同义词、缩写、跨语言都不行；真实嵌入模型才有语义空间。
- **哈希碰撞**：不同 token 落到同一个 bucket 会互相干扰；1536 维下概率不高，但不是零。
- **词袋无序**：`A 打 B` 与 `B 打 A` 向量相同；真实模型会区分语序。
- **只适合自测**：生产必须换成真实嵌入模型，并重新评估召回质量。

> **一句话**：**mock 的哈希向量器不是「假装有嵌入」，而是「用一个确定性的词袋模型，把检索链路跑通并让分数可复现」——它验证的是管道与排序，不是语义智能。**

## 9. 常见坑汇总（跨阶段 7）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **迁移后 HNSW 索引被删** | `\di` 找不到 `chunks_embedding_hnsw`；检索变慢但不报错 | `prisma migrate dev` 生成了 `DROP INDEX`；删除该自动迁移并手工重建（§7） |
| 2 | **向量维度与列定义不一致** | `expected 1536 dimensions, not N` | `EMBEDDING_MODEL` 返回的维度不是 1536；换模型或改迁移（不能只改代码） |
| 3 | **两端切分参数不同步** | `chunkCount` 不同 / `sha256` 对不上 | 500/80/分隔符/`keep_separator` 必须逐项一致（§5） |
| 4 | **`len` 用字符数比较** | 中文文档的 `len` 对不上 | `len` 指 **UTF-8 字节数**；用 `content.encode('utf-8')` |
| 5 | **`score` 用 `toFixed(3)` 比较** | 验收失败 | 展示 3 位，断言用全精度（`04` §7.5） |
| 6 | **`ORDER BY <=>` 写成 `DESC`** | 命中「最不相关」的块 | 距离升序 = 分数降序 |
| 7 | **检索 SQL 忘记 `WHERE knowledge_base_id`** | 跨库 / 越权召回 | 归属过滤必须在 SQL（`03` / `04`） |
| 8 | **`EMBEDDING_MODEL` 没设 / 用了默认** | 请求打到真实 OpenAI，401 / 维度错 | `.env` 显式 `EMBEDDING_MODEL=mock-embedding` 并重启 |
| 9 | **api-py 读 `os.environ`** | `.env` 的值静默失效 | pydantic-settings 不回写进程环境；读 `settings.*`（`04` §5.5） |
| 10 | **上传手写 `Content-Type`** | 400 `Document is empty` | `FormData` 不设 Content-Type，字段名 `file`（`04` §7.2） |
| 11 | **未知工具 / 未知库的 nodeId 写错** | 文案对不上 | 文案里的 `{nodeId}` 是图里的节点 id（本例 `kb_1`） |
| 12 | **无密钥时以为还有 `retrieval`** | 等不到事件，以为卡住 | 嵌入失败 → 直接 `run_failed`；**不发** `retrieval` / `node_finished` |
| 13 | **用 `SELECT *` 把向量读出来比较** | 结果巨大 / 浮点格式不同 | 只取 `content` / `chunk_index` / `document_id`；向量不参与比对 |
| 14 | **删知识库后旧 chunk 还在** | 检索仍能命中已删库的内容 | 数据库 `ON DELETE CASCADE` 应带走；若没有，检查迁移外键 |
| 15 | **B 访问 A 的库返回 403** | 泄露「该库存在」 | 统一 404 `Knowledge base not found`（§3.3） |

## 10. 本篇复盘与知识点

**一句话总结阶段 7**：在既有图模型上新增一个 `knowledge` 节点，把「上传 → 切分 → 嵌入 → 写 pgvector → 余弦检索」做成一条可复现的链路；两套后端在**切分参数、向量维度、SQL 形状、错误文案**上逐项对齐，于是同一份原文切出的 6 个 chunk 的 `len + sha256` 逐项相同、同一 query 的 `score` 精确到浮点末位相同、`context` 逐字节相同；Prisma 用 `Unsupported` 承认不认识向量、用原生 SQL 读写，SQLAlchemy 用 `Vector(1536)` 原生映射但同样走原生 SQL；HNSW 索引必须手工维护，每次 `migrate dev` 后都要用 `\di` 确认它还在。

**本篇学到的工程 / 架构要点**

1. **阶段 7 补上「先检索私有资料再回答」**：RAG = 检索（召回原文）+ 生成（模型基于 context 作答），引用来自 `retrieval` 事件。
2. **参数即契约**：500/80/分隔符/`keep_separator`/1536/`score` 公式/排序/`context` 分隔符，任意一项漂移都会让 `sha256` 与 `score` 分叉。
3. **Prisma vs SQLAlchemy 的 pgvector**：一个用 `Unsupported` + `$queryRaw` 逃生，一个有 `Vector(n)` 原生类型；本项目统一走原生 SQL 保证两端同构。
4. **HNSW 与 Prisma 迁移冲突**：`migrate dev` 会生成 `DROP INDEX "chunks_embedding_hnsw"`；删除自动迁移并手工重建，迁移后必查 `\di`。
5. **mock 哈希向量器**：确定性词袋 + FNV-1a + L2 归一化，让无密钥环境也能验证「共享词多 → 分数高」；它验证管道与排序，不验证语义。
6. **分层验收**：契约 → 库结构与索引 → CRUD → 上传切分 → chunk 逐字节 → 检索全精度 → 运行 / 错误 / 回归，逐层自证。
7. **错误分类**：接口 400/404、预检 400、运行流内 `run_failed` 三个通道，文案逐字一致且不泄露资源存在性。

**遗留到下阶段**

- HNSW 与 Prisma 迁移的冲突尚未自动化（目前靠人工检查 `\di`）。
- 没有 rerank、混合检索、query 改写；召回质量只有「调试面板」这一层观测。
- 知识库页无分页 / 重命名 / 重新处理；文档只支持文本类。
- 引用只在面板展示，未写入 `run_finished.outputs`，也未做「点击跳转原文」。
- FastAPI 侧无请求体大小上限（只在上传服务里判 1MB）。
- 把 L2~L7 固化成 CI 断言（索引存在、chunk 哈希、score 全精度、9 组错误文案）。

**基础技术要点**：RAG · 向量 / 余弦相似度 · pgvector `vector(n)` 与 `<=>` · HNSW（`vector_cosine_ops`） · `RecursiveCharacterTextSplitter` 参数 · `Vector(1536)` vs `Unsupported` · 原生 SQL 的 `CAST(... AS vector)` · 维度校验 · 嵌入错误映射 · `retrieval` 事件与引用 · `topK` 与 `score = 1 - distance`。
