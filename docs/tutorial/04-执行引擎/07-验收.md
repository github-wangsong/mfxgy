## 1. 本篇目标

做完这一篇，你能：

- 沿**依赖顺序**逐层验收阶段 4：契约编译 → **LangGraph 依赖就位** → 两套后端各跑一张图返回 **SSE 流** → **两端事件序列逐项一致** → **token 分片逐字节一致** → **反向用例两端一致** → 浏览器全链路。
- 用**可直接复制的命令**证明两套后端「行为一致」：**事件名序列一致**、**payload 键集合一致**、**帧格式逐字节一致**（除 `runId` / `elapsedMs` 两处不定的值外）。
- 讲清楚**为什么阶段 4 是项目的质变点**：从「图 = 数据」（阶段 3 的**存取 + 校验**）进入「**数据 → 可执行程序**」——`Graph`(JSON) 被**编译**成 LangGraph `StateGraph` 并**执行**，产出流式事件。
- 讲清楚**LangGraph 带来的能力边界**：本阶段只用了**线性拓扑**；**条件边 / 循环 / checkpoint / HITL** 是后续阶段（8 / 9 / 11）的原生扩展点。
- 讲清楚 **SSE 的双通道错误设计**：请求级 **400（普通 JSON）** vs 运行期 **`run_failed`（流内事件）**——为什么必须这样分。
- 讲清楚「契约一致」在本阶段**新增的层次**：**事件序列与帧格式的一致**（而不只是响应体的形状）。

## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序（先契约与依赖、后两端流、再一致性、最后反向与前端）

```
L1 契约编译        L2 依赖就位
      ↓                    ↓
L3 两端各跑一张图（SSE 流）
      ↓
L4 事件序列一致 → L5 token 分片一致 → L6 反向用例一致 → L7 浏览器
```

**为什么按这个顺序**：契约不编译 / `RunRequest` 不存在，路由与 DTO 对不上；LangGraph 不在，`StateGraph` 无法编译；两端各自能出流之后，「序列一致 / 分片一致 / 反向一致」才有意义；最后才是浏览器。

### 3.3 L3 —— 两套后端各跑一张图，返回 SSE 流

**在哪执行**：任意目录（用 `127.0.0.1`）

**先建一个应用并保存一张 `start → llm → end` 的图**（`llm` 桩节点按模板渲染 prompt）：

```bash
APP_ID=$(curl -s -X POST http://127.0.0.1:3001/apps \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"run-demo","mode":"workflow"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['id'])")

curl -s -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"start_1","type":"start","position":{"x":0,"y":0},
         "data":{"title":"开始","inputs":[{"name":"topic","type":"string","required":true}]}},
        {"id":"llm_1","type":"llm","position":{"x":0,"y":160},
         "data":{"title":"LLM","model":"gpt-4o","prompt":"Hello {{ inputs.topic }}"}},
        {"id":"end_1","type":"end","position":{"x":0,"y":320},
         "data":{"title":"结束","outputs":[{"name":"result","value":"{{ llm_1.text }}"}]}}
      ],"edges":[
        {"id":"e1","source":"start_1","target":"llm_1","sourceHandle":null,"targetHandle":null},
        {"id":"e2","source":"llm_1","target":"end_1","sourceHandle":null,"targetHandle":null}
      ]}' > /dev/null
```

**两端各发一次运行请求**（`-N` 关闭 curl 缓冲，`-i` 看响应头；`-s` 静默进度）：

```bash
# api-ts（NestJS）—— 先看响应头确认 Content-Type
curl -s -i -N -X POST http://127.0.0.1:3001/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{"topic":"mini-dify"}}'

# api-py（FastAPI）—— 同一 token（同一认证域）
curl -s -i -N -X POST http://127.0.0.1:8000/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{"topic":"mini-dify"}}'
```

**预期输出（实测·两端相同）**

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

event: run_started
data: {"runId":"3f2b…","appId":"<APP_ID>"}

event: node_started
data: {"nodeId":"start_1","nodeType":"start"}

event: node_finished
data: {"nodeId":"start_1","nodeType":"start","output":{"inputs":{"topic":"mini-dify"}}}

event: node_started
data: {"nodeId":"llm_1","nodeType":"llm"}

event: token
data: {"nodeId":"llm_1","text":"Hello mi"}

event: token
data: {"nodeId":"llm_1","text":"ni-dify"}

event: node_finished
data: {"nodeId":"llm_1","nodeType":"llm","output":{"text":"Hello mini-dify"}}

event: node_started
data: {"nodeId":"end_1","nodeType":"end"}

event: node_finished
data: {"nodeId":"end_1","nodeType":"end","output":{"outputs":{"result":"Hello mini-dify"}}}

event: run_finished
data: {"runId":"3f2b…","outputs":{"result":"Hello mini-dify"},"elapsedMs":31}
```

**结果解读（两个关键点）**：

- **成功路径先开流、再执行**：预检（草稿非空 / 图合法 / 节点数据形状）全部通过后，才 `flushHeaders` 打开 `text/event-stream`；`run_started` 是流的**第一帧**（见第 6 节「双通道」）。
- **两端 `Content-Type` 都是 `text/event-stream`**：TS 用底层 `Response` 手写；Py 用 `StreamingResponse` 并**显式给 `headers={"Content-Type": "text/event-stream"}`**，避免 Starlette 追加 `; charset=utf-8`（承 `05-SSE流式响应实现.md`）。

### 3.4 L4 —— 两端事件序列**逐项一致**（除 `runId` / `elapsedMs`）

**在哪执行**：任意目录
**目的**：这是阶段 4 的一致性核心——**事件名序列**必须逐项相同，**payload 键集合**一致，且**除 `runId`/`elapsedMs` 外逐字节相同**。

```bash
# 各抓一份原始流到文件
curl -s -N -X POST http://127.0.0.1:3001/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{"topic":"mini-dify"}}' > ts.sse
curl -s -N -X POST http://127.0.0.1:8000/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{"topic":"mini-dify"}}' > py.sse

# 抽「事件名序列」比对（逐项相同）
grep '^event:' ts.sse | sed 's/^event: //' > ts.names
grep '^event:' py.sse | sed 's/^event: //' > py.names
diff ts.names py.names && echo "SEQUENCE IDENTICAL"

# 归一后整帧比对（抹掉 runId / elapsedMs）
sed -E 's/"runId":"[^"]*"/"runId":"X"/g; s/"elapsedMs":[0-9]+/"elapsedMs":N/g' ts.sse > ts.norm
sed -E 's/"runId":"[^"]*"/"runId":"X"/g; s/"elapsedMs":[0-9]+/"elapsedMs":N/g' py.sse > py.norm
diff ts.norm py.norm && echo "FRAMES IDENTICAL (except runId/elapsedMs)"
```

**预期输出（实测）**

```
SEQUENCE IDENTICAL
FRAMES IDENTICAL (except runId/elapsedMs)
```

**事件名序列（两端一致，共 10 帧）**

```
run_started
node_started
node_finished
node_started
token
token
node_finished
node_started
node_finished
run_finished
```

**payload 键集合（两端一致）**

| 事件 | 键集合 |
| --- | --- |
| `run_started` | `runId` `appId` |
| `node_started` | `nodeId` `nodeType` |
| `token` | `nodeId` `text` |
| `node_finished` | `nodeId` `nodeType` `output` |
| `run_finished` | `runId` `outputs` `elapsedMs` |
| `run_failed` | `runId` `nodeId` `message` |

**结果解读**：

- **帧格式固定**：每帧 `event: <name>\n` + `data: <单行 JSON>\n\n`（唯一真源 `sse-events.md` §1）。两端的序列化实现不同（TS `JSON.stringify` ↔ Python `json.dumps(ensure_ascii=False, separators=(",",":"))`），但**产出的单行 JSON 逐字节相同**。
- **唯一的差异是「值不定」的两处**：`runId`（每次运行的 UUID）与 `elapsedMs`（每次耗时），用归一后即完全一致。
- **节点按拓扑序、各执行一次**，从 `start` 出发；`start → llm → end` 就是本阶段的**线性拓扑**（见第 5 节能力边界）。

### 3.5 L5 —— token 分片一致 + `run_finished.outputs` 一致

**在哪执行**：任意目录
**目的**：证明「流式分片」这一**引擎语义**两端一致，且最终输出一致。

```bash
# 抽 token 帧的 text（两端应同为 "Hello mi" + "ni-dify"）
grep -A1 '^event: token' ts.sse | grep '^data:' | sed 's/^data: //'
grep -A1 '^event: token' py.sse | grep '^data:' | sed 's/^data: //'

# 抽 run_finished 的 outputs
grep -A1 '^event: run_finished' ts.sse | grep '^data:'
grep -A1 '^event: run_finished' py.sse | grep '^data:'
```

**预期输出（实测·两端相同）**

```
# token 分片（每 8 个 Unicode 码点一片）
data: {"nodeId":"llm_1","text":"Hello mi"}
data: {"nodeId":"llm_1","text":"ni-dify"}

# run_finished.outputs
data: {"runId":"3f2b…","outputs":{"result":"Hello mini-dify"},"elapsedMs":31}
```

**结果解读（三个一致点）**：

- **分片口径（每 8 个码点一片）**：`"Hello mini-dify"` 共 15 个码点 → 第 1 片 `"Hello mi"`（8） + 第 2 片 `"ni-dify"`（7）。TS 用 `Array.from(text)`（按码点）切片；Python 的 `str` 索引**天然按码点**（`text[i:i+8]`），因此**分片逐字节一致**（承 `03-节点运行时与变量池.md`）。
- **渲染结果**：`prompt = "Hello {{ inputs.topic }}"`，`pool.inputs.topic = "mini-dify"` → `"Hello mini-dify"`。
- **`end` 输出**：`end_1.outputs = [{name:"result", value:"{{ llm_1.text }}"}]` → `{"result":"Hello mini-dify"}`，即 `run_finished.outputs`（承 `sse-events.md` §4「多 `end` 取拓扑序最后一个」）。

### 3.6 L6 —— 反向用例（两端一致）

**在哪执行**：任意目录
**目的**：证明「失败」也两端一致——且**分清两种通道**：请求级 400（普通 JSON）vs 流内 `run_failed`。

#### 6.1 空草稿 → `400 Graph is empty`（**普通 JSON，不是流**）

```bash
# 建一个「从未编辑过图」的应用
EMPTY_APP_ID=$(curl -s -X POST http://127.0.0.1:3001/apps \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"empty-demo","mode":"workflow"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['id'])")

curl -s -i -X POST http://127.0.0.1:8000/apps/$EMPTY_APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{}}'
```

**预期输出（实测·两端相同）**

```
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"statusCode":400,"message":"Graph is empty","error":"Bad Request"}
```

#### 6.2 图非法 → 400 图校验文案

```bash
# 把草稿改成一幅缺 end 的非法图（PUT 本身就会 400；这里直接构造非法草稿需要绕过 PUT，
# 故改为观察「PUT 非法图」的 400 与「运行非法草稿」的 400 同源文案）
BODY='{"version":"1","nodes":[
        {"id":"start_1","type":"start","position":{"x":0,"y":0},"data":{}},
        {"id":"llm_1","type":"llm","position":{"x":0,"y":160},"data":{"prompt":"hi"}}
      ],"edges":[{"id":"e1","source":"start_1","target":"llm_1"}]}'
curl -s -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' -d "$BODY"
curl -s -X PUT http://127.0.0.1:8000/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' -d "$BODY"
```

**预期输出（实测·两端逐字节相同）**

```
{"statusCode":400,"message":"graph must contain at least one end node","error":"Bad Request"}
```

> 运行时的**节点数据形状**校验与图校验**合并为一条 `message`**（承 `error-messages.md` §4.1）：先跑 §3 图校验（保持内部顺序），再跑节点数据校验（按 `nodes` 顺序）。例：`start.data.inputs` 不是数组 → `start node start_1 inputs must be an array`。

#### 6.3 模板变量不存在 → 流内 `run_failed`

```bash
# 换一张 llm.prompt 引用不存在路径的图（图本身合法，错误发生在运行时）
curl -s -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"start_1","type":"start","position":{"x":0,"y":0},
         "data":{"title":"开始","inputs":[{"name":"topic","type":"string","required":true}]}},
        {"id":"llm_1","type":"llm","position":{"x":0,"y":160},
         "data":{"title":"LLM","model":"gpt-4o","prompt":"Hello {{ inputs.nope }}"}},
        {"id":"end_1","type":"end","position":{"x":0,"y":320},
         "data":{"title":"结束","outputs":[{"name":"result","value":"{{ llm_1.text }}"}]}}
```

## 4. 【技术讨论 1】阶段 4：从「图 = 数据」到「数据 → 可执行程序」

**问题**：阶段 3 已经把图**存下来**并**校验过**了，阶段 4 到底「新」在哪？为什么总纲把阶段 4 称为**分水岭**（总纲 §6）？

**答案的一句话**：**阶段 4 是「执行」**。阶段 3 结束时会「**存取与校验一张图**」；阶段 4 结束时会「**把一张图跑起来**」——同一个 `Graph`(JSON)，第一次成为一个**可执行程序**。

**分层的职责边界**

| 层 | 阶段 3（图 = 数据） | 阶段 4（执行） |
| --- | --- | --- |
| 输入 | `Graph`(JSON) | `Graph`(JSON) + `RunRequest.inputs` |
| 核心动作 | **存取**（JSONB）+ **校验**（纯函数 7 规则） | **编译**（JSON → LangGraph `StateGraph`）+ **执行** |
| 输出 | 同一份 JSON 文档 | **SSE 事件流**（`run_started` … `run_finished`） |
| 不变式 | 「存的图是自洽的」 | 「**同一份图、两套引擎、同一条事件序列**」 |

**「编译思维」是阶段 4 的认知跳跃**

- 阶段 3 眼里，图是**文档**（`nodes` + `edges` 两个数组，整块塞进 `jsonb`）。
- 阶段 4 眼里，图是**程序**：`nodes` 是「要跑的算子」，`edges` 是「算子间的数据流」，`start` 是入口、`end` 是出口。
- 连接两副眼镜的，是一个**编译动作**（两端的实现惊人一致，因为都用了 LangGraph）：

  | 图里的东西 | 编译到 LangGraph |
  | --- | --- |
  | `nodes[]` | 逐个 `addNode(node.id, action)` |
  | `edges[]` | 逐个 `addEdge(source, target)` |
  | `start` 节点 | `addEdge(START, start.id)` |
  | 每个 `end` 节点 | `addEdge(end.id, END)` |
  | — | `compile().invoke({ pool: { inputs } })` |

> 一句话：**阶段 3 把「图」变成了能存的文档；阶段 4 把「图」变成了能跑的程序。** 同一份 `Graph` 契约，前后两端视角不同——这正是「**数据 → 可执行程序**」的质变。

## 5. 【技术讨论 2】LangGraph 的能力边界：本阶段只用了线性拓扑

**问题**：LangGraph 号称能表达条件、循环、持久化……为什么本阶段「只用」了一点？

**答案的一句话**：阶段 4 的验收标准是「**调试页能逐字输出**」（总纲 §6），只需要证明「**JSON → StateGraph → 流式输出**」这条**最小链路**跑通；LangGraph 的其余能力，是留给后续阶段的**原生扩展点**。

**本阶段真正用到的 LangGraph 能力**

| 能力 | 本阶段用法 | 出处 |
| --- | --- | --- |
| `StateGraph` 构建器 | `new StateGraph(RunState)` / `StateGraph(RunState)` | `02`（TS）/ `04`（Py） |
| **State 注解 + reducer** | `pool` 用「合并」reducer：节点返回 `{pool:{<id>:<output>}}` 逐步累积 | 同上 |
| `START` / `END` | `START → start`、`end → END` | 同上 |
| `compile` / `invoke` | `compile().invoke({pool:{inputs}})`（Py 用 `ainvoke`） | 同上 |
| **线性拓扑** | `addNode` + `addEdge` 逐条连边 | 同上 |

**「节点 = 纯函数」的心智模型**

- LangGraph 的节点就是一个函数：**收到 state → 返回对 state 的「更新」**。本工程里节点返回 `{ pool: { [nodeId]: output } }`，由 reducer 合并进 `pool`。
- 正因为节点是纯的（只读 `state.pool`、只回写自己的输出），**「变量池」才是一个干净的数据流**：`pool.inputs` 进 → 各节点依次写入 `pool[nodeId]` → 模板按点路径取值。事件（`node_started` / `token` / `node_finished`）通过**自建队列**旁路产出，与执行器解耦。
- 关键取舍：**事件不走 LangGraph 的 custom stream**，而走自建 `RunEventQueue`（TS）/ `asyncio.Queue`（Py）——这样才能保证**两端事件顺序与 payload 完全可控、逐字节可比**（见第 6 节）。

**扩展点（本阶段不碰，但已预留）**

| 能力 | 后续阶段 | 说明 |
| --- | --- | --- |
| **条件边**（按 state 选下一条边） | 阶段 8 · 条件 / 变量 / 迭代 | `addConditionalEdges` |
| **循环** | 阶段 8 | 回到已执行节点 |
| **checkpointer / 断点续跑** | 阶段 9 · 会话与记忆 | `@langchain/langgraph-checkpoint-postgres`（总纲 §5 已点明） |
| **HITL / `interrupt`** | 阶段 11 · 自主 Agent 运行时 | 工作流暂停等人工输入 |

> 一句话：**本阶段把 LangGraph 当作「一个能线性跑完全图、并在过程中吐事件」的编排器**；它的陡峭部分（条件 / 循环 / checkpoint）刻意留到需要它们的阶段——这正是总纲「阶段 3/4 先用最小 StateGraph，逐步加复杂度」的落地。

## 6. 【技术讨论 3】SSE 的双通道错误设计，与「契约一致」的新增层次

### 6.1 双通道：请求级 400（JSON）vs 运行期 `run_failed`（流内）

一个运行请求，可能在三处失败，而它们**分属两个通道**：

| 阶段 | 失败点 | 通道 | 表现 |
| --- | --- | --- | --- |
| **开流前**（预检） | 归属不符 | **请求级** | `404 App not found`（普通 JSON） |
| | 未认证 | **请求级** | `401 Missing bearer token`（普通 JSON） |
| | 草稿为空 / 图非法 / 节点数据形状非法 | **请求级** | `400`（普通 JSON），`message` 由多条用 `"; "` 连接 |
| **开流后**（执行中） | 缺必填输入 / 模板取值失败 / 其它执行期异常 | **运行期** | 流内 `run_failed` 事件（HTTP 仍是 `200`） |

**为什么必须这样分（三条硬约束）**

1. **HTTP 状态码**（在 `flushHeaders` 那一刻就已固定为 `200`）**无法再改**。一旦开始吐 SSE 帧，就没有「回头报 400/404」的机会——所以**凡是要非 2xx 的失败，必须在开流前判定**。这就是「**先校验、后开流**」。
2. **错误信息的形状不同**：预检是「**整请求**级」的（一次可级联多条规则成一条 `message`），运行期是「**定位到某个节点**」的（`run_failed` 带 `nodeId`，无法归属节点时为 `null`）。两种语义无法塞进同一条通道。
3. **消费方不同**：预检失败时前端还没拿到流，只能按**普通 JSON**读 `message`；因此前端**必须先判 `content-type`**（`text/event-stream` 才是流，否则按 JSON 读错误），这一步在 `06` 有讲。

> 一句话：**「能预检的失败，一律在开流前用普通 JSON 报；只有『跑着跑着才发生』的失败，才走流内 `run_failed`。」**

### 6.2 「契约一致」在阶段 4 新增的层次：**事件序列与帧格式一致**

> 回顾：阶段 0 · 08 拆出「结构一致 / 值规范一致」两层；阶段 2 · 07 收口错误信封与时间戳；阶段 3 · 07 推进到「业务校验文案逐字节一致 + JSONB 往返形状一致」。

阶段 4 的一致性对象**变了性质**：前面的阶段比的是**一次请求 → 一个响应体**；阶段 4 比的是**一段有无穷多帧的过程**。于是新增了三个层次：

| 层 | 内容 | 实测证据 |
| --- | --- | --- |
| **事件序列一致** | 帧的**顺序**逐项相同（事件名序列） | L4：`diff ts.names py.names` 无差异 |
| **payload 键集合一致** | 每个事件的键集合相同；帧内 JSON **逐字节相同**（除 `runId`/`elapsedMs`） | L4：归一后整帧 `diff` 无差异 |
| **分片语义一致** | `token` 的切片口径（每 8 个码点）与渲染结果一致 | L5：`"Hello mi"` + `"ni-dify"` |

**为什么这更难**：响应体比对只需「一次序列化相等」；事件流比对要求**两套独立的执行器**在**每一步**（节点调度顺序、token 切片、错误归属）上都做同样的决定。唯一真源是 `packages/contract/sse-events.md`——**事件协议本身就是契约**（承 `01-运行契约与SSE事件协议.md`：协议是唯一真源，改事件或顺序必须同步更新本文件与两端）。

> 关键认知：**契约从「响应体的形状」扩展到了「过程的形状」**。这也是为什么本阶段两端的实现都**刻意弃用**各自框架自带的事件流设施（TS 弃 `@Sse()`、Py 走 `StreamingResponse` + 自建队列），改用自建队列——**可控、可比**优先于「用现成的」。

## 7. 常见坑汇总（跨阶段 4）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **用 `EventSource` 发起运行** | 请求 401 / 收不到流 | 浏览器 `EventSource` **不能携带 `Authorization` 头**，也不能发 `POST`。改用 `fetch` + `response.body.getReader()`，自己按帧解析（见 `06`） |
| 2 | **把预检 400 当流处理** | 前端拿到 400 却去 `parseSseStream`，报解析错 | 预检失败返回的是**普通 JSON**（`application/json`）。前端**先判 `content-type`**：非 `text/event-stream` 就按 JSON 读 `message`（`06`） |
| 3 | **token 不逐段显示** | 事件日志一条条出，但流式文本框一次性闪出全文 | React 对 `setState` **批处理**：一个微任务内的多次更新只渲染一次。**逐事件 `await` 一次宏任务让出**（`yieldToPaint` = `setTimeout(0)`）即可（`06`） |
| 4 | **`content-type` 多了 `; charset=utf-8`** | 前端 `includes('text/event-stream')` 侥幸过、`===` 比对失败 | Starlette 的 `StreamingResponse` 会追加 charset。Py 侧**显式给 `headers={"Content-Type": "text/event-stream"}`** 覆盖，与 api-ts 对齐（`05`） |
| 5 | **`TextDecoder` 没带 `{stream:true}`** | 中文/多字节字符偶尔乱码 | 网络分块会在任意**字节**处切断，多字节 UTF-8 字符被切两半。必须 `decoder.decode(value, {stream:true})` 增量解码（`06`） |
| 6 | **分帧假设「一 chunk 一帧」** | 偶发漏帧 / 半帧 | 一个帧、甚至一行都可能**跨 chunk**。必须用**缓冲区**拼接，按最近的 `\n` 切行（`06`） |
| 7 | **用 `@Sse()` 返回** | 帧格式出现偏差，两端比对不一致 | NestJS `@Sse()` 的序列化细节不可控。改用底层 `@Res()` + `Response` **手写 `event: …\ndata: …\n\n`**（`05`） |
| 8 | **模板点路径写错** | 运行报 `run_failed template variable not found: inputs.nope` | 模板按**点路径**从 `pool` 取值（`{{ inputs.topic }}` / `{{ <llmId>.text }}`），花括号内允许空格；路径任一段不存在即抛错 |
| 9 | **`run_failed` 却没看到 400** | 以为「失败应该 400」 | 缺必填输入 / 模板取值失败发生在**已开流之后**，属**流内** `run_failed`（HTTP 已 200）。只有预检失败才是 400（见第 6 节） |
| 10 | **非字符串模板值渲染不一致** | 两端把 `0.7` 渲染成 `0.7` vs `0.7000001` 之类 | 渲染值非字符串时按**紧凑 JSON 序列化**：TS `JSON.stringify` ↔ Py `json.dumps(ensure_ascii=False, separators=(",",":"))`（`03`） |
| 11 | **重启后 LangGraph 版本漂移** | 两端行为细微不一 | `@langchain/langgraph` 用 `^1.5.1`、`langgraph` 钉 `>=1.2.16`（`uv.lock` 锁到 `1.2.16`）；升级时以契约为准、跑 L4/L5/L6 |
| 12 | **`localhost` 解析竞态** | `curl` 偶发连不上 | 统一用 `127.0.0.1`（见 `00-项目初始化/08` §7） |
| 13 | **前端未登录进画布页** | 显示 401 而非跳登录 | 进页面先查 token、`null` 或 `401` 就 `router.replace('/login')`（阶段 2 · 06） |

## 8. 本篇复盘与知识点

**一句话总结阶段 4**：在两套后端实现 `POST /apps/{id}/run`，用 **LangGraph** 把契约里的 `Graph` **编译**成 `StateGraph` 并按拓扑序**执行**，以 **SSE** 流式返回「事件序列 + token 分片」；两端的事件名序列、payload 键集合、帧格式**逐字节一致**（除 `runId` / `elapsedMs`）；前端用 `fetch + getReader`（因 `EventSource` 无法带鉴权）在调试面板里**逐字**跑出来。

**本篇学到的工程/架构要点**

1. **阶段 4 是质变点**：从「存取与校验」（阶段 3）进入「**执行**」——`图 = 数据` 变成「**数据 → 可执行程序**」，连接两副眼镜的是一个**编译动作**（`addNode`/`addEdge`/`START`/`END`/`compile`/`invoke`）。
2. **分层验收**：契约编译 → 依赖就位 → 两端出流 → **事件序列一致** → **token 分片一致** → **反向用例一致** → 浏览器，逐层自证。
3. **LangGraph 能力边界**：本阶段只用**线性拓扑 + State(reducer) + START/END + compile/invoke**；**条件边 / 循环 / checkpoint / HITL** 是阶段 8 / 9 / 11 的原生扩展点。
4. **SSE 双通道错误**：请求级 **400/401/404（普通 JSON，开流前）** vs 运行期 **`run_failed`（流内，HTTP 已 200）**——因为状态码开流后无法改，且两类错误的形状与语义不同。
5. **契约一致新增一层**：从「响应体的形状」扩展到「**过程的形状**」——**事件序列 + 帧格式**必须两端一致；唯一真源是 `packages/contract/sse-events.md`。
6. **「节点 = 纯函数」+ 自建事件队列**：节点只读 `pool`、只回写自己的输出；事件走自建队列（TS `RunEventQueue` / Py `asyncio.Queue`）而非框架自带流，以换取**可控可比**。

**遗留到下阶段**

- 契约测试双跑自动化：把本文 L4/L5/L6 的「事件序列一致 / 分片一致 / 反向一致」固化成 CI 断言。
- **LLM 节点完善**（真实模型、参数面板）是**阶段 5** 的主题（本阶段 `llm` 是**桩**：渲染 prompt 后按 8 码点切片，不调用真实模型）。

**基础技术要点**：LangGraph `StateGraph` / State + reducer / `compile`-`invoke` · SSE 帧格式与事件协议 · 双通道错误 · 模板变量池 · 流式分片 · `fetch + ReadableStream` 前端消费。
