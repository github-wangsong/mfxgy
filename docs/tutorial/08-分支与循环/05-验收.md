## 1. 本篇目标

做完这一篇，你能：

- 沿**依赖顺序**逐层验收阶段 8：契约 `0.8.0` → 7 种节点类型 → 分支 → 聚合 → 迭代 → 跨语言数值一致 → 错误 + 回归。
- 用可直接复制的命令证明：
  - `condition` 节点选中 `good` 时，SSE 里有**一次** `branch_taken {caseId:"good",label:"好评"}`，且**只执行 `good` 分支**（`else1` 的 `nodeId` 完全没出现）；
  - `topic="服务很差"` 时走 `else`，`branch_taken {caseId:"else",label:"else"}`；
  - `aggregator` 引用**未执行分支**的 `{{ else1.text }}` **不报错**，输出 `{"answer":"echo: PRAISE 服务很好"}`；
  - `items=["A","B","C"]` 产生 **3 个** `iteration_item`（`index` 1/2/3），`outputs.result` 为三行 `第1/3项: A` 等；
  - `items=[1, 2.5, 3.0, {"a":1.0}, {"b":[4.0,5]}]` 时两端 `outputs.result` **逐字节相同**（`1 / 1` … `{"b":[4,5]} / 5`）；
  - 8 组错误（6 条预检 + 2 条运行期）两端文案**逐字一致**；
  - 阶段 5 的 token 序列与 usage、阶段 6 的 `tool_call` / `tool_result`、阶段 7 的 `retrieval` **没有被破坏**。
- 讲清 **条件边是通用机制**：同一个 `addConditionalEdges(source, router, pathMap)`，在阶段 6 是「单出口判断（工具 or 继续）」，在阶段 8 是「多出口映射（caseId → 下游）」。
- 讲清 **跨语言一致性必须细到 `1.0` vs `1`**：JS 只有一种 `number`，Python 有 `int` / `float`；`JSON.stringify` 与 `json.dumps` 的默认输出不同，必须显式归一。

**验收标准（对齐总纲 §6 阶段 8）**

> 能按条件分叉、把分支收敛、对数组循环；两端事件与输出一致。

具体化为下面 7 层**每条命令的「预期输出」都命中**：

| # | 检查层 | 预期 |
| --- | --- | --- |
| L1 | 契约 | `pnpm run build:contract` 成功；`CONTRACT_VERSION` = **`0.8.0`**；`ConditionNodeData` / `AggregatorNodeData` / `IterationNodeData` 就位 |
| L2 | **节点类型** | 7 种：`start` / `llm` / `end` / `knowledge` / `condition` / `aggregator` / `iteration` |
| L3 | **分支** | `topic="服务很好"` → `branch_taken {caseId:"good",label:"好评"}`，**只执行 good 分支**；`topic="服务很差"` → `caseId:"else"` |
| L4 | **聚合** | 未执行分支的 `{{ else1.text }}` 不存在时**不报错**，输出 `{"answer":"echo: PRAISE 服务很好"}` |
| L5 | **迭代** | `items=["A","B","C"]` → 3 个 `iteration_item`（1/2/3）；`results` / `joined` 为 `第1/3项: A\n第2/3项: B\n第3/3项: C` |
| L6 | **跨语言数值** | `items=[1, 2.5, 3.0, {"a":1.0}, {"b":[4.0,5]}]` → 两端 `outputs.result` **逐字节相同** |

## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序（先静态、后动态、最后错误与回归）

```
L1 契约编译(0.8.0) ──> L2 7 种节点类型
                              │
                              ▼
                  L3 分支（good / else 两条路）
                              │
                              ▼
                  L4 聚合（未执行分支的变量）
                              │
                              ▼
                  L5 迭代（3 项 → 3 条进度）
                              │
                              ▼
          L6 跨语言数值序列化（逐字节）
                              │
                              ▼
     L7 6 条预检 + 2 条运行期 → 阶段 5/6/7 回归
```

**为什么按这个顺序**：契约不编译，节点类型与事件类型无从谈起；分支是聚合与迭代的语义前提（「另一条路没走」正是聚合要处理的情况）；迭代与数值序列化是同一个节点的两层验收（先证明「循环次数对」，再证明「每项字符串化对」）；最后用错误与回归证明「新能力没有破坏旧行为」。

### 3.3 L3 —— 分支：只执行被选中的那条路

#### 3.3.1 建一张条件图

**在哪执行**：任意目录

```bash
cat > cond-graph.json <<'JSON'
{
  "version": "1",
  "nodes": [
    {"id":"start_1","type":"start","position":{"x":0,"y":0},
     "data":{"title":"开始","inputs":[{"name":"topic","type":"string","required":true}]}},
    {"id":"cond_1","type":"condition","position":{"x":0,"y":160},
     "data":{"title":"条件分支","conditions":[
       {"id":"good","label":"好评","variable":"{{ inputs.topic }}","operator":"contains","value":"很好"}
     ]}},
    {"id":"good1","type":"llm","position":{"x":-200,"y":320},
     "data":{"title":"好评分支","model":"mock-model","prompt":"PRAISE {{ inputs.topic }}"}},
    {"id":"else1","type":"llm","position":{"x":200,"y":320},
     "data":{"title":"兜底分支","model":"mock-model","prompt":"ELSE {{ inputs.topic }}"}},
    {"id":"agg_1","type":"aggregator","position":{"x":0,"y":480},
     "data":{"title":"变量聚合","outputs":[
       {"name":"answer","values":["{{ good1.text }}","{{ else1.text }}"]}
     ]}},
    {"id":"end_1","type":"end","position":{"x":0,"y":640},
     "data":{"title":"结束","outputs":[{"name":"answer","value":"{{ agg_1.answer }}"}]}}
  ],
  "edges": [
    {"id":"e_start","source":"start_1","target":"cond_1"},
    {"id":"e_good","source":"cond_1","target":"good1","sourceHandle":"good"},
    {"id":"e_else","source":"cond_1","target":"else1","sourceHandle":"else"},
    {"id":"e_agg_good","source":"good1","target":"agg_1"},
    {"id":"e_agg_else","source":"else1","target":"agg_1"},
    {"id":"e_end","source":"agg_1","target":"end_1"}
  ]
}
JSON

curl -s -o /dev/null -w '%{http_code}\n' -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  --data-binary @cond-graph.json
```

**预期输出（实测）**

```
200
```

**这段在干什么**：`cond_1` 只有**一个条件** `good`（`contains 很好`）+ 一个固定 `else`；两条出边的 `sourceHandle` 分别为 `"good"` / `"else"`。`agg_1` 的 `values` **同时引用两个分支**的文本——这正是 L4 要验证的「未执行分支变量不存在」。

#### 3.3.2 `topic = 服务很好`：走 `good`

```bash
curl -s -N -X POST http://127.0.0.1:3001/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{"topic":"服务很好"}}' > ts.good.sse

curl -s -N -X POST http://127.0.0.1:8000/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{"topic":"服务很好"}}' > py.good.sse

grep -A1 '^event: branch_taken$' ts.good.sse
python -c "
import re
for path in ('ts.good.sse','py.good.sse'):
    text=open(path,encoding='utf-8').read()
    ids=sorted(set(re.findall(r'\"nodeId\":\"(good1|else1)\"',text)))
    print(path,ids)
"
```

**预期输出（实测·两端相同）**

```
event: branch_taken
data: {"nodeId":"cond_1","caseId":"good","label":"好评"}

ts.good.sse ['good1']
py.good.sse ['good1']
```

**结果解读**：

- `branch_taken` 每个 `condition` 节点**只发一次**，顺序固定为 `node_started(cond_1)` → `branch_taken` → `node_finished(cond_1)`；`node_finished.output` 为 `{"matched":"good"}`。
- **`else1` 的 `nodeId` 完全未出现**：未选中的分支不是「执行了但输出为空」，而是**连 `node_started` 都没有**。这比「检查输出为空」更强——它证明引擎真的没有走进那条边。
- `good1` 照常产生 `token` 与 `node_finished`；由于它下游是 `agg_1`，最终 `outputs.answer` 为 `echo: PRAISE 服务很好`。

#### 3.3.3 `topic = 服务很差`：走 `else`

```bash

"
```

**预期输出（实测）**

```
event: branch_taken
data: {"nodeId":"cond_1","caseId":"else","label":"else"}

['else1']
```

**结果解读**：唯一条件 `contains 很好` 不成立 → 走兜底；`caseId` 与 `label` **都是 `"else"`**（不是画布上的中文「否则」，见 `04` §5.3）。本次只有 `else1` 执行，`good1` 完全未出现。

### 3.4 L4 —— 聚合：未执行分支的变量不存在，但**不报错**

**在哪执行**：任意目录（沿用 3.3 的图）

```bash
python -c "
import json,re
for path in ('ts.good.sse','py.good.sse'):
    text=open(path,encoding='utf-8').read()
    payload=re.search(r'event: run_finished\r?\ndata: (.+)',text).group(1)
    print(path,json.loads(payload)['outputs'])
    print('run_failed' in text)
"
```

**预期输出（实测·两端相同）**

```
ts.good.sse {'answer': 'echo: PRAISE 服务很好'}
False
py.good.sse {'answer': 'echo: PRAISE 服务很好'}
False
```

**结果解读**：

- `agg_1` 的 `values = ["{{ good1.text }}", "{{ else1.text }}"]`；本次 `else1` **没有执行**，变量池里根本没有 `else1` 这个键。
- 若用普通模板解析，这里会抛 `template variable not found: else1.text` → `run_failed`。实际结果是**不报错**：`aggregator` 用**分支安全解析**（`tryRenderTemplate`），缺失路径视为**空串**，于是取第一个非空值 `good1.text`。
- 输出是**扁平对象**：`{"answer": "echo: PRAISE 服务很好"}`——不是 `{"answer": {"answer": ...}}`。`end` 用 `{{ agg_1.answer }}` 取到字符串，最终 `run_finished.outputs` 也是 `{"answer": ...}`。
- `run_failed` 不出现，证明「另一条路没走」不会让整张图失败。

> 反向验证（可选）：把 `values` 改成 `["{{ llm_none.text }}"]`（一个**任何分支都不产生**的节点 id），仍应输出 `{"answer": ""}` 而不是报错——安全解析对「不存在」一律空串，不做「是否来自某分支」的判断。

## 4. 【技术讨论 1】阶段 8 补上了什么：从「单线执行」到「能分叉、能收敛、能循环」

**问题**：阶段 4~7 已经能把图编译成可执行程序、能调模型 / 工具 / 检索，阶段 8 的三个节点到底新在哪？

**答案的一句话**：**阶段 7 的执行仍然是「一条线走到底」；阶段 8 让图第一次拥有「按条件选择路径、把多条路径收敛、对数组逐项处理」这三种控制流。**

| 能力 | 阶段 7 | 阶段 8 |
| --- | --- | --- |
| 执行路径 | 拓扑序**全执行**（可达即执行） | **按条件只执行一条分支** |
| 多路汇合 | 多个节点直接连到同一个下游 | **`aggregator` 显式收敛**，且能引用「没走的那条路」 |
| 重复处理 | 无 | **`iteration` 内部逐项循环**（不产生图环） |
| 新节点 | `knowledge` | `condition` / `aggregator` / `iteration`（共 7 种） |
| 新事件 | `retrieval` | `branch_taken` / `iteration_item` |
| 新失败面 | 嵌入、检索 | 分支配置（缺边 / 非法 handle）、聚合取值、迭代输入与上限 |
| 新一致性要求 | chunk / 分数 | **分支事件序列** + **数值序列化** |

**它没有解决什么（必须诚实）**

- **图级循环**：`iteration` 是「节点内部对数组循环」，不是「回到上游节点」；真正的循环图（带退出条件）仍不在本阶段。
- **并行分支**：`condition` 是**单选**（第一个匹配），不是「同时走多条」；没有 fan-out / fan-in 的并行执行。
- **分支内的局部变量作用域**：变量池仍是全局的，只是「没执行的节点没有键」；没有显式的分支作用域。
- **断点 / 人工审核**：没有 checkpoint、没有 HITL。
- **迭代的嵌套**：`iteration` 的输出模板里不能再跑一个 `iteration` 节点；嵌套循环需要图级能力。

> **一句话**：**阶段 8 把「图」从一条直线变成了有岔路、有汇合、有循环的流程图——但仍是一张「静态可编译」的图，不是通用编程语言。**

## 5. 【技术讨论 2】同一个 `addConditionalEdges` 的两种形态

**问题**：阶段 6 的 ReAct 循环与阶段 8 的分支，看起来是两件完全不同的事，为什么说它们用的是**同一个机制**？

**答案的一句话**：**条件边 = 「路由器函数 + 键→目标映射」。路由器返回一个键，引擎沿该键对应的边走；键的取值域有多大、映射有多少项，决定了它是「单出口判断」还是「多出口映射」。**

**阶段 6：单出口判断（gate）**

```ts
// 伪代码：llm 节点内部决定「继续调工具」还是「走原来的下游」
builder.addConditionalEdges(
  llmId,
  (state) => ((state.toolCalls[llmId] ?? []).length > 0 ? 'tools' : 'continue'),
  { tools: `${llmId}__tools`, continue: downstream },
)
builder.addEdge(`${llmId}__tools`, llmId)   // 环：工具执行完回到 llm
```

**阶段 8：多出口映射（fan-out）**

```ts
// 伪代码：condition 节点写回 matched，条件边按 caseId 分派
builder.addConditionalEdges(
  condId,
  (state) => state.branches[condId] ?? 'else',
  { good: 'good1', else: 'else1' },   // 每个 caseId 一个目标
)
```

**对照**

| 维度 | 阶段 6（ReAct） | 阶段 8（分支） |
| --- | --- | --- |
| 路由器返回域 | 2 个键：`tools` / `continue` | N+1 个键：每个 `caseId` + `else` |
| 映射目标 | 一个回环节点 + 一个下游 | 每个键一个下游节点 |
| 图的形态 | 有**环** | **无环**（DAG） |
| 谁决定键 | `llm` 的 `tool_calls` | `condition` 的求值结果（第一个匹配） |
| 普通边 | **必须跳过**从 llm 出发的原普通边 | **必须跳过** condition 的所有普通出边 |
| 事件 | `tool_call` / `tool_result` | `branch_taken` |

**「跳过普通边」是两者共同的陷阱**

- LangGraph 的条件边与普通边是**二选一**：同一个 source 既有普通边又有条件边时，普通边会**无条件**再走一遍。
- 阶段 6 如果不跳过 llm 的原普通边，工具轮次结束后会「额外再走一次下游」，事件重复。
- 阶段 8 如果不跳过 condition 的普通出边，**所有分支都会被执行**——分支就白做了。
- 两端的做法一致：条件边负责路由，普通边只用于「非 condition / 非带工具 llm」的节点。

**为什么 `branch_taken` 在**节点内**发，而不是在条件边里发**

1. **节点知道「匹配了谁」**：`runConditionNode` 逐个求值，第一个匹配时就知道 `caseId` 与 `label`；条件边的路由器只读 `state.branches[nodeId]`，拿不到 `label`。
2. **只发一次**：节点执行一次，事件就一次；如果放在边里，边的重试 / 重复路由可能重复发。
3. **顺序固定**：协议要求 `node_started → branch_taken → node_finished`；节点内发能保证它落在 `node_finished` 之前。
4. **与「节点算结果、条件边只路由」一致**：节点的输出是 `{ "matched": caseId }`（业务结果），条件边只把它翻译成「下一站」。

> **一句话**：**条件边本身不产生业务数据，它只是一个「键→节点」的查表；真正决定走哪条路的是节点写回的 `matched`，真正告诉用户走了哪条路的是节点发出的 `branch_taken`。**

## 6. 【技术讨论 3】「分支安全的变量解析」是分支系统的必然结果

**问题**：为什么 `aggregator` 引用一个「不存在的变量」不能报错？这不是把错误藏起来了吗？

**答案的一句话**：**分支系统一旦存在，「另一条路没走」就是正常状态；如果解析仍要求「路径必须存在」，那么每一张有条件分支的图都会在汇合点必然失败——所以必须有一个「缺失即空串」的安全解析，且只能用在**明确知道会跨分支取值**的地方。**

**普通解析 vs 分支安全解析**

```ts
// 普通：缺失即抛错（llm / knowledge / end / iteration.outputTemplate）
renderTemplate("{{ else1.text }}", pool)
// → RunError: template variable not found: else1.text

// 安全：缺失即空串（condition.variable/value、aggregator.values）
tryRenderTemplate("{{ else1.text }}", pool)
// → ""
```

**适用范围（协议明确限定）**

| 字段 | 解析方式 | 原因 |
| --- | --- | --- |
| `condition.conditions[].variable` | **安全** | 条件本身可能引用尚未执行节点的输出（如「第一轮没走分支」） |
| `condition.conditions[].value` | **安全** | 同上；`value` 也允许写模板 |
| `aggregator.outputs[].values[]` | **安全** | 按定义要同时引用多条分支的输出 |
| `iteration.inputArray` | **安全**（但结果必须是 JSON 数组） | 复用「不存在即空串」的行为；空串 `JSON.parse` 失败 → 运行期报错 |
| `llm.prompt` / `knowledge.query` / `end.outputs[].value` / `iteration.outputTemplate` | **严格** | 这些是「真正要用的值」，拼错变量名必须当场报错 |

**为什么不能全局放开**

- 如果 `end.outputs[].value` 也「缺失即空串」，用户把 `{{ llm_1.text }}` 拼成 `{{ llm_1.txt }}`，会得到一个空输出而不是错误——**错误被静默吞掉**，比失败更糟。
- 安全解析的代价是「拼写错误不报错」，所以它只能用在**语义上确实允许缺失**的字段：跨分支取值。
- 这就是「**最小豁免**」：只放开必须放开的，其余保持严格。

**为什么说它是「必然结果」**

- 条件分支的收敛点（`aggregator`）天然要引用「所有可能来源」；任一时刻只有一条路径执行，其余变量必然不存在。
- 如果没有安全解析，用户只有两个选择：为每条分支各写一个聚合器（图爆炸），或者永远不聚合（分支无法收敛）。
- 所以「安全解析」不是妥协，而是**分支 + 收敛**这套语义的组成部分。

> **一句话**：**分支安全解析不是「宽容」，而是「精确地把宽容限制在跨分支取值的三个字段上」；其余字段仍然「拼错就报错」。**

## 7. 【技术讨论 4】跨语言一致性要细到 `1.0` vs `1`

**问题**：同样是「把当前项转成字符串」，为什么 TS 的 `JSON.stringify` 与 Python 的 `json.dumps` 会分叉？差在哪？

**答案的一句话**：**JS 只有一种数字类型 `number`，Python 有 `int` 与 `float`；两套标准库对浮点、非有限数、分隔符、非 ASCII 的默认处理都不同。要逐字节一致，就必须显式归一。**

**四处真实差异**

| 输入 | `JSON.stringify`（JS） | `json.dumps`（Python 默认） | 归一后 |
| --- | --- | --- | --- |
| `1.0` | `1` | `1.0` | `1` |
| `3.0` | `3` | `3.0` | `3` |
| `[4.0, 5]` | `[4,5]` | `[4.0, 5]` | `[4,5]` |
| `{"a": 1.0}` | `{"a":1}` | `{"a": 1.0}` | `{"a":1}` |
| `NaN` | `null` | `NaN`（**非法 JSON**） | `null` |
| `Infinity` | `null` | `Infinity`（非法 JSON） | `null` |
| `True` | `true` | `true` | `true`（**先判 bool**） |
| 中文 | 原样 | 默认 `\uXXXX` | 原样（`ensure_ascii=False`） |
| `-0.0` | `0` | `-0.0` | `0`（`int(-0.0)`） |

**Python 侧的归一实现（`apps/api-py/app/engine/template.py`）**

```python
def js_json_dumps(value: Any) -> str:
    return json.dumps(
        _js_normalize(value), ensure_ascii=False, separators=(",", ":")
    )

def _js_normalize(value: Any) -> Any:
    if isinstance(value, bool):
        # bool 是 int 的子类，必须排在 float/int 判断之前
        return value
    if isinstance(value, float):
        if value != value or value in (float("inf"), float("-inf")):  # NaN / ±Inf
            return None
        return int(value) if value.is_integer() else value
    if isinstance(value, list):
        return [_js_normalize(item) for item in value]
    if isinstance(value, dict):
        return {key: _js_normalize(item) for key, item in value.items()}
    return value
```

**这段在干什么**：

- `isinstance(value, bool)` **必须最先判断**：Python 里 `True` 是 `int` 的子类，若先走 `isinstance(value, int)`，`True` 会被当成 `1`，输出 `1` 而不是 `true`。
- `float.is_integer()` 为真时转 `int`：完成 `1.0 → 1`、`3.0 → 3`。
- `NaN`（`value != value`）与 `±Infinity` → `None` → `null`，与 JS 一致，也避免 `json.dumps` 产出非法 JSON。
- `separators=(",", ":")`：去掉 Python 默认的 `", "` / `": "` 空格。
- `ensure_ascii=False`：中文按原字符输出，与 JS 一致。
- 容器递归：对象数组里的 `1.0` 也要归一（`{"a":1}`、`{"b":[4,5]}`）。

**TS 侧为什么不用改**

`JSON.stringify` 本身就是「JS 口径」：`number` 只有一种，整数值浮点自然输出 `1`；`NaN` / `Infinity` 自然输出 `null`；默认紧凑、非 ASCII 不转义。TS 侧直接用 `JSON.stringify` 就是基准。

**还有哪些没覆盖（边界要诚实）**

- **指数格式**：`1e-7` 在 JS 是 `"1e-7"`，Python 是 `"1e-07"`（补零）；本阶段的验收数组不含这种值，属于已知未归一细节。
- **超大整数**：JS 的 `number` 只有 53 位安全整数；Python 的 `int` 无上限。超过 `2^53` 的值两端本就不同，应在数据层避免。
- **键顺序**：两端都按插入顺序序列化；如果上游对象的构造顺序不同，字节也会不同——本项目所有对象都在同一段代码里按固定顺序构造。

> **一句话**：**跨语言一致不是「都调一个 JSON 库」就行，而是「把 Python 的数字模型投影到 JS 的数字模型」：`1.0→1`、`NaN→null`、`bool` 先于 `int`、紧凑分隔符、非 ASCII 原样。**

## 8. 【技术讨论 5】校验必须前置：分支缺边不能「跑到一半才崩」

**问题**：分支缺一条边，为什么不能在运行到 `condition` 节点时再报错？提前校验的价值是什么？

**答案的一句话**：**「分支缺边」是图的静态属性，不依赖输入；把它留到运行期，只会让用户在等了若干 token 之后看到一个中途失败——前置校验能在保存 / 开流之前就给出精确到 `nodeId` / `caseId` / `edgeId` 的 400。**

**静态规则 vs 动态规则**

| 规则 | 例子 | 何时可判 | 校验位置 |
| --- | --- | --- | --- |
| 图结构 | 缺 `start` / 缺 `end` / 边指向不存在的节点 | 只看图 | `validateGraph`（PUT / run 预检） |
| 分支完整性 | 缺出边 / 重复边 / 非法 `sourceHandle` | 只看图 | `validateGraph` 规则 8 |
| 节点数据形状 | `conditions` 为空 / 非法 operator / `maxIterations` 越界 | 只看图 | `validateGraph` 规则 8~10 |
| 运行输入相关 | `inputArray` 解析后不是数组 / 数组超过上限 | 需要 `inputs` | 运行期 `run_failed` |

**「跑到一半才崩」的代价**

1. **已有输出作废**：用户已经看到了 `branch_taken`、部分 token，最后却 `run_failed`；他分不清是模型问题还是图问题。
2. **定位困难**：流内错误只带 `nodeId`，不会告诉你「哪条边缺了」；前置 400 的文案直接写 `case good has no outgoing edge`。
3. **无法重试**：运行期失败后要改图、重存、重跑；前置失败可以在保存时就修好。
4. **两端一致性**：静态规则可以在两端用**同一个纯函数**实现并逐字比对；运行期规则混在引擎里，更难保证一致。

**三层防线（本项目）**

```
画布红字（missingBranches）   ← 用户最常犯的「缺出边」，连线时即时提示
        │
        ▼
PUT / publish 的 validateGraph  ← 规则 1~10，静态错误一律 400
        │
        ▼
POST /run 的开流前预检          ← 再跑一遍 validateGraph + validateNodeData + 外部资源校验
        │
        ▼
SSE 流内的 run_failed          ← 只有依赖 inputs 的错误才在这里报
```

- **画布层**只覆盖「缺出边」，因为它最影响体验且最容易当场修；其余静态错误由后端兜底。
- **保存层**与**运行层**都跑 `validateGraph`：保存时拦住错误图，运行时再拦「历史遗留 / 直接改库」的错误图。
- **运行期**只保留真正依赖输入的两类（`inputArray` 非数组、超上限）——它们**不可能**在保存时被判定。

**为什么 `maxIterations` 要分两处校验**

- 预检校验的是**设置值**：`maxIterations` 必须是 1..100 的整数（规则 8.1.12）。
- 运行期校验的是**实际数组长度**：`len(items) > maxIterations` → `exceeded max iterations`（§8.2）。
- 两者是不同命题：设置合法不代表数组不超限；数组不超限也不代表设置合法。**都要有。**

> **一句话**：**能在图上看出来的错，就在保存/开流前报；只有依赖本次输入的错，才允许在流内报。校验前置不是「更严格」，而是「把错误放在用户还能低成本修复的时刻」。**

## 9. 常见坑汇总（跨阶段 8）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **分支边没写 `sourceHandle`** | 400 `condition node ... has no outgoing edge` 或 `invalid sourceHandle: null` | 多出口节点每条出边必须带 `caseId` / `else`（`04` §5.1） |
| 2 | **同一分支拖了两条边** | 400 `has duplicate edge for case ...` | 每个分支恰好一条出边；删掉多余的那条（8.1.8） |
| 3 | **`else` 忘记连线** | 400 `else branch has no outgoing edge` | `else` 也必须有出边（8.1.6）；画布红字会列出「否则」 |
| 4 | **给 condition 同时保留了普通边** | 所有分支都被执行 / 事件重复 | 条件边与普通边二选一；condition 的出边全部由 `sourceHandle` 路由（§5） |
| 5 | **aggregator 用普通模板解析** | `run_failed: template variable not found: else1.text` | 跨分支取值必须用安全解析（§6） |
| 6 | **`aggregator.values` 为空数组** | 400 `output {name} must have at least one value` | 至少一个取值（8.1.10）；UI 的「删除值」在只剩 1 个时禁用 |
| 7 | **`iteration.inputArray` 写成字面量数组** | `inputArray must be an array` 或模板解析异常 | 该字段是**模板字符串**，解析结果才必须是 JSON 数组 |
| 8 | **`items` 直接传字符串 `"A,B,C"`** | `inputArray must be an array` | 需要 JSON 数组 `["A","B","C"]`；字符串不是数组 |
| 9 | **数组长度超过 `maxIterations`** | 流内 `run_failed: exceeded max iterations: N` | 调大 `maxIterations`（1..100）或减小数组；上限是保护 |
| 10 | **`maxIterations` 设成 0 / 101** | 400 `must be between 1 and 100` | 预检只认 1..100 的整数（8.1.12） |
| 11 | **Python 直接 `json.dumps` 序列化 item** | `1.0` / `{"a": 1.0}` 与 TS 分叉 | 用 `js_json_dumps`（§7） |
| 12 | **Python 先判 `int` 再判 `bool`** | `True` 输出 `1` | `bool` 是 `int` 子类，必须先判 bool（§7） |
| 13 | **Python 默认分隔符** | `{"a": 1}` 多一个空格 | `separators=(",", ":")`（§7） |
| 14 | **`NaN` 写进 SSE** | 帧不是合法 JSON，前端 `JSON.parse` 抛错 | Python 归一为 `null`；JS 天然是 `null` |
| 15 | **把 `branch_taken` 当最终输出** | `outputs` 里找不到分支信息 | 过程事件是旁路；最终结果看 `run_finished.outputs`（`04` §6.2） |
| 16 | **用「检查输出为空」代替「检查未执行」** | 误以为另一条分支执行了 | 应断言 `else1` 的 `nodeId` **完全没出现**（§3.3） |
| 17 | **`topic` 两个用例共用同一张已发布图** | 改了草稿但运行的是旧发布快照 | `/run` 读草稿；发布快照是另一份拷贝（阶段 3 的「两态」） |
| 18 | **预检错误当成流内错误去 grep** | 等不到 `event:` 行 | 预检是普通 JSON 400，不带 SSE 帧；先看 `content-type`（阶段 4 的双通道） |

## 10. 本篇复盘与知识点

**一句话总结阶段 8**：在既有的「图即数据、编译执行」之上，新增了 `condition` / `aggregator` / `iteration` 三个节点，把执行从「单线」扩展为「按条件分叉 → 在多路汇合处安全收敛 → 对数组逐项处理」。分支的落地靠「出边 `sourceHandle` = 分支 `caseId` / `else`」这条契约；收敛的落地靠「跨分支取值缺失即空串」的最小豁免；迭代的落地靠「节点内部循环 + `iteration_item` 进度」；而两端一致则靠「分支事件序列逐帧相同」与「数值序列化逐字节相同」（`1.0→1`、`NaN→null`、`bool` 先于 `int`）。所有静态错误都在保存 / 开流前以 400 拦下，只有依赖输入的数组错误才走流内 `run_failed`。

**本篇学到的工程 / 架构要点**

1. **阶段 8 补上三种控制流**：条件分叉（单选）、聚合收敛、数组迭代；仍无图级循环 / 并行 / HITL。
2. **条件边是通用机制**：同一个 `addConditionalEdges(source, router, pathMap)`，阶段 6 是单出口 gate，阶段 8 是多出口 fan-out；两者都必须跳过原普通边。
3. **`branch_taken` 在节点内发**：节点知道匹配结果与 label；条件边只负责「键→目标」查表，不产生业务数据。
4. **分支安全解析是最小豁免**：只放开 `condition.variable/value`、`aggregator.values`（及 `iteration.inputArray`），其余字段保持「缺失即报错」。
5. **跨语言数值一致性**：JS 一种 `number` vs Python `int`/`float`；`1.0→1`、`NaN/Inf→null`、`bool` 先判、紧凑分隔符、非 ASCII 原样。
6. **校验分层**：画布提示 → 保存/运行预检（静态规则 1~10）→ 流内 `run_failed`（仅动态规则）。
7. **负向证据同样重要**：`else1` 的 `nodeId` 完全未出现，比「输出为空」更能证明分支真的没执行。

**遗留到下阶段**

- 分支是**单选**，没有并行 fan-out / fan-in；多条分支不能同时执行。
- `iteration` 不支持嵌套循环，也不支持「循环体内再引用上游节点输出」的复杂作用域。
- 数值归一未覆盖指数格式（`1e-07` vs `1e-7`）与超过 `2^53` 的整数。
- 前端预检只覆盖「缺出边」，其余静态错误仍靠后端 400 + 顶部文案。
- 没有把 L1~L7 固化成 CI 断言（节点枚举、分支事件序列、数值逐字节、8 组错误文案）。
- 没有分支级的执行统计 / 覆盖率视图（例如「哪些分支从未被走到」）。

**基础技术要点**：条件分支（`sourceHandle` / `caseId` / `else`） · 「第一个匹配生效」 · 12 个 operator 语义 · 变量聚合（第一个非空、扁平输出） · 分支安全解析（`tryRenderTemplate`） · 迭代（`inputArray` / `itemName` / `itemIndex` / `itemCount` / `joined`） · `addConditionalEdges` 的两种形态 · 跨语言数值序列化（`js_json_dumps`） · 静态预检 vs 运行期错误。
