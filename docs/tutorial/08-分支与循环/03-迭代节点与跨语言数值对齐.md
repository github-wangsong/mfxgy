## 0. 定位：迭代是「节点内部的循环」

### 0.1 三种「重复」不要混淆

工作流里会出现三种看起来都像「循环」的东西，它们的成本、可观测性和失败语义完全不同：

| 形态 | 长什么样 | 例子 | 事件表现 |
| --- | --- | --- | --- |
| **图循环** | 画布上真的有一条边指回上游 | 阶段 6 的 ReAct：`llm → tools → llm` | 每绕一圈重复发 `node_started` / `node_finished` |
| **节点内循环**（本篇） | 画布上只有**一个** `iteration` 节点，循环藏在节点实现里 | 把一个数组的每一项都套一遍模板 | 一次 `node_started`、N 次 `iteration_item`、一次 `node_finished` |
| **前端重复渲染** | 后端只发一次结果，前端 `map` 出多行 | 运行面板把 `results` 列表画出来 | 与后端事件无关 |

本篇的 `iteration` 属于**第二种**。这个区分很重要，因为：

- 它**不会**把图变成有环图，所以 `graph.validator` 的「必须是有向无环图」规则不受影响；
- LangGraph 的 `recursionLimit` 也不会因为「数组有 50 项」而爆掉（TS 侧注释里专门写了这一点：*「迭代节点只在节点内部循环（不产生图循环）」*）；
- 失败时**整个运行**失败（`run_failed`），而不是「前 3 项成功、第 4 项失败后继续」。

### 0.2 术语先立住（首次出现，一句话解释）

| 术语 | 一句话解释 |
| --- | --- |
| **迭代（iteration）** | 对一个**数组**的每个元素，执行同一段「取元素 → 套模板 → 收集结果」的处理。 |
| **`inputArray`** | 迭代节点的输入**模板**（字符串）；渲染后必须是一段合法的 **JSON 数组**文本。 |
| **`itemName`** | 当前元素注入变量池时使用的**顶层键名**，默认 `"item"`。 |
| **`itemIndex` / `itemCount`** | 当前项序号（**从 1 开始**）与总项数；由节点自动注入，不需要用户配置。 |
| **`maxIterations`** | 单次运行允许处理的最大项数，默认 **20**，契约允许范围 **1..100**。 |
| **`iteration_item`** | 每处理一项就发一次的 SSE 事件，payload 只有 `nodeId` / `index` / `total`。 |
| **整数值浮点（integral float）** | 数学上是整数、但类型是浮点数的值，如 `3.0`、`1.0`。它是本篇「两端输出分叉」的根源。 |
| **`js_json_dumps`** | 本项目 Python 侧的「按 JavaScript `JSON.stringify` 口径」序列化函数；**不是** `json.dumps` 的别名。 |
| **NaN / Infinity** | 非数字 / 正负无穷，IEEE-754 的特殊值；它们**不是合法 JSON 值**，两种语言的默认处理不同。 |

> 「变量池（`pool`）」「模板 `{{ a.b }}` 的点路径解析」「`RunError` → `run_failed`」都是阶段 4 已首次教学的机制，本篇直接使用，不重讲：见 `04-执行引擎/03-节点运行时与变量池.md`。

### 0.3 一次迭代节点的生命周期

```text
node_started(iteration)
   │
   ├─ ① 渲染 inputArray 模板（安全解析：缺失 → 空串）
   ├─ ② JSON.parse 渲染结果
   ├─ ③ 不是数组 → RunError（整个运行失败）
   ├─ ④ 长度 > maxIterations → RunError
   │
   ├─ 对每一项（index 从 0 开始）：
   │     ├─ iteration_item(index+1, total)      ← 先发进度
   │     └─ 渲染 outputTemplate（注入 item / itemIndex / itemCount）
   │
   └─ node_finished(iteration, {results, count, joined})
```

### 1.2 验收标准（本篇实测口径，逐字节比较）

1. **字符串数组**：`items=["A","B","C"]`、`outputTemplate="第{{ itemIndex }}/{{ itemCount }}项: {{ item }}"`，两端都发出 **3 次** `iteration_item`（`index` 为 1 / 2 / 3），并且 `node_finished.output` 逐字节相同：
   ```text
   results = ["第1/3项: A", "第2/3项: B", "第3/3项: C"]
   joined  = "第1/3项: A\n第2/3项: B\n第3/3项: C"
   ```
2. **数值数组（核心）**：`items=[1, 2.5, 3.0, {"a":1.0}, {"b":[4.0,5]}]`、`outputTemplate="{{ item }} / {{ itemIndex }}"`，两端 `results` 均为：
   ```text
   1 / 1
   2.5 / 2
   3 / 3
   {"a":1} / 4
   {"b":[4,5]} / 5
   ```
   修复前 Python 侧会输出 `1.0`、`3.0`、`{"a":1.0}`、`{"b":[4.0,5]}`（见 §11.8）。
3. **错误文案**：`inputArray` 非数组 / 超上限时，两端 `run_failed.message` 逐字节相同（见 §14）。

## 3. 先看清要做什么

### 3.1 五个字段的分工

| 字段 | 谁用 | 关键点 |
| --- | --- | --- |
| `title` | 画布 / 校验 | 纯展示，引擎不读 |
| `inputArray` | **节点** | **模板**；渲染后 `JSON.parse` 必须是数组 |
| `itemName` | **节点** | 当前项注入变量池时的键名；空串视为未配置 |
| `maxIterations` | **节点** | 运行期长度上限；默认 20 |
| `outputTemplate` | **节点** | 每项渲染一次；只能引用 `pool` 的顶层键 |

### 3.2 `inputArray` 的常见写法

| 写法 | 渲染结果（文本） | 解析后 | 说明 |
| --- | --- | --- | --- |
| `["A","B","C"]` | 原样 | `["A","B","C"]` | 字面量数组，自测最方便 |
| `{{ start.inputs.items }}`（值是数组） | `["A","B","C"]` | 同上 | 上游把**真数组**放进变量池，渲染时自动 JSON 序列化 |
| `{{ start.inputs.items }}`（值是字符串 `'["A","B"]'`） | `["A","B"]` | 同上 | 上游只传了 JSON 文本；字符串原样插入 |
| `[{{ a }},{{ b }}]` | `["x","y"]` | 同上 | 模板可以先拼接再解析 |
| 路径不存在 | `""`（空串） | 解析失败 | 安全解析把缺失当空串 → 报「must be an array」 |

**最后一行是关键**：`inputArray` 用的是**安全解析**（`tryRenderTemplate` / `try_render_template`），路径不存在**不会**报 `template variable not found`，而是替换成空串，然后在解析阶段报 `must be an array`。这是阶段 8 契约里明确规定的（`sse-events.md` §4.1 最后一段）。

### 3.3 事件与输出的时序（实测）

```text
event: node_started          data: {"nodeId":"iter_1","nodeType":"iteration"}
event: iteration_item        data: {"nodeId":"iter_1","index":1,"total":3}
event: iteration_item        data: {"nodeId":"iter_1","index":2,"total":3}
event: iteration_item        data: {"nodeId":"iter_1","index":3,"total":3}
event: node_finished         data: {"nodeId":"iter_1","nodeType":"iteration","output":{...}}
```

注意 `iteration_item` 出现在 `node_finished` **之前**，且**没有** `node_started` / `node_finished` 的重复。

## 5. 【技术教学 · 首次】为什么需要迭代

### 5.1 三个真实场景

| 场景 | 输入 | 每项做的事 | 产出 |
| --- | --- | --- | --- |
| 批量翻译 | `["你好","谢谢","再见"]` | 把每句翻成英文 | 3 条译文 |
| 逐条摘要 | 一批用户评论（对象数组） | 每条抽一句话摘要 | 3 条摘要 |
| 逐项打分 | 一组候选答案 | 给每个答案打 1–5 分 | 3 个分数 |

共同点：**同一个处理逻辑，作用于数组的每个元素**。如果没有 `iteration`，你要么在画布上复制 N 个相同节点（N 变了图就废了），要么写一个 Code 节点（本项目的节点库里没有 Code 节点），要么让 LLM「一次性处理整个数组」（不可控、易漏项、无法逐项观测进度）。

### 5.2 为什么不在画布上画 N 个相同节点

```text
做法 A（不用迭代）：         做法 B（用迭代）：
start → t1 → t2 → t3 → end    start → iteration → end
        ↑ 每项一个节点                ↑ 一个节点内部循环
```

- **做法 A 的图是「写死」的**：数组变成 4 项，就得改图；100 项基本不可维护。
- 做法 A 的每个节点都要各自配置一遍模板，改一处要改 N 处。
- 做法 A 的事件序列会「看起来像」N 个不同节点，前端无法把它归并成「一个进度条」。
- 做法 B 把「循环」从**图结构**下沉到**节点实现**：图不变，行为随数组长度变化。

### 5.3 它是「循环」但不是「环」

图论意义上的环（cycle）指边走回上游节点；`iteration` 的循环是**节点函数里的 `for` / `map`**。所以：

- 图校验仍然可以要求 DAG；
- LangGraph 的 `recursionLimit` 不需要随数组长度增加；
- 但**执行时间**会随项数线性增长——于是有了 `maxIterations`（§8）和逐项进度事件（§9）。

## 6. 【技术教学 · 首次】`inputArray`：模板，而不是变量引用

### 6.1 为什么是字符串模板

契约把 `inputArray` 定义成 `type: string`，而不是 `type: array`。原因有三：

1. **来源不唯一**：数组可能来自 `start` 的输入、上游 `llm` 解析出的 JSON、`aggregator` 拼出的字符串……模板是唯一能统一表达的载体。
2. **允许先加工**：`[{{ a }},{{ b }}]`、`{{ start.inputs.prefix }}{{ llm_1.items }}` 这类拼接只有模板能做到。
3. **与项目其它字段一致**：`llm.prompt`、`end.outputs[].value` 全是模板；不引入第二种「表达式语言」是刻意的取舍。

代价是**两阶段处理**：先渲染成**文本**，再把文本解析成**值**。

```text
inputArray: "{{ start.inputs.items }}"
      │ ① tryRenderTemplate（安全解析）
      ▼
"[\"A\",\"B\",\"C\"]"        ← 一段 JSON 文本
      │ ② JSON.parse / json.loads
      ▼
["A","B","C"]                ← 真正的数组（内存里的值）
```

### 6.2 为什么「先渲染、再解析」而不是「直接取变量」

如果直接按路径取值（`resolvePath("start.inputs.items")`），你拿到的是**值**，确实也能判断是不是数组。但那样会失去：

- 拼接能力（`[{{ a }},{{ b }}]`）；
- 「上游只给了 JSON 字符串」的兼容性（字符串要原样插入，不能再套一层引号）；
- 统一的错误面（所有输入问题都收敛到同一句 `must be an array`）。

所以本项目选择：**模板负责「怎么得到文本」，解析负责「文本是不是数组」**。

### 6.3 TS：逐行

**完整文件路径：`apps/api-ts/src/engine/nodes/iteration.node.ts`（行 17–59）**

```ts
// 完整文件路径：apps/api-ts/src/engine/nodes/iteration.node.ts
export function runIterationNode(
  node: GraphNode,
  pool: Pool,
  emitItem: (index: number, total: number) => void,                      // ← 进度回调：节点只管「第几项/共几项」，发不发事件由引擎决定
): Record<string, unknown> {
  const data = node.data as unknown as IterationNodeData                 // ← data 在图里是自由结构，先断言成契约类型再取字段
  const maxIterations =
    typeof data.maxIterations === 'number' ? data.maxIterations : DEFAULT_MAX_ITERATIONS  // ← 类型不对/缺失 → 默认 20
  const itemName =
    typeof data.itemName === 'string' && data.itemName !== '' ? data.itemName : 'item'    // ← 空串视为未配置

  const rendered = tryRenderTemplate(data.inputArray, pool)              // ← ① 安全解析：路径不存在 → 空串，不抛错
  let items: unknown
  try {
    items = JSON.parse(rendered)                                         // ← ② 文本 → 值（非 JSON 会在这里抛 SyntaxError）
  } catch {
    throw new RunError(`iteration node ${node.id} inputArray must be an array`)  // ← 统一文案（不区分「非 JSON」与「非数组」）
  }
  if (!Array.isArray(items)) {                                           // ← ③ JSON 合法但不是数组（对象/数字/字符串/布尔）
    throw new RunError(`iteration node ${node.id} inputArray must be an array`)
  }
  if (items.length > maxIterations) {                                    // ← ④ 先检查长度：要么全做，要么一项都不做
    throw new RunError(`iteration node ${node.id} exceeded max iterations: ${maxIterations}`)
  }

  const total = items.length                                             // ← 总项数：后面每项都要用到
  const results = items.map((item, index) => {                           // ← ⑤ 顺序遍历，index 从 0 开始
    emitItem(index + 1, total)                                           // ← ⑥ 先发进度事件，再渲染（渲染失败也能看到「卡在第几项」）
    return renderTemplate(data.outputTemplate, {                         // ← ⑦ 强制解析：模板路径缺失会抛 RunError
      ...pool,                                                           // ← 继承：inputs 与所有上游节点输出仍然可见
      [itemName]: stringifyItem(item),                                   // ← 顶层键注入当前项（已字符串化）
      itemIndex: index + 1,                                              // ← 对外 1-based：第 1 项而不是第 0 项
      itemCount: total,
    })
  })

  return { results, count: results.length, joined: results.join('\n') }  // ← ⑧ 三种消费形态（§10）
}

/** 当前项字符串化：字符串原样，其余按紧凑 JSON（两端一致）。 */
function stringifyItem(item: unknown): string {
  return typeof item === 'string' ? item : JSON.stringify(item)          // ← 不能直接 String(item)：对象会变成 [object Object]
}
```

**这段在干什么**（按执行顺序）：

1. 把 `node.data` 断言成 `IterationNodeData`；`maxIterations` / `itemName` 都做「类型 + 非空」兜底，缺省分别是 `20` / `"item"`。
2. `tryRenderTemplate` 渲染 `inputArray`：**安全解析**，缺失路径替换为空串。
3. `JSON.parse` 把渲染文本变成值；解析失败与「解析成功但不是数组」共用同一句 `RunError` 文案。
4. 长度检查在循环**之前**：超过上限直接失败，不会「先做 20 项再报错」。
5. `items.map` 顺序遍历：每项先 `emitItem(index+1, total)`，再渲染模板。
6. 渲染的上下文是 `{ ...pool, item, itemIndex, itemCount }`——`pool` 在后、注入键在前，所以注入键可以遮蔽同名键（§7.2）。
7. 返回三个字段；`joined` 用 `\n` 连接，供「不能索引数组」的模板消费。

### 6.4 Python：逐行

**完整文件路径：`apps/api-py/app/engine/nodes/iteration.py`**

```python
# 完整文件路径：apps/api-py/app/engine/nodes/iteration.py（去掉模块顶部注释后的逐行版）
import json                                                              # ← TS: JSON.parse / JSON.stringify
from collections.abc import Awaitable, Callable                          # ← 类型：返回可等待对象的「发射函数」
from typing import Any                                                   # ← TS: unknown

from app.engine.events import RunError                                   # ← 同一个错误类型 → 同一条 run_failed 文案
from app.engine.template import js_json_dumps, render_template, try_render_template  # ← 注意是 js_json_dumps，不是 json.dumps

DEFAULT_MAX_ITERATIONS = 20                                              # ← 与 TS / 契约同值

EmitItem = Callable[[int, int], Awaitable[None]]                         # ← TS: (index: number, total: number) => void


async def run_iteration_node(
    node: dict[str, Any],
    pool: dict[str, Any],
    emit_item: EmitItem,
) -> dict[str, Any]:
    """执行 `iteration` 节点：逐项发 `iteration_item` 并渲染 `outputTemplate`。"""
    data: dict[str, Any] = node["data"]                                  # ← 预检已保证 data 存在，直接取
    raw_max = data.get("maxIterations")
    max_iterations = (
        int(raw_max)
        if isinstance(raw_max, (int, float)) and not isinstance(raw_max, bool)  # ← 排除 bool：Python 里 True 也是 int
        else DEFAULT_MAX_ITERATIONS
    )
    raw_item_name = data.get("itemName")
    item_name = raw_item_name if isinstance(raw_item_name, str) and raw_item_name != "" else "item"

    rendered = try_render_template(data["inputArray"], pool)             # ← ① 安全解析（与 TS 同名同义）
    try:
        items = json.loads(rendered)                                     # ← ② 文本 → 值（失败抛 ValueError）
    except ValueError:
        raise RunError(f"iteration node {node['id']} inputArray must be an array") from None  # ← from None：隐藏底层异常链
    if not isinstance(items, list):                                      # ← ③ TS: Array.isArray
        raise RunError(f"iteration node {node['id']} inputArray must be an array")
    if len(items) > max_iterations:                                      # ← ④ 先检查长度
        raise RunError(
            f"iteration node {node['id']} exceeded max iterations: {max_iterations}"
        )

    total = len(items)
    results: list[str] = []
    for index, item in enumerate(items):                                 # ← ⑤ 顺序遍历，index 从 0 开始
        await emit_item(index + 1, total)                                # ← ⑥ 先发进度（异步：必须 await）
        results.append(
            render_template(
                data["outputTemplate"],
                {
                    **pool,                                              # ← 字典解包 = TS 的对象展开
                    item_name: _stringify_item(item),                    # ← 变量名是运行时值：这就是为什么 TS 用计算属性 [itemName]
                    "itemIndex": index + 1,
                    "itemCount": total,
                },
            )
        )

    return {"results": results, "count": len(results), "joined": "\n".join(results)}  # ← ⑧


def _stringify_item(item: Any) -> str:
    """当前项字符串化：字符串原样，其余按紧凑 JSON（两端一致）。"""
    if isinstance(item, str):
        return item
    return js_json_dumps(item)                                           # ← ★ 不是 json.dumps（§11）
```

**这段在干什么**：

1. `data.get("maxIterations")` 取配置；`isinstance(raw_max, (int, float)) and not isinstance(raw_max, bool)` 是「是数字且不是布尔」的写法——**`bool` 必须显式排除**，否则 `true` 会被当成 `1`（§11.6 同一个陷阱的另一个化身）。
2. `try_render_template` 渲染；`json.loads` 解析。`raise ... from None` 让日志只显示我们自己的文案，不附带 `During handling of the above exception...` 的底层异常链。
3. `isinstance(items, list)` 对应 `Array.isArray`；`len(items) > max_iterations` 在循环前检查。
4. `enumerate` 同时给出 0-based 下标和元素；`await emit_item(index + 1, total)` 先发事件。
5. 上下文字典用 `**pool` 解包，再覆盖/新增三个键；返回时用 `"\n".join(results)`。
6. `_stringify_item` 对非字符串走 `js_json_dumps`——这是本篇核心修复的调用点。

## 7. 【技术教学 · 首次】逐项的上下文注入

### 7.1 注入表达式

```ts
{ ...pool, [itemName]: stringifyItem(item), itemIndex: index + 1, itemCount: total }
```

```python
{ **pool, item_name: _stringify_item(item), "itemIndex": index + 1, "itemCount": total }
```

三个键都是**顶层键**（`pool` 的直接子键），不是嵌套在某个对象里。所以模板里只能写：

| 写法 | 结果 | 原因 |
| --- | --- | --- |
| `{{ item }}` | ✅ 当前项（字符串） | `item` 是顶层键 |
| `{{ itemIndex }}` | ✅ 1-based 序号 | 顶层键 |
| `{{ itemCount }}` | ✅ 总项数 | 顶层键 |
| `{{ item.title }}` | ❌ `template variable not found: item.title` | `item` 的值**已经被字符串化**；而且 `resolvePath` 对数组/非对象直接判失败 |
| `{{ item[0] }}` | ❌ 同上 | 模板**没有下标语法**：`resolvePath` 只会按 `.` 切分，且遇到数组就返回「不存在」 |

### 7.2 顶层键注入的三个后果

1. **可遮蔽**：如果用户把 `itemName` 配成 `"start"`，那么模板里的 `{{ start.inputs.x }}` 在迭代内部会失效（`start` 被当前项覆盖）。这是「`...pool` 在前、注入键在后」的直接结果。命名时避开已有节点 id / `inputs` 是最省心的做法。
2. **只读**：注入发生在**每次渲染前**构造的新对象里，`pool` 本身不会被修改；下一项不会看到上一项的 `item`（每次都是新对象，但值被顺序覆盖）。
3. **必须是字符串**：模板替换的产物是文本，所以非字符串项必须先序列化。TS 用 `JSON.stringify`，Python 用 `js_json_dumps`——**这正是两端最容易分叉的地方**。

### 7.3 项字符串化的规则

| 项的类型 | TS `JSON.stringify` | Python（修复后）`js_json_dumps` | 插入模板后的文本 |
| --- | --- | --- | --- |
| 字符串 `"A"` | 原样（`stringifyItem` 特判） | 原样（`_stringify_item` 特判） | `A` |
| 数字 `2.5` | `"2.5"` | `"2.5"` | `2.5` |
| 整数值浮点 `3.0` | `"3"` | 规范化后 `"3"` | `3` |
| 对象 `{"a":1}` | `'{"a":1}'`（紧凑，无空格） | 同左（`separators=(",", ":")`） | `{"a":1}` |
| 数组 `[4,5]` | `"[4,5]"` | 同左 | `[4,5]` |
| 布尔 `true` | `"true"` | 同左（`bool` 先判断） | `true` |
| `null` | `"null"` | 同左 | `null` |

**为什么字符串要特判**：如果不特判，`JSON.stringify("A")` 会得到 `"\"A\""`（带引号），模板里就会出现 `"A"` 而不是 `A`。这是「逐项渲染」和「渲染一个对象」的语义差别：项是**内容**，不是**JSON 片段**。

### 7.4 变量可见性（迭代内部 vs 外部）

```text
迭代节点内部渲染 outputTemplate 时可见：
  inputs.*                    ← 运行输入
  <上游节点 id>.*             ← 所有已执行节点的输出
  item / itemIndex / itemCount ← 本次注入

迭代节点外部（下游节点）可见：
  <iteration 节点 id>.results / .count / .joined
  item / itemIndex / itemCount ← 不可见（只在节点内部存在）
```

所以下游**不能**写 `{{ item }}`；要用 `{{ iter_1.joined }}` 或 `{{ iter_1.results }}`。这与「节点输出写入 `pool[node.id]`」的机制一致（阶段 4 已讲）。

## 8. 【技术教学 · 首次】`maxIterations`：保护性上限

### 8.1 两个数字

| 数字 | 含义 | 谁负责 |
| --- | --- | --- |
| **20** | 未配置时的默认上限 | 节点实现（`DEFAULT_MAX_ITERATIONS`），与契约 `default: 20` 对齐 |
| **100** | 允许配置的**最大值** | **预检**（`graph.validator` / `validator.py` 规则 10；`engine.service.ts` 的节点数据校验只查类型） |

`maxIterations` 的语义是：**这次运行最多处理多少项**。数组长度超过它就**整体失败**，不会「只处理前 N 项」。

### 8.2 两层防护

| 层 | 时机 | 触发条件 | 表现形式 |
| --- | --- | --- | --- |
| **预检** | `POST /run` 之前（图校验 / 节点数据校验） | `maxIterations` 不是 1..100 的整数；`inputArray` 为空 | **HTTP 400** 普通 JSON：`iteration node {id} maxIterations must be between 1 and 100` / `iteration node {id} inputArray is required` |
| **运行期** | 节点执行中 | 数组长度 > 配置值（数组来自上游，预检时**看不到**） | SSE 流内 `run_failed`：`iteration node {id} exceeded max iterations: {max}` |

**为什么必须两层**：预检只能看「配置本身」，看不到「运行时数组有多长」——`inputArray` 可能引用上游输出。运行期检查才是真正的闸门。

### 8.3 为什么它是保护，不是功能限制

「上限」这个词容易被误解为「这个节点最多只能处理 100 项」。实际上：

- 它是**成本护栏**：迭代里每一项都可能触发一次 LLM 调用。若上游错误地产生 5000 项（比如把整篇文档按字符切开），一次运行就会打爆模型额度。
- 它是**故障放大器**的反面：数组爆炸通常意味着上游逻辑错了，**立刻失败**比「默默跑 20 分钟」更容易定位。
- 想处理更多项，应当**改上游**（分页、分批、先过滤），而不是把上限调大。
- 100 是**契约层**的硬上限：即使把 `maxIterations` 配成 5000，预检也会 400 拒绝。

### 8.4 超上限的实测表现

配置 `maxIterations: 2`、数组 3 项：

```text
run_failed: iteration node iter1 exceeded max iterations: 2
```

注意文案里的数字是**配置值**，不是数组长度。这样调用方一眼能看出「我配的 2 太小」还是「数组确实太大」。

## 9. 【技术教学 · 首次】`iteration_item` 事件

### 9.1 事件形状

```ts
// 完整文件路径：apps/api-ts/src/engine/events.ts（行 72–75）
/** 构造 `iteration_item` 事件（`index` 从 1 开始）。 */
export function iterationItem(nodeId: string, index: number, total: number): RunEvent {
  return { event: 'iteration_item', data: { nodeId, index, total } }     // ← 只有三个字段：谁、第几项、共几项
}
```

SSE 帧（协议见阶段 4）：

```text
event: iteration_item
data: {"nodeId":"iter_1","index":2,"total":3}

```

**挂载点（两端）：引擎把回调接到事件队列上**

**完整文件路径：`apps/api-ts/src/engine/engine.service.ts`（行 432–435）**

```ts
// 完整文件路径：apps/api-ts/src/engine/engine.service.ts
      case 'iteration':                                                  // ← 按节点类型分派
        return runIterationNode(node, pool, (index, total) =>            // ← 第三个参数就是「发进度」的回调
          queue.emit(iterationItem(node.id, index, total)),              // ← 节点不需要知道队列/事件的存在
        )
```

**完整文件路径：`apps/api-py/app/engine/engine.py`（行 562–567）**

```python
# 完整文件路径：apps/api-py/app/engine/engine.py
    if node["type"] == "iteration":

        async def emit_item(index: int, total: int) -> None:             # ← 闭包捕获当前 node（每个节点一份）
            await queue.put(iteration_item(node["id"], index, total))    # ← Python 的队列写入是协程

        return await run_iteration_node(node, pool, emit_item)
```

**这段在干什么**：

1. 引擎按 `node.type` 分派，把 `node` / 当前变量池 / 一个**闭包**交给节点函数。
2. TS 的回调是普通函数（`queue.emit` 同步入队）；Python 的回调是 `async def`（`queue.put` 要 `await`）。
3. 节点函数只负责「该发第几项」，**不导入 `events` / 不持有队列**——这让节点可以脱离引擎单独测试（§17.1 就是直接调用它）。
4. 事件里的 `nodeId` 由引擎捕获，节点实现不需要知道自己的 id 怎么进 payload。

### 9.2 为什么逐项发

| 理由 | 展开 |
| --- | --- |
| **前端能看到进度** | 20 项就是 20 次事件，运行面板可以显示 `迭代 2/20`，用户知道「还在动」 |
| **长任务不至于静默卡住** | 如果只在 `node_finished` 时给结果，一个 30 秒的迭代在 SSE 流里就是 30 秒空白；很多代理/网关会因空闲超时断开 |
| **与阶段 4 的流式理念一致** | `token` 事件是「过程可观测」，`iteration_item` 是同一理念在「批量处理」上的投影：**过程可观测 > 只给结果** |

### 9.3 事件顺序与「不产生图循环」

`sse-events.md` 规定：`node_started(iteration)` → `iteration_item` ×N → `node_finished`。也就是说：

- `node_started` / `node_finished` **各只发一次**；
- `iteration_item` 的数量**恰好等于数组长度**（在没有失败、也没超上限的前提下）；
- 节点内部循环不会重复发节点的开始/结束事件——否则前端会把一个节点画成 N 个。

失败时（比如第 3 项模板写错）：第 1、2 项正常完成，**第 3 项的 `iteration_item` 也已经发出**（代码是「先发事件、再渲染」），随后渲染抛错，直接 `run_failed`，**没有** `node_finished`。这与阶段 5 的「出错不发 `node_finished`」规则一致；前端看到的进度会停在「3/3」，而不是「2/3」。

### 9.4 前端怎么用

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（相关行，节选）**

```tsx
// 完整文件路径：apps/web/app/apps/[id]/page.tsx（行 951–960、1633–1645）

  const parsed = JSON.parse(frame.data) as { nodeId?: string; index?: number; total?: number }
  setIterationEvents((prev) => [                                          // ← 追加到本次运行的进度列表
    ...prev,
    {
      nodeId: parsed.nodeId ?? '',
      index: typeof parsed.index === 'number' ? parsed.index : 0,
      total: typeof parsed.total === 'number' ? parsed.total : 0,
    },
  ])
}
```

```tsx
// 完整文件路径：apps/web/app/apps/[id]/page.tsx（行 1633–1645，节选）
{iterationEvents.length > 0 && (
  <div>
    <div style={{ fontWeight: 600 }}>迭代进度（iteration_item）</div>
    {iterationEvents.map((item, index) => (
      <div key={`${item.nodeId}-${index}`}>迭代 {item.index}/{item.total}</div>
    ))}
  </div>
)}
```

**这段在干什么**：

1. SSE 客户端已经按帧解析出 `event` 与 `data` 字符串（阶段 4 已讲分帧）。
2. 这里只做「按事件名分流」：`iteration_item` → 解析成 `{nodeId, index, total}` → 追加进 `iterationEvents`。
3. 渲染时逐条显示 `迭代 i/N`；`key` 用 `nodeId-index`，避免同一节点多次运行时冲突。
4. 每个事件都触发一次 `setState`，但前端在 SSE 循环里做了 `yieldToPaint()`（阶段 4 的 React 批处理坑），所以能看到逐项刷新。

> 事件里**不带**当前项的内容。想看内容要等 `node_finished.output.results`。这是刻意的：事件 payload 越小、越稳定，前端越容易做通用展示；而「内容」可能很大（对象数组），塞进每条事件会放大流量。

## 10. 【技术教学 · 首次】输出形状 `{results, count, joined}`

### 10.1 三个字段

| 字段 | 类型 | 内容 |
| --- | --- | --- |
| `results` | `string[]` | 每项渲染后的文本，**顺序与输入数组一致** |
| `count` | `number` | `results.length`（冗余，便于下游直接引用 `{{ iter_1.count }}`） |
| `joined` | `string` | `results.join("\n")` |

### 10.2 为什么额外给 `joined`

因为**模板不能索引数组**。`resolvePath` 的规则是「按点路径逐段取值，遇到数组就判不存在」，所以下游拿不到 `results[0]`、`results[1]`。把整个数组渲染出来，得到的是 JSON 文本：

```text
{{ iter_1.results }}  →  ["第1/3项: A","第2/3项: B","第3/3项: C"]
{{ iter_1.joined }}   →  第1/3项: A
                          第2/3项: B
                          第3/3项: C
```

对「把结果交给 LLM 或直接给用户看」这种最常见需求，`joined` 就是**可以直接用的那一种**。`results` 保留结构化形态，给未来需要 JSON 的下游（或前端）用。

### 10.3 下游的三种消费方式

| 需求 | 写法 | 得到 |
| --- | --- | --- |
| 一整段文本（喂 LLM / 展示） | `{{ iter_1.joined }}` | 换行连接的文本 |
| 结构化数组文本（再解析 / 存库） | `{{ iter_1.results }}` | `["…","…"]` |
| 只关心数量 | `{{ iter_1.count }}` | `3` |

> 注意：`end` 节点的输出**一律是字符串**（`renderTemplate` 返回 `string`），所以 `count` 到了最终 `run_finished.outputs` 里也是 `"3"` 而不是 `3`。这是阶段 4 就定下的「end 只渲染文本」语义，不是迭代节点的锅。

## 11. 【技术教学 · 首次 · 本篇核心】跨语言数值序列化对齐

### 11.1 现象：同一次迭代，两端文本不同

输入（同一份 JSON 数组）：

```json
[1, 2.5, 3.0, {"a":1.0}, {"b":[4.0,5]}]
```

`outputTemplate = "{{ item }} / {{ itemIndex }}"`。

| 端 | 修复前 `results` |
| --- | --- |
| TS | `["1 / 1", "2.5 / 2", "3 / 3", "{\"a\":1} / 4", "{\"b\":[4,5]} / 5"]` |
| Python | `["1.0 / 1", "2.5 / 2", "3.0 / 3", "{\"a\":1.0} / 4", "{\"b\":[4.0,5]} / 5"]` |

两边都「算对了」（`3.0 == 3`），但**输出文本不同**。而本项目的验收标准是**逐字节相同**——所以这就是 bug。

### 11.2 根因：JS 只有一种数字，Python 有两种

| 事实 | JavaScript | Python |
| --- | --- | --- |
| 数字类型 | 只有 `number`（IEEE-754 双精度） | `int`（任意精度整数）与 `float`（双精度）**两种** |
| `3` 与 `3.0` | **完全同一个值**，内存里没有区别 | 不同类型：`int` vs `float` |
| 解析 `3.0` | 得到 `number` 3 | 得到 `float` 3.0 |
| 序列化 | `JSON.stringify(3)` → `"3"`；`JSON.stringify(3.0)` → `"3"` | `json.dumps(3)` → `"3"`；`json.dumps(3.0)` → `"3.0"` |

所以分叉不是「谁算错了」，而是**两种语言对同一个数学值的标准打印形式不同**。JSON 规范允许 `3` 和 `3.0` 都表示数字 3，两者在语义上等价；但字符串比较不会这么认为。

**为什么偏偏在迭代里爆发**：迭代会把每一项渲染成**文本**并 `join`。任何数字数组（分数、计数、价格、ID）都会在每一行上分叉；下游无论是给 LLM、存库还是返回给前端，都会看到两种不同的文本。

### 11.3 `NaN` / `Infinity`：更危险的一种分叉

| 值 | `JSON.stringify`（JS） | `json.dumps`（Python 默认） |
| --- | --- | --- |
| `NaN` | `"null"` | `"NaN"` |
| `Infinity` | `"null"` | `"Infinity"` |
| `-Infinity` | `"null"` | `"-Infinity"` |

JS 的做法符合 RFC 8259（JSON 里没有 NaN/Infinity，只能写 `null`）；Python 默认 `allow_nan=True`，会输出 `NaN` / `Infinity`——**这不是合法 JSON**。后果：

- 前端 `JSON.parse` 会直接抛错；
- Python 自己 `json.loads` 能读回来，但 TS 读不了，往返不对称；
- 如果这个文本被塞进另一个 `inputArray`，下一次迭代在 TS 侧会解析失败。

NaN / Infinity 从哪里来？上游 LLM 返回的松散数字、工具里的除法、`float("inf")` 的显式比较……教学项目里不常见，但一旦出现就是「一端能跑、一端报错」的硬故障。修复方式是**统一成 `null`**。

### 11.4 修复：`js_json_dumps` + `_js_normalize`

**完整文件路径：`apps/api-py/app/engine/template.py`（行 65–96）**

```python
# 完整文件路径：apps/api-py/app/engine/template.py（行 65–96）
def js_json_dumps(value: Any) -> str:
    """按 **JavaScript `JSON.stringify` 的口径**做紧凑 JSON 序列化。"""
    return json.dumps(
        _js_normalize(value),                                            # ← ★ 先递归规范化（整数值浮点 → int；非有限数 → None）
        ensure_ascii=False,                                              # ← 中文原样输出（JS 也不转义非 ASCII）
        separators=(",", ":"),                                           # ← 无空格紧凑输出（= JSON.stringify 的默认）
    )


def _js_normalize(value: Any) -> Any:
    """递归把 Python 数值/容器规范成 JS `JSON.stringify` 的等价形式。"""
    if isinstance(value, bool):                                          # ← ★ 必须先判断 bool（它是 int 的子类）
        return value                                                     # ← True/False 原样交给 json.dumps → true/false
    if isinstance(value, float):                                         # ← 只处理 float：int 本来就是整数字面量
        if value != value or value in (float("inf"), float("-inf")):      # ← NaN 的唯一性质：x != x；以及 ±Inf
            return None                                                  # ← JS: NaN/Infinity → null
        return int(value) if value.is_integer() else value               # ← 3.0 → 3；2.5 保持不变
    if isinstance(value, list):
        return [_js_normalize(item) for item in value]                   # ← ★ 递归数组的每个元素
    if isinstance(value, dict):
        return {key: _js_normalize(item) for key, item in value.items()} # ← ★ 递归对象的每个值
    return value                                                         # ← int / str / None / 其它原样
```

**这段在干什么**（按执行顺序）：

1. `js_json_dumps` 先调 `_js_normalize`，再用 `json.dumps` 输出。**规范化在前，序列化在后**——顺序不能反，否则 `1.0` 已经变成 `"1.0"` 文本，改不回来了。
2. `ensure_ascii=False`：让中文保持原字符。JS 的 `JSON.stringify` 不转义非 ASCII，Python 默认会转义成 `\uXXXX`，两者会分叉。
3. `separators=(",", ":")`：去掉 `, ` 与 `: ` 的空格。JS 默认就是紧凑格式。
4. `_js_normalize` 先判 `bool`（见 §11.6），再判 `float`：
   - `value != value` 是检测 `NaN` 的惯用法（`NaN` 不等于任何值，包括自己）；
   - `value in (float("inf"), float("-inf"))` 检测正负无穷；
   - `value.is_integer()` 判断「整数值浮点」，是则转 `int`；
   - 其它 `float`（如 `2.5`）原样返回。
5. `list` / `dict` 递归处理每个元素/值；其余类型（`int`、`str`、`None`）原样返回。

**为什么修复放在 `template.py` 而不是 `iteration.py`**：`template.py` 的 `_stringify` 也是同一个出口——任何**非字符串模板值**（比如 `{{ llm_1.score }}`、`{{ start.inputs.items }}`）都走它。数值分叉不是迭代独有的，只是迭代把「每项都渲染成文本」放大了。修在共享出口，才是一次性收口。

### 11.5 为什么必须递归，而不能只在顶层判断

假设只做顶层判断：

```python
# ❌ 只在顶层处理
if isinstance(value, float) and value.is_integer():
    value = int(value)
return json.dumps(value, ensure_ascii=False, separators=(",", ":"))
```

那么：

| 输入 | 顶层处理后 | 输出 | JS 输出 | 是否分叉 |
| --- | --- | --- | --- | --- |
| `3.0` | `3` | `"3"` | `"3"` | ✅ |
| `{"a":1.0}` | 不变（顶层是 dict） | `"{\"a\":1.0}"` | `"{\"a\":1}"` | ❌ |
| `[4.0,5]` | 不变（顶层是 list） | `"[4.0,5]"` | `"[4,5]"` | ❌ |

**迭代的项经常是对象**（一批用户记录、一批候选答案），嵌套数值才是常态。所以必须**深度遍历**：`list` 逐元素、`dict` 逐值递归。`_js_normalize` 的两个递归分支就是干这个的。

### 11.6 `bool` 是 `int` 的子类：判断顺序的陷阱

Python 里：

```python
isinstance(True, int)     # → True
isinstance(True, float)   # → False
```

也就是说，**布尔值会被任何 `int` 判断捕获**。如果「整数值 → int」写成下面这样：

```python
# ❌ 危险写法：用 (int, float) 一起判断
if isinstance(value, (int, float)) and float(value).is_integer():
    return int(value)
```

那么：

```text
True → int(True) → 1 → json.dumps(1) → "1"
```

而 JS 的 `JSON.stringify(true)` 是 `"true"`。于是 `{"ok": true}` 在 Python 侧会变成 `{"ok":1}`——**又一处跨语言分叉，而且更隐蔽**（`true` 与 `1` 看起来都「像」布尔/数字）。

所以 `_js_normalize` 的**第一行**就是：

```python
if isinstance(value, bool):
    return value
```

**先排掉 `bool`，后面的 `float`/`int` 判断才安全。** 当前实现里没有 `int` 分支，这个判断看起来「多余」，但它是**防御性**的：只要有人后来加了 `int` 分支、或把判断改成 `(int, float)`，没有这一行就会立刻把 `true` 变成 `1`。同样的陷阱在 `iteration.py` 取 `maxIterations` 时也出现过一次：`not isinstance(raw_max, bool)`。

### 11.7 为什么 TS 侧一行都不用改

因为 `JSON.stringify` **本来就是 JS 的口径**：

- 整数值浮点 → 整数（JS 里没有「浮点 3.0」这个东西）；
- `NaN` / `Infinity` → `null`；
- 紧凑、不转义非 ASCII。

所以「对齐」的方向是**让 Python 模仿 TS**，而不是反过来。不要在 TS 侧手写格式化函数——那只会引入第二套需要维护的规则。

### 11.8 实测：修复前 vs 修复后

输入 `[1, 2.5, 3.0, {"a":1.0}, {"b":[4.0,5]}]`，模板 `"{{ item }} / {{ itemIndex }}"`：

| 项 | 修复前 Python | 修复后 TS | 修复后 Python |
| --- | --- | --- | --- |
| 1 | `1.0 / 1` | `1 / 1` | `1 / 1` ✅ |
| 2.5 | `2.5 / 2` | `2.5 / 2` | `2.5 / 2` ✅ |
| 3.0 | `3.0 / 3` | `3 / 3` | `3 / 3` ✅ |
| `{"a":1.0}` | `{"a":1.0} / 4` | `{"a":1} / 4` | `{"a":1} / 4` ✅ |
| `{"b":[4.0,5]}` | `{"b":[4.0,5]} / 5` | `{"b":[4,5]} / 5` | `{"b":[4,5]} / 5` ✅ |

修复后两端 `results` 与 `joined` **逐字节一致**（`joined` 是 5 行，用 `\n` 连接）。

### 11.9 已知的剩余边界（本次未处理，实测记录）

`_js_normalize` 解决的是**常见数值**。下面两类仍然会分叉，属于教学项目刻意不处理的边界：

| 输入 | JS `JSON.stringify` | Python `js_json_dumps` | 原因 |
| --- | --- | --- | --- |
| `1e21` | `"1e+21"` | `"1000000000000000000000"` | JS 用科学计数法打印大数；Python 规范化后把整数值浮点转成了 `int`，`json.dumps` 打印完整十进制 |
| `123456789012345678901`（整数） | `"123456789012345680000"` | `"123456789012345678901"` | JS 只有双精度，超过 2^53 的整数会丢精度；Python `int` 是任意精度 |
| `-0.0` | `"0"` | `"0"` | ✅ 已被 `int(-0.0) == 0` 顺带对齐 |

**结论**：本项目验收用的数值都远小于 2^53、也不是科学计数法量级，所以「逐字节一致」在这些用例上成立；如果要处理金融级大整数或超大浮点，需要额外的格式化规则（不要直接假设 `js_json_dumps` 万能）。

### 11.10 结论：跨语言一致性是具体细节，不是口号

「两端契约一致」在阶段 0~7 已经收口过很多层：错误文案、时间格式、JSONB 往返、chunk 字节、检索分数……阶段 8 又加了一层**序列化口径**：

```text
契约一致
  ├─ 结构一致（字段名、类型、必填）
  ├─ 值规范一致（时间格式、错误文案）
  ├─ 过程一致（事件序列、帧格式）
  └─ ★ 序列化一致（同一个值 → 同一串字节）
```

`1.0` vs `1` 就是最后一层的最小例子。它不会让程序崩溃，却会让「逐字节验收」失败、让 LLM 的输入差一个字符、让前端的展示出现 `1.0`。**真正的跨语言一致性，就是由这类细节堆出来的。**

## 12. 【加厚】与 TS 侧的对照

| 关注点 | TS（`iteration.node.ts`） | Python（`iteration.py`） | 差异与影响 |
| --- | --- | --- | --- |
| 函数形态 | 同步 `runIterationNode` | `async def run_iteration_node` | Python 必须等 `queue.put`，所以整个节点是异步的 |
| 进度回调 | `emitItem: (index, total) => void` | `EmitItem = Callable[[int,int], Awaitable[None]]` | TS 是「发出去就返回」；Python 要 `await` |
| 默认上限 | `DEFAULT_MAX_ITERATIONS = 20` | 同名常量 | 同值 |
| `maxIterations` 取默认 | `typeof === 'number'` | `isinstance((int,float)) and not isinstance(bool)` + `int()` | Python 多一层 `bool` 排除；且会把 `2.5` 截成 `2`（契约要求整数，预检已拦） |
| `itemName` 取默认 | `typeof === 'string' && !== ''` | `isinstance(str) and != ""` | 一致 |
| 安全渲染 | `tryRenderTemplate` | `try_render_template` | 同名同义 |
| 解析 | `JSON.parse`（抛 `SyntaxError`） | `json.loads`（抛 `ValueError`） | 捕获的异常类型不同，文案相同 |
| 数组判断 | `Array.isArray(items)` | `isinstance(items, list)` | 一致 |
| 遍历 | `items.map((item, index) => …)` | `for index, item in enumerate(items)` | 语义一致 |
| 项字符串化 | `typeof === 'string' ? item : JSON.stringify(item)` | `isinstance(item, str) ? item : js_json_dumps(item)` | **核心差异**：Python 不能直接用 `json.dumps` |
| 上下文构造 | `{ ...pool, [itemName]: …, itemIndex, itemCount }` | `{ **pool, item_name: …, "itemIndex": …, "itemCount": … }` | 计算属性 vs 运行时键名；展开语法一致 |
| 输出拼接 | `results.join('\n')` | `"\n".join(results)` | 一致 |
| 错误文案插值 | 模板字符串 `` `iteration node ${node.id} …` `` | f-string `f"iteration node {node['id']} …"` | 输出文本逐字节相同 |
| 类型标注 | `Record<string, unknown>` | `dict[str, Any]` | TS 的 `unknown` 对应 Python 的 `Any`（但 Python 运行期不强制） |

### 12.1 三个值得记住的不对称

**① 回调的同步/异步。** TS 的 `queue.emit()` 是同步入队，所以节点可以是普通函数；Python 的 `asyncio.Queue.put()` 是协程，必须 `await`。这就是为什么 `run_iteration_node` 是 `async`，而 `runIterationNode` 不是。写 Python 侧时如果忘了 `await`，会得到一个未等待的协程对象——事件不会发出，运行时只给一条 `RuntimeWarning: coroutine was never awaited`，流程却照常往下走（最隐蔽的那种 bug）。

**② 数字类型系统不同。** TS 只有 `number`，Python 有 `int` / `float` / `bool`（且 `bool` 是 `int` 子类）。本篇的 `js_json_dumps` 与 `not isinstance(..., bool)` 都是为这个不对称打的补丁。

**③ 序列化默认值不同。** `JSON.stringify` 紧凑、不转义非 ASCII、NaN → `null`；`json.dumps` 默认带空格、转义非 ASCII、NaN → `NaN`。三个默认值都必须显式对齐，缺一个就会在某类输入上分叉。

## 13. 【加厚】本篇首次出现的机制

> 每条按「**是什么 → TS 里对应什么 → 这里为什么这么写**」展开。

### 13.1 节点内循环（不产生图循环）

**是什么**：把「对数组逐项处理」实现在节点函数内部，画布上仍是一个节点、图上仍是无环的。

**TS 里对应什么**：`iteration.node.ts` 的 `items.map`；对应 `condition` 的一次性判断、`aggregator` 的一次性合并，都是「一个节点只发一对 `node_started`/`node_finished`」。

**这里为什么这么写**：

- 图结构稳定：数组长度变化不需要改图；
- 不触发 LangGraph 的 `recursionLimit`；
- 事件序列可预期：`node_started` → N × `iteration_item` → `node_finished`，前端容易做进度条；
- 代价是节点执行时间长，必须靠 §8 的上限与 §9 的进度事件兜住。

### 13.2 模板驱动的数组输入（渲染 + 解析两阶段）

**是什么**：`inputArray` 先按模板渲染成文本，再 `JSON.parse` / `json.loads` 成值；两阶段都可能失败，但共用一句文案。

**TS 里对应什么**：`tryRenderTemplate`（阶段 8 的 `condition` / `aggregator` 也在用）+ `JSON.parse`。

**这里为什么这么写**：

- 一个字符串字段就能表达「字面量数组」「上游数组」「上游 JSON 字符串」「拼接结果」四种来源；
- 安全解析让「上游分支没执行」不报模板错，而是得到空串 → 随后统一报 `must be an array`；
- 文案不区分「不是 JSON」与「不是数组」，因为对用户来说这是同一件事：**你给的不是数组**。

### 13.3 顶层键上下文注入与变量遮蔽

**是什么**：每项渲染时构造 `{...pool, item, itemIndex, itemCount}`，三个键都在**顶层**。

**TS 里对应什么**：`{ ...pool, [itemName]: … }`；Python 的 `{**pool, ...}`。与阶段 4 的 `pool[nodeId] = output` 是同一套「扁平命名空间」。

**这里为什么这么写**：

- 模板没有「局部作用域」概念，只有顶层点路径；注入顶层键是唯一能让 `{{ item }}` 生效的方式；
- 注入键放在展开之后，所以可以覆盖同名键（包括误用节点 id 当 `itemName` 的情况）；
- `item` 是**字符串**而非原对象，因此 `{{ item.title }}` 必然失败——这是设计约束，不是 bug（§7.1）。

### 13.4 项字符串化（字符串原样 / 其余紧凑 JSON）

**是什么**：`stringifyItem` / `_stringify_item`：`string` 原样返回，其它值序列化成紧凑 JSON。

**TS 里对应什么**：`typeof item === 'string' ? item : JSON.stringify(item)`。

**这里为什么这么写**：

- 模板替换的产物是**文本**，非字符串必须先转；
- 不能直接 `String(item)`：对象会变成 `[object Object]`，数组会变成 `1,2,3`（丢结构）；
- 字符串特判是为了避免多出一层引号：项是「内容」，不是「JSON 片段」。

### 13.5 `maxIterations` 的双层上限

**是什么**：配置范围 1..100 由**预检**保证；运行时数组长度由**节点**保证不超过配置值；默认 20。

**TS 里对应什么**：`graph.validator.ts` 规则 10 + `engine.service.ts` 的节点数据校验（类型）+ 节点内的 `items.length > maxIterations`。

**这里为什么这么写**：

- 预检看不到运行时数组长度（它可能来自上游），所以必须有运行期检查；
- 上限是**成本护栏**：每项可能是一次 LLM 调用；
- 整体失败（而不是部分成功）让「数组爆炸」立刻暴露，避免半成品输出被下游消费。

### 13.6 `iteration_item` 进度事件

**是什么**：每项开始处理时发一次 `{nodeId, index, total}`，`index` 从 1 开始。

**TS 里对应什么**：`events.ts` 的 `iterationItem`；引擎在 `case 'iteration'` 里把它接到 `queue.emit`。Python 对应 `events.py` 的 `iteration_item` + `queue.put`。

**这里为什么这么写**：

- 长任务需要「心跳」，否则 SSE 流长时间无事件容易被中间层判定空闲；
- 与 `token` 的流式理念一致：**过程可观测**；
- payload 只放进度，不放内容：体积小、稳定、不泄露数据。

### 13.7 `joined` 聚合输出

**是什么**：`results.join("\n")` 的整串文本。

**TS 里对应什么**：`results.join('\n')`；Python `"\n".join(results)`。

**这里为什么这么写**：

- 模板**不能索引数组**（`resolvePath` 遇数组即判不存在），`results[0]` 写不出来；
- 最常见的下游需求是「把 N 条结果作为一段文本交给 LLM / 展示」，`joined` 让它一行模板就能用；
- `results` 仍保留结构化形态，供需要 JSON 的消费方使用。

### 13.8 跨语言数值规范化（`js_json_dumps` / `_js_normalize`）

**是什么**：把 Python 的数值/容器递归规范成 JS `JSON.stringify` 的等价形式，再紧凑序列化。

**TS 里对应什么**：**不需要对应物**——`JSON.stringify` 本身就是目标口径。

**这里为什么这么写**：

- `json.dumps(1.0)` → `"1.0"`，而 `JSON.stringify(1.0)` → `"1"`；
- `json.dumps(nan)` → `"NaN"`（非法 JSON），而 `JSON.stringify(NaN)` → `"null"`；
- 迭代把每个值都渲染成文本，分叉会被放大到每一行；
- 修复必须**递归**，因为项经常是嵌套对象/数组。

### 13.9 Python 的 `bool` 与数值类型层级

**是什么**：`bool` 是 `int` 的子类；`isinstance(True, int)` 为 `True`，`isinstance(True, float)` 为 `False`。

**TS 里对应什么**：`typeof true === 'boolean'`，与 `number` 完全不重叠，所以 TS 没有这个问题。

**这里为什么这么写**：

- 任何「数字判断」都必须先排除 `bool`，否则 `true` 会被转成 `1`；
- 这在 `_js_normalize`（序列化）与 `maxIterations`（配置解析）两处都出现过；
- 是一个「不报错、只出错」的类型系统陷阱，靠测试和代码评审发现。

### 13.10 递归规范化容器

**是什么**：`_js_normalize` 对 `list` 逐元素、对 `dict` 逐值递归。

**TS 里对应什么**：`JSON.stringify` 内部本来就会递归遍历整个对象图。

**这里为什么这么写**：

- 只在顶层判断只能修好「裸数字」；
- 迭代的项常常是对象，嵌套的 `1.0` 才是多数；
- 递归实现很短（两个分支），却能覆盖任意深度。

## 14. 【加厚】写错会怎样

### 14.1 `inputArray` 是字符串 `"abc"` → `must be an array`

**现象**（实测）：

```text
run_failed: iteration node iter1 inputArray must be an array
```

**原因**：`tryRenderTemplate` 把 `"abc"` 原样渲染（它没有 `{{ }}`），`JSON.parse("abc")` 抛 `SyntaxError` → 被捕获 → 统一文案。若写 `{"a":1}`（合法 JSON 但不是数组），走的是 `Array.isArray` 分支，**文案相同**。

**正解**：`inputArray` 必须是「渲染后能得到 JSON 数组」的模板。自测时用 `["A","B","C"]`；引用上游时确认该值是数组或 JSON 数组字符串。

### 14.2 数组超上限 → `exceeded max iterations: 2`

**现象**（实测，`maxIterations: 2`、3 项）：

```text
run_failed: iteration node iter1 exceeded max iterations: 2
```

**原因**：长度检查在循环之前；文案里的数字是**配置值**。

**正解**：先确认数组为什么这么长（通常是上游拆分粒度错了），再决定是过滤、分批，还是（确实需要时）调整 `maxIterations`（不得超过 100）。

### 14.3 模板写 `{{ item.name }}` → `template variable not found: item.name`

**现象**（实测）：

```text
run_failed: template variable not found: item.name
```

**原因**：`item` 注入的是**字符串**（`stringifyItem` 的产物），`resolvePath` 的第一段就要求当前值是普通对象；字符串/数组都会判「不存在」。

**正解**：

- 要整个对象的 JSON 文本：直接 `{{ item }}`（得到 `{"name":"A"}`）；
- 想取字段：让上游先把数组元素拆成扁平结构，或用模板对整串再处理——**本项目没有在模板里索引/取属性的语法**。

### 14.4 忘记递归规范化 → `1.0` vs `1` 分叉

**现象**：两端都能跑完，但 `results` / `joined` 文本不同：

```text
TS     : 第1/3项: 1
Python : 第1/3项: 1.0
```

`node_finished.output` 不再逐字节相同；下游 LLM prompt 差一个字符；前端展示不一致。

**原因**：`json.dumps(1.0)` → `"1.0"`，而 `JSON.stringify(1.0)` → `"1"`。

**正解**：非字符串项一律走 `js_json_dumps`；且它必须**递归**处理 `list` / `dict`（§11.5）。修完用 §17.1 的数值用例两端各跑一次，直接比对 `JSON.stringify(out)` 的字节。

### 14.5 `isinstance(True, int)` 陷阱 → `true` 变 `1`

**现象**：`{"ok": true}` 在 Python 侧渲染成 `{"ok":1}`；TS 侧是 `{"ok":true}`。

**原因**：`True` 是 `int` 的子类，任何「整数值 → int」的判断都会捕获它。

**正解**：在数值判断**之前**先 `if isinstance(value, bool): return value`；不要用 `isinstance(value, (int, float))` 直接当「数字」。

### 14.6 `inputArray` 为空 → 预检 400

**现象**：

```json
{"statusCode":400,"message":"iteration node iter1 inputArray is required","error":"Bad Request"}
```

**原因**：预检规则 8.1.11（`inputArray` 不是字符串或全是空白）。

**正解**：至少写 `[]`（空数组是合法的，`results=[]`、`count=0`、`joined=""`），而不是留空串。

### 14.7 `maxIterations` 越界 → 预检 400

**现象**：

```json
{"statusCode":400,"message":"iteration node iter1 maxIterations must be between 1 and 100","error":"Bad Request"}
```

**原因**：预检规则 8.1.12；`0`、`101`、`2.5` 都算越界（必须是 1..100 的**整数**）。

**正解**：保持整数；不确定时干脆不写，用默认 20。

### 14.8 改了 `itemName` 但模板没改 → `item` 找不到

**现象**：

```text
run_failed: template variable not found: item
```

**原因**：配置 `itemName: "row"` 后，只有 `row` 被注入；`{{ item }}` 不再存在。

**正解**：`itemName` 与模板一起改；或者干脆不配，用默认 `item`。

### 15.1 `apps/api-ts/src/engine/nodes/iteration.node.ts`

**完整文件路径：`apps/api-ts/src/engine/nodes/iteration.node.ts`**

```ts
import type { GraphNode, IterationNodeData } from '@mini-dify/contract'

import { RunError } from '../events'
import { renderTemplate, tryRenderTemplate, type Pool } from '../template'

/** `iteration.maxIterations` 的默认值（与契约 `default: 20` 一致）。 */
export const DEFAULT_MAX_ITERATIONS = 20

/**
 * `iteration` 节点（阶段 8）：`inputArray` 安全解析后 `JSON.parse`，必须是数组；
 * 逐项先发 `iteration_item`（`index` 从 1 开始），再以
 * `{ ...pool, <itemName>: <item>, itemIndex, itemCount }` 渲染 `outputTemplate`。
 *
 * 输出 `{ results, count, joined }`，`joined = results.join("\n")`。
 * 数组长度超过 `maxIterations` 或解析结果不是数组时抛 `RunError`（见 error-messages.md §8.2）。
 */
export function runIterationNode(
  node: GraphNode,
  pool: Pool,
  emitItem: (index: number, total: number) => void,
): Record<string, unknown> {
  const data = node.data as unknown as IterationNodeData
  const maxIterations =
    typeof data.maxIterations === 'number' ? data.maxIterations : DEFAULT_MAX_ITERATIONS
  const itemName =
    typeof data.itemName === 'string' && data.itemName !== '' ? data.itemName : 'item'

  const rendered = tryRenderTemplate(data.inputArray, pool)
  let items: unknown
  try {
    items = JSON.parse(rendered)
  } catch {
    throw new RunError(`iteration node ${node.id} inputArray must be an array`)
  }
  if (!Array.isArray(items)) {
    throw new RunError(`iteration node ${node.id} inputArray must be an array`)
  }
  if (items.length > maxIterations) {
    throw new RunError(`iteration node ${node.id} exceeded max iterations: ${maxIterations}`)
  }

  const total = items.length
  const results = items.map((item, index) => {
    emitItem(index + 1, total)
    return renderTemplate(data.outputTemplate, {
      ...pool,
      [itemName]: stringifyItem(item),
      itemIndex: index + 1,
      itemCount: total,
    })
  })

  return { results, count: results.length, joined: results.join('\n') }
}

/** 当前项字符串化：字符串原样，其余按紧凑 JSON（两端一致）。 */
function stringifyItem(item: unknown): string {
  return typeof item === 'string' ? item : JSON.stringify(item)
}
```

### 15.2 `apps/api-py/app/engine/nodes/iteration.py`

**完整文件路径：`apps/api-py/app/engine/nodes/iteration.py`**

```python
"""`iteration` 节点（阶段 8）。

与 api-ts 的 `apps/api-ts/src/engine/nodes/iteration.node.ts` 对齐：
`inputArray` 安全解析后 `JSON.parse`，必须是数组；逐项先发 `iteration_item`
（`index` 从 1 开始），再以 `{...pool, <itemName>: <item>, itemIndex, itemCount}`
渲染 `outputTemplate`。

输出 `{ "results": string[], "count": number, "joined": string }`，
`joined = "\\n".join(results)`。数组长度超过 `maxIterations` 或解析结果不是数组时抛
`RunError`（见 error-messages.md §8.2）。
"""

import json
from collections.abc import Awaitable, Callable
from typing import Any

from app.engine.events import RunError
from app.engine.template import js_json_dumps, render_template, try_render_template

# `iteration.maxIterations` 的默认值（与契约 `default: 20` 一致）
DEFAULT_MAX_ITERATIONS = 20

EmitItem = Callable[[int, int], Awaitable[None]]


async def run_iteration_node(
    node: dict[str, Any],
    pool: dict[str, Any],
    emit_item: EmitItem,
) -> dict[str, Any]:
    """执行 `iteration` 节点：逐项发 `iteration_item` 并渲染 `outputTemplate`。"""
    data: dict[str, Any] = node["data"]
    raw_max = data.get("maxIterations")
    max_iterations = (
        int(raw_max)
        if isinstance(raw_max, (int, float)) and not isinstance(raw_max, bool)
        else DEFAULT_MAX_ITERATIONS
    )
    raw_item_name = data.get("itemName")
    item_name = raw_item_name if isinstance(raw_item_name, str) and raw_item_name != "" else "item"

    rendered = try_render_template(data["inputArray"], pool)
    try:
        items = json.loads(rendered)
    except ValueError:
        raise RunError(f"iteration node {node['id']} inputArray must be an array") from None
    if not isinstance(items, list):
        raise RunError(f"iteration node {node['id']} inputArray must be an array")
    if len(items) > max_iterations:
        raise RunError(
            f"iteration node {node['id']} exceeded max iterations: {max_iterations}"
        )

    total = len(items)
    results: list[str] = []
    for index, item in enumerate(items):
        await emit_item(index + 1, total)
        results.append(
            render_template(
                data["outputTemplate"],
                {
                    **pool,
                    item_name: _stringify_item(item),
                    "itemIndex": index + 1,
                    "itemCount": total,
                },
            )
        )

    return {"results": results, "count": len(results), "joined": "\n".join(results)}


def _stringify_item(item: Any) -> str:
    """当前项字符串化：字符串原样，其余按紧凑 JSON（两端一致）。

    用 `js_json_dumps` 而不是 `json.dumps`：整数值浮点在 JS 里序列化为 `1`、
    在 Python 里是 `1.0`，迭代数字数组时会导致两端输出分叉。
    """
    if isinstance(item, str):
        return item
    return js_json_dumps(item)
```

### 15.3 `apps/api-py/app/engine/template.py`（`js_json_dumps` / `_js_normalize`）

**完整文件路径：`apps/api-py/app/engine/template.py`（行 65–96）**

```python
def js_json_dumps(value: Any) -> str:
    """按 **JavaScript `JSON.stringify` 的口径**做紧凑 JSON 序列化。

    为什么不能直接用 `json.dumps`：两种语言对浮点的输出不同 ——
    `JSON.stringify(1.0)` 得到 `"1"`，而 Python `json.dumps(1.0)` 得到 `"1.0"`。
    迭代节点对「数字数组」逐项渲染时，这个差异会让两端输出分叉。
    另外 JS 对 `NaN`/`Infinity` 输出 `null`，Python 默认输出 `NaN`/`Infinity`（非法 JSON）。

    规则：
    - 整数值的 `float` → 整数（`1.0` → `1`）
    - `NaN` / `±Infinity` → `None`（序列化为 `null`）
    - 递归处理 list / dict
    """
    return json.dumps(
        _js_normalize(value), ensure_ascii=False, separators=(",", ":")
    )


def _js_normalize(value: Any) -> Any:
    """递归把 Python 数值/容器规范成 JS `JSON.stringify` 的等价形式。"""
    if isinstance(value, bool):
        # bool 是 int 的子类，必须排在 float/int 判断之前
        return value
    if isinstance(value, float):
        if value != value or value in (float("inf"), float("-inf")):  # NaN / ±Inf
            return None
        return int(value) if value.is_integer() else value
    if isinstance(value, list):
        return [_js_normalize(item) for item in value]
    if isinstance(value, dict):
        return {key: _js_normalize(item) for key, item in value.items()}
    return value
```

## 18. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `inputArray must be an array` | 模板渲染结果不是 JSON，或不是数组 | 用 `["A","B"]` 自测；引用上游时确认值类型；注意缺失路径会变空串 |
| 明明上游有数组，却报「must be an array」 | 路径写错（安全解析把缺失当空串） | 对照变量池：`inputs.*` 与 `<nodeId>.*`；先看该节点的 `node_finished.output` |
| `template variable not found: item.name` | `item` 是字符串，模板不能取属性/下标 | 用 `{{ item }}`；需要字段就改上游数据形状 |
| Python 输出 `1.0`、`{"a":1.0}`、`[4.0,5]` | 用了 `json.dumps` 而不是 `js_json_dumps` | 换成 `js_json_dumps`，并确认 `_js_normalize` **递归** |
| Python 输出里出现 `NaN` / `Infinity` | `json.dumps` 默认 `allow_nan=True` | 规范化阶段把非有限数转 `None` |
| Python 把 `true` 输出成 `1` | `bool` 是 `int` 子类，判断顺序错了 | `bool` 判断放在最前 |
| `exceeded max iterations: 20` | 数组比默认上限长 | 先查上游为什么这么长；确需更多项时再调 `maxIterations`（≤100） |
| 配了 `maxIterations: 200` 直接 400 | 契约上限 100，预检拒绝 | 改成 ≤100；或改上游分批 |
| 改小 `maxIterations` 后仍跑很久 | 每项可能触发 LLM 调用，耗时线性 | 用 `iteration_item` 观察进度；必要时减少项数而不是只调上限 |
| 下游写 `{{ item }}` 报 not found | `item` 只在迭代节点**内部**存在 | 用 `{{ iter_1.joined }}` / `{{ iter_1.results }}` |
| `{{ iter_1.results[0] }}` 报错 | 模板没有数组下标语法 | 用 `joined`，或在迭代的 `outputTemplate` 里就把需要的形态拼好 |
| `end` 输出 `count` 是 `"3"` 不是 `3` | `end` 的值一律渲染成字符串 | 这是阶段 4 的既定语义；需要数字请在下游自行解析 |
| 两端 `results` 相同但 `joined` 不同 | 连接符写错（`\n` vs 其它） | 统一 `join('\n')` / `"\n".join(...)` |
| 事件里看不到「处理到哪一项」 | 只看了 `node_finished` | `iteration_item` 在它之前逐项发出；前端面板有「迭代进度」区 |
