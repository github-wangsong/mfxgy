## 0. 阶段 8 的立论：只会直线执行的图，是玩具

前七个阶段，应用的能力线是：**画图 → 存取 → 执行 → 调模型 → 调工具 → 查知识库**。但它始终有一个隐含限制：

> **一张图只有一条路径。**

`start → llm → end`、`start → knowledge → llm → end`、`start → llm(带工具) → end`——不论节点多少，执行序列都是**唯一**的。阶段 6 的 ReAct 虽然出现了「条件边 + 环」，但那是在**一个 `llm` 节点内部**用 LangGraph 实现的，画布上并没有「分支」这个概念。

真实业务几乎没有单一路径：

| 场景 | 条件 | 两条路径 |
| --- | --- | --- |
| 客服质检 | 用户说的是好评还是差评 | 好评 → 感谢模板；差评 → 安抚 + 转人工话术 |
| 库存查询 | 库存 > 0 | 有货 → 下单链接；无货 → 到货提醒 |
| 金额审核 | 金额 > 阈值 | 小额 → 自动通过；大额 → 人工复核 |
| 多语言 | 语言 = zh / en / ja | 三套 prompt / 三个模型 |
| 容错 | 上一步输出是否为空 | 有值 → 用值；为空 → 走兜底文案 |
| 批处理 | 输入是不是数组 | 是 → 逐项处理；否 → 直接返回 |

阶段 8 增加三种节点，本质是给图加**三种控制流**：

```
condition    分支：一个节点 → 多个出口，运行时只走一条
aggregator   汇聚：多条分支 → 一个汇合点，收敛成单一路径的输入
iteration    迭代：一个节点内部对数组逐项循环（不是图循环）
```

其中 `aggregator` 不是「可选的便利工具」，而是分支图的**必要配套**：分支一旦存在，下游就会同时引用「只执行了一条」的两个变量——`aggregator` 就是为了让下游不必知道「刚才走的是哪条」而存在的（§18）。

> 一句话记住本阶段：**分支负责「分开」，聚合负责「合上」，迭代负责「重复」，而 `sourceHandle` 是分支这件事在图里的唯一表达方式。**

8. 下列 7 组非法输入，两端返回 **逐字节相同**的 400 文案（本篇实测）：

10. `iteration` 数组长度超过 `maxIterations`（流内）→ `run_failed`：`iteration node iter1 exceeded max iterations: 2`。
11. 运行合法分支图时事件序列出现 **恰好一次** `branch_taken`，其 `caseId` 是选中分支的 `id`（全部不匹配时是 `"else"`）。

### 3.2 一张合法的分支图（本篇反复使用）

```
                 ┌──(good)──▶ llm_good ──┐
s1(start) ──▶ c1(condition)             ├──▶ agg1(aggregator) ──▶ e1(end)
                 ├──(bad)───▶ llm_bad  ──┤
                 └──(else)──▶ llm_bad  ──┘
```

要点：

- `c1` 有 **4 条出边**？不，是 **3 条**（`good` / `bad` / `else`），其中 `bad` 与 `else` 指向**同一个** `llm_bad`。这是允许的：校验只看 `sourceHandle`，不看 `target` 是否重复（§8.1 第 7 条注释）。
- `llm_good` 与 `llm_bad` **只会执行一个**，但 `agg1` 一定执行——它把「两条分支各自的 `text`」收敛成一个 `answer`。
- `e1` 只引用 `{{ agg1.answer }}`，**从不**直接引用 `{{ llm_good.text }}`：那是分支图里最容易踩的坑（§18.3）。

完整 JSON（`branch.json`，保存到仓库根，UTF-8 无 BOM）：

```json
{
  "version": "1",
  "nodes": [
    {
      "id": "s1",
      "type": "start",
      "position": { "x": 0, "y": 0 },
      "data": { "inputs": [{ "name": "topic", "type": "string", "required": true }] }
    },
    {
      "id": "c1",
      "type": "condition",
      "position": { "x": 220, "y": 0 },
      "data": {
        "title": "情感分流",
        "conditions": [
          {
            "id": "good",
            "label": "好评",
            "variable": "{{ inputs.topic }}",
            "operator": "contains",
            "value": "好"
          },
          {
            "id": "bad",
            "label": "差评",
            "variable": "{{ inputs.topic }}",
            "operator": "contains",
            "value": "差"
          }
        ]
      }
    },
    {
      "id": "llm_good",
      "type": "llm",
      "position": { "x": 440, "y": -120 },
      "data": { "title": "好评回复", "model": "", "prompt": "感谢用户：{{ inputs.topic }}" }
    },
    {
      "id": "llm_bad",
      "type": "llm",
      "position": { "x": 440, "y": 120 },
      "data": { "title": "差评安抚", "model": "", "prompt": "安抚用户并致歉：{{ inputs.topic }}" }
    },
    {
      "id": "agg1",
      "type": "aggregator",
      "position": { "x": 680, "y": 0 },
      "data": {
        "title": "收敛答案",
        "outputs": [
          { "name": "answer", "values": ["{{ llm_good.text }}", "{{ llm_bad.text }}"] }
        ]
      }
    },
    {
      "id": "e1",
      "type": "end",
      "position": { "x": 900, "y": 0 },
      "data": { "outputs": [{ "name": "answer", "value": "{{ agg1.answer }}" }] }
    }
  ],
  "edges": [
    { "id": "e_s_c", "source": "s1", "target": "c1" },
    { "id": "e_good", "source": "c1", "target": "llm_good", "sourceHandle": "good" },
    { "id": "e_bad", "source": "c1", "target": "llm_bad", "sourceHandle": "bad" },
    { "id": "e_else", "source": "c1", "target": "llm_bad", "sourceHandle": "else" },
    { "id": "e_g_agg", "source": "llm_good", "target": "agg1" },
    { "id": "e_b_agg", "source": "llm_bad", "target": "agg1" },
    { "id": "e_agg_end", "source": "agg1", "target": "e1" }
  ]
}
```

**这段在干什么**

1. `c1` 的 `data.conditions` 是**有序数组**：`good` 在前、`bad` 在后。顺序就是优先级——如果某段文本同时含「好」和「差」，走 `good`（§16）。
2. 每个条件有 `id`（分支标识，等于 `edge.sourceHandle`）、`label`（给人和事件看）、`variable`（模板）、`operator`、`value`（模板或字面量）。
3. `c1` 的**所有出边**都带 `sourceHandle`，且只取 `good` / `bad` / `else` 三个值之一。
4. `llm_*` 与 `agg1` 之间的边**没有** `sourceHandle`：普通节点只有一个出口，句柄为空（省略）即「默认出口」。
5. `agg1.outputs[0].values` 是**两个模板**，按顺序取第一个非空；未执行的那条分支在变量池里根本不存在，安全解析把它渲染成 `""`（§18）。

### 3.3 迭代图（另一张，用于 §19 与验收）

```
s1(start) ──▶ iter1(iteration) ──▶ e1(end)
```

```json
{
  "version": "1",
  "nodes": [
    {
      "id": "s1",
      "type": "start",
      "position": { "x": 0, "y": 0 },
      "data": { "inputs": [{ "name": "items", "type": "string", "required": true }] }
    },
    {
      "id": "iter1",
      "type": "iteration",
      "position": { "x": 220, "y": 0 },
      "data": {
        "title": "逐条改写",
        "inputArray": "{{ inputs.items }}",
        "itemName": "item",
        "maxIterations": 20,
        "outputTemplate": "{{ itemIndex }}/{{ itemCount }}: {{ item }}"
      }
    },
    {
      "id": "e1",
      "type": "end",
      "position": { "x": 440, "y": 0 },
      "data": { "outputs": [{ "name": "joined", "value": "{{ iter1.joined }}" }] }
    }
  ],
  "edges": [
    { "id": "e_s_it", "source": "s1", "target": "iter1" },
    { "id": "e_it_e", "source": "iter1", "target": "e1" }
  ]
}
```

**这段在干什么**

1. `inputArray` 是**字符串模板**，不是数组字面量。运行时先用分支安全规则渲染，再 `JSON.parse`——所以它必须是「渲染后能得到 JSON 数组」的字符串。
2. 运行时传入 `inputs.items = ["退款","物流"]`（**数组**）时，模板渲染的非字符串值走紧凑 JSON，得到 `["退款","物流"]`，正好可解析（§19.2）。注意 `start.data.inputs[].type` 目前**不参与校验**（预检只查 `name`），所以声明为 `"string"` 也能接到数组——这是本阶段刻意保留的宽松点（见 §24）。
3. `outputTemplate` 里 `{{ item }}` 是当前项**字符串化**后的值，`{{ itemIndex }}` 从 **1** 开始，`{{ itemCount }}` 是总数。
4. 下游只认 `{{ iter1.joined }}`——`iteration` 的输出是 `{ results, count, joined }` 三个键。

### 3.4 三种节点在事件流里的位置

```
run_started
  node_started(condition)
  branch_taken          ← 恰好一次
  node_finished(condition)   output = { "matched": "good" }

  node_started(iteration)
  iteration_item        ← 每项一次，index 从 1 开始
  iteration_item
  …
  node_finished(iteration)   output = { "results": [...], "count": N, "joined": "..." }

  node_started(aggregator)
  node_finished(aggregator)   ← 没有专属事件，输出是扁平对象
run_finished
```

**为什么第 1 步不能跳过**

`ConditionOperator`、`ConditionNodeData`、`BranchTakenData` 这些类型来自 `@mini-dify/contract` 的 **`dist`**，不是源码目录。不跑 `build:contract`，NestJS 侧会报「找不到导出成员」；Python 侧虽然不读 TS 类型，但契约文档与错误文案都在这份真源里。

**为什么第 7 步会「写图即校验」**

`PUT /apps/{id}/graph` 与 `POST /apps/{id}/graph/publish` 都会调用纯函数 `validateGraph` / `validate_graph`（阶段 3 定下的规矩：**只有写才校验**，读不校验）。分支图的 8 类规则就挂在同一条链路上，所以「保存」本身就能发现分支错误。

**为什么第 10 步不是 400**

`inputArray` 是不是 JSON 数组，取决于**运行期输入**（`{{ inputs.items }}` 渲染出来才知道）。保存时它只是一个合法字符串，无法判死。因此这类错误只能走**流内 `run_failed`**（阶段 4 的「双通道错误」：请求级 → 400 普通 JSON；流内 → `run_failed`）。

**完整文件路径：`packages/contract/openapi.yaml`**

### 5.1 版本号

```yaml
info:
  title: mini-dify API
  version: 0.8.0
  description: >-
    唯一契约（单真源）。NestJS（api-ts）与 FastAPI（api-py）都必须实现本规范，
    并由同一套契约测试校验两者的响应结构、状态码与错误响应体一致。
```

**这段在干什么**

`version` 是**契约版本**，必须与 `src/index.ts` 的 `CONTRACT_VERSION` 同步（阶段 7 是 `0.7.0`，本篇加了 3 个节点类型、2 个事件、12 条错误，升到 `0.8.0`）。

### 5.2 `GraphNode.type` 扩到 7 种

```yaml
    GraphNode:
      type: object
      additionalProperties: false
      required: [id, type, position, data]
      properties:
        id:
          type: string
        type:
          type: string
          enum: [start, end, llm, knowledge, condition, aggregator, iteration]
        position:
          $ref: "#/components/schemas/NodePosition"
        data:
          type: object
          description: >-
            节点各自的配置（自由结构，由各节点类型自行约定）。
            执行引擎按下列形状解释（见 error-messages.md §4）：
            start → `{ "inputs": [{ "name": string, "type": "string", "required": boolean }] }`；
            llm → `LlmNodeData`（见同文件 components.schemas.LlmNodeData，`model` 为空时回退环境变量 `LLM_MODEL`）；
            knowledge → `KnowledgeNodeData`（见同文件 components.schemas.KnowledgeNodeData）；
            condition → `ConditionNodeData`（见同文件 components.schemas.ConditionNodeData）；
            aggregator → `AggregatorNodeData`（见同文件 components.schemas.AggregatorNodeData）；
            iteration → `IterationNodeData`（见同文件 components.schemas.IterationNodeData）；
            end → `{ "outputs": [{ "name": string, "value": string }] }`（`value` 支持模板）。
          additionalProperties: true
```

**这段在干什么**

1. 节点类型从 5 种变 **7 种**。加节点类型是**契约级变更**：两端校验器、执行引擎、前端画布都得同步认识它，所以必须升版本。
2. `data` 仍是**自由结构**（`additionalProperties: true`），各节点的形状由同文件的 schema 约定；引擎按 `description` 逐类型解释。
3. 注意 `data` 的 `required`（例如 `ConditionNodeData.required: [title, conditions]`）**只是文档层面的形状约定**，两端**不会**逐字段校验 `title`（详见 §12 的分工与 §24 的坑）。

### 5.3 `GraphEdge`：`sourceHandle` 是分支端口

```yaml
    GraphEdge:
      type: object
      additionalProperties: false
      required: [id, source, target]
      properties:
        id:
          type: string
        source:
          type: string
        target:
          type: string
        sourceHandle:
          type: ["string", "null"]
        targetHandle:
          type: ["string", "null"]
```

**这段在干什么**

1. `sourceHandle` / `targetHandle` **不是必填**，且允许显式 `null`：ReactFlow 里没有「端口」的连线就是 `null`，契约必须能接受前端原样回传。
2. 语义上，`targetHandle` 目前**引擎不使用**（目标节点只有一个入口）；真正承载分支语义的是 **`sourceHandle`**。
3. 类型写成 `["string", "null"]` 而不是 `string`：如果只写 `string`，前端把 `null` 回传时会在 DTO 层被拒（`@IsString()` 不允许 `null`），画布保存就会莫名其妙 400。

### 5.4 `ConditionNodeData`

```yaml
    ConditionNodeData:
      type: object
      additionalProperties: true
      required: [title, conditions]
      description: >-
        `condition` 节点的 `data` 形状。按 `conditions` 数组顺序取**第一个**匹配的分支；
        全部不匹配走 `else`。每个 `conditions[].id` 必须有一条 `sourceHandle` 等于它的出边，
        `else` 分支同理（`sourceHandle` 为 `"else"`）。输出 `{ "matched": string }`。
      properties:
        title:
          type: string
        conditions:
          type: array
          minItems: 1
          items:
            type: object
            additionalProperties: true
            required: [id, label, variable, operator]
            properties:
              id:
                type: string
                description: 分支标识（该节点内唯一），用作 `edge.sourceHandle`
              label:
                type: string
              variable:
                type: string
                description: 模板（如 `"{{ inputs.topic }}"`），按分支安全规则解析
              operator:
                type: string
                enum:
                  [equals, not_equals, contains, not_contains, starts_with, ends_with,
                   is_empty, is_not_empty, gt, gte, lt, lte]
              value:
                type: string
                description: 模板或字面量
```

**这段在干什么（按字段）**

1. `conditions` 声明 `minItems: 1`：至少要有一个条件，否则这个节点等价于「总是走 else」，没有存在意义。契约声明边界，**真正的强制在 `validateGraph` 的 8.1.1**。
2. `id` 的 `description` 写死了一件事：**它同时是 `edge.sourceHandle`**。这就是「分支」与「边」的绑定方式（§15）。
3. `label` 是**展示名**，会原样出现在 `branch_taken.label` 里（`else` 分支的 `label` 固定是 `"else"`）。
4. `value` **不是必填**：`is_empty` / `is_not_empty` 不需要右操作数；缺省时按空串参与比较（§17.2）。
5. `operator` 的 `enum` **恰好 12 个**——这是前端下拉框、两端校验器、两端实现的**同一份白名单**。

### 5.5 `AggregatorNodeData`

```yaml
    AggregatorNodeData:
      type: object
      additionalProperties: true
      required: [title, outputs]
      description: >-
        `aggregator` 节点的 `data` 形状。对每个 `name`，按 `values` 顺序取「第一个能解析出
        非空值」的模板结果（模板解析失败视为空串），全空时为 `""`。
        输出为**扁平对象** `{ "<name>": "<值>", ... }`。
      properties:
        title:
          type: string
        outputs:
          type: array
          minItems: 1
          items:
            type: object
            additionalProperties: true
            required: [name, values]
            properties:
              name:
                type: string
              values:
                type: array
                minItems: 1
                items:
                  type: string
```

**这段在干什么**

1. `outputs` 是「要产出哪些变量」；`values` 是「这个变量可以从哪些模板里来」——**有序**，取第一个非空。
2. `values` 的每一项都是**字符串模板**（不是任意 JSON 值）：因为要「渲染后看是否为空串」，必须是字符串。
3. 输出是**扁平对象**（`{ "answer": "..." }`），下游用 `{{ agg1.answer }}`，不需要再拆一层 `outputs[0].value`。

### 5.6 `IterationNodeData`

```yaml
    IterationNodeData:
      type: object
      additionalProperties: true
      required: [title, inputArray, outputTemplate]
      description: >-
        `iteration` 节点的 `data` 形状。`inputArray` 用分支安全规则渲染后必须是 JSON 数组；
        逐项以 `{ ...pool, <itemName>: <item 字符串>, itemIndex, itemCount }` 渲染
        `outputTemplate`。输出 `{ "results": string[], "count": number, "joined": string }`，
        `joined = results.join("\n")`。
      properties:
        title:
          type: string
        inputArray:
          type: string
          description: 模板，解析后必须是 JSON 数组
        itemName:
          type: string
          default: item
          description: 当前项的变量名，默认 `item`
        maxIterations:
          type: integer
          minimum: 1
          maximum: 100
          default: 20
        outputTemplate:
          type: string
          description: 每项渲染一次（支持 `{{ item }}` / `{{ itemIndex }}` / `{{ itemCount }}`）
```

**这段在干什么**

1. `inputArray` 的类型是 **`string`**（模板），不是 `array`。这是全篇最容易误解的一处：**数组是「渲染 + `JSON.parse` 之后」的产物**。
2. `itemName` 默认 `"item"`，允许改名（例如 `row`），避免嵌套迭代时同名遮蔽。
3. `maxIterations` 默认 **20**、范围 **1..100**：既是成本护栏，也是「别把整库当数组逐项打模型」的刹车。
4. `outputTemplate` 每项渲染一次；三个内置变量 `item` / `itemIndex` / `itemCount` 由引擎注入，**不是**来自变量池。

```yaml
        data:
          type: object
          additionalProperties: true

```

**这段在干什么**

1. 枚举从 9 种变 **11 种**，在 `retrieval` 之后插入 `branch_taken`、`iteration_item`——位置有意义：它们都发生在 `node_finished` 之前。

### 6.1 版本号

**这段在干什么**

### 6.2 `GraphNode` 与 `GraphEdge`

```ts
/** 画布节点。`data` 为节点各自的配置（自由结构）。 */
export interface GraphNode {
  id: string
  type: 'start' | 'end' | 'llm' | 'knowledge' | 'condition' | 'aggregator' | 'iteration'
  position: NodePosition
  data: Record<string, unknown>
}

/** 画布连线。 */
export interface GraphEdge {
  id: string
  source: string
  target: string
  sourceHandle?: string | null
  targetHandle?: string | null
}

/** 画布图（草稿与已发布共用同一结构）。 */
export interface Graph {
  /** 图结构版本，当前固定为 `"1"` */
  version: string
  nodes: GraphNode[]
  edges: GraphEdge[]
}

/** 节点类型别名（便于执行引擎引用）。 */
export type GraphNodeType = GraphNode['type']
```

**这段在干什么**

1. `type` 的**字面量联合**把 7 个类型变成编译期白名单：任何按类型 `switch` 的地方，漏了一个类型都会编译报错——这正是我们想要的提醒。
2. `sourceHandle?: string | null`：`?` 表示**可以省略**（`undefined`），`| null` 表示**可以显式为空**。两者在引擎里都按「默认出口」处理。
3. `GraphNodeType` 让 `node_started.nodeType` / `node_finished.nodeType` 直接复用同一联合，不会出现「事件里多写一个类型」。

**这段在干什么**

3. `id` 的注释再次强调「它同时是 `sourceHandle`」——这是读代码时最容易忽略的一条耦合。

### 6.4 `AggregatorNodeData` 与 `IterationNodeData`

```ts
/** `aggregator` 节点的 `data` 形状（见 openapi.yaml `AggregatorNodeData`）。 */
export interface AggregatorNodeData {
  title: string
  /** 每个 `name` 取 `values` 中「第一个能解析出非空值」的模板结果 */
  outputs: Array<{ name: string; values: string[] }>
}

/** `iteration` 节点的 `data` 形状（见 openapi.yaml `IterationNodeData`）。 */
export interface IterationNodeData {
  title: string
  /** 模板，解析后必须是 JSON 数组 */
  inputArray: string
  /** 默认 `"item"` */
  itemName?: string
  /** 1..100，默认 20 */
  maxIterations?: number
  /** 每项渲染一次 */
  outputTemplate: string
}
```

**这段在干什么**

1. `values: string[]`：聚合的候选项必须是**模板字符串**（要渲染后判空）。
2. `inputArray: string`（**不是** `unknown[]`）：契约把「数组的获取方式」固定为「模板 → `JSON.parse`」，而不是「前端传数组对象」。这样与变量池的取值方式统一（§19.2）。
3. `itemName` / `maxIterations` 可选，缺省值由契约 `default` 给出（`item` / `20`），**引擎里也会再兜一次**（§19.4）。

**这段在干什么**

```ts
/** `branch_taken`：`condition` 节点选中某个分支（每节点只发一次）。 */
export interface BranchTakenData {
  nodeId: string
  /** 选中的条件 `id`；全部不匹配时为 `"else"` */
  caseId: string
  /** 该条件的 `label`；`else` 分支亦为 `"else"` */
  label: string
}

/** `iteration_item`：`iteration` 节点开始处理某一项（`index` 从 1 开始）。 */
export interface IterationItemData {
  nodeId: string
  index: number
  total: number
}
```

**这段在干什么**

1. `BranchTakenData.caseId` 与 `edge.sourceHandle` **同一取值空间**：前端看到 `caseId: "good"`，就知道该点亮哪条出边——不需要再查一次节点配置。
2. `IterationItemData` 用 `index`（当前第几项，**1 起**）+ `total`（总数），前端可以直接算进度百分比。
3. 两个 payload 都**不带**条件表达式的内容：事件描述「发生了什么」，不重复「配置长什么样」。

```ts
  data:
    | RunStartedData
    | NodeStartedData
    | TokenData
    | ToolCallData
    | ToolResultData
    | RetrievalData
    | BranchTakenData
    | IterationItemData
    | NodeFinishedData
    | RunFinishedData
    | RunFailedData
}
```

**这段在干什么**

联合类型加两支后，前端 `switch (event)` 能拿到精确 payload；**加事件不改帧格式**（仍是 `event:` + `data:` 两行），已有解析器不用改。

## 7. 完整代码：SSE 事件协议（sse-events.md 的本篇段落）

**完整文件路径：`packages/contract/sse-events.md`**

### 7.1 §2 事件表新增两行

````markdown
| `branch_taken` | `condition` 节点选中某个分支（**每节点只发一次**） | `nodeId`(string)、`caseId`(string)、`label`(string) |
| `iteration_item` | `iteration` 节点开始处理某一项（**每项一次**，`index` 从 **1** 开始） | `nodeId`(string)、`index`(number)、`total`(number) |
````

**这段在干什么**

1. **「每节点只发一次」**：一个 `condition` 节点只选一次分支，所以只产生一个 `branch_taken`（不像 `token` 那样多个）。
2. **「每项一次」**：`iteration_item` 的条数 = 数组长度，`index` 从 1 开始——这对前端进度条是硬约定，0 起会让「第 0 项」出现。
3. `label` 单独给出来：`caseId` 是**机器标识**（也是 `sourceHandle`），`label` 是**给人看的**，两者不能混用。

### 7.2 §3 事件顺序补充

````markdown
run_started
  （对每个按拓扑序执行的节点，依次：）
    node_started
    （仅 llm 节点：若干 token）
    （仅启用了工具的 llm 节点：可多轮 tool_call / tool_result）
    （仅 knowledge 节点：一次 retrieval）
    （仅 condition 节点：一次 branch_taken）
    （仅 iteration 节点：每项一次 iteration_item）
    node_finished
run_finished
````

**这段在干什么**

1. 在既有顺序里**插入两行**：`branch_taken` 在 `node_started` 与 `node_finished` **之间**；`iteration_item` 同理，只是可出现多次。
2. 重点：**`condition` 节点自己也是「一个节点」，有开始有结束**——分支不是「跳过节点」，而是「节点选完再决定下游」。
3. `iteration` **不重复**发 `node_started` / `node_finished`：它在内部循环，对图执行器而言仍是一个节点（§19.5）。

### 7.3 §3 的两条关键补注

````markdown
- `condition` 节点只执行被选中分支的下游，其余分支不执行（其变量在池中不存在）。
- `iteration` 节点内部逐项循环，**不产生图循环**，也不重复发 `node_started` / `node_finished`。
````

**这段在干什么**

1. 第一句是「分支」的**后果**：没执行的节点不会写池，所以下游若直接引用对端分支的变量，会**取值失败**（严格模板抛 `template variable not found`）。这就是 `aggregator` 存在的理由（§18.3）。
2. 第二句是「迭代 ≠ 图循环」：`iteration` 不会让 LangGraph 的图产生环，因此**不需要**额外的 `recursionLimit` 预算，也不会触发「环」相关的状态收敛语义。

### 7.4 §4 三种节点的引擎语义

````markdown
- **`condition`**（阶段 8）：按 `data.conditions` **数组顺序**取**第一个**匹配的分支；
  全部不匹配走 `else`。事件顺序固定为 `node_started(condition)` → **一次** `branch_taken` →
  `node_finished(condition)`；输出为 `{ "matched": string }`（选中的 `caseId`，或 `"else"`）。
  - `variable` / `value` 都按「分支安全」规则解析（见 §4.1）。运算符语义（两端一致）：
    `equals`/`not_equals` 为字符串全等；`contains`/`not_contains`、`starts_with`/`ends_with`
    为字符串包含/前后缀；`is_empty`/`is_not_empty` 判断字符串是否为 `""`；
    `gt`/`gte`/`lt`/`lte` 先转数字再比较（任一侧不是有限数字时为 `false`）。
  - 出边的 `sourceHandle` 即分支 `caseId`；`else` 分支的出边 `sourceHandle` 固定为 `"else"`。
    每个分支恰好一条出边（预检保证），引擎按 `sourceHandle` 分派下游，其余分支不执行。
- **`aggregator`**（阶段 8）：无新增事件，顺序仍为 `node_started` → `node_finished`。
  对 `data.outputs` 每个 `name`，按 `values` 顺序用分支安全解析（§4.1）取**第一个非空串**；
  全部为空时取 `""`。输出为**扁平对象** `{ "<name>": "<值>", ... }`。
- **`iteration`**（阶段 8）：`node_started(iteration)` → `iteration_item` ×N → `node_finished`。
  `data.inputArray` 用分支安全解析（§4.1）后 `JSON.parse`，**必须是 JSON 数组**；长度超过
  `maxIterations`（默认 20，范围 1..100）即失败（见 `error-messages.md` §8）。
  逐项（`index` 从 1 开始）先发 `iteration_item`，再以
  `{ ...pool, <itemName>: <item 字符串化>, itemIndex: index, itemCount: total }` 渲染
  `outputTemplate`（`itemName` 默认 `"item"`）。`<item 字符串化>` 规则：**字符串原样**，
  其余按紧凑 `JSON.stringify`（两端一致）。输出为
  `{ "results": string[], "count": number, "joined": string }`，`joined = results.join("\n")`。
````

**这段在干什么（按节点）**

1. **`condition` 的输出是 `{ matched }`**：把「选了哪条」写进变量池，下游可用 `{{ c1.matched }}` 拿到分支名（例如拼日志或再分支）。这也是引擎写入 `branches[nodeId]` 状态、供条件边路由的依据。
2. **「每个分支恰好一条出边（预检保证）」**：这句话把「运行期不出错」的责任**显式转移给了预检**——引擎里 `branchTargets` 只做 `find`，不处理「找不到目标」的情况（§21）。
3. **`aggregator` 的「全空时为 `""`」**：不报错、不返回 `null`。下游 `end` 拿到的是空字符串，页面显示空白——这是**语义选择**：聚合是「尽力而为」，不是「必有值」。
4. **`iteration` 的「`<item 字符串化>`」**：字符串原样，其余紧凑 JSON。这条规则决定了下游只能 `{{ item }}`，**不能** `{{ item.field }}`（§24）。
5. **`joined = results.join("\n")`**：换行符在契约里写死，两端逐字节一致；下游 `{{ iter1.joined }}` 直接可用。

### 7.5 §4.1 分支安全的变量解析（本篇最容易被忽略的一段）

````markdown
### 4.1 分支安全的变量解析

`condition` 与 `aggregator` 解析模板时，模板里的**路径不存在一律视为空串**（不抛错）——
因为分支未执行时，对端分支的变量本就不存在。这是安全解析（`tryRenderTemplate`）的唯一适用范围：

- 只影响 `condition.conditions[].variable` / `value`，以及 `aggregator.outputs[].values[]`；
- 逐段检查路径、**模板内的路径缺失只替换为空串**，模板其余文本原样保留；
- 非字符串值仍按紧凑 JSON 字符串化（与普通模板一致）；
- 其余节点（`llm` / `knowledge` / `end` / `iteration.outputTemplate`）维持「缺失即
  `RunError('template variable not found: {path}')`」。

`iteration.inputArray` 也使用安全解析（以便复用「不存在即空串」的行为），但其解析结果
必须是 JSON 数组，否则仍按 §8 报错。
````

**这段在干什么**

1. **这是「安全解析」的唯一适用范围**：三个位置——`condition.variable` / `condition.value`、`aggregator.values[]`、`iteration.inputArray`。
2. 「路径缺失 → 空串」不是「宽容」，而是**分支图的必然要求**：`good` 分支没执行时，`llm_good` 这个键**根本不在池里**；若用严格解析，聚合器必然抛错。
3. **其余节点仍严格**：`end` 直接写 `{{ llm_good.text }}` 在 else 分支下会 `run_failed`。严格与安全的**边界**就是「这个位置是否可能引用未执行分支」。
4. 「模板其余文本原样保留」：`"前缀-{{ missing }}-后缀"` 渲染成 `"前缀--后缀"`，不是整段消失。
5. `iteration.inputArray` 用安全解析是为了**复用同一条代码路径**；但它是否合法还要过「`JSON.parse` 后必须是数组」这一关。

## 9. 完整代码：TS 图语义校验（graph.validator.ts）

**完整文件路径：`apps/api-ts/src/graph/graph.validator.ts`**

```ts
import type { ConditionOperator, Graph } from '@mini-dify/contract'

/**
 * 图**语义**校验（纯函数）。
 *
 * 与 api-py 的 `app/graph/validator.py::validate_graph` 逐条对齐：
 * 规则顺序、同规则内的遍历顺序、文案模板完全一致，见
 * `packages/contract/error-messages.md` §3。
 *
 * 返回错误文案数组（可能为空）；调用方用 `"; "` 连接成一个 `message`。
 * 注意：本函数**不含**「读取草稿」时的豁免 —— 草稿为 null 时读取返回合法空图，
 * 不走本校验；只有 `PUT` / `publish` 才调用本函数（空图会因规则 3/4 不通过）。
 */
export function validateGraph(graph: Graph): string[] {
  const errors: string[] = []

  // 规则 1：version 必须为 "1"
  if (graph.version !== '1') {
    errors.push('graph version must be 1')
  }

  // 规则 2：节点 id 必须唯一（按数组顺序，每个重复 id 只报一次）
  const seenNodeIds = new Set<string>()
  const reportedNodeIds = new Set<string>()
  for (const node of graph.nodes) {
    if (seenNodeIds.has(node.id) && !reportedNodeIds.has(node.id)) {
      errors.push(`node id must be unique: ${node.id}`)
      reportedNodeIds.add(node.id)
    }
    seenNodeIds.add(node.id)
  }

  // 规则 3：恰好一个 start 节点（0 个或 ≥2 个都报此条）
  if (graph.nodes.filter((node) => node.type === 'start').length !== 1) {
    errors.push('graph must contain exactly one start node')
  }

  // 规则 4：至少一个 end 节点
  if (graph.nodes.filter((node) => node.type === 'end').length === 0) {
    errors.push('graph must contain at least one end node')
  }

  // 规则 5：边 id 必须唯一（按数组顺序，每个重复 id 只报一次）
  const seenEdgeIds = new Set<string>()
  const reportedEdgeIds = new Set<string>()
  for (const edge of graph.edges) {
    if (seenEdgeIds.has(edge.id) && !reportedEdgeIds.has(edge.id)) {
      errors.push(`edge id must be unique: ${edge.id}`)
      reportedEdgeIds.add(edge.id)
    }
    seenEdgeIds.add(edge.id)
  }

  // 规则 6：边的 source/target 必须指向存在的节点（先 source 后 target）
  const nodeIds = new Set(graph.nodes.map((node) => node.id))
  for (const edge of graph.edges) {
    if (!nodeIds.has(edge.source)) {
      errors.push(`edge ${edge.id} references unknown node: ${edge.source}`)
    }
    if (!nodeIds.has(edge.target)) {
      errors.push(`edge ${edge.id} references unknown node: ${edge.target}`)
    }
  }

  // 规则 7：不允许自环（source === target）
  for (const edge of graph.edges) {
    if (edge.source === edge.target) {
      errors.push(`edge ${edge.id} must not connect a node to itself`)
    }
  }

  // 规则 8：condition 节点（分支标识 / 运算符 / 出边 sourceHandle）
  for (const node of graph.nodes) {
    if (node.type === 'condition') {
      errors.push(...validateConditionNode(node, graph.edges))
    }
  }

  // 规则 9：aggregator 节点（outputs 与各自 values 非空）
  for (const node of graph.nodes) {
    if (node.type !== 'aggregator') {
      continue
    }
    const data = (node.data ?? {}) as Record<string, unknown>
    const outputs = data.outputs
    // 「不是数组」由 validateNodeData 负责（避免同一条文案重复出现）
    if (Array.isArray(outputs) && outputs.length === 0) {
      errors.push(`aggregator node ${node.id} must have at least one output`)
      continue
    }
    if (!Array.isArray(outputs)) {
      continue
    }
    for (const item of outputs) {
      const output = isPlainObject(item) ? item : {}
      const name = typeof output.name === 'string' ? output.name : String(output.name)
      const values = output.values
      if (Array.isArray(values) && values.length === 0) {
        errors.push(`aggregator node ${node.id} output ${name} must have at least one value`)
      }
    }
  }

  // 规则 10：iteration 节点（inputArray / maxIterations）
  for (const node of graph.nodes) {
    if (node.type !== 'iteration') {
      continue
    }
    const data = (node.data ?? {}) as Record<string, unknown>
    if (typeof data.inputArray === 'string' && data.inputArray.trim() === '') {
      errors.push(`iteration node ${node.id} inputArray is required`)
    }
    const maxIterations = data.maxIterations
    if (
      typeof maxIterations === 'number' &&
      !(Number.isInteger(maxIterations) && maxIterations >= 1 && maxIterations <= 100)
    ) {
      errors.push(`iteration node ${node.id} maxIterations must be between 1 and 100`)
    }
  }

  return errors
}

/** `condition` 节点支持的运算符（与契约 `ConditionOperator` 一致）。 */
const CONDITION_OPERATORS = new Set<ConditionOperator>([
  'equals',
  'not_equals',
  'contains',
  'not_contains',
  'starts_with',
  'ends_with',
  'is_empty',
  'is_not_empty',
  'gt',
  'gte',
  'lt',
  'lte',
])

/**
 * 规则 8 的细节（见 error-messages.md §8.1）：按 8.1.1 → 8.1.8 的顺序收集文案。
 * 8.1.1 命中后跳过该节点其余规则。
 */
function validateConditionNode(
  node: Graph['nodes'][number],
  edges: Graph['edges'],
): string[] {
  const errors: string[] = []
  const data = (node.data ?? {}) as Record<string, unknown>
  const conditions = data.conditions
  // 「不是数组」由 validateNodeData 负责（避免同一条文案重复出现）
  if (!Array.isArray(conditions)) {
    return []
  }
  if (conditions.length === 0) {
    return [`condition node ${node.id} must have at least one condition`]
  }

  const cases = conditions.map((item) => (isPlainObject(item) ? item : {}))
  const caseIds = cases.map((item) =>
    typeof item.id === 'string' ? item.id : String(item.id),
  )

  // 8.1.2：条件 id 重复（每个重复 id 只报一次）
  // 另：`else` 是保留分支名（条件边 mapping 的 key），不能作为 case id，否则会静默错路由
  const seenCaseIds = new Set<string>()
  const reportedCaseIds = new Set<string>()
  const reportedReserved = new Set<string>()
  for (const caseId of caseIds) {
    if (caseId === 'else' && !reportedReserved.has(caseId)) {
      errors.push(`condition node ${node.id} case id "else" is reserved`)
      reportedReserved.add(caseId)
    }
    if (seenCaseIds.has(caseId) && !reportedCaseIds.has(caseId)) {
      errors.push(`condition node ${node.id} has duplicate case id: ${caseId}`)
      reportedCaseIds.add(caseId)
    }
    seenCaseIds.add(caseId)
  }

  // 8.1.3 / 8.1.4：按 conditions 数组顺序逐条检查
  cases.forEach((item, index) => {
    const operator = item.operator
    if (typeof operator !== 'string' || !CONDITION_OPERATORS.has(operator as ConditionOperator)) {
      errors.push(`condition node ${node.id} has invalid operator: ${String(operator)}`)
    }
    if (typeof item.variable !== 'string' || item.variable.trim() === '') {
      errors.push(`condition node ${node.id} case ${caseIds[index]} variable is required`)
    }
  })

  const outgoing = edges.filter((edge) => edge.source === node.id)

  // 8.1.5：每个 caseId 必须有一条出边
  for (const caseId of caseIds) {
    if (!outgoing.some((edge) => edge.sourceHandle === caseId)) {
      errors.push(`condition node ${node.id} case ${caseId} has no outgoing edge`)
    }
  }

  // 8.1.6：else 分支必须有一条出边
  if (!outgoing.some((edge) => edge.sourceHandle === 'else')) {
    errors.push(`condition node ${node.id} else branch has no outgoing edge`)
  }

  // 8.1.7：出边的 sourceHandle 必须是某个 caseId 或 "else"（缺失写作 null）
  const validHandles = new Set<string>([...caseIds, 'else'])
  for (const edge of outgoing) {
    const handle = edge.sourceHandle
    if (typeof handle !== 'string' || !validHandles.has(handle)) {
      const shown = handle === null || handle === undefined ? 'null' : String(handle)
      errors.push(
        `edge ${edge.id} from condition node ${node.id} has invalid sourceHandle: ${shown}`,
      )
    }
  }

  // 8.1.8：同一分支多条边（分支按 conditions 顺序，else 最后）
  const edgeCounts = new Map<string, number>()
  for (const edge of outgoing) {
    const handle = edge.sourceHandle
    if (typeof handle === 'string' && validHandles.has(handle)) {
      edgeCounts.set(handle, (edgeCounts.get(handle) ?? 0) + 1)
    }
  }
  for (const caseId of new Set(caseIds)) {
    if ((edgeCounts.get(caseId) ?? 0) > 1) {
      errors.push(`condition node ${node.id} has duplicate edge for case ${caseId}`)
    }
  }
  if ((edgeCounts.get('else') ?? 0) > 1) {
    errors.push(`condition node ${node.id} has duplicate edge for case else`)
  }

  return errors
}

/** 是否为「普通对象」（数组与 null 不算）。 */
function isPlainObject(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value)
}
```

**这段在干什么（按执行顺序）**

1. **规则 1~7 是阶段 3 的既有规则**（`version`、节点 id 唯一、恰好一个 `start`、至少一个 `end`、边 id 唯一、端点存在、禁止自环），本篇原样保留。
2. **规则 8 遍历 `graph.nodes`，只对 `condition` 调用 `validateConditionNode`**：一个节点一次，天然按 `nodes` 数组顺序。
3. **`validateConditionNode` 的第一件事是「`conditions` 不是数组就返回 `[]`」**：把这个错误**让给引擎的 `validateNodeData`**，避免同一句话被两个函数各报一次（`msg; msg`）。
4. **`conditions` 是空数组 → 直接 `return` 一条**：短路，后面的 8.1.2a~8.1.8 全部不跑（契约明确要求）。
5. **`cases` 先做「非对象 → `{}`」归一**，再取 `caseIds`；**非字符串 id 用 `String(id)`**（缺失即 `"undefined"`），因为错误文案里要「像 JS 那样」显示它。
6. **8.1.2 用三个 `Set`**（`seenCaseIds` / `reportedCaseIds` / `reportedReserved`）：同一循环里**先查保留名 `else`（8.1.2a）、再查重复 id（8.1.2）**，各只报一次——与规则 2/5 同一套写法。
7. **8.1.3 / 8.1.4 在同一个 `forEach` 里按 `conditions` 顺序逐条查**：所以同一个 case 的「operator 非法」总是排在「variable 为空」前面。
8. **8.1.5 用 `outgoing.some(edge.sourceHandle === caseId)`**：只看出边的句柄，**不看 `target` 类型**（可以指向 `end`，甚至与前一条边同目标）。
9. **8.1.6 单独查 `'else'`**：`else` 不是 `conditions` 里的成员，必须额外确认。
10. **8.1.7 把「所有以该节点为 source 的边」都过一遍**：`null` / `undefined` / 任意其它字符串都非法；缺失归一成 `"null"`。
11. **8.1.8 先统计**每个合法句柄的边数，再按 `new Set(caseIds)`（**去重后的条件顺序**）报重复，最后单独报 `else`。用 `Set` 是为了「`conditions` 里同名 id 已由 8.1.2 报过，这里不重复刷」。
12. **规则 9 / 10 只做「空数组 / 空串 / 数值越界」**：所有「类型不对」都 `continue` 让给 `validateNodeData`。这就是**互斥命中**的实现方式（§20）。

## 10. 完整代码：Python 图语义校验（validator.py）

**完整文件路径：`apps/api-py/app/graph/validator.py`**

```python
"""图**语义**校验（纯函数）。

与 api-ts 的 `apps/api-ts/src/graph/graph.validator.ts::validateGraph` 逐条对齐：
规则顺序、同规则内的遍历顺序、文案模板完全一致，见
`packages/contract/error-messages.md` §3。

入参是普通 dict（来自请求体 `model_dump()` 或数据库 JSONB 读出的草稿），
返回错误文案列表（可能为空）；调用方用 `"; "` 连接成一个 `message`。
注意：本函数**不含**「读取草稿」时的豁免 —— 草稿为 NULL 时读取返回合法空图，
不走本校验；只有 `PUT` / `publish` 才调用本函数（空图会因规则 3/4 不通过）。
"""

from typing import Any


def validate_graph(graph: dict[str, Any]) -> list[str]:
    errors: list[str] = []
    nodes: list[dict[str, Any]] = graph.get("nodes") or []
    edges: list[dict[str, Any]] = graph.get("edges") or []

    # 规则 1：version 必须为 "1"
    if graph.get("version") != "1":
        errors.append("graph version must be 1")

    # 规则 2：节点 id 必须唯一（按数组顺序，每个重复 id 只报一次）
    seen_node_ids: set[str] = set()
    reported_node_ids: set[str] = set()
    for node in nodes:
        node_id = node.get("id")
        if node_id in seen_node_ids and node_id not in reported_node_ids:
            errors.append(f"node id must be unique: {node_id}")
            reported_node_ids.add(node_id)
        seen_node_ids.add(node_id)

    # 规则 3：恰好一个 start 节点（0 个或 ≥2 个都报此条）
    if sum(1 for node in nodes if node.get("type") == "start") != 1:
        errors.append("graph must contain exactly one start node")

    # 规则 4：至少一个 end 节点
    if sum(1 for node in nodes if node.get("type") == "end") == 0:
        errors.append("graph must contain at least one end node")

    # 规则 5：边 id 必须唯一（按数组顺序，每个重复 id 只报一次）
    seen_edge_ids: set[str] = set()
    reported_edge_ids: set[str] = set()
    for edge in edges:
        edge_id = edge.get("id")
        if edge_id in seen_edge_ids and edge_id not in reported_edge_ids:
            errors.append(f"edge id must be unique: {edge_id}")
            reported_edge_ids.add(edge_id)
        seen_edge_ids.add(edge_id)

    # 规则 6：边的 source/target 必须指向存在的节点（先 source 后 target）
    node_ids = {node.get("id") for node in nodes}
    for edge in edges:
        if edge.get("source") not in node_ids:
            errors.append(f"edge {edge.get('id')} references unknown node: {edge.get('source')}")
        if edge.get("target") not in node_ids:
            errors.append(f"edge {edge.get('id')} references unknown node: {edge.get('target')}")

    # 规则 7：不允许自环（source == target）
    for edge in edges:
        if edge.get("source") == edge.get("target"):
            errors.append(f"edge {edge.get('id')} must not connect a node to itself")

    # 规则 8：condition 节点（分支标识 / 运算符 / 出边 sourceHandle）
    for node in nodes:
        if node.get("type") == "condition":
            errors.extend(_validate_condition_node(node, edges))

    # 规则 9：aggregator 节点（outputs 与各自 values 非空）
    for node in nodes:
        if node.get("type") != "aggregator":
            continue
        data = _data_of(node)
        outputs = data.get("outputs")
        # 「不是数组」由 validate_node_data 负责（避免同一条文案重复出现）
        if isinstance(outputs, list):
            if len(outputs) == 0:
                errors.append(f"aggregator node {node.get('id')} must have at least one output")
                continue
        else:
            continue
        for item in outputs:
            output = item if isinstance(item, dict) else {}
            name = _js_string(output.get("name", _UNSET))
            values = output.get("values")
            if isinstance(values, list) and len(values) == 0:
                errors.append(
                    f"aggregator node {node.get('id')} output {name} must have at least one value"
                )

    # 规则 10：iteration 节点（inputArray / maxIterations）
    for node in nodes:
        if node.get("type") != "iteration":
            continue
        data = _data_of(node)
        input_array = data.get("inputArray")
        if isinstance(input_array, str) and input_array.strip() == "":
            errors.append(f"iteration node {node.get('id')} inputArray is required")
        max_iterations = data.get("maxIterations", _UNSET)
        if _is_number(max_iterations) and not (
            float(max_iterations).is_integer() and 1 <= max_iterations <= 100
        ):
            errors.append(
                f"iteration node {node.get('id')} maxIterations must be between 1 and 100"
            )

    return errors


# `condition` 节点支持的运算符（与契约 `ConditionOperator` 一致）
_CONDITION_OPERATORS = frozenset(
    {
        "equals",
        "not_equals",
        "contains",
        "not_contains",
        "starts_with",
        "ends_with",
        "is_empty",
        "is_not_empty",
        "gt",
        "gte",
        "lt",
        "lte",
    }
)

# 区分「键缺失」（JS `undefined`）与「显式 null」
_UNSET = object()


def _data_of(node: dict[str, Any]) -> dict[str, Any]:
    data = node.get("data")
    return data if isinstance(data, dict) else {}


def _js_string(value: Any) -> str:
    """错误文案里的取值：对齐 JS `String(value)` 的常见标量表现。"""
    if value is _UNSET:
        return "undefined"
    if value is None:
        return "null"
    if value is True:
        return "true"
    if value is False:
        return "false"
    return str(value)


def _is_number(value: Any) -> bool:
    return isinstance(value, (int, float)) and not isinstance(value, bool)


def _validate_condition_node(node: dict[str, Any], edges: list[dict[str, Any]]) -> list[str]:
    """规则 8 的细节（见 error-messages.md §8.1）：按 8.1.1 → 8.1.8 的顺序收集文案。

    8.1.1 命中后跳过该节点其余规则。
    """
    errors: list[str] = []
    node_id = node.get("id")
    data = _data_of(node)
    conditions = data.get("conditions")
    # 「不是数组」由 validate_node_data 负责（避免同一条文案重复出现）
    if not isinstance(conditions, list):
        return []
    if len(conditions) == 0:
        return [f"condition node {node_id} must have at least one condition"]

    cases = [item if isinstance(item, dict) else {} for item in conditions]
    case_ids = [_js_string(item.get("id", _UNSET)) for item in cases]

    # 8.1.2：条件 id 重复（每个重复 id 只报一次）
    seen_case_ids: set[str] = set()
    reported_case_ids: set[str] = set()
    reported_reserved: set[str] = set()
    for case_id in case_ids:
        # `else` 是保留分支名（条件边 mapping 的 key），不能作为 case id，否则会静默错路由
        if case_id == "else" and case_id not in reported_reserved:
            errors.append(f'condition node {node_id} case id "else" is reserved')
            reported_reserved.add(case_id)
        if case_id in seen_case_ids and case_id not in reported_case_ids:
            errors.append(f"condition node {node_id} has duplicate case id: {case_id}")
            reported_case_ids.add(case_id)
        seen_case_ids.add(case_id)

    # 8.1.3 / 8.1.4：按 conditions 数组顺序逐条检查
    for index, item in enumerate(cases):
        operator = item.get("operator", _UNSET)
        if not isinstance(operator, str) or operator not in _CONDITION_OPERATORS:
            errors.append(f"condition node {node_id} has invalid operator: {_js_string(operator)}")
        variable = item.get("variable", _UNSET)
        if not isinstance(variable, str) or variable.strip() == "":
            errors.append(
                f"condition node {node_id} case {case_ids[index]} variable is required"
            )

    outgoing = [edge for edge in edges if edge.get("source") == node_id]

    # 8.1.5：每个 caseId 必须有一条出边
    for case_id in case_ids:
        if not any(edge.get("sourceHandle") == case_id for edge in outgoing):
            errors.append(f"condition node {node_id} case {case_id} has no outgoing edge")

    # 8.1.6：else 分支必须有一条出边
    if not any(edge.get("sourceHandle") == "else" for edge in outgoing):
        errors.append(f"condition node {node_id} else branch has no outgoing edge")

    # 8.1.7：出边的 sourceHandle 必须是某个 caseId 或 "else"（缺失写作 null）
    valid_handles = {*case_ids, "else"}
    for edge in outgoing:
        handle = edge.get("sourceHandle", _UNSET)
        if not isinstance(handle, str) or handle not in valid_handles:
            shown = "null" if handle is None or handle is _UNSET else str(handle)
            errors.append(
                f"edge {edge.get('id')} from condition node {node_id} has invalid sourceHandle: {shown}"
            )

    # 8.1.8：同一分支多条边（分支按 conditions 顺序，else 最后）
    edge_counts: dict[str, int] = {}
    for edge in outgoing:
        handle = edge.get("sourceHandle")
        if isinstance(handle, str) and handle in valid_handles:
            edge_counts[handle] = edge_counts.get(handle, 0) + 1
    for case_id in dict.fromkeys(case_ids):
        if edge_counts.get(case_id, 0) > 1:
            errors.append(f"condition node {node_id} has duplicate edge for case {case_id}")
    if edge_counts.get("else", 0) > 1:
        errors.append(f"condition node {node_id} has duplicate edge for case else")

    return errors
```

**这段在干什么（与 TS 逐条对照）**

| 关注点 | TS | Python | 为什么必须同一写法 |
| --- | --- | --- | --- |
| 遍历顺序 | `graph.nodes` 数组序 | `nodes` 数组序 | 多条错误拼成一句话，顺序不同就逐字节不同 |
| 重复 id 只报一次 | `Set` + `reported` | `set` + `reported` | 同上 |
| 保留名预检（8.1.2a） | `reportedReserved`，先查 `caseId === 'else'` | `reported_reserved`，先查 `case_id == "else"` | 必须与重复 id 检查同循环、同顺序，文案位置才会一致 |
| `conditions` 非数组 | `return []` | `return []` | 交给引擎字段校验，避免重复文案 |
| 空数组 | 一条并 `return` | 一条并 `return` | 8.1.1 短路 |
| 缺失 id 的显示 | `String(undefined)` → `"undefined"` | `_js_string(_UNSET)` → `"undefined"` | 文案里可能出现 `case undefined` |
| `sourceHandle` 缺失 | `null` / `undefined` → `"null"` | `_UNSET` / `None` → `"null"` | 契约规定写作 `null` |
| 数值判定 | `typeof === 'number'` + `Number.isInteger` | `_is_number`（排除 `bool`）+ `float(x).is_integer()` | Python 里 `True` 是 `int`，不排除会把布尔当数字 |
| 去重报名 | `new Set(caseIds)` | `dict.fromkeys(case_ids)` | 3.7+ 有序去重；顺序影响文案顺序 |

**关键差异点：`_UNSET` 这个哨兵**

Python 的 `dict.get("id")` 无法区分「键不存在」与「键存在但值是 `None`」。错误文案里前者要写 `undefined`（对齐 JS），后者要写 `null`，所以用一个模块级唯一的 `object()` 作默认值——`value is _UNSET` 才表示「缺键」。

```ts
import { Type } from 'class-transformer'
import { IsArray, IsDefined, IsIn, IsNumber, IsObject, IsOptional, IsString, ValidateNested } from 'class-validator'

const NODE_TYPES = ['start', 'end', 'llm', 'knowledge', 'condition', 'aggregator', 'iteration'] as const

/** 对应契约 `NodePosition`。 */
class NodePositionDto {
  @IsNumber()
  x!: number

  @IsNumber()
  y!: number
}

/** 对应契约 `GraphNode`。`data` 为节点各自的配置（自由结构，不做内部约束）。 */
class GraphNodeDto {
  @IsString()
  id!: string

  @IsIn(NODE_TYPES)
  type!: (typeof NODE_TYPES)[number]

  @IsDefined()
  @ValidateNested()
  @Type(() => NodePositionDto)
  position!: NodePositionDto

  @IsObject()
  data!: Record<string, unknown>
}

/** 对应契约 `GraphEdge`（`sourceHandle` / `targetHandle` 可选，可为 null）。 */
class GraphEdgeDto {
  @IsString()
  id!: string

  @IsString()
  source!: string

  @IsString()
  target!: string

  @IsOptional()
  @IsString()
  sourceHandle?: string | null

  @IsOptional()
  @IsString()
  targetHandle?: string | null
}

/** PUT /apps/{id}/graph 的请求体 —— 对应契约 `Graph`。 */
export class GraphDto {
  @IsString()
  version!: string

  @IsArray()
  @ValidateNested({ each: true })
  @Type(() => GraphNodeDto)
  nodes!: GraphNodeDto[]

  @IsArray()
  @ValidateNested({ each: true })
  @Type(() => GraphEdgeDto)
  edges!: GraphEdgeDto[]
}
```

**这段在干什么（按装饰器）**

1. **`NODE_TYPES` 扩到 7 个**：`@IsIn(NODE_TYPES)` 是**运行期**白名单（TS 类型在运行期被擦除），漏加一个类型就会在 `PUT` 时被 400 拦下。
2. **`@IsOptional()` + `@IsString()`**：`@IsOptional()` 会跳过 `null` 与 `undefined` 的后续校验，所以 `sourceHandle: null` 能通过——这是「普通节点没有端口」能正常保存的前提。
3. **`data` 只做 `@IsObject()`**：内部结构**完全不在 DTO 层校验**。分支/聚合/迭代的形状由 `validateGraph`（语义）和 `validateNodeData`（类型）负责——DTO 层管「是不是对象」，别的一概不管。
4. **`@ValidateNested({ each: true })` + `@Type(...)`**：让 `nodes` / `edges` 里的每一项真正按 DTO 类校验（阶段 3 已讲）。
5. **`version` 只查 `@IsString()`**：`"1"` 这个值由语义校验规则 1 检查——DTO 管类型，语义管值。

## 13. 【技术教学 · 首次】为什么工作流需要分支

### 13.1 「让模型自己判断」不是分支

初学者最常问：**为什么不在 prompt 里写「如果是差评就道歉，否则就感谢」？**

| 维度 | 让模型在 prompt 里判断 | **图里的 `condition` 节点** |
| --- | --- | --- |
| 确定性 | 同一输入可能给出不同走法（采样、模型版本） | 同一输入**必然**走同一条边 |
| 可审计 | 只能从生成文本里猜它「想了什么」 | `branch_taken` 事件明确记录「走了哪条、为什么」 |
| 成本 | 每次都要过一遍模型 | 纯字符串比较，0 token |
| 可测试 | 要构造大量语义样本 | 直接断言 `matched === "good"` |
| 可编排 | 分支里的模型/工具/知识库无法分开配置 | 每条分支可以是**不同的**节点链（不同模型、不同知识库） |

> **一句话**：LLM 负责「不确定的、需要理解的部分」；**控制流负责「确定的、可枚举的部分」**。把两者混在一起，会得到一个既不可测、也不可审计的系统。

### 13.2 分支带来的三个新问题

一旦图允许「只走一条路」，就立即出现三个必须回答的问题：

| 问题 | 阶段 8 的答案 |
| --- | --- |
| **「多条出边」怎么在图里表达？** | `edge.sourceHandle`（§15） |
| **多条分支汇合后，下游引用哪个变量？** | `aggregator`（§18） |
| **「走错边 / 没边可走」怎么在运行前发现？** | 8 类分支预检（§21） |

## 14. 【技术教学 · 首次】`condition` 节点三要素

### 14.1 第一要素：`conditions[]` 是**有序**数组

```json
"conditions": [
  { "id": "good", "label": "好评", "variable": "{{ inputs.topic }}", "operator": "contains", "value": "好" },
  { "id": "bad",  "label": "差评", "variable": "{{ inputs.topic }}", "operator": "contains", "value": "差" }
]
```

- **数组，不是对象/映射**：因为顺序有意义（§16）。
- **每一项是「条件表达式」**：`(变量, 运算符, 值)` 三元组。
- **`id` 不是展示名**：它是**分支标识**，必须与出边的 `sourceHandle` **逐字符相等**（大小写敏感）。`label` 才是给人看的。

### 14.2 第二要素：`operator`（12 个，闭集）

闭集的好处：前端下拉框、两端校验白名单、两端实现 `switch`，**三处同源**。加第 13 个运算符是一次契约变更（要升版本、改三处、补测试）。

### 14.3 第三要素：`else` 兜底

`else` **不在 `conditions` 数组里**——它不是「条件」，而是「所有条件都不成立时的那条路」。它只以两种形式存在：

1. 出边的 `sourceHandle: "else"`；
2. `branch_taken` 事件里的 `caseId: "else"` / `label: "else"`。

为什么它必须是**强制**的，见 §16.3。

### 14.4 一次条件判定的完整生命周期

```
① 预检（保存 / 运行前）
    conditions 非空、id 不重复、operator 合法、variable 非空、
    每个 id 有且仅有一条出边、else 有且仅有一条出边、没有非法 sourceHandle

② 执行（运行期）
    node_started(condition)
    按数组顺序对每个 condition：
        left  = tryRenderTemplate(variable)   ← 缺失 → ""
        right = tryRenderTemplate(value ?? "")← 缺失 → ""
        applyOperator(operator, left, right) ?
            命中 → branch_taken(caseId, label)；matched = caseId；break
    全部不命中 → branch_taken("else", "else")；matched = "else"
    node_finished(condition)  output = { "matched": ... }

③ 路由（LangGraph 条件边）
    读 matched → 查预检保证存在的 branchTargets[matched] → 只调度那一条下游
```

> 注意 ② 与 ③ 的**分工**：节点本身只「选分支」，不「跳节点」；真正的跳转由 LangGraph 的条件边完成（阶段 6 已讲 `addConditionalEdges`）。

## 15. 【技术教学 · 首次】`sourceHandle`：图模型里的「多出口」

### 15.1 一条边到底是什么

在 ReactFlow 的模型里，一条边由两个**端口**连接：

```
(source 节点, sourceHandle)  ─────▶  (target 节点, targetHandle)
        ↑ 出口端口                            ↑ 入口端口
```

本项目里：

| 字段 | 谁在用 | 语义 |
| --- | --- | --- |
| `source` | 引擎 | 起点节点 id |
| `target` | 引擎 | 终点节点 id |
| `sourceHandle` | **引擎（分支时）** + 画布 | `null` / 省略 = 默认出口；`caseId` = 该分支专用出口；`"else"` = 兜底出口 |
| `targetHandle` | **只有画布** | 目标节点的入口（引擎忽略） |

> 所以「一条边」在本项目中是 **`(source, sourceHandle, target)` 三元组**。`id` 只是给画布和错误文案用的标识。

### 15.2 为什么用「边上的端口」而不是「节点上的 exits 数组」

给节点加 `exits: [{ name, target }]` 也能表达多出口。但会立刻遇到三个问题：

| 方案 | 问题 |
| --- | --- |
| 节点内嵌 `exits[]` | 图变成**两种边**（普通 `edges[]` + 内嵌 `exits[]`），校验、保存、画布都要写两套；删除目标节点时内嵌引用会成为**悬挂指针**（而 `edges[]` 能统一做「端点存在」检查——规则 6） |
| **端口编码进边（本项目）** | 图仍是 **`nodes[] + edges[]` 两个数组**；「端点存在 / 自环 / 重复」等规则 1~7 **原样复用**；分支只多一条「句柄必须合法」的规则 8.1.7 |

这正是图论里的取舍：**「多出口」不必升级成超图（hypergraph）**，把「走哪个口」编码在边的端点上即可——边仍然是 `(u, v)`，只是 `u` 带了一个标签。

### 15.3 前端与后端用的是同一个句柄

画布上给 `condition` 节点画的每个分支把手（ReactFlow 的 `Handle`）有一个 `id`，就是 `caseId`；连线时 ReactFlow 会把该 `id` 写进 `edge.sourceHandle`。因此：

```
画布上的「好评」把手 id="good"  →  edge.sourceHandle = "good"  →  branchTargets["good"] = llm_good
```

三者一旦有一处写错（比如把手 id 是 `good-1`），就会得到 **8.1.7 `invalid sourceHandle`** 或 **8.1.5 `has no outgoing edge`**。这是阶段 8 最常见的画布 bug。

### 15.4 引擎怎么用这些句柄

**完整文件路径：`apps/api-ts/src/engine/engine.service.ts`**（节选：条件边的建图与路由表）

```ts
      for (const edge of graph.edges) {
        // 启用了工具的 llm 节点改由条件边分派，跳过其普通出边（否则两者冲突）
        if (toolNodes.some((node) => node.id === edge.source)) {
          continue
        }
        // condition 节点的出边按 sourceHandle 分派，同样跳过普通边
        if (conditionNodes.some((node) => node.id === edge.source)) {
          continue
        }
        builder.addEdge(edge.source, edge.target)
      }
      // ……
      for (const node of conditionNodes) {
        // 路由读节点写回的 `branches[nodeId]`，mapping 由 precheck 保证每个分支都有目标
        builder.addConditionalEdges(
          node.id,
          (state: RunStateValue) => state.branches[node.id] ?? 'else',
          branchTargets(graph, node),
        )
      }
```

**这段在干什么（建图部分）**

1. 普通边逐条 `addEdge`，但**两类节点被跳过**：启用了工具的 `llm`（阶段 6）与本篇的 `condition`。
2. `condition` 的每条出边都**不在**普通边集合里——它们只以 `branchTargets(...)` 的形式进入条件边的 `mapping`。
3. 跳过必须彻底：如果漏跳，同一条边既做普通边又做条件边，下游会被**无条件**触发，分支形同虚设。

```ts
/** 条件边的路由表：`caseId -> target`，外加 `else -> target`（预检保证每条都存在）。 */
function branchTargets(graph: Graph, node: GraphNode): Record<string, string> {
  const paths: Record<string, string> = {}
  for (const condition of conditionCases(node)) {
    const edge = graph.edges.find(
      (candidate) => candidate.source === node.id && candidate.sourceHandle === condition.id,
    )
    if (edge !== undefined) {
      paths[condition.id] = edge.target
    }
  }
  const elseEdge = graph.edges.find(
    (candidate) => candidate.source === node.id && candidate.sourceHandle === 'else',
  )
  if (elseEdge !== undefined) {
    paths.else = elseEdge.target
  }
  return paths
}
```

**这段在干什么（路由表部分）**

1. **`condition` 节点的所有出边被 `continue` 跳过**：它们不会成为普通边。否则「普通边 + 条件边」会同时生效，分支等于没分。
2. **`branchTargets` 只做 `find`，不做容错**：找不到就**不写**这个 key。这意味着如果预检漏了某个分支，路由表就少一项——而这正是 8.1.5 / 8.1.6 要挡住的场景（§21）。
3. **`state.branches[nodeId] ?? 'else'`**：路由值来自节点写回的状态；兜底 `'else'` 只防「节点没写」，不是「条件不匹配」的兜底（条件不匹配时节点自己已写 `'else'`）。
4. **`find` 语义 = 取第一条**：这是 8.1.8（同一分支多条边）必须报错的原因——第二条会被**静默忽略**。

## 16. 【技术教学 · 首次】「第一个匹配生效」：顺序即优先级

### 16.1 短路语义

```ts
for (const condition of data.conditions) {
  if (matches(condition, pool)) {
    emitBranchTaken(condition.id, condition.label ?? '')
    return { matched: condition.id }        // ← 命中即返回，后续条件连看都不看
  }
}
emitBranchTaken('else', 'else')
return { matched: 'else' }
```

**这就是 `if / else if / else if … else` 的图版本**：一旦某条成立，后面的条件**不再求值**。

由此产生一条重要推论：

> **`conditions` 的数组顺序 = 优先级。** 把最宽松的条件放在前面，后面的条件永远不会生效。

例：文本 `"服务很好，但物流差"`，条件顺序是 `contains("好")` → `contains("差")`，则走 `good`；反过来则走 `bad`。**这是配置问题，不是 bug**——所以保存时必须保持用户排的顺序（前端不要「自动排序」）。

### 16.2 顺序还影响错误文案

`validateGraph` 里 8.1.3 / 8.1.4 / 8.1.5 / 8.1.8 都是按 `conditions` 数组顺序逐条报。顺序变了，`message` 里错误的先后也就变了——**两端逐字节一致**的前提是「前端不自作主张重排」。

### 16.3 为什么 `else` 是强制项

因为 LangGraph 的条件边是**查表路由**：

```ts
builder.addConditionalEdges(node.id, router, mapping)   // Router 返回 key，LangGraph 去 mapping[key] 找目标
```

Router 的返回值只有两种可能：某个 `caseId`，或 `"else"`。`mapping` 必须**覆盖这两类值**，否则运行期会直接抛错（分支目标不存在）——而且这个错发生在**流量最大的那次运行**，不是保存时。

所以 `else` 不是「可选的兜底」，而是**让条件边成为全函数（total function）的补集**：

```
路由函数的定义域 = { 每个 caseId } ∪ { "else" }
路由表的目标集  = { 每个 caseId } ∪ { "else" }
两者必须相等 —— 8.1.5 保证左半边，8.1.6 保证右半边。
```

> **一句话**：`else` 让「路由表是完备的」这件事**可以被静态检查**，而不是靠运气。

## 17. 【技术教学 · 首次】12 个 `operator` 的确切语义

### 17.1 先看实现

**完整文件路径：`apps/api-ts/src/engine/nodes/condition.node.ts`**

```ts
import type { ConditionCase, ConditionNodeData, ConditionOperator, GraphNode } from '@mini-dify/contract'

import { tryRenderTemplate, type Pool } from '../template'

/**
 * `condition` 节点（阶段 8）：按 `data.conditions` **数组顺序**取第一个匹配的分支，
 * 全部不匹配走 `else`；返回 `{ matched }` 并回调发一次 `branch_taken`。
 *
 * `variable` / `value` 都用**分支安全**解析（`tryRenderTemplate`）：路径缺失视为空串，
 * 因为分支未执行时对端变量本就不存在（见 sse-events.md §4.1）。
 */
export function runConditionNode(
  node: GraphNode,
  pool: Pool,
  emitBranchTaken: (caseId: string, label: string) => void,
): Record<string, unknown> {
  const data = node.data as unknown as ConditionNodeData
  for (const condition of data.conditions) {
    if (matches(condition, pool)) {
      // `label` 在契约里是必填，但缺省时统一降级为空串（两端一致，避免 TS 省略键 / Python KeyError 分叉）
      emitBranchTaken(condition.id, condition.label ?? '')
      return { matched: condition.id }
    }
  }
  emitBranchTaken('else', 'else')
  return { matched: 'else' }
}

/** 单条条件是否成立；`value` 缺省时按空串参与比较。 */
function matches(condition: ConditionCase, pool: Pool): boolean {
  const left = tryRenderTemplate(condition.variable, pool)
  const right = condition.value === undefined ? '' : tryRenderTemplate(condition.value, pool)
  return applyOperator(condition.operator, left, right)
}

/** 运算符语义（两端一致，见 sse-events.md §4）。 */
function applyOperator(operator: ConditionOperator, left: string, right: string): boolean {
  switch (operator) {
    case 'equals':
      return left === right
    case 'not_equals':
      return left !== right
    case 'contains':
      return left.includes(right)
    case 'not_contains':
      return !left.includes(right)
    case 'starts_with':
      return left.startsWith(right)
    case 'ends_with':
      return left.endsWith(right)
    case 'is_empty':
      return left === ''
    case 'is_not_empty':
      return left !== ''
    case 'gt':
      return compareNumbers(left, right, (a, b) => a > b)
    case 'gte':
      return compareNumbers(left, right, (a, b) => a >= b)
    case 'lt':
      return compareNumbers(left, right, (a, b) => a < b)
    case 'lte':
      return compareNumbers(left, right, (a, b) => a <= b)
  }
}

/** 数字比较：任一侧不是有限数字时为 `false`。 */
function compareNumbers(
  left: string,
  right: string,
  predicate: (a: number, b: number) => boolean,
): boolean {
  const a = Number(left)
  const b = Number(right)
  if (!Number.isFinite(a) || !Number.isFinite(b)) {
    return false
  }
  return predicate(a, b)
}
```

**这段在干什么（按函数）**

1. **`runConditionNode`**：`for...of` + `return` 就是短路；命中时**先发事件再返回**（顺序固定：事件在 `node_finished` 之前）。
2. **`matches`**：`left` / `right` **都是字符串**——模板渲染的结果一律字符串化（非字符串走紧凑 JSON）。`value` 缺省（`undefined`）时按 `''`，因此 `is_empty` 不需要右操作数。
3. **`applyOperator`**：`switch` 覆盖 12 个值。因为 `operator` 已被预检限定在 12 个之内，`switch` 不需要 `default`（TS 也把它当成穷尽匹配）。
4. **`compareNumbers`**：**先 `Number(...)` 再判 `Number.isFinite`**。注意这一步的语义陷阱见 §17.3。

### 17.2 12 个运算符逐条

| operator | 语义 | 边界（必须记住） |
| --- | --- | --- |
| `equals` | `left === right`，**字符串全等** | 不做大小写归一、不做数字归一：`"1" ≠ "1.0"`、`"A" ≠ "a"` |
| `not_equals` | `left !== right` | 左侧变量缺失 → `""`，通常**成立**（除非右侧也是空串） |
| `contains` | `right` 是 `left` 的**子串** | 空 `right` 恒真（任何字符串都包含 `""`） |
| `not_contains` | 上一条取反 | 空 `right` 恒假 |
| `starts_with` | `left` 以 `right` 开头 | 同上：空 `right` 恒真 |
| `ends_with` | `left` 以 `right` 结尾 | 同上 |
| `is_empty` | `left === ''` | **只判空串**：`" "`（空格）不是空；`null` 不会出现（渲染结果总是字符串）；变量缺失 → `""` → **成立** |
| `is_not_empty` | `left !== ''` | 与上一条互补；**唯一的**「判断变量是否缺失」的办法 |
| `gt` | `Number(left) > Number(right)` | 任一侧 `Number(...)` 为 `NaN` / `±Infinity` → `false` |
| `gte` | `Number(left) >= Number(right)` | 同上 |
| `lt` | `Number(left) < Number(right)` | 同上 |
| `lte` | `Number(left) <= Number(right)` | 同上 |

### 17.3 数字比较的两个陷阱

**陷阱一：空串会变成 `0`，不是 `false`。**

```js
Number('')      // 0
Number('   ')   // 0
Number('abc')   // NaN
Number('1e3')   // 1000
Number('0x10')  // 16
```

所以 `variable` 缺失（→ `""`）时，`gt` 是拿 **0** 在比较：

```
gt  左侧缺失、右侧 "5"  →  0 > 5  →  false
lt  左侧缺失、右侧 "5"  →  0 < 5  →  true   ← 意外！
```

契约写的「任一侧不是有限数字时为 `false`」本身没错，但**空串是有限数字 0**。想判断「有没有值」，请用 `is_empty` / `is_not_empty`，不要指望 `gt` 帮你兜底。Python 侧为此专门写了 `_to_number`（对齐 JS）：

**完整文件路径：`apps/api-py/app/engine/nodes/condition.py`**（节选）

```python
def _to_number(text: str) -> float:
    """对齐 JS `Number(text)` 的常见表现：空串为 0，无法解析为 NaN。"""
    trimmed = text.strip()
    if trimmed == "":
        return 0.0
    try:
        return float(trimmed)
    except ValueError:
        return math.nan
```

**这段在干什么**

`strip()` 后为空 → `0.0`（对齐 `Number("   ") === 0`）；解析失败 → `nan`（对齐 `NaN`）。若这里写成 `float(text)`，Python 会对 `""` 抛 `ValueError`，两端行为立刻分叉。

**陷阱二：`contains` 是**大小写敏感**的子串匹配，不是「包含这些词之一」。**

`contains("你好")` 在 `"你好，请问"` 中成立，在 `"您 好"`（中间有空格）中**不**成立。需要多关键词时，用**多个条件**（它们按顺序短路，等价于 OR），或在上游节点里先把文本归一化。

### 17.4 为什么 `is_empty` 只判 `""`

因为**渲染结果永远是字符串**：`{{ x }}` 渲染出来要么是值的字符串化结果，要么是缺失时的 `""`。所以「空」在这个上下文里只可能有一种形态——空串。不需要处理 `null` / `undefined` / `[]` / `{}`。

反过来说：一个渲染结果是 `"[]"`（空数组的 JSON）时，`is_empty` **不**成立。要判「数组为空」，得在下游用别的办法（本项目没有提供）。

## 18. 【技术教学 · 首次】`aggregator`：把多条路径收敛成一个输入

### 18.1 它解决的问题

分支之后，下游会同时面对两个「可能不存在」的变量：

```
llm_good.text   ← 走 good 分支时存在
llm_bad.text    ← 走 bad 或 else 分支时存在
```

下游 `end` 只想写一行 `answer = ???`。三种做法：

| 做法 | 结果 |
| --- | --- |
| 写 `{{ llm_good.text }}` | 走 bad 时 → `template variable not found: llm_good.text` → `run_failed` |
| 写两个 `end` 节点，各自在一条分支上 | 可行，但每条分支都要维护一份「收尾」，分支越多越难改；且 `run_finished.outputs` 取**拓扑序最后一个** `end`（阶段 4 语义），行为隐晦 |
| **加一个 `aggregator`** | 两条分支都指向它，它输出一个**一定存在**的变量 |

```
                 ┌──(good)──▶ llm_good ──┐
s1 ──▶ c1 ──────┤                       ├──▶ agg1 ──▶ e1（只引用 agg1.answer）
                 ├──(bad)───▶ llm_bad  ──┤
                 └──(else)──▶ llm_bad  ──┘
```

### 18.2 它到底做什么

**完整文件路径：`apps/api-ts/src/engine/nodes/aggregator.node.ts`**

```ts
import type { AggregatorNodeData, GraphNode } from '@mini-dify/contract'

import { tryRenderTemplate, type Pool } from '../template'

/**
 * `aggregator` 节点（阶段 8）：对每个 `name`，按 `values` 顺序用**分支安全**解析取
 * **第一个非空串**；全部为空时取 `""`。
 *
 * 输出为**扁平对象** `{ "<name>": "<值>", ... }`（不做 `outputs` 包装）。
 * 未执行分支的变量在这里不存在，安全解析保证不报错（见 sse-events.md §4.1）。
 */
export function runAggregatorNode(node: GraphNode, pool: Pool): Record<string, unknown> {
  const data = node.data as unknown as AggregatorNodeData
  const output: Record<string, unknown> = {}
  for (const item of data.outputs) {
    let value = ''
    for (const template of item.values) {
      const rendered = tryRenderTemplate(template, pool)
      if (rendered !== '') {
        value = rendered
        break
      }
    }
    output[item.name] = value
  }
  return output
}
```

**这段在干什么（按嵌套层次）**

1. **外层遍历 `outputs`**：每个 `name` 产出一个键（可一次聚多个变量）。
2. **内层遍历 `values`**：按顺序渲染，**第一个非空**就 `break`——与 `condition` 同构的短路。
3. **全部为空 → `''`**：不抛错。空串在页面上的表现是「空白」，这是有意的（聚合是尽力而为）。
4. **`tryRenderTemplate`**：路径缺失 → `""`（不抛错）。没有它，走 good 分支时聚合器读到 `llm_bad.text` 会直接**运行失败**——这就是 §4.1 存在的第二个理由。
5. **输出扁平**：`{ answer: "..." }`，下游 `{{ agg1.answer }}`。

### 18.3 使用它的三条纪律

| 纪律 | 原因 |
| --- | --- |
| **下游只引用 `aggregator` 的键，不直接引用分支内节点的输出** | 分支未执行时那个键不存在，严格模板会 `run_failed` |
| **`values` 的顺序 = 优先级** | 若两条分支都可能产出非空值（理论上只有一个会执行），先写的优先 |
| **`aggregator` 必须能被所有分支到达** | 否则某条分支会绕过它，下游照样拿到空值 |

> 与 `condition` 对照：**两者都是「按顺序取第一个满足的」**；区别是 `condition` 取的是**布尔成立**，`aggregator` 取的是**非空字符串**。

## 19. 【技术教学 · 首次】`iteration` 三要素

### 19.1 它不是「图循环」

先澄清一个常见误解：

| | 图循环（LangGraph 的环） | **`iteration` 节点** |
| --- | --- | --- |
| 存在形式 | `edges` 里出现回边（阶段 6 的 ReAct） | **节点内部** `for` 循环 |
| `node_started` | 每绕一圈再发一次 | **只发一次** |
| 状态 | 每轮都经过 reducer 合并 | 循环期间不改图状态，结束才写一次 `pool[nodeId]` |
| 终止条件 | 条件边 + 轮次上限 | 数组长度 + `maxIterations` |
| 对 `edges` 的要求 | 必须显式写回边 | **不需要**任何回边 |

所以 `iteration` 的图仍然是 **DAG**——这也是 `sse-events.md` 写「不产生图循环」的原因。

### 19.2 第一要素：`inputArray`（模板 → JSON 数组）

```json
"inputArray": "{{ inputs.items }}"
```

运行时三步：

```
① tryRenderTemplate("{{ inputs.items }}", pool)
      → 非字符串值走 JSON.stringify（紧凑）→ '["退款","物流"]'
② JSON.parse(...)
      → ["退款","物流"]        （失败 → 8.2「must be an array」）
③ Array.isArray(...)
      → true                  （否则同样 8.2）
```

要点：

- 类型是 **`string`**：必须自己写成「能渲染出 JSON 的模板」，不能直接塞数组字面量（`['a','b']` 是非法 JSON，单引号不允许）。
- 也可以用**字面量 JSON**：`"inputArray": "[\"a\",\"b\",\"c\"]"`——不引用任何变量，常用于测试。
- `JSON.parse` 之后**必须**是数组：对象、数字、字符串都算失败。

### 19.3 第二要素：`itemName`（默认 `"item"`）

每项渲染时，池被临时扩展：

```
{ ...pool, [itemName]: <item 字符串化>, itemIndex: index, itemCount: total }
```

- `itemName` 默认 `"item"`；改成 `"row"` 后模板写 `{{ row }}`。
- **`item` 是「字符串化后的值」**：字符串原样，其余按紧凑 JSON。所以对象数组只能用 `{{ item }}` 拿到 `{"a":1}` 这样的文本，**不能** `{{ item.a }}`（§24）。
- `itemIndex` 从 **1** 开始，`itemCount` 是总数——**与 `iteration_item` 事件的 `index` 一致**。

### 19.4 第三要素：`outputTemplate`（每项渲染一次）

```json
"outputTemplate": "{{ itemIndex }}/{{ itemCount }}: {{ item }}"
```

- 每项渲染一次，结果按顺序进 `results`。
- **这里用严格解析**（`renderTemplate`）：引用了不存在的变量 → `run_failed`（§4.1 明确它不在安全解析范围内）。
- 输出 `{ results, count, joined }`，`joined = results.join("\n")`。

### 19.5 完整实现

**完整文件路径：`apps/api-ts/src/engine/nodes/iteration.node.ts`**

```ts
import type { GraphNode, IterationNodeData } from '@mini-dify/contract'

import { RunError } from '../events'
import { renderTemplate, tryRenderTemplate, type Pool } from '../template'

/** `iteration.maxIterations` 的默认值（与契约 `default: 20` 一致）。 */
export const DEFAULT_MAX_ITERATIONS = 20

/**
 * `iteration` 节点（阶段 8）：`inputArray` 安全解析后 `JSON.parse`，必须是数组；
 * 逐项先发 `iteration_item`（`index` 从 1 开始），再以
 * `{ ...pool, <itemName>: <item>, itemIndex, itemCount }` 渲染 `outputTemplate`。
 *
 * 输出 `{ results, count, joined }`，`joined = results.join("\n")`。
 * 数组长度超过 `maxIterations` 或解析结果不是数组时抛 `RunError`（见 error-messages.md §8.2）。
 */
export function runIterationNode(
  node: GraphNode,
  pool: Pool,
  emitItem: (index: number, total: number) => void,
): Record<string, unknown> {
  const data = node.data as unknown as IterationNodeData
  const maxIterations =
    typeof data.maxIterations === 'number' ? data.maxIterations : DEFAULT_MAX_ITERATIONS
  const itemName =
    typeof data.itemName === 'string' && data.itemName !== '' ? data.itemName : 'item'

  const rendered = tryRenderTemplate(data.inputArray, pool)
  let items: unknown
  try {
    items = JSON.parse(rendered)
  } catch {
    throw new RunError(`iteration node ${node.id} inputArray must be an array`)
  }
  if (!Array.isArray(items)) {
    throw new RunError(`iteration node ${node.id} inputArray must be an array`)
  }
  if (items.length > maxIterations) {
    throw new RunError(`iteration node ${node.id} exceeded max iterations: ${maxIterations}`)
  }

  const total = items.length
  const results = items.map((item, index) => {
    emitItem(index + 1, total)
    return renderTemplate(data.outputTemplate, {
      ...pool,
      [itemName]: stringifyItem(item),
      itemIndex: index + 1,
      itemCount: total,
    })
  })

  return { results, count: results.length, joined: results.join('\n') }
}

/** 当前项字符串化：字符串原样，其余按紧凑 JSON（两端一致）。 */
function stringifyItem(item: unknown): string {
  return typeof item === 'string' ? item : JSON.stringify(item)
}
```

**这段在干什么（按执行顺序）**

1. **`maxIterations` 兜底**：字段不是数字时用 `20`（预检已挡掉「不是数字」，这里防的是旧草稿 / 直接改库）。**注意兜底值是 20，不是 `Infinity`**。
2. **`itemName` 兜底**：空字符串也退回 `"item"`（否则模板里的 `{{ item }}` 永远取不到值）。
3. **`tryRenderTemplate`**：安全解析（缺失 → 空串）。
4. **`JSON.parse` 失败 / 不是数组 → 同一条文案**：契约把两种情形合并成 `inputArray must be an array`，因此两处 `throw` 用的是**逐字相同**的模板。
5. **`items.length > maxIterations` → `exceeded max iterations: {max}`**：`{max}` 是**配置值**（不是实际长度），所以本例实测是 `... exceeded max iterations: 2`。
6. **`map` 里先 `emitItem(index + 1, total)`**：保证「事件先于该项的处理」，与契约顺序一致。
7. **渲染用的池是「`...pool` + 三个注入键」**：注入键**覆盖**池里的同名键（如果变量池里恰好有 `item`，会被当前项盖住）。
8. **`stringifyItem`**：字符串原样、其余紧凑 JSON——这条规则决定了 `{{ item }}` 的输出格式，两端必须逐字节一致。

## 20. 【技术教学 · 首次】图校验的分工：语义 vs 字段类型

### 20.1 两个函数，两件事

| | **语义校验** | **字段类型校验** |
| --- | --- | --- |
| 文件 | `graph/graph.validator.ts` / `graph/validator.py` | `engine/engine.service.ts` / `engine/engine.py` |
| 函数 | `validateGraph` / `validate_graph` | `validateNodeData` / `validate_node_data` |
| 输入 | **整张图**（`nodes` + `edges`） | 单个节点的 `data` |
| 管什么 | 空数组、重复 id、operator 合法性、`variable` 非空、**分支边是否完整**、`maxIterations` 数值越界 | 是不是数组、是不是字符串、是不是数字、工具名是否存在 |
| 什么时候跑 | **保存（PUT / publish）** 与 **运行前** | **只在运行前** |
| 能否独立使用 | 能（纯函数，无 IO） | 需要引擎上下文（工具注册表等） |

### 20.2 为什么必须拆开

1. **语义规则需要「边」**：8.1.5~8.1.8 都要看 `graph.edges`。`validateNodeData` 的入参是单节点，看不到边。
2. **保存时还不知道「能不能执行」**：`PUT /graph` 只做语义校验（不查工具名、不查知识库归属）。字段类型校验在 `POST /run` 才跑——因为旧草稿可能是在阶段 8 之前存的，字段形状只有运行时才需要保证。
3. **职责单一**：语义校验是「这张图讲不讲得通」，字段校验是「这个节点能不能被引擎解释」。

### 20.3 「互斥命中」：同一条文案只能有一个来源

两边的代码里都写了同一句文案，**但只有一边真的会报**：

| 情形 | 语义层 | 字段层 | 最终谁报 |
| --- | --- | --- | --- |
| `conditions` 缺失 / 不是数组 | `return []` | `!Array.isArray` → 报 | **字段层** |
| `conditions: []` | 空数组 → 报 | `Array.isArray` 为真，不报 | **语义层** |
| `aggregator.outputs` 缺失 / 不是数组 | `continue` | `!Array.isArray` → 报 | **字段层** |
| `aggregator.outputs: []` | 空数组 → 报 | 数组为真，不报 | **语义层** |
| `outputs[].values` 不是数组 | 只查「是数组且空」 | `!Array.isArray` → 报 | **字段层** |
| `outputs[].values: []` | 空数组 → 报 | 数组为真，不报 | **语义层** |
| `iteration.inputArray` 不是字符串 | `typeof === 'string'` 才查，否则跳过 | `typeof !== 'string'` → 报 | **字段层** |
| `iteration.inputArray: "   "` | 空白串 → 报 | 是字符串，不报 | **语义层** |
| `maxIterations` 不是数字 | `typeof === 'number'` 才查，否则跳过 | `typeof !== 'number'` → 报 | **字段层** |
| `maxIterations: 0` / `200` / `1.5` | 数字但越界/非整数 → 报 | 是数字，不报 | **语义层** |

**为什么这件事必须做到**

因为两条错误是**拼接**的：

```ts
const errors = [...validateGraph(graph), ...validateNodeData(graph)]
if (errors.length > 0) throw new BadRequestException(errors.join('; '))
```

若两边都报，用户会看到 `condition node c1 must have at least one condition; condition node c1 must have at least one condition`——既难看，又让「两端逐字节一致」变得脆弱（顺序稍有不同就不同）。

**实现上的通用手法**：语义层先做「类型判断」，**类型不对就 `continue` / `return []`**；字段层则只判断类型。两条规则集合的交集**恰好是空集**。

> 这也是为什么 8.1.1 / 8.1.9 / 8.1.11 / 8.1.12 的契约文字写了「含不是数组」「含非数字」——它的意思是「**最终**用户会看到这句文案」，而不是「语义层自己会报」。文字层面合并、实现层面互斥，是这套分工的契约表达方式。

### 20.4 实测（本篇）

| 输入 | 响应（两端逐字节相同） |
| --- | --- |
| `condition` 无 `conditions` | `{"statusCode":400,"message":"condition node c1 must have at least one condition","error":"Bad Request"}` |
| `condition.conditions = []` | 同上（**只出现一次**） |
| `aggregator` 无 `outputs` | `{"statusCode":400,"message":"aggregator node agg1 must have at least one output","error":"Bad Request"}` |
| `aggregator.outputs = []` | 同上（**只出现一次**） |

## 21. 【技术教学 · 首次】8 类分支预检：每条在防什么

> 这里只讲 **condition 的 8.1.1~8.1.8**（8 类分支预检）。`aggregator` / `iteration` 的 8.1.9~8.1.12 在 §18 / §19 已随语义讲过。
>
> 另有 **8.1.2a**（case id 用了保留名 `else`）与 8.1.2 在同一个循环里执行：**先查保留名、再查重复**，文案 `condition node {nodeId} case id "else" is reserved`。它防的是「某个 case 占用了兜底分支的 key」——`branchTargets` 会把 `else` 当成同一个分支，条件命中的实际走向与配置相反，且不会报任何运行期错误。

### 21.1 逐条对照

| 序 | 规则 | 文案 | **没有这条会发生什么** |
| --- | --- | --- | --- |
| 8.1.1 | `conditions` 为空 | `condition node c1 must have at least one condition` | 节点必然走 `else`。表面「能跑」，实则分支配置被清空且没人发现；且 8.1.2a~8.1.8 全部无从检查（没有 case 可查） |
| 8.1.2 | case id 重复 | `condition node c1 has duplicate case id: good` | 两个不同条件共用一个 `sourceHandle`：`branchTargets["good"]` 只保留**一条**边的目标，另一个条件命中时会走到**错的节点** |
| 8.1.3 | operator 非法 | `condition node c1 has invalid operator: regex` | 运行期 `switch` 匹配不到任何分支。TS 的 `applyOperator` 在类型层面穷尽，但**运行期值来自 JSON**，非法值会让函数返回 `undefined`（JS 的 switch 落空），被当成 `false`——**静默永远走 else** |
| 8.1.4 | `variable` 为空 | `condition node c1 case good variable is required` | 左侧恒为 `""`：`is_empty` 恒真、`contains` 在右侧非空时恒假、`equals` 只在右侧也为空时成立——**一个恒定结果的「假分支」**，比报错更难发现 |
| 8.1.5 | **每个 case 必须有出边** | `condition node c1 case good has no outgoing edge` | 选中 `good` 时，路由表里**没有 `good` 这个 key**，LangGraph 条件边**在运行期抛错**（找不到分支目标）。而且只有「真的走到这条分支」的用户才会失败——典型的**潜伏型崩溃** |
| 8.1.6 | `else` 必须有出边 | `condition node c1 else branch has no outgoing edge` | 与上一条同源：全部条件不匹配时 router 返回 `"else"`，映射缺失 → 运行期崩溃。而且 `else` 是**最容易忘**的一条（用户常常只连了「有值」的那条） |
| 8.1.7 | `sourceHandle` 非法 | `edge e1 from condition node c1 has invalid sourceHandle: bogus` | `condition` 的所有出边都**跳过普通边**、只走条件路由。句柄不合法的边**既不是普通边、也进不了路由表** → 目标节点**永远不可达**，画布上却明明连着一条线——**静默丢边**，最隐蔽 |
| 8.1.8 | 同一分支多条边 | `condition node c1 has duplicate edge for case good` | `branchTargets` 用 `find`（取第一条），第二条被**静默忽略**。用户以为「两个下游都会执行」，实际只有一个。图上的拓扑与运行行为不一致 |

### 21.2 为什么「每个 case 必须有出边」最值得讲

它是**唯一一条**「不做静态检查就必然在运行期爆炸」的规则——其余 7 条多数是「静默错」：

```
预检缺失 8.1.5
  → 图保存成功（200）
  → 用户点「运行」，输入恰好命中 good
  → LangGraph: conditional edge 返回 "good"，但 mapping 里没有 "good"
  → 抛错 → run_failed（nodeId = c1）
  → 用户看到「运行失败」，但**不知道是图缺了一条边**
```

对比：如果预检存在，错误在**保存**时就以 400 返回，文案直接指出「哪个节点的哪个 case 缺出边」。

**这就是「图上的一条线」和「运行期的一个分支」之间的距离**：预检把后者「编译」成了前者。

### 21.3 `aggregator` / `iteration` 的四条

| 序 | 规则 | 没有它会怎样 |
| --- | --- | --- |
| 8.1.9 | `outputs` 为空 | 聚合器输出 `{}`，下游 `{{ agg1.answer }}` 直接 `run_failed`（而且是**多处**下游一起崩） |
| 8.1.10 | 某 `values` 为空数组 | 该 `name` 恒为 `""`，静默空值（与 8.1.1 同理：配置被清空却无人发现） |
| 8.1.11 | `inputArray` 为空串 | 渲染得到 `""` → `JSON.parse` 失败 → 运行期 `run_failed`。**空串是能静态发现的，所以提前到 400** |
| 8.1.12 | `maxIterations` 越界 | 0 会让每次迭代都失败；负数是显然的错误；`>100` 破坏成本护栏。**数值能静态检查，就不要留给运行期** |

## 22. 【技术教学 · 首次】为什么校验放在「保存 / 运行前」，而不是运行中

### 22.1 三个硬理由

| 理由 | 说明 |
| --- | --- |
| **HTTP 状态码只有一次机会** | 一旦开始写 SSE 流，响应头就已经是 `200`，再发现配置错也只能塞进 `run_failed`。届时前端要区分「图配错了（该去改图）」和「模型挂了（该重试）」，只能靠解析字符串 |
| **早失败 = 不浪费** | 分支配错如果放到运行中，前面的 `start` / LLM 调用可能已经花了钱、发了 token，然后才失败 |
| **文案稳定 = 两端可比** | 400 普通 JSON 的 `message` 是纯函数产物；`run_failed` 的 `message` 来自异常（可能带库的原始信息）。要做到「两端逐字节一致」，必须尽量把错误前移到纯函数里 |

### 22.2 但也不能全放到保存时

| 只能在运行前做的 | 原因 |
| --- | --- |
| `iteration.inputArray` 是不是数组 | 取决于运行输入（`{{ inputs.items }}` 渲染后才知道） |
| `iteration` 长度是否超 `maxIterations` | 同上 |
| 工具名是否存在（§6.1） | 需要工具注册表 |
| 知识库归属（§7.2） | 需要数据库 + 当前用户 |

于是形成**三层**结构：

```
保存（PUT / publish）     → 语义校验（纯函数，无 IO）
运行前（POST /run）       → 语义校验 + 字段类型校验 + 需要 DB 的预检
执行中（SSE 流）           → 只能 run_failed（渲染结果、外部依赖、数组长度）
```

### 22.3 一条可以长期执行的原则

> **能在 Pure Function 里判死的，就不要留给运行期；必须在运行期判的，就写进契约的 §8.2，并保证两端同一句文案。**

阶段 3 的「写图即校验」、阶段 4 的「先校验、后开流」、本篇的「分支边预检」，是同一条原则的三次应用。

## 24. 常见坑

| 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- |
| 给 `condition` 加了一条「没有句柄」的默认边当兜底 | 400 `edge ex from condition node c1 has invalid sourceHandle: null` | `condition` 的**所有**出边都必须带 `sourceHandle`。想兜底就显式写 `sourceHandle: "else"`；那条无句柄的边即使被放过也永远不可达（8.1.7） |
| 画布把手 id 写成 `good-1` 之类 | `has no outgoing edge` / `invalid sourceHandle` | `caseId` 与 `sourceHandle` 必须**逐字符相等**、大小写敏感。改条件 id 后要同步改边 |
| 只连了「有值」分支，忘了 `else` | 400 `condition node c1 else branch has no outgoing edge` | `else` 是强制项（§16.3）。哪怕 `else` 与某个 case 指向同一节点，也要单独连一条 |
| 同一分支连了两条线 | 400 `has duplicate edge for case good` | 引擎 `branchTargets` 用 `find`，只认第一条；第二条会被静默忽略（8.1.8） |
| 把 `is_empty` 当成「判空值 / 判空数组」 | 变量为 `"[]"`、`" "` 时 `is_empty` 不成立 | `is_empty` 只判 `""`。变量缺失 → `""` → 成立；空格串不成立（§17.4） |
| 用 `gt` 判「有没有值」 | 变量缺失时 `lt 5` 竟然成立 | `Number('') === 0`，空串被当作 0 参与比较（§17.3） |
| 用 `contains("好")` 判「正向」 | 「不好」被误判为好评 | 子串匹配没有语义：`"不好"` 包含 `"好"`。要么用 `not_contains("不好")` 前置，要么先在上游做文本归一 |
| 条件顺序随手调换 | 同一输入走的分支变了 | 数组顺序 = 优先级（§16.1）。前端不要自动排序 |
| 下游直接写 `{{ llm_good.text }}` | 走 bad 分支时 `run_failed: template variable not found: llm_good.text` | 分支未执行 → 该键不在池里；必须经 `aggregator` 收敛（§18.3） |
| `aggregator` 的 `values` 写成了单个字符串 | 400 `aggregator node agg1 output answer must have at least one value`（字段层报） | `values` 必须是**数组**，哪怕只有一项 |
| `aggregator` 全部分支为空 | 下游拿到空字符串，页面一片空白 | 这是**设计语义**（全空 → `""`），不是 bug；要兜底就给 `values` 末尾加一个字面量模板 |
| `inputArray` 直接写 JSON 数组（不是字符串） | 400 `iteration node iter1 inputArray is required`（字段层，因为不是字符串） | 它是**字符串模板**，要写 `"{{ inputs.items }}"` 或 `"[\"a\",\"b\"]"`（注意双引号转义） |
| 单引号 JSON | `run_failed: iteration node iter1 inputArray must be an array` | `["a","b"]` 是合法 JSON，`['a','b']` 不是 |
| `start` 输入声明 `type: "string"` 却传数组给 `iteration` | 不报错，`{{ inputs.items }}` 渲染成 JSON 数组 | `start.data.inputs[].type` **不在预检范围内**（§4.1.4 只查 `name`）。这是本阶段刻意的宽松点：`type` 目前只有 `"string"` 一个取值，实际类型由运行输入的 JSON 决定 |
| 用 `{{ item.name }}` 取对象字段 | `run_failed: template variable not found: item.name` | `item` 是**字符串化后的值**，不是对象；对象数组只能整体用 `{{ item }}`（§19.3） |
| 把 `iteration` 当成「图循环」 | 想画一条回边 | 它是节点内部循环，**不需要**回边；加了回边反而形成真正的图环 |
| 以为 `maxIterations` 不填就没上限 | 只处理了前 20 项 | 默认 **20**（契约 `default: 20`），不是无限 |
| `maxIterations: true` | 400 `iteration node iter1 maxIterations must be between 1 and 100`（两端一致） | Python 的 `bool` 是 `int` 子类，`_is_number` 显式排除；TS 侧 `typeof true !== 'number'` 直接判非数字 |
| 条件 id 取名为 `else`（**保留分支名**） | 400 `condition node c1 case id "else" is reserved` | **`else` 是保留分支名**，不能用作 case id：8.1.2a 与 8.1.2 同循环、先查保留名再查重复（§24.1） |
| `data.title` / `label` 漏填 | 保存能过；`branch_taken` 的 `label` 为 `""`（**已修复，两端一致**） | 契约里 `label` 仍是 required，但两端都把缺失的 `label` **统一降级为空串**，不再出现「TS 省略键 / Python `KeyError`」的分叉（§24.1） |
| 保存时以为会做字段校验 | 图存进去了，`run` 时才 400 | 保存只跑**语义校验**；字段类型校验在 `POST /run`（§20.1） |
| 改了条件但没改边 / 改了边但没改条件 | 一会儿 8.1.5，一会儿 8.1.7 | `id` ↔ `sourceHandle` ↔ 画布把手 id 是**三处同一份数据**，必须同步改 |
| PowerShell 里写 `curl` | 报 `-H` 参数错误 / 输出 `StatusCode` | 用 `curl.exe`（§4） |
| 请求体文件存成 UTF-16 / 带 BOM | 400（JSON 解析失败）或中文乱码 | 存 **UTF-8 无 BOM**；用 `--data-binary @file` 而不是 `-d @file`（后者会去掉换行） |
| 忘了 `pnpm run build:contract` | NestJS 编译报「找不到 `ConditionOperator`」 | 类型来自 `dist`（§4） |
| 两端错误文案「看起来一样但顺序不同」 | `a == b` 为 `False` | 检查 `nodes` / `edges` 的数组顺序、以及语义层是否漏了「先 condition 再 aggregator 再 iteration」的遍历顺序 |

### 24.1 两个曾经的「静默」缺陷（均已修复并实测）

1. **`caseId === "else"` 曾被静默接受**：`else` 是条件边 `mapping` 的保留 key，与「否则」分支冲突会静默错路由。现在两端校验器都在 8.1.2 的同一个循环里**先查保留名、再查重复**（8.1.2a），同一张图（case id = `else`）两端都返回 **HTTP 400**，且 `message` **逐字节相同**：

   ```text
   condition node c1 case id "else" is reserved; condition node c1 has duplicate edge for case else; condition node c1 has duplicate edge for case else
   ```

   > 后两条重复提示是既有规则 8.1.8「同一 `sourceHandle` 有多条出边」在同一畸形图上被触发两次（`caseIds` 循环里报一次、`else` 专项检查再报一次）；**两端行为一致，属预期**，不是新增缺陷。

2. **`label` 缺失曾导致两端分叉**（TS 省略键 / Python `KeyError`）：现在两端都把缺失的 `label` **统一降级为空串**（TS `condition.label ?? ''`；Python `condition.get("label") or ""`），不新增预检，契约里 `label` 仍是 required。实测同一张「case 缺 `label`」的图，两端 `branch_taken` 均为：

   ```json
   {"nodeId":"c1","caseId":"case1","label":""}
   ```

   且整条 SSE 流（归一化 `runId` / `appId` / `elapsedMs` 后）逐字节相同。

| **为什么工作流需要分支** | 真实业务按条件走不同路径；「让模型在 prompt 里判断」不确定、不可审计、费 token、难测试；**LLM 管不确定的理解，控制流管确定的枚举**；分支带来三个新问题：多出口怎么表达、汇合怎么取值、走错边怎么提前发现 | **首次教学于本篇** |
| **`condition` 三要素** | `conditions[]`（**有序**、每项是 `(variable, operator, value)` 三元组、`id` 即分支标识）、`operator`（12 个闭集）、`else`（不在数组里，只以 `sourceHandle:"else"` 与事件 `caseId:"else"` 存在）；节点输出 `{ matched }` | **首次教学于本篇** |
| **`edge.sourceHandle` 是分支的载体** | 一条边 = `(source, sourceHandle, target)`；`null`/省略 = 默认出口，`caseId` = 指定分支，`"else"` = 兜底；`targetHandle` 只有画布用；「多出口」用边端点编码而非节点内嵌 `exits[]`，图仍是 `nodes[] + edges[]`，规则 1~7 可原样复用 | **首次教学于本篇** |
| **「第一个匹配生效」的短路语义** | `for` + `return` 即短路；**数组顺序 = 优先级**；顺序同时决定错误文案顺序；`else` 强制的原因是「让条件边的路由表成为全函数」，缺表项会在运行期抛错 | **首次教学于本篇** |
| **12 个 operator 的确切语义** | `equals/not_equals` 字符串全等（不归一大小写/数字）；`contains/not_contains/starts_with/ends_with` 子串/前后缀（大小写敏感）；`is_empty/is_not_empty` 只判 `""`；`gt/gte/lt/lte` 先 `Number()` 再比较，`NaN`/`Infinity` → `false`，**但空串会变成 0** | **首次教学于本篇** |
| **分支安全的变量解析（§4.1）** | 路径缺失 → 空串、不抛错；**只**用于 `condition.variable/value`、`aggregator.values[]`、`iteration.inputArray`；其余节点（`llm`/`knowledge`/`end`/`iteration.outputTemplate`）仍严格抛 `template variable not found`；模板其余文本原样保留 | **首次教学于本篇** |
| **`aggregator`：多分支收敛** | 对每个 `name` 按 `values` 顺序取**第一个非空串**，全空取 `""`；输出扁平对象；存在理由：分支未执行时对端变量不在池中，下游直接引用会 `run_failed`；与 `condition` 同为「按顺序取第一个」，只是判据是「非空」而非「为真」 | **首次教学于本篇** |
| **`iteration` 三要素与非图循环** | `inputArray`（**字符串模板** → 渲染 → `JSON.parse` → 必须是数组）、`itemName`（默认 `item`，值是**字符串化**后的项）、`outputTemplate`（每项渲染一次，注入 `item`/`itemIndex`（1 起）/`itemCount`）；输出 `{ results, count, joined }`，`joined = results.join("\n")`；`maxIterations` 默认 20、范围 1..100；**不是图环**，只发一次 `node_started`/`node_finished` | **首次教学于本篇** |
| **图校验的分工：语义 vs 字段类型** | `validateGraph`/`validate_graph` 管整图语义（空数组、重复 id、operator、`variable` 非空、分支边完整性、数值越界）；引擎 `validateNodeData`/`validate_node_data` 只查字段类型（是否数组/字符串/数字）；**两者互斥命中**（语义层「类型不对就 return/continue」），避免 `msg; msg`；契约文字层面合并、实现层面互斥 | **首次教学于本篇** |
| **8 类分支预检各自防什么** | 8.1.1 空条件（分支被清空仍「能跑」）；8.1.2 重复 id（路由指向错节点）；8.1.3 非法 operator（静默恒 false）；8.1.4 空 variable（恒定假分支）；**8.1.5 每个 case 必须有出边（唯一必然在运行期抛错的规则）**；8.1.6 else 必须有出边（最容易忘）；8.1.7 非法句柄（边静默不可达）；8.1.8 同分支多条边（`find` 只取第一条）；**8.1.2a `else` 为保留分支名**（与 8.1.2 同循环、先查保留名） | **首次教学于本篇** |
| **校验为什么放在保存 / 运行前** | HTTP 状态码只有一次机会（开流后只能 `run_failed`）；早失败不浪费 token；纯函数保证文案稳定、两端逐字节一致；三层结构：保存（语义）→ 运行前（语义 + 字段 + DB 预检）→ 执行中（`run_failed`） | **首次教学于本篇** |
