## 1. 本篇目标

做完这一篇，你能：

- 沿**依赖顺序**逐层验收阶段 3：契约编译 → **JSONB 列迁移** → 两套后端的图接口 → **校验规则一致性（逐字节）** → **发布两态** → **归属隔离** → **跨后端同列一致** → 浏览器全链路。
- 用**可直接复制的命令**证明两套后端「行为一致」：状态码一致、响应体**形状**一致、**业务校验文案逐字节一致**、**JSONB 往返后的对象形状一致**。
- 讲清楚**为什么阶段 3 是「从 CRUD 进入编排引擎」的转折点**：图=数据、后端只**存取 + 校验**、执行留给阶段 4。
- 讲清楚「契约一致」在本阶段**新增的层次**：从「状态码 / 形状」推进到「**业务校验文案逐字节一致**」与「**JSONB 往返对象形状一致**」。

> 拖节点连线并保存 / 重载。

## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序（先契约与库、后两端、再一致性与隔离、最后前端）

```
L1 契约编译        L2 迁移 / JSONB 列
      ↓                    ↓
L3 api-ts 图接口   L4 api-py 图接口
      ↓                    ↓
L5 校验规则一致 → L6 发布两态 → L7 归属隔离 → L8 跨后端同列一致 → L9 浏览器
```

**为什么按这个顺序**：契约不编译，两端类型对不上；JSONB 列不存在，存取必然 500；两端各自能存取之后，「校验一致 / 两态 / 隔离 / 同列一致」才有意义；最后才是浏览器。

### 3.3 L3 —— api-ts（NestJS）图接口

**在哪执行**：任意目录（用 `127.0.0.1`）

```bash
# 读草稿（从未保存过）→ 期望 200 合法空图
curl -i http://127.0.0.1:3001/apps/$APP_ID/graph -H "Authorization: Bearer $TS_TOKEN"

# 保存一份合法图 → 期望 200（返回保存后的草稿）
curl -i -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"n-start","type":"start","position":{"x":0,"y":0},"data":{"title":"开始"}},
        {"id":"n-llm","type":"llm","position":{"x":0,"y":160},"data":{"title":"LLM","model":"gpt-4o","prompt":"你好"}},
        {"id":"n-end","type":"end","position":{"x":0,"y":320},"data":{"title":"结束"}}
      ],"edges":[
        {"id":"e1","source":"n-start","target":"n-llm","sourceHandle":null,"targetHandle":null},
        {"id":"e2","source":"n-llm","target":"n-end","sourceHandle":null,"targetHandle":null}
      ]}'

# 再读草稿 → 与刚存的一致
curl -s http://127.0.0.1:3001/apps/$APP_ID/graph -H "Authorization: Bearer $TS_TOKEN"

# 发布 → 期望 200 {publishedAt, graph}
curl -i -X POST http://127.0.0.1:3001/apps/$APP_ID/graph/publish -H "Authorization: Bearer $TS_TOKEN"

# 读已发布 → 期望 200 graph
curl -i http://127.0.0.1:3001/apps/$APP_ID/graph/published -H "Authorization: Bearer $TS_TOKEN"

# 无 token → 期望 401
curl -i http://127.0.0.1:3001/apps/$APP_ID/graph
```

**预期输出（实测·形状）**

```
# 读草稿（尚未编辑）200
HTTP/1.1 200 OK
{"version":"1","nodes":[],"edges":[]}

# 保存 200（原样返回）
HTTP/1.1 200 OK
{"version":"1","nodes":[{...}],"edges":[{...}]}

# 发布 200（publishedAt 为 UTC 毫秒 Z）
HTTP/1.1 200 OK
{"publishedAt":"2026-10-18T...Z","graph":{"version":"1","nodes":[...],"edges":[...]}}

# 读已发布 200
HTTP/1.1 200 OK
{"version":"1","nodes":[...],"edges":[...]}

# 无 token 401（错误信封）
HTTP/1.1 401 Unauthorized
{"statusCode":401,"message":"Missing bearer token","error":"Unauthorized"}
```

**结果解读**：`GET /graph` 在草稿为 `NULL` 时返回**合法空图**（`{"version":"1","nodes":[],"edges":[]}`）——**读取不做语义校验**；`PUT` / `publish` 才做校验（见 3.5、第 6 节坑 2）。`publishedAt` 为 24 字符、形如 `2026-10-18T12:10:18.900Z`（UTC 毫秒 `Z`，阶段 2 已收口）。

**在哪执行**：任意目录

```bash

PY_TOKEN=$(curl -s -X POST http://127.0.0.1:8000/auth/login \

# bob 先建自己的应用
PY_APP_ID=$(curl -s -X POST http://127.0.0.1:8000/apps \

curl -i http://127.0.0.1:8000/apps/$PY_APP_ID/graph -H "Authorization: Bearer $PY_TOKEN"    # 200 空图
curl -i -X PUT http://127.0.0.1:8000/apps/$PY_APP_ID/graph \
  -H "Authorization: Bearer $PY_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"n-start","type":"start","position":{"x":0,"y":0},"data":{"title":"开始"}},
        {"id":"n-end","type":"end","position":{"x":0,"y":160},"data":{"title":"结束"}}
      ],"edges":[{"id":"e1","source":"n-start","target":"n-end"}]}'
curl -i -X POST http://127.0.0.1:8000/apps/$PY_APP_ID/graph/publish -H "Authorization: Bearer $PY_TOKEN"
curl -i http://127.0.0.1:8000/apps/$PY_APP_ID/graph/published -H "Authorization: Bearer $PY_TOKEN"
curl -i http://127.0.0.1:8000/apps/$PY_APP_ID/graph                                     # 无 token → 401
```

**预期输出（实测）**：与 L3 **结构完全一致**——空草稿读 **200** / 保存 **200** / 发布 **200** / 读已发布 **200** / 无 token **401** / 结构或语义非法 **400**，字段名与类型相同，错误体同为 `{"statusCode","message","error"}`。

> 注意 api-py 的 `PUT` 用了 `model_dump(exclude_unset=True)`：请求体里**没写** `sourceHandle` / `targetHandle` 时，落库对象里就**不含**这两个键（不像 api-ts 的 `GraphDto` 会因为字段声明而带上 `undefined` 再被序列化丢弃）。两种实现都保证「**存下的形状 = 请求体的形状**」——这是 L8 要验证的。

### 3.5 L5 —— 校验规则一致性（7 组，逐字节）

**在哪执行**：任意目录
**目的**：这是阶段 3 的一致性核心——**业务校验文案**必须两端**逐字节相同**。规则与文案的唯一真源是 `packages/contract/error-messages.md` §3；两端的纯函数（`apps/api-ts/src/graph/graph.validator.ts` 的 `validateGraph` ↔ `apps/api-py/app/graph/validator.py` 的 `validate_graph`）**规则顺序、遍历顺序、文案模板逐条对齐**。

**7 组非法图**（`version` 必须为 `"1"`，这是所有合法图的前提）：

| 组 | 触发 | 请求体要点 | 两端一致的 `message` |
| --- | --- | --- | --- |
| 1 | `version` ≠ `"1"` | `"version":"2"` | `graph version must be 1` |
| 2 | 节点 id 重复 | 两个 `id:"n1"` | `node id must be unique: n1` |
| 3 | `start` 数 ≠ 1 | 无 start | `graph must contain exactly one start node` |
| 4 | `end` 数为 0 | 无 end | `graph must contain at least one end node` |
| 5 | 边 id 重复 | 两条 `id:"e1"` | `edge id must be unique: e1` |
| 6 | 边端点不存在 | `target:"ghost"` | `edge e1 references unknown node: ghost` |
| 7 | 自环 | `source === target` | `edge e1 must not connect a node to itself` |

```bash
# 以「组 4：缺 end 节点」为例 —— 两端各打一次，比对 message
BODY='{"version":"1","nodes":[
        {"id":"n-start","type":"start","position":{"x":0,"y":0},"data":{}},
        {"id":"n-llm","type":"llm","position":{"x":0,"y":160},"data":{}}
      ],"edges":[{"id":"e1","source":"n-start","target":"n-llm"}]}'

curl -i -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' -d "$BODY"
curl -i -X PUT http://127.0.0.1:8000/apps/$PY_APP_ID/graph \
  -H "Authorization: Bearer $PY_TOKEN" -H 'Content-Type: application/json' -d "$BODY"
```

**预期输出（实测·两端逐字节相同）**

```
HTTP/1.1 400 Bad Request
{"statusCode":400,"message":"graph must contain at least one end node","error":"Bad Request"}
```

**多规则同时命中**时按**规则顺序**拼接（`"; "` 连接），例（`version:"2"` 且无 start）：

```json
{"statusCode":400,"message":"graph version must be 1; graph must contain exactly one start node","error":"Bad Request"}
```

**结果解读**：7 组全部通过 ⇒ 业务校验层两端**逐字节一致**。这与「结构校验」（DTO / Pydantic 的字段、类型、枚举、`additionalProperties:false`）**分层**：结构校验由各自框架的管线完成（阶段 2 已把错误信封与文案归一），**语义校验**由两端手写的**同一份纯函数规则**完成。二者都在 `error-messages.md` 有唯一真源。

### 3.6 L6 —— 发布两态（draft / published 快照）

**在哪执行**：任意目录
**目的**：证明「草稿」与「已发布」是**两份独立数据**——发布把**当时的草稿**快照一份；之后继续改草稿，**已发布不受影响**。

```bash
# 先无脑读 published —— 从未发布过
curl -i http://127.0.0.1:3001/apps/$APP_ID/graph/published -H "Authorization: Bearer $TS_TOKEN"
# ↑ 注意：此时 $APP_ID 在 3.3 已发布过；若想复现「从未发布」，用 3.4 里刚建、未发布的 $PY_APP_ID 打 api-ts/8000

# A. 把草稿改成「不同」的图（只留 start + end），再发布/或先读 published 看是否变
curl -s -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"n-start","type":"start","position":{"x":0,"y":0},"data":{"title":"改动后"}},
        {"id":"n-end","type":"end","position":{"x":0,"y":400},"data":{"title":"结束"}}
      ],"edges":[{"id":"e9","source":"n-start","target":"n-end"}]}'

# B. 读草稿（应是刚改的这份）
curl -s http://127.0.0.1:3001/apps/$APP_ID/graph -H "Authorization: Bearer $TS_TOKEN"

# C. 读已发布（应还是 3.3 发布时的旧快照，未被上面的改动影响）
curl -s http://127.0.0.1:3001/apps/$APP_ID/graph/published -H "Authorization: Bearer $TS_TOKEN"
```

**预期输出（实测）**

```
# 从未发布过时读 published
HTTP/1.1 404 Not Found
{"statusCode":404,"message":"Graph not published","error":"Not Found"}

# B. 草稿 = 刚 PUT 的新图（3 节点→2 节点、e2→e9、title 变了）
{"version":"1","nodes":[{"id":"n-start",...,"data":{"title":"改动后"}},{"id":"n-end",...}],"edges":[{"id":"e9",...}]}

# C. 已发布 = 仍是旧快照（3 节点 2 边 + 原 title）
{"version":"1","nodes":[{"id":"n-start",...,"data":{"title":"开始"}},...],"edges":[{"id":"e1",...},{...}]}
```

**结果解读**：`published_graph_json` 在 `publish` 那一刻**拷贝当前草稿**；此后草稿怎么改，**都不动已发布**（两态隔离）。从未发布过时读已发布 → **404** `Graph not published`（这条文案也在 `error-messages.md` §2 登记，两端一致）。

### 3.7 L7 —— 归属隔离（404）

**在哪执行**：任意目录
**目的**：沿用阶段 2 的安全核心——用户只能操作**自己的**应用图。

```bash
# B（bob）用**自己的** token 去读 A（alice）的应用图 → 期望 404
curl -i http://127.0.0.1:3001/apps/$APP_ID/graph -H "Authorization: Bearer $BOB_TOKEN"

# B 去发布 A 的应用图 → 期望 404（不是 403，也不是 500）
curl -i -X POST http://127.0.0.1:3001/apps/$APP_ID/graph/publish -H "Authorization: Bearer $BOB_TOKEN"
```

**预期输出（实测）**

```
HTTP/1.1 404 Not Found
{"statusCode":404,"message":"App not found","error":"Not Found"}
```

**结果解读**：与 `/apps` 一致，图接口复用同一套归属检查（`findOwned` / `_find_owned`）：**查不到、或不属于当前用户 → 404**（隐藏资源存在性，见 `02-应用管理/07` 的技术讨论）。

### 3.8 L8 —— 跨后端同列一致（JSONB 往返）

**在哪执行**：任意目录
**目的**：证明两套后端读写的是**同一个 JSONB 列**，且**往返后对象形状一致**——尤其 `position` 的数值类型、`data` 的自由结构、句柄字段的有无。

```bash
# 用 api-ts（bob？这里用 alice 的 A 应用）保存一份带 int 坐标与自由 data 的图
curl -s -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"n-start","type":"start","position":{"x":0,"y":0},"data":{"title":"开始"}},
        {"id":"n-llm","type":"llm","position":{"x":260,"y":160},
         "data":{"title":"LLM","model":"gpt-4o","prompt":"你好","temperature":0.7}},
        {"id":"n-end","type":"end","position":{"x":0,"y":320},"data":{}}
      ],"edges":[
        {"id":"e1","source":"n-start","target":"n-llm"},
        {"id":"e2","source":"n-llm","target":"n-end","sourceHandle":null,"targetHandle":null}
      ]}' > /dev/null

# 用 api-py（同一 bob 的 token）读同一应用的图 —— 应返回**同一条**（形状一致）
curl -s http://127.0.0.1:8000/apps/$APP_ID/graph -H "Authorization: Bearer $PY_TOKEN"
```

**预期输出（实测）**

```json
{"version":"1","nodes":[
  {"id":"n-start","type":"start","position":{"x":0,"y":0},"data":{"title":"开始"}},
  {"id":"n-llm","type":"llm","position":{"x":260,"y":160},
   "data":{"title":"LLM","model":"gpt-4o","prompt":"你好","temperature":0.7}},
  {"id":"n-end","type":"end","position":{"x":0,"y":320},"data":{}}],
 "edges":[
  {"id":"e1","source":"n-start","target":"n-llm"},      // api-ts 存时未带句柄，往返后**仍无**句柄键
  {"id":"e2","source":"n-llm","target":"n-end","sourceHandle":null,"targetHandle":null}
]}
```

**结果解读**（三个「形状一致」点）：

- **`position` 的数值类型保持**：`x:0` / `x:260` 是 `int`，往返后仍是 `int`（api-py 的 `NodePosition` 用 `int | float` 显式接受两者并原样保留，避免 `1 → 1.0` 漂移）。
- **`data` 自由结构原样保留**：`temperature: 0.7`（未在契约声明）也能存下并读回——契约对 `data` 是 `additionalProperties: true`。
- **可选句柄字段「有则保留、无则不造」**：`e1` 请求体里没写句柄，往返后**仍没有**这两个键；`e2` 写了 `null`，往返后**仍是** `null`。两端实现不同（TS 用 `?? null` 归一、Py 用 `exclude_unset`），但**对外形状一致**。

> 这就是「**同一张表、同一列**」在数据层的直接证据：api-ts 写入，api-py 读出（含同一条 `id`），且**对象形状逐键一致**。

## 4. 【技术讨论 1】阶段 3：从 CRUD 进入编排引擎的转折点

**问题**：前两个阶段的接口都是**典型 CRUD**（`/auth/*`、`/apps`）——资源是**结构化记录**，后端逐字段校验、逐列落库。阶段 3 的图为什么要「原样存、只校验、不执行」？

**答案的一句话**：**图 = 数据**。到了阶段 3，后端第一次面对一个**内部结构对后端不透明**的**文档型资源**——它不再解释节点的含义，只做两件事：**存取**与**校验**。真正的「把图跑起来」留给阶段 4 的执行引擎。

**分层的职责边界**

| 层 | 阶段 2（CRUD） | 阶段 3（图 = 数据） |
| --- | --- | --- |
| 存储 | 逐列（`name` / `mode` / ...），ORM 逐字段映射 | **整块 JSONB 文档**（`graph_json`），ORM 只当「一个 JSON 字段」 |
| 校验 | 字段级：必填 / 长度 / 枚举 / 额外字段 | **两层**：① 结构（同上）② **语义**（`validateGraph` 纯函数 7 规则：版本、id 唯一、恰一个 start、至少一个 end、边端点存在、禁自环） |
| 语义 | 无（CRUD 无「业务规则」） | **有**：图作为「一份流程」必须自洽 |
| 执行 | 无 | **无**——执行是**阶段 4** 的事 |

**为什么这样切（设计取舍）**

1. **让「图」成为一等公民的**数据**，而不是「后端的一组表」**：前端编辑器、后端存取、阶段 4 的执行引擎，三者吃的是**同一份**契约 `Graph`。存入的是**整块文档**，读出的也是同一份——前端刷新后能 1:1 复现（L9）。
2. **校验与执行解耦**：本阶段只保证「**存的图是自洽的**」；至于「怎么把 `Graph` 编译成 LangGraph `StateGraph`、怎么跑出流式输出」，是执行引擎的职责。这样，**执行引擎换实现（LangGraph.js ↔ LangGraph Python）不影响存取层**。
3. **契约先行**：`GraphNode` / `GraphEdge` / `Graph` 在 `openapi.yaml` 钉死（含 `type` 的 `enum: [start, end, llm]`、`additionalProperties: false`）。前端、两套后端、以及未来的引擎，都以它为准。

> 一句话：阶段 2 结束时，后端会「增删改查**一条记录**」；阶段 3 结束时，后端会「存取与校验**一张图**」——**它就是编排引擎的接口层**，执行引擎在阶段 4 接到它后面。

## 5. 【技术讨论 2】「契约一致」在阶段 3 新增的层次

> 回顾：阶段 0 · 08 把「契约一致」拆成两层——① **结构一致**（字段集合/名/类型/必填/允不许多余字段）；② **值规范一致**（取值格式/精度/大小写/时间基准）。阶段 2 · 07 把错误信封与值规范层收口（错误文案、时间戳）。

阶段 3 在**图**这一新资源上，把「一致」推进了两步：

### 5.1 新增层次 A：**业务校验文案的逐字节一致**（7 组全通过）

- 结构校验（DTO / Pydantic）只能表达「**形状**」约束——它管不了「图里有几个 `start` 节点」「某条边是不是自环」这类**语义**规则。
- 因此两端各自**手写一份纯函数**做语义校验，并把**规则顺序、遍历顺序、文案模板**全部对齐到唯一真源 `packages/contract/error-messages.md` §3：

  | 端 | 实现 |
  | --- | --- |
  | api-ts | `apps/api-ts/src/graph/graph.validator.ts::validateGraph` → `BadRequestException(errors.join('; '))` |
  | api-py | `apps/api-py/app/graph/validator.py::validate_graph` → `HTTPException(400, detail="; ".join(errors))` |

- **实测**：7 组非法图（版本 / 节点 id 重复 / start 数 / end 数 / 边 id 重复 / 边端点不存在 / 自环）两端响应体**逐字节相同**，如 `{"statusCode":400,"message":"graph must contain at least one end node","error":"Bad Request"}`。

> 这是「契约一致」的**新高度**：**不只是「同一形状」，而是「同一句话」**——语义校验的**文案**也必须一字不差。

### 5.2 新增层次 B：**JSONB 往返后两端的对象形状一致**

- 图是**自由结构文档**（`data: additionalProperties: true`、`position` 数值、可选句柄），天然容易在往返中**变形**。本阶段对三处做了归一：

  | 维度 | 风险 | 两端的处理 |
  | --- | --- | --- |
  | `position` 数值 | `1` 变 `1.0`（int → float） | api-py 的 `NodePosition` 用 `x: int | float` **原样保留**；api-ts 走原生 JSON number |
  | `data` 自由结构 | 未知键被丢弃 | 契约 `additionalProperties: true`；两端**整块存**，不裁剪 |
  | 可选句柄 | 有无不一 / `null` vs 省略 | 语义等价：两侧都保证「**存下的形状 = 请求体的形状**」（TS `JSON.parse(JSON.stringify(...))`、Py `model_dump(exclude_unset=True)`） |

- **实测**：api-ts 写入 → api-py 读出，`int` 坐标不变、`temperature` 等未声明键保留、句柄「有则保留、无则不造」，**对象形状逐键一致**（L8）。

> 关键认知：**「自由结构」不等于「不管形状」**。正因为 `data` 自由、`position` 是数值、句柄可选，才更需要在**往返**这一步守住「形状不漂移」——否则「同一份契约、两套实现」在数据层就名存实亡。

### 5.3 一句话结论

> 阶段 3 把「契约一致」从**结构层**（OpenAPI schema 可机械校验）推进到**语义层**：**业务校验文案逐字节一致**（手写纯函数对齐 + 双跑验证，7/7）、**JSONB 往返对象形状一致**（数值/自由结构/可选字段）。
> 这再次印证：**契约里写不下的语义规则与自由结构，只能靠「运行期双跑比对」来保证一致**（承 `02-应用管理/07` §4.2）。

## 6. 常见坑汇总（跨阶段 3）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **`version` 不是 `"1"`** | 保存/发布 **400** `graph version must be 1` | 契约固定 `version: "1"`；前端 `buildGraph` 写死 `'1'`，不要传别的值 |
| 2 | **空图读取「看起来不合法」** | 以为空图也能保存；结果 PUT 一个 `{"nodes":[],"edges":[]}` 报 400 | 「草稿为 `NULL`」**读取**时返回合法空图、**不做校验**；但若把这**空图**当请求体 PUT / publish，会因规则 3/4（0 start / 0 end）**不通过**。两件事别混淆 |
| 3 | **Pydantic 3 值枚举文案的切分 bug（已修）** | 非法节点 `type` 曾两端文案不一致 | `GraphNode.type` 是 **3 值枚举** `start/end/llm`。Py 侧从 Pydantic 的「允许取值」生成 `"… must be one of: …"` 时，早期 `_enum_values` 按 `" or "` **切分**，`Literal` 有 3 个及以上取值时就会切错。**已修**：改用**引号正则抽取**，现两端均为 `type must be one of: start, end, llm`（同一文案模板 `enum(a, b, c)`；细节见 `05-FastAPI图模块.md`） |
| 4 | **ReactFlow 连线拖拽落空** | 从连接点拖线，第二条线**落空**、生成不了边 | 节点**实际约 215px 宽** > 200px 网格间距 ⇒ 目标连接点被遮挡；且视口未自适应 ⇒ 目标节点在可视区外。**解决**：列距改 **260px**、给 `<ReactFlow>` 加 `fitView`，先让整图入视口再连线（见 `06` 第 7 节坑 2） |
| 5 | **`onConnect` 忘了 `addEdge`** | 拖出线松手后**什么都不出现** | ReactFlow 只回传 `Connection`，**不替你加边**（见 `06` 第 5.2 节） |
| 6 | **改 `node.data` 改的是原对象** | 检查器输入了、画布标题不刷新 | 必须**不可变更新**（新建节点对象 + 新建 data 对象，见 `06` 第 5.7 节） |
| 7 | **发布的 400** | 点「发布」报错 | 后端**只校验当前草稿**；本页「发布」会**先 `putDraft` 再 publish**，草稿不合法则发布必 400（见 `06` 第 7 节坑 11） |
| 8 | **误把 404 当 bug** | 访问自己的应用图却 404 | 确认用的是**同一个用户**的 token；`App not found`（他资源）与 `Graph not published`（未发布）都是**设计**（L6 / L7） |
| 9 | **未发布就调 `published`** | 报 404 `Graph not published` | 从未 `publish` 过时为 `NULL`；先发布再读 |
| 10 | **重置库后列不在** | 存取报 500 | 迁移未应用；`pnpm --filter @mini-dify/api-ts exec prisma migrate dev`（本题为 `add_app_graph`） |
| 11 | **`localhost` 解析竞态** | `curl` 偶发连不上 | 统一用 `127.0.0.1`（见 `00-项目初始化/08` §7） |
| 12 | **前端未登录进画布页** | 显示 401 而非跳登录 | 进页面先查 token、`null` 或 `401` 就 `router.replace('/login')`（阶段 2 · 06） |

## 7. 本篇复盘与知识点

**一句话总结阶段 3**：在两套后端实现 `/apps/{id}/graph*` 的图存取与校验，把图作为**整块 JSONB 文档**存两态（草稿 / 已发布），用**同一套纯函数规则**保证语义校验文案**逐字节一致**；前端用 ReactFlow 把「**图 = 数据**」可视化，加节点/连线/编辑/保存/刷新/发布全链路跑通。

**本篇学到的工程/架构要点**

1. **阶段 3 是转折点**：从「逐字段 CRUD」进入「**文档型资源 = 图**」——后端**只存取 + 校验**，`执行`留给阶段 4；图的契约（`GraphNode`/`GraphEdge`/`Graph`）成为前端、两套后端、未来引擎的**共同数据**。
2. **分层验收**：契约编译 → JSONB 列 → 两端图接口 → **校验一致（逐字节）** → 发布两态 → 归属隔离 → **跨后端同列一致** → 浏览器，逐层自证。
3. **契约一致新增两层**：**业务校验文案逐字节一致**（手写纯函数对齐 + 双跑，7/7）+ **JSONB 往返对象形状一致**（数值类型 / 自由 data / 可选句柄）。
4. **两态设计**：`graph_json`（草稿）与 `published_graph_json`（发布快照）独立；改草稿不动已发布；未发布读 404。
5. **归属隔离沿用 404**：图接口复用 `/apps` 的归属检查，隐藏资源存在性。

**遗留到下阶段**

- 契约测试双跑自动化：把 §5.1 的「7 组文案逐字节一致」与 §5.2 的「JSONB 往返形状一致」固化成 CI 断言。
- 图**执行**（把 `Graph` 编译成 LangGraph 并流式跑）是**阶段 4** 的主题。

**基础技术要点**：文档型存储（JSONB）· 语义校验纯函数 · 双实现文案对齐 · draft/published 两态 · 归属隔离 · ReactFlow 画布。
