## 1. 本篇目标

做完这一篇，你能：

- 沿**依赖顺序**逐层验收阶段 5：契约编译`0.5.0` → **LLM 依赖就位** → **起 mock + 配环境（无密钥自测）** → 两端跑同一张图得到**真流式** `token` 序列（逐字节一致）→ **6 组错误映射两端一致** → **回归阶段 4 的反向用例**。
- 用**可直接复制的命令**证明两套后端在「真模型调用」上**行为一致**：`token` 序列一致、`node_finished(llm).output` 一致、`run_finished.outputs` 一致、`run_failed.message` 逐字节一致。
- 讲清楚**阶段 5 补齐的是什么**：阶段 4 证明了「**通道**」（事件 / 流式 / 拓扑），阶段 5 才证明「**内容**」（真模型、真分片、真错误）。
- 讲清楚**「真流式」与「假流式」的分界**：桩是自己按码点切；真实现的分片由 **provider** 决定——两端 `token` 序列一致靠的是「**同一个 provider + 同一套映射**」，而不是自己切。
- 讲清楚**外部依赖是本地练习与真实系统的分水岭**：错误分类、超时、重试策略都必须在**契约层面定死**。
- 讲清楚**同一项目里的两套 SSE**：OpenAI 的**分片协议** vs 本项目的 **`/run` 事件协议**（最易混淆点）。

**验收标准（对齐总纲 §6 阶段 5）**

> `llm` 节点能调用真实模型并流式输出；错误可读。

具体化为本文第 3 节**每条命令的「预期输出」都命中**：

## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序（先契约与依赖、后 mock 与环境、再两端一致性、最后错误与回归）

```
L1 契约编译(0.5.0)   L2 依赖就位(langchain-openai)
        ↓                     ↓
L3 起 mock + 配环境（无密钥自测）
        ↓
L4 两端同一张图（真流式 token 序列一致）
        ↓
L5 错误映射 6 组一致 → L6 回归（阶段 4 反向用例）
```

**为什么按这个顺序**：契约不编译 / `LlmNodeData` 不存在，「节点级覆盖全局默认」无从谈起；`langchain-openai` 不在，真实调用无法发起；mock 与 env 就位后，**无需任何真实密钥**就能跑出**确定可预测**的流；两端「内容一致」之后，才谈错误映射与回归。

### 3.3 L3 —— 无密钥自测：起 mock + 配环境

**在哪执行**：仓库根起 mock；env 配到两套后端的 `.env`

**起 mock 桩**（零依赖、OpenAI 兼容；回复确定可预测）：

```bash
node tools/mock-llm/server.mjs
```

**预期输出（实测）**

```
mock-llm listening on http://127.0.0.1:11435/v1/chat/completions
```

**mock 的确定性约定**（`tools/mock-llm/server.mjs`，唯一真源见 `04-mock-LLM与无密钥自测.md`）：

| 约定 | 值 | 说明 |
| --- | --- | --- |
| 端口 | `11435` | 可用 `MOCK_LLM_PORT` 覆盖 |
| 回显 | `echo: ` + **最后一条 user 消息** | 固定前缀 |
| 分片 | **每 5 个 Unicode 码点**一片 | 由 mock 自己决定，供两端逐字节比对 |
| usage | 按消息字符数 / 回显码点数计算 | `prompt_tokens` / `completion_tokens` / `total_tokens` |
| 错误注入 | HTTP 头 `x-mock-status` / `x-mock-delay`，或 user 消息里 `[[mock-status:N]]` / `[[mock-delay:N]]` | 两种等价 |

**结果解读**：mock 让「真实模型调用」的验收**完全离线、无需任何密钥、结果可预测**——这就是「**无密钥自测**」：把**外部依赖**换成一个**确定性桩**，两端仍走**真实的调用路径**（`ChatOpenAI.stream()` / 真 SSE 请求），只是 provider 换成了本地桩。这样，两端 `token` 序列能否逐字节一致，就**只剩「两端映射是否一致」这一个变量**（见第 5 节）。

### 3.4 L4 —— 两端跑同一张图，真流式 `token` 序列逐字节一致

**在哪执行**：任意目录（用 `127.0.0.1`）

**建一个应用并保存一张 `start → llm → end` 的图**：

```bash
APP_ID=$(curl -s -X POST http://127.0.0.1:3001/apps \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"llm-demo","mode":"workflow"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['id'])")

curl -s -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"start_1","type":"start","position":{"x":0,"y":0},
         "data":{"title":"开始","inputs":[{"name":"topic","type":"string","required":true}]}},
        {"id":"llm_1","type":"llm","position":{"x":0,"y":160},
         "data":{"title":"LLM","model":"mock-model","prompt":"Hello {{ inputs.topic }}"}},
        {"id":"end_1","type":"end","position":{"x":0,"y":320},
         "data":{"title":"结束","outputs":[{"name":"result","value":"{{ llm_1.text }}"}]}}
      ],"edges":[
        {"id":"e1","source":"start_1","target":"llm_1","sourceHandle":null,"targetHandle":null},
        {"id":"e2","source":"llm_1","target":"end_1","sourceHandle":null,"targetHandle":null}
      ]}' > /dev/null
```

**两端各发一次运行请求，抓原始流到文件**：

```bash
curl -s -N -X POST http://127.0.0.1:3001/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{"topic":"mini-dify"}}' > ts.sse
curl -s -N -X POST http://127.0.0.1:8000/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"inputs":{"topic":"mini-dify"}}' > py.sse

# 事件名序列逐项比对
grep '^event:' ts.sse | sed 's/^event: //' > ts.names
grep '^event:' py.sse | sed 's/^event: //' > py.names
diff ts.names py.names && echo "SEQUENCE IDENTICAL"

# 归一后整帧比对（抹掉 runId / elapsedMs）
sed -E 's/"runId":"[^"]*"/"runId":"X"/g; s/"elapsedMs":[0-9]+/"elapsedMs":N/g' ts.sse > ts.norm
sed -E 's/"runId":"[^"]*"/"runId":"X"/g; s/"elapsedMs":[0-9]+/"elapsedMs":N/g' py.sse > py.norm
diff ts.norm py.norm && echo "FRAMES IDENTICAL"
```

**预期输出（实测·两端相同）**

```
SEQUENCE IDENTICAL
FRAMES IDENTICAL
```

**事件名序列（两端一致，共 12 帧）**

```
run_started
node_started
node_finished
node_started
token ×5
node_finished
node_started
node_finished
run_finished
```

**`token` 序列（两端**逐字节一致**）**

```
data: {"nodeId":"llm_1","text":"echo:"}
data: {"nodeId":"llm_1","text":" Hell"}
data: {"nodeId":"llm_1","text":"o min"}
data: {"nodeId":"llm_1","text":"i-dif"}
data: {"nodeId":"llm_1","text":"y"}
```

即 `["echo:"," Hell","o min","i-dif","y"]`，拼接得 `"echo: Hello mini-dify"`。

**`node_finished(llm).output`（两端一致）**

```json
{"text":"echo: Hello mini-dify","model":"mock-model","usage":{"promptTokens":15,"completionTokens":21,"totalTokens":36}}
```

**`run_finished.outputs`（两端一致）**

```json
{"result":"echo: Hello mini-dify"}
```

**结果解读（三个关键点）**：

- **分片由 provider 决定**：`"echo: Hello mini-dify"` 共 21 个码点，mock 按**每 5 码点**切 → 5 片（`echo:` / ` Hell` / `o min` / `i-dif` / `y`）。注意**这不是两端切的**，而是 mock 切的；两端只是**原样转发**每个 `chunk.content`（承 `sse-events.md` §4：`token.text` 是 **provider 的真实流式片段**）。所以两端要一致，靠的是「**同一个 provider + 同一套映射**」（见第 5 节）。
- **渲染 + 回显**：`prompt = "Hello {{ inputs.topic }}"`，`pool.inputs.topic = "mini-dify"` → user 消息 `"Hello mini-dify"`；mock 把它回显并加前缀 → `"echo: Hello mini-dify"`。
- **`usage` 一致**：`promptTokens = 15`（= 消息字符数 `"Hello mini-dify"`）、`completionTokens = 21`（= 回显码点数）、`totalTokens = 36`。两端都从 `chunk.usage_metadata` 取并映射成同一键名；**provider 不给 usage 时两端都省略 `usage` 字段**。
- **`model` 一致**：节点输出 `model` 为**实际使用的模型名**（`data.model` 非空则用它，否则回退 `LLM_MODEL`）；本例 `data.model = "mock-model"` → 输出 `"mock-model"`。

### 3.5 L5 —— LLM 错误映射 6 组，两端 `run_failed.message` 逐字节一致

**在哪执行**：任意目录
**目的**：这是阶段 5 的一致性核心之一——**外部依赖的错误**必须被归一到**规范文案**，且两端**逐字节相同**；出错时**不发该节点的 `node_finished`**。唯一真源是 `packages/contract/error-messages.md` §5；实现为两端各自的**纯函数**（`apps/api-ts/src/engine/nodes/llm.node.ts::mapLlmError` ↔ `apps/api-py/app/engine/nodes/llm.py::map_llm_error`）。

**统一观察方式**：把 `llm` 节点换成一张**单节点（start → llm → end）**、`prompt` 里带注入标记的图，运行后看流尾。以 **G2（401）** 为例：

```bash
# 换一张 prompt 含注入标记的图（图本身合法，错误由 provider 在运行期制造）
curl -s -X PUT http://127.0.0.1:3001/apps/$APP_ID/graph \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"version":"1","nodes":[
        {"id":"start_1","type":"start","position":{"x":0,"y":0},
         "data":{"title":"开始","inputs":[]}},
        {"id":"llm_1","type":"llm","position":{"x":0,"y":160},
         "data":{"title":"LLM","model":"mock-model","prompt":"[[mock-status:401]]"}},
        {"id":"end_1","type":"end","position":{"x":0,"y":320},
         "data":{"title":"结束","outputs":[{"name":"result","value":"{{ llm_1.text }}"}]}}
      ],"edges":[
        {"id":"e1","source":"start_1","target":"llm_1"},
        {"id":"e2","source":"llm_1","target":"end_1"}
      ]}' > /dev/null

# 两端运行（HTTP 仍 200；错误在流内的 run_failed）
curl -s -N -X POST http://127.0.0.1:3001/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' -d '{"inputs":{}}'
curl -s -N -X POST http://127.0.0.1:8000/apps/$APP_ID/run \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' -d '{"inputs":{}}'
```

**预期输出（实测·两端逐字节相同）**

```
event: run_started
data: {"runId":"…","appId":"<APP_ID>"}
event: node_started
data: {"nodeId":"start_1","nodeType":"start"}
event: node_finished
data: {"nodeId":"start_1","nodeType":"start","output":{"inputs":{}}}
event: node_started
data: {"nodeId":"llm_1","nodeType":"llm"}
event: run_failed
data: {"runId":"…","nodeId":"llm_1","message":"llm request unauthorized"}
```

> **注意流尾**：`node_started(llm_1)` 之后**直接** `run_failed`，**没有** `llm_1` 的 `node_finished`。这是契约要求（`sse-events.md` §4 / `error-messages.md` §5）——出错节点**不透出** `node_finished`。

**6 组错误（触发方式 → 两端一致的 `message`）**

| 组 | 触发方式 | `run_failed.message` |
| --- | --- | --- |
| G1 未配置密钥 | 把两端 `.env` 的 `LLM_API_KEY` **置空**并重启后端 | `llm provider not configured: LLM_API_KEY` |
| G2 未授权 | mock 注入 `[[mock-status:401]]`（403 同） | `llm request unauthorized` |
| G3 限流 | mock 注入 `[[mock-status:429]]` | `llm rate limited` |
| G4 其它 HTTP | mock 注入 `[[mock-status:500]]` | `llm request failed: 500` |
| G5 超时 | mock 注入 `[[mock-delay:10000]]`，`LLM_TIMEOUT_MS=3000`（延迟 > 超时） | `llm request timed out` |
| G6 无法归类 | `LLM_BASE_URL` 指向**不可达端口**（如 `http://127.0.0.1:9/v1`）并重启后端 | `llm request failed: unknown` |

**结果解读（三个一致点）**：

- **映射规则两端一致**：状态码优先（401/403 → unauthorized；429 → rate limited；其它 → `llm request failed: {statusCode}`），其次超时，最后归入 `unknown`。两端实现分别是 `mapLlmError`（TS 读 `error.status`）与 `map_llm_error`（Py 读 `status_code` / `status`），**规则与文案模板逐条对齐**。
- **不透出库的原始 message**：provider 的原始错误文案（如 `Incorrect API key provided`）**绝不**外泄——否则两端渲染的库版本差异会破坏逐字节一致。
- **出错不发 `node_finished`**：6 组一致；`run_failed` 的 `nodeId` 为出错节点（无法归属时为 `null`）。
- **注入绕法**：LangChain 的 `ChatOpenAI` **不允许自定义请求头**，所以 mock 支持**第二种等价的注入方式**——把 `[[mock-status:N]]` / `[[mock-delay:N]]` 写进 **user 消息内容**（即 `llm.data.prompt`），mock 从最后一条 user 消息里解析（见 `04-mock-LLM与无密钥自测.md`）。

> G1 / G6 需要改 `LLM_BASE_URL` / `LLM_API_KEY` 并**重启后端**（env 启动时读取），其余组只需改图、无需重启。

## 4. 【技术讨论 1】阶段 5 补齐的是什么：从「通道」到「内容」

**问题**：阶段 4 已经把图**跑起来**了（真 SSE、真事件序列、真流式分片），阶段 5 的 `llm` 节点到底「新」在哪？

**答案的一句话**：**阶段 4 证明了「通道」，阶段 5 才证明「内容」。** 阶段 4 的 `llm` 是**桩**（渲染 prompt 后按 8 码点切分，不调真实模型）——事件、流式、拓扑（**通道**）都对；阶段 5 把桩换成**真模型**（**真模型、真分片、真错误**），才证明「**内容**」经得起外部依赖。

| 层 | 阶段 4（通道） | 阶段 5（内容） |
| --- | --- | --- |
| 输入 | `Graph` + `RunRequest.inputs` | 同（契约不变） |
| `llm` 核心动作 | 渲染 prompt → **回显**（桩） | 渲染 prompt → **调 provider**（真） |
| `token` 来源 | **自己按 8 码点切** | **provider 的真实分片** |
| `llm` 输出 | `{ text }` | `{ text, model, usage? }`（usage 由 provider 给） |
| 错误来源 | 模板 / 输入 | **+ 外部依赖错误**（6 类归一） |
| 不变式 | 「同一图、两套引擎、同一条事件序列」 | 「**同一 provider、两端逐字节一致**」 |

**为什么这样切**：阶段 4 的所有验证（事件序列 / 帧格式 / 分片）都建立在「**行为可控**」之上——桩的分片由**自己**决定，所以两端只要切法相同就一致。阶段 5 引入了**不可控的外部依赖**，于是必须回答一批**通道时代不必回答的问题**：provider 的分片是谁切的？usage 拿不到怎么办？401 / 429 / 超时分别怎么归类？——**这些正是「内容」的验收对象**。

> 一句话：**阶段 4 结束时，系统会「把图跑成一条流」；阶段 5 结束时，系统会「把图跑成一条带着真实模型输出与可读错误的流」。** 从「通道」到「内容」，是阶段 5 的关键增量。

## 5. 【技术讨论 2】「真流式」与「假流式」的分界

**问题**：阶段 4 的桩也发 `token`、也是「边算边发」；阶段 5 也是发 `token`。两者到底差在哪？为什么阶段 5 的 `token` 序列还能**逐字节一致**？

**答案的一句话**：**分界在于「分片是谁切的」。** 假流式（桩）：**自己**按固定码点数切；真流式（阶段 5）：分片由 **provider** 决定，两端**只做转发**。

| 维度 | 假流式（阶段 4 桩） | 真流式（阶段 5） |
| --- | --- | --- |
| 分片决策者 | **引擎自己**（每 8 个码点） | **provider**（本例 mock 每 5 码点；真实 OpenAI 由模型 token 决定） |
| 两端一致的前提 | 「两端切法相同」（都按 8 码点） | 「**同一 provider + 同一套映射**」（都原样转发 `chunk.content`） |
| `token.text` 语义 | 引擎造的切片 | **provider 的真实流式片段**（`sse-events.md` §4 已明确） |
| 可预测性 | 完全可预测 | 取决于 provider（mock 使其可预测） |

**两端为什么还能逐字节一致**

- 一致性**不再来自「自己怎么切」**，而来自两个**共同变量**：
  1. **同一个 provider**：两端打的是**同一个** mock（`:11435`），provider 切出的片段对两端**是同一串**；
  2. **同一套映射**：两端都「逐 chunk 取 `chunk.content`（字符串化）→ **立即**发 `token`」，**不合并、不重切、不缓存**。
- 于是「真流式」的验收，本质是验证**转发逻辑两端一致**——把「切法」这个变量交给 provider 固定住，剩下的就只剩「两端怎么写」。

**「边收边发」的工程含义**

- `client.stream()` / `client.astream()` 返回**异步可迭代的 chunk**：每收到一片，**立即** `emitToken`，而不是「收完整段再切」。这才叫**真流式**（**边收边发**）。
- 对照 `ChatOpenAI.invoke()`（**非流式**）：它只在**收完整段后**返回一个 `AIMessage`。用它就只能「假流式」（整段拿到后自己切）——阶段 5 **坚持 `stream`**，就是为了让 `token` 与 provider 的节奏**同频**。

> 一句话：**假流式是「引擎假装在流」，真流式是「provider 真在流、引擎只做转发」。** 两端一致的地基，从「切法约定」换成了「**同一 provider + 同一映射**」。

## 6. 【技术讨论 3】外部依赖：本地练习与真实系统的分水岭

**问题**：阶段 4 除了 `start` / `end`（纯计算）就没有别的东西；阶段 5 第一次引入**真正的外部系统**（LLM provider）。这带来的**认知**是什么？

**答案的一句话**：**一旦系统里出现「不属于你、会失败、会超时、有配额」的外部依赖，你就必须为它的每一种失败都定好策略**——而策略必须在**契约层面定死**，否则「两套实现行为一致」直接破产。

**外部依赖带来的四类新问题（阶段 5 全部面对）**

| 问题 | 若不处理会怎样 | 阶段 5 的处理 |
| --- | --- | --- |
| **错误分类** | 两端各透出库的原始 message → 逐字节不一致；消费者无法按类别处理 | 6 类**规范文案**（`error-messages.md` §5），纯函数两端对齐 |
| **超时** | 请求永久挂起、连接堆积 | `LLM_TIMEOUT_MS` 统一超时（两端同键）→ 归一为 `llm request timed out` |
| **重试** | 两端重试次数不同 → 行为/耗时不一致 | **`maxRetries = 0`**（见下） |
| **密钥 / 端点** | 硬编码进仓库 → 泄露；写死端点 → 无法切 provider | 全走 env（`LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`），密钥**不进仓库** |

**`maxRetries = 0` 的对齐取舍（重点）**

- LangChain 的 `ChatOpenAI` 默认带**自动重试**（`AsyncCaller`，默认重试多次）。这在本项目里是**必须关掉**的：
  1. **两端不会同步**：TS 与 Py 的重试实现/次数/退避不同 → 同一失败在两端表现为不同耗时、不同最终错误，**逐字节一致无从谈起**；
  2. **错误会「挂起」**：5xx / 超时被静默重试多次 → 单次运行长时间不出 `run_failed`，验收与体验都糟。
- 因此两端**都显式 `maxRetries: 0` / `max_retries=0`**：**一次请求、一次失败、一次归一**。重试作为**上层策略**（未来阶段）单独设计，而不是藏在库的默认值里。

**「外部依赖 = 分水岭」的最终体会**

- **本地练习**里，你只面对「自己写的代码」——行为完全可控。
- **真实系统**里，你要面对「别人的服务」——它**会失败**（网络、配额、超时、鉴权）。**能不能把它的所有失败都收编成一套你说了算的规范**，正是「demo」与「产品」的分水岭。
- 这也是为什么阶段 5 先做 **mock**：把「外部依赖」先换成**确定性桩**，把**映射逻辑**验透；等映射稳定了，再指向真实 provider（换 `LLM_BASE_URL` / `LLM_API_KEY` 即可，**代码不动**）。

> 一句话：**阶段 5 第一次让「别人的服务」成为系统的一部分；而从这一刻起，凡是「别人的服务会犯错的地方」，都必须由「你的契约」说了算。**

## 7. 【技术讨论 4】同一项目里的两套 SSE：最易混淆点

**问题**：一提到 SSE，本项目里有**两处**都在用——它们长得像，但**根本不是一回事**。混淆它们会踩什么坑？

**答案的一句话**：**一套是「我们对外吐」的事件协议（`/run`），一套是「provider 对我们吐」的分片协议（OpenAI）**——**方向相反、格式不同、消费方不同**。

| 维度 | 本项目 `/run` 事件协议 | OpenAI 分片协议（provider → 我们） |
| --- | --- | --- |
| 方向 | **我们 → 前端**（我们是**生产者**） | **provider → 我们**（我们是**消费者**） |
| 唯一真源 | `packages/contract/sse-events.md` | OpenAI 官方格式（`chat.completion.chunk`） |
| 帧内容 | `event: <name>` + `data: {…业务事件…}` | 只有 `data: {…chunk…}` + 结尾 `data: [DONE]` |
| 事件语义 | `run_started` / `node_started` / `token` / `node_finished` / `run_finished` / `run_failed` | `choices[].delta.content` 逐片增量 + 末尾 `usage` |
| 谁定义「分片」 | 由 provider 决定（阶段 5 起） | **就是它**（`delta.content` 就是分片） |
| 消费方 | 前端 `fetch + getReader`（`06`） | 后端 `ChatOpenAI.stream()`（LangChain 解析） |

**为什么最容易混**

- **两种都叫「SSE」、都叫 `token`、都在流**。但 `/run` 的 `token` 是**业务事件**（带 `nodeId`），而 OpenAI 的 `delta.content` 是**协议分片**（无 `nodeId`）——**`llm` 节点做的就是「把后者翻译成前者」**：读 OpenAI 的每个 `delta.content` → 发一条 `/run` 的 `token`。
- **格式规范不同**：`/run` 帧固定为 `event: …` + `data: …`（`sse-events.md` §1）；OpenAI 帧**只有** `data: …`（`event:` 行通常省略），且以 `data: [DONE]` 收尾（`tools/mock-llm/server.mjs` 就照此实现）。
- **别把两套解析器通用**：前端的 `parseSseStream`（`apps/web/app/apps/[id]/sse.ts`）是给 **`/run` 协议**写的——**不要**拿它去解析 provider 的流；provider 的流由 **LangChain 负责解析**。

> 一句话：**`/run` 是「我们对外的事件协议」，OpenAI 是「provider 对我们的分片协议」；`llm` 节点就是这两套 SSE 之间的翻译层。** 认清「谁生产、谁消费」，就不会把两套协议搅在一起。

## 8. 常见坑汇总（跨阶段 5）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **`LLM_API_KEY` 为空** | 运行即 `run_failed llm provider not configured: LLM_API_KEY` | 节点在构造 client 前先检查密钥；本地自测填**非空**（如 `test`）即可（`03`） |
| 2 | **忘了重启后端** | 改了 `.env` 却仍打旧端点 / 旧超时 | 两端 env 在**启动时**读取（TS `process.env`、Py `settings` 实例化于模块导入）；改完**必须重启**（`01`） |
| 3 | **以为 `token` 是两端切的** | 对不上时去改「切分码点数」 | 阶段 5 起 `token` 是 **provider 分片**，两端只**转发**；要改的是「映射」与「provider」，不是切法（第 5 节） |
| 4 | **provider 不透出 usage** | `node_finished(llm).output` 里**没有** `usage` 键 | 这是**设计**：provider 未给 usage 时**省略** `usage`（契约 `usage?` 可选，两端一致）；不要硬造 0（`01` / `sse-events.md` §4） |
| 5 | **库的默认重试把错误「吃」了** | 5xx / 超时长时间不出 `run_failed`，或两端耗时不一 | `ChatOpenAI` 默认自动重试；两端**都** `maxRetries: 0` / `max_retries=0`（第 6 节） |
| 6 | **用 `invoke` 而非 `stream`** | `token` 一次性整段出现 / 只有一帧 | `invoke` 不流式；要「边收边发」必须 `stream` / `astream`（第 5 节） |
| 7 | **注入错误时给 LangChain 加自定义头** | 报「客户端不支持自定义头」/ 注入不生效 | LangChain `ChatOpenAI` **不允许自定义头**；改用**第二种注入**——把 `[[mock-status:N]]` / `[[mock-delay:N]]` 写进 user 消息（= `prompt`）（`04`） |
| 8 | **超时没生效** | 注入 `[[mock-delay:10000]]` 却等到 10s 后**成功**返回 | `LLM_TIMEOUT_MS` 必须 **< 注入延迟**（本例 `3000 < 10000`）（`03`） |
| 9 | **把 provider 的 SSE 当 `/run` 解析** | 手势解析 provider 流、字段对不上 | 两套 SSE **不同协议**：provider 流交给 LangChain；`/run` 流才用前端 `parseSseStream`（第 7 节） |
| 10 | **出错却期望有 `node_finished`** | 等不到 `node_finished` 以为卡住 | 契约规定：`llm` 节点出错时**不发** `node_finished`，直接 `run_failed`（`sse-events.md` §4 / 第 3.5 节） |
| 11 | **`localhost` 解析竞态** | `curl` / 后端偶发连不上 mock | 统一用 `127.0.0.1`（见 `00-项目初始化/08` §7） |
| 12 | **mock 端口被占** | `EADDRINUSE` | 改 `MOCK_LLM_PORT`（如 `MOCK_LLM_PORT=11436`），并同步改两端 `LLM_BASE_URL`（`04`） |

## 9. 本篇复盘与知识点

**一句话总结阶段 5**：把阶段 4 的 `llm` **桩**换成**真实模型调用**（LangChain `ChatOpenAI` + `.stream()` 边收边发），`token` 由 **provider** 分片、两端**原样转发**，故逐字节一致；把**外部依赖的每一种失败**收编为 6 条**规范文案**（命中 `run_failed`、不发 `node_finished`）；用一个零依赖 mock 实现了**无密钥、确定性**的自测与验收。

**本篇学到的工程/架构要点**

1. **从「通道」到「内容」**：阶段 4 证明通道（事件 / 流式 / 拓扑），阶段 5 证明内容（**真模型、真分片、真错误**）。
2. **真 / 假流式的分界在「谁切分片」**：假流式是引擎自己切；真流式由 **provider** 决定——两端一致靠「**同一 provider + 同一映射**」。
3. **外部依赖是分水岭**：错误分类 / 超时 / 重试 / 密钥都必须在**契约层面**定死（6 条文案 + `maxRetries: 0` + env 配置）。
4. **同一项目里的两套 SSE**：`/run` 事件协议（我们→前端）vs OpenAI 分片协议（provider→我们）；`llm` 节点是**翻译层**。
5. **mock 是工程手段**：把不确定的外部依赖换成**确定性桩**，把「映射正确性」从「依赖是否可用」里**隔离出来**单独验证。
6. **分层验收**：契约编译 → 依赖就位 → 起 mock/配环境 → **两端同一张图（token 序列一致）** → **错误映射 6 组一致** → 回归，逐层自证。

**遗留到下阶段**

- 契约测试双跑自动化：把本文 L4（`token` 序列一致）/ L5（6 组错误文案一致）固化成 CI 断言。
- **真实 provider 对接**：把 `LLM_BASE_URL` / `LLM_API_KEY` 指向真实 OpenAI（或兼容）服务，代码零改动即可切换（本阶段 mock 与真实 provider 走**同一条代码路径**）。
- 更丰富的 LLM 能力（工具调用 / 结构化输出 / 多轮流式）留给后续阶段。

**基础技术要点**：LangChain `ChatOpenAI` / `.stream()` 真流式 · provider 分片 vs 自切片 · 外部依赖错误归一（6 类）· `maxRetries: 0` · env 配置与密钥管理 · mock 外部依赖做无密钥自测 · 两套 SSE 协议辨析。
