# 02 · 真实模型调用与流式

> 所属：阶段 5 · LLM 节点
> 本篇覆盖：把 `llm` 节点从「本地切片的桩」换成**真实模型调用**——两端分别实现 `apps/api-ts/src/engine/nodes/llm.node.ts` 与 `apps/api-py/app/engine/nodes/llm.py`：用 LangChain `ChatOpenAI` 调 OpenAI 兼容 provider、`.stream()` / `.astream()` 逐 chunk **立即**发 `token`、累积全文作为节点输出 `{ text, model, usage? }`、把调用错误归一为规范文案走 `run_failed`。**两端逐条对照**。
> **本篇首次教学：① `ChatOpenAI`（LangChain 封装）的用法（`baseURL` / `apiKey` / `model` / `temperature` / `maxTokens` / `timeout` / `maxRetries`）与**为什么用 LangChain 封装而不是裸 HTTP**；② **真实的流式**——`.stream()` 逐 chunk 取增量并**立刻**发 `token`，讲清「累积全文」与「边收边发」的区别（真流式 vs 假流式的分水岭）；③ **`usage` 从哪里来**，以及有些 provider 流式时**不给 usage** 的现实；④ **阶段 4 的桩 vs 阶段 5 的真**——桩是「按 8 码点切」，真是「provider 决定分片」，所以**两端的 token 序列一致靠的是「同一个 provider」而不是「自己切」**；⑤ **一个真实踩坑**：LangChain JS 内部 `AsyncCaller` 默认重试 6 次，会把 5xx / 超时拖到 30 秒以上，为对齐两端显式设 `maxRetries` / `max_retries = 0`**

## 0. 阶段 5 的立论：桩 → 真模型

阶段 4 的 `llm` 节点是**桩**：它把 `prompt` 渲染后，**自己**按每 8 个 Unicode 码点切一片、逐片发 `token`（见 `04-执行引擎/03-节点运行时与变量池.md` §8）。它把**流式通道**打通了，但片是**本地造的**。

阶段 5 换成**真实模型调用**：

```
阶段 4：prompt ──本地每 8 码点切──▶ token 事件（片 = 自己切的）
阶段 5：prompt ──ChatOpenAI 流式──▶ provider 吐增量 ──逐 chunk 转发──▶ token 事件（片 = provider 的）
```

关键的不同，就一句话：**片从「自己切」变成「provider 给」**。这一句改变了两端的对齐依据（见 §11）——桩模式下两端「因为算法相同」而一致；真模型下两端「**因为连同一个 provider、发同一个请求**」而一致。

> 本篇是**两端对照篇**：TS（`llm.node.ts`）与 Python（`llm.py`）逐条对应，讲清「同一套语义、两种语法」。

## 1. 本篇目标

- 让两端 `llm` 节点**真实调用**一个 OpenAI 兼容 provider：`ChatOpenAI` + `base_url` / `api_key` / `model` / `timeout`。
- 用 `.stream()` / `.astream()` 做**真流式**：每收到一个 chunk，**立即**发 `token`（`text` = provider 的真实增量），同时**累积全文**。
- 节点输出 `{ text, model, usage? }`：`model` 为**回退后**的实际模型名；`usage` 有则带、无则省（§10）。
- 把调用错误归一为规范文案（`mapLlmError` / `map_llm_error`，见 `error-messages.md` §5），走 `run_failed`，**不**发该节点 `node_finished`。
- 显式关闭重试（`maxRetries: 0` / `max_retries=0`），让两端**错误行为一致**（§12）。

**验收标准**

1. 用本地 mock provider（`LLM_MODEL=mock-model`）跑一张 `start → llm → end` 的图，两端都得到 `token` 序列 **`["echo:", " Hell", "o min", "i-dif", "y"]`**（拼接为 `"echo: Hello mini-dify"`），**两端逐字节一致**。
2. `node_finished(llm).output` 两端一致为：
   ```json
   {"text":"echo: Hello mini-dify","model":"mock-model","usage":{"promptTokens":15,"completionTokens":21,"totalTokens":36}}
   ```
3. `run_finished.outputs` 两端一致为 `{"result":"echo: Hello mini-dify"}`。
4. 整条 SSE 流**除 `runId` / `elapsedMs` 外逐字节相同**。
5. 触发错误（如 mock 注入 401）时两端都得到**同一条**规范文案，走 `run_failed`。

> 验收不需要真实密钥——用仓库自带的 mock（`tools/mock-llm/server.mjs`）即可（见 §4、§15）。

```
apps/api-ts/src/engine/nodes/
   └── llm.node.ts     ← 真实模型调用（TS）：ChatOpenAI + .stream() + mapLlmError     （本篇 §6）

```

**执行时序**（`llm` 节点内部）：

```
node_started(llm)  ← 执行器发（见 04-执行引擎 系列）
  │
  ├─ 读 data（LlmNodeData）、渲染 prompt（模板 → 变量池）
  ├─ model = data.model || LLM_MODEL       ← 回退（见 01 篇）
  ├─ 建 ChatOpenAI（base_url / key / timeout / maxRetries=0 …）
  ├─ 组装 messages：[SystemMessage?] + HumanMessage(prompt)
  └─ for await chunk of client.stream(messages):
        piece = stringifyContent(chunk.content)     ← 字符串化（§8.4）
        if piece ≠ "":  text += piece; emitToken(piece)   ← 累积 + 立刻发（§9）
        读 chunk.usage_metadata → usage（§10）
  │
输出 { text, model, usage? }
node_finished(llm)  ← 执行器发（带上 output）
```

## 6. 完整代码：TS 侧（llm.node.ts）

**完整文件路径：`apps/api-ts/src/engine/nodes/llm.node.ts`**

```ts
import { HumanMessage, SystemMessage, type BaseMessage, type MessageContent } from '@langchain/core/messages'
import { ChatOpenAI } from '@langchain/openai'
import type { GraphNode, LlmNodeData } from '@mini-dify/contract'

import { RunError } from '../events'
import { renderTemplate, type Pool } from '../template'

/**
 * `llm` 节点（阶段 5）：把 `data.prompt` 用池渲染后作为 user 消息，调用 LangChain `ChatOpenAI`。
 *
 * 逐 chunk 取 `chunk.content`（字符串化后）**立即**发 `token` 事件（provider 的真实流式片段），
 * 同时累积全文；节点输出为 `{ text, model, usage? }`（provider 未给 usage 时省略 `usage`）。
 * 任何调用错误都经 `mapLlmError` 归一为规范文案（见 error-messages.md §5），且不透出库原始 message。
 */
export async function runLlmNode(
  node: GraphNode,
  pool: Pool,
  emitToken: (text: string) => void,
): Promise<Record<string, unknown>> {
  const data = node.data as unknown as LlmNodeData
  const apiKey = process.env.LLM_API_KEY ?? ''
  if (apiKey === '') {
    throw new RunError('llm provider not configured: LLM_API_KEY')
  }

  const prompt = renderTemplate(String(data.prompt), pool)
  const model = data.model ? data.model : (process.env.LLM_MODEL ?? '')
  const client = new ChatOpenAI({
    apiKey,
    model,
    configuration: { baseURL: process.env.LLM_BASE_URL ?? 'https://api.openai.com/v1' },
    timeout: Number(process.env.LLM_TIMEOUT_MS ?? 60000),
    // 不重试（LangChain AsyncCaller 默认重试 6 次会让 5xx/超时长时间挂起）；两端一致
    maxRetries: 0,
    ...(typeof data.temperature === 'number' ? { temperature: data.temperature } : {}),
    ...(typeof data.maxTokens === 'number' ? { maxTokens: data.maxTokens } : {}),
  })

  const messages: BaseMessage[] = []
  if (typeof data.system === 'string' && data.system !== '') {
    messages.push(new SystemMessage(data.system))
  }
  messages.push(new HumanMessage(prompt))

  let text = ''
  let usage: { promptTokens: number; completionTokens: number; totalTokens: number } | undefined
  try {
    for await (const chunk of await client.stream(messages)) {
      const piece = stringifyContent(chunk.content)
      if (piece !== '') {
        text += piece
        emitToken(piece)
      }
      const meta = chunk.usage_metadata
      if (meta && typeof meta.input_tokens === 'number') {
        usage = {
          promptTokens: meta.input_tokens,
          completionTokens: meta.output_tokens,
          totalTokens: meta.total_tokens,
        }
      }
    }
  } catch (error) {
    throw new RunError(mapLlmError(error))
  }

  const output: Record<string, unknown> = { text, model }
  if (usage !== undefined) {
    output.usage = usage
  }
  return output
}

/** chunk.content 字符串化：字符串原样；数组拼各 text 部分；其余紧凑 JSON（与 api-py 对齐）。 */
function stringifyContent(content: MessageContent): string {
  if (typeof content === 'string') {
    return content
  }
  if (Array.isArray(content)) {
    return content
      .map((part) => {
        if (typeof part === 'string') {
          return part
        }
        const text = (part as unknown as { text?: unknown }).text
        return typeof text === 'string' ? text : ''
      })
      .join('')
  }
  if (content === null || content === undefined) {
    return ''
  }
  return JSON.stringify(content)
}

/**
 * 把 LangChain / 底层异常映射为规范文案（规则与 api-py 的 `map_llm_error` 一致，见 error-messages.md §5）。
 * 映射为纯函数：HTTP 状态码优先，其次超时，最后归入 unknown。
 */
export function mapLlmError(error: unknown): string {
  const status = statusCodeOf(error)
  if (status !== null) {
    if (status === 401 || status === 403) {
      return 'llm request unauthorized'
    }
    if (status === 429) {
      return 'llm rate limited'
    }
    return `llm request failed: ${status}`
  }
  if (isTimeout(error)) {
    return 'llm request timed out'
  }
  return 'llm request failed: unknown'
}

/** 取异常的 HTTP 状态码（OpenAI SDK 的 APIError 带 `status`）。 */
function statusCodeOf(error: unknown): number | null {
  if (typeof error === 'object' && error !== null) {
    const status = (error as { status?: unknown }).status
    if (typeof status === 'number') {
      return status
    }
  }
  return null
}

/** 判定是否为超时（OpenAI SDK 的 `APIConnectionTimeoutError` / AbortError，或消息含 timeout）。 */
function isTimeout(error: unknown): boolean {
  if (typeof error !== 'object' || error === null) {
    return false
  }
  const name = (error as { name?: unknown }).name
  if (name === 'APIConnectionTimeoutError' || name === 'TimeoutError' || name === 'AbortError') {
    return true
  }
  const message = (error as { message?: unknown }).message
  return typeof message === 'string' && /timed? ?out|timeout/i.test(message)
}
```

**读法要点**：

- **`emitToken` 是同步回调**（TS 单线程事件循环）：执行器传入 `(text) => queue.emit(token(node.id, text))`（见 `04-执行引擎` 系列）；`llm.node.ts` **不碰队列**，只管「算 + 发片」。
- **空 key 短路**在发请求**之前**：`apiKey === ''` 立刻抛 `RunError`，不出网（§13）。
- **`...（temperature/maxTokens 存在才展开）`**：只把**节点显式设置**的参数传给 provider；没设就不传，走 provider 默认（对应 `01` 篇 §10.1「可选字段」）。
- **`configuration: { baseURL }`**：TS 把 `baseURL` 放在 `configuration` 里透传给底层 OpenAI SDK 客户端（Python 是顶层 `base_url=`，见 §8.2）。
- **`timeout: Number(LLM_TIMEOUT_MS)`**：JS 的 `timeout` 单位是**毫秒**（§8.3）。

## 7. 完整代码：Python 侧（llm.py）

**完整文件路径：`apps/api-py/app/engine/nodes/llm.py`**

```python
"""`llm` 节点（阶段 5）：把 `data.prompt` 用池渲染后作为 user 消息，调用 LangChain `ChatOpenAI`。

逐 chunk 取 `chunk.content`（字符串化后）**立即**经 `emit` 发 `token` 事件
（provider 的真实流式片段），同时累积全文；节点输出为 `{"text", "model", "usage"}`。
任何调用错误都经 `map_llm_error` 归一为规范文案（见 error-messages.md §5），
不透出库的原始 message，与 api-ts 的 `mapLlmError` 规则一致。
"""

import json                                                    # 序列化：把「非字符串」的 chunk 转成紧凑 JSON
from collections.abc import Awaitable, Callable                # 给回调类型 EmitToken 起别名用
from typing import Any

from langchain_core.messages import HumanMessage, SystemMessage   # 具名消息类（≈ 请求里的 role）
from langchain_openai import ChatOpenAI                        # LangChain 对 OpenAI 兼容 chat 客户端的封装

from app.config import settings                                # 配置（llm_api_key / llm_base_url / …）
from app.engine.events import RunError                         # 运行期错误（其 message 走 run_failed）
from app.engine.template import render_template                # 模板渲染（把 {{ inputs.topic }} 换成值）

EmitToken = Callable[[str], Awaitable[None]]                   # 类型别名：emit 是「吃一个字符串、返回可 await 的东西」的函数


async def run_llm_node(                                        # ★ async def：身体里要 await（异步回调 + 异步迭代）
    node: dict[str, Any], pool: dict[str, Any], emit: EmitToken
) -> dict[str, Any]:
    data: dict[str, Any] = node["data"]
    api_key = settings.llm_api_key
    if not api_key:                                            # 空 key 短路：不发网络请求（先于建 client）
        raise RunError("llm provider not configured: LLM_API_KEY")

    prompt = render_template(str(data["prompt"]), pool)        # 用变量池渲染 prompt（模板外文本原样保留）
    model = data.get("model") or settings.llm_model            # `or` 同时覆盖「键不存在」与「空串」→ 回退环境变量
    extra: dict[str, Any] = {}
    if isinstance(data.get("temperature"), (int, float)):      # 只把「显式设置」的可选参数传给 provider
        extra["temperature"] = data["temperature"]
    if isinstance(data.get("maxTokens"), int):
        extra["max_tokens"] = data["maxTokens"]                # ⚠ 键名转 snake_case（TS 是 camelCase maxTokens）

    client = ChatOpenAI(                                       # 建「OpenAI 兼容」客户端
        model=model,
        api_key=api_key,
        base_url=settings.llm_base_url,                        # 顶层 base_url（TS 放在 configuration 内）
        timeout=settings.llm_timeout_ms / 1000,                # ⚠ Python timeout 单位是【秒】：毫秒 ÷ 1000
        # 不重试（与 api-ts 的 maxRetries: 0 对齐，保证错误快速、归一）
        max_retries=0,
        **extra,                                               # `**` 字典解包：把显式参数摊开当关键字参数传
    )

    messages: list[Any] = []
    if isinstance(data.get("system"), str) and data["system"]:
        messages.append(SystemMessage(content=data["system"]))   # 有 system 才加一条
    messages.append(HumanMessage(content=prompt))              # user 消息 = 渲染后的 prompt

    text = ""
    usage: dict[str, int] | None = None
    try:
        async for chunk in client.astream(messages):           # ★ 异步迭代：每轮 await 拿到一个 chunk
            piece = _stringify_content(chunk.content)          # 字符串化（字符串 / 列表 / 其它 → 紧凑 JSON）
            if piece:                                          # 空片跳过（如流首的 role 帧）
                text += piece                                  # ① 累积全文（给 node_finished.output.text）
                await emit(piece)                              # ② 立刻发 token（异步回调 → 入队）
            meta = getattr(chunk, "usage_metadata", None)      # 取 usage；没有该属性 → None（不抛）
            if isinstance(meta, dict) and isinstance(meta.get("input_tokens"), int):
                usage = {
                    "promptTokens": meta["input_tokens"],      # 映射成契约的 camelCase 键
                    "completionTokens": meta.get("output_tokens"),
                    "totalTokens": meta.get("total_tokens"),
                }
    except Exception as error:                                 # 任何调用错误
        raise RunError(map_llm_error(error)) from error        # 归一为规范文案；`from error` 保留「因由」链

    output: dict[str, Any] = {"text": text, "model": model}
    if usage is not None:                                      # 有 usage 才写（无则省，两端同规则）
        output["usage"] = usage
    return output


def _stringify_content(content: Any) -> str:
    """chunk.content 字符串化：字符串原样；列表拼各 text 部分；其余紧凑 JSON（与 api-ts 对齐）。"""
    if isinstance(content, str):
        return content
    if isinstance(content, list):
        parts: list[str] = []
        for part in content:
            if isinstance(part, str):
                parts.append(part)
            elif isinstance(part, dict) and isinstance(part.get("text"), str):
                parts.append(part["text"])
        return "".join(parts)
    if content is None:
        return ""
    return json.dumps(content, ensure_ascii=False, separators=(",", ":"))


def map_llm_error(error: Exception) -> str:
    """把 LangChain / 底层异常映射为规范文案（规则与 api-ts 的 `mapLlmError` 一致）。"""
    status = _status_code(error)
    if status is not None:
        if status in (401, 403):
            return "llm request unauthorized"
        if status == 429:
            return "llm rate limited"
        return f"llm request failed: {status}"
    if _is_timeout(error):
        return "llm request timed out"
    return "llm request failed: unknown"


def _status_code(error: Exception) -> int | None:
    """取异常的 HTTP 状态码（Python openai SDK 的 APIStatusError 带 `status_code`）。"""
    for attr in ("status_code", "status"):
        value = getattr(error, attr, None)
        if isinstance(value, int):
            return value
    return None


def _is_timeout(error: Exception) -> bool:
    """判定是否为超时（`APITimeoutError` / `TimeoutError`，或消息含 timeout）。"""
    if type(error).__name__ in ("APITimeoutError", "TimeoutError", "APIConnectionTimeoutError"):
        return True
    message = str(error).lower()
    return "timed out" in message or "timeout" in message
```

**这段在干什么（按执行顺序）**：

1. **import 与类型别名**：`json`（序列化）、`Awaitable`/`Callable`（给回调起别名）、`HumanMessage`/`SystemMessage`（消息类）、`ChatOpenAI`（客户端）、`settings`（配置）、`RunError`、`render_template`。`EmitToken = Callable[[str], Awaitable[None]]` 是**类型别名**——说明 `emit` 是「吃一个 `str`、返回一个可 `await` 的对象」的函数（≈ TS 里 `type EmitToken = (t: string) => Promise<void>`）。
2. `async def run_llm_node(...)`：**异步函数**。因为身体里要 `await emit(...)` 和 `async for`，**必须**是 `async def`（否则语法错误）。
3. `api_key = settings.llm_api_key` → `if not api_key: raise RunError(...)`：**空 key 短路**，先于建 client、先于出网。
4. `prompt = render_template(...)`：把 `{{ inputs.topic }}` 之类渲染成实际文本。
5. `model = data.get("model") or settings.llm_model`：`data.get("model")` 取不到键返回 `None`（不抛 `KeyError`）；`or` 让「空串也算假」→ **回退**。这 ≈ TS 的 `data.model || LLM_MODEL`。
6. `if isinstance(...)` 两段：把**显式设置**的 `temperature` / `maxTokens` 收进 `extra`；注意 `maxTokens`→`max_tokens` 改名。
7. `ChatOpenAI(...)`：建客户端。`timeout=settings.llm_timeout_ms / 1000`（**毫秒→秒**）；`max_retries=0`；末尾 `**extra` 把 `extra` 的键**摊开**当关键字参数传入。
8. 组装 `messages`：有 `system` 才加 `SystemMessage`，再加 `HumanMessage(prompt)`。
9. `try:` 里 `async for chunk in client.astream(messages):`：**异步迭代**——每轮 `await` 拿一个 chunk。每个 chunk 做「字符串化 → 非空则累积 + `await emit` → 取 usage」。
10. `except Exception as error:` → `raise RunError(map_llm_error(error)) from error`：调用错误**归一**为规范文案；`from error` 保留「哪个原始异常引起的」因果链（便于排查，但不外传）。
11. 组 `output`：`{"text", "model"}`，有 `usage` 才加。返回。

**读法要点（对照 §6）**：

- `settings` 来自 `app.config`（`pydantic-settings`，四个 `llm_*` 键见 `01` 篇 §12.4）；TS 侧直接读 `process.env`。
- **`emit` 是异步回调**（`Awaitable[None]`）：Python 在 `asyncio` 事件循环里，`await emit(piece)`；TS 是同步 `emitToken(piece)`。差别来自两边的**执行模型**，不影响对外输出。
- `max_tokens=...`（Python 用 **snake_case** `max_tokens`；TS 用 camelCase `maxTokens`）。
- `timeout=settings.llm_timeout_ms / 1000`：**Python `timeout` 单位是秒**，故把毫秒÷1000（§8.3）。
- `model = data.get("model") or settings.llm_model`：`or` 同时覆盖「键不存在」与「空串」→ 回退（与 TS 的 `data.model ? data.model : env` 等价）。

## 8. 【技术教学 · 首次】`ChatOpenAI`（LangChain 封装）的用法

### 8.1 是什么

`ChatOpenAI` 是 LangChain 对「OpenAI 兼容 chat 客户端」的封装：把「组装 chat 请求 → 发 HTTP → 解析流式增量」这一套封装成一个对象，暴露 `stream()` / `astream()` 等**统一方法**。TS 在 `@langchain/openai`，Python 在 `langchain-openai`。

### 8.2 两端构造参数对照

| 语义 | TS（`new ChatOpenAI({...})`） | Python（`ChatOpenAI(...)`） | 说明 |
| --- | --- | --- | --- |
| 端点 | `configuration: { baseURL }` | `base_url=...` | TS 放在 `configuration`（透传底层 SDK）；Py 顶层 |
| 密钥 | `apiKey` | `api_key` | 内容同 |
| 模型 | `model` | `model` | 回退后的实际模型名 |
| 温度 | `temperature` | `temperature` | 可选 |
| 最大输出 | `maxTokens` | `max_tokens` | **命名不同**（camelCase vs snake_case） |
| 超时 | `timeout`（**毫秒**） | `timeout`（**秒**） | **单位不同**（§8.3） |
| 重试次数 | `maxRetries: 0` | `max_retries=0` | **默认非 0**，见 §12 |

### 8.3 一个必须记住的跨语言差异：`timeout` 的单位

| | TS `@langchain/openai` | Python `langchain-openai` |
| --- | --- | --- |
| `timeout` 单位 | **毫秒** | **秒** |
| 本项目传值 | `Number(LLM_TIMEOUT_MS ?? 60000)` → 直接是 ms | `settings.llm_timeout_ms / 1000` → 换算成秒 |

**为什么不能都直接传 `LLM_TIMEOUT_MS`**：JS 的 OpenAI SDK 用**毫秒**，Python 的 openai SDK 用**秒**。若 Python 侧忘了 `/1000`，`3000` 会被当成 `3000` 秒（≈50 分钟）——**两端超时行为就不一致了**。所以本项目 Python 侧显式 `/ 1000`，让两端「同一个 `LLM_TIMEOUT_MS`」产生**同一个真实超时**。

### 8.4 为什么用 LangChain 封装，而不是裸 HTTP

「裸 HTTP」= 自己拼 `POST {base_url}/chat/completions`、自己解析 SSE 帧、自己把 `data:` 里的 `delta.content` 拼起来。用 `ChatOpenAI` 的好处：

| 维度 | 裸 HTTP | `ChatOpenAI`（本项目） |
| --- | --- | --- |
| 统一接口 | 每换一个 provider 都要重写请求/解析 | 只改 `base_url`（**OpenAI 兼容**） |
| 与 LangGraph 同族 | 要自己适配 | 已是 LangChain 的 `BaseChatModel`，**与阶段 4 的 LangGraph 同生态** |
| 流式 | 自己分帧 | `.stream()` 直接给 `AsyncIterable<AIMessageChunk>` |
| 消息 | 自己拼 `{role,content}` | `HumanMessage` / `SystemMessage` 具名类 |
| usage | 自己从帧里抠 | `chunk.usage_metadata` 统一取 |

一句话：**「统一接口 + 与 LangGraph 同族 + 将来换 provider 只改一处」**。代价是多一层依赖（§5），换来的是「不重造轮子」。

> 注意：这里选 LangChain **不是**为了「更高级」——是因为它正好把「OpenAI 兼容 + 流式 + usage」这几件本阶段要的事**标准化**了。若只连一家 provider 且要极简，裸 HTTP 也成立；本项目要**一份代码对接多 provider + 与 LangGraph 协同**，所以用封装。

### 8.5 `stringifyContent` / `_stringify_content`：chunk.content 不一定是字符串

`chunk.content` 的类型是 `MessageContent`（TS）/ `Any`（Py），可能是：

- **字符串**（最常见，纯文本增量）→ 原样；
- **数组**（多模态：`[{ type:'text', text:'…' }, …]`）→ 拼各 `text` 部分；
- **`null` / `undefined`** → 空串（**跳过不发**）；
- **其它** → **紧凑 JSON**（`JSON.stringify` / `json.dumps(..., ensure_ascii=False, separators=(",", ":"))`）。

「其它 → 紧凑 JSON」用的是与阶段 4 §9**同一套序列化口径**（`04-执行引擎/03-节点运行时与变量池.md` §9：紧凑 + `ensure_ascii=False`），保证两端逐字节对齐。**「空片不发」**（`if piece !== ''` / `if piece:`）保证了 `token` 事件**只承载真实文本**——空 delta（如流首的 `role` 帧）不会变成一个空 `token`。

## 9. 【技术教学 · 首次】真实的流式：逐 chunk 立刻发 `token`

### 9.1 `.stream()` / `.astream()` 是什么

`ChatOpenAI.stream(messages)`（TS）/ `client.astream(messages)`（Python）返回一个**异步可迭代**，逐块产出 `AIMessageChunk`。每个 chunk 的 `.content` 就是 provider 这一片吐出的文本增量。

```
client.stream(messages)  ──▶  chunk1  ──▶  chunk2  ──▶  chunk3  ──▶  …
                                │            │            │
                                ▼            ▼            ▼
                            emitToken    emitToken    emitToken        ← 一到就发
```

### 9.2 关键：**「累积全文」与「边收边发」是两件事，同时做**

```ts
for await (const chunk of await client.stream(messages)) {
  const piece = stringifyContent(chunk.content)
  if (piece !== '') {
    text += piece           // ← ① 累积：为最终 node_finished.output.text
    emitToken(piece)        // ← ② 立刻发：为过程 token 事件
  }
  // ③ 读 usage（§10）
}
```

| 动作 | 目的 | 输出到哪 |
| --- | --- | --- |
| ① `text += piece` | 得到**全文** | `node_finished(llm).output.text`（一次，结束时） |
| ② `emitToken(piece)` | 让用户**边收边看** | 每个 `token` 事件（多次，过程中） |

**两者缺一不可**：只累积不发 → 等模型全说完才出结果（假流式）；只发不累积 → 拿不到全文、`end` 节点无从取值。

### 9.3 「真流式」与「假流式」的分水岭

| | 假流式（阶段 4 的桩 / 先等全量再本地切） | **真流式（本阶段）** |
| --- | --- | --- |
| 片从哪来 | 先拿到**完整响应**，再本地切开发 | provider **边生成边吐**增量 |
| 首个 token 何时到 | 要等模型把全部说完 | **首字时间（TTFT）** 就能看到 |
| 「边收边发」 | 名义上边发，实则先等全量 | **真的**一到就发 |
| 用户体验 | 长时间空白后一次性刷出 | 逐字浮现 |

分水岭就在 §9.2 的 ②：**每收到一个 chunk 就立刻发**。阶段 4 的桩虽然也发了多次 `token`，但它是「先有全文、再切开」，属于「本地造的流」；本阶段是「provider 生成到哪、就发到哪」。

> 注意：真流式下，`token` 事件的**片数与大小由 provider 决定**——可能一片几个字、也可能一片一个词。**客户端不能假设固定分片**（阶段 4 的「每 8 码点」只是桩的巧合）。

### 9.4 【加厚 · 本篇首次出现的 Python 机制】异步迭代（`async for`）与异步回调（`await emit`）

TS 学习者读 `llm.py` 最容易卡住的两处，一个在「`async for`」、一个在「`await emit`」。这里正面讲透。

**① `async for chunk in client.astream(messages)`——异步迭代**

**术语先立住**：**异步迭代器（async iterator）** = 一个「下一步要用 `await` 才能取出」的对象；**`async for`** = 「反复 `await` 它的下一步，直到它耗尽」。

**是什么**：`client.astream(messages)` 返回一个**异步迭代器**；`async for` 会对它反复做「`await` 取下一个 chunk」，直到抛 `StopAsyncIteration`（即「吐完了」）才停。

**TS 里对应什么**：`for await (const chunk of await client.stream(messages))`——TS 的 `for await...of` 与 Python 的 `async for` **语义完全一样**。

**为什么这么写（讲透）**：provider 是**一片一片**吐 token 的，我们要「一来一片就处理一片」，所以用异步迭代**逐片**拿。**不能用普通 `for`**——`client.astream(...)` 是异步迭代器，普通 `for` 迭代它会报错（异步生成器不可用同步迭代）。这与阶段 4 的桩最大的不同：桩是「先有全文、本地切开」，这里是「provider 吐到哪、拿到哪」。

```python
# 骨架：异步迭代 = 「反复 await 取下一个」
async for chunk in client.astream(messages):   # 每轮 await 一个 chunk
    piece = _stringify_content(chunk.content)  # 处理这一片
    ...
```

**② `await emit(piece)`——异步回调**

**是什么**：`emit` 是**调用方传进来的一个函数**（由执行器造），它负责把这一片文本「发出去」。本项目里它长这样（`apps\api-py\app\engine\engine.py` 的 `_execute_node`）：

```python
async def emit(text: str) -> None:                 # 异步闭包：吃一片文本
    await queue.put(token(node["id"], text))       # 把 token 事件塞进队列
```

**TS 里对应什么**：TS 侧同一个东西是**同步回调** `emitToken: (text) => void`，执行器传的是 `(text) => queue.emit(token(node.id, text))`（见 §6 的 `llm.node.ts`）。

**为什么两端一个同步、一个异步（讲透）**：这不是喜好问题，是**执行模型**决定的——

| | TS | Python |
| --- | --- | --- |
| 队列入队 | `queue.emit(event)` 是**同步**方法（单线程事件循环下入队即刻完成） | `queue.put(event)` 是**协程**，必须 `await` |
| 回调形状 | `emitToken(piece)` 同步调用 | `await emit(piece)` 异步调用 |
| 对外结果 | 一样：一片文本变成一条 `token` 事件 | 一样 |

**所以 `run_llm_node` 必须是 `async def`**：它要 `await emit(...)`、要 `async for`——两处都要求函数种类是异步。

> **分步记**：`async for` 拿到片 → `text += piece`（累积给你的 `node_finished.output.text`）→ `await emit(piece)`（立刻发一条 `token` 事件）→ 继续下一片。**「累积」与「立刻发」是同时做的两件事**（§9.2）。

### 9.5 【加厚 · 与 TS 侧的对照】语言机制（`isinstance` / `getattr` / `**extra` / 异步回调）

上一节讲的两个机制，对上 TS 的习惯写法：

| 语言机制 | TypeScript | Python（本项目） | 关键差异 |
| --- | --- | --- | --- |
| 类型判断 | `typeof x === 'number'` | `isinstance(x, int)` | ⚠ Python 里 **`bool` 是 `int` 的子类**：`isinstance(True, int)` 为 `True`；TS 里 `typeof true === 'number'` 为 `false` |
| 取「可能有、可能没有」的字段 | `obj.x` / `obj?.x`（可能 `undefined`） | `data.get("x")`（dict，取不到→`None`）/ `getattr(obj, "x", None)`（对象，取不到→`None`） | Python 用显式方法取，**不写就会 `KeyError`/`AttributeError`** |
| 展开「额外参数」 | `{ ...extra }` 展开对象 → 传给库 | `**extra` 展开 dict → 当**关键字参数**传入 | Python 的 `**` 是「展开成 `key=value`」，不是「展开进对象」 |
| 回退默认值 | `data.model ? data.model : LLM_MODEL` | `data.get("model") or settings.llm_model` | `or` 把**空串**也当假 → 顺带覆盖「空串」情形（更省事） |
| 回调形状 | 同步 `emitToken(piece)` | 异步 `await emit(piece)` | 执行模型不同（§9.4） |
| 遍历异步流 | `for await (const c of it)` | `async for c in it:` | 写法差一截 |
| 错误因果链 | `new Error(msg, { cause: err })` | `raise RunError(msg) from err` | Python 用 `from err` 保留「因由」 |
| 非字符串值序列化 | `JSON.stringify(x)`（天然紧凑） | `json.dumps(x, ensure_ascii=False, separators=(",", ":"))` | Python 默认带空格、转义中文，**必须显式**给这两个参数才能和 TS 对齐 |

**两个必须记住的点**：

1. **`isinstance(x, int)` 会把 `True` 当成 `int`**：本项目契约里 `temperature`/`maxTokens` 是数字，实际不会传布尔，所以无碍；但写别的校验时要留心这条 Python 特性。
2. **`getattr(chunk, "usage_metadata", None)` 的第三个参数是「默认值」**：`chunk` 若没有该属性就返回 `None`（≈ TS 的 `chunk.usage_metadata ?? null`）。若省掉第三个参数，属性不存在会直接抛 `AttributeError`——这也是为什么读 `usage` 用 `getattr` 而非 `chunk.usage_metadata`。

### 9.6 【加厚】写错会怎样（Python / LLM 流式）

| 错误 | 症状 | 原因 / 正解 |
| --- | --- | --- |
| **对异步迭代器用普通 `for`** | `TypeError: 'async_generator' object is not iterable` | `client.astream(...)` 是**异步**迭代器；必须用 **`async for`**。 |
| **忘记 `await emit(piece)`** | **前端看不到流式**（没有 `token` 帧）；日志 `RuntimeWarning: coroutine '…' was never awaited` | Python 协程**懒惰**：不 `await` 就只造对象、不执行——`token` 事件**根本没入队**。补 `await`。 |
| **在同步 `def` 里写 `async for` / `await`** | 程序**编译不过**：`SyntaxError` | `await` 与 `async for` 只能出现在 `async def`；把函数改成 `async def`。 |
| **忘了 `max_retries=0`** | 遇 5xx/超时被库**重试 6 次**，卡 30 秒以上，且两端耗时不一致 | 显式 `max_retries=0`（§12）。 |
| **Python `timeout` 忘 `/1000`** | 配 `3000` 变成 3000 秒（≈50 分钟） | Python `timeout` 单位是**秒**，JS 是**毫秒**（§8.3）。 |
| **直接读 `chunk.usage_metadata`** | 某 provider 不给 usage 时抛 `AttributeError` | 用 `getattr(chunk, "usage_metadata", None)`，拿不到就当 `None`（有则带、无则省）。 |

> 一句话：**「异步迭代」和「异步回调」是同一个「协程要 `await` 才跑」规则的两个面**。漏 `await` 在 Python 里是**静默失败**（不报错、只是没发生），比 TS 更隐蔽——所以本项目把 `emit` 设计成必须 `await`，让「没发出去」这件事**无处藏身**（配合 §16 的「整流 diff」验收抓出来）。

## 10. 【技术教学 · 首次】`usage` 从哪里来，以及 provider 不给的现实

### 10.1 `usage` 的来源

```ts
const meta = chunk.usage_metadata
if (meta && typeof meta.input_tokens === 'number') {
  usage = {
    promptTokens: meta.input_tokens,
    completionTokens: meta.output_tokens,
    totalTokens: meta.total_tokens,
  }
}
```

`AIMessageChunk.usage_metadata`（Python 同名字段）由 LangChain 从 provider 的响应里填好，含 `input_tokens` / `output_tokens` / `total_tokens`。两端映射为契约的 **camelCase** 键：`promptTokens` / `completionTokens` / `totalTokens`（**对齐契约 `LlmNodeOutput.usage`**，见 `01` 篇 §11）。

### 10.2 现实：有些 provider 流式时**不给 usage**

- OpenAI 兼容实现**通常**在流末尾带一段 usage（本项目的 mock 就是这样：最后发一个 `choices: []` + `usage` 的帧，见 §15.0）；
- 但**并非所有** provider 流式时都返回用量——有的只在非流式返回。

两端的处理**完全一致**：

```
usage_metadata 存在（且 input_tokens 是数字）→ 带上 usage
否则                                        → 省略 usage 字段
```

（TS `output.usage = usage` 仅当 `usage !== undefined`；Python `if usage is not None: output["usage"] = usage`。）这正是 `01` 篇 §11 讲的「`usage` 为什么可选」在**实现侧**的落地：**有则带、无则省**，两端同规则，于是输出形状两端一致。

### 10.3 为什么判据是 `input_tokens` 是否为数字

两端都用「`input_tokens` 是数字」当判据（而非「meta 存在」）：因为某些 provider / 中间态可能给一个**只有部分字段**的 `usage_metadata`。以 `input_tokens` 为门槛，保证带出来的 usage **三个字段都是数**，避免半成品形状破坏两端一致。

## 11. 【技术教学 · 首次】桩 vs 真：两端 token 序列一致，靠的是「同一个 provider」

### 11.1 阶段 4（桩）为什么两端一致

桩的逻辑在**引擎内部**：`Array.from(text)`（TS）与 `text[i:i+8]`（Python）**同一套算法**，故切片结果必然逐片相同（见 `04-执行引擎/03-节点运行时与变量池.md` §8）。**一致性来自「算法相同」。**

### 11.2 阶段 5（真）为什么两端也要一致，靠的是什么

真模型下，**片由 provider 决定**：

```
TS 引擎 ──┐
          ├──▶ 同一个 provider（同 base_url / 同 model / 同请求）──▶ 同一串增量
Py 引擎 ──┘
```

两端各自把「收到的 chunk」原样转发成 `token`——**没有**任何本地切片。所以两端 token 序列逐字节一致，**前提是它们连的是同一个 provider、发的是同一个请求**（同 `base_url`、同 `model`、同 `messages`、同参数）。

| | 桩（阶段 4） | 真（阶段 5） |
| --- | --- | --- |
| 片从哪来 | 引擎**自己切**（8 码点） | **provider 给** |
| 两端一致靠 | **算法相同** | **同一个 provider + 同一个请求** |
| 若两端片不一致 | 几乎不可能（代码写死） | **可能**：`base_url`/`model`/参数不一，或 provider 非确定性 |

### 11.3 这条结论的实践含义（务必记住）

1. **要让两端 token 一致，就必须让两端「连同一个 provider」**——否则再怎么写代码也白搭。这正是 `01` 篇 §12、§15 反复强调「两端 `.env` 的 `LLM_BASE_URL`/`LLM_MODEL` **必须同值**」的原因。
2. **mock 是「确定性 provider」**：它对**同一输入**永远返回**同一串增量**（把 user 消息回显、固定每 5 码点一片）。所以两端的 token 序列可比对（§15）。真实 provider（尤其带采样）未必确定性——本阶段验收用 mock，正是为了「可逐字节比对」。
3. **一致性从「代码属性」变成了「环境属性」**：阶段 4 的一致性写在代码里；阶段 5 的一致性挂在**配置**上（同 provider）。这也是为什么 `01` 篇要把 provider 配置做成**环境变量**并**两端同值**。

> 一句话：**桩时代，「两端一致」是代码保证的；真模型时代，「两端一致」是配置（同一个 provider）保证的。** 理解这一点，才算真正理解本阶段的行为。

## 12. 【技术教学 · 首次】踩坑：LangChain JS 默认重试 6 次 → 必须 `maxRetries: 0`

### 12.1 现象

不设 `maxRetries` 时，provider 返回 **500** 或**请求超时**，**TS 侧**会「卡很久」（30 秒以上）才把错误吐出来；而 **Python 侧**因为默认重试次数更少，往往**很快就失败**。于是同一张图、同一个错误，两端**耗时与时机严重不一致**——验收/契约比对时表现为「一端秒失败、一端要等半天」。

### 12.2 原因

LangChain JS 内部用 **`AsyncCaller`** 包装每个请求，**默认重试 6 次**，且带**指数退避**：一次 5xx / 超时会被重试 6 次，退避累加，**总耗时轻松超过 30 秒**。Python 侧的 openai SDK 默认重试次数少得多（**2 次**）。**两端默认值不同**，错误行为自然不同。

### 12.3 解决：显式关闭重试

```ts
// TS
maxRetries: 0,
```

```python
# Python
max_retries=0,
```

设成 **0** 后：任何 5xx / 超时**第一次**出现就立刻上抛 → 被 `mapLlmError` / `map_llm_error` 归一为规范文案 → 走 `run_failed`。两端**都**秒失败、文案**都**一致。

### 12.4 为什么「必须关掉重试才能让两端错误行为一致」（讲透）

| 开着默认重试 | 关掉重试（`=0`） |
| --- | --- |
| TS 重试 6 次、Py 重试 2 次 → **次数不同** | 都 0 次 → **次数相同** |
| 一次 500 在 TS 侧 ≈ 30s+（退避），Py 侧数秒 → **时机不同** | 都**立即**抛 → **时机相同** |
| 重试可能把「偶发成功」变成「最终成功」，两端命运不同 | 结果**确定**：要么成功、要么同一文案失败 |
| 契约测试无法固定错误时延/次数 | 错误路径**可预测、可比对** |

**本质**：本项目的硬要求是「两端行为**逐字节/逐时序**可比」。**重试次数是「行为」的一部分**——默认值不同，行为就不同。把它钉成 **0**，等于把「重试」这个不确定因素**从两端都拿掉**，剩下的路径才是确定的、可对齐的。

> 附带好处：跑长任务时不会「明明 provider 已经报错，本地却傻等 30 秒」。失败**快速暴露**，也让 mock 注入的错误（`[[mock-status:401]]` 等）**立刻**可见（§15）。

## 13. 错误归一映射（`mapLlmError` / `map_llm_error`）

两端把 LangChain / 底层异常映射为**同一组规范文案**（规则登记在 `error-messages.md` §5）：

```ts
// TS
export function mapLlmError(error: unknown): string {
  const status = statusCodeOf(error)
  if (status !== null) {
    if (status === 401 || status === 403) return 'llm request unauthorized'
    if (status === 429) return 'llm rate limited'
    return `llm request failed: ${status}`
  }
  if (isTimeout(error)) return 'llm request timed out'
  return 'llm request failed: unknown'
}
```

```python
# Python
def map_llm_error(error: Exception) -> str:
    status = _status_code(error)
    if status is not None:
        if status in (401, 403):
            return "llm request unauthorized"
        if status == 429:
            return "llm rate limited"
        return f"llm request failed: {status}"
    if _is_timeout(error):
        return "llm request timed out"
    return "llm request failed: unknown"
```

**规则（两端一致，优先级从高到低）**：

| 优先级 | 判据 | 文案 |
| --- | --- | --- |
| 1 | 有 HTTP 状态码 | 401/403 → `llm request unauthorized`；429 → `llm rate limited`；其它 → `llm request failed: {status}` |
| 2 | 无状态码但超时 | `llm request timed out` |
| 3 | 其余 | `llm request failed: unknown` |

**要点**：

- **「归一」= 不透出库原始 message**：本阶段**绝不**把 `error.message`（如 OpenAI 的 `"Incorrect API key provided"`）透出——否则两端库的措辞不同，`run_failed.message` 就**无法逐字节一致**。归一为**我们自己定义的**文案，才两端可比（这正是「错误文案唯一真源」的意义）。
- **取状态的字段名两端不同**：TS 读 `error.status`（OpenAI **JS** SDK 的 `APIError`）；Python 读 `error.status_code`（openai **Python** SDK 的 `APIStatusError`）——Python 侧 `_status_code` 先试 `status_code` 再试 `status` 兜底。
- **超时判据两端都「先看类型名，再兜底看 message」**：TS 看 `name ∈ {APIConnectionTimeoutError, TimeoutError, AbortError}`；Python 看 `type(error).__name__ ∈ {APITimeoutError, TimeoutError, APIConnectionTimeoutError}`；都再兜底「message 含 timeout」。
- **纯函数**：`mapLlmError` / `map_llm_error` **不碰网络、不依赖上下文**——与阶段 3 的 `validateGraph`、阶段 4 的节点函数一脉相承（见 `04-执行引擎/03-节点运行时与变量池.md` §7）。所以它**可以被单独喂异常对象测试**、两端逐条对齐。
- **出错不发 `node_finished`**：`llm` 节点抛 `RunError` 后，执行器捕获、记录 `failedNodeId = llmId`、往外吐 `run_failed`，**跳过**该节点的 `node_finished`（见 `04-执行引擎` 系列的节点动作层）。

## 15. 实测：用 mock 跑两端

### 15.0 mock 是什么

`tools/mock-llm/server.mjs` 是一个**零依赖、OpenAI 兼容**的最小 provider：

- `POST /v1/chat/completions`，支持 `stream: true`（SSE）；
- 回复**确定可预测**：把收到的**最后一条 user 消息**原样回显并加固定前缀 `echo: `；
- 分片固定为**每 5 个 Unicode 码点**一片（故两端 token 序列可逐字节比对）；
- 返回 `usage`（`prompt_tokens` / `completion_tokens` / `total_tokens`）；
- 可注入错误 / 延迟：HTTP 头 `x-mock-status: 401`，或 user 消息含 `[[mock-status:401]]`（供不设自定义头的 LangChain 用）。

**起 mock**（仓库根）：

```bash
node tools/mock-llm/server.mjs
# → mock-llm listening on http://127.0.0.1:11435/v1/chat/completions
```

### 15.1 准备一张图

`PUT /apps/{id}/graph`（结构见 `03-画布/01-图JSON契约与校验.md`）：

```jsonc

  "version": "1",
  "nodes": [
    { "id": "start_1", "type": "start", "position": { "x": 0, "y": 0 },
      "data": { "inputs": [{ "name": "topic", "type": "string", "required": true }] } },
    { "id": "llm_1", "type": "llm", "position": { "x": 200, "y": 0 },
      "data": { "title": "问候", "model": "", "prompt": "Hello {{ inputs.topic }}" } },
    { "id": "end_1", "type": "end", "position": { "x": 400, "y": 0 },
      "data": { "outputs": [{ "name": "result", "value": "{{ llm_1.text }}" }] } }
```

> `llm_1.data.model` 故意留空 `""` → 回退环境变量 `LLM_MODEL=mock-model`（顺带验证 `01` 篇 §10.2 的回退）。

### 15.2 运行

### 15.4 实测事实（照实记录）

| 项 | 实测结果 |
| --- | --- |
| `token` 序列 | **`["echo:", " Hell", "o min", "i-dif", "y"]`**，拼接为 **`"echo: Hello mini-dify"`**；**两端逐字节一致** |
| `node_finished(llm)` 的 `output` | **`{"text":"echo: Hello mini-dify","model":"mock-model","usage":{"promptTokens":15,"completionTokens":21,"totalTokens":36}}`**；**两端一致** |
| `run_finished.outputs` | **`{"result":"echo: Hello mini-dify"}`**；**两端一致** |
| 整条 SSE 流 | 除 **`runId` / `elapsedMs`** 外**逐字节相同** |

**数字怎么来的（对得上）**：

- `promptTokens = 15` = mock 统计的 `messages` 文本总长 = user 消息 `"Hello mini-dify"` 的 **15** 个字符（图里无 `system` 消息）；
- `completionTokens = 21` = `"echo: Hello mini-dify"` 的 **21** 个码点；
- `totalTokens = 36 = 15 + 21`；
- 每 5 码点一片 → 21 码点 = **5 + 5 + 5 + 5 + 1** → 正是上面 5 片。

> 注意：这 5 片是 **mock 的**切法（`CHUNK_SIZE = 5`），**不是**两端引擎切的——两端只做「收到就转发」（§11）。换成真实 provider，片数与大小随之改变，**两端仍因「同一个 provider」而一致**。

## 17. 常见坑

| 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- |
| 没设 `maxRetries: 0` / `max_retries=0` | 500/超时一端秒失败、一端卡 30s+ | LangChain JS `AsyncCaller` 默认重试 6 次；**必须显式关**（§12） |
| Python `timeout` 忘了 `/1000` | 配 `3000` 变成 3000 秒 | Python `timeout` 单位是**秒**，JS 是**毫秒**（§8.3） |
| 两端 `.env` 的 `LLM_BASE_URL`/`LLM_MODEL` 不同值 | 两端 token 序列不一致 | 真模型下「两端一致」靠**同一个 provider**（§11）——两端同值 |
| 先拿完整响应再本地切开发 | 假流式，首字要等很久 | 要**逐 chunk 立刻 `emitToken`**（§9） |
| 只发 token 不累积全文 | `end` 无从取值 / `node_finished.output.text` 空 | 既 `text += piece` 又 `emitToken(piece)`（§9.2） |
| 把 `usage` 强行必填 | provider 不给时伪造/报错 | 有则带、无则省（§10、`01` 篇 §11） |
| 直接透出 `error.message` | 两端 `run_failed.message` 不一致 | 必须**归一为规范文案**，不透出库原始 message（§13、`error-messages.md` §5） |
| 用错状态码字段 | 取不到状态码、全归 unknown | TS 读 `error.status`；Python 读 `error.status_code`（再兜底 `status`）（§13） |
| 空 `delta`（如流首 role 帧）也发 token | 多出空 `token` 事件、两端难对齐 | 空片**跳过**（`if piece !== ''` / `if piece:`）（§8.5） |
| 忘了「未配置」短路 | 空 key 也去出网，慢且有歧义 | `LLM_API_KEY` 为空**先抛** `RunError`（§6、`01` 篇 §12.5） |
| 出错还发该节点 `node_finished` | 流里既有失败又有「完成」 | 出错只发 `run_failed`，**跳过** `node_finished`（§13） |
| `temperature`/`maxTokens` 未设却硬传默认值 | 覆盖了 provider 默认 | 只传**显式设置**的（存在才展开 / `isinstance` 判断）（§6、§7） |
| 以为片大小固定 | 客户端按 8 码点假设 | 真流式的片**由 provider 决定**（§9.3） |

## 18. 本篇技术点登记（同步到 `docs/tutorial/INDEX.md`）

| 技术点 | 说明 |
| --- | --- |
| **`ChatOpenAI`（LangChain 封装）用法** | `baseURL`（TS 放 `configuration` 内）/ `base_url`（Py 顶层）、`apiKey`/`api_key`、`model`、`temperature`、`maxTokens`/`max_tokens`、`timeout`（**JS 毫秒 / Py 秒**）、`maxRetries`/`max_retries`；**为什么用封装而非裸 HTTP**（统一接口、与 LangGraph 同族、换 provider 只改一处） | **首次教学于本篇** |

| **`usage` 的来源与「provider 不给」的现实** | `chunk.usage_metadata`（`input_tokens`/`output_tokens`/`total_tokens`）；有则带、无则省；以 `input_tokens` 为数字为判据 | **首次教学于本篇** |

| **LangChain JS 默认重试 6 次 → 显式 `maxRetries` / `max_retries = 0`** | 默认重试次数两端不同会让 5xx/超时的**时机与次数**不一致；关掉重试才能让两端**错误行为一致**（快速、可预测、可归一） | **首次教学于本篇** |
| **LLM 错误归一映射（`mapLlmError` / `map_llm_error`）** | HTTP 状态码优先（401/403 / 429 / 其它）、其次超时、最后 unknown；**不透出库原始 message**；映射为**纯函数**；出错不发 `node_finished` | **首次教学于本篇** |
| **`chunk.content` 字符串化** | 字符串原样 / 数组拼 `text` / 其它紧凑 JSON（复用阶段 4 §9 口径）；空片跳过 | 本篇 |
| **Python 机制：异步迭代 `async for` 与异步回调 `await emit`** | `client.astream(...)` 是异步迭代器、须 `async for`；`emit` 是异步回调（因 `queue.put` 可 await），对照 TS 的同步 `emitToken`（§9.4） | **首次教学于本篇（加厚）** |
