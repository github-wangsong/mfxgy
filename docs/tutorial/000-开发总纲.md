# Mini-Dify 开发总纲

> 一个以「学习 Agent 开发」为目标的类 Dify 应用开发平台（阉割版）
>
> **三主线目标**：既带你成为合格的 Agent 开发工程师，也让你系统掌握 TS · LangChain · LangGraph · React · Next.js · NestJS · **Python · FastAPI · SQLAlchemy** · PostgreSQL 全套技术栈
>
> 技术栈：TypeScript (NestJS) + **Python (FastAPI)** 双后端 · Next.js + React · PostgreSQL (pgvector) · LangChain / LangGraph（JS 与 Python 双实现）
>
> 后端策略：**契约优先 · 双实现**——同一份 OpenAPI 契约，NestJS 与 FastAPI 各实现一遍，行为由同一套契约测试保证一致
>
> 文档状态：v3 草案。本文件是全项目的**路线总索引**，后续每个阶段都会产出对应的教程笔记。

## 1. 项目定位

### 1.1 目标

**产品目标**
- 从零实现一个**能拖拽搭建、能调试运行、能发布调用**的对话式 AI 应用平台。
- 核心能力：**工作流编排引擎、Agent 循环（tool calling / ReAct）、RAG、流式输出与状态管理，以及独立的自主 Agent 运行时**。

**学习目标（三主线）**
- 主线 A · Agent 开发能力：理解并实战编排引擎、Agent 循环、RAG 全链路。
- 主线 B · TS 全栈：掌握 TypeScript、LangChain.js、LangGraph.js、React、Next.js、NestJS、PostgreSQL/pgvector。
- 主线 C · Python 后端与语言对比：用 **FastAPI + SQLAlchemy 2.0 + LangGraph(Python)** 实现**与 TS 版功能完全一致**的后端，从而直观理解 Python 与 TS 的差异及各自优缺点。
- 三条主线**互相成就**：每一个产品功能都用对应技术实现，边做边学、学以致用。

**交付物**
- ① 可运行的项目；② 一套配套的教学笔记（含「功能笔记」「技术精讲」「语言对比」三类）。

### 1.2 非目标（明确砍掉，避免摊大饼）

| 砍掉的 | 原因 |
| --- | --- |
| 多种应用类型（Chatbot / Completion / Agent / Workflow / Chatflow 并存） | 只保留**一种：对话式工作流**，统一心智 |
| SSO / 计费 / 团队协作 / 多租户工作空间 | 与 Agent 学习关系弱、工程量大。**注：账号体系与基础 RBAC 已改为纳入**（见 §3.9、阶段 1） |
| 插件守护进程（plugin daemon）/ 插件市场 / MCP 服务端管理 | 复杂度极高，学习阶段不需要 |
| 多向量库抽象（Weaviate / Qdrant / Milvus / …） | 统一用 **pgvector**，一个库解决 |
| 复杂可观测性 / 标注 / 用户反馈 | 可选接 LangSmith 看 trace 即可 |
| 分布式任务调度（Celery / Beat） | 起步用**同步执行 + SSE**，后期再上 BullMQ |
| 前端复杂状态同步（多人协作编辑） | 单人编辑即可 |

### 2.4 典型端到端用户旅程（验收基准）

1. 搭建者**注册并登录**平台
2. 创建应用「客服助手」
3. 在画布上拖出 `Start → 知识检索 → LLM → End` 并连线、配置
4. 点击「调试」，输入问题，看到**逐字流式**回答，且引用来自知识库
5. 上传一份产品手册到知识库，重新调试，回答质量提升
6. 点击「发布」，拿到 API Key
7. 用终端用户界面/第三方调接口与其对话，得到同样的流式回答

**能完整走通这条旅程，就是 P0 的验收定义。**

### 3.2 后端功能模块（NestJS 与 FastAPI 双实现）

### 3.3 编排引擎（核心，最值得投入）

- **输入**：画布 JSON（`nodes[]` + `edges[]`）。
- **编译**：JSON → LangGraph `StateGraph`（节点映射、条件边映射）。
- **状态**：统一的 State（`messages` 对话消息 + `variables` 自定义变量）。
- **执行**：`graph.stream(state)` → 转成统一事件流（SSE）返回前端。
- **节点契约**：每个节点 = `(state, config) => Partial<State>` 的纯函数，便于测试与复用。
- **持久化**（进阶）：LangGraph checkpointer（`@langchain/langgraph-checkpoint-postgres`）支持断点续跑与 HITL。

> 这一块是整个项目的技术心脏，也是教程笔记篇幅最重的部分。

### 3.4 RAG 模块

| 环节 | 技术 | 精简策略 |
| --- | --- | --- |
| 文档加载 | `@langchain/community` loaders | 先支持 txt / md / pdf |
| 切分 | `@langchain/textsplitters` (RecursiveCharacterTextSplitter) | 固定参数，起步不做可调 |
| 向量化 | `@langchain/openai` Embeddings | 单一 embedding 模型 |
| 存储检索 | PostgreSQL + pgvector（余弦相似度） | 砍掉 rerank、混合检索、parent-child |
| 增强 | Retrieval 节点拼接 context 进 Prompt | — |

### 3.5 模型 / 工具模块

- 模型：环境变量或简单配置表存 provider + key，用 LangChain 的 `ChatOpenAI`（兼容 OpenAI 协议即可接大部分厂商）。
- 工具：用 `@langchain/core/tools` 的 `tool()` 定义内置工具；LLM 节点开启 `bindTools` 即获得 function calling。
- Agent：不加「Agent 节点」也行——LLM 节点 + 工具 + 条件边即可构成 ReAct 循环（这正是学习价值所在）。

### 3.6 数据 / 存储

- PostgreSQL 承担全部结构化数据 + 向量（pgvector）。
- 文件：起步落本地磁盘，抽象出 Storage 接口，后期可换 S3/MinIO。

### 3.7 流式与实时

- TS 后端：NestJS `@Sse()` + RxJS `Observable`（或直接写 `res` 流）。
- Python 后端：FastAPI `StreamingResponse`（`text/event-stream`）产出同一事件序列。
- 前端：`fetch` + ReadableStream 解析 SSE（或用 `EventSource`）——**两套后端产出的事件流完全一致**。
- 事件类型见第 5.3 节。

### 3.8 双后端策略（契约优先 · 双实现）

> 这是本项目最关键的工程约束，契约细节见第 5.5 节。

- **唯一契约来源**：`packages/contract/` 存放语言无关的契约——OpenAPI 规范 + SSE 事件协议 + 画布 JSON Schema。
- **双方由契约生成模型**：TS 侧生成类型（Zod / oRPC）；Python 侧生成 Pydantic 模型。
- **前端后端无关**：前端通过环境变量（如 `NEXT_PUBLIC_API_BASE`）指向 `api-ts` 或 `api-py`，**代码零改动**。
- **一致性由测试保证**：同一套 **contract test** 分别打两套后端，校验「响应结构 / 状态码 / SSE 事件序列」逐项一致。
- **开发节奏**：每个阶段「先 TS 落地 → 再 Python 对照实现 → 记录语言差异」。
- **Python 定位**：以「对照学习」为主，不追求生产冗余；核心逻辑保持薄，降低同步成本。

### 3.9 认证与权限设计

- **认证方式**：无状态 **JWT**（access token + 可选 refresh token），登录后由前端携带。
- **密码存储**：bcrypt / argon2 哈希（TS: `bcrypt`；Python: `passlib` + `bcrypt`）。
- **后端校验**：
  - NestJS：`AuthGuard` + `@UseGuards()`（或 Passport JWT 策略）；
  - FastAPI：`Depends(get_current_user)` 依赖注入 + `OAuth2PasswordBearer`。
- **权限模型**：基础 RBAC——`admin`（可管理用户/模型）与 `member`（仅自己的应用）；起步可先只启用单角色，字段预留。
- **与契约的关系**：登录/注册接口、JWT 载荷结构、错误码全部进 `packages/contract`（§5.5）。
- **对照学习点**：NestJS Guard/Passport ↔ FastAPI Depends/OAuth2，两种「依赖注入式鉴权」是绝佳的语言对照素材。

### 3.10 自主 Agent 运行时（对齐 dify-agent）

> 与工作流引擎**并列的第二个执行核心**，独立成模块与契约，借鉴 Dify 新版 `dify-agent`。

- **独立模块**：`AgentModule`（TS）/ `agent_runtime`（Python），**不塞进** `WorkflowModule`；对外是独立的 Agent Run API。
- **Run 模型**（借鉴 dify-agent）：`POST /agent/runs` 异步受理（202 + `run_id`）→ 轮询状态 + SSE 事件流（支持 `Last-Event-ID` 断点重放）→ `POST /agent/runs/{id}/cancel` 独立取消。
- **Composition 声明式装配**（借鉴 dify-agent）：一个 Run 由 JSON `composition` 描述，委托若干「层」（prompt / knowledge / llm / tools / history / output …）；服务端用 registry 把 `name` 映射到模块，**无图、无连线**。
- **Layer 分层**：每层自包含 `Config` + `State`，状态归层所有、写回显式。
- **实现分工（刻意例外）**：TS 侧用 **LangGraph**（ReAct agent），Python 侧用 **Pydantic AI**（直接对齐 dify-agent 源码）——**同一契约、两套框架**，是绝佳的框架对照素材。
- **简化范围（砍掉）**：dify-agent 的 Workspace / Binding / RuntimeLease **资源账本**与沙箱后端（E2B / OpenShell）——那是平台运维，不是 Agent 开发。
- **保留的核心学习点**：ReAct 循环、工具调用、记忆/历史、**上下文压缩（compaction）**、事件流与重放。

### 3.11 基础设施与本地运行（Docker 只跑中间件）

> 决策：**Docker 只用于中间件，应用全部本地运行。**

- **中间件（Docker Compose）**：根目录 `docker-compose.yml` 仅含 `db` 服务（`pgvector/pgvector:pg16`，:5432，命名卷持久化）；后续阶段需要 Redis 时再加一个 `redis` 服务。
- **应用（本地）**：`api-ts`（`pnpm dev:api-ts`）、`api-py`（`uv run`）、`web`（`pnpm dev:web`）三个开发服务器都在宿主机跑。
- **理由**：① 学习目标是亲手写/调代码，容器化应用会拖慢热重载、增加断点调试难度、隐藏日志；② Windows 原生装 PostgreSQL + pgvector 很折磨，官方镜像最省事；③ 与 Dify 自己的「docker 起中间件 + 应用本地开发」一致。
- **连接串**：**每个 app 自包含 env**——根目录 `.env` 只保留 `POSTGRES_*`（供 compose 做变量替换）；应用连接串下放到 `apps/api-py/.env`（`postgresql+psycopg://...`，SQLAlchemy 格式）与 `apps/api-ts/.env`（`postgresql://...`，Prisma 格式，不带 `+psycopg`）。
- **常用命令**：`docker compose up -d db` 启动数据库。
- **全容器化**（连应用一起容器化）仅作为将来「部署」阶段的加分项，不是学习目标。

## 5. 关键设计约定（全项目统一）

### 5.1 画布 JSON 结构（共享类型）

```ts
interface Graph { nodes: Node[]; edges: Edge[]; }
interface Node { id: string; type: string; position: XY; data: Record<string, unknown>; }
interface Edge { id: string; source: string; sourceHandle?: string; target: string; }
```

### 5.2 节点契约（统一接口）

```ts
// 每个节点类型实现：
type NodeExecutor = (state: GraphState, config: NodeConfig) => Promise<Partial<GraphState>>;
```

### 5.3 执行事件协议（SSE）

| 事件 | 载荷 | 用途 |
| --- | --- | --- |
| `node_started` | nodeId, title | 高亮当前节点 |
| `node_finished` | nodeId, outputs | 展示中间结果 |
| `token` | text | 打字机流式输出 |
| `message_end` | fullText, usage | 结束 |
| `error` | message | 错误 |

> 前后端以此协议解耦：后端只发事件，前端只按事件渲染。

### 5.4 变量与状态

- `variables`：用户输入变量 + 节点输出变量，按 `nodeId.varName` 命名空间。
- `messages`：对话消息数组，作为 Agent 的短期记忆。

### 5.5 契约优先（唯一真源）

> 全项目最高优先级约定：**任何接口、事件、数据结构，先落契约，再写实现。**

- 契约文件（`packages/contract`）是唯一真源，两套后端都不得「各自发明」接口。
- 契约至少包含：REST 接口（路径/方法/请求/响应/错误码）、SSE 事件序列、画布 JSON Schema、节点配置 Schema。
- 变更流程：改契约 → 两套后端同步实现 → 契约测试双跑通过 → 才算完成。
- 目的：让「TS 版与 Python 版效果一致」成为**可验证的事实**，而非口头承诺。

### 5.6 认证约定

- 控制台接口**默认需要认证**，仅 `注册 / 登录 / 健康检查` 例外。
- 请求头：`Authorization: Bearer <jwt>`。
- JWT 载荷（两套后端必须一致）：`sub`（userId）、`role`、`exp`、`iat`。
- 被发布的应用接口不走 JWT，改走 **API Key**（`X-Api-Key`），与平台认证独立——两条鉴权链路不要混淆。

### 5.7 Agent 运行时契约（Composition + 事件）

> 独立于工作流契约，专属于自主 Agent 运行时。

- **Run 接口**：`POST /agent/runs`（202 + `run_id`）、`GET /agent/runs/{id}`、`GET /agent/runs/{id}/events/sse`、`POST /agent/runs/{id}/cancel`。
- **Composition 结构**：`{ schema_version, layers: [{ name, config }] }`，层的 `name` 由 registry 解析；两套后端必须支持同一份 composition。
- **事件流**：事件需带可续传游标（对齐 `Last-Event-ID`），事件类型至少含 run 状态、token、工具调用、结束/错误。
- **一致性**：同一份 composition 打两套后端，必须产出**等价的事件序列**（由契约测试校验）。

## 8. 关键技术决策（ADR 摘要）

| 决策 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 后端框架 | NestJS | 模块化 + DI，天然贴合 controller/service 分层 | 比 Express 略重 |
| 编排引擎 | LangGraph.js | 状态图 + 循环 + checkpoint，正好覆盖 Agent 编排 | 抽象层需学习 |
| LangChain 定位 | 仅组件/集成层 | 复用集成、不接管编排，避免与图引擎打架 | 需自己画边界 |
| 向量方案 | pgvector | 一套 PG 全解决，砍掉多向量库抽象 | 大规模检索弱于专用库 |
| 执行模型 | 起步同步 + SSE | 最简单、最易调试、最适合学习 | 长任务占请求；后期换 BullMQ |
| ORM | Prisma | DX 好、迁移简单、社区大 | pgvector 需原生 SQL 补充 |
| DeepAgents | 暂不采用 | JS 支持新、可控性弱 | 高阶 Agent 需自行用 LangGraph 搭 |
| 账号体系 | 完整注册/登录 + JWT + 基础 RBAC | 用户明确要求；且是双语言「鉴权」对照的绝佳题材 | 推翻原「非目标」，工作量增加 |
| 双后端策略 | **契约优先 · 双实现** | 「效果一致」可被契约测试验证；两语言对照学习 | 后端维护成本约 2x |
| Python 后端栈 | **FastAPI + SQLAlchemy 2.0** | 与 NestJS 心智最接近（DI/校验/异步）；贴近 Dify 源码可对照 | 需额外学习 Pydantic / Alembic |
| Python 编排 | **LangGraph (Python)** | 官方参考实现、集成最全，便于对照 Dify | 与 LangGraph.js API 有细节差异 |
| Agent 运行时 | 独立模块（对齐 dify-agent） | Run + Composition + Layer 架构；与工作流引擎解耦；学习 Dify 新架构 | 增加一个模块与契约面 |
| Agent 运行时实现 | Python = **Pydantic AI** / TS = LangGraph | 同契约两框架，便于对照 dify-agent；其余模块仍用 LangGraph | 两侧库不同，靠契约测试兜底 |
| 本地运行形态 | **Docker 只跑中间件**，应用本地运行 | 保学习体验（热重载/断点/日志）；Windows 装 PG+pgvector 麻烦 | 需本地具备 Node/uv/pnpm |

> 这些决策都可在推进中调整；若某步实证受挫，我们再回头修订本表并说明原因。

## 10. 风险与替代方案

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| LangChain.js 生态不如 Python 完善（部分 loader 缺失） | RAG 加载受限 | 先支持 txt/md/pdf，必要时自写解析 |
| LangGraph 抽象陡峭 | 上手成本 | 阶段 3 先用最小 StateGraph，逐步加复杂度 |
| React 19 与部分库兼容 | 前端集成风险 | 优先选已支持 React 19 的库（@xyflow/react v12） |
| 同步执行阻塞请求 | 长工作流超时 | 阶段 3 先接受；阶段 9 引入 BullMQ |
| 向量维度/索引性能 | 检索变慢 | 加 HNSW 索引；数据量大再考虑专用库 |
| 双后端行为漂移 | 「效果一致」名存实亡 | 契约优先 + 同一套 contract test 双向校验；Python 紧跟 TS |
| 双后端维护成本≈2x | 进度变慢 | Python 定位为「对照学习」而非生产冗余；核心逻辑保持薄 |
| LangGraph(Python) 与 LangGraph.js 细节差异 | 实现行为不一致 | 以契约为准，只求外部行为一致，不追求内部实现一致 |
| 范围蔓延 | 做不完 | 严守第 1.2 节「非目标」清单 |
