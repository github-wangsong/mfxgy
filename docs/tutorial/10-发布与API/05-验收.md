做完这一篇，你能：

- 沿**依赖顺序**逐层验收阶段 10：契约 `0.10.0` → 迁移与索引 → Key 生命周期 → 对外运行 → 草稿/快照隔离 → 两端一致 → 错误 + 回归。

## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序

```
L1 契约编译(0.10.0)
        │
        ▼
L2 迁移与索引（api_keys + 唯一索引 + HNSW 仍在）
        │
        ▼
L3 Key 生命周期（201 → 列表无明文 → 204 → 401）
        │
        ▼
L4 对外运行（双认证头 + SSE 结构）
        │
        ▼
L5 草稿 vs 快照隔离（改草稿不影响线上）
        │
        ▼
L6 两端一致（对外 SSE + 9 组错误文案）
        │
        ▼
L7 阶段 5/6/7/8/9 回归
```

**为什么按这个顺序**：没有表与唯一索引，就没有「哈希查找 O(1)」；没有 Key 生命周期，就无法证明「撤销立即失效」；没有对外运行，就谈不上快照隔离；隔离是阶段 10 最重要的一条，必须在一致性之前单独验证；最后用回归证明新入口没有破坏旧行为。

### 3.3 L3 —— Key 生命周期：`201` → 列表无明文 → `204` → `401`

#### 3.3.1 创建：`201`，明文 35 字符，`prefix` = 前 11

```bash
CREATE_BODY=$(curl -s -X POST http://127.0.0.1:3001/apps/$APP_ID/api-keys \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"ui-demo"}')

KEY=$(echo "$CREATE_BODY" | python -c "import sys,json;print(json.load(sys.stdin)['key'])")
KEY_ID=$(echo "$CREATE_BODY" | python -c "import sys,json;print(json.load(sys.stdin)['id'])")

echo "len=${#KEY}"
echo "prefix=${KEY:0:11}"
echo "$CREATE_BODY" | python -m json.tool

curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:3001/apps/$APP_ID/api-keys \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"another-demo"}'
```

**预期输出（实测·节选）**

```
len=35
prefix=sk-ec5a2884
{
    "id": "<uuid>",
    "appId": "<appId>",
    "name": "ui-demo",
    "prefix": "sk-ec5a2884",
    "createdAt": "2026-10-23T13:42:26.294Z",
    "lastUsedAt": null,
    "revokedAt": null,
    "key": "sk-ec5a28841fa965ac4c69e19c4d30b86e"
}
201
```

**结果解读**：

- `key` = `sk-` + 32 位十六进制 = **35 字符**；`prefix` = 前 **11** 字符（`sk-` + 8 位十六进制）。两者**必须满足** `key.startsWith(prefix)` 且 `prefix.length === 11`。
- `key` **只在这一个响应里出现**（`CreateApiKeyResponse`）；`lastUsedAt` / `revokedAt` 初始为 `null`。
- 创建第二个 key（不同名）也是 `201`：同一应用可以有多把 key（用于轮换、按环境区分）。
- 明文 `key` 既不在 URL 里、也不在列表里，只在这个 201 的 body 里——**任何日志系统都不应该记录它**。

## 4. 【技术讨论 1】阶段 10 补上了 P0 闭环的最后一环：第三方可调用

**问题**：到阶段 9 为止，应用已经能编排、能跑、能记住历史、能在画布上调试——为什么还不能叫「完成」？

**答案的一句话**：**因为在阶段 9 之前，所有运行都必须由「登录我们自己的前端」的用户发起；产品只是一个「工作室」，还不是一个「服务」。**

**P0 闭环的六个环节**

| 环节 | 阶段 | 用户得到什么 |
| --- | --- | --- |
| 1. 建应用 | 2 | 一个可命名的容器 |
| 2. 可视化编排 | 3 / 8 | 一张可编辑的图（节点 + 边 + 分支 + 循环） |
| 3. 执行 | 4~7 | 真流式输出、工具、检索 |
| 4. 记忆 | 9 | 多轮对话 |
| 5. **发布** | **10** | **一份稳定的线上快照** |
| 6. **被外部调用** | **10** | **任何系统用一把 key 接入** |

**「不能调用」到底缺了什么**

| 缺的东西 | 阶段 9 的状态 | 阶段 10 的补法 |
| --- | --- | --- |
| 认证方式 | 只有 JWT（人类登录） | API Key（机器对机器） |
| 图来源 | 只有草稿（调试用） | 已发布快照（线上用） |
| 错误语义 | 面向内部用户（`App not found` 等） | 面向集成方（`Missing` / `Invalid API key` / `App is not published`） |
| 接入文档 | 只存在于仓库 | 面板里的 curl 示例 |

**为什么「机器身份」不能用 JWT**

- JWT 是**短期、绑定人**的：`expiresIn` 默认 1 小时，过期就得重新登录；第三方服务器没有「登录页」。
- JWT 携带 `sub`（用户 id）与 `role`，权限粒度是「这个人能做什么」；对外集成需要的是「**这个应用**能被调用」。
- 撤销 JWT 需要黑名单或轮换密钥；撤销 API Key 只是一行 `UPDATE revoked_at`。
- 所以：**人类用 JWT，机器用 API Key**——两套身份、两套生命周期，互不替代。

> **一句话**：阶段 10 之前，mini-dify 能「做出」一个应用；阶段 10 之后，mini-dify 能「交付」一个应用。**能交付，才是产品。**

## 5. 【技术讨论 2】草稿/快照隔离是「可视化编排 + 线上服务」类产品的基石

**问题**：为什么几乎所有「可视化编排 + 在线服务」产品（Dify、n8n、Coze、Zapier……）都有「草稿 / 发布」两态，而不是「保存即生效」？

**答案的一句话**：**因为「编辑」和「上线」是两种完全不同的风险模型：编辑允许出错、允许中间态、允许高频；上线要求确定、可审计、低频。**

**两种风险模型**

| | 草稿（编辑） | 快照（线上） |
| --- | --- | --- |
| 谁在看 | 作者本人 | 所有调用方 |
| 容错 | 允许语法错、缺节点、断线 | 必须能跑通 |
| 变更频率 | 每分钟可能多次 | 每次都是一次「事件」 |
| 出错代价 | 自己调试一下 | 客户收到 400 / 错误回答 |
| 需要审计 | 不需要 | 需要（谁、何时、发布了什么） |

**「发布 = 复制」而不是「发布 = 打标记」**

本项目的实现是：`publish` 把 `graph_json` 的**值**写进 `published_graph_json`（JSONB 复制），并写 `published_at`。

| 方案 | 行为 | 问题 |
| --- | --- | --- |
| **复制快照**（本项目） | 发布后两边独立演化 | 占一份额外存储（图是 KB 级，可忽略） |
| 指针 / 版本号 | `published_version = 3`，读取时按版本取 | 必须保留历史版本表，否则「编辑即改动历史」；实现更重 |
| 共享同一份 | 保存即上线 | 编辑中间态直接暴露给客户（`04` §5.3 的五个后果） |

**为什么复制是对的**

- 图很小（节点 + 边，通常几十 KB），复制成本可忽略；换来的隔离是**语义级**的。
- 不需要版本表就能做到「线上不随编辑变化」；这是最小的实现。
- 代价：**没有历史快照链**，不能「回滚到上一版」——要回滚只能把旧图重新 `PUT` + `publish`（`02` 的遗留讨论）。

**这个隔离会带来哪些真实问题（诚实清单）**

| 问题 | 表现 | 本项目的处理 |
| --- | --- | --- |
| 发布时不校验节点数据 | 引用了已删除知识库、或带 `useHistory` 的图能发布成功 | 第一次对外调用才 400（`knowledge node ... references unknown knowledge base` / `llm node ... useHistory requires a conversation`） |
| 快照引用的资源会变 | 知识库被删 / 模型名变了 | 预检在**运行时**用 `app.ownerId` 校验，失败即 400 |
| 快照不会自动跟随字段升级 | 以后图 schema 加字段，旧快照仍是旧形状 | 迁移时需要考虑旧快照的兼容；本项目尚未遇到 |
| 无发布历史 | 不能看「上一版长什么样」 | 只能靠人工备份；后续可加 `published_versions` 表 |
| 无发布审计 | 不知道谁在何时发布 | `published_at` 只能给出「何时」，没有「谁」 |

> **一句话**：**「所见即所得」和「线上稳定」在同一个字段上是不可能同时成立的**；隔离不是架构洁癖，而是把两种风险模型分开的必需品。阶段 10 选择「复制一份」，是用最小代价买到最重要的那条性质。

## 6. 【技术讨论 3】凭证安全取决于攻击模型：密码要慢哈希，机器 key 要快哈希

**问题**：阶段 1 的用户密码用 `bcrypt`（成本因子 10），阶段 10 的 API Key 却用 `sha256`。为什么同样是「存哈希」，一个要慢、一个要快？

**答案的一句话**：**因为两者的「输入熵」和「验证频率」完全不同：密码是人选的、低熵、每次登录验一次；key 是 128 位随机、高熵、每个请求都验一次。**

**对照表（这是本篇最该记住的一张）**

| 维度 | 用户密码 | 机器 API Key |
| --- | --- | --- |
| 输入来源 | 人选（可能 `123456`） | `crypto.randomBytes(16)`（128 bit） |
| 熵 | 极低（几十亿量级） | 2^128（天文数字） |
| 主要威胁 | **拖库后离线爆破** | 泄露 / 在线猜测（后者不可行） |
| 需要「慢」吗 | **需要**（bcrypt 让每次尝试变贵） | **不需要**（爆破 2^128 次没有意义） |
| 能否按哈希建索引 | **不能**（bcrypt 每次加随机盐，结果不确定） | **能**（`sha256` 确定性） |
| 每次验证成本 | 一次登录（几十~几百 ms 可接受） | 每个请求（必须毫秒级） |
| 本项目实现 | `bcrypt`（`01-账号与认证/06-JWT与密码哈希.md`） | `sha256` + `UNIQUE(key_hash)` |

**为什么 bcrypt 不能用来存 API Key（两个硬伤）**

1. **无法索引查找**：bcrypt 的盐是随机的，同一个明文两次哈希结果不同，`WHERE key_hash = ?` 永远查不到。只能用「取出所有 key、逐条 `compare`」——**O(n)**，而且每个 `compare` 都要付成本因子。
2. **每次请求都付慢哈希**：公开接口是热路径，成本因子 10 意味着每个请求多几十~上百毫秒；QPS 一高就是灾难。

**为什么 `sha256` 在这里是安全的**

- 明文有 **128 bit** 随机熵：彩虹表、字典、模式猜测全部无效；暴力枚举 2^128 不可行。
- 不加盐没问题：盐的意义是「防止相同输入产生相同输出被批量破解」，而随机 key **本来就不会重复**。
- 确定性带来**唯一索引 + O(1) 查找**：`WHERE key_hash = ?` 一次 B-tree 命中。

**`prefix` 泄露了多少**

- `prefix` = 前 11 字符 = `sk-` + 8 位十六进制 = **32 bit** 明文。
- 剩余 **96 bit** 仍然不可猜。
- 为什么要存它：列表里要「认出这是哪把 key」（按环境 / 按团队），这是**为了可用性的有意妥协**；它不足以还原 key，也不足以缩短爆破到可行范围。

**写放大：`lastUsedAt` 是一次额外的 `UPDATE`**

- 每个成功请求都会 `UPDATE api_keys SET last_used_at = now()`（`03`）。
- 收益：运维能看出「哪把 key 还在用、什么时候用的」——这对轮换与下线至关重要。
- 代价：**每个请求多一次写**。QPS 高时应改为「异步批量刷新」或「按分钟节流」。
- 本项目是教学项目，选择「准确优先」；生产环境要在这里做取舍。

**限流未做（必须诚实）**

- 代码里留了注释：`// 生产环境应在此处加限流（按 key / 应用维度），本阶段不实现。`
- 没有限流时，一把泄露的 key 可以被无限次调用（成本由你承担）。
- 这是阶段 10 **唯一明确标注为「未实现」的安全能力**；讨论与后续方向见 `02`。

> **一句话**：**「哈希」不是一种算法，而是一个按威胁模型选参数的决策**。人选的秘密要「慢到爆破不划算」，机器生成的秘密要「快到每请求都能验」——同一个 `sha256`，用错地方就是漏洞，用对地方就是正确。

## 7. 【技术讨论 4】401 与 404 的选择，是信息泄露控制

**问题**：为什么「没带 key」是 401，「appId 不存在」是 404，而「key 不属于这个 app」又是 401？同样是「不让你用」，为什么要分这么细？

**答案的一句话**：**401 回答「你是谁」（认证），404 回答「你要的东西在不在」（资源）；把两者混用，要么泄露信息，要么让集成方无法排错。**

**本项目的判定顺序与状态码**

| 序 | 条件 | 状态码 | 文案 | 泄露了什么 |
| --- | --- | --- | --- | --- |
| 1 | 没有 key（两个头都空） | `401` | `Missing API key` | 什么都不泄露 |
| 2 | key 哈希不匹配 / 已撤销 | `401` | `Invalid API key` | **不查 app**，所以不泄露 app 是否存在 |
| 3 | key 有效，但不属于路径里的 `appId`：**应用不存在** | `404` | `App not found` | 向**持有有效 key 的人**泄露「这个 appId 不存在」 |
| 4 | key 有效，但不属于路径里的 `appId`：**应用存在** | `401` | `Invalid API key` | 不泄露「存在但不属于你」 |
| 5 | key 与 app 匹配，但**未发布** | `400` | `App is not published` | 不泄露（调用方本就知道自己的应用） |

**为什么第 1~2 步绝不查应用**

- 如果「key 无效」时也去查 `appId`，攻击者可以用任意无效 key 探测「哪些 appId 存在」（枚举 UUID 虽然难，但错误码差异本身就是信息）。
- 所以先认证、**认证失败立即 401**，连数据库都不碰 App 表。

**为什么第 3 步允许 404（这是有意的例外）**

- 能走到第 3 步的人**已经持有一把有效 key**——他们是平台的集成方，不是匿名攻击者。
- 对他们来说，`App not found` 与 `Invalid API key` 的区别是**排错的关键**：前者说明「appId 写错了」，后者说明「key 拿错了」。
- 代价：一个持有有效 key 的人可以探测「某个 appId 是否存在」。这是**有界泄露**（需要先有合法 key），换来的是可用性。
- 如果连这一点都不想泄露，第 3 步可以统一返回 401；本项目选择「可用性优先」，并在 `02` 里记录了这个取舍。

**与内部接口的对照（为什么那边一律 404）**

| 场景 | 内部接口（JWT） | 对外接口（API Key） |
| --- | --- | --- |
| 资源不存在 | `404` | `404`（第 3 步） |
| 资源存在但不属于你 | **`404`**（伪装成不存在） | **`401`**（第 4 步） |
| 为什么 | 用户可能是攻击者，必须隐藏存在性 | 调用方是持 key 的集成方，需要可区分的错误 |

- 阶段 2 的应用、阶段 9 的会话都遵循「不存在 / 不是我的 / 不是这个应用的」**一律 404**——因为它们是**人类用户**能随便尝试的接口。
- 对外接口的「key 不属于这个 app」返回 401 而不是 404：**认证失败**比「资源不存在」更准确，也不会让调用方误以为「应用被删了」。

**为什么「未发布」是 400 而不是 404 / 403**

- 404 会让人以为「地址写错了」；403 会让人以为「权限不足」。
- 真实原因是「应用存在、你有权、但当前状态不能服务」——这是**请求在当前资源状态下无法完成**，属于 400 家族。
- 文案 `App is not published` 直接把「该怎么做」（去发布）告诉调用方。

**客户端重试逻辑必须按状态码分流**

| 状态码 | 正确反应 | 错误反应 |
| --- | --- | --- |
| `401` | 检查 / 更换 key；**不要重试** | 无限重试同一把坏 key |
| `404` | 检查 `appId` / 应用是否被删 | 当成临时故障重试 |
| `400 App is not published` | 去发布；**不要重试** | 轮询式重试（永远不会成功） |
| `5xx` | 可退避重试 | 直接放弃 |

> **一句话**：**状态码不是「错误分类」，而是「给调用方的行动指令」。** 401 说「换凭证」、404 说「换地址」、400 说「改状态」——分得越准，集成方越不需要猜，也越不会把「配置错误」当成「服务抖动」去重试。

## 8. 【技术讨论 5】对外接口不是另一套协议：同一引擎、同一事件流

**问题**：为什么对外接口不单独写一套 SSE？「内部调试」和「对外服务」不是两种场景吗？

**答案的一句话**：**因为它们的「执行」是同一件事，只有「谁在调用」和「读哪张图」不同；为差异写两套协议，等于给同一条流水线装两个出口，迟早会分叉。**

**`precheck()` 抽取：把「运行前校验」变成唯一实现**

`EngineService` 里现在有三个方法：

```ts
// 草稿运行（JWT）
async run(appId, ownerId, inputs, conversationId?, userMessage?) {
  // 归属 → 草稿 → precheck(ownerId, graph, hasConversation) → 读历史/写 user → execute
}

// 对外运行（API Key）
async runPublished(appId, inputs) {
  // 应用存在 → 已发布快照 → precheck(app.ownerId, graph, false) → execute
}

// 预检（两者共用）
private async precheck(ownerId, graph, hasConversation) {
  // validateGraph + validateNodeData + validateKnowledgeNodes
}
```

**`run` 与 `runPublished` 的三处差异（只有三处）**

| 维度 | `run`（草稿 / 调试） | `runPublished`（对外） |
| --- | --- | --- |
| **身份来源** | JWT（`ownerId` 来自 token） | API Key（`appId` / `ownerId` 来自 `api_keys` 行） |
| **图来源** | `graph_json`（草稿） | `published_graph_json`（快照） |
| **会话支持** | 可选 `conversationId`（读历史 / 写消息） | 不支持（`hasConversation = false`，不写任何消息） |

**完全相同的东西（这才是重点）**

| 维度 | 是否相同 | 说明 |
| --- | --- | --- |
| `precheck` | ✅ 同一个方法 | 图校验 + 节点数据 + 知识库归属，错误文案一致 |
| 图编译（LangGraph builder） | ✅ 同一段代码 | 节点 / 条件边 / 环 / 迭代全部复用 |
| 事件构造器 | ✅ 同一套 | `run_started` / `node_started` / `token` / … / `run_finished` |
| 帧序列化 | ✅ 同一个 `formatSseFrame` | 一个空格都不能差 |
| 错误映射 | ✅ 同一套 | LLM / 工具 / 检索 / 迭代文案 |
| 响应头 | ✅ 相同 | `text/event-stream`、`no-cache`、`keep-alive` |

**为什么必须复用而不是另写**

1. **客户端可迁移**：为调试写的 `parseSseStream` 直接能解析对外流；第三方按契约写一次即可（`04` 的 curl 示例就是调试面板的同一套帧）。
2. **一致性可验收**：L6 的「`frames equal after normalize`」只有在共用构造器时才可能成立；两套实现永远差一点。
3. **缺陷只修一次**：工具事件、`usage` 省略、`retrieval` 顺序……每个语义改动只落一处；两套实现意味着两倍回归面。
4. **错误语义统一**：「请求级 400 vs 流内 `run_failed`」的双通道设计（阶段 4）对两个入口同样成立。

**`PublicRunRequest` 只含 `inputs` 的连锁效果**

- 契约里 `additionalProperties: false`（Pydantic `extra="forbid"` / DTO `forbidNonWhitelisted`）：在对外 body 里多传 `conversationId` → `400 conversationId should not exist`。
- 这是**有意的拒绝**：如果静默忽略，调用方会以为「会话生效了」，实际一条消息都没写——比报错更糟。
- 由此推出：**带 `useHistory` 的图可以发布，但对外调用一定 400**（`llm node <id> useHistory requires a conversation`）。发布校验只看图结构（`validateGraph`），不看节点数据，所以这个矛盾要等到第一次对外调用才暴露。这是本阶段一个**已知的产品级缺口**（见 §9 坑 3）。

**与阶段 9 的一个细节差异**

- `run` 的 `run_started` 在**有会话时**带 `conversationId`；`runPublished` 永远不带（`hasConversation = false`）。
- 所以 L6 里 `run_started` 的键集合是 `["runId","appId"]`——与阶段 9 的「无会话运行」**逐字节相同**。这意味着：**对外流 = 阶段 9 的无会话调试流**，一个字都不多。

> **一句话**：**对外接口不是「第二套产品」，而是「同一台引擎的第二个入口」。** 入口可以有两个，协议只能有一个；把差异限制在「身份 / 图来源 / 会话」三处，是这个设计能成立的全部原因。

## 9. 常见坑汇总（跨阶段 10）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **迁移后 HNSW 被删** | 检索变慢但不报错 | 本次 `DROP INDEX` 写进了 **`add_api_keys` 同文件**；检查迁移文件、删掉语句、跑 `db:index`（§3.2） |
| 2 | **`api_keys` 少了唯一索引** | 鉴权全表扫描；理论上可插入重复哈希 | 确认 `api_keys_key_hash_key`（L2） |
| 3 | **带 `useHistory` 的图发布成功** | 第一次对外调用 `400 llm node ... useHistory requires a conversation` | 发布只做图结构校验；对外运行不支持会话（§8）；发布前先对 `llm` 节点关掉 `useHistory` |
| 4 | **对外 body 带 `conversationId`** | `400 conversationId should not exist` | `PublicRunRequest` 只有 `inputs`（`additionalProperties: false`） |
| 5 | **只改草稿就想上线** | 对外仍输出旧结果 | 必须重新 `POST .../publish`（L5） |
| 6 | **发布前忘了保存草稿** | 上线的是上一次保存的图 | 前端 `handlePublish` 已先 `putDraft`；用 curl 时要先 `PUT` |
| 7 | **把 `prefix` 当完整 key** | 401 `Invalid API key` | `prefix` 只有 11 字符；完整 key 只在 201 响应里（L3） |
| 8 | **明文 key 只显示一次却没保存** | 关掉区块后无法找回 | 只能撤销重建；后端不存明文（`04` §7.5） |
| 9 | **撤销后指望「恢复」** | 没有恢复接口 | 撤销不可逆；新建一把 key 即可（同名可复用） |
| 10 | **撤销后 `lastUsedAt` 停在撤销前** | 以为撤销没生效 / 以为 key 仍被调用 | 撤销后鉴权在写 `last_used_at` 之前就 401（§3.3.4） |
| 11 | **拿 A 的 key 调 B** | 401 `Invalid API key`，但 A 的 `lastUsedAt` 被刷新 | 先认证再比对 `appId`（§3.4.3） |
| 12 | **appId 不存在时用无效 key** | 期望 404，实际 401 | 认证失败优先，不查应用（§7 讨论 4） |
| 13 | **`missing required input`** | 对外 400 | 示例 body 的输入名与 `start.data.inputs` 不符（`04` §9.1） |
| 14 | **`X-API-Key: ` 空值** | 401 `Missing API key` | 空白值视为未提供；这是有意的（`03`） |
| 15 | **两种认证头同时传且不同** | 按 `X-API-Key` 生效 | 契约规定优先级（`03`） |
| 16 | **响应 `content-type` 带 charset** | 第三方严格比较时失败 | api-py 已显式设置 `text/event-stream`（L4） |
| 17 | **curl 不加 `-N`** | 终端一次性输出，看不出流式 | 加 `-N`（`04` §9.3） |
| 18 | **发布后刷新页面看不到时间** | 以为发布失败 | `GET .../published` 不返回 `publishedAt`（`04` §6.4） |
| 19 | **删除应用后 key 还在** | 孤儿行 | 外键 `ON DELETE CASCADE`（L2）；若还在，说明迁移未生效 |
| 20 | **限流缺失** | 泄露的 key 可无限调用 | 本阶段未实现（`02`）；生产必须补 |

## 10. 本篇复盘与知识点

**一句话总结阶段 10**：在既有的「图即数据、编译执行、有状态会话」之上，新增了一张 `api_keys` 表与一个**对外入口**：Key 只存 `sha256` 哈希与 `prefix`，明文只在 201 里出现一次；撤销是置 `revoked_at` 的软失效，立即 401；发布把草稿**复制**成 `published_graph_json`，对外运行只读快照，因此**改草稿不影响线上**；对外接口与调试运行**共用** `precheck` / 图编译 / 事件构造器 / 帧序列化，差异只有「身份来源 / 图来源 / 会话支持」三处，所以两者的 SSE **归一后逐字节相同**；9 组认证与发布错误文案两端一致。至此，P0 闭环（建应用 → 编排 → 执行 → 记忆 → 发布 → 被外部调用）闭合。

**本篇学到的工程 / 架构要点**

1. **P0 的最后一环是「被调用」**：能编排不等于能交付；没有对外入口，产品只是工作室。
2. **草稿/快照隔离是基石**：编辑与上线是两种风险模型；发布 = 复制，不是共享、也不是指针。
3. **凭证哈希按威胁模型选**：密码慢哈希（低熵、低频），机器 key 快哈希（高熵、每请求）。
4. **`sha256` 的确定性换来了 O(1) 查找**：`UNIQUE(key_hash)` 是性能与正确性的同一个来源。
5. **401/404 是行动指令**：401 换凭证、404 换地址、400 改状态；混用会让集成方把配置错误当故障重试。
6. **对外不是第二套协议**：同一引擎、同一事件流；差异被压缩到三处，才有一致性可言。
7. **一次性明文是 UX 与安全的交点**：后端不给，前端不能编；只能「当场展示 + 明确警告」。
8. **负向证据最有价值**：L5 的「改草稿后线上不变」比「发布后能跑」更能证明隔离生效。

**遗留到下阶段**

- 没有限流（每 key / 每应用维度）；泄露的 key 可无限调用。
- 没有 key 轮换流程（先建新、再撤旧的一键操作）与过期时间（`expires_at`）。
- 没有发布历史 / 回滚：只有最新快照，`publishedAt` 也只在发布响应里可见。
- 发布不校验节点数据（`useHistory` / 知识库引用），问题留到第一次对外调用。
- 对外运行不支持会话（`PublicRunRequest` 只有 `inputs`），无法做「对外多轮」。
- 没有按 key 的用量统计 / 配额 / 审计日志（只有 `lastUsedAt`）。
- `lastUsedAt` 每请求一次 `UPDATE`，高 QPS 下需要异步 / 节流。
- 没有把 L1~L7 固化成 CI 断言（唯一索引、HNSW 存在、35 字符、9 组 byte-equal、L5 隔离）。

**基础技术要点**：发布 = 复制快照 · 草稿 vs 快照隔离 · `api_keys` 四元组（`name` / `prefix` / `hash` / `revoked_at`） · `sk-` + 32 hex · `prefix` = 11 · `sha256` 确定性 + 唯一索引 · 一次性明文 · 软撤销 · 双认证头 · `apiKeyAuth` · `PublicRunRequest` 只含 `inputs` · `precheck()` 复用 · `run` vs `runPublished` 三处差异 · 401/404 信息泄露控制 · 对外 SSE 与调试运行同构。
