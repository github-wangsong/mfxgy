# 04 · 前端发布面板与调用示例

> 所属：阶段 10 · 发布与 API
> 本篇覆盖：画布右侧新增的「**发布与 API**」面板——**发布状态三态**、**一次性明文密钥**、**撤销**、**调用示例（curl）**，以及这些 UI 背后的语义：为什么「保存草稿」不等于「上线」、为什么列表永远拿不到明文、为什么示例里的地址不能硬编码。
> **本篇首次教学**：**「发布」是显式动作**（保存 = 本地编辑，发布 = 上线，两者是两条语义） · **用 HTTP 状态码驱动 UI 分支**（`200` = 已发布 / `404` = 从未发布） · **一次性密钥的 UX**（创建后必须当场展示明文：醒目区块 + 复制按钮 + 明确警告；关闭后只留 `prefix`） · **前端不能弥补后端的安全设计**（后端不返回明文，前端就无法「想办法」展示） · **撤销不是删除，是让它失效**（条目保留 + 标记，按钮消失） · **调用示例放进产品里的价值**与 **`curl -N` 关闭缓冲让 SSE 逐段可见** · **示例地址从 `NEXT_PUBLIC_API_BASE` 推导**（不在示例里硬编码端口）。
> 发布语义、API Key 契约（四元组 / `prefix` / `apiKeyAuth` / `PublicRunRequest`）见本阶段 `01-发布语义与API-Key契约.md`；慢哈希 vs 快哈希、软撤销、限流等安全论证见 `02-API-Key安全设计.md`；`precheck()`、`runPublished`、双认证头与校验顺序见 `03-对外SSE接口与双后端对齐.md`；分层验收见 `05-验收.md`。
> 受控输入、列表渲染 `map`+`key`、三态（loading/error/empty）与带鉴权 `fetch` 见 `02-应用管理/06-前端应用列表页.md`；`NEXT_PUBLIC_*` 构建期内联见 `00-项目初始化/07-NextJS起步.md`；`formatMessageTime` 与气泡渲染见 `09-会话与记忆/04-Python对齐与前端会话面板.md`；`parseSseStream` 见 `04-执行引擎/06-前端SSE客户端与运行面板.md`——以上**直接使用、不重讲**。

## 1. 本篇目标

做完这一篇，你能：

- 说清 **为什么「保存草稿」不能自动上线**：保存是**编辑动作**（高频、可随时回退），发布是**上线动作**（低频、需要评审与可追溯）；把两者合并会让「另存一次格式」等于「改线上行为」。
- 说清 **发布状态为什么由 HTTP 状态码决定**：`GET /apps/{id}/graph/published` 在「从未发布」时返回 **404**（`Graph not published`），在「已发布」时返回 **200** + 图；前端据此把 `status` 置为 `never` / `published`，而不是靠「图是不是空」来猜。
- 说清 **为什么「发布时间」只可能来自发布响应**：`GET .../graph/published` 的响应体**只有图、没有 `publishedAt`**（见 `01`），所以进入页面时只能显示「已发布」；时间只能来自本页 `POST .../graph/publish` 的响应。**刷新后时间消失是契约决定的，不是 bug**。
- 说清 **一次性密钥的 UX 三件套**：醒目（橙色边框 + 提示文案）、可复制（`navigator.clipboard` + 失败回退提示）、有警告（「此密钥只显示这一次」）；因为**明文只在 201 响应里出现一次**，关掉区块就再也拿不到。
- 说清 **为什么列表不能显示明文**：后端的 `ApiKeyResponse` **根本没有 `key` 字段**，只有 `prefix`（前 11 字符）。前端不是「不想显示」，是**拿不到**——**前端无法弥补后端的安全设计**。
- 说清 **撤销的心智**：`DELETE /api-keys/{id}` 不是删行，是把 `revokedAt` 置为当前时间；条目继续出现在列表里、带「已撤销」标记，撤销按钮消失，而**再次调用立即 401**。
- 说清 **调用示例为什么放进产品**：把「怎么接」写在用户看得到的地方，降低接入门槛；示例里的**端口跟随后端地址**（`NEXT_PUBLIC_API_BASE`），不硬编码。
- 说清 **`curl -N` 的作用**：关闭 curl 的输出缓冲，让 SSE 的每一帧**到达即打印**；不加 `-N` 时 curl 会攒够缓冲区再输出，「流式」看起来像「一次性返回」。
- 独立完成一次前端实测：状态「从未发布」→ 点「发布当前草稿」→ 「已发布 · `<ISO 时间>`」；新建 `ui-demo` → 看到警告 → 剪贴板读回 35 字符明文；关闭后页面不再出现明文、列表只剩 `prefix`；撤销后显示「已撤销」；curl 调用后 `lastUsedAt` 更新；撤销后再调 401；`tsc --noEmit` 通过。

**验收标准（对齐总纲 §6 阶段 10 的前端部分）**

| # | 检查项 | 预期 |
| --- | --- | --- |
| 1 | 从未发布的应用 | 面板显示「从未发布」；`GET /apps/{id}/graph/published` 为 `404` |
| 2 | 发布当前草稿 | 先 `PUT` 草稿成功，再 `POST .../publish`；面板变「已发布 · `<publishedAt>`」 |
| 3 | 刷新页面 | 仍显示「已发布」（但没有时间，只显示「已发布快照可用」） |
| 4 | 新建 Key | 橙色区块出现；警告文案可见；明文可复制；`key` 长度 35 |
| 5 | 关闭区块 | 明文从 DOM 消失；列表只显示 `name` / `prefix…` / 时间 |
| 6 | 撤销 | 条目保留、显示「已撤销」、撤销按钮消失；再调用返回 `401` |
| 7 | 调用示例 | 地址与 `NEXT_PUBLIC_API_BASE` 一致；含 `-N`；可一键复制 |

## 4. 面板挂在哪儿：第三个 tab

const [panel, setPanel] = useState<'inspector' | 'run' | 'publish'>('inspector')

```tsx
gridTemplateColumns: panel === 'publish' ? '150px 1fr 460px' : '150px 1fr 340px',
```

```tsx
<button style={tabStyle(panel === 'publish')} onClick={() => setPanel('publish')}>
  发布与 API
</button>
```

**这段在干什么**：

- `panel` 是一个**三值联合类型**的本地状态：检查器（节点属性）、调试运行（阶段 4 起）、发布与 API（阶段 10）。三个面板**互斥**，同一时刻只渲染一个。
- 发布面板更宽（`460px`）：要在里面放明文 key、`prefix`、curl 示例与时间，`340px` 会频繁折行。
- tab 用 `tabStyle(active)` 的纯函数生成样式：**选中态是深底白字**，与未选中的白底黑字形成对比。这是「状态 → 样式」的最简写法，不需要额外的 CSS 类。
- **面板不占画布**：画布仍是 `1fr`，发布面板只是右侧 `aside` 的另一种内容。这样「改图 / 发布 / 看调用方式」在同一屏内完成，不用来回跳页。

> 发布面板是**只读展示 + 两个动作**（发布、增删 Key），没有拖拽、没有画布交互。把它塞进画布页而不是单开 `/apps/{id}/publish` 页面，是因为「发布」总是紧跟着「改图」发生：用户刚改完就想上线，跳页会打断心流。

## 5. 「保存草稿」与「发布当前草稿」是两条语义

### 5.1 两个按钮，两段代码

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（节选）**

```tsx
/** PUT 草稿；成功返回 null，失败返回需展示的文案（401 直接跳登录）。 */
const putDraft = useCallback(
  async (token: string): Promise<string | null> => {
    const res = await fetch(`${API_BASE}/apps/${appId}/graph`, {
      method: 'PUT',
      headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
      body: JSON.stringify(buildGraph()),
    })
    if (res.ok) return null
    if (res.status === 401) {
      router.replace('/login')
      return '未登录'
    }
    const body = (await res.json().catch(() => null)) as { message?: string } | null
    return body?.message ?? `HTTP ${res.status}`
  },
  [appId, buildGraph, router],
)
```

```tsx
async function handleSave(): Promise<void> {
  const token = localStorage.getItem('accessToken')
  if (token === null) {
    router.replace('/login')
    return
  }
  setError(null)
  setMessage(null)
  setBusy(true)
  try {
    const err = await putDraft(token)
    if (err !== null) {
      setError(err)
      return
    }
    setMessage('草稿已保存')
  } catch (err: unknown) {
    setError(err instanceof Error ? err.message : String(err))
  } finally {
    setBusy(false)
  }
}
```

```tsx
async function handlePublish(): Promise<void> {
  const token = localStorage.getItem('accessToken')
  if (token === null) {
    router.replace('/login')
    return
  }
  setError(null)
  setMessage(null)
  setBusy(true)
  try {
    const err = await putDraft(token)
    if (err !== null) {
      setError(err)
      return
    }
    const res = await fetch(`${API_BASE}/apps/${appId}/graph/publish`, {
      method: 'POST',
      headers: { Authorization: `Bearer ${token}` },
    })
    if (!res.ok) {
      if (res.status === 401) {
        router.replace('/login')
        return
      }
      const body = (await res.json().catch(() => null)) as { message?: string } | null
      setError(body?.message ?? `HTTP ${res.status}`)
      return
    }
    const data = (await res.json()) as PublishResponse
    setPublishState({ status: 'published', at: data.publishedAt })
    setMessage(`已发布 · ${data.publishedAt}`)
  } catch (err: unknown) {
    setError(err instanceof Error ? err.message : String(err))
  } finally {
    setBusy(false)
  }
}
```

**这段在干什么**：

- `putDraft` 返回 `string | null`：**`null` 表示成功**，字符串表示要展示的错误文案。这是一种「错误即值」的写法——调用方不需要 `try/catch`，只需判断是否为 `null`。
- `handleSave` 只做一件事：`PUT /apps/{id}/graph`。它改的是 `graph_json`（草稿）。
- `handlePublish` 做两件事：**先 `putDraft`，再 `POST /apps/{id}/graph/publish`**。第二步改的是 `published_graph_json`（已发布快照）。
- 先保存再发布，是为了让「**你屏幕上看到的图**」就是「**即将上线的那份图**」。如果先发布再保存，用户会以为自己发布的是刚拖出来的节点，其实上线的是上一次保存的版本——这是最典型的「所见非所得」。
- `putDraft` 失败时直接 `return`，**不会**发出 `publish` 请求：图非法（如缺 `start`）时，服务端 `publish` 也会 400，但提前拦住能给出更明确的上下文。

### 5.2 两条语义的对照

| | 保存草稿 | 发布当前草稿 |
| --- | --- | --- |
| 接口 | `PUT /apps/{id}/graph` | `POST /apps/{id}/graph/publish` |
| 写入字段 | `graph_json`（草稿） | `published_graph_json` + `published_at` |
| 谁看得到 | 只有登录用户（画布 / 调试运行） | **第三方**（`POST /public/apps/{appId}/run`） |
| 频次 | 高（每改几个节点就存一次） | 低（一次「上线」） |
| 失败后果 | 画布内容没存上 | 线上行为不对 / 未切换 |
| 心智 | **本地编辑** | **上线** |

### 5.3 为什么不能让「保存草稿」自动上线

如果 `PUT /apps/{id}/graph` 顺手把 `published_graph_json` 也更新了，会有五个立刻出现的问题：

| 问题 | 具体表现 |
| --- | --- |
| **编辑过程中的中间态会被上线** | 用户拖了一个节点、还没连线，画布自动保存一次 → 线上拿到一张不完整的图 → 第三方调用 400 或结果缺失 |
| **没有评审点** | 团队里「能进画布的人」= 「能改线上的人」；想加一个 review 步骤都没有地方挂 |
| **无法回滚** | 每次保存都覆盖快照，没有任何「上一版」可退；线上出错只能靠手改回去 |
| **调试与线上互相污染** | 调试运行读草稿（`03` 的 `run`），线上读快照（`runPublished`）；一旦合并，调试时改一个 prompt 就改变了客户看到的回答 |
| **失去「发布」这个事件** | 没有发布动作，就没有发布时间、没有发布审计、也没法做「草稿 vs 线上」的差异对比（`05` L5 的核心验收也就无从谈起） |

> **一句话**：保存回答「我改到哪里了」，发布回答「客户现在会得到什么」。把两个问题合并成一个动作，等于让**每一个编辑动作都成为一次上线**。

**写错会怎样**

| 错误写法 | 现象 |
| --- | --- |
| `handlePublish` 只调 `publish`、不先 `putDraft` | 发布的是**上一次保存**的图；界面上刚改的节点没上线，且没有任何提示 |
| 把 `publish` 放在 `putDraft` 之前 | 草稿非法时先发布成功、再保存失败，出现「线上是旧图、草稿是新图」的错位 |
| `putDraft` 失败后仍然继续 `publish` | 用户看到的是「操作失败」+「已发布」两条矛盾提示（本页 `setMessage` 会被覆盖，实际只剩错误） |
| 自动保存时顺带发布 | 编辑中间态被上线，第三方随机收到 400 `App is not published` 之外的图校验错误 |

## 6. 发布状态三态：用 HTTP 状态码驱动 UI 分支

### 6.1 状态类型

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（节选）**

```tsx
/**
 * 发布状态：`GET /apps/{id}/graph/published` 只返回图（没有 publishedAt），
 * 所以进入页面时只能区分「已发布 / 从未发布」；`at` 来自本页发布接口的响应。
 */
type PublishState = {
  status: 'loading' | 'published' | 'never' | 'error'
  at: string | null
}
```

**这段在干什么**：

- `status` 把「接口事实」压缩成**四个互斥取值**：`loading`（请求中）、`published`（200）、`never`（404）、`error`（其它/网络异常）。
- `at` 与 `status` **分开存**：状态可以由 `GET` 决定，时间只能由 `POST publish` 提供。两者来源不同，所以不能塞进一个字符串。
- 为什么不用 `publishedAt: string | null` 直接表示三态？因为 `null` 同时可能意味着「从未发布」和「已发布但没时间」——**一个 `null` 表达两件事，早晚会有人读错**。

### 6.2 读状态：200 / 404 两个分支

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（节选）**

```tsx
/** 进入页面时读发布状态：200 = 已发布（无 publishedAt），404 = 从未发布。 */
const loadPublishState = useCallback(
  async (token: string): Promise<void> => {
    const res = await fetch(`${API_BASE}/apps/${appId}/graph/published`, {
      headers: { Authorization: `Bearer ${token}` },
    })
    if (res.status === 401) {
      router.replace('/login')
      return
    }
    if (res.status === 404) {
      setPublishState({ status: 'never', at: null })
      return
    }
    if (!res.ok) {
      setPublishState({ status: 'error', at: null })
      return
    }
    // GET 只返回图；保留本页发布成功后拿到的 publishedAt。
    setPublishState((prev) => ({ status: 'published', at: prev.at }))
  },
  [appId, router],
)
```

**这段在干什么**：

- **不读响应体**：状态完全由 `res.status` 决定。`200` 说明快照存在；`404` 说明从未发布。响应体里的图只在需要「对比草稿与线上」时才有用，这个面板不展示图。
- **`404` 不是错误**：它是契约里「从未发布」的表达（`Graph not published`，见 `error-messages.md` §2）。把它当异常弹红字，会让每个新应用一打开就报错。
- **`401` 优先处理**：token 过期时直接回登录页，而不是显示「状态不可用」。
- **其它非 2xx** 才落到 `error`（如 500）。
- `setPublishState((prev) => ({ status: 'published', at: prev.at }))`：**用函数式更新保留旧的 `at`**。如果写成 `setPublishState({ status: 'published', at: null })`，那么「发布后又重新拉了一次状态」会把刚拿到的时间抹掉。

### 6.3 渲染：三种业务状态 + 两种过渡状态

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（节选）**

```tsx
<div style={{ display: 'flex', alignItems: 'center', gap: 8 }}>
  <div style={{ fontWeight: 600 }}>发布状态</div>
  {publishState.status === 'loading' && <span style={{ color: '#888', fontSize: 12 }}>读取中…</span>}
  {publishState.status === 'published' && (
    <span style={{ color: 'seagreen', fontWeight: 600, fontSize: 13 }}>已发布</span>
  )}
  {publishState.status === 'never' && (
    <span style={{ color: '#888', fontWeight: 600, fontSize: 13 }}>从未发布</span>
  )}
  {publishState.status === 'error' && <span style={{ color: 'crimson', fontSize: 12 }}>状态不可用</span>}
</div>
{publishState.status === 'published' && (
  <div style={{ fontSize: 12, color: '#555' }}>
    {publishState.at !== null
      ? `发布时间：${formatMessageTime(publishState.at)}`
      : '已发布快照可用'}
  </div>
)}
<button type="button" onClick={() => void handlePublish()} disabled={busy}>
  {busy ? '发布中…' : '发布当前草稿'}
</button>
```

**这段在干什么**：

- `loading` / `published` / `never` / `error` **四种状态各自渲染一个 `<span>`**，而不是 `if/else` 链。这样每一行的条件与显示内容都写在一起，读起来就是一张状态表。
- **业务三态**：`从未发布`（灰）、`已发布`（绿）、刚发布（绿 + 时间）。
- **两种过渡态**：`读取中…`（灰，首屏请求未回）、`状态不可用`（红，非 404 的失败）。
- `at !== null` 才显示时间；否则显示「已发布快照可用」。**绝不**用 `new Date()` 补一个「现在」——那是在**伪造发布时间**。
- 按钮文案随 `busy` 变成「发布中…」，并 `disabled`，避免连点发出两次发布（第二次会刷新 `publishedAt`，让时间看起来「跳动」）。

**状态机（记住这张表就够了）**

```
             GET /graph/published
                     │
      ┌──────────────┼───────────────┐
      │              │               │
    200            404            其它/网络
      │              │               │
  published        never           error
      │
  本页 POST publish 成功
      │
  published + at = publishedAt
```

### 6.4 实测

真实 headless Chrome（`api-ts` 3001 + web 3000）：

```
进入画布 → 发布与 API 面板 → 状态：从未发布
点「发布当前草稿」       → 提示：已发布 · 2026-10-23T13:42:26.294Z
                         状态标签：已发布；发布时间：2026/10/23 21:42:26
刷新页面                 → 状态标签：已发布；副标题：已发布快照可用
```

**结果解读**：

- 首次进入是 `404` → `从未发布`；点发布后 `POST` 返回 `publishedAt`，UI 立刻是「已发布 + 时间」。
- 刷新后**时间消失**：`GET` 的响应体里没有 `publishedAt`（见 `01`），前端只能保留标签。这不是前端偷懒，而是**契约没给**——前端不能编。
- 「已发布 · 2026-10-23T13:42:26.294Z」是 `setMessage` 拼的**原始 ISO 字符串**；下面那行「发布时间」走 `formatMessageTime`，显示**本地时区**（21:42:26）。两处格式不同是因为前者是调试提示、后者是正式展示；如果你希望统一，改 `setMessage` 的拼法即可，不影响任何语义。

> **404 的双重含义**：`GET /apps/{id}/graph/published` 对「应用不存在/不属于你」也返回 404（`App not found`）。本页是在画布已经加载成功之后才调它，所以 404 几乎只能是「从未发布」；但如果你把这个请求复用到别的页面，**必须先确认应用归属**，否则会把「无权访问」误显示成「从未发布」。

**写错会怎样**

| 错误写法 | 现象 |
| --- | --- |
| 把 `404` 当错误弹红字 | 每个新应用一打开就报错；用户以为系统坏了 |
| 用「图是否为空」判断是否发布 | 发布后把草稿清空，会被误判成「从未发布」 |
| `at` 用 `new Date().toISOString()` 补 | 刷新后显示一个假的发布时间，且每次刷新都变 |
| 函数式更新写成直接覆盖 `at: null` | 发布后立刻重拉状态，时间消失 |
| 发布按钮不禁用 | 连点两次，`publishedAt` 被刷新，用户以为「发布没生效」 |

## 7. 一次性密钥的 UX

### 7.1 创建：只在这一个响应里能拿到明文

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（节选）**

```tsx
// 刚创建的明文 key：只在这个区块里显示，关闭后不再出现。
const [newKeyPlain, setNewKeyPlain] = useState<{ name: string; key: string } | null>(null)
```

```tsx
/** 新建 API Key：成功后把**一次性明文 key**放进醒目区块，并刷新列表。 */
async function handleCreateApiKey(event: FormEvent<HTMLFormElement>): Promise<void> {
  event.preventDefault()
  const name = newKeyName.trim()
  if (name === '') return
  const token = localStorage.getItem('accessToken')
  if (token === null) {
    router.replace('/login')
    return
  }
  setApiKeyError(null)
  setCopyHint(null)
  setApiKeyBusy(true)
  try {
    const res = await fetch(`${API_BASE}/apps/${appId}/api-keys`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
      body: JSON.stringify({ name }),
    })
    if (res.status === 401) {
      router.replace('/login')
      return
    }
    if (!res.ok) {
      const body = (await res.json().catch(() => null)) as { message?: string | string[] } | null
      setApiKeyError(apiErrorMessage(body?.message) ?? `HTTP ${res.status}`)
      return
    }
    const created = (await res.json()) as CreatedApiKey
    setNewKeyPlain({ name: created.name, key: created.key })
    setNewKeyName('')
    await loadApiKeys(token)
  } catch (err: unknown) {
    setApiKeyError(err instanceof Error ? err.message : String(err))
  } finally {
    setApiKeyBusy(false)
  }
}
```

**这段在干什么**：

- `newKeyPlain` 只存**两个字段**：`name`（给标题用）与 `key`（明文）。**不写 `localStorage`、不写 URL、不写日志**——它只活在这个组件的内存里。
- `setNewKeyName('')` 清空输入框：创建成功后，输入框里那串名字已经没有用了，留着会让用户误以为「还能再建一个同名的」（实际上会 400）。
- `await loadApiKeys(token)`：立刻刷新列表，这样新条目马上出现在下方（显示 `prefix` 与「最后使用：从未使用」）。
- `apiErrorMessage` 兼容 `message` 是字符串或字符串数组：NestJS 校验管道可能给出数组；这里统一成一行（该工具函数在本页顶部早已定义，阶段 2 起的所有错误展示都复用它）。
- **错误不弹窗、只显示在表单下方**：创建失败（重名 / 名称过长）时，明文区块不影响，用户可以直接改名重试。

### 7.2 醒目区块：警告 + 只读输入 + 复制 + 关闭

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（节选）**

```tsx
{newKeyPlain !== null && (
  <div
    data-testid="new-api-key"
    style={{
      border: '2px solid #b26a00',
      background: '#fff8e6',
      borderRadius: 6,
      padding: 10,
      display: 'grid',

    }}
  >
    <div style={{ fontWeight: 700, color: '#b26a00' }}>新 API Key 已生成（{newKeyPlain.name}）</div>
    <p style={{ margin: 0, fontSize: 12, color: 'crimson', fontWeight: 600 }}>
      此密钥只显示这一次，关闭后无法再次查看
    </p>
    <input
      readOnly
      value={newKeyPlain.key}
      onFocus={(e) => e.currentTarget.select()}
      style={{ width: '100%', fontFamily: 'monospace', fontSize: 12 }}
    />
    <div style={{ display: 'flex', gap: 6 }}>
      <button type="button" onClick={() => void copyToClipboard(newKeyPlain.key, 'API Key ')}>

      </button>
      <button
        type="button"
        onClick={() => {
          setNewKeyPlain(null)
          setCopyHint(null)
        }}
      >

      </button>
    </div>
    {copyHint !== null && <div style={{ fontSize: 12, color: 'seagreen' }}>{copyHint}</div>}

```

**这段在干什么（UX 三件套）**：

| 要求 | 具体实现 | 为什么 |
| --- | --- | --- |
| **醒目** | `2px` 橙色边框 + `#fff8e6` 浅黄底 + 加粗标题 | 用户在页面上有一堆灰框；一次性信息必须**跳出视觉层级**，否则会被当成普通提示划过去 |
| **明确警告** | 红色加粗「此密钥只显示这一次，关闭后无法再次查看」 | 提前告知「关掉就没了」，避免用户点「关闭」之后才来问「key 在哪」 |
| **可复制** | `复制` 按钮 + 只读输入框（点击自动全选） | 35 字符的十六进制串**手动抄写必错**；按钮失败时还有提示（§7.3） |
| **显式关闭** | 「我已保存，关闭」——文案本身就是一个确认 | 关闭是**破坏性操作**（明文永久消失），按钮上写清后果，而不是一个 ✕ |

**其它细节**：

- `readOnly` 而不是 `disabled`：`disabled` 的输入框无法选中文本，`readOnly` 可以聚焦、可以全选、可以复制。
- `onFocus={(e) => e.currentTarget.select()}`：点进输入框即全选，用户按 `Ctrl+C` 就能复制；这是对「复制按钮不可用」环境的兜底。
- `fontFamily: 'monospace'`：密钥是 `sk-` + 32 位十六进制，等宽字体让 `0/O`、`1/l` 的辨识更容易。
- `data-testid="new-api-key"`：给浏览器自动化一个稳定锚点（`05` 的实测就靠它定位；不依赖文案，改文案不会让测试失效）。
- 关闭时同时 `setCopyHint(null)`：否则「已复制」的绿字会残留到下一次打开。

### 7.3 复制：成功提示 + 失败回退

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（节选）**

```tsx
/** 复制到剪贴板，并在按钮旁给出结果提示（失败时提示手动复制）。 */
async function copyToClipboard(text: string, label: string): Promise<void> {
  try {
    await navigator.clipboard.writeText(text)
    setCopyHint(`${label}已复制`)
  } catch {
    setCopyHint('复制失败，请手动选择文本复制')
  }
}
```

**这段在干什么**：

- `navigator.clipboard.writeText` 返回 Promise：成功才提示「已复制」。**不能**在调用后立刻提示成功——权限被拒或非安全上下文时会静默失败。
- `catch` 里给的是**可执行的替代方案**（手动选择文本复制），而不是「复制失败」四个字——用户需要知道下一步怎么做。
- `label` 让同一个函数服务两处：`API Key ` 与 `curl `；提示语分别是「API Key 已复制」「curl 已复制」。
- **剪贴板 API 需要安全上下文**：`https` 或 `localhost`。用 `http://192.168.x.x:3000` 打开时会被拒绝——此时失败提示与输入框全选就是兜底。

- `prefix` 后面跟一个省略号 `…`：明确告诉用户「这不是完整 key」。`prefix` 是明文的前 11 个字符（`sk-` + 8 位十六进制），用于**辨识**（「线上跑的是哪把 key」），不足以还原 key。

### 7.5 为什么列表不展示明文：前端不能弥补后端的安全设计

**契约里根本没有这个字段**（`packages/contract/src/index.ts`）：

```ts
/** API Key 对外视图（**不含明文 key**，只有 `prefix`）。 */
export interface ApiKeyResponse {
  id: string
  appId: string
  name: string
  /** 明文 key 的前 11 个字符（如 `sk-1a2b3c4d`），用于辨识；不是密钥本身 */
  prefix: string
  createdAt: string
  lastUsedAt: string | null
  revokedAt: string | null
}

/** POST /apps/{id}/api-keys 的响应体：在 ApiKeyResponse 之外附带**一次性明文 key**。 */
export interface CreateApiKeyResponse extends ApiKeyResponse {
  /** 明文 key（`sk-` + 32 位十六进制，共 35 字符），**仅此一次返回** */
  key: string
}
```

- `GET /apps/{id}/api-keys` 返回的是 `ApiKeyResponse[]`——**没有 `key`**。
- 后端数据库里也只有 `key_hash`（`sha256`）与 `key_prefix`，**明文不落库**（见 `02`）。所以「再查一次」这件事在服务端**物理上不可能**。
- 于是前端只有两个选择：如实说明「只能看这一次」，或者**编一个假的明文**（比如把 `prefix` 拼成 `prefix + "…"` 假装完整）。后者会让用户复制走一个永远 401 的字符串——比不给更糟。

> **原则**：**UI 能展示什么，取决于 API 返回什么。** 当前端拿不到明文时，正确做法是**把限制说清楚**（警告文案 + 一次性展示），而不是用「看起来像 key」的占位符掩盖。**安全设计在服务端，前端不可能「补」回来**；任何「前端想办法显示」的念头，实际都是在制造一个错误的安全感。

**写错会怎样**

| 错误写法 | 现象 |
| --- | --- |
| 把 `key` 存进 `localStorage` | 明文长期留在浏览器；XSS 或共用电脑即泄露 |
| 关闭后从某个缓存里「恢复」明文 | 缓存里根本没有（后端不返回），只能显示占位符；用户复制到无效 key |
| 用 `prefix` 拼出「完整 key」展示 | 用户复制后 401，且无法自行判断哪里错了 |
| 创建失败也置 `newKeyPlain` | 显示一个空/错误的区块；用户以为拿到了 key |
| 复制后不提示结果 | 剪贴板权限被拒时用户完全无感，粘贴出旧内容 |

## 8. 撤销：不是「删除」，是「让它失效」

### 8.1 代码

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（节选）**

```tsx
/** 撤销 API Key（DELETE /api-keys/{id}），成功后刷新列表以显示「已撤销」。 */
async function handleRevokeApiKey(id: string): Promise<void> {
  const token = localStorage.getItem('accessToken')
  if (token === null) {
    router.replace('/login')
    return
  }
  setApiKeyError(null)
  setApiKeyBusy(true)
  try {
    const res = await fetch(`${API_BASE}/api-keys/${id}`, {
      method: 'DELETE',
      headers: { Authorization: `Bearer ${token}` },
    })
    if (res.status === 401) {
      router.replace('/login')
      return
    }
    if (!res.ok) {
      const body = (await res.json().catch(() => null)) as { message?: string | string[] } | null
      setApiKeyError(apiErrorMessage(body?.message) ?? `HTTP ${res.status}`)
      return
    }
    await loadApiKeys(token)
  } catch (err: unknown) {
    setApiKeyError(err instanceof Error ? err.message : String(err))
  } finally {
    setApiKeyBusy(false)
  }
}
```

**这段在干什么**：

- `DELETE /api-keys/{id}` 成功是 **204**（无响应体），所以这里**不解析 body**，直接 `loadApiKeys(token)` 刷新。
- **刷新而不是本地改状态**：撤销后的「已撤销」标记与 `revokedAt` 时间都来自服务端；本地只把按钮藏起来会让条目信息不完整（少了撤销时间）。
- 失败（404 `API key not found`）显示在表单下方；不弹窗、不打断画布。
- `apiKeyBusy` 同时禁用「新建」与「撤销」：两个写操作共用一个忙碌标记，避免并发请求把列表刷成中间态。

### 8.2 撤销的心智：让它失效，不是让它消失

| | 物理删除（`DELETE` 行） | 软撤销（本项目的做法） |
| --- | --- | --- |
| 数据库 | 行消失 | 行保留，`revoked_at` 置时间 |
| 列表 | 条目消失 | 条目保留，带「已撤销」标记 |
| 能否审计 | 不能（谁在什么时候撤销了哪把 key 都无从查） | 能（`revoked_at` 就是审计线索） |
| 同名重建 | 可以（行没了） | 可以（重名检查只针对未撤销的） |
| 误删恢复 | 不可能 | 数据还在，可人工改回 `null`（本项目未提供接口） |
| 对外行为 | 立即失效 | 立即失效（无宽限期） |

**UI 上的三个可见结果**：

1. 条目**仍然显示**，`opacity: 0.6`，标题后多一个红色「已撤销」。
2. 「撤销」按钮**消失**（`item.revokedAt === null` 才渲染）。
3. 时间行**多一段**「· 撤销：`<本地时间>`」。

**实测**：

```
撤销前：ui-demo | sk-ec5a2884… | 创建 21:42:26 · 最后使用 21:42:34 | [撤销]
点撤销 → 刷新列表
撤销后：ui-demo | sk-ec5a2884… | 创建 21:42:26 · 最后使用 21:42:34 · 撤销 21:43:02 | 已撤销
```

随后用同一把 key 调对外接口：

```json
{"statusCode":401,"message":"Invalid API key","error":"Unauthorized"}
```

**结果解读**：

- 撤销是**立即生效**的：没有「等待缓存过期」的宽限期（`02` 会讨论这个取舍）。
- 条目保留是**产品需求**：用户需要看到「这把 key 曾经存在、什么时候被谁停用」，而不是一片空白。
- 「最后使用」停在撤销前的时间：撤销后再调用会在鉴权阶段就 401，**不会**刷新 `lastUsedAt`（`02` 的写放大讨论会用到这个事实）。

**写错会怎样**

| 错误写法 | 现象 |
| --- | --- |
| 撤销后本地 `filter` 掉条目 | 用户点完「撤销」发现整行消失，以为「删除了」，无法确认撤销时间 |
| 撤销后不刷新列表 | 「已撤销」标记不出现，按钮还在，用户会再点一次（404） |
| 用 `PATCH` 传 `{revokedAt: null}` 当作「恢复」 | 后端没有该接口，404；前端显示了不存在的操作 |
| 撤销按钮用 `confirm()` 之外的隐式操作 | 一次误点让线上集成立刻 401（本项目未加二次确认，是可接受的取舍：撤销本身可重建 key） |

| 放在 README 里 | 放在产品里（本项目） |
| --- | --- |
| 用户要先找到文档、再对应到自己的应用 | 打开应用就能看到「调用我自己的这个应用」的完整命令 |
| 地址 / key / 输入名都是占位符，需要自己替换 | 地址是本页真实使用的 base、输入名来自本图的 `start`、key 位对应真实 `prefix` |
| 文档版本容易过期 | 与代码同源渲染，**不会过期** |
| 接入门槛 = 读文档 + 试错 | 接入门槛 = 复制 + 粘贴（只需补上明文 key） |

> **一句话**：接入成本越低，被接入的概率越高。把示例放在离应用最近的地方（而不是离开发者最近的文档里），是**产品设计**而不是「写文档」。

### 9.1 生成 curl

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`（节选）**

```tsx
// 对外调用示例：端口跟随当前 API_BASE；key 位用未撤销 key 的 prefix 占位。
const activeApiKey = apiKeys.find((item) => item.revokedAt === null) ?? null
const keyPlaceholder = activeApiKey === null ? '<你的 key>' : `<${activeApiKey.prefix}…>`
const firstInputName = startInputs[0]?.name ?? 'topic'
const curlExample = `curl -N -X POST ${API_BASE}/public/apps/${appId}/run \\
  -H "X-API-Key: ${keyPlaceholder}" -H "Content-Type: application/json" \\
  -d '{"inputs":{"${firstInputName}":"你好"}}'`
```

```tsx
<div style={{ fontWeight: 600 }}>调用示例</div>
<p style={{ fontSize: 11, color: '#888', margin: 0 }}>
  对外接口无需登录，用 <code>X-API-Key</code>（或 <code>Authorization: Bearer</code>）鉴权，
  返回与调试运行一致的 SSE。
</p>
<pre style={{ whiteSpace: 'pre-wrap', wordBreak: 'break-all', /* ... */ }}>
  {curlExample}
</pre>
<button type="button" onClick={() => void copyToClipboard(curlExample, 'curl ')}>
  复制 curl
</button>
```

**这段在干什么**：

- `${API_BASE}` 来自 `process.env.NEXT_PUBLIC_API_BASE ?? 'http://localhost:3001'`（见 §9.2）。**示例里的 host:port 与实际请求完全一致**。
- `keyPlaceholder` **不是**真 key，而是 `<sk-ec5a2884…>`：`prefix` 已经在列表里公开，用它做占位既能让用户对号入座（「哦，是这把」），又**不会**把明文写进可复制的文本。
- 没有未撤销的 key 时用 `<你的 key>`：明确告诉用户「先去上面建一个」。
- `firstInputName` 取 `start` 的第一个输入变量名（缺省 `topic`）：示例的 body 要**能被直接粘贴运行**，所以必须用这张图真实存在的输入名。输入名写错会得到 `400 missing required input: topic`。
- `whiteSpace: 'pre-wrap'` + `wordBreak: 'break-all'`：长 URL 与 header 在窄面板里自动折行，不会撑破布局。
- 「复制 curl」复用 `copyToClipboard`：与复制 key 同一套成功/失败提示。

### 9.2 地址从环境变量推导，不硬编码

```ts
const API_BASE = process.env.NEXT_PUBLIC_API_BASE ?? 'http://localhost:3001'
```

`NEXT_PUBLIC_*` 在**构建期**被内联进客户端 bundle（首次教学见 `00-项目初始化/07-NextJS起步.md`）。因此：

- 默认配置下，页面请求打 `3001`（api-ts），示例也打 `3001`。
- 把 `apps/web/.env` 改成 `NEXT_PUBLIC_API_BASE=http://localhost:8000` 并重启 web，页面与示例**同时**切到 FastAPI。
- **示例里写死 `3001` 或 `8000` 都是错的**：写死 `3001` 时，切到 Python 后端的用户复制示例会打到另一个后端（数据同一张库，但版本/行为可能不同）；写死 `8000` 时，默认配置下示例直接打不通。

| 写法 | 默认配置 | 切到 8000 后 |
| --- | --- | --- |
| `${API_BASE}`（本篇） | 正确（3001） | 正确（8000） |
| 写死 `http://localhost:3001` | 正确 | **错误**：示例与页面不一致 |
| 写死 `http://localhost:8000` | **错误**：默认没起 Python 时复制即失败 | 正确 |
| 写相对路径 `/public/apps/...` | 打到 Next.js（3000） | 同样错（前端没有该路由） |

> 前端与后端**跨端口**部署，相对路径不可能工作；唯一正确来源就是「页面自己用的那个 base」。

### 9.3 `-N` 的作用：让 SSE 逐段可见

```bash
curl -N -X POST http://localhost:3001/public/apps/<APP_ID>/run \
  -H "X-API-Key: <sk-ec5a2884…>" -H "Content-Type: application/json" \
  -d '{"inputs":{"q":"你好"}}'
```

- `-N` 即 `--no-buffer`：**关闭 curl 的输出缓冲**，收到一块就写一块。
- 不加 `-N` 时，curl 会把响应攒在缓冲区里（尤其是管道 / 重定向到文件 / 某些终端），表现为「命令卡住几秒，然后一次性吐出全部帧」——**SSE 看起来像普通 JSON**。
- 这与阶段 4 前端遇到的 `TextDecoder` / React 批处理问题是**同一类现象的另一端**：**流式协议的「逐段」必须由消费方保证**，服务端只能保证「边产生边发」。
- 重定向到文件时 `-N` 同样有效（`curl -N ... > out.sse`），这也是 `05` 的验收脚本能实时观察帧的原因。

### 9.4 实测：调用后的 `lastUsedAt`

```
复制示例 → 把 key 占位换成真实明文（创建时复制的那串）
执行 curl -N → 终端逐帧打印：
  event: run_started
  data: {"runId":"...","appId":"..."}
  event: node_started ...
  ...
  event: run_finished
  data: {"runId":"...","outputs":{"answer":"echo: Hello 你好"},"elapsedMs":...}

回到面板刷新列表 → 最后使用：2026/10/23 21:42:34
```

- `lastUsedAt` 由**服务端在鉴权成功后**写入（`02` 会讲这个写放大），前端只负责显示。
- 它显示为本地时间（`formatMessageTime`），而接口响应里是 UTC ISO（`13:42:34Z`）——**存储/传输用 UTC，展示用本地**，这是阶段 2 起就定下的规范。
- 撤销后再次执行同样的 curl → `401 Invalid API key`，且 `lastUsedAt` **保持不变**（鉴权失败，更新语句不会执行）。

**写错会怎样**

| 错误写法 | 现象 |
| --- | --- |
| 示例硬编码端口 | 切换后端后示例打错服务；或默认环境下连不上 |
| 示例里的 key 位写成 `sk-xxx` 之类假串 | 用户直接复制 → 401；不知道要先创建 key |
| 不加 `-N` | 终端看起来「卡住然后一次性输出」，用户以为不是流式 |
| 在 Windows PowerShell 里直接粘贴示例 | `curl` 是 `Invoke-WebRequest` 的别名，参数不兼容直接报错；改用 `curl.exe -N ...` 或 Git Bash |
| 示例 body 用 `topic` 而图里输入叫 `q` | `400 missing required input: q`（`error-messages.md` §4.2） |
| 示例地址写成 `http://127.0.0.1:3001` 而页面用 `localhost` | 一般等价；但若后端只监听 IPv4 或存在 hosts 差异，会出现「页面能通、示例不通」的排查噪音 |

## 11. 常见坑

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | 把 404 当错误 | 新应用一打开就红字「状态不可用」 | 404 = 从未发布（§6.2） |
| 2 | 刷新后时间消失当成 bug | 「发布时间怎么没了」 | `GET` 不返回 `publishedAt`（§6.4） |
| 3 | 用 `new Date()` 补发布时间 | 每次刷新时间都变 | 只信服务端返回值（§6.3） |
| 4 | 发布前不保存草稿 | 上线的是上一次保存的图 | `handlePublish` 先 `putDraft`（§5.1） |
| 5 | 保存草稿顺手发布 | 编辑中间态被上线 | 两条语义分开（§5.3） |
| 6 | 把明文 key 存 `localStorage` | 长期泄露风险 | `newKeyPlain` 只存内存（§7.1） |
| 7 | 关闭后「再查一次 key」 | 查不到，显示占位符 | 后端只存哈希，物理上拿不到（§7.5） |
| 8 | 用 `prefix` 拼完整 key | 用户复制后 401 | `prefix` 只有 11 字符，不是密钥（§7.4） |
| 9 | 不显示「只显示一次」警告 | 用户关掉后才来问 key | 警告 + 显式关闭按钮（§7.2） |
| 10 | 撤销后本地删条目 | 用户以为「删除了」 | 软撤销：保留 + 标记（§8.2） |
| 11 | 撤销后不刷新列表 | 按钮还在，重复点 → 404 | `await loadApiKeys`（§8.1） |
| 12 | 示例硬编码端口 | 切后端后示例打错服务 | 用 `API_BASE` 推导（§9.2） |
| 13 | 示例缺 `-N` | 终端一次性输出，看不出流式 | 加 `-N`（§9.3） |
| 14 | 示例输入名与图不符 | 400 `missing required input` | 取 `startInputs[0].name`（§9.1） |
| 15 | 连点发布 | `publishedAt` 被刷新 | 按钮 `disabled={busy}`（§6.3） |
| 16 | 剪贴板 API 在非 localhost 下失败 | 复制按钮无反应 | 需要安全上下文；有失败提示与全选兜底（§7.3） |
| 17 | 把「发布」理解成「部署新代码」 | 找不到构建/部署入口 | 本项目的发布 = **复制一份图快照**，不是部署（`01`） |

## 12. 本篇复盘

**一句话总结**：发布面板把两个原本只存在于 API 里的概念变成了**可操作的 UI**——「发布」是一次**显式动作**（保存 ≠ 上线），状态由 **HTTP 状态码**驱动（200/404），快照的时间只来自发布响应；密钥只在创建时**当场展示一次**（醒目 + 复制 + 警告），之后列表只剩 `prefix`，因为后端根本不返回明文；撤销是**软失效**而不是删除；调用示例直接长在面板里，地址跟随后端地址、`-N` 让流式可见。

**本篇学到的工程要点**

1. **编辑动作与上线动作必须分开**：保存回答「我改到哪了」，发布回答「客户会得到什么」。
2. **状态码就是状态**：`200` / `404` 已经把「已发布 / 从未发布」说清楚了，不需要靠响应体猜。
3. **不能伪造服务端没给的数据**：没有 `publishedAt` 就不显示时间；没有明文就不假装能显示。
4. **一次性信息要有「破坏性操作」的仪式感**：醒目区块 + 明确后果 + 显式关闭。
5. **前端是安全设计的消费者，不是补丁**：后端不返回明文，任何前端技巧都只会制造错误的安全感。
6. **撤销 = 失效 + 留痕**：保留条目、带时间、带标记，让「停用」可审计。
7. **示例是产品的一部分**：能直接复制运行，才能降低接入门槛；地址必须来自运行时配置。
8. **流式的「逐段」由消费方保证**：`curl -N` 与前端 `getReader` 是同一件事的两端。

**遗留 / 后续**

- 发布时间在 `GET` 后不可见（契约未返回 `publishedAt`）；要做「发布历史 / 回滚」需要新增字段与接口。
- 发布前没有「草稿 vs 线上」差异对比，也没有二次确认。
- 撤销没有二次确认；误撤销只能新建 key。
- 明文 key 只在创建时可见；没有「轮换」（先建新、再撤旧）的一键流程。
- 调用示例只给 curl，没有 SDK / OpenAPI 片段；`Authorization: Bearer <key>` 只在文字里提到，示例只用 `X-API-Key`。
- 列表没有分页与搜索；key 数量多时只能滚动。
