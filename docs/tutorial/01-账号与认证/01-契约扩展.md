## 1. 本篇目标

- 在**唯一真源**里定义「用户 + 登录」的三个接口与它们的成功 / 失败状态码。
- 让两套后端（NestJS / FastAPI）在**错误响应上也收敛到同一形状**。

**接口清单（契约中的定义）**

| 方法 / 路径 | operationId | 成功 | 失败 |

## 3. 先看清要做什么

阶段 0 的契约只有 `/health`。阶段 1 要补上「账号与认证」，所以按**契约优先**的流程，第一步永远是**先落契约、再写实现**：

```
packages/contract/
   ├── openapi.yaml      ← 追加 /auth/* 三个接口 + 新 schema            （本篇 §5）
   └── src/index.ts      ← 同步追加对应的 TS 类型                        （本篇 §6）
        ↓ pnpm run build:contract
      dist/index.js + dist/index.d.ts   ← NestJS / FastAPI / 前端统一消费 （本篇 §9）
```

三个接口的语义：

```
POST /auth/register   你给我 email + 密码   → 建用户，返回用户视图（不含密码）
POST /auth/login      你给我 email + 密码   → 校验通过，返回 JWT 令牌 + 用户
GET  /auth/me         你带上 Bearer 令牌     → 返回令牌对应的用户
```

**关键点**：`/auth/me` 是**需要认证**的接口；`register` / `login` 是**匿名**接口。这个区别在契约里用 `security` 字段表达（见 §8）。

## 5. 完整代码：契约（openapi.yaml）

**完整文件路径：`packages/contract/openapi.yaml`**

```yaml
openapi: 3.1.0
info:
  title: mini-dify API
  version: 0.1.0
  description: >-
    唯一契约（单真源）。NestJS（api-ts）与 FastAPI（api-py）都必须实现本规范，
    并由同一套契约测试校验两者的响应结构、状态码与错误响应体一致。
servers:
  - url: http://localhost:3001
    description: api-ts (NestJS)
  - url: http://localhost:8000
    description: api-py (FastAPI)
paths:
  /health:
    get:
      operationId: getHealth
      summary: 健康检查
      responses:
        "200":
          description: 服务健康
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/HealthResponse"

  /auth/register:
    post:
      operationId: register
      summary: 注册
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/RegisterRequest"
      responses:
        "201":
          description: 注册成功
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/UserResponse"
        "400":
          $ref: "#/components/responses/BadRequest"
        "409":
          $ref: "#/components/responses/Conflict"

  /auth/login:
    post:
      operationId: login
      summary: 登录
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/LoginRequest"
      responses:
        "200":
          description: 登录成功
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/TokenResponse"
        "400":
          $ref: "#/components/responses/BadRequest"
        "401":
          $ref: "#/components/responses/Unauthorized"

  /auth/me:
    get:
      operationId: getCurrentUser
      summary: 当前登录用户
      security:
        - bearerAuth: []
      responses:
        "200":
          description: 当前用户
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/UserResponse"
        "401":
          $ref: "#/components/responses/Unauthorized"

components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

  responses:
    BadRequest:
      description: 参数校验失败
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/ErrorResponse"
    Unauthorized:
      description: 未认证或凭证无效
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/ErrorResponse"
    Conflict:
      description: 资源冲突（如邮箱已存在）
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/ErrorResponse"

  schemas:
    HealthResponse:
      type: object
      additionalProperties: false
      required: [status, service, version, time]
      properties:
        status:
          type: string
          enum: [ok]
        service:
          type: string
          description: 服务标识，取值 api-ts 或 api-py
          examples: [api-ts]
        version:
          type: string
          examples: ["0.1.0"]
        time:
          type: string
          format: date-time
          description: ISO-8601 时间戳

    RegisterRequest:
      type: object
      additionalProperties: false
      required: [email, password]
      properties:
        email:
          type: string
          format: email
        password:
          type: string
          minLength: 8

    LoginRequest:
      type: object
      additionalProperties: false
      required: [email, password]
      properties:
        email:
          type: string
          format: email
        password:
          type: string

    UserResponse:
      type: object
      additionalProperties: false
      required: [id, email, role, createdAt]
      properties:
        id:
          type: string
        email:
          type: string
        role:
          type: string
          enum: [admin, member]
        createdAt:
          type: string
          format: date-time

    TokenResponse:
      type: object
      additionalProperties: false
      required: [accessToken, tokenType, expiresIn, user]
      properties:
        accessToken:
          type: string
        tokenType:
          type: string
          enum: [Bearer]
        expiresIn:
          type: integer
          description: 有效期（秒）
        user:
          $ref: "#/components/schemas/UserResponse"

    ErrorResponse:
      type: object
      additionalProperties: false
      required: [statusCode, message, error]
      properties:
        statusCode:
          type: integer
          examples: [401]
        message:
          type: string
          examples: [Invalid email or password]
        error:
          type: string
          examples: [Unauthorized]
```

**本阶段新增的部分（与阶段 0 的 `/health` 相比）**

| 新增 | 类型 | 说明 |
| --- | --- | --- |
| `paths./auth/register`、`/auth/login`、`/auth/me` | path item | 三个新接口（见 §1 的表） |
| `components.securitySchemes.bearerAuth` | security scheme | 定义「Bearer JWT」这种认证方式（§8） |
| `components.responses.BadRequest / Unauthorized / Conflict` | response 对象 | 把**可复用的错误响应**抽出来，供各接口 `$ref`（§7） |
| `RegisterRequest` / `LoginRequest` / `UserResponse` / `TokenResponse` / `ErrorResponse` | schema | 新数据结构 |

**读法要点**（`$ref` / `additionalProperties` / `enum` / `format` 的通用含义见 `00-项目初始化/04-契约包与TypeScript类型.md`，此处只补本阶段特有的两点）：

- **`responses` 里用 `$ref` 引用另一个 response**：`"400": { $ref: "#/components/responses/BadRequest" }`。这表示「400 的响应体就是复用的 `BadRequest` 定义」，不必每个接口重复写一遍错误体。
- **`security` 写在 operation 上**：`/auth/me` 的 `security: - bearerAuth: []` 表示**该接口需要 Bearer 认证**；没有这段的接口（`register` / `login`）就是匿名可访问。

## 6. 完整代码：TS 类型（src/index.ts）

契约的 YAML 是**给人类和工具看**的；TS 侧还需要一份**与它逐字段对应**的类型文件，才能让 NestJS 编译期拿到类型。

**完整文件路径：`packages/contract/src/index.ts`**

```ts
/**
 * 契约 TS 类型（由 openapi.yaml 派生）。
 *
 * 唯一真源是同仓库根目录下的 `packages/contract/openapi.yaml`；此文件保持与其逐字段一致。
 * 两套后端（NestJS / FastAPI）都必须返回符合本结构的数据。
 */

/** 契约版本；修改契约时递增，并与 openapi.yaml 的 info.version 保持同步。 */
export const CONTRACT_VERSION = '0.1.0'

/** GET /health 的响应体。 */
export interface HealthResponse {
  /** 固定为 'ok' */
  status: 'ok'
  /** 服务标识：api-ts | api-py */
  service: string
  /** 服务版本 */
  version: string
  /** ISO-8601 时间戳 */
  time: string
}

/** POST /auth/register 请求体。 */
export interface RegisterRequest {
  email: string
  /** 至少 8 位 */
  password: string
}

/** POST /auth/login 请求体。 */
export interface LoginRequest {
  email: string
  password: string
}

/** 用户对外视图（**绝不包含密码哈希**）。 */
export interface UserResponse {
  id: string
  email: string
  role: 'admin' | 'member'
  /** ISO-8601 时间戳 */
  createdAt: string
}

/** POST /auth/login 的响应体。 */
export interface TokenResponse {
  accessToken: string
  tokenType: 'Bearer'
  /** 有效期（秒） */
  expiresIn: number
  user: UserResponse
}

/**
 * 统一错误响应体。
 *
 * 两套后端必须产出**同一形状**的错误体：NestJS 默认就是该形状，
 * FastAPI 需要自定义异常处理器把默认的 `{detail}` 归一化过来。
 */
export interface ErrorResponse {
  statusCode: number
  message: string
  error: string
}
```

**为什么 `role: 'admin' | 'member'` / `tokenType: 'Bearer'`**：这是把 YAML 里的 `enum` 用 TS 的「字面量类型 + 联合类型」表达出来（原理见 `00-项目初始化/04-契约包与TypeScript类型.md` §9.4）。写 `role: 'boss'` 编译期就会报错。

> **手工同步**：`openapi.yaml` 与 `src/index.ts` 是**两份手工维护、必须一致**的文件。改了 YAML 里的 schema，就要同步改这里的 interface（阶段 0 · 04 §12 已列为常见坑）。

## 7. 【技术教学 · 首次】错误信封（Error Envelope）

### 7.1 是什么

**错误信封（error envelope）** 指的是：**所有失败响应，统一用同一个固定的外层结构包起来**。本项目的信封就是 `ErrorResponse`：

```json
{ "statusCode": 401, "message": "Invalid email or password", "error": "Unauthorized" }
```

不管哪个接口、哪种失败（400 / 401 / 409），响应体都长这**同一个形状**，只有三个字段的值不同。

### 7.2 为什么需要它：两套框架的默认形状不一样

这是本阶段最值得理解的一处设计取舍。两套后端来自不同生态，**默认的错误体形状天然不同**：

| 框架 | 默认错误体 | 来源 |
| --- | --- | --- |
| NestJS | `{ "statusCode": 400, "message": "...", "error": "Bad Request" }` | `HttpException` 的默认序列化 |
| FastAPI | `{ "detail": "..." }` | `HTTPException` 的默认序列化 |

如果不管，前端就要**写两套错误处理**：请求 api-ts 时读 `message`，请求 api-py 时读 `detail`。这直接违背「契约优先、行为一致」的目标。

### 7.3 收敛方案：契约定义形状，两侧各自归一化

```
            契约（唯一真源）
       ErrorResponse = {statusCode, message, error}
                    │  两侧都必须产出这个形状
        ┌───────────┴───────────┐
    NestJS：正好是默认形状        FastAPI：默认是 {detail}
    → 只需把 message 统一成字符串  → 写异常处理器把 {detail} 改写成信封
    （main.ts 里 useGlobalFilters(HttpErrorFilter)）
```

- **NestJS 侧**：默认形状**已经接近**信封（`statusCode` / `message` / `error` 都有），只需一个全局异常过滤器把 `message` 统一成**字符串**（校验失败时 Nest 默认会给数组），见阶段 0 · 05 §9.4 提到的 `HttpErrorFilter`。
- **FastAPI 侧**：默认是 `{detail}`，必须**自定义异常处理器**把它重写成 `{statusCode, message, error}`。

> 一句话：**契约不只管成功响应，也管错误响应**。错误信封不进契约，一致性就是空谈。

### 7.4 在契约里怎么表达（本例的写法）

```yaml
components:
  responses:                      # 可复用的「错误响应」定义
    BadRequest:
      description: 参数校验失败
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/ErrorResponse"
    Unauthorized: { ... }         # 同上，指向同一个 ErrorResponse
    Conflict:     { ... }
```

- 三个失败语义（400 / 401 / 409）**共用同一个** `ErrorResponse` schema —— 形状唯一，语义靠 HTTP 状态码区分。
- 各接口用 `"400": { $ref: "#/components/responses/BadRequest" }` 把这份定义**复用**进去，避免每个接口重抄一遍。

### 7.5 信封三字段的含义

| 字段 | 类型 | 含义 | 例子 |
| --- | --- | --- | --- |
| `statusCode` | integer | HTTP 状态码（与响应行一致，冗余但便于前端统一读取） | `401` |
| `message` | string | 人类可读的失败原因 | `Invalid email or password` |
| `error` | string | 错误类别（HTTP 标准短语） | `Unauthorized` / `Conflict` / `Bad Request` |

> 注意 `message` 在契约里被**约束为 string（不是数组）**——这正是为了逼两侧把校验错误归一化成字符串（TS 侧默认是数组，需要过滤器 join）。

## 8. 【技术教学 · 首次】`securityScheme`（HTTP Bearer JWT）

### 8.1 是什么

**`securityScheme`** 是 OpenAPI 里描述「接口如何认证」的机制。它告诉读者与工具（文档、代码生成器、测试）：「这个 API 用哪种凭证、放在哪里、是什么格式」。

本项目定义一个 **HTTP Bearer** 方案，用 JWT 作为凭证：

```yaml
components:
  securitySchemes:
    bearerAuth:
      type: http          # 认证类型：HTTP 认证
      scheme: bearer      # 方案：Bearer 令牌
      bearerFormat: JWT   # 令牌格式（提示信息）：JWT
```

对应到请求头：

```
Authorization: Bearer <JWT>
```

### 8.2 基本语法

`securityScheme` 的常见 `type`：

| type | 含义 | 凭证放哪 |
| --- | --- | --- |
| `http` | HTTP 标准认证 | `Authorization` 头；`scheme: bearer` 即 Bearer 令牌（本项目） |
| `apiKey` | 自定义 API Key | 由 `in` 决定放 header / query / cookie |
| `oauth2` / `openIdConnect` | 完整 OAuth 流程 | 复杂场景（本项目不用） |

`type: http` + `scheme: bearer` 的组合，就等价于「请求头里带 `Authorization: Bearer <token>`」。

### 8.3 把方案「挂」到接口上

定义了方案之后，接口用 `security` 字段引用它：

```yaml
  /auth/me:
    get:
      operationId: getCurrentUser
      security:
        - bearerAuth: []        # ← 引用上面的方案；[] 表示该方案无需额外 scope
      responses: { ... }
```

- 写法是**数组**：`security: - bearerAuth: []`，表示「需要满足列表里的方案」。`[]` 是 scope 列表，Bearer 方案没有 scope，所以写空数组。
- **没写 `security` 的接口（`register` / `login`）就是匿名接口**——不需要令牌。

> 口诀：**`securitySchemes` 定义「怎么带令牌」，operation 上的 `security` 声明「这个接口要不要令牌」**。

### 8.4 本例为什么这么用

因为阶段 1 的目标之一是「**跨后端令牌互认**」：api-py 签发的 JWT 能被 api-ts 接受，反之亦然。要在契约里把这件事说清楚，就必须：

1. 明确「这是 Bearer JWT」（`bearerFormat: JWT`）——而不是 Cookies 或 API Key；
2. 明确「哪些接口要认证」（`/auth/me`）——这样两侧的实现（NestJS Guard / FastAPI `Depends(HTTPBearer)`）才有共同的依据。

签名算法（HS256）与密钥（共享 `JWT_SECRET`）属于**实现细节**，不在契约里表达；契约只表达「用 JWT、放 Bearer 头」这一层的约定。

| 信封唯一 | 看 `components.responses` | `BadRequest`/`Unauthorized`/`Conflict` 都指向同一个 `ErrorResponse` |
| 认证声明 | 看 `/auth/me` 的 `security` | `- bearerAuth: []` |
| 类型一致 | 人工比对 `openapi.yaml` 与 `src/index.ts` | 字段逐项对应（`role` / `tokenType` 的 enum 落到字面量类型） |

**契约测试视角（阶段 1 · 07 会用到）**：两侧后端对同一失败场景应返回**同一形状**的信封，例如：

```jsonc
// 401
{ "statusCode": 401, "message": "...", "error": "Unauthorized" }
// 409
{ "statusCode": 409, "message": "...", "error": "Conflict" }
```

（`message` 文案因校验器不同可能不同，属预期；**形状**必须一致。）

## 11. 常见坑

| 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- |
| 只改 YAML 忘了改 TS | NestJS 拿不到新类型 / 类型与契约不符 | `openapi.yaml` 与 `src/index.ts` 是**手工同步**的两份文件，必须一起改 |
| `security` 写错位置 | 文档里 `/auth/me` 没标出需要认证 | `security` 要写在 **operation（get/post）** 上，不是 `securitySchemes` 里；`securitySchemes` 只做**定义** |
| `bearerAuth` 名字对不上 | `security: - bearerAuth: []` 引用了不存在的方案 | `securitySchemes` 里的**键名**必须与 `security` 引用名一致（此处都是 `bearerAuth`） |
| 信封字段名不统一 | 前端得写两套错误处理 | 侧侧都必须落到 `{statusCode, message, error}`；FastAPI 默认是 `{detail}`，需要异常处理器改写 |
| `message` 被当成数组 | 契约校验失败（`message` 声明为 string） | Nest 校验失败默认给数组 → 用全局过滤器 join 成字符串（见阶段 0 · 05 §9.4 的 `HttpErrorFilter`） |
| 忘了重编译契约 | NestJS 编译用的还是旧 `dist` | 契约改完必须 `pnpm run build:contract`（`dev:api-ts` / `build:api-ts` 已自动包含此步） |
| 改了契约没升级版本 | 两侧「契约版本」对不上 | 契约变更时同步递增 `openapi.yaml#/info/version` 与 `src/index.ts#CONTRACT_VERSION`（当前均为 `0.1.0`） |
