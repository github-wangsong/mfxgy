### 3.3 L3 —— api-ts（NestJS）注册 / 登录 / me

**在哪执行**：任意目录（用 `127.0.0.1`）

```bash
# 注册（期望 201）
curl -i -X POST http://127.0.0.1:3001/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"secret123"}'

# 登录（期望 200），拿 token
TS_TOKEN=$(curl -s -X POST http://127.0.0.1:3001/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"secret123"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['accessToken'])")

# me（期望 200）
curl -i http://127.0.0.1:3001/auth/me -H "Authorization: Bearer $TS_TOKEN"
```

**预期输出（实测·示例值）**

```
HTTP/1.1 201 Created
{"id":"<uuid>","email":"alice@example.com","role":"member","createdAt":"2026-10-18T..."}

HTTP/1.1 200 OK
{"accessToken":"<JWT>","tokenType":"Bearer","expiresIn":3600,"user":{...}}

HTTP/1.1 200 OK
{"id":"<uuid>","email":"alice@example.com","role":"member","createdAt":"..."}
```

**结果解读**：`/auth/me` 只认 `Authorization: Bearer`；返回体是 `UserResponse`（**不含** `password_hash`）。

### 3.5 L5 / L6 —— 错误场景与错误体形状（两端一致）

**在哪执行**：任意目录
**目的**：这是阶段 1「行为一致」最关键的一组——**不仅状态码一致，错误体形状也一致**。

```bash
# ① 重复邮箱 → 409（两端）
curl -i -X POST http://127.0.0.1:3001/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"secret123"}'
curl -i -X POST http://127.0.0.1:8000/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"bob@example.com","password":"secret123"}'

# ② 错误密码 → 401（两端）
curl -i -X POST http://127.0.0.1:3001/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"wrong-pass"}'
curl -i -X POST http://127.0.0.1:8000/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"bob@example.com","password":"wrong-pass"}'

# ③ 无效 token 访问 me → 401（两端）
curl -i http://127.0.0.1:3001/auth/me -H "Authorization: Bearer not.a.jwt"
curl -i http://127.0.0.1:8000/auth/me -H "Authorization: Bearer not.a.jwt"

# ④ 参数校验失败（密码不足 8 位）→ 400（两端）
curl -i -X POST http://127.0.0.1:3001/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"x@example.com","password":"123"}'
curl -i -X POST http://127.0.0.1:8000/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"x@example.com","password":"123"}'
```

**预期输出（实测·形状）**

```
# ① 409
{"statusCode":409,"message":"Email already registered","error":"Conflict"}

# ② 401
{"statusCode":401,"message":"Invalid email or password","error":"Unauthorized"}

# ③ 401
{"statusCode":401,"message":"Invalid or expired token","error":"Unauthorized"}

# ④ 400 —— 形状一致、文案各自不同（见下）
{"statusCode":400,"message":"<一个字符串>","error":"Bad Request"}
```

**结果解读**：

- **状态码**：注册 201 / 登录 200 / me 200；重复邮箱 409 / 错误凭据或无效 token 401 / 校验失败 400——**两端逐条一致**。
- **错误体形状**：两端都是 `{"statusCode":n,"message":"字符串","error":"..."}`，且 `message` 是**字符串**（见第 4 节）。
- **唯一差异**：第 ④ 条的 `message` **文案**来自各自校验器，**内容**会不同（例如 TS 可能是 `"password must be longer than or equal to 8 characters"`，Py 可能是 `"String should have at least 8 characters"`）。这是**值规范层**的合理差异——形状与类型一致即可，文案不要求逐字相同。**（阶段 2 进展：文案本身也已归一，两端逐字节一致，见 `02-应用管理/07-验收.md` §4.2。）**

### 3.6 L7 —— 跨后端令牌互认（阶段 1 的核心）

**在哪执行**：任意目录（原理见 `01-账号与认证/06` 第 7 节）

```bash
# api-ts 的 token → api-py 的 /auth/me
curl -i http://127.0.0.1:8000/auth/me -H "Authorization: Bearer $TS_TOKEN"     # alice 的 token

# api-py 的 token → api-ts 的 /auth/me
curl -i http://127.0.0.1:3001/auth/me -H "Authorization: Bearer $PY_TOKEN"     # bob 的 token
```

**预期输出（实测）**：两次均 **200**，且各自返回**签发方**的用户信息

```
HTTP/1.1 200 OK
{"id":"<alice-uuid>","email":"alice@example.com","role":"member","createdAt":"..."}

HTTP/1.1 200 OK
{"id":"<bob-uuid>","email":"bob@example.com","role":"member","createdAt":"..."}
```

**结果解读**：token 在两个后端**等价可用**——两端共享算法 `HS256` 与密钥 `JWT_SECRET`，构成**同一认证域**。这是「唯一契约、两套实现」在认证维度上最直接的可验证证据。

## 4. 【技术讨论】错误信封归一化属于「契约一致」的哪一层

阶段 0 第 08 篇讲过：**「契约一致」分两层**——① 结构一致（字段集合/名/类型/必填/是否允许多余字段，可被 schema 机械校验）；② 值规范一致（取值的格式/精度/类型规范，必须额外约定）。阶段 0 的遗留是**值规范层**的时间戳格式与 `version`。

阶段 1 引入的**错误信封归一化**，恰好**同时跨越这两层**：

### 4.1 契约要求的形状

`packages/contract/openapi.yaml` 的 `ErrorResponse`（外加 TS 类型 `ErrorResponse`）：

```yaml
ErrorResponse:
  type: object
  additionalProperties: false
  required: [statusCode, message, error]
  properties:
    statusCode: { type: integer, examples: [401] }
    message:    { type: string,  examples: [Invalid email or password] }
    error:      { type: string,  examples: [Unauthorized] }
```

注意两处硬约束：**`additionalProperties: false`**（不能多字段）与 **`message: type: string`**（**必须是字符串**，不是数组）。

### 4.2 两套框架的「默认形状」并不相同

| 框架 | 默认错误体 | 与契约相比 |
| --- | --- | --- |
| NestJS | `{"statusCode":400,"message":[...],"error":"Bad Request"}` | **形状对**（三字段），但 `message` 可能是**数组** |
| FastAPI | `{"detail":[{"loc":...,"msg":...}]}` | **形状错**（是 `detail`，且非三字段） |

于是两套后端分别做了归一化（实现细节见 `01-账号与认证/03` 的 `HttpErrorFilter`、`01/05` 的 `register_error_handlers`）。

### 4.3 归到哪一层：结构层补齐 + 值规范层收敛

| 归一化动作 | 属于哪一层 | 为什么 |
| --- | --- | --- |
| FastAPI 把 `{detail}` 改写成 `{statusCode,message,error}` | **结构一致** | 改了**字段集合/名**——这是 schema 能机械校验的部分 |
| 两端把 `error` 固定成标准 reason phrase（`Bad Request`/`Unauthorized`/`Conflict`…） | **值规范一致** | 字段已对，只是**取值**要按约定归一 |
| NestJS 把 `message`（数组）**`join('; ')` 成字符串** | **值规范一致** | 字段与名都对，但**类型**违反契约 `type: string` |

**一句话结论**：

> 「错误信封归一化」的主体是**结构一致**（让 FastAPI 对齐字段形状），但其中**最容易被忽略、也最必须显式处理**的一步——把 `message` 从数组收敛为字符串——属于**值规范一致**。

### 4.4 为什么 NestJS 的 `message`（数组）必须收敛为字符串

- **来源**：NestJS 的 `ValidationPipe`（配 `class-validator`）一次会产出**多条**校验错误，默认把它们塞进 `message` **数组**：`["email must be an email","password must be longer than or equal to 8 characters"]`。
- **冲突**：契约 `ErrorResponse.message` 是 **`type: string`**（`additionalProperties: false`），数组**直接违约**——即便字段齐全，schema 校验也会判失败。
- **归一**：在 `HttpErrorFilter.extractMessage` 里把数组 `map(String).join('; ')` 成**单个字符串**（源码见 `01-账号与认证/03`）：

  ```ts
  if (Array.isArray(message)) {
    return message.map(String).join('; ')
  }
  ```

- **为什么与 FastAPI 一致**：FastAPI 侧 `register_error_handlers` 对 `RequestValidationError` 只取**第一条**错误的 `msg` 作为字符串 `message`。两端最终都产出**「一个字符串」**，形状与类型因此对齐；只是**文案内容**不同（值规范层不要求逐字相同）。

**由此得到一条通用纪律**：当契约把某字段声明为 `type: string`，实现方就必须**保证它始终是字符串**——框架「顺手」给出的数组/对象，正是最容易被漏掉的违约点。

> **后续进展（阶段 2）**：在此「数组 → 字符串」之上，**文案本身也归一了**——唯一真源 `packages/contract/error-messages.md` 规定「约束名 → 文案模板」，两端 12/12 组用例响应体**逐字节一致**（见 `02-应用管理/07-验收.md` §4.2）。

## 5. 常见坑汇总（跨阶段 1）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **`JWT_SECRET` 两端不一致** | 跨端 token 报 401 | 密钥须逐字节相同；核对 `apps/api-ts/.env` 与 `apps/api-py/.env` 的 `JWT_SECRET`（见 `01/06` §7） |
| 2 | **token 过期** | 一段时间后 401 | `exp` 到期，重新登录（当前有效期 3600 秒） |
| 3 | **算法不匹配** | 校验 `invalid algorithm` | 一端 HS256、另一端非对称算法；统一为 HS256 |
| 4 | **NestJS `message` 是数组** | 400 返回 `"message":[...]`，契约校验失败 | `ValidationPipe` 默认数组；由 `HttpErrorFilter` 收敛为 `join('; ')` 字符串 |
| 5 | **FastAPI 未注册异常处理器** | 错误体是 `{"detail":...}` | 未调用 `register_error_handlers`；在 `main.py` 创建 app 后注册 |
| 6 | **重置/换库后表不在** | 注册报 500（no such table） | 迁移未应用；`prisma migrate dev` / `migrate deploy` |
| 7 | **邮箱唯一约束未生效** | 重复注册竟成功 | 迁移/表缺 `users_email_key` 唯一索引；检查 `\d users` |
| 8 | **弱密码通过校验** | 6 位密码注册成功 | 契约 `minLength: 8` 未落实；两端校验器需含最小长度（Py `Field(min_length=8)`、TS `@MinLength(8)`） |
| 9 | **`Authorization` 头格式错** | 401 `Missing bearer token` | 必须是 `Bearer <token>`（含空格） |
| 10 | **`localhost` 解析竞态** | `curl` 偶发连不上 | 统一用 `127.0.0.1`（见 `00-项目初始化/08-验收.md` §7） |
| 11 | **值不同的字段（如 `createdAt` 时区）** | 两端字符串曾不等 | 属值规范层；契约需额外约定（沿用阶段 0 结论）。**阶段 2 已收口**：全站统一 UTC 毫秒 `Z`、文案归一（见 `02-应用管理/07-验收.md` §4.2） |

> 第 1~3、9 属「认证」类，详解见 `01-账号与认证/06`；第 4~5 属「错误信封」类，实现见 `01/03`、`01/05`。

## 6. 本篇复盘与知识点

**一句话总结阶段 1**：用「注册 → 登录 → 携带 JWT 访问受保护接口」把**认证闭环**跑通，并让**两套后端行为一致**——不仅状态码一致，**错误体形状与类型也一致**，且**令牌可跨端互换**。

**本篇学到的工程/架构要点**

1. **分层验收是收口手段**：契约编译 → 迁移/表 → 两端认证 → 错误场景 → 跨端互认，逐层自证，出错能立刻定位到层。
2. **错误信封归一化跨两层**：FastAPI 补字段形状属「结构一致」，NestJS 把 `message` 收敛为字符串属「值规范一致」。
3. **契约的 `type: string` 是硬约束**：框架默认给数组/对象时，必须显式归一，否则机械校验必失败。
4. **「同一认证域」可被验证**：共享算法 + 密钥 ⇒ 令牌跨端有效，是「唯一契约、两套实现」在认证维度的直接证据。

**遗留到下阶段**

- 把「错误信封」纳入契约测试双跑（两端 4xx 的 `statusCode/message 类型/error` 断言）。
- 时间戳等「值规范」的契约化（沿用阶段 0 遗留）。**（阶段 2 已收口：时间统一 UTC 毫秒 `Z`、错误文案归一，见 `02-应用管理/07-验收.md` §4.2。）**
- `JWT_EXPIRES_IN` 已抽成环境变量并两端对齐：两端都读 `JWT_EXPIRES_IN`（**秒**），实测均为 `3600`（见 `01/06`）。

**基础技术要点**：JWT 认证闭环 · 错误响应体归一化 · 契约一致的双层归属 · 跨实现凭证互换。
