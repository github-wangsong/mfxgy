# 05 · 验收

> 所属：阶段 11 · 自主 Agent 运行时
> 本篇覆盖：把阶段 11 的交付（契约 `0.11.0`、`agent_runs` / `agent_run_events`、五个 Agent 接口、Composition 与五层语义）串成一条可复现的验收链：**契约编译 → 迁移与索引 → 异步受理（202）→ 事件序列与 `id` → 两端一致 → 重放与取消 → 压缩 + 错误 + 阶段 5~10 回归**，逐条命令给出**实测**预期。
> **本篇首次教学：阶段 11 新增的一致层次**——不只比「事件名序列」（阶段 4 起就有），还要比 **`id` 序列（seq 1..N 连续且两端相同）** 与 **确定性压缩结果（20 → 7 → 8 条）**。这是「长任务 + 可重放」带来的新维度：同一份事件流必须能被任意一端、任意时刻、从任意位置重放出**完全相同**的帧。

## 1. 本篇目标

做完这一篇，你能：

- 沿**依赖顺序**逐层验收阶段 11：契约 `0.11.0` → 迁移与索引 → 异步受理 → 事件序列与 `id` → 两端一致 → 重放与取消 → 压缩 / 错误 / 回归。
- 用可直接复制的命令证明：
  - `agent_runs` / `agent_run_events` 两张表存在，**`(run_id, seq)` 唯一**，且 **`chunks_embedding_hnsw` 仍在**；
  - `POST /agent/runs` 返回 **202** `{id, status:"queued"}`，**立即**返回而不等执行；
  - 一次默认运行的事件 **`id` 为 1..16 连续**，事件序列固定（5 对 `layer_*` + 中间 3 片 token）；
  - **两端（3001 / 8000）重放同一次运行**，`id` 序列、事件名序列、每帧 payload 键集合、`run_finished.output` **完全一致**；工具运行同样一致（输出 `answer: 14`）；
  - `Last-Event-ID: 5` **只补发 `seq > 5`**（首帧 `id: 6`、末帧 `id: 15`），两端一致；
  - 取消 → 终态**只有** `run_cancelled`（**没有** `run_finished`）；再取消 → **400** `Run is not cancellable`；
  - 历史压缩：20 条 + `compactionThreshold:12, keepRecent:6` → **7 条**（1 compacted + 6 近期），再经 `prompt` 层 +1 → **模型实收 8 条**；
  - **12 组预检错误 + 2 组运行期错误**文案两端逐字一致；
  - 阶段 5 的 token `["echo:"," Hell","o min","i-dif","y"]` 与 `usage 15/21/36`、阶段 6 工具事件、阶段 7 `retrieval`、阶段 8 `branch_taken`/`iteration_item`、阶段 9 会话 4 条、阶段 10 对外 SSE + `Invalid API key` **全部未破坏**。
- 讲清 **阶段 11 的质变**：前 10 阶段交付的是**一张图**（工作流引擎）；阶段 11 交付的是 **第二种产品形态**——**配置驱动的自主 Agent**：没有节点与边，只有**有序的层**与一段 `input`；但它复用同一台执行底座（LangGraph / 同一套工具 / 同一个 mock / 同一套 SSE 纪律）。

**验收标准（对齐总纲 §6 阶段 11）**

> 能声明式配置、异步运行一个自主 Agent，事件可重放、可取消；两端一致。

## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序

```
L1 契约编译(0.11.0) + agent-events.md
        │
        ▼
L2 迁移与索引（两张表 + UNIQUE(run_id,seq) + HNSW 仍在）
        │
        ▼
L3 异步受理（202 立即返回，run_queued 已落库）
        │
        ▼
L4 事件序列与 id（1..16 连续、固定序列）
        │
        ▼
L5 两端一致（同一次运行，两个后端重放）
        │
        ▼
L6 重放与取消（Last-Event-ID / 取消检查点 / 终态唯一）
        │
        ▼
L7 压缩 + 14 组错误 + 阶段 5~10 回归
```

**为什么按这个顺序**：没有唯一索引，`seq` 就不受约束，「重放不重复」无从谈起；没有 202 与 `run_queued` 落库，就没有「先受理、后执行」的可观测性；没有稳定的事件序列，两端一致就没有比较对象；一致之后再验重放与取消这两个**状态相关**的行为；最后用压缩 + 错误 + 回归证明新链路没有破坏旧能力。

**结果解读**：

- **`UNIQUE(run_id, seq)`** 是阶段 11 最重要的一条约束：`seq` 是 SSE 的 `id:` 与 `Last-Event-ID` 的唯一依据，**重复就会让重放错位**。数据库级唯一索引是最后一道保险（应用层虽然串行写，但并发/重试时仍可能撞）。
- `composition` / `data` 是 **JSONB**：与阶段 3 的图、阶段 9 的消息一致；`data` 存 payload 原文（`run_queued` 的 `{runId,status}`、`token` 的 `{text}`…）。
- `agent_runs.output` / `error` 可空：`succeeded` 只有 `output`、`failed` 只有 `error`、`cancelled` 两者都为 `null`——**用 `null` 表达「没有」，不用空串糊弄**。
- `cancel_requested_at` 是**取消的异步标记**（`01`）：非空表示「请求过取消」，执行器在层边界检查。
- 两个外键 `ON DELETE CASCADE`：删用户 → 删他的所有 run → 删所有事件（两级级联）。

### 3.3 L3 —— 异步受理：`202` + `queued` + `run_queued` 已落库

#### 3.3.1 受理：`202`，立即返回

请求体必须**同时**含 `input` 与 `composition`：

```bash
python - <<'PY'
import json
comp = json.load(open("agent-default.json", encoding="utf-8"))
with open("create-body.json", "w", encoding="utf-8") as f:
    json.dump({"input": "hello", "composition": comp}, f, ensure_ascii=False)
PY

curl -s -o create.json -w '%{http_code}\n' -X POST http://127.0.0.1:3001/agent/runs \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @create-body.json

python -m json.tool create.json
```

**预期输出（实测）**

```
202
{
    "id": "<uuid>",
    "status": "queued"
}
```

**结果解读**：

- **`202 Accepted`** 而不是 `200`：契约语义是「**已受理、尚未完成**」。`200` 会让人以为「跑完了」。
- 响应体**只有 `id` 与 `status`**（`CreateAgentRunResponse`），**不含** `output` / `error` / 事件——结果要靠事件流或 `GET /agent/runs/{id}` 拿。
- `status: "queued"` 是**受理那一刻**的状态；后台执行会立刻把它推进到 `running`，但**响应体永远是 `queued`**（响应在 `void execute()` 之前返回）。
- **不要**在这里期待输出：Agent 是长任务，同步等待会把 HTTP 连接拖死；「受理」与「执行」解耦正是三件套的第一件（§4 技术讨论 2）。

```
   2 | run_started   | {"runId": "..."}
   3 | layer_started | {"layer": "history", "index": 1}
(3 rows)

queued|t|t
```

- 第 1 条**必定**是 `run_queued`（`accept` 内写入）；第 2 条之后可能还没写（后台刚起步），所以这里只断言「第一条是 seq 1 的 `run_queued`」，不承诺行数。

**结果解读**：

- **`run_queued` 是 seq 1**，在 `accept()` 里与建 run **同一个流程**写入（`01`）——所以「客户端拿到 202 时，至少有一条事件可重放」。
- 第 2 条查到的状态可能是 `queued` 或 `running`（后台已启动）：**202 的 `queued` 是响应体语义，不是数据库快照**。这不是 bug，是异步的必然。
- `output` / `error` 均为 `null`：还没到终态。
- 「先写库、再推送」：`run_queued` 写入时**还没有订阅者**，它只靠**重放**被客户端看到（`01`）。这也是为什么打开事件流时总会先看到 `#1`。

### 3.7 L7 —— 压缩 + 14 组错误 + 阶段 5~10 回归

#### 3.7.1 历史压缩：20 → 7 → 8 条

## 4. 【技术讨论 1】阶段 11 补上了什么：从「工作流引擎」到「第二种产品形态」

> 实现细节（Run 模型、层契约、ReAct）见本阶段 `01` / `02` / `03`；这一节只讨论「为什么它是第二种产品形态」。

**问题**：阶段 4~10 已经有了图、节点、分支、循环、工具、RAG、会话、发布——为什么还需要一个「Agent」？

**答案的一句话**：**因为它们回答的不是同一个产品问题。工作流回答「我画的这张图怎么跑」；Agent 回答「我只想声明目标与能力，剩下的编排你来做」。**

| | 工作流（阶段 3~10） | 自主 Agent（阶段 11） |
| --- | --- | --- |
| 作者界面 | 画布：节点 + 边 + 分支 + 循环 | 一段 JSON：**有序的层** + 一个 `input` |
| 谁决定控制流 | **作者**（拓扑是显式的） | **层顺序 + `llm` 层的 ReAct 循环** |
| 最小可用配置 | 至少 start / llm / end + 两条边 | 5 层（history / prompt / tools / llm / output） |
| 存储 | `apps.graph_json` | `agent_runs.composition` |
| 运行模型 | 同步流式（请求-响应） | **异步受理（202）+ 可重放事件 + 取消** |
| 复用 | — | 同一台执行底座：LangGraph、工具注册表、mock、错误映射、SSE 纪律 |

**「第二种产品形态」具体指什么**

1. **配置即程序**：没有画布、没有边，**层数组的顺序就是控制流**。作者用「声明」代替「连线」。
2. **长任务是一等公民**：`202` + 落库事件 + `Last-Event-ID`，让「跑 30 秒的 Agent」不再是「一个卡住的 HTTP 请求」。
3. **过程可解释**：`layer_started/finished` 把「装配」暴露出来，用户能解释「为什么这次没调工具」「历史被压缩了吗」。
4. **不绑应用**：`/agent/runs` 是用户级资源，可以先有 Agent、后有应用（甚至永远不做应用）。

> **一句话**：阶段 4 把「图」编译成程序；阶段 11 把「**声明**」编译成程序。两者共享同一个运行时，但**作者的心智模型完全不同**——这才是「第二种产品形态」，而不是「多了几个接口」。

## 5. 【技术讨论 2】`202` + 事件持久化 + `Last-Event-ID` 是「长任务可观测」的三件套

> 202 受理、事件表结构、重放衔接窗口的实现见本阶段 `01-Run模型与事件重放.md`；这一节只讨论「三件套为什么必须同时存在」。

**问题**：为什么 Agent 不能像工作流那样「一个 POST 直接流式返回」，非要先 202、再单独开流？

**答案的一句话**：**因为长任务必须能被「迟到的人」和「断线的人」看到；HTTP 连接不是存储，事件表才是。**

**三件套各自解决什么**

| 件 | 解决 | 缺了会怎样 |
| --- | --- | --- |
| **① `202` 异步受理** | 「提交」与「执行」解耦；连接不再被任务时长绑架 | 客户端必须挂着一个可能几分钟的请求；网关超时即失败；无法后台跑 |
| **② 事件持久化（`agent_run_events`）** | 事件成为**事实**，谁在什么时候看都一致 | 刷新页面/换设备就丢过程；无法审计；无法做「运行历史」 |
| **③ `Last-Event-ID` 重放** | 断线续传；从任意 `seq` 继续读 | 每次重连从头刷一遍；高频 token 让重复量爆炸；无法验证「不重不漏」 |

**为什么「先写库、再推送」是前提**

- 如果先推内存、再异步写库：推送到达时事件可能还没落库 → 客户端立刻重连会**读不到刚收到的那条**，出现「重放比实时少一条」的缝。
- 本项目顺序是**写库成功后才 `publish`**，并且 `seq` 由**单次运行内的串行链**分配（`01`）。于是「重放 + 实时」的交界处既不重复、也不丢失。
- 终态事件与 `agent_runs.status` 更新在**同一个事务**里提交：不会出现「状态已 succeeded、事件表里还没有 `run_finished`」的空窗。

**取消为什么也属于这套**

- 长任务的第三个动作是「**停**」。取消走 `POST .../cancel` → `202` → 置 `cancelRequestedAt`，由执行器在**检查点**（层边界 / 工具轮边界）收尾。
- 不做「强杀线程」：强杀会让事件表缺少终态、状态永远停在 `running`。**异步标记 + 检查点**保证终态**恰好一个**。
- 检查点位置的取舍：越密越及时（但每层一次 DB 查询），越疏越省（但取消延迟变大）。本项目选「层边界 + 工具轮边界」，是**可解释**的粒度。

**可观测 = 可重放**

| 只有日志 | 有事件表 + 游标 |
| --- | --- |
| 「大概在 13:42 出错」 | 「第 11 条 `tool_call` 的参数是 `{expression:"2+"}`」 |
| 无法复现 | 带 `Last-Event-ID` 从任意点重看 |
| 排查靠猜 | 排查靠**帧** |

> **一句话**：**异步是「不占用连接」，持久化是「不依赖连接」，游标是「不重复消费」。** 三件事各自简单，合起来才让「长任务」从「祈祷它别断」变成「断了也能接着看」。

## 6. 【技术讨论 3】Composition 的取舍：不要图，换来了什么、失去了什么

> 层契约、`llm` 层唯一、默认值入契约见本阶段 `02-Composition声明式装配与层设计.md`；这一节只讨论「取舍」。

**问题**：既然工作流已经有图，为什么 Agent 不也画一张图？「不要图」是进步还是退化？

**答案的一句话**：**不是「图不好」，而是「这一类产品的最优表达不是图」。用固定层 + 顺序，换来了极低的上手成本与跨语言一致性；代价是表达力。**

**换来了什么**

| 收益 | 具体表现 |
| --- | --- |
| **配置极小** | 5 层 JSON 约 20 行；同能力的工作流要 5 个节点 + 4 条边 + 坐标 |
| **无拓扑校验** | 不用验环、连通性、孤立节点、`sourceHandle`（阶段 8 的一整套预检） |
| **顺序即语义** | 改数组顺序就改执行顺序，**可 diff、可 review** |
| **跨语言实现小** | 两端只需实现五个纯函数 + 一个循环；工作流要复刻图编译、条件边、迭代 |
| **可复制、可模板化** | 一段 JSON 就是一份可分享的「Agent 预设」 |
| **可解释** | 每层一对事件，用户能逐层对上「配置里的哪一项生效了」 |

**失去了什么**

| 代价 | 具体表现 |
| --- | --- |
| **无并行** | 层是串行的，没有「两个 LLM 同时跑再合并」 |
| **无条件分支 / 循环** | 只有 `llm` 层内部的 ReAct 环；不能按条件跳到不同层 |
| **层类型固定** | 只有 5 种；工作流可以加任意新节点类型 |
| **`llm` 层唯一** | 不能在一个 composition 里放两个独立模型（对比、投票、路由都做不了） |
| **调试可视化弱** | 没有画布；只能看事件与配置 |
| **表达力上限低** | 复杂流程最终还是得回到工作流 |

**为什么「固定 5 层 + 唯一 `llm`」是合理的起点**

- 五个层恰好覆盖「**上下文 → 指令 → 能力 → 推理 → 取结果**」这条最小链路；任何 Agent 框架的骨架都是这五件事。
- `llm` 层唯一，才能让「ReAct 循环」有明确归属（循环发生在这一层内部），也让 `output` 层的「取最后一条 assistant 消息」无歧义。
- 层名闭集 + 同层不重复，换来**校验文案可以穷举**（12 组预检），两端逐字节一致才有可能。

**诚实结论**：Composition 不是「更高级的工作流」，而是**另一条产品线**。想做复杂拓扑，仍应回到画布；想做「一句话配置 + 自主循环」，Composition 更快。**两种形态并存，比强行统一更诚实。**

> **一句话**：**图表达「拓扑」，层表达「流水线」。** 选哪个，取决于用户想控制的是「连接方式」还是「装配顺序」。

## 7. 【技术讨论 4】确定性压缩 vs LLM 摘要：可复现 vs 信息保真

> 两步压缩公式与两端实现见本阶段 `03-ReAct循环与上下文压缩.md` 与 `agent-events.md` §3.1；这一节只讨论「选型」。

**问题**：历史太长要压缩。为什么不用模型做摘要（业界常见做法），而是用一条「保留最后 N 条 + 一条 `[compacted] …`」的确定性规则？

**答案的一句话**：**因为本项目的第一优先级是「两端逐字节一致、可复现、可验收」，而 LLM 摘要在三件事上都做不到。**

**两种方案对照**

| | 确定性截断（本项目） | LLM 摘要 |
| --- | --- | --- |
| 结果可复现 | ✅ 同样的输入永远同样输出 | ❌ 温度/模型版本/服务端差异 |
| 两端一致 | ✅ 一条公式，纯函数 | ❌ 两次调用几乎不可能相同 |
| 成本 | 零（不发请求） | 每次压缩多一次模型调用（钱 + 延迟） |
| 失败模式 | 无 | 超时 / 限流 / 幻觉摘要 |
| 可测试 | ✅ 断言条数与首条内容 | ❌ 只能断言「大概提到了」 |
| 信息保真 | ❌ 旧消息**直接丢弃**，只留条数 | ✅ 保留语义要点 |
| 对模型的作用 | 明确告知「有 14 条被省略」 | 给一段连贯的背景 |

**为什么本项目选确定性**

- 阶段 11 的验收要求 **L5 两端 `frames equal`** 与 **压缩结果逐字节相同**；LLM 摘要会让这两条**永远无法稳定通过**。
- 压缩发生在 `history` 层，是**纯函数**（`agent-events.md` §3.1）：`20 → 1 + 6 = 7`，公式可写进契约、可用脚本断言。
- 「`[compacted] 14 earlier messages omitted`」虽然没有语义，但它**诚实地告诉模型「这里有缺口」**——比编一段看似合理却错误的摘要更安全。

**确定性方案的代价（必须承认）**

- 被丢弃的 14 条**信息真的没了**：如果用户的约束条件在第 3 条，压缩后模型就看不到。
- `keepRecent` / `compactionThreshold` 是**一刀切**：不区分「重要消息」与「寒暄」。
- 没有「摘要 + 原始消息」的分层保留。

**折中方向（本项目未做）**

- **结构化摘要**：只压缩「已完成的任务结果」，保留「用户偏好/约束」；仍用规则而非模型。
- **可复现摘要**：固定 prompt + `temperature=0` + 固定模型版本，把摘要也纳入契约与回归——但跨语言仍难逐字节一致。
- **两段式**：确定性截断作为**兜底**，模型摘要作为**可选增强**（默认关闭，验收只跑确定性路径）。

> **一句话**：**「可复现」不是学术洁癖，而是双栈同契约项目的工程底线。** 先用确定性方案把「一致」钉死，再谈信息保真。

## 8. 【技术讨论 5】框架取舍：为什么最终两侧都用 LangGraph（而不是总纲原计划的 Pydantic AI）

> **完整论证见本阶段 `03-ReAct循环与上下文压缩.md` 的「框架取舍」一节**；这里只保留结论与取舍表，避免重复。

**问题**：总纲最初设想 Python 侧用 Pydantic AI，TS 侧用 LangGraph——「各用各的生态」听起来更真实。为什么最终**两侧都改成 LangGraph**？

**答案的一句话**：**因为这个项目的核心目标是「同一份契约、两套实现、逐字节一致」；引入第三个框架，等于引入第三套事件顺序与第三套循环语义。**

**具体理由**

| 理由 | 说明 |
| --- | --- |
| **已有先例** | 阶段 4 的图编译、阶段 6 的 ReAct 循环都用 LangGraph（TS + Python）。Agent 的 `llm` 层就是「同一张 StateGraph + 条件边 + 环」，**代码可复用** |
| **事件顺序可控** | 节点的执行顺序决定事件顺序；同一套 `START → llm ⇄ tools → END` 拓扑，让两端 `layer/token/tool` 序列天然一致 |
| **跨语言同名概念** | `StateGraph` / `Annotation(TypedDict)` / `addConditionalEdges` / `recursionLimit` 在 JS 与 Python 里**语义对齐**，对照读文档即可 |
| **降低验收面** | 只需证明「两端 LangGraph 产出相同事件」；若一边 Pydantic AI，还要证明「两个框架的循环次数、工具结果注入方式、错误语义」相同 |
| **不引入第三个「心智模型」** | 学生已经学了工作流的 LangGraph；再学 Pydantic AI 会分散注意力，且与本项目的「双栈对照」主题无关 |
| **失败模式的统一** | provider 错误映射、工具失败文案都复用阶段 5/6 的既有实现；换框架就要重做一遍映射 |

**Pydantic AI 本身不好吗**

- 不。它类型安全、DSL 优雅，适合「单栈 Python + 强类型工具」的项目。
- 但它与 LangGraph 的**图/循环抽象不同**：调用次数、工具消息注入顺序、流式分片边界都可能有差异。
- 在「两端逐字节一致」的验收标准下，**任何差异都会被放大成验收失败**。这不是框架优劣，而是**项目目标不匹配**。

**这个取舍的代价**

- 少了一次「多框架对照」的教学机会（可以在 `lang-diff/` 里补，但不属于阶段 11 的交付）。
- Python 侧没有用上 Pydantic AI 的类型推导，`config` 仍是 `dict` + 手工校验（`validator.py`）。
- 如果未来要支持「两套不同框架」，事件协议需要更强的**归一化层**。

> **一句话**：**框架选择不是「哪个更先进」，而是「哪个让契约更容易被证明」。** 在双栈同契约的项目里，**同一框架的两套实现**比「两个框架各写一遍」更容易一致，也更容易教学。

## 9. 常见坑汇总（跨阶段 11）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **迁移后 HNSW 被删** | 检索变慢但不报错 | `add_agent_runs` 同文件里的 `DROP INDEX`；检查、删除、跑 `db:index`（§3.2） |
| 2 | **`(run_id, seq)` 没有唯一索引** | 重放错位、同 seq 两条事件 | 确认 `agent_run_events_run_id_seq_key`（L2） |
| 3 | **把 202 当 200 等待结果** | 客户端拿到 `{id}` 就以为结束 | 202 只表示受理；结果看事件流或 `GET`（§3.3.1） |
| 4 | **`run_queued` 不落库** | 首次重放缺 `#1`，`id` 从 2 开始 | `accept` 里建 run + 写 seq 1 必须同流程（§3.3.2） |
| 5 | **`seq` 每次从 1 重新数** | 同一次运行出现重复 seq | 起点取 DB 现有最大 seq（`01`） |
| 6 | **先推送、后写库** | 重连后少一条刚收到的事件 | 必须「写库成功 → publish」（§5） |
| 7 | **终态事件与状态更新分开提交** | 状态 succeeded 但事件表无 `run_finished` | 同事务（`01`） |
| 8 | **`Last-Event-ID` 当作「重新执行」** | 以为重连会重跑 Agent | 它只读事件（§3.6.1） |
| 9 | **`Last-Event-ID` 传字符串 id** | 400 `invalid Last-Event-ID` | 只接受非负十进制整数 |
| 10 | **重放从 `>= lastEventId` 开始** | 客户端收到重复帧 | 必须 `seq > lastEventId` |
| 11 | **取消当同步** | 取消后立刻查状态仍是 `running` | 202 受理、执行器检查点收尾（§3.6.2） |
| 12 | **已发出 `run_cancelled` 后又出现 `run_finished`** | 终态两个 | 取消分支立即 `return`；若取消在终态前没被检查到，仍以 `run_finished` 结束属正常（协作式，以 SSE 终态为准） |
| 13 | **`llm` 层缺失** | 400 `composition must contain exactly one llm layer` | 契约要求恰好一个（§3.7.2） |
| 14 | **层名拼错** | 400 `unknown layer: {name}` | 闭集 5 个（§3.7.2） |
| 15 | **同一层写两次** | 400 `layer {name} appears more than once` | 每层最多一次 |
| 16 | **`history` 压缩后仍按 20 条想** | 以为模型收到 20 条 | 压缩先于 `maxMessages`（§3.7.1） |
| 17 | **把压缩当 LLM 摘要** | 找不到「摘要调用」 | 本项目是确定性截断（§7） |
| 18 | **`usage` 在 Agent 事件里找不到** | 以为没实现 | Agent 的 `run_finished` 只有 `output` / `elapsedMs`；`usage` 是工作流 `llm` 节点字段 |
| 19 | **`tool_result.result` 当对象用** | `JSON.stringify` 多包一层引号 | 契约是字符串（§3.5.2） |
| 20 | **拿 A 的 run 用 B 的 token 打开流** | 404 `Run not found` | 归属校验（`owner_id`） |
| 21 | **事件 payload 键顺序不同就判失败** | 两端「不一致」的假阳性 | 契约只要求**解析后 JSON 相等**（L5 我们顺带做到全等） |
| 22 | **`elapsedMs` 参与逐字节比较** | 永远不相等 | 它是耗时；Agent 的 `run_finished` 里必须排除 |
| 23 | **删 run 后事件还在** | 孤儿行 | 外键 `ON DELETE CASCADE`（L2） |
| 24 | **进程重启后 `running` 永远不变** | 状态卡死 | 本阶段**不做**续跑/租约；见 `INDEX.md` 第五节遗留项 |

## 10. 本篇复盘与知识点

**一句话总结阶段 11**：在既有的「图即数据、编译执行、有状态会话、发布与对外调用」之上，新增了**第二条产品线**：`POST /agent/runs` **202 异步受理**（`run_queued` 立即落库）→ 后台按 `composition.layers` **逐层装配**（`layer_started/finished` 可见）→ `llm` 层内部跑 **ReAct 循环**（`token` / `tool_call` / `tool_result`）→ 终态**唯一**（`run_finished` / `run_failed` / `run_cancelled`）。所有事件**先写库再推送**，帧带 `id:`，`Last-Event-ID` 支持**重放**（补发，不是重跑）。Composition 用**有序层**代替图，换来低门槛与跨语言一致，代价是表达力。历史压缩采用**确定性截断**（20 → 1+6=7，经 prompt +1 → 模型 8 条），可复现、可断言。取消是**异步标记 + 检查点**，保证终态唯一。

**本篇学到的工程 / 架构要点**

1. **长任务的三件套**：异步受理（202）、事件持久化、重放游标（`Last-Event-ID`）。
2. **「先写库再推送」是重放的 correctness 前提**，不是性能优化。
3. **`seq` 是协议的一部分**：连续、唯一、可比较；数据库唯一索引是最后防线。
4. **终态唯一**：任何路径都必须收口到一个终态事件，否则「重放」会永远等下去。
5. **声明式配置要选对载体**：层数组 + 顺序，比图更适合「固定骨架 + 自主循环」。
6. **压缩的优先级取决于项目目标**：本项目要可复现，所以不要 LLM 摘要。
7. **框架取舍服务于验收标准**：两侧同框架，才有一致性可言。
8. **验收要比「过程」**：`id` 序列、事件名序列、payload 键集合、压缩结果——四条都过，才算「两端一致」。

**遗留到下阶段**

- **运行不跨进程恢复**：进程重启时 DB 中 `queued` / `running` 的 run 不会自动续跑；`Last-Event-ID` 仍可重放已落库事件。生产需要独立 worker + 租约（`INDEX.md` 第五节）。
- 没有并行层、条件跳层、多个 `llm` 层；表达力止于「固定流水线 + 单 ReAct 环」。
- 压缩不可配置为「保留重要消息」；`[compacted]` 摘要没有语义。
- 取消只有层 / 工具轮检查点，**模型流式过程中无法立刻中断**（要等当前调用返回）。
- `GET /agent/runs` 无分页、无按状态过滤；事件表无清理策略（长跑会膨胀）。
- 没有把 L1~L7 固化成 CI 断言（唯一索引、HNSW 存在、`id` 连续、两端全等、压缩 7/8）。
- 前端没有自动重连（依赖手动按钮）；Composition 无草稿持久化。

**基础技术要点**：202 Accepted · Run 状态机（`queued/running/succeeded/failed/cancelled`） · `run_queued` seq 1 · 「先写库再推送」 · `UNIQUE(run_id, seq)` · 帧 `id:` 行 · `Last-Event-ID` 补发 · 终态唯一 · 取消检查点（协作式，以 SSE 终态为准） · Composition 五层（`history/prompt/tools/llm/output`） · `llm` 层唯一 · 层顺序即语义 · 确定性压缩（12/6/20 → 7 → 8） · Agent 级 ReAct · `maxRounds` · 12 组预检 + 2 组运行期错误。
