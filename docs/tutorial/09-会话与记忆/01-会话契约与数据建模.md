## 0. 阶段 9 的立论：图是函数，会话是函数的延续

前八个阶段，执行引擎有一个非常干净的性质：

> **每一次运行，都只依赖这一次请求里的 `inputs`。**

`POST /apps/{id}/run` 的请求体是 `{ "inputs": {...} }`；引擎新建变量池 `pool = { "inputs": inputs }`；图跑完、流结束、请求结束。两次相同的运行互不影响，服务端不保存任何「运行到哪、上次说了什么」的信息。

这就是**无状态（stateless）**。它带来三个好处：

| 好处 | 说明 |
| --- | --- |
| 可水平扩展 | 任意一个进程都能处理任意一次运行，不需要粘性会话 |
| 重启不丢 | 进程里本来就没有需要保存的运行状态 |
| 易测试 | 同一输入 → 同一事件序列（除 `runId` / 时间外） |

但真实对话不是「一问一答就结束」：

```
用户：帮我写个开头
助手：好的，开头是……
用户：再短一点          ← 这句话的含义完全依赖上一轮
```

第二轮的那句话「再短一点」，如果引擎仍然只拿到 `{ inputs }`，它根本不知道「短一点」是相对什么而言。**图是函数，会话是函数的延续**——阶段 9 要做的，就是让同一会话的多次运行共享一段**有序的对话记录**。

### 0.1 关键设计：状态放数据库，计算仍然无状态

最容易想到的做法是「在服务进程里给每个会话开一个内存数组」。这是错的：

| 问题 | 后果 |
| --- | --- |
| 多实例 | 下一次请求落到另一个进程，历史就丢了 |
| 重启 | 历史全丢 |
| 并发 | 两个请求同时改内存数组，需要自己加锁 |
| 审计 | 进程崩溃后无法还原用户到底说了什么 |

本项目的做法是 **stateless compute + stateful storage**：

```
每次运行：
  读 messages 表（该会话最近 N 条，按 seq 升序）   ← 不含本轮
      ↓
  写本轮 user（在开流之前）
      ↓
  构造 pool.conversation
      ↓
  和 inputs 一起作为「本次运行的初始状态」喂给图
      ↓
  图跑完，写本轮 assistant（在 run_finished 之前）
```

> 一句话记住：**记忆不是引擎的一个字段，而是数据库里的一行行消息；引擎每次把它们读出来，注入一个本来无状态的图。**

这也解释了为什么阶段 9 要先做「契约 + 数据建模」：**会话的本质是一张只追加的表**，5 个接口只是这张表的不同视角。

### 0.2 引入会话后新增的四个问题

| 新问题 | 本阶段的答案 | 对应机制 |
| --- | --- | --- |
| 同一条会话的消息，顺序怎么保证 | 会话内单调递增的 `seq` | `messages.seq` + `ORDER BY seq` |
| 两个请求同时往同一会话写 | 唯一约束 + 重试 | `UNIQUE(conversation_id, seq)` |
| 别人的会话能不能读 | 归属校验，一律 404 | `ownerId` + `appId` + 存在性 |
| 历史会不会无限增长、烧 token | 只取最近 `MAX_HISTORY_MESSAGES` 条 | `loadHistory(limit)` |

### 3.2 5 个 HTTP 接口 + 运行接口的两个新字段

| # | 方法与路径 | 请求体 | 成功响应 | 关键点 |
| --- | --- | --- | --- | --- |
| 1 | `GET /apps/{id}/conversations` | — | `200` `{items:[Conversation]}` | 按 `updatedAt` **倒序**；只列当前用户在该应用下的会话 |

| 字段 | 可选性 | 作用 |

### 3.3 一轮带会话的运行，发生了什么

```
POST /apps/{id}/run  { inputs, conversationId, userMessage }
  │
  ├─ 1. 校验应用归属                      失败 → 404 App not found
  ├─ 2. 校验会话归属（ownerId + appId）    失败 → 404 Conversation not found
  ├─ 3. 图预检（含 useHistory 必须有会话） 失败 → 400 普通 JSON
  ├─ 4. 读历史：最近 N 条（seq 升序）      ← 此时**还没有**本轮 user
  ├─ 5. 写入 user 消息（seq = max + 1）    失败 → 400 failed to persist conversation message
  ├─ 6. 构造 pool.conversation = {id, history, messages}
  ├─ 7. 发 run_started（带 conversationId）
  ├─ 8. 执行图 → token / node_* / …
  ├─ 9. 写 assistant 消息（带 runId）       失败 → 抛错，由统一 catch 发唯一一帧 run_failed
  └─ 10. 发 run_finished（此时 assistant 已落库；终态事件每轮恰好 1 个）
        （如果第 8 步执行失败，则**跳过**第 9、10 步，只发一帧 run_failed）
```

注意第 4 步和第 5 步的**顺序不可颠倒**，这是阶段 9 最重要的实现约束之一（完整实现见 `02-历史加载与上下文注入-NestJS.md`；本篇 §12.10 只给出结论）。

### 3.4 两轮对话后，数据库里长什么样

`conversations` 一行：

```json
{
  "id": "conv_...",
  "app_id": "app_...",
  "owner_id": "user_...",
  "title": "demo",
  "created_at": "2026-10-22T14:07:44.000",
  "updated_at": "2026-10-22T14:09:10.000"
}
```

`messages` 四行（按 `seq` 升序读出来）：

| seq | role | content | run_id |
| --- | --- | --- | --- |
| 1 | `user` | `帮我写个开头` | `null` |
| 2 | `assistant` | `主题：AI` | `run_1` |
| 3 | `user` | `再短一点` | `null` |
| 4 | `assistant` | `主题：ML` | `run_2` |

> 这就是第 9、10 条验收标准里的「恰好 4 条、`seq` 1..4、`role` 交替」的来源。

````markdown
### 4.2 会话上下文

`RunRequest` 可带可选的 `conversationId` / `userMessage`（见 `openapi.yaml`）。
带 `conversationId` 时：

- 引擎先校验会话归属（`ownerId` 为当前用户、`appId` 与路径一致），不符即 404
  `Conversation not found`；
- **先读取历史、再写入本轮用户消息**（顺序不可颠倒：否则本轮 user 会混进历史，
  模型会看到两条相同的用户话）；
- 随后把本轮 `userMessage`（非空时）写一条 `role: "user"` 的消息；
- 历史取该会话最近 `MAX_HISTORY_MESSAGES` 条（默认 20，可由环境变量覆盖）消息，
  在变量池中放入 `pool.conversation`；
- `run_started` 的 payload 带上 `conversationId`；**不带会话时省略该键**；
- `run_finished` **之前**写入助手消息（`role: "assistant"`，`runId` 为本次运行 id）；
  内容规则：`outputs` 只有 1 个键时取其字符串值，否则取 `JSON.stringify(outputs)`（紧凑）；
  写入失败即抛错，由统一 `catch` 发出**唯一一帧** `run_failed`（每轮终态恰好一个）；
  `run_failed` 时**不写**助手消息。

`pool.conversation` 的形状固定为：

```json
{
  "id": "<conversationId>",
  "history": "user: ...\nassistant: ...",
  "messages": [{ "role": "user", "content": "..." }]
}
```

- `messages` 按 `seq` **升序**，每项只有 `role` 与 `content` 两个键；
- `history` 由 `messages` 生成：按 `seq` 升序，每条形如 `"{role}: {content}"`，
  多条之间用 **`\n`** 连接（无尾随换行；无消息时为 `""`）。

无会话运行时 `pool` 里**没有** `conversation` 键；模板 `{{ conversation.history }}`
会因路径缺失走 `run_failed`（`template variable not found: conversation.history`）。

**`llm` 的 `useHistory`**：当 `llm.data.useHistory === true` 且 `pool.conversation` 存在时，
把历史消息**前置**为真实消息对象，再接本轮的 system/user 消息：

| 历史 `role` | 转换后 |
| --- | --- |
| `user` | `HumanMessage` |
| `assistant` | `AIMessage` |
| `system` | `SystemMessage` |
| `tool` | **跳过** |

`useHistory === true` 但请求未带 `conversationId` 时，运行前预检即 400
（`llm node {nodeId} useHistory requires a conversation`，见 `error-messages.md` §9）。
````

**这段在干什么**

1. 它定义了**会话如何进入图**：不是全局变量，而是 `pool` 里一个固定形状的 `conversation` 对象；图通过模板 `{{ conversation.history }}` 或 `useHistory` 两种方式消费它。
2. 它把「先读后写」的理由写死了：反过来会让本轮用户消息既在历史里、又在当前 prompt 里，模型会看到两条相同的话。
3. 它规定了 assistant 消息的内容规则与失败时的行为（`run_failed` 不写）。
4. 它明确「无会话时 `pool` 里没有 `conversation` 键」，因此普通模板会**严格报错**（不是空串——空串是阶段 8 分支安全解析的特例，只用于三个位置）。

```markdown
| 预检：`llm.useHistory` 为 true 但请求没带 `conversationId` | 400 | `llm node {nodeId} useHistory requires a conversation` |
| 保存消息失败（流内） | 200(SSE) | `failed to persist conversation message` |

说明：

- **用户消息在开流前写入**：写入失败即返回普通 JSON `400`
  （`message` 为 `failed to persist conversation message`，**不是** SSE 流）。
- **助手消息在 `run_finished` 前写入**：写入失败时抛错，由统一 `catch` 在流内发出
  **唯一一帧** `run_failed`，`message` 为 `failed to persist conversation message`
  （HTTP 状态码不变，仍是 `200` 的 SSE 流）。
- `run_failed` 时不写助手消息。
```

**这段在干什么**

1. 4 条文案覆盖了会话的全部错误面：归属（404）、标题（400）、配置（400）、持久化（双通道）。
2. 第一条把「不存在」与「不属于你」「不属于该应用」合并成**同一句话**，从文案上就不泄露资源是否存在。
3. 第三、四条展示了阶段 4 的「双通道错误」：**能开流前发现的 → 普通 JSON 400；开流后才发现（写 assistant 失败）→ 流内 `run_failed`**。同一个文案 `failed to persist conversation message` 出现在两个通道，但 HTTP 状态码不同。

**这段在干什么**

2. `Message` 只存**消息流水**：`conversationId`、`role`、`content`、`seq`、`runId`。它**没有** `ownerId` / `appId`——归属通过 `conversation` 继承，避免同一事实存两份。
3. `Message` **没有** `updatedAt`：消息是不可变的，只追加、不修改。
4. `@@unique([conversationId, seq])` 是本篇的核心并发保护，同时也能服务「按会话查消息」的常规路径；`@@index([conversationId])` 是单列索引，与唯一索引的前缀重叠（§9.2 末的注）。
5. `role` 用 `String` 而不是 Prisma `enum`：数据库层不建 PG enum，取值由契约的 `enum` 与应用层约束（跨语言更省事，见 §12.5）。
6. `@default(uuid())` 是 **Prisma Client 侧**的默认值，数据库没有 `gen_random_uuid()` 默认值；因此 Python 侧写入时必须自己生成 UUID（§12.11）。

**这段在干什么（按行）**

1. **两张表，零冗余**：`conversations` 不存消息，`messages` 不存 owner/app。归属只在一个地方定义。
2. **`TEXT` 主键**：id 由应用侧生成（Prisma 的 `uuid()` 是客户端默认值）。Python 侧写入时用 `uuid.uuid4()` 生成同样格式的字符串。
3. **`TIMESTAMP(3)`**：毫秒精度，和契约的时间序列化（§2 的 24 字符 `...Z`）配套。注意 Postgres 的 `CURRENT_TIMESTAMP` 是**事务开始时间**，同一事务内多行会拿到同一个值——这正是不能用它排序的原因（§12.3）。
4. **`UNIQUE (conversation_id, seq)`**：会话内的消息序号唯一。两个并发写入算出同一个 `max+1` 时，后提交的那个会违反约束、**失败**，而不是悄悄产生两个同号消息。
5. **三个外键全部 `ON DELETE CASCADE`**：删应用 → 删它的会话 → 删会话的消息；删用户同理。清理路径只有一条，不会留下孤儿消息。
6. **`ON UPDATE CASCADE`**：主键是应用生成的、基本不会更新；这里是 Prisma 迁移的默认写法，保留无害。

> 一个可以观察到的设计余量：`(conversation_id, seq)` 的唯一索引已经以 `conversation_id` 为前缀，单独的 `messages_conversation_id_idx` 在 Postgres 里是**前缀冗余**的。两条都保留不影响正确性；想精简可以删掉后者，但会产生一次额外的迁移。

## 10. 完整代码：`apps/api-py/app/models/conversation.py`

**完整文件路径：`apps/api-py/app/models/conversation.py`**

```python
"""`conversations` / `messages` 表模型（阶段 9）。

重要：这两张表的 DDL 由 TS 侧 Prisma 迁移拥有
（`apps/api-ts/prisma/migrations/20261022140744_add_conversations`）。
Python 只做**映射与读写**、不产生 DDL，以免两套迁移系统互相冲突。

`messages` 的 `(conversation_id, seq)` 有唯一约束；`seq` 在会话内从 1 递增。
"""

from datetime import datetime

from sqlalchemy import DateTime, ForeignKey, Integer, String, Text, func
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.models.base import Base


class Conversation(Base):
    __tablename__ = "conversations"

    # id 由应用侧生成（Prisma 的 uuid() 是客户端默认值，数据库没有默认）
    id: Mapped[str] = mapped_column(String, primary_key=True)
    app_id: Mapped[str] = mapped_column(
        String, ForeignKey("apps.id", ondelete="CASCADE"), nullable=False, index=True
    )
    owner_id: Mapped[str] = mapped_column(
        String, ForeignKey("users.id", ondelete="CASCADE"), nullable=False
    )
    title: Mapped[str | None] = mapped_column(String, nullable=True)
    created_at: Mapped[datetime] = mapped_column(DateTime, nullable=False, server_default=func.now())
    # Prisma 侧 `@updatedAt` 由客户端维护；这里保留应用层 default/onupdate 作为兜底，
    # 追加消息时服务层会显式刷新该列（与 TS 的 `conversation.update({updatedAt})` 对齐）。
    updated_at: Mapped[datetime] = mapped_column(
        DateTime, nullable=False, default=func.now(), onupdate=func.now()
    )

    app: Mapped["App"] = relationship("App", back_populates="conversations")
    owner: Mapped["User"] = relationship("User", back_populates="conversations")
    # `passive_deletes=True`：删除会话时交给数据库的 ON DELETE CASCADE 删消息，
    # 避免 SQLAlchemy 先把 messages.conversation_id 置 NULL（该列 NOT NULL）。
    messages: Mapped[list["Message"]] = relationship(
        "Message", back_populates="conversation", passive_deletes=True
    )


class Message(Base):
    __tablename__ = "messages"

    id: Mapped[str] = mapped_column(String, primary_key=True)
    conversation_id: Mapped[str] = mapped_column(
        String, ForeignKey("conversations.id", ondelete="CASCADE"), nullable=False, index=True
    )
    role: Mapped[str] = mapped_column(String, nullable=False)
    content: Mapped[str] = mapped_column(Text, nullable=False)
    seq: Mapped[int] = mapped_column(Integer, nullable=False)
    run_id: Mapped[str | None] = mapped_column(String, nullable=True)
    created_at: Mapped[datetime] = mapped_column(DateTime, nullable=False, server_default=func.now())

    conversation: Mapped["Conversation"] = relationship(
        "Conversation", back_populates="messages"
    )
```

**这段在干什么（按区块）**

1. **只映射，不建表**：模块 docstring 写死了迁移所有权，避免有人给 Python 再加一套 alembic。
2. **列与 Prisma 一一对应**：`String` → `TEXT`，`Integer` → `INTEGER`，`DateTime` → `TIMESTAMP(3)`（SQLAlchemy 默认的 `DateTime` 是 `TIMESTAMP WITHOUT TIME ZONE`，与 Prisma 的 `TIMESTAMP(3)` 对齐到「naive UTC」的用法）。
3. **`id` 没有数据库默认值**：`mapped_column(String, primary_key=True)`；插入时必须显式给 `str(uuid.uuid4())`。
4. **`updated_at` 的双保险**：`default=func.now()` + `onupdate=func.now()` 是 ORM 兜底；真正与 TS 对齐的是服务层在追加消息时显式 `UPDATE conversations SET updated_at = now()`（否则只读 Python 的 ORM 语义，可能与 Prisma 的 `@updatedAt` 行为不一致）。
5. **`passive_deletes=True`**：删除会话时不先 `UPDATE messages SET conversation_id = NULL`，而是直接把删除交给数据库的 `ON DELETE CASCADE`。阶段 7 删除知识库时踩过同样的坑（`NotNullViolation` → 500）。
6. **双向关系**：`App.conversations` / `User.conversations` / `Conversation.messages` 在对应模型里都有 `back_populates`；Python 侧通过字符串目标延迟解析，避免循环导入。

**完整文件路径：`apps/api-ts/src/conversations/conversations.service.ts`**

```ts
import { BadRequestException, Injectable, NotFoundException } from '@nestjs/common'
import type {
  ConversationListResponse,
  ConversationResponse,
  MessageListResponse,
  MessageResponse,
} from '@mini-dify/contract'

import { PrismaService } from '../prisma/prisma.service'

/** 会话标题长度上限（字符数）。 */
const MAX_TITLE_LENGTH = 120

/** 历史消息默认条数（可由环境变量 `MAX_HISTORY_MESSAGES` 覆盖）。 */
const DEFAULT_MAX_HISTORY_MESSAGES = 20

/** `appendMessage` 遇到唯一约束冲突时的重试次数（并发写同一会话时的兜底）。 */
const APPEND_MESSAGE_RETRIES = 3

/** `pool.conversation` 的形状（见 sse-events.md §4.2）。 */
export interface ConversationContext {
  id: string
  history: string
  messages: Array<{ role: string; content: string }>
}

/**
 * 会话（阶段 9）读写：会话 CRUD + 消息追加 + 历史读取。
 *
 * 归属校验与 `/apps` 一致：查不到、不属于当前用户、或不属于路径中的应用，
 * 一律 404 `Conversation not found`（不泄露存在性）。
 */
@Injectable()
export class ConversationsService {
  constructor(private readonly prisma: PrismaService) {}

  async list(ownerId: string, appId: string): Promise<ConversationListResponse> {
    await this.assertAppOwned(ownerId, appId)
    const conversations = await this.prisma.conversation.findMany({
      where: { ownerId, appId },
      orderBy: { updatedAt: 'desc' },
      include: { _count: { select: { messages: true } } },
    })
    return { items: conversations.map((conversation) => toConversationResponse(conversation)) }
  }

  async create(ownerId: string, appId: string, title?: string): Promise<ConversationResponse> {
    await this.assertAppOwned(ownerId, appId)
    if (title !== undefined && [...title].length > MAX_TITLE_LENGTH) {
      throw new BadRequestException('Conversation title is too long')
    }
    const conversation = await this.prisma.conversation.create({
      data: { ownerId, appId, title },
      include: { _count: { select: { messages: true } } },
    })
    return toConversationResponse(conversation)
  }

  async get(ownerId: string, id: string): Promise<ConversationResponse> {
    return toConversationResponse(await this.findOwned(ownerId, id))
  }

  async remove(ownerId: string, id: string): Promise<void> {
    await this.findOwned(ownerId, id)
    await this.prisma.conversation.delete({ where: { id } })
  }

  async listMessages(ownerId: string, id: string): Promise<MessageListResponse> {
    await this.findOwned(ownerId, id)
    const messages = await this.prisma.message.findMany({
      where: { conversationId: id },
      orderBy: { seq: 'asc' },
    })
    return { items: messages.map((message) => toMessageResponse(message)) }
  }

  /**
   * 引擎侧：按 `ownerId` + `appId` 校验会话归属。
   * 不符时 404 `Conversation not found`（error-messages.md §9）。
   */
  async assertOwnedByApp(ownerId: string, appId: string, id: string): Promise<void> {
    const conversation = await this.prisma.conversation.findUnique({ where: { id } })
    if (conversation === null || conversation.ownerId !== ownerId || conversation.appId !== appId) {
      throw new NotFoundException('Conversation not found')
    }
  }

  /**
   * 追加一条消息：`seq = max(seq) + 1`（事务内读取；唯一约束 `(conversation_id, seq)`
   * 兜底并发冲突，冲突时重试）。同时刷新会话 `updatedAt`。
   */
  async appendMessage(
    conversationId: string,
    role: 'user' | 'assistant' | 'system',
    content: string,
    runId?: string,
  ): Promise<void> {
    for (let attempt = 1; ; attempt += 1) {
      try {
        await this.prisma.$transaction(async (tx) => {
          const last = await tx.message.findFirst({
            where: { conversationId },
            orderBy: { seq: 'desc' },
            select: { seq: true },
          })
          await tx.message.create({
            data: {
              conversationId,
              role,
              content,
              seq: (last?.seq ?? 0) + 1,
              runId: runId ?? null,
            },
          })
          await tx.conversation.update({
            where: { id: conversationId },
            data: { updatedAt: new Date() },
          })
        })
        return
      } catch (error) {
        if (attempt >= APPEND_MESSAGE_RETRIES || !isUniqueViolation(error)) {
          throw error
        }
      }
    }
  }

  /** 读取最近 `limit` 条消息（按 `seq` 升序返回，供 `pool.conversation` 使用）。 */
  async loadHistory(
    conversationId: string,
    limit = maxHistoryMessages(),
  ): Promise<Array<{ role: string; content: string }>> {
    const messages = await this.prisma.message.findMany({
      where: { conversationId },
      orderBy: { seq: 'desc' },
      take: limit,
      select: { role: true, content: true },
    })
    return messages.reverse()
  }

  private async assertAppOwned(ownerId: string, appId: string): Promise<void> {
    const app = await this.prisma.app.findUnique({
      where: { id: appId },
      select: { ownerId: true },
    })
    if (app === null || app.ownerId !== ownerId) {
      throw new NotFoundException('App not found')
    }
  }

  private async findOwned(ownerId: string, id: string) {
    const conversation = await this.prisma.conversation.findUnique({
      where: { id },
      include: { _count: { select: { messages: true } } },
    })
    if (conversation === null || conversation.ownerId !== ownerId) {
      throw new NotFoundException('Conversation not found')
    }
    return conversation
  }
}

/** 历史消息条数上限（`MAX_HISTORY_MESSAGES`，默认 20）。 */
export function maxHistoryMessages(): number {
  const raw = Number(process.env.MAX_HISTORY_MESSAGES ?? DEFAULT_MAX_HISTORY_MESSAGES)
  return Number.isInteger(raw) && raw > 0 ? raw : DEFAULT_MAX_HISTORY_MESSAGES
}

/** 把消息列表构造为 `pool.conversation`（见 sse-events.md §4.2）。 */
export function buildConversationContext(
  id: string,
  messages: Array<{ role: string; content: string }>,
): ConversationContext {
  return {
    id,
    history: messages.map((message) => `${message.role}: ${message.content}`).join('\n'),
    messages: messages.map((message) => ({ role: message.role, content: message.content })),
  }
}

/** Prisma 唯一约束冲突（`P2002`），用于并发追加消息时重试。 */
function isUniqueViolation(error: unknown): boolean {
  return (
    typeof error === 'object' &&
    error !== null &&
    (error as { code?: unknown }).code === 'P2002'
  )
}

function toConversationResponse(conversation: {
  id: string
  appId: string
  title: string | null
  createdAt: Date
  updatedAt: Date
  _count: { messages: number }
}): ConversationResponse {
  return {
    id: conversation.id,
    appId: conversation.appId,
    title: conversation.title ?? null,
    messageCount: conversation._count.messages,
    createdAt: conversation.createdAt.toISOString(),
    updatedAt: conversation.updatedAt.toISOString(),
  }
}

function toMessageResponse(message: {
  id: string
  conversationId: string
  role: string
  content: string
  seq: number
  runId: string | null
  createdAt: Date
}): MessageResponse {
  return {
    id: message.id,
    conversationId: message.conversationId,
    role: message.role as MessageResponse['role'],
    content: message.content,
    seq: message.seq,
    runId: message.runId ?? null,
    createdAt: message.createdAt.toISOString(),
  }
}
```

**这段在干什么（按方法）**

1. **`list`**：先 `assertAppOwned`（应用存在且属于你，否则 404 `App not found`），再 `where: {ownerId, appId}` 双条件过滤，`orderBy updatedAt desc`，并用 `_count` 一次拿到每个会话的消息数（不是循环查询）。
2. **`create`**：先校验应用归属，再用 `[...title].length` 检查**码点**长度（一个中文汉字算 1 个字符；两端都按码点计，组合 emoji 的计数也一致），超长抛固定文案。创建后 `_count.messages` 为 0。
3. **`get` / `remove` / `listMessages`**：统一走 `findOwned`（存在 + `ownerId`）；删除依赖数据库级联；消息按 `seq` 升序。
4. **`assertOwnedByApp`**：给引擎用的**三层校验**——存在、`ownerId`、`appId` 必须同时满足。
5. **`appendMessage`**：在一个事务里「读最大 `seq` → 插入 `max+1` → 刷新会话 `updatedAt`」。唯一约束冲突（`P2002`）时重试，最多 3 次；其它错误直接抛。
6. **`loadHistory`**：按 `seq` 倒序取最近 N 条，再 `reverse()` 成正序；只选 `role` / `content` 两列。
7. **`buildConversationContext`**：把消息列表变成 `pool.conversation` 的三键形状；`history` 用 `\n` 连接、无尾随换行。
8. **`toConversationResponse` / `toMessageResponse`**：只暴露契约字段；可空列统一 `?? null`；时间统一 `toISOString()`（UTC、毫秒、`Z` 结尾，阶段 2 已收口）。

## 12. 首次技术教学

### 12.1 无状态 vs 有状态：状态可以「有」，但不要放在进程里

**是什么**

- **无状态（stateless）**：处理一次请求所需的全部信息都在请求里；服务端不依赖之前的请求，也不修改「下一次请求会读到」的进程内状态。
- **有状态（stateful）**：本次请求的结果依赖并改变之前的状态（例如内存里的对话数组）。

**前 8 阶段的执行是无状态的**

```ts
// EngineService.execute
pool = { inputs }
```

**这段在干什么**

这是前 8 阶段引擎的初始状态：变量池里只有一个 `inputs`。它没有任何「上次运行留下的东西」，所以每次运行都是一次全新的计算。

两次 `POST /run`，只要 `inputs` 相同、图相同，事件序列就相同（除 `runId` / `elapsedMs` 外）。这是阶段 4 能建立「两端事件序列逐字节一致」验收的前提。

**阶段 9 需要跨请求的上下文**

第二轮的用户说「再短一点」，模型必须知道上一轮的回答是什么。上下文必须来自**上一次请求之外**，否则无从获得。

**本项目的解法：无状态计算 + 有状态存储**

| 层 | 是否无状态 | 说明 |
| --- | --- | --- |
| HTTP 处理 / 执行引擎 | 是 | 每次运行新建 `pool`，跑完即弃 |
| Postgres 的 `messages` 表 | 否（持久化） | 会话的全部历史都在这里 |
| `pool.conversation` | 本次运行内 | 从表里读出来的**快照**，运行结束后不再使用 |

**为什么不能放内存**

| 方案 | 问题 |
| --- | --- |
| 进程内 `Map<conversationId, Message[]>` | 多实例不共享、重启丢失、并发要加锁、无法审计 |
| 粘性会话（sticky session） | 只解决「同一实例」，不解决重启与审计，扩容受限 |
| 数据库表 | 天然共享、持久、可查询、可用事务与约束保护 |

**一句话**：**「有状态」是业务语义，不是部署形态。** 会话状态放在数据库里，服务进程仍然是「来一个请求、读一次状态、算一次、写一次」的无状态函数。

### 12.2 两张表的职责划分：归属与元信息 vs 只追加的流水

**职责表**

| 表 | 回答的问题 | 代表列 | 不应该出现的东西 |
| --- | --- | --- | --- |
| `conversations` | 「这是谁的、属于哪个应用、叫什么、最近什么时候动过」 | `owner_id`、`app_id`、`title`、`updated_at` | 消息内容、消息条数、模型名 |
| `messages` | 「这个会话里，谁在第几位说了什么」 | `role`、`content`、`seq`、`run_id` | `owner_id`、`app_id`、`updated_at` |

**为什么消息不重复存归属**

`messages` 只存 `conversation_id`。归属链是：

```
messages.conversation_id → conversations.app_id / conversations.owner_id
```

这样「一条消息属于谁」永远只有一个答案，不会出现「会话属于 A、消息却标了 B」的不一致。

**为什么消息表是只追加（append-only）**

| 理由 | 说明 |
| --- | --- |
| 语义正确 | 对话记录是**发生过的事实**，不是可编辑的文档；改一条历史会让后续所有轮次的上下文失真 |
| `seq` 有意义 | 只有「只追加」，`seq` 才能稳定表示「第几条」；允许插入/删除会让序号出现空洞或需要重排 |
| 并发简单 | 只追加不需要行锁更新；并发冲突由唯一约束暴露 |
| 可审计 | 用户到底说了什么、模型到底答了什么，原样保留 |

> 注意：**「只追加」不等于「永远不删」**。删除整个会话时，消息随 `ON DELETE CASCADE` 一起删除；这是「会话生命周期」的操作，不是「编辑单条消息」。

**为什么 `messageCount` 不落库**

如果在 `conversations` 存一个 `message_count` 整数，就要在每次追加/删除时维护它；一旦某次写入失败或有人手工改库，计数就会与事实不一致。本项目改为**读时计算**：

- Prisma：`include: { _count: { select: { messages: true } } }`，一次查询带出所有会话的计数。
- Python：相关子查询 `select count(messages.id) where ...`，同样一次查询。

这是典型的「**派生值不存储**」：用一点读开销换掉一整类不一致。

### 12.3 `seq` 为什么必须显式：`created_at` 不是顺序

**看起来可行的方案**

```sql
SELECT * FROM messages WHERE conversation_id = $1 ORDER BY created_at ASC;
```

**这段在干什么**

这是「用时间戳当顺序」的最自然写法：按写入时间升序读。下面的四个问题说明它为什么不可靠。

**它在四个地方会坏**

| 问题 | 说明 |
| --- | --- |
| 毫秒精度会撞车 | 列是 `TIMESTAMP(3)`。同一毫秒内写入两条消息，`created_at` 完全相同，`ORDER BY` 对它们没有定义顺序 |
| Postgres 的 `CURRENT_TIMESTAMP` 是**事务开始时间** | 同一个事务里插入多行，所有行拿到**同一个**时间戳。`now()` 在事务内是常量 |
| 时钟会回拨 | NTP 校时、虚拟机迁移都可能让后写入的行时间更早 |
| 并发写入顺序不确定 | 两条事务同时提交，时间戳先后不保证等于提交顺序 |

**本项目的方案：会话内显式的单调序号**

```text
seq = 1, 2, 3, 4, ...
```

**这段在干什么**

这是 `messages.seq` 的取值序列：每个会话各自从 1 开始，由应用在写入时计算，而不是数据库全局自增。下面的四条是它的语义边界。

- **从 1 开始**：第一轮 user 是 1，assistant 是 2，第二轮 user 是 3……
- **只在一个会话内递增**：不同会话可以都有 `seq = 1`。
- **由应用计算**：`seq = max(seq) + 1`（事务内读取）。
- **不暴露全局信息**：不是数据库自增序列，所以不会泄露「全站一共有多少条消息」，删除会话也不会留下跨会话的空洞。

**为什么不用数据库自增（identity / sequence）**

| 问题 | 说明 |
| --- | --- |
| 全局而非按会话 | 一个全局序列无法表达「每个会话都从 1 开始」 |
| 空洞 | 回滚、删除都会产生空洞；前端看到 `seq` 跳跃会误以为丢消息 |
| 泄露规模 | `seq` 直接暴露全站写入量 |

**`seq` 是契约的一部分**

`MessageResponse.required` 里包含 `seq`。客户端可以拿它做：

- 分页游标（`afterSeq`）；
- 去重（同一条消息被重复推送时按 `seq` 判定）；
- 展示「第几条」。

所以它不能只是「数据库内部的排序辅助列」。

### 12.4 `UNIQUE(conversation_id, seq)` 是并发保护，不是装饰

**并发场景**

```text
会话当前最大 seq = 5

请求 A：读 max = 5 → 打算写 6
请求 B：读 max = 5 → 打算写 6
        ↓
     两者都写 6
```

**没有唯一约束时**

两行 `seq = 6` 都成功插入。后果：

- `ORDER BY seq` 对这两行**没有确定顺序**（数据库可以任意返回）；
- 历史可能变成 `... user, user, assistant, assistant ...`（两条用户消息相邻）；
- 下一轮读到的是「错乱的历史」，模型回答的质量无法解释；
- 这类错误**不会报错**，只会偶尔出现，极难排查。

**有唯一约束时**

后提交的那条违反 `UNIQUE (conversation_id, seq)`：

- Prisma 抛 `P2002`；
- SQLAlchemy 抛 `IntegrityError`；
- 服务层捕获后**重试**：重新读 `max`（此时是 6）→ 写 7。

结果：消息顺序始终唯一且连续，最坏情况是写入变慢，而不是数据悄悄坏掉。

**这是「乐观并发控制」**

| 特点 | 说明 |
| --- | --- |
| 无锁 | 不在读的时候锁住会话，两个请求可以并行算 |
| 冲突窗口小 | 从「读到 max」到「插入」之间只有极短时间 |
| 冲突显式化 | 由数据库约束把冲突变成异常，而不是让应用猜 |
| 重试兜底 | 3 次足够覆盖正常的并发碰撞；仍失败就按契约报错 |

**为什么不能只靠重试、不加约束**

重试的前提是「冲突能被发现」。没有唯一约束，两个 `seq = 6` 都能成功，应用**根本不知道**发生了冲突，也就不会重试。

### 12.5 `role` 的取值与 `runId` 为什么只在 assistant 上

**`role` 的三个值**

| 值 | 谁产生 | 本阶段是否实际写入 | 含义 |
| --- | --- | --- | --- |
| `user` | 请求里的 `userMessage` | 是 | 人类这一轮说的话 |
| `assistant` | 图的输出（`run_finished.outputs`） | 是 | 本轮运行产出的回答 |
| `system` | 人工/系统注入 | 否（预留） | 系统提示、规则、运营注入 |

- 数据库列是 `TEXT`，**没有 CHECK 约束**；闭集由契约的 `enum` 与写入方的类型约束（TS 的 `'user' | 'assistant' | 'system'`，Python 的类型注释）保证。
- 为什么不建 PG enum：跨语言、跨迁移系统的 enum 变更成本高；本项目的取值很少变，用契约做唯一真源更轻。
- 为什么没有 `tool`：工具调用是**一次运行内部的中间步骤**，已经通过 SSE 的 `tool_call` / `tool_result` 事件暴露；它不属于「用户与助手之间的持久对话」。§4.2 的映射表里保留 `tool` → 跳过，是为了将来兼容外部导入的历史。

**`runId` 只在 assistant 上**

| 消息 | `runId` | 原因 |
| --- | --- | --- |
| `user` | `null` | 写入发生在 `execute()` 之前，此时 `runId` 还没生成（`randomUUID()` 在 `run_started` 前才调用） |
| `assistant` | 本次运行的 id | 这条消息是「第几次运行」的产物，用它可以把回答与 SSE 流、日志、问题排查关联起来 |
| `system` | `null` | 不是某次运行产生的 |

- `runId` **不是外键**：本项目没有 `runs` 表，不会为每次运行建一行。它只是一个**关联 id**，用于跨日志追踪。
- 因此 `runId` 可空，且历史数据里可能永远查不到对应的运行记录——这是设计，不是缺陷。

### 12.6 归属三层校验：为什么统一返回 404

**三层分别是什么**

| 层 | 检查 | 不满足时 |
| --- | --- | --- |
| 会话存在 | `findUnique(id)` 有结果 | 404 `Conversation not found` |
| 谁是主人 | `conversation.ownerId === 当前用户.sub` | 404 `Conversation not found` |
| 属于哪个应用 | `conversation.appId === 路径中的 appId` | 404 `Conversation not found` |

**不同路由上生效的层数不同（这是源码的真实行为）**

| 路由 | 存在 | ownerId | appId | 说明 |
| --- | --- | --- | --- | --- |
| `GET/POST /apps/{id}/conversations` | —（列表/新建） | 查询条件 `ownerId` | 查询条件 `appId` + 先校验应用归属 | 应用不属于你 → 404 `App not found` |
| `GET/DELETE /conversations/{id}`、`GET .../messages` | ✔ | ✔ | 路径里没有 appId，无法校验 | 只校验存在 + `ownerId` |
| `POST /apps/{id}/run` + `conversationId` | ✔ | ✔ | ✔ | `assertOwnedByApp` 三层全查 |

> 「归属三层」在**运行接口**上是完整的三层；在 `/conversations/{id}` 上只有两层（存在 + ownerId），因为路径里没有 `appId` 可供比对。这不是遗漏：会话创建时 `appId` 已固定，且它只能由 `ownerId` 的主人创建。

**为什么是 404 而不是 403**

| 返回 | 泄露的信息 |
| --- | --- |
| `403 Forbidden` | 「这个 id 确实存在，只是不属于你」——攻击者可以用它枚举有效 id |
| `404 Not Found` | 「不存在、不是你的、不属于这个应用」三者**不可区分** |

阶段 2 已经定下这条惯例（`App not found`），阶段 9 原样复用（`Conversation not found`）。文案也统一：三种失败原因共用一句话。

**实现上的一个小选择**

源码用 `findUnique({where:{id}})` 后再比较，而不是 `findFirst({where:{id, ownerId}})`：

- 两者都能达到「不泄露」的效果；
- 先取再比较，可以在一处同时检查 `ownerId` 与 `appId`（引擎侧需要三层）；
- 对单条主键查询来说，代价一样。

### 12.7 5 个接口的契约设计

**为什么消息列表按 `seq` 升序，会话列表按 `updatedAt` 倒序**

| 列表 | 方向 | 理由 |
| --- | --- | --- |
| 消息 | `seq ASC` | 对话是**从上往下读**的；`seq` 是唯一的总顺序。客户端拿到即可直接渲染，不用反转 |
| 会话 | `updatedAt DESC` | 侧边栏的「最近会话」在最上面；`updatedAt` 在每次追加消息时刷新，正好代表「最近活跃」 |

> 反例：如果消息按 `createdAt DESC` 返回，前端每次都要 `reverse()`；一旦有同毫秒消息，反转后的顺序仍然不确定。

**为什么 `POST` 是 201、`DELETE` 是 204**

| 接口 | 状态码 | 理由 |
| --- | --- | --- |
| `POST /apps/{id}/conversations` | `201 Created` | 服务端分配了 `id`，创建了一个新资源；响应体返回完整资源，客户端可直接入列表 |
| `DELETE /conversations/{id}` | `204 No Content` | 删除没有有意义的表示；返回空体，客户端只看状态码 |

这与阶段 2 的应用 CRUD 完全同一套约定。

**为什么有 `messageCount`**

列表页要显示「这个会话有 4 条消息」。如果没有这个字段，客户端会对每个会话再发一次 `GET /messages` ——典型的 N+1。服务端一次查询带出计数更便宜。

- TS：Prisma 的 `_count` 关系聚合；
- Python：相关标量子查询（`select count(...) where messages.conversation_id = conversations.id`）。

**为什么没有分页**

本阶段的消息列表返回**全部**消息。这不代表永远不分页：`seq` 已经为将来留下 `afterSeq` / `beforeSeq` 的游标基础。当前先保持契约最小。

**为什么没有 `PATCH /conversations/{id}`**

本阶段不需要改标题。少一个接口，就少一份归属校验、少一组错误文案、少一处两端对齐的成本。等有真实需求再加。

**为什么标题长度检查在服务层**

| 位置 | 产出的文案 |
| --- | --- |
| DTO 的 `@MaxLength(120)` / Pydantic `max_length` | 通用文案 `title must be at most 120 characters` |
| 服务层 `if ([...title].length > 120)` | 契约文案 `Conversation title is too long` |

契约 §9 指定了后者，所以 DTO 只做类型校验，长度交给服务层。**「契约文案优先于框架默认文案」**是本项目从阶段 2 起的一贯原则。

### 12.8 `run_started.conversationId` 可选：省略键，而不是写 `null`

**契约怎么说**

```text
run_started  payload: runId(string)、appId(string)、conversationId(string，可选：无会话时省略该键)
```

**两种实现只差一个字符，但 JSON 形状不同**

```jsonc
// 正确：无会话
{ "runId": "r1", "appId": "a1" }

// 错误：无会话时写了 null
{ "runId": "r1", "appId": "a1", "conversationId": null }
```

**这段在干什么**

上面两个 JSON 在「业务上都是无会话」，但**形状不同**：左边只有两个键，右边有三个键。契约比对的是解析后的 JSON，二者不相等；而契约声明 `conversationId` 是 `string`，右边的 `null` 还违反了类型。

**为什么必须省略**

1. **契约一致性**：`conversationId` 的类型是 `string` 且「可选」，不是 `["string","null"]`。写 `null` 是类型违规。
2. **两端逐字节一致**：阶段 4 的验收要求两端帧的**键集合**一致。一端省略、一端写 `null`，解析后的 JSON 也不相等。
3. **消费方语义**：「没有会话」应表达为「这个键不存在」，消费方用 `'conversationId' in data` 就能判断；`null` 会迫使每个消费方额外处理一种「键在但值为空」的状态。
4. **模板解析**：如果未来有人在模板里写 `{{ conversation.id }}`，键缺失会走严格报错；`null` 会变成字符串 `"null"`，更难排查。

**两端的实现方式**

```ts
// api-ts：条件构造，绝不填 null
export function runStarted(runId: string, appId: string, conversationId?: string): RunEvent {
  return conversationId === undefined
    ? { event: 'run_started', data: { runId, appId } }
    : { event: 'run_started', data: { runId, appId, conversationId } }
}
```

```python
# api-py：先放两个键，有会话才加第三个
def run_started(run_id: str, app_id: str, conversation_id: str | None = None) -> dict[str, Any]:
    data: dict[str, Any] = {"runId": run_id, "appId": app_id}
    if conversation_id is not None:
        data["conversationId"] = conversation_id
    return {"event": "run_started", "data": data}
```

**这段在干什么**

两端都用「**先构造两个必备键，再按条件追加第三个**」的写法，而不是先把 `conversationId` 设成 `null` 再序列化。这样「无会话」的帧里根本不存在该键，与契约的「可选」完全一致；两种实现也天然对齐。

**请求侧的「可选」也不等于「可空」**

- TS 用 `@ValidateIf((_dto, v) => v !== undefined)`，而不是 `@IsOptional()`：显式传 `null` 会进入 `@IsString()` 并失败。
- Python 用 `conversationId: str = Field(default=None)` 的写法（注解是 `str`、默认是 `None`）：缺省不校验，显式 `null` 判类型错误。

这样「无会话」只有一种表达：**不传这个键**。

### 12.9 `userMessage` 与 `inputs` 为什么要分开

**两个字段回答的是不同的问题**

| 字段 | 回答的问题 | 典型形状 | 去向 |
| --- | --- | --- | --- |
| `inputs` | **图需要什么参数？** | `{ "topic": "AI", "style": "口语" }` | 进入 `pool.inputs`，被节点模板 `{{ inputs.topic }}` 渲染；`start` 节点据此做必填预检 |
| `userMessage` | **用户这一轮说了什么？** | `"帮我写个开头"` | 写入 `messages`（`role: "user"`），供列表展示与后续轮次的历史 |

**例子：两者常常不同**

```
inputs      = { "topic": "AI", "style": "口语" }
userMessage = "帮我写个开头"
```

- 图需要的是**结构化参数**（主题、风格），它们决定 prompt 怎么拼；
- 用户实际说的是**一句自然语言**，它要显示在聊天窗口里、要成为下一轮的历史。

反过来也成立：用户说「再短一点」，`inputs.style` 可能是 `"更短"`，也可能根本没变——**自然语言与结构化参数不是一一映射**。

**为什么不由 `inputs` 自动生成 `userMessage`**

| 方案 | 问题 |
| --- | --- |
| `userMessage = JSON.stringify(inputs)` | 聊天窗口会显示一串 JSON，不可读 |
| `userMessage = inputs.query ?? inputs.topic ?? ''` | 没有统一的约定；图可以有任意多个字段，无法可靠推断 |
| 独立字段 | 语义清晰；调用方明确表达「用户说了什么」和「图需要什么」 |

**为什么不由 `userMessage` 自动生成 `inputs`**

`inputs` 的形状由 `start.data.inputs` 声明，可能是多个字段、数字、对象；把一句自然语言塞进去无法通过必填/类型预检。**`inputs` 是图的输入，`userMessage` 是人的输入。**

**生命周期差异**

| 行为 | `inputs` | `userMessage` |
| --- | --- | --- |
| 参与运行前预检（必填字段） | 是 | 否 |
| 写入数据库 | 否 | 是（非空时） |
| 进入 `pool.inputs` | 是 | 否 |
| 进入 `pool.conversation.history` | 否 | 本轮**不**进（先读后写） |
| 参与模板渲染 | 通过 `{{ inputs.* }}` | 只能通过图自己的 prompt 引用对应 `inputs` |

**两个常见误解**

1. **「传了 `userMessage`，模型就会看到它」**：不会。模型看到的是 `llm.data.prompt` 渲染后的文本；如果 prompt 没有引用包含这段文字的 `inputs`，它就不会进模型。`userMessage` 只负责「被记录下来」。
2. **「`userMessage` 会进入本轮历史」**：不会。历史在写 user 之前读取（§12.10），所以本轮 user 只以「当前 prompt」的身份出现，不会在历史里重复一遍。

**边界值**

- `userMessage` 最多 4000 字符；超过 → 通用校验 400（`userMessage must be at most 4000 characters`）。
- `userMessage === ''` 视为「没有要记录的用户消息」，**不写行**（但运行照常进行，assistant 消息仍会写）。

### 12.10 运行时的三个事实（完整实现见本阶段 `02`）

本节只讲「这两张表如何在一次运行里被读写」的三个关键事实。引擎的完整接入（`engine.service.ts` / `engine.py` 的会话分支、`pool.conversation` 的逐字节构造、`useHistory` 的消息转换）由 `02-历史加载与上下文注入-NestJS.md` 首次教学，本篇只引用。

**① 先读历史、再写本轮 user**

```
读历史（最近 N 条，seq 升序）   ← 快照里不含本轮
        ↓
写 user（seq = max + 1）
        ↓
构造 pool.conversation
```

为什么顺序不可颠倒：如果先写 user 再读历史，历史里就会包含本轮用户话；而本轮的 prompt 又由 `inputs` 渲染出同一段话。模型会收到**两条一模一样的用户消息**。先读后写保证：

- 历史 = **之前**的轮次；
- 本轮用户话 = **当前** prompt；
- 各出现一次。

**② 写入选时机的双通道**

| 消息 | 写入时机 | 失败处理 |
| --- | --- | --- |
| user | 打开 SSE 流之前 | 普通 JSON **400** `failed to persist conversation message` |
| assistant | `run_finished` 发出之前（带 `runId`） | 流内**唯一一帧** `run_failed`（HTTP 仍 200；`run_finished` 不会出现） |

`run_failed` 时不写 assistant：失败时没有可信的 `outputs`，把错误存成「回答」会污染后续轮次。这也是阶段 4「HTTP 状态码只有一次机会」的再次应用。

**③ 历史是一个有窗口的视图**

`pool.conversation` 的固定形状（完整规则见 `sse-events.md` §4.2）：

```json
{
  "id": "conv_...",
  "history": "user: 帮我写个开头\nassistant: 主题：AI",
  "messages": [
    { "role": "user", "content": "帮我写个开头" },
    { "role": "assistant", "content": "主题：AI" }
  ]
}
```

- `messages` 按 `seq` 升序，每项只有 `role` / `content`；
- `history` 由 `messages` 生成（`"{role}: {content}"`、`\n` 连接、无尾随换行、空时 `""`）；
- 只取最近 `MAX_HISTORY_MESSAGES`（默认 20）条：消息表可以无限增长，但每次运行只带一个有界的窗口进上下文。

**无会话时没有 `conversation` 键**：`pool` 只有 `{ inputs }`，所以 `{{ conversation.history }}` 会走严格模板解析并 `run_failed`（`template variable not found: conversation.history`）。阶段 8 的「路径缺失 → 空串」只适用于 `condition` / `aggregator` / `iteration.inputArray` 三个位置，**不适用于普通模板**。

### 12.11 两端映射与迁移所有权

**同一张表，两套 ORM**

| 事实 | Prisma（api-ts） | SQLAlchemy（api-py） |
| --- | --- | --- |
| DDL 归属 | **拥有**（`prisma migrate`） | **不产生**（无 alembic） |
| 表/列名 | `@@map("conversations")` / `@map("app_id")` | `__tablename__` / `mapped_column` 显式列名 |
| `id` 生成 | `@default(uuid())`（**客户端**） | `str(uuid.uuid4())`（服务层显式） |
| `updated_at` | `@updatedAt`（客户端维护） | `default` / `onupdate` 兜底 + 追加消息时显式刷新 |
| 级联删除 | `onDelete: Cascade`（迁移里是数据库外键） | `passive_deletes=True`，交给数据库 |
| 时间 | `toISOString()` | `iso_z()`（阶段 2 已收口） |
| 标题长度 | `[...title].length`（码点） | `len(title)`（码点） |

**为什么 Python 不建表**

如果 Python 也维护一套迁移，两张表就有两个「真相」：一边改了列，另一边不知道，启动后才 500。阶段 1 已经定下：**Prisma 是 DDL 的唯一所有者**，Python 只映射。新增字段的正确流程永远是：

```
改 schema.prisma → prisma migrate dev → Python 模型跟着加 mapped_column → 两端重启
```

**为什么 `id` 必须由应用生成**

Prisma 的 `@default(uuid())` 是 **Prisma Client** 的行为，数据库列上没有 `DEFAULT gen_random_uuid()`。Python 走的是另一条写入路径，如果不自己生成 UUID，就会插入 `NULL` 主键。

**为什么 `updated_at` 要显式刷新**

- Prisma 的 `@updatedAt` 只在通过 Prisma Client 执行 `update` 时自动写；
- 追加消息时源码显式 `conversation.update({ data: { updatedAt: new Date() } })`，所以两条路径都可靠；
- Python 侧 `onupdate` 只在 ORM 发出 UPDATE 时生效，服务层同样显式 `UPDATE conversations SET updated_at = now()`。

**`passive_deletes` 为什么必须有**

删除会话时，如果 ORM 认为「关系归它管」，会先执行：

```sql
UPDATE messages SET conversation_id = NULL WHERE conversation_id = ...;
```

而 `messages.conversation_id` 是 `NOT NULL` → `NotNullViolation` → 500。`passive_deletes=True` 告诉 SQLAlchemy「别管，交给数据库的 `ON DELETE CASCADE`」。阶段 7 删除知识库时已经踩过这个坑（见 `INDEX.md` 的「已知遗留」）。

**（d）保存消息失败**

`failed to persist conversation message` 需要制造数据库写入失败（例如外键失效、唯一约束连续冲突 3 次）。本阶段不要求手工复现，但文案已经在 §9 登记；实现上：

- user 写入失败 → 普通 JSON 400（开流前）；
- assistant 写入失败 → 流内 `run_failed`（HTTP 仍 200）。

## 14. 常见坑

| 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- |
| 用 `created_at` 给消息排序 | 两条消息顺序偶尔互换；同一事务写入的多条顺序完全乱 | `TIMESTAMP(3)` 只有毫秒精度；Postgres 的 `CURRENT_TIMESTAMP` 是**事务开始时间**；时钟可能回拨。用 `ORDER BY seq`（§12.3） |
| 以为 `seq` 可以由数据库自增 | 不同会话的 `seq` 不都从 1 开始 | 全局序列无法表达「会话内从 1 递增」；`seq` 必须应用侧按会话计算（§12.3） |
| 并发写同一会话，偶尔出现两个相同 `seq` | 历史顺序错乱，且没有任何报错 | 检查唯一约束是否真的建了：`\d messages` 应有 `messages_conversation_id_seq_key UNIQUE`；应用侧要捕获 `P2002` / `IntegrityError` 并重试（§12.4） |
| 给 `messages` 加 `owner_id` / `app_id` | 同一条消息出现两份归属，可能不一致 | 归属只在 `conversations` 存一份；消息通过 `conversation_id` 继承（§12.2） |
| 给 `messages` 加 `updated_at` 并允许编辑 | 历史被改写，后续轮次的上下文失真 | 消息表是只追加的；要「改」就追加一条新消息（§12.2） |
| 在 `conversations` 存 `message_count` | 计数与实际条数偶尔不一致 | 改为读时计算（`_count` / 相关子查询），派生值不落库（§12.2） |
| 不带 `conversationId`，却在 prompt 里写 `{{ conversation.history }}` | `run_failed: template variable not found: conversation.history` | 无会话时 `pool` 里没有 `conversation` 键；普通模板是**严格**解析，不会当成空串（§12.10） |
| 以为「缺路径 → 空串」到处适用 | 分支图能跑，普通 LLM 节点却报错 | 空串规则只用于 `condition` / `aggregator` / `iteration.inputArray`（阶段 8 §4.1）；会话模板不适用 |
| 只传 `userMessage`、不传 `inputs` | 400 `missing required input: topic` | `userMessage` 不参与 `start` 的必填预检；图需要的是 `inputs`（§12.9） |
| 只传 `inputs`、不传 `userMessage` | 会话里第一条消息是 `assistant`（`seq = 1`） | user 消息只在 `userMessage` 非空时写入；assistant 在 `run_finished` 前无条件写（§12.9、§12.10） |
| 以为 `userMessage` 会自动成为模型输入 | 模型完全没看到用户那句话 | `userMessage` 只入库；模型看到的是 `llm.data.prompt` 渲染结果。要让本轮文本进模型，prompt 必须引用包含它的 `inputs`（§12.9） |
| 以为本轮 `userMessage` 会出现在 `pool.conversation.history` 里 | 历史条数比预期多 1 或出现重复用户话 | 历史在写 user **之前**读取；本轮 user 以「当前 prompt」的身份出现（§12.10） |
| 把「先读历史、再写 user」的顺序写反 | 模型看到两条相同的用户话 | 顺序不可颠倒；反了就会把本轮 user 混进历史（§12.10） |
| 无会话时把 `run_started` 写成 `conversationId: null` | 两端帧的键集合不同，比对失败 | 必须**省略键**；TS 用条件构造，Python 用 `if conversation_id is not None`（§12.8） |
| 请求里显式传 `conversationId: null` | 400 类型错误，而不是「当成无会话」 | 契约里「可选」≠「可空」；TS 的 `ValidateIf` 与 Python 的 `str = Field(default=None)` 都会拒绝 `null`（§12.8） |
| 在 DTO 上加 `@MaxLength(120)` | 超长标题的文案变成 `title must be at most 120 characters` | 契约要求 `Conversation title is too long`；长度检查放服务层（§12.7） |
| 用字节数检查标题长度 | 中文标题在 40 字左右就被拒 | 两端都按**码点**：TS `[...title].length`、Python `len(title)`（组合 emoji 也按码点计，两端一致） |
| 访问别人的会话期望 403 | 实际 404 | 统一 404 不泄露存在性（§12.6） |
| 用别人的 `appId` 查会话列表 | 返回 404 `App not found`，不是 `Conversation not found` | 列表 / 创建先校验应用归属；这是阶段 2 的既有惯例（§12.6） |
| 删除会话后想保留消息 | 消息全没了 | 外键 `ON DELETE CASCADE` 是设计；要保留历史就不要删会话（§12.2） |
| Python 删除会话报 `NotNullViolation` | 500 | `Conversation.messages` 必须加 `passive_deletes=True`，让数据库级联（§12.11） |
| Python 侧直接读 `os.environ["MAX_HISTORY_MESSAGES"]` | `.env` 里的值不生效，永远 20 | pydantic-settings 只把 `.env` 读进 `Settings`，不回写进程环境；走 `settings.max_history_messages`（详见 `04-Python对齐与前端会话面板.md`） |
| Python 侧自己建表 / 跑 alembic | 两套迁移系统冲突，列定义漂移 | Prisma 拥有 DDL，Python 只映射（§12.11） |
| Python 插入消息不生成 UUID | 主键 `NULL` 或重复 | Prisma 的 `uuid()` 是客户端默认值；Python 必须 `str(uuid.uuid4())`（§12.11） |
| 认为 `runId` 一定可以回查 | 查不到对应的运行记录 | 没有 `runs` 表；`runId` 只是关联 id（§12.5） |
| 把 `tool` 当成 `role` 的合法值 | 400 / 写入脏数据 | 契约只有 `user` / `assistant` / `system`；`tool` 只在 SSE 事件里（§12.5） |
| `messages` 的 `seq` 出现 0 或跳号 | 排序/分页异常 | `seq` 从 1 开始；`max ?? 0` 后 +1；不要手工改库 |
| Prisma 迁移顺手 DROP 了 HNSW 索引 | 检索变慢 / 报错 | 已知遗留：删掉自动生成的 `DROP INDEX`，执行 `db:index` 重建（§4） |

## 15. 本篇技术点登记（同步到 `docs/tutorial/INDEX.md`）

| 技术点 | 说明 | 登记 |
| --- | --- | --- |
| **无状态 vs 有状态（会话版）** | 前 8 阶段每次运行只依赖 `{inputs}`，两次运行互不影响；阶段 9 让同一会话的多次运行共享上下文。实现是 **stateless compute + stateful storage**：状态放 `messages` 表，进程仍无状态；每次运行「读历史 → 构造 `pool.conversation` → 跑图 → 追加消息」。不能放内存（多实例 / 重启 / 并发 / 审计四个问题） | **首次教学于本篇** |
| **会话两表职责划分** | `conversations` = 归属与元信息（`appId` / `ownerId` / `title` / `createdAt` / `updatedAt`）；`messages` = 只追加的消息流水（`conversationId` / `role` / `content` / `seq` / `runId`）。归属只存一份，消息通过会话继承；`messageCount` 是读时计算的派生值，不落库；消息不可变、无 `updated_at` | **首次教学于本篇** |
| **`seq` 为什么必须显式** | 消息顺序不能靠 `created_at`：`TIMESTAMP(3)` 毫秒精度会撞车；Postgres 的 `now()` / `CURRENT_TIMESTAMP` 是**事务开始时间**（同事务多行同值）；时钟回拨；并发提交顺序不保证。`seq` 是会话内从 1 递增的显式整数（`max+1`），是契约字段，可用于分页 / 去重；不用全局自增（无法按会话、有空洞、泄露规模） | **首次教学于本篇** |
| **`UNIQUE(conversation_id, seq)` 是并发保护** | 两个请求同时读到 `max=5` 都想写 6；唯一约束让后提交者失败（Prisma `P2002` / SQLAlchemy `IntegrityError`），服务层重试（3 次）；没有约束则会**静默**产生两个 `seq=6`，`ORDER BY seq` 顺序不确定、历史错乱。这是乐观并发控制：无锁、冲突窗口小、冲突显式化 | **首次教学于本篇** |
| **`role` 三取值与 `runId` 的归属** | `role` 闭集 `user` / `assistant` / `system`，由契约 `enum` 约束，DB 为 `TEXT`（不建 PG enum）；`tool` 不属于持久对话，只在 SSE 事件里，历史映射时跳过。`runId` 只在 assistant 上：user 在 `runId` 生成前写入故为 `null`，system 非运行产物；`runId` 不是外键（没有 `runs` 表），只是关联 id | **首次教学于本篇** |
| **归属三层校验与统一 404** | 「会话存在 + `ownerId` 是当前用户 + `appId` 与路径一致」，任一不符统一 404 `Conversation not found`；`/apps/{id}/conversations` 先校验应用归属（404 `App not found`）；`/conversations/{id}` 因路径无 `appId` 只查存在 + ownerId；`/run` 三层全查。404 而非 403 是为了不泄露「存在但不属于你」，三种失败原因共用一句文案 | **首次教学于本篇** |
| **5 个会话接口的契约设计** | 消息按 `seq` **升序**（对话从上往下读、`seq` 是唯一总顺序）；会话按 `updatedAt` **倒序**（最近活跃在最上，追加消息时刷新）；`POST` 201（新建资源、返回完整体）；`DELETE` 204（无表示）；`messageCount` 读时计算避免 N+1（Prisma `_count` / SQL 相关子查询）；暂不分页（`seq` 为将来 `afterSeq` 留基础）、暂不做 `PATCH` | **首次教学于本篇** |
| **`run_started.conversationId` 可选 = 省略键** | 契约类型是 `string` + 可选，不是 `["string","null"]`；无会话时**不能**写 `null`，否则两端帧键集合不同、解析后的 JSON 也不等，消费方还要多处理一种「键在但空」的状态。TS 用三元条件构造，Python 用 `if conversation_id is not None` 条件加键；请求侧「可选」同样不等于「可空」（`ValidateIf` / `Field(default=None)` 拒绝显式 `null`） | **首次教学于本篇** |
| **`userMessage` 与 `inputs` 的分工** | `inputs` = 给图用的结构化参数（进入 `pool.inputs`、参与 `start` 必填预检、被模板渲染）；`userMessage` = 给人看的聊天文本（写入 `messages.role=user`、用于展示与后续历史）。两者常不同（`{topic, style}` vs 「帮我写个开头」）；不能互相推导（JSON 不可读、无统一字段约定）；`userMessage` 不自动进模型、也不进本轮历史；≤ 4000 字符，空串不写 | **首次教学于本篇** |
| **会话表的两端映射与迁移所有权** | Prisma 拥有 DDL（迁移 `20261022140744_add_conversations`），SQLAlchemy 只映射（无 alembic）；`@default(uuid())` 是客户端默认值 → Python 必须 `uuid4()`；`@updatedAt` 客户端维护 → Python 用 `default/onupdate` + 显式刷新；`onDelete: Cascade` ↔ `passive_deletes=True`（否则先置 NULL → `NOT NULL` 违约 500）；`TIMESTAMP(3)` ↔ `DateTime`（naive UTC）；时间输出 `toISOString()` / `iso_z()`；标题长度两端都按码点 | **首次教学于本篇** |
