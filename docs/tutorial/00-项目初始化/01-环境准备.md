## 5. 【技术教学 · 首次】包管理器：npm 与 pnpm

> 规则：本节是「包管理器 / pnpm」的**首次教学**，后续笔记遇到 `pnpm install`、`--filter` 只写「见阶段 0·01」并直接使用。

### 5.1 包管理器是什么

JS 生态里，一个项目依赖几十上百个第三方库，而这些库自己又依赖别人。**包管理器**负责三件事：

1. **读依赖清单**（`package.json` 的 `dependencies` / `devDependencies`）。
2. **解析版本与依赖树**，并把结果写进**锁文件**（`pnpm-lock.yaml`），保证别人装出同样的树。
3. **下载并落盘**到 `node_modules`，再把可执行脚本挂上来（如 `nest`、`next`）。

`npm` 是 Node 自带的那个；`pnpm` 是**同一件事的另一种实现**，也就是「npm 的替代品」。

### 5.2 npm 与 pnpm 的核心差异

| 维度 | npm | pnpm |
| --- | --- | --- |
| 存放方式 | 每个项目的 `node_modules` 里各存一份包（扁平化 + 提升） | 所有包先按内容哈希存进**全局 store**，项目里只建**硬链接 / 符号链接**指过去 |
| 磁盘 | 同一版本在 10 个项目里 = 10 份 | 同一版本全机只有 **1 份**（store 里） |
| 安装速度 | 一般 | 更快（大量操作只是建链接） |
| `node_modules` 结构 | 扁平化提升 → 能 import 到「没写进 dependencies 的包」（**幽灵依赖**） | 严格：只有声明过的依赖才能 import |
| 多包仓库（monorepo） | 需要额外工具 | **workspace 一等公民**（`workspace:*` + `--filter`） |

**本项目为什么用 pnpm**：这是一个 monorepo（`apps/*` + `packages/*`），要让 `apps/api-ts` 直接引用 `packages/contract`（见 `04-契约包与TypeScript类型.md`），pnpm 的 workspace 链接最省事；顺带省磁盘。

### 5.3 基本语法（记住这几条就够）

```powershell
pnpm -v                      # 看版本（最常用的「体检」命令）
pnpm install                 # 按 package.json + 锁文件安装（本项目在仓库根执行）
pnpm add fastify             # 装运行时依赖，写进 dependencies
pnpm add -D typescript       # 装开发依赖，写进 devDependencies
pnpm store path              # 打印当前全局 store 的绝对路径（排障时很有用）
pnpm store prune             # 清理 store 里没人引用的包
```

### 5.4 store 与硬链接：为什么会「坏」

pnpm 的 store 是一个**内容寻址**的仓库：包被解压后按内容哈希存放，并且 store 目录里还带一份「索引」数据（记录包文件的位置）。项目 `node_modules` 里的文件其实是**硬链接**指向 store。

由此产生一个后果：

> 如果启动器（`pnpm` 这个命令本身）被配置成去读一个**已经不存在或已损坏**的 store 目录，它连索引都打不开 → 直接报 `unable to open database file`。

**本项目就踩了这个坑**（见第 8 节实测）：本机的 pnpm 启动器指向了失效的 `D:\.pnpm-store`，于是 `pnpm -v` 都跑不起来——这属于「装坏了」，而不是「没装」。

### 5.5 `packageManager` 字段与「钉版本」

根 `package.json` 里的：

```json
"packageManager": "pnpm@12.10.1"
```

这是 Node 的 **Corepack** 约定：声明「本仓库请用 pnpm 12.10.1」。`npm install -g pnpm` 做的是把 shim 装到本机，而「该用哪个版本」由这个字段说了算——**环境版本别靠记忆，靠文件**。

## 6. 【技术教学 · 首次】uv：Python 的包管理器 + 版本管理器

> 规则：本节是「uv」的**首次教学**，后续笔记遇到 `uv run` / `uv sync` 只写「见阶段 0·01」并直接使用。

### 6.1 传统 Python 工具链有多碎

在 uv 出现之前，做一件事要装一堆工具：

| 要干的事 | 传统工具 |
| --- | --- |
| 装某个 Python 版本 | `pyenv`（或官网安装包） |
| 创建隔离环境 | `python -m venv` / `virtualenv` |
| 激活环境 | `.\venv\Scripts\activate`（每个终端都要来一次） |
| 装依赖 | `pip install -r requirements.txt` |
| 锁依赖（可复现） | `pip-tools` / `pipenv` / `poetry` |
| 跑命令 | 先激活，再 `python xxx.py` |

### 6.2 uv 是什么

uv 是 **Rust 写的单一二进制工具**，把上面那张表**一个人全干了**：

- **管 Python 版本**：`uv python install 3.12` 会把解释器下到 uv 自己的目录（不污染系统 Python）。
- **管项目依赖**：读 `pyproject.toml` + 锁文件 `uv.lock`，装进项目自己的 `.venv`。
- **管运行**：`uv run ...` 会**自动**保证环境就绪，再执行命令——不用手动激活 venv。

### 6.3 基本语法

```powershell
uv --version                  # 看版本
uv python install 3.12        # 安装 CPython 3.12（uv 管理，不覆盖系统 Python）
uv python list                # 列出已知解释器（已安装 / 可下载）
uv python find 3.12           # 打印 3.12 解释器的绝对路径

uv init                       # 新建一个 Python 项目（生成 pyproject.toml）
uv add fastapi                # 加依赖（同时更新 pyproject.toml 与 uv.lock）
uv sync                       # 按清单把依赖装进 .venv
uv run python --version       # 在项目环境里执行命令
```

### 6.4 本例为什么这么用

根 `package.json` 里这一行就是 uv 的落地方式：

```json
"dev:api-py": "uv run --directory apps/api-py uvicorn app.main:app --reload --port 8000"
```

- `--directory apps/api-py`：先把**工作目录**切到 `apps/api-py`，再在该目录下执行后面的命令；uv 会去读它的 `pyproject.toml`、必要时建/更新 `.venv`。
- **注意别写成 `--project`**：`uv run --project <目录>` 只告诉 uv「用哪个项目的 `.venv` 与依赖」，**并不会切换当前工作目录**。因为 `app` 是这个项目里的**本地包**、并没有被安装进虚拟环境，所以从仓库根直接跑 `uv run --project apps/api-py uvicorn app.main:app` 会失败，报 `ModuleNotFoundError: No module named 'app'`。
- 正确做法必须用 `--directory` 切工作目录：`uv run --directory apps/api-py uvicorn app.main:app --reload --port 8000`（仓库根的 `dev:api-py` 脚本即采用此写法，已实测可从仓库根正常启动）。
- 于是**一条命令就能起后端**：不需要 `activate` 脚本，也不用自己先 `cd` 到某个目录（`--directory` 已经替你切好了）。

而 `apps/api-py/pyproject.toml` 里的 `requires-python = ">=3.12"` 与 `dependencies = [...]` 就是 uv 的输入：前者约束解释器，后者是依赖清单。**注意**：这是「清单」，不是「已安装的包」——安装这件事由 `uv sync` / `uv run` 完成。

## 7. 【技术教学 · 首次】Node 与 Python 的版本管理思路差异

两边都要「装某个语言的某个版本」，但**默认心智不同**：

| 维度 | Node.js | Python |
| --- | --- | --- |
| 版本管理器 | `nvm` / `fnm` / `volta`（切换全局 node） | `pyenv` / **uv python** |
| 版本声明文件 | `.nvmrc`、`package.json` 的 `engines` | `.python-version`、`pyproject.toml` 的 `requires-python` |
| 依赖装在哪 | 项目里的 `node_modules/`（每个项目一份） | 项目里的 `.venv/`（每个项目一份） |
| 版本切换粒度 | 通常**全局切换**（切完所有终端一起变） | 项目级 / 每次命令级（`.venv` 记录用哪个解释器） |
| 多版本共存 | 版本管理器统一管 | 传统上 pyenv + venv 各管一半；**uv 一个工具全包** |

**一句话记忆**：

- Node 世界：**Node 版本靠全局切，依赖靠项目装**——两件事由两拨工具做。
- Python 世界：**解释器版本 + 依赖**可以都由 uv 一个工具做，并且解释器是「uv 私有」的，不动系统那份。

**本项目的实际选择**（也是实测事实）：

- Node：直接用本机已装的 **v22.20.0**，不做版本切换。
- Python：本地原本**没有** Python；用 `uv python install 3.12` 让 uv 装了一个**自己管理的** CPython 3.12.15。

> 结论：本项目**不需要**你另外装系统级 Python，也不需要 nvm。

## 9. 第二步（实测）：诊断并修复 pnpm

### 9.1 先诊断：`pnpm -v` 直接报错

**命令**

**实测输出（故障现象）**

**结论**：与根 `package.json` 的 `"packageManager": "pnpm@12.10.1"` 一致，pnpm 修复完成。

## 10. 第三步（实测）：安装 uv

**命令**

```powershell
irm https://astral.sh/uv/install.ps1 | iex
```

| 项 | 值 |
| --- | --- |
| 在哪执行 | 任意目录，**PowerShell**（`irm`/`iex` 是 PowerShell 专有命令，cmd 里不能用） |
| 目的 | 下载官方安装脚本并立即执行，把 uv 装到用户目录 |
| 预期输出 | 脚本打印安装进度，末尾提示已安装成功 |

**这条命令在干什么**（语法拆解）：

- `irm` = `Invoke-RestMethod`：从 URL 取回文本（这里是安装脚本）。
- `|` = 管道：把脚本内容交给右边。
- `iex` = `Invoke-Expression`：**把拿到的脚本当代码执行**。

> 安全提醒：`irm ... | iex` 等于「下载什么就执行什么」。这里 URL 是官方 `astral.sh`。若你对该 URL 不放心，可以先 `irm https://astral.sh/uv/install.ps1 -OutFile uv.ps1`，**看过脚本**再 `.\uv.ps1`。

**实测结果**

- uv 版本：**0.13.1**
- 安装位置：`C:\Users\27382\.local\bin`

**注意（重要）**：安装脚本已把 `C:\Users\27382\.local\bin` 写入**用户环境变量 PATH**，且它现在是该 PATH 的**第一项**。因此**任何新打开的终端 / VS Code 都能直接调用 `uv`，不需要再手动把它加入 PATH**。只有**在 uv 安装之前就已经开着**的 shell 才会报 `'uv' is not recognized`——因为它继承的是安装前的**旧 PATH**。

**解决：重启终端 / 重启 IDE**（最简单），或在当前窗口临时重载：

```powershell
$env:Path = [Environment]::GetEnvironmentVariable('Path','User') + ';' + [Environment]::GetEnvironmentVariable('Path','Machine')
```

**验证**

```powershell
uv --version
```

**实测输出**

```
uv 0.13.1
```

**若此时仍提示 `uv : 无法将“uv”项识别为 cmdlet...`**：说明这是**安装前就已打开**的 shell（继承了旧 PATH）——重启终端 / IDE 即可；见第 13 节常见坑。

## 13. 常见坑

| 坑 | 现象 | 原因 | 解决 |
| --- | --- | --- | --- |
| pnpm store 损坏 | `pnpm -v` 报 `unable to open database file` | 启动器指向失效的 store 目录（本项目为 `D:\.pnpm-store`），索引打不开 | `npm install -g pnpm` 重装复位（实测恢复为 12.10.1）；排障可用 `pnpm store path` 看当前 store 位置 |
| uv 装完当前终端找不到 | `uv : 无法将“uv”项识别为 cmdlet、函数、脚本文件或可运行程序的名称` | PATH 条目本就存在（安装器已写入用户 PATH），只是**安装前就已打开的 shell** 继承了**旧 PATH** | 重启终端 / IDE；或临时重载 `$env:Path = [Environment]::GetEnvironmentVariable('Path','User') + ';' + [Environment]::GetEnvironmentVariable('Path','Machine')`；兜底可用绝对路径 `C:\Users\27382\.local\bin\uv.exe` |
| 把 uv 当 pip 用 | 手动 `pip install`，然后 `uv run` 找不到包 | `pip` 装的是**系统/其它**环境，uv 只认 `pyproject.toml` + `.venv` | 加依赖用 `uv add <pkg>`，安装用 `uv sync` |
| Python 版本不符 | `uv sync` 报需要 3.12 的解释器 | 本机没有 3.12；`requires-python` 会硬性拒绝 | `uv python install 3.12` |
| `irm \| iex` 在 cmd 里报错 | `'irm' 不是内部或外部命令` | `irm`/`iex` 是 PowerShell 专有 | 用 PowerShell，不要用 cmd.exe |
| 网络受限装不上 uv | `irm` 超时、连接被拒 | 访问 `astral.sh` 受阻 | 换官方提供的其它渠道（如 `winget install --id=astral-sh.uv -e`，或已有 Python 时 `pip install uv`） |
| 版本「差不多」就行 | 装了 Node 18 也能跑，但后面 Next 15 报错 | 环境是**文件钉死的契约**，不是意会 | 按第 3 节的表格核对版本；改了要求先改文件再改环境 |
