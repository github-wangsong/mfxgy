## 1. 本篇目标

做完这一篇，你能：

- 把阶段 0 的四件事**按依赖顺序逐层验收**，而不是「跑起来就算数」。
- 用**可直接复制的命令**自证：数据库可用 → 两套后端各自健康 → 前端能读到后端。

- 会通过环境变量让**同一份前端代码**指向 `api-ts` 或 `api-py`。

**验收标准（对齐总纲 §6 阶段 0）**：

> 前端能连通**两套后端**的 `/health`。

具体化到可执行层面，就是本文第 3 节**每一条命令的「预期输出」都命中**：

## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序（先中间件、后应用、最后前端）

```
L1/L2  db 容器 healthy + pgvector 就位
   ↓（数据库是后端的前提）
L3     api-ts  /health        L4  api-py  /health
   ↓（后端必须先健康）
L5     web :3000 渲染          L6  切换 NEXT_PUBLIC_API_BASE → api-py
```

**为什么要按这个顺序**：后一层的可用性依赖前一层。乱序排查会让你在同一时刻面对多个可疑点，无法定位。

---

### 3.1 L1 —— 中间件容器是否健康

**在哪执行**：仓库根（`mini-dify/`，`docker-compose.yml` 所在目录）
**目的**：确认数据库容器已启动且通过健康检查。

```bash
docker compose ps
```

**预期输出**

```
NAME           IMAGE                     SERVICE   STATUS                   PORTS
mini-dify-db   pgvector/pgvector:pg16    db        Up 2 hours (healthy)     0.0.0.0:5432->5432/tcp
```

**结果解读**：关键看 `STATUS` 里的 **(healthy)**。若显示 `(health: starting)`，再等 5~10 秒重跑；若一直 `unhealthy` 或根本没这行，见第 7 节常见坑。

---

### 3.2 L2 —— pgvector 扩展是否就位

**在哪执行**：仓库根
**目的**：验证「所有结构化数据 + 向量都交给 PostgreSQL」这一决策的底座就绪——镜像自带 pgvector，扩展版本要能查出来。

```bash
docker exec mini-dify-db psql -U postgres -d minidify -c "select extname, extversion from pg_extension where extname='vector'"
```

**预期输出**

```
 extname | extversion
---------+------------
 vector  | 0.8.7
(1 row)
```

**结果解读**：能查到 `vector | 0.8.7`，说明日后的 `vector` 列类型、余弦相似度检索有底座（阶段 7 才用得上）。`extname` 输出会是 `vector`（不是 `pgvector`）。

---

### 3.3 L3 —— api-ts（NestJS）健康检查

**在哪执行**：任意目录（既然要验，就用 `127.0.0.1` 而非 `localhost`，原因见第 7 节）

```bash
curl http://127.0.0.1:3001/health
```

**预期输出（实测）**

```json
{"status":"ok","service":"api-ts","version":"0.1.0","time":"2026-10-18T00:30:52.879Z"}
```

**结果解读**：`service: api-ts` 证明这是 NestJS 那套后端；`time` 是 `new Date().toISOString()` 的产物——UTC、毫秒 3 位、`Z` 后缀。

---

### 3.4 L4 —— api-py（FastAPI）健康检查

```bash
curl http://127.0.0.1:8000/health
```

**预期输出（实测）**

```json
{"status":"ok","service":"api-py","version":"0.1.0","time":"2026-10-18T01:48:53.857Z"}
```

**结果解读**：`service: api-py` 证明这是 FastAPI 那套后端；`time` 由 `app/timefmt.py` 的 `iso_z()` 归一（Pydantic `field_serializer`）——**阶段 2 已收口：两端均为 UTC 毫秒 `Z`**（TS 侧本就是 `new Date().toISOString()` 的毫秒 `Z`）。

> **注意 `version`**：两端现在都是 `0.1.0`，已对齐（api-ts 早期为 `0.0.0`，现已修复，见第 5.5 节）。

---

### 3.5 L5 —— 前端能否读到后端

**在哪执行**：浏览器
**目的**：验证「前端 → 后端」这一跳真的通（含 CORS）。

打开 `http://localhost:3000`，页面应显示：

```
mini-dify · 阶段 0 · 项目初始化
当前后端：http://localhost:3001
切换后端：改 NEXT_PUBLIC_API_BASE（http://localhost:3001 = api-ts，http://localhost:8000 = api-py）后重启 web。

{
  "status": "ok",
  "service": "api-ts",
  "version": "0.1.0",
  "time": "2026-10-18T00:30:52.879Z"
}
```

**结果解读**：页面渲染出 `service: api-ts` 的健康信息，且浏览器控制台**无报错**（若后端没放开 CORS，这里会红字报跨域）。至此「契约 → TS 后端 → 前端」这条链路打通。

### 3.6 L6 —— 切换后端，验证「零改动」

**在哪执行**：`apps/web/` 目录 + 重新跑 web 的终端

**完整文件路径：`apps/web/.env.example`**

```bash
# 前端指向的后端地址（契约一致，切换后端无需改代码）
# api-ts (NestJS)
NEXT_PUBLIC_API_BASE=http://localhost:3001
# api-py (FastAPI) —— 取消注释即可切换
# NEXT_PUBLIC_API_BASE=http://localhost:8000
```

**操作步骤**

1. 在 `apps/web/` 下把 `.env.example` 复制为 `.env.local`：

   ```bash
   cp apps/web/.env.example apps/web/.env.local
   ```

2. 把 `apps/web/.env.local` 中的 `NEXT_PUBLIC_API_BASE` 改成 `http://localhost:8000`：

   ```bash
   # apps/web/.env.local
   NEXT_PUBLIC_API_BASE=http://localhost:8000
   ```

3. **重启** web（`Ctrl+C` 后重跑 `pnpm dev:web`）—— 为什么必须重启，见第 6 节。

**预期输出**：`http://localhost:3000` 页面变为

```
当前后端：http://localhost:8000
...
{
  "status": "ok",
  "service": "api-py",
  "version": "0.1.0",
  "time": "2026-10-18T01:48:53.857Z"
}
```

**结果解读**：**一行代码都没改**，前端就从 NestJS 切到了 FastAPI。这正是总纲 §3.8「前端后端无关」的落地。

## 4. 【技术教学 · 首次】健康检查与「逐层验收」

> 规则：本节是「健康检查端点 + 逐层验收」的**首次教学**，后续跨后端验收只写「见阶段 0·08」并直接使用。

### 4.1 什么是健康检查（health check）

**是什么**：一个约定俗成的只读端点（惯例是 `GET /health`），返回服务「我活着、我叫什么、我什么时候答的」这类最小信息。它不查权重、不写库，**必须极快极稳**。

**为什么要单独做它**：在功能还没写之前先立一个 `GET /health`，是为了给整条链路一个**可验证的锚点**——「契约 → 两套实现 → 前端」这条链是否打通，用一句 `curl` 就能判断，而不必等第一个业务接口。

**本例的落地**：

- 契约侧：`packages/contract/openapi.yaml` 定义 `GET /health` → `HealthResponse`（见 `00-项目初始化/04-契约包与TypeScript类型.md`）。
- TS 侧：`HealthController`（`@Controller('health')` + `@Get()`）返回 `HealthResponse`。
- Python 侧：`api/health.py` 里 `@router.get("/health", response_model=HealthResponse, operation_id="getHealth")`。

### 4.2 「容器健康」与「应用健康」是两套语义

初学最容易混淆的点：`docker compose ps` 的 `healthy` **不等于**应用的 `/health` 返回 `ok`。它们由两套机制分别判定：

| | 谁在探测 | 探测什么 | 本项目里的证据 |
| --- | --- | --- | --- |
| 容器 healthcheck | Docker 守护进程，按 `healthcheck.test` 定期执行 | 容器内**进程/依赖**是否就绪 | `docker-compose.yml` 里 `test: ["CMD-SHELL", "pg_isready -U postgres -d minidify"]` |
| 应用 `/health` | 你自己（浏览器/curl/监控）主动请求 | 你的**业务级**存活 | `{}` 里含 `status/service/version/time` 的 JSON |

一个是「容器里的数据库接受连接了吗」，一个是「我给外界承诺的接口还在答吗」。**L1 与 L3/L4 分别验证它们，不能互相替代。**

### 4.3 什么是「逐层验收」

把一条端到端链路拆成**有序的若干层**，每层先自证健康，再验下一层：

```
L1 容器      L2 扩展      L3 api-ts     L4 api-py     L5 前端      L6 切换
healthy  →  pgvector  →  /health   →  /health   →  :3000 渲染 → env 生效
```

**收益**：当 L5 报错时，你能立刻推断「L3/L4 刚才是绿的，所以问题出在前端这一跳（CORS？env 没生效？）」——而不是在四个进程里瞎猜。这就是「先骨架、后血肉；每一步都独立可运行、独立验证」（总纲 §6）的验收侧体现。

## 5. 【技术教学 · 首次】什么叫「契约一致」

> 规则：本节是「契约一致」的**首次教学**。它不只属于阶段 0，是**贯穿全项目**的核心纪律。

总纲 §5.5 说「唯一契约、两套实现、行为一致」。但「一致」这个词太笼统，实际要拆成**两层**，只有第一层是机械可校验的。

### 5.1 第一层：结构一致（schema 层）

**指什么**：字段**集合**、字段**名**、字段**类型**、**必填**与否、是否允许**额外字段**。

**谁来保证**：OpenAPI / JSON Schema 校验器可以机械地逐字段比对。契约里对应的写法（`packages/contract/openapi.yaml`）：

```yaml
HealthResponse:
  type: object
  additionalProperties: false          # 多一个字段也算违约
  required: [status, service, version, time]
  properties:
    status: { type: string, enum: [ok] }
    service: { type: string }
    version: { type: string }
    time: { type: string, format: date-time }
```

**本阶段现状：已满足。** 证据：

- TS 侧：`HealthService.getHealth(): HealthResponse` 返回类型就是契约接口，编译期就能挡住字段错配。
- Python 侧：`HealthResponse(BaseModel)` 且 `model_config = ConfigDict(extra="forbid")`——`forbid` 与契约的 `additionalProperties: false` 是同义约定。

两条 `curl` 的输出字段完全对齐：`status / service / version / time`，一个不多、一个不少。

### 5.2 第二层：值规范一致（format / 语义层）

**指什么**：同一字段**取值本身**的规范——格式、精度、大小写、时间基准、枚举拼写。

**为什么结构一致还不够**：`time` 在契约里只约束到 `type: string, format: date-time`。而 **`format` 在 JSON Schema 里默认只是「注解（annotation）」**，是否强制校验取决于实现；而且 ISO-8601 / RFC 3339 本身允许**许多等价写法**。于是两边即使都「合法」，字符串也能不相等。

**实测对比**（同一天、同一契约、同一字段 `time`）：

| 后端 | 生成代码 | 实测值 | 特征 |
| --- | --- | --- | --- |
| api-ts | `new Date().toISOString()` | `2026-10-18T00:30:52.879Z` | UTC · 毫秒 **3** 位 · 后缀 `Z` |
| api-py | `iso_z()`（`app/timefmt.py`，经 `field_serializer`） | `2026-10-18T01:48:53.857Z` | UTC · 毫秒 **3** 位 · 后缀 `Z` |

**结论**：**阶段 2 已收口**——两端均为 UTC 毫秒 `Z`（阶段 0 当时两个字符串**都合法**却**逐字节不相等**：Python 默认 `isoformat()` 产出微秒 6 位、后缀 `+00:00`，而 TS 是毫秒 3 位、后缀 `Z`；这正是**值规范层**必须额外约定的典型）。所以：

> 「结构一致」可以通过 schema 机械校验；**「值规范一致」必须在契约里额外约定**，否则永远靠不住。

### 5.3 如果要「逐字节一致」，契约该怎么补

在 `openapi.yaml` 的 `time` 描述里把规范写死，例如：

> 时间统一为 UTC，**后缀用 `Z`**，**精度统一毫秒（3 位）**。

然后两侧按此规范生成：

```ts
// TS 侧：toISOString() 天然符合（UTC + Z + 毫秒）
time: new Date().toISOString()
```

```python
# Python 侧：默认 isoformat() 会产出 +00:00 且精度到微秒，需要显式归一
from datetime import datetime, timezone

def utc_iso_millis() -> str:
    return (
        datetime.now(timezone.utc)
        .isoformat(timespec="milliseconds")   # 精度收敛到毫秒
        .replace("+00:00", "Z")               # 后缀换成 Z
    )
```

> 这是**值规范化（normalization）**，属于契约纪律的一部分；真正的强制手段是第 5.4 节说的契约测试。

### 5.4 契约测试如何覆盖这两层

「一致」要成为**可验证的事实**而不是口头承诺（总纲 §5.5/§10），靠的是同一套 **contract test** 分别打两套后端：

- **结构一致** → 用 JSON Schema 严格校验（`additionalProperties: false` 生效，字段多/少都失败）。
- **值规范一致** → 对 `time`、`createdAt` 这类字段，或**在测试里先归一化再比**（都转成 UTC 毫秒），或**直接断言规范的字面格式**（正则 `^\d{4}-...\d{3}Z$`）。

两个手段用哪个，取决于契约里对「值规范」的约定强度——这也是本阶段留给后续的功课。

> **后续进展（阶段 2 已收口）**：全站时间统一为 **UTC 毫秒 `Z`**——契约里 4 个时间字段（`HealthResponse.time`、`UserResponse.createdAt`、`AppResponse.createdAt`/`updatedAt`）都写明了规范，Python 侧新增 `iso_z()` 归一，实测两端均为 24 字符、形如 `2026-10-18T12:10:18.900Z`。**值规范层的这两项（时间戳格式、错误文案）均已在阶段 2 收口**（见 `02-应用管理/07-验收.md` §4.2）。

### 5.5 曾经的一处遗留：`version` 的取值（已修复）

早期实测里两端不一致：

- api-ts → `"version":"0.0.0"`
- api-py → `"version":"0.1.0"`

**它是结构一致、值不同的典型**：字段、类型都对，只是值没对齐。而契约 `openapi.yaml` 的 `info.version` 是 `0.1.0`。

**修复动作**：把 `apps/api-ts/src/health/health.service.ts` 里的 `version: '0.0.0'` 改为 `version: '0.1.0'`。

**实测结果**：两端现已一致。

```json
// api-ts
{"status":"ok","service":"api-ts","version":"0.1.0","time":"2026-10-18T02:36:24.278Z"}
// api-py
{"status":"ok","service":"api-py","version":"0.1.0","time":"2026-10-18T02:36:24.290Z"}
```

**结论**：这一处**值规范层**的遗留已消除（结构一致原本就满足）。后续可把 `version` 的取值一并归入契约测试的断言项，防止再次漂移。

## 6. 【技术教学 · 首次】`NEXT_PUBLIC_API_BASE`：前端零改动切换后端

> 规则：本节是 Next.js 环境变量驱动切换的**首次教学**。

### 6.1 Next.js 怎么读环境变量

Next.js 会自动加载应用目录下的环境文件（按优先级，后者覆盖前者）：

```
.env.local       ← 本地私有，不提交（切换后端就改这里）
.env.development / .env.production
.env             ← 各环境共享
```

所以第 3.6 节的正确姿势是：把 `.env.example` 复制成 **`.env.local`**，改的是 `.env.local`。

### 6.2 关键字规则：只有 `NEXT_PUBLIC_` 前缀会送去浏览器

前端代码是**跑在浏览器的**，浏览器里**没有服务端进程的 `process.env`**。Next.js 的规矩是：

> 只有以 `NEXT_PUBLIC_` 开头的变量，才会被「内联」进浏览器端产物；**不带该前缀的变量只在服务端可用**。

这正是变量叫 `NEXT_PUBLIC_API_BASE`（而不是 `API_BASE`）的原因。

### 6.3 「内联」意味着必须重启

**内联（inlining）** = 构建/启动时，把代码里的 `process.env.NEXT_PUBLIC_API_BASE` **文本替换成一个字符串字面量**。看 `apps/web/app/page.tsx` 的用法：

```ts
// 通过环境变量切换后端：api-ts(:3001) 或 api-py(:8000)，前端代码零改动。
const API_BASE = process.env.NEXT_PUBLIC_API_BASE ?? 'http://localhost:3001'
```

它**不是运行期读取 env**，而是启动时被替换成 `"http://localhost:3001"` 这个字面量。所以：

- 只改 `.env.local` 而**不重启**，页面仍是旧值——必须 `Ctrl+C` 后重跑 `pnpm dev:web`。
- `?? 'http://localhost:3001'` 是「未设置时的兜底默认值」，保证空配置也能跑。

### 6.4 与总纲的呼应

总纲 §3.8：**「前端后端无关：前端通过环境变量（如 `NEXT_PUBLIC_API_BASE`）指向 `api-ts` 或 `api-py`，代码零改动。」** 第 3.6 节就是这句话的可执行验证。

## 8. 本篇复盘与知识点

**一句话总结阶段 0**：用最小的一个端点（`/health`），把「**契约 → TS 实现 → Python 实现 → 前端**」整条链路先打通——功能还没开始，地基已经可验证。

**本篇学到的工程/架构要点**

1. **逐层验收**：链路拆层、从下往上验，出错能立刻定位到层，比「一把梭跑起来看看」高效得多。
2. **两套健康语义**：容器 `healthy`（Docker 用 healthcheck 探进程/依赖）≠ 应用 `/health`（你定义的业务级存活），不能互相替代。
3. **「契约一致」是两层**：结构一致可被 schema 机械校验（本阶段已满足）；值规范一致（格式/精度/时间基准）必须额外约定，否则「都合法但字符串不同」。
4. **值不一致 ≠ 结构违约**：`version` 曾是 `0.0.0`（api-ts）vs `0.1.0`（api-py），属值规范遗留；现已把 api-ts 对齐到 `0.1.0`，两端一致。
5. **前端后端无关的开关**是 `NEXT_PUBLIC_API_BASE`：只有 `NEXT_PUBLIC_` 前缀会内联到浏览器，改它必须重启。

**遗留到下阶段（阶段 1）**

- （已修复）api-ts 的 `/health` 的 `version` 已从 `0.0.0` 对齐到 `0.1.0`，两端实测一致。
- 把「时间统一 UTC `Z` + 毫秒」等值规范写进契约，并由契约测试固化。**（阶段 2 已收口：契约已写明、Python `iso_z()` 已落地，全站统一 UTC 毫秒 `Z`；契约测试双跑尚待固化。）**

**基础技术要点**：健康检查端点设计 · 容器 healthcheck · Next.js 环境变量与构建期内联 · ISO-8601 时间戳的等价写法。
