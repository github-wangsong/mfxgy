## 3. 逐条验收命令 + 预期输出

### 3.0 验收顺序（先契约与库、后两套后端、再隔离与前端）

```
L1 契约编译        L2 迁移 / apps 表
      ↓                   ↓
L3 api-ts /apps    L4 api-py /apps
      ↓                   ↓
L5 归属隔离（404）→ L6 跨后端同表一致 → L7 浏览器
```

**为什么按这个顺序**：契约不编译，两端类型对不上；表不存在，创建必然 500；两端各自能 CRUD 之后，「隔离」与「同表一致」才有意义；最后才是浏览器。

### 3.3 L3 —— api-ts（NestJS）应用 CRUD

**在哪执行**：任意目录（用 `127.0.0.1`）

```bash
# 创建（期望 201），拿 id
APP_ID=$(curl -s -X POST http://127.0.0.1:3001/apps \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"demo-ts","mode":"chatflow"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['id'])")

# 列表（期望 200）
curl -i http://127.0.0.1:3001/apps -H "Authorization: Bearer $TS_TOKEN"

# 更新（期望 200）
curl -i -X PATCH http://127.0.0.1:3001/apps/$APP_ID \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"demo-ts-renamed"}'

# 删除（期望 204，无响应体）
curl -i -X DELETE http://127.0.0.1:3001/apps/$APP_ID -H "Authorization: Bearer $TS_TOKEN"

# 无 token（期望 401）
curl -i http://127.0.0.1:3001/apps

# 校验失败：name 为空（期望 400）
curl -i -X POST http://127.0.0.1:3001/apps \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":""}'
```

**预期输出（实测·形状）**

```
# 创建 201
HTTP/1.1 201 Created
{"id":"<uuid>","name":"demo-ts","description":null,"mode":"chatflow","ownerId":"<alice-uuid>","createdAt":"2026-10-18T...","updatedAt":"2026-10-18T..."}

# 列表 200
HTTP/1.1 200 OK
{"items":[{"id":"<uuid>","name":"demo-ts",...,"mode":"chatflow","ownerId":"<alice-uuid>",...}]}

# 更新 200
HTTP/1.1 200 OK
{"id":"<uuid>","name":"demo-ts-renamed",...}

# 删除 204（无体）
HTTP/1.1 204 No Content
（空）

# 无 token 401（错误信封）—— 消息为 "Missing bearer token"
HTTP/1.1 401 Unauthorized
{"statusCode":401,"message":"Missing bearer token","error":"Unauthorized"}

# 校验失败 400（错误信封）
HTTP/1.1 400 Bad Request
{"statusCode":400,"message":"<字符串>","error":"Bad Request"}
```

**结果解读**：`ownerId` 是**当前 token 的用户**（不是请求体传的——请求体根本不允许传 `ownerId`）。`description` 缺省时统一为 `null`。`DELETE` 是 **204 无体**。

### 3.5 L5 —— 归属隔离（404）

**在哪执行**：任意目录
**目的**：这是阶段 2 的**安全核心**——用户只能看见自己的应用。

```bash
# A（alice）创建一个应用，拿到 id
A_APP_ID=$(curl -s -X POST http://127.0.0.1:3001/apps \
  -H "Authorization: Bearer $TS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"alice-private","mode":"chatflow"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['id'])")

# B（bob）用**自己的** token 去访问 A 的应用 → 期望 404
curl -i http://127.0.0.1:3001/apps/$A_APP_ID -H "Authorization: Bearer $BOB_TOKEN"

# B 的列表里**不应**出现 A 的应用
curl -s http://127.0.0.1:3001/apps -H "Authorization: Bearer $BOB_TOKEN"
```

**预期输出（实测）**

```
# B 访问 A 的应用
HTTP/1.1 404 Not Found
{"statusCode":404,"message":"App not found","error":"Not Found"}

# B 的列表：items 里没有 alice-private
{"items":[]}      # 或只含 bob 自己的应用
```

**结果解读**：`owner_id` 与 token 的 `sub` 不一致时，后端**当作「不存在」**返回 404（而不是 403）。两套后端用同一套逻辑：`findOwned` 查不到**或**不属于当前用户 → 404。

### 3.6 L6 —— 跨后端同表一致性

**在哪执行**：任意目录
**目的**：证明两套后端读写的是**同一张 `apps` 表**——一个后端写入的数据，另一个后端立刻可见。

```bash
# 用 api-py（bob 的 token）创建一个应用
PY_APP_ID=$(curl -s -X POST http://127.0.0.1:8000/apps \
  -H "Authorization: Bearer $PY_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"created-by-python","mode":"workflow"}' \
  | python -c "import sys,json;print(json.load(sys.stdin)['id'])")

# 用 api-ts（同一 bob 的 token）列出 —— 应能看到刚在 py 建的这条
curl -s http://127.0.0.1:3001/apps -H "Authorization: Bearer $PY_TOKEN"
```

**预期输出（实测）**

```json
{"items":[{"id":"<PY_APP_ID>","name":"created-by-python","mode":"workflow","ownerId":"<bob-uuid>",...}]}
```

**结果解读**：api-py 创建的记录，api-ts 能列出（含同一条 `id`）⇒ **同一张表、同一认证域**。这正是「唯一契约、两套实现」在数据层的直接证据（bob 的 py token 也能在 ts 上通过鉴权，见阶段 1 · 06 的跨端互认）。

## 4. 【技术讨论 1】「契约一致」的两层在阶段 2 新增了什么

> 回顾：阶段 0 · 08 把「契约一致」拆成两层——① **结构一致**（字段集合/名/类型/必填/允不允许多余字段，schema 可机械校验）；② **值规范一致**（取值的格式/精度/大小写/时间基准，须额外约定）。阶段 1 · 07 讨论了「错误信封归一化」跨这两层。

阶段 2 的应用 CRUD 把「一致」又推进了一步，主要体现在**运行期形状**上：

### 4.1 已完全一致的部分

| 维度 | 阶段 2 表现 | 归属哪层 |
| --- | --- | --- |
| **状态码** | 创建 **201**、列表/更新 **200**、删除 **204**、无 token **401**、校验失败 **400**、越权/不存在 **404**——两端逐条相同 | 结构一致 |
| **响应体形状** | `AppResponse` / `AppListResponse` 字段集合、名、类型、`additionalProperties: false` 全对齐 | 结构一致 |
| **204 语义** | `DELETE` 两端都返回**无响应体**的 204（不是 200 带空对象） | 结构一致 |
| **错误体形状** | 两端 4xx 均为 `{statusCode,message,error}`（阶段 1 已收敛） | 结构一致 |

**结论**：阶段 2 的**状态码与响应体形状已经完全一致**——这正是「同一契约、两套实现」在 CRUD 上可被 schema 机械校验的部分。

### 4.2 「值规范」层的收口（✅ 已收口，并已实测）

阶段 0 · 08 留下的两处「值规范」差异（错误 `message` 文本、时间戳精度/后缀）在本阶段一并收口，且经反复实测确认。

**（a）错误 `message` 文本：用「错误文案目录」把两套校验方言归一**

新建唯一真源 `packages/contract/error-messages.md`，规定「约束名 → 文案模板」：

| 约束 | 文案模板 |
| --- | --- |
| `required` | `"{field} is required"` |
| `email` | `"{field} must be a valid email"` |
| `minLength(N)` | `"{field} must be at least {N} characters"` |
| `maxLength(N)` | `"{field} must be at most {N} characters"` |
| `enum(a, b)` | `"{field} must be one of: a, b"` |
| `unknown` | `"{field} should not exist"` |

多个错误按**字段声明顺序**用 `"; "` 连接。两侧各自落地：

- TS 侧新增 `apps/api-ts/src/common/validation-exception-factory.ts`，在 `main.ts` 里注入 `exceptionFactory`；
- Py 侧在 `app/errors.py` 的 `RequestValidationError` 处理器里做同一映射。

**实测：12/12 组用例两端响应体逐字节完全一致**，节选：

| 触发 | 两端一致的响应体 |
| --- | --- |
| 注册缺 email/password | `{"statusCode":400,"message":"email is required; password is required","error":"Bad Request"}` |
| `name` 超 64 字符 | `{"statusCode":400,"message":"name must be at most 64 characters","error":"Bad Request"}` |
| `mode` 非法 | `{"statusCode":400,"message":"mode must be one of: chatflow, workflow","error":"Bad Request"}` |
| 重复邮箱 | `{"statusCode":409,"message":"Email already registered","error":"Conflict"}` |
| 错误凭据 | `{"statusCode":401,"message":"Invalid email or password","error":"Unauthorized"}` |
| 缺 token | `{"statusCode":401,"message":"Missing bearer token","error":"Unauthorized"}` |
| 访问他人应用 | `{"statusCode":404,"message":"App not found","error":"Not Found"}` |

**收口过程中暴露的真实分歧：邮箱的「接受集合」不同**

首轮归一后，`a@b.c` 这类邮箱两端出现分歧——`class-validator`（底层 validator.js 默认 `require_tld: true`）**拒绝**单字符 TLD，而 Pydantic `EmailStr` **接受**。解决方式是新增自定义装饰器 `apps/api-ts/src/common/is-email.decorator.ts`（`@IsEmailFormat()`，`require_tld: false` 并额外要求域名含点，约束名仍沿用 `isEmail`），把两端的「邮箱接受集合」对齐。

> 这正是「契约一致必须靠**运行期验证**才能发现」的实例：契约里对邮箱只有 `format: email` 一句注解，两种实现对「什么算合法邮箱」的解释其实不同——只有**双跑比对**才把这个分歧暴露出来。

**（b）时间戳精度与后缀：统一为 UTC + 毫秒 + `Z`**

- 契约里 4 个时间字段（`HealthResponse.time`、`UserResponse.createdAt`、`AppResponse.createdAt`、`AppResponse.updatedAt`）的 `description` 已明确「UTC、ISO-8601、毫秒精度、以 `Z` 结尾」；
- Python 新增 `apps/api-py/app/timefmt.py` 的 `iso_z()`，并用 Pydantic `field_serializer` 应用到所有出参时间字段；TS 侧本就全走 `toISOString()`。

**实测**：两端都是 **24 字符**、形如 `2026-10-18T12:10:18.900Z`（此前 Python 为 `...+00:00` 带微秒）。

### 4.3 一句话结论

> 阶段 2 把「结构一致」在**运行期**又收紧了（状态码与响应体形状全对齐，含 204 无体）；
> 同时把**错误 `message` 文本**与**时间戳精度/后缀**这两处「值规范一致」层**一并收口**——文案写进 `packages/contract/error-messages.md`、时间统一 UTC 毫秒 `Z`，实测**逐字节一致**（详见 §4.2）。

## 5. 【技术讨论 2】归属隔离：为什么是 404 而不是 403

**问题**：B 去访问 A 的应用，后端已鉴权通过（B 确实是合法用户），只是**这个资源不归 B**。此时该回 **403 Forbidden**（「你没权限」）还是 **404 Not Found**（「没有这个资源」）？

本项目的选择：**一律回 404**。两套后端的注释与实现都写明了这一点：

- api-ts：`AppsService.findOwned` 里 `app === null || app.ownerId !== ownerId` → `throw new NotFoundException('App not found')`。
- api-py：`_find_owned` 里同理 → `HTTPException(404, detail="App not found")`。
- 契约：`NotFound` 的描述就是「**资源不存在或不属于当前用户**」。

**为什么不是 403**

| | 403 Forbidden | 404 Not Found（本项目） |
| --- | --- | --- |
| 对「他人资源」的语义 | 「它存在，但你没权限」 | 「没有这个资源」（对 B 而言确实不可见） |
| **信息泄露** | **泄露了资源存在性**：B 可以拿一串 id 去试，用 403/404 的差别**枚举推断**「哪些 id 是真实存在的」，为后续攻击（撞库、探测）提供情报 | 不存在与不属于自己**不可区分**，无法据此推断存在性 |
| 一致性 | 需要额外判断「是权限问题还是不存在」，两套后端容易实现不一 | 「不属于我 = 看不到」，实现简单且两端天然一致 |

**核心取舍**：**「不该看见的东西，连『它存在』都不要告诉他。」** 用 404 把「不存在」与「不属于你」合并成同一种对外表现，抹掉**资源存在性**这一侧信道。这是越权类接口的通行做法，也是本阶段「安全核心」。

> 代价：客户端无法从状态码区分「真不存在」与「不是我的」——但在「按当前用户过滤」的语义下，这两者对用户**本就等价**（反正是看不到）。

## 6. 常见坑汇总（跨阶段 2）

| # | 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- | --- |
| 1 | **Prisma `updatedAt` 无 DB 默认值 → Python 插入失败**（已收口） | 用 api-py 创建应用曾报 **500**（`null value in column "updated_at" violates not-null constraint`） | 旧迁移里 `updated_at TIMESTAMP(3) NOT NULL` **没有** `DEFAULT`（Prisma 的 `@updatedAt` 由**客户端**赋值）。**已收口**：新迁移 `20261018120000_add_updated_at_default_and_trigger` 给该列加 `SET DEFAULT now()` 并建 `BEFORE UPDATE` 触发器刷新；`schema.prisma` 的 `updatedAt` 加 `@default(now())`；SQLAlchemy 侧保留 `default=func.now(), onupdate=func.now()` 作为兜底（**DB 触发器为权威 + ORM 兜底的双保险**）。实测：手工 `INSERT`/`UPDATE` 与两端 `PATCH` 均正常 |
| 2 | **JWT 配置重复注册的漂移风险（已重构）** | 两端 `expiresIn` 或密钥不一致，导致跨端 401 / 有效期不同 | 有效期一度**硬编码在两处**（TS `auth.module.ts` 的 `signOptions.expiresIn: '1h'`、Py `config.py` 的 `access_token_expires_in = 3600`），改一处漏一处就会漂移。**已重构**：两端都读 `JWT_EXPIRES_IN`（**秒**），实测 `expiresIn` 均 `3600`；密钥同读 `JWT_SECRET`（见阶段 1 · 06 / 07） |
| 3 | **无 token 时前端没跳 `/login`** | `/apps` 直接报「操作失败：HTTP 401」，而不是引导登录 | 列表页必须先查 `localStorage.getItem('accessToken')`，为 `null` 就 `router.replace('/login')`；`res.status === 401` 时同样回登录页（见 `06` 第 5.5 / 7 节） |
| 4 | **对 204 读了响应体** | 删除「成功」却抛解析异常 | 204 无响应体；成功后不要 `res.json()`，直接重新拉列表 |
| 5 | **`Authorization` 格式错** | 全部 401 | 必须 `Bearer <token>`（含空格） |
| 6 | **`localhost` 解析竞态** | `curl` 偶发连不上 | 统一用 `127.0.0.1`（见 `00-项目初始化/08` §7） |
| 7 | **误把 404 当 bug** | 访问自己的应用却 404 | 确认用的是**同一个用户**的 token；别的情况下 404 是**设计**（归属隔离），不是故障 |
| 8 | **跨端看到别人的数据** | B 的列表出现 A 的应用 | 归属过滤失效（`where ownerId` / `App.owner_id == current_user.id` 缺失）；核对两端的 list 实现与 `apps_owner_id_idx` |
| 9 | **重置库后表不在** | 创建报 500 | 迁移未应用；`pnpm --filter @mini-dify/api-ts exec prisma migrate dev` |
| 10 | **值不同（`createdAt` 精度）**（已收口） | 旧版本两端字符串不等（`...879Z` vs `...879000+00:00`） | 属**值规范层**，现已收口（见 §4.2）：统一为 UTC 毫秒 `Z`，两端均为 24 字符、形如 `2026-10-18T12:10:18.900Z` |

## 7. 本篇复盘与知识点

**一句话总结阶段 2**：在两套后端各实现一套 `/apps` 的 CRUD，用**归属隔离**保证「用户只看得见自己的应用」，并让两套实现**共用同一张表、同一认证域**——状态码与响应体形状全对齐。

**本篇学到的工程/架构要点**

1. **分层验收收口**：契约编译 → 迁移/表 → 两端 CRUD → 归属隔离 → 跨后端同表一致 → 浏览器，逐层自证，出错能立刻定位到层。
2. **归属隔离是本阶段安全核心**：查不到**或**不属于当前用户 → **404**（不是 403），抹掉资源存在性侧信道。
3. **契约一致在阶段 2 的运行期收敛**：状态码与响应体形状（含 **204 无体**）两端完全一致。
4. **值规范层已收口**：错误 `message` 文本写进 `packages/contract/error-messages.md`（`require_tld` 分歧也已对齐），时间统一 UTC 毫秒 `Z`——12/12 组用例两端响应体**逐字节一致**。
5. **DDL 单一所有权有硬约束（已补齐）**：`updated_at` 曾无 DB 默认值 ⇒ Python 映射侧必须自备 `default`/`onupdate`，否则 INSERT 失败；现迁移已补 `DEFAULT now()` + `BEFORE UPDATE` 触发器，ORM 的 `onupdate` 保留为兜底。

**遗留到下阶段**

- 契约测试双跑自动化：把 §4.2 已手工验证的「文案 / 时间戳逐字节一致」固化成 CI 断言。
- 前端登出/自动刷新 token 等交互，留待后续阶段。

**基础技术要点**：越权防护与 404/403 取舍 · 按用户过滤的同表 CRUD · 204 语义 · schema 单一所有权带来的映射侧约束。
