## 1. 本篇目标

| --- | --- | --- | --- |

## 3. 先看清要做什么

阶段 1 的契约有 `/health` 与 `/auth/*`。阶段 2 要引入**第一个真正的业务资源**——「应用（App）」。仍然按**契约优先**的流程，第一步先落契约：

```
packages/contract/
   ├── openapi.yaml      ← 追加 /apps、/apps/{id} + 新 schema + NotFound   （本篇 §5）
   └── src/index.ts      ← 同步追加对应的 TS 类型                        （本篇 §6）
        ↓ pnpm run build:contract
      dist/index.js + dist/index.d.ts   ← NestJS / FastAPI / 前端统一消费  （本篇 §10）
```

五个接口的语义：

```
GET    /apps          你带上令牌     → 返回「你名下的」应用列表
POST   /apps          你给我 name 等 → 在你的名下新建一个应用
GET    /apps/{id}     你带上令牌 + id → 返回该应用的详情（仅限本人）
PATCH  /apps/{id}     你给我要改的字段 → 局部更新该应用（仅限本人）
DELETE /apps/{id}     你带上令牌 + id → 删除该应用（仅限本人）
```

**关键点**：路径里出现的是**资源**（`apps` / `apps/{id}`），动作由 **HTTP 方法**表达（GET 读、POST 建、PATCH 改、DELETE 删）——这就是 REST 资源化设计的核心（见 §7）。

**本阶段新增的部分（与阶段 1 相比）**

| 新增 | 类型 | 说明 |
| --- | --- | --- |
| `paths./apps`（`get` + `post`）、`paths./apps/{id}`（`get` + `patch` + `delete`） | path item | 两组资源路径、五个 operation（见 §1 表） |
| `components.responses.NotFound` | response 对象 | 可复用的 404 响应（错误体仍是同一个 `ErrorResponse`，见 `01-账号与认证/01-契约扩展.md` 的错误信封） |
| `AppResponse` / `CreateAppRequest` / `UpdateAppRequest` / `AppListResponse` | schema | 应用资源的新数据结构 |
| `info.version` → `0.2.0` | — | 契约版本与 `CONTRACT_VERSION` 同步递增 |

**读法要点**（只补本阶段特有的几点）：

- **同一路径下的多个方法合并写**：`/apps` 下的 `get` 与 `post` 是**同一个 path item 的两个字段**，不是两条路径；`/apps/{id}` 下的 `get` / `patch` / `delete` 同理。
- **`description` 允许 null**：`type: ["string", "null"]` 是 3.1 的写法，表示「字符串或 null」（见 §6 的 `string | null`）。创建/更新请求里 `description` **不在 `required`**，但**给了就必须是 string**。
- **`UpdateAppRequest` 无 `required`**：所有字段都可选——这正是 `PATCH` 的语义（局部更新，见 §7.3）。
- **`DELETE` 的 `204` 没有 `content`**：204 表示「成功但无响应体」，所以它下面**不写 `content`**（见 §7.2）。

## 6. 完整代码：TS 类型（src/index.ts）

契约的 YAML 是**给人类和工具看**的；TS 侧还需要一份**与它逐字段对应**的类型文件，才能让 NestJS 编译期拿到类型。

**完整文件路径：`packages/contract/src/index.ts`**

```ts
/**
 * 契约 TS 类型（由 openapi.yaml 派生）。
 *
 * 唯一真源是同仓库根目录下的 `packages/contract/openapi.yaml`；此文件保持与其逐字段一致。
 * 两套后端（NestJS / FastAPI）都必须返回符合本结构的数据。
 */

/** 契约版本；修改契约时递增，并与 openapi.yaml 的 info.version 保持同步。 */
export const CONTRACT_VERSION = '0.2.0'

/** GET /health 的响应体。 */
export interface HealthResponse {
  /** 固定为 'ok' */
  status: 'ok'
  /** 服务标识：api-ts | api-py */
  service: string
  /** 服务版本 */
  version: string
  /** 时间戳：UTC、ISO-8601、毫秒精度、以 `Z` 结尾（24 字符） */
  time: string
}

/** POST /auth/register 请求体。 */
export interface RegisterRequest {
  email: string
  /** 至少 8 位 */
  password: string
}

/** POST /auth/login 请求体。 */
export interface LoginRequest {
  email: string
  password: string
}

/** 用户对外视图（**绝不包含密码哈希**）。 */
export interface UserResponse {
  id: string
  email: string
  role: 'admin' | 'member'
  /** 时间戳：UTC、ISO-8601、毫秒精度、以 `Z` 结尾（24 字符） */
  createdAt: string
}

/** POST /auth/login 的响应体。 */
export interface TokenResponse {
  accessToken: string
  tokenType: 'Bearer'
  /** 有效期（秒） */
  expiresIn: number
  user: UserResponse
}

/** 应用对外视图（只暴露契约字段，不含内部实现细节）。 */
export interface AppResponse {
  id: string
  name: string
  /** 空描述统一序列化为 `null` */
  description: string | null
  mode: 'chatflow' | 'workflow'
  /** 归属用户 id */
  ownerId: string
  /** 时间戳：UTC、ISO-8601、毫秒精度、以 `Z` 结尾（24 字符） */
  createdAt: string
  /** 时间戳：UTC、ISO-8601、毫秒精度、以 `Z` 结尾（24 字符） */
  updatedAt: string
}

/** POST /apps 请求体。 */
export interface CreateAppRequest {
  /** 1-64 位 */
  name: string
  /** 最多 256 位 */
  description?: string
  mode?: 'chatflow' | 'workflow'
}

/** PATCH /apps/{id} 请求体（字段均可选）。 */
export interface UpdateAppRequest {
  /** 1-64 位 */
  name?: string
  /** 最多 256 位 */
  description?: string
  mode?: 'chatflow' | 'workflow'
}

/** GET /apps 的响应体。 */
export interface AppListResponse {
  items: AppResponse[]
}

/**
 * 统一错误响应体。
 *
 * 两套后端必须产出**同一形状**的错误体：NestJS 默认就是该形状，
 * FastAPI 需要自定义异常处理器把默认的 `{detail}` 归一化过来。
 */
export interface ErrorResponse {
  statusCode: number
  message: string
  error: string
}
```

**本阶段新增/变化的类型**

| 类型 | 关键点 |
| --- | --- |
| `AppResponse` | `description: string \| null`（对应 YAML 的 `type: ["string", "null"]`）；`mode` 用联合字面量 `'chatflow' \| 'workflow'`（对应 `enum`）；含 `ownerId` / `createdAt` / `updatedAt` |
| `CreateAppRequest` | `name` 必填；`description?` / `mode?` 可选（对应 `required: [name]`） |
| `UpdateAppRequest` | **三个字段全部可选**——`PATCH` 局部更新的类型表达 |
| `AppListResponse` | `items: AppResponse[]`——列表被**包装**成对象（见 §7.1） |
| `CONTRACT_VERSION` | 由 `'0.1.0'` 改为 `'0.2.0'` |

`mode` / `description` 的字面量 / 联合写法，原理见 `00-项目初始化/04-契约包与TypeScript类型.md` §9.4（TS 类型系统）。

> **手工同步**：`openapi.yaml` 与 `src/index.ts` 是**两份手工维护、必须一致**的文件。改了 YAML 里的 schema，就要同步改这里的 interface，并递增 `CONTRACT_VERSION`。

## 7. 【技术教学 · 首次】REST 资源化设计

### 7.1 列表返回 `{items: [...]}` 还是裸数组？

同一个「应用列表」接口，有两种常见写法：

```jsonc
// 写法 A：裸数组
[ { "id": "…", "name": "…" }, { "id": "…", "name": "…" } ]

// 写法 B：包装成对象（本项目采用）
{ "items": [ { "id": "…", "name": "…" }, { "id": "…", "name": "…" } ] }
```

| 维度 | 裸数组 | `{items: [...]}` 包装 |
| --- | --- | --- |
| 顶层类型 | array | object |
| **加元数据**（分页游标、总数、`hasMore`） | 无处可放，只能改响应形状（**破坏性变更**） | 直接加字段 `{items, total, nextCursor}`，**向后兼容** |
| 扩展性 | 差 | 好 |
| 简洁度 | 略高 | 略低（多一层 `items`） |

**本项目选包装**。理由：应用列表迟早要加分页（教学项目后续阶段会迭代），裸数组一旦要加 `total` / `nextCursor` 就只能改结构，前端与两套后端都得跟着改；而 `{items:[...]}` 是从一开始就把「可扩展」的位置留好——加字段是**非破坏性**的。

> 口诀：**「列表」也是一种资源视图，用对象包起来，给未来的元数据留位置。** 对应到 TS 就是 `AppListResponse { items: AppResponse[] }`，不是 `AppResponse[]`。

### 7.2 `DELETE` 用 `204 No Content`

HTTP 里「删除成功」有两种常见表达：

| 状态码 | 含义 | 是否带响应体 |
| --- | --- | --- |
| `200 OK` | 成功，且**有**响应体（可回删掉的资源快照） | 有 |
| `204 No Content` | 成功，且**没有**响应体 | 无 |

**本项目用 `204`**：

```yaml
    delete:
      responses:
        "204":
          description: 删除成功      # ← 注意：204 下面没有 content
```

- 删完资源就没了，回传它的快照**没有意义**（谁也不会去用）。
- 204 的语义就是「**成功但没有内容**」，客户端拿到 204 就知道**不应去解 json**。这也让契约更诚实：`DELETE` 的响应体为空，前端就不必写「解析删除响应」的死代码。
- 契约上表现为：`"204"` 节点**只有 `description`，没有 `content`**——这是刻意为之。

> 后端实现要跟着对齐：NestJS 里 `@HttpCode(204)` + handler 返回 `void`；FastAPI 里 `status_code=204` 且**不能**返回 body（否则框架会报错）。

### 7.3 `PATCH`（局部更新）vs `PUT`（全量替换）

更新接口有两条路：

| 方法 | 语义 | 请求体 | 未出现的字段 |
| --- | --- | --- | --- |
| `PUT /apps/{id}` | **全量替换**：用请求体**整体覆盖**资源 | 所有字段都该给 | 视为「置空 / 默认值」 |
| `PATCH /apps/{id}` | **局部更新**：只改请求体里出现的字段 | 字段均可选 | **保持原值不动** |

**本项目用 `PATCH`**，所以 `UpdateAppRequest` 的**所有字段都是可选的，且没有 `required`**：

```yaml
    UpdateAppRequest:
      type: object
      additionalProperties: false
      # ← 没有 required：任何字段都可以不给
      properties:
        name: { ... }
        description: { ... }
        mode: { ... }
```

对照 `CreateAppRequest`（有 `required: [name]`）——**创建必须有名字，更新可以只改模式**。若用 `PUT`，语义上「我只想改 mode」也得把 name / description 一起传回来，客户端体验差且容易误清空字段。

> 口诀：**`PUT` = 覆盖整份，`PATCH` = 打补丁改几处。** 契约里 `PATCH` 的请求 schema 必然「无 `required`、字段全可选」。

### 7.4 资源化的整体形态

```
        资源（名词）              动作（方法）              本项目
  ┌────────────────────┐   ┌──────────────────┐
   /apps                    GET    读列表        listApps
   /apps                    POST   建一个        createApp
   /apps/{id}               GET    读一个        getApp
   /apps/{id}               PATCH  改几处        updateApp
   /apps/{id}               DELETE 删一个        deleteApp
```

- **路径只放名词**：`/apps`、`/apps/{id}`——不出现 `/getApps`、`/deleteAppById` 这类「动词塞进 URL」的写法。
- **动作靠方法表达**：读用 GET、建用 POST、改用 PATCH、删用 DELETE。
- 好处：路径稳定（资源集合 + 资源个体两条就够）、语义由 HTTP 标准承担、可被通用工具（缓存、文档、网关）理解。

## 8. 【技术教学 · 首次】路径参数 `{id}` 在 OpenAPI 里的写法

### 8.1 什么是路径参数

**路径参数（path parameter）** 是**嵌在 URL 路径里**、用来定位某个具体资源的一小段：

```
/apps/{id}          ← {id} 是占位符
/apps/8f3a-...-2b1c ← 实际请求时被替换成真实 id
```

它是「`{id}` 位置上的那段字符串」，属于 URL 的一部分，**不是** query（`?id=`）也不是 header。

### 8.2 OpenAPI 里怎么声明

路径里写了 `{id}`，**必须在 `parameters` 里声明它**，否则规范校验会报「路径模板变量没有对应参数」。写法：

```yaml
  /apps/{id}:
    get:
      operationId: getApp
      security:
        - bearerAuth: []
      parameters:                      # ← 参数列表
        - name: id                     #    名字必须与路径里的 {id} 一致
          in: path                     #    in: path = 路径参数
          required: true               #    路径参数必须 required: true
          schema:
            type: string               #    类型
      responses: { ... }
```

三个**硬性规则**（能解释绝大多数字段校验报错）：

| 规则 | 为什么 |
| --- | --- |
| `in: path` 的参数，`required` **必须为 `true`** | 路径参数是 URL 的一部分，要么整条路径匹配上、要么路径就根本不是这条——不存在「可选缺失」 |
| `name` 必须与路径模板里的 `{name}` **逐字一致** | `{id}` 就得叫 `id`；写成 `appId` 会报「模板变量未被定义」 |
| 路径参数写在使用它的 **operation 上**（`get` / `patch` / `delete`） | 它与「哪个方法」绑定；本项目三个方法都用到 `id`，所以**三处各声明一次** |

### 8.3 与 query 参数的区别

```yaml
parameters:
  - name: id
    in: path      # 来自 URL 路径段：/apps/{id}
  - name: mode
    in: query     # 来自 ？mode=chatflow
```

- `in: path`：定位「哪一个资源」，通常 `required: true`。
- `in: query`：过滤 / 排序等附加条件，可 `required: false`。

> 口诀：**`{id}` 在路径里 → `in: path` 且 `required: true`，名字必须与花括号里的一致，且写在用到它的每个 operation 上。**

## 9. 【技术教学 · 首次】为什么「找不到」返回 404 而不是 403

### 9.1 场景

`GET /apps/{id}`、`PATCH /apps/{id}`、`DELETE /apps/{id}` 都需要判断两件事：

1. 这个 `id` 对应的应用**存在吗**？
2. 它**属于当前登录用户吗**？

若「存在但不属于你」，直觉可能想返回 `403 Forbidden`（「你没权限」）。**但本项目对所有「不存在 / 不属于你」都返回 `404 Not Found`**：

```yaml
        "404":
          $ref: "#/components/responses/NotFound"   # description: 资源不存在或不属于当前用户
```

### 9.2 为什么：403 会泄露「资源是否存在」

对比两种返回：

| 情况 | 返回 403 的信息量 | 返回 404 的信息量 |
| --- | --- | --- |
| id 对应的应用**存在**、但不是你的 | 403 → 攻击者得知「**这个 id 存在**，只是不归我」 | 404 → 「找不到」（存在与否不明） |
| id **根本不存在** | 404 | 404 |

如果「存在但非本人」返回 403、「不存在」返回 404，那么攻击者可以**遍历 id**、用状态码区分这两种情况，从而**枚举出系统里有哪些应用**（即使内容看不到，也能探测「某个 id 是否存在」）。这本身就是一种信息泄露。

**返回 404 则两种情况的响应**完全一致**，攻击者无法区分，也就**无从枚举资源**。这是「**不泄露资源是否存在**」的通用安全原则（你在很多大厂 API 里都能看到：找不到 / 无权限都统一 404）。

> 一句话：**「你没权限看」和「它不存在」，对外表现成同一个 404**——这样「有没有这个资源」这件事就不会漏出去。

### 9.3 实现层的含义（后续篇会用）

- NestJS 侧：Service 查询时**用 `ownerId` 一起过滤**（`where: { id, ownerId }`），查到就返回、查不到就抛 `NotFoundException` → 落到 404。
- FastAPI 侧：同样按 `id + owner_id` 查，`None` 就 `raise HTTPException(404, ...)`。
- 两侧都**不**先「查存在 / 再查归属」——那样容易写成「先 404 后 403」从而踩到上面的泄露坑。

> 契约只表达了「404 有两种含义」（`description` 里写了「资源不存在**或**不属于当前用户」）；具体怎么查由实现篇负责。

## 12. 常见坑

| 坑 | 现象 | 原因 / 解决 |
| --- | --- | --- |
| 只改 YAML 忘了改 TS | NestJS 拿不到新类型 / 类型与契约不符 | `openapi.yaml` 与 `src/index.ts` 是**手工同步**的两份文件，必须一起改 |
| 忘了递增版本 | 两侧「契约版本」对不上 | 契约变更时同步递增 `openapi.yaml#/info/version` 与 `src/index.ts#CONTRACT_VERSION`（本次均为 `0.2.0`） |
| 路径参数没声明 | 规范校验报「路径模板变量未定义」 | 路径里写了 `{id}`，就必须在**用到它的每个 operation** 的 `parameters` 里声明 `in: path` 且 `required: true`，`name` 与 `{id}` 逐字一致 |
| 给 `204` 写了 `content` | 语义自相矛盾（说「无内容」却定义了响应体） | `204` 下**只写 `description`**，不写 `content`；后端实现要返回空 body |
| `PATCH` 却带 `required` | 前端被迫每次传全量字段 | `PATCH` 是局部更新，`UpdateAppRequest` 必须**无 `required`**、字段全可选；要全量覆盖才用 `PUT` |
| 列表返回裸数组 | 将来加分页就得改响应结构（破坏性变更） | 用 `{items:[...]}` 包装（`AppListResponse`），给分页等元数据留位置 |
| 「不存在 / 非本人」返回 403 | 攻击者能靠状态码区分并枚举资源 | 两种情况**统一 404**（`NotFound`），不泄露资源是否存在 |
| 两次查询（先查存在再查归属） | 容易写成「先 404 后 403」，踩泄露坑 | 实现时用 `where: { id, ownerId }` 一次查，查不到即 404 |
| 忘了重编译契约 | 后端编译用的还是旧 `dist` | 契约改完必须 `pnpm run build:contract`（`dev:api-ts` / `build:api-ts` 已自动包含此步） |
