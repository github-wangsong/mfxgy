## 3. FastAPI 默认的三种错误

### 3.1 抛 `HTTPException`

```python
from fastapi import HTTPException

raise HTTPException(status_code=404, detail="App not found")
```

响应：

```json
{"detail": "App not found"}
```

### 3.2 校验失败

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "name"],
      "msg": "Field required",
      "input": {}
    }
  ]
}
```

状态码 **`422`**。

### 3.3 未捕获异常

```python
@app.get("/boom")
def boom():
    return 1 / 0
```

| 环境 | 响应 |
| --- | --- |
| 生产（`debug=False`） | `500` + `{"detail": "Internal Server Error"}`（**无堆栈**） |
| 开发（`debug=True`） | `500` + HTML/文本堆栈页 |

### 3.4 三种形态的问题

| 问题 | 后果 |
| --- | --- |
| 形状不统一（`detail` vs 数组 vs 字符串） | 前端要写三套解析 |
| 默认 422 | 与 NestJS 的 400 不一致 |
| `detail` 可任意类型 | 契约无法约束 |
| 无统一字段 | 无法做统一 toast / 埋点 |

> **错误响应也是 API 契约的一部分**。它不稳定，前端就无法写出健壮的错误处理。

## 4. `HTTPException` 细节

### 4.1 三个参数

```python
raise HTTPException(
    status_code=401,
    detail="Missing bearer token",
    headers={"WWW-Authenticate": "Bearer"},
)
```

| 参数 | 作用 |
| --- | --- |
| `status_code` | 状态码 |
| `detail` | 响应体里的说明（**任意可 JSON 序列化的值**） |
| `headers` | 附加响应头（`WWW-Authenticate`、`Allow`、`Retry-After`） |

### 4.2 `detail` 可以是结构化数据

```python
raise HTTPException(409, detail={"reason": "duplicate", "field": "name"})
```

响应：`{"detail": {"reason": "duplicate", "field": "name"}}`

> 但一旦用了结构化 `detail`，就必须和前端约定形状——**契约项目应统一用信封，而不是让每个接口自定义 `detail`**。

### 4.3 `FastAPI.HTTPException` vs `Starlette.HTTPException`

```python
from fastapi import HTTPException                              # 子类
from starlette.exceptions import HTTPException as StarletteHTTPException   # 父类
```

| 事实 | 说明 |
| --- | --- |
| FastAPI 的 `HTTPException` 继承 Starlette 的 | 多了 `headers` 等便利 |
| 注册父类的处理器 | **能捕获子类**（按 MRO 往上找） |
| 项目注册的是父类 | 所以 `HTTPException` 与 Starlette 内部的 404/405 都被统一处理 |

> 这是项目能把「路由不存在」也归一化的原因——那个 404 是 Starlette 自己抛的，不是你的代码抛的。

## 5. `@app.exception_handler` 的匹配规则

```python
@app.exception_handler(ValueError)
async def handle_value_error(request: Request, exc: ValueError):
    return JSONResponse({"message": str(exc)}, status_code=400)
```

| 规则 | 说明 |
| --- | --- |
| 按**异常类的继承链**找最具体的处理器 | 注册了 `Exception` 也能兜住全部 |
| 只匹配**完全限定名**相同或父类 | 不会跨模块误匹配同名类 |
| 处理器是 `async def` | 内部不能阻塞 |
| 必须返回 `Response` | 返回 `None` 会报错 |
| 注册时机 | 在 `app` 创建之后、**开始服务之前** |

匹配示例：

```python
class AppError(Exception): ...
class NotFoundError(AppError): ...

app.add_exception_handler(AppError, handle_app_error)
# NotFoundError 没单独注册 → 命中 AppError 的处理器
```

> 注册顺序无关，**具体的类优先**。这让「基类兜底 + 子类特化」成为标准写法。

## 6. 三种处理策略

### 6.1 视图内抛 `HTTPException`（最常用）

```python
@app.get("/apps/{id}")
def get_app(id: str, db=Depends(get_db)):
    app = db.get(App, id)
    if app is None:
        raise HTTPException(404, "App not found")
    return app
```

| 优点 | 缺点 |
| --- | --- |
| 简单直接 | 业务层与 HTTP 耦合 |
| 无需注册 | 大量重复的 `404`/`409` 判断 |

> 项目 `_find_owned()` 就是这种：把「查 + 归属校验」收成一个函数，内部抛 404。

### 6.2 自定义业务异常 + 全局处理器

```python
# app/errors_business.py
class AppError(Exception):
    def __init__(self, message: str, status_code: int = 400):
        self.message = message
        self.status_code = status_code


class NotFound(AppError):
    def __init__(self, message: str = "Not found"):
        super().__init__(message, 404)


# app/main.py
@app.exception_handler(AppError)
async def handle_app_error(request: Request, exc: AppError):
    return _envelope(exc.status_code, exc.message)
```

好处：

| 好处 | 说明 |
| --- | --- |
| 业务层不依赖 FastAPI | service 只 `raise NotFound(...)` |
| 统一映射 | 所有业务错误走同一个信封 |
| 易测试 | 直接断言异常类型 |

> 分层项目（`api/` + `service/`）推荐这种；单层小项目用 `HTTPException` 更省事。**两者可以混用**：基础设施层用 `HTTPException`，服务层用自定义异常。

### 6.3 兜底：未捕获异常

```python
@app.exception_handler(Exception)
async def handle_any(request: Request, exc: Exception):
    logger.exception("未处理异常: %s %s", request.method, request.url.path)
    return _envelope(500, "Internal Server Error")
```

| 要点 | 说明 |
| --- | --- |
| **必须记日志**（带堆栈） | 否则 bug 无法定位 |
| **绝不能回堆栈** | 泄露路径、SQL、密钥 |
| 统一文案 | `Internal Server Error`，细节留在日志 |
| 注意 | 加了它之后，`debug=True` 的调试页也没了 |

> 「**对外脱敏，对内详细**」是错误处理的第一原则。

## 7. `RequestValidationError` 的消费

### 7.1 它是 FastAPI 特有的

```python
from fastapi.exceptions import RequestValidationError

@app.exception_handler(RequestValidationError)
async def handle_validation(request, exc: RequestValidationError):
    errors = exc.errors()      # list[dict]
```

`errors()` 的每条：

```python
{
  "type": "string_too_short",
  "loc": ("body", "name"),
  "msg": "String should have at least 1 character",
  "input": "",
  "ctx": {"min_length": 1},
}
```

| 字段 | 用途 |
| --- | --- |
| `type` | 决定用哪条文案规则 |
| `loc` | 定位字段（`("body","items",0,"price")`） |
| `msg` | Pydantic 的英文消息（**不适合直接给用户**） |
| `ctx` | 约束参数（`min_length`/`expected`） |

### 7.2 为什么不能直接把 `msg` 给前端

| 问题 | 说明 |
| --- | --- |
| 英文、含类名 | 「String should have at least 1 character」 |
| 不稳定 | Pydantic 升级会改文案 |
| 双栈不一致 | NestJS 的 `class-validator` 文案完全不同 |
| 含 `input` | 可能带用户敏感数据 |

> 所以契约项目必须**自己定义文案规则**（项目的真源是 `packages/contract/error-messages.md`）。

## 8. 项目实战：`errors.py` 全解

### 8.1 整体结构

```
register_error_handlers(app)
├── _envelope(status, message)          → 统一响应体
├── _http_exception_handler             → 捕获 Starlette/ FastAPI 的 HTTPException
└── _validation_exception_handler       → 捕获 RequestValidationError
        └── _build_message(errors)
              ├── _describe(err)        → (规则名, 文案)
              │     └── _enum_values()  → 枚举 expected 解析
              └── 按 (字段顺序, 规则顺序) 稳定排序
```

### 8.2 统一信封

```python
_REASON_PHRASES: dict[int, str] = {
    400: "Bad Request",
    401: "Unauthorized",
    403: "Forbidden",
    404: "Not Found",
    409: "Conflict",
    500: "Internal Server Error",
}


def _envelope(status_code: int, message: str) -> JSONResponse:
    return UTF8JSONResponse(
        status_code=status_code,
        content={
            "statusCode": status_code,
            "message": message,
            "error": _REASON_PHRASES.get(status_code, "Error"),
        },
    )
```

| 字段 | 来源 | 为什么需要 |
| --- | --- | --- |
| `statusCode` | 冗余状态码 | 前端某些场景只看 body（如被 axios 拦截后） |
| `message` | 人读文案 | 直接展示 |
| `error` | 原因短语 | 与 NestJS 一致（Nest 默认就带这个字段） |

> `UTF8JSONResponse` 保证 `charset=utf-8`——**中文错误文案不乱码**，且与 TS 侧逐字节一致。

### 8.3 两个 handler

```python
@app.exception_handler(StarletteHTTPException)
async def _http_exception_handler(_request: Request, exc: StarletteHTTPException) -> JSONResponse:
    message = exc.detail if isinstance(exc.detail, str) else str(exc.detail)
    return _envelope(exc.status_code, message)


@app.exception_handler(RequestValidationError)
async def _validation_exception_handler(_request: Request, exc: RequestValidationError) -> JSONResponse:
    return _envelope(status.HTTP_400_BAD_REQUEST, _build_message(exc.errors()))
```

| 处理 | 关键点 |
| --- | --- |
| HTTP 异常 | `detail` 非字符串时 `str()` 兜底，保证 `message` 是字符串 |
| 校验异常 | **状态码改成 400**（与 NestJS 对齐），并把数组压成**一条** `message` |

> 「数组 → 一条字符串」是契约选择：前端只展示 `message`，不需要逐字段渲染。**形状越简单，双栈越容易一致。**

### 8.4 文案映射表

```python
_RULE_ORDER: list[str] = ["required", "email", "minLength", "maxLength", "enum", "unknown", "string"]
```

```python
if err_type == "missing":
    return "required", f"{field} is required"
if err_type == "value_error":            # EmailStr
    return "email", f"{field} must be a valid email"
if err_type in ("string_too_short", "too_short"):
    return "minLength", f"{field} must be at least {ctx.get('min_length')} characters"
if err_type in ("string_too_long", "too_long"):
    return "maxLength", f"{field} must be at most {ctx.get('max_length')} characters"
if err_type in ("literal_error", "enum"):
    return "enum", f"{field} must be one of: {_enum_values(str(ctx.get('expected', '')))}"
if err_type == "extra_forbidden":
    return "unknown", f"{field} should not exist"
if err_type == "string_type":
    return "string", f"{field} must be a string"
return "unknown", f"{field} is invalid"
```

| 教学点 | 说明 |
| --- | --- |
| 用 `type` 而不是解析 `msg` | `type` 是稳定标识，`msg` 会变 |
| `loc[-1]` 取字段名 | 嵌套时取最内层字段 |
| 兜底 `unknown` | **未映射的新类型不会崩，也不会漏报** |
| 文案规则集中 | 与 `error-messages.md` 一表对应 |

### 8.5 确定性排序

```python
def _build_message(errors):
    field_order: dict[str, int] = {}
    items = []
    for err in errors:
        field = str(err.get("loc", ())[-1]) if err.get("loc") else ""
        field_order.setdefault(field, len(field_order))
        rule, message = _describe(err)
        rule_rank = _RULE_ORDER.index(rule) if rule in _RULE_ORDER else len(_RULE_ORDER)
        items.append((field_order[field], rule_rank, message))
    items.sort(key=lambda item: (item[0], item[1]))
    return "; ".join(item[2] for item in items)
```

排序键 = **字段出现顺序 + 规则优先级**。

为什么必须排序：

| 不排序 | 排序 |
| --- | --- |
| Pydantic 多错误顺序不确定 | 稳定 |
| 双栈文案顺序不同 | 逐字节一致 |
| 契约测试偶发失败 | 可断言 |

示例结果：

```
name is required; email must be a valid email
```

> 关键洞察：**同一字段有两个错误时**（如既太短又不匹配 pattern），谁先谁后必须有统一规则，否则「同一请求两次返回不同文案」。

### 8.6 `_enum_values`：一个真实坑

```python
def _enum_values(expected: str) -> str:
    values = re.findall(r"'([^']*)'", expected)
    return ", ".join(values) if values else expected
```

Pydantic 的 `ctx["expected"]` 文本随取值个数变化：

| 取值数 | `expected` 文本 |
| --- | --- |
| 2 | `"'chatflow' or 'workflow'"` |
| 3 | `"'start', 'end' or 'llm'"` |

若按 `" or "` 切分，3 个取值时会得到 `["'start', 'end'", "'llm'"]` —— **中间项被切坏**。用正则抽取所有引号内容才是稳妥做法。

> 这是「依赖第三方库的错误文案格式」的典型风险：**格式不保证稳定，解析要宽松、要兜底**。

## 9. 错误契约的三条硬规则

### 9.1 形状固定

```json
{
  "statusCode": 404,
  "message": "App not found",
  "error": "Not Found"
}
```

| 规则 | 理由 |
| --- | --- |
| 顶层只这三个字段 | 前端一套解析 |
| `statusCode` 与 HTTP 状态码一致 | 避免自相矛盾 |
| `message` 永远是字符串 | 不允许数组/对象 |
| `error` 是固定短语表 | 可枚举、可翻译 |

### 9.2 状态码对齐

| 场景 | NestJS 默认 | FastAPI 默认 | 契约选择 |
| --- | --- | --- | --- |
| 校验失败 | `400` | `422` | **`400`** |
| 未认证 | `401` | `401`（手写） | `401` |
| 无权限 | `403` | `403` | `403` |
| 不存在 | `404` | `404` | `404` |
| 冲突 | `409` | 手写 | `409` |

> 项目把 422 改成 400，就是为了「同一请求打到两套后端，前端看到的状态码与文案完全一样」。

### 9.3 文案可复现

| 要求 | 实现 |
| --- | --- |
| 不随机 | 无时间戳、无 trace id 混入 `message` |
| 不本地化差异 | 统一英文（真源文档里定） |
| 顺序确定 | §8.5 的排序 |
| 不含内部细节 | 不出现 SQL、堆栈、类名 |

## 10. 日志与响应要分开

```python
@app.exception_handler(Exception)
async def handle_unexpected(request: Request, exc: Exception):
    logger.exception(                       # 对内：完整堆栈
        "unhandled error: %s %s",
        request.method,
        request.url.path,
    )
    return _envelope(500, "Internal Server Error")   # 对外：一句固定文案
```

| 面向 | 内容 |
| --- | --- |
| **响应** | 固定文案 + 状态码，不含堆栈/路径/参数 |
| **日志** | 堆栈、请求方法、路径、`request_id`、用户 id |
| 两者关联 | 用 `request_id` 串起来（[03-工程化/02](../03-工程化/02-配置与日志.md) §7.3） |

反面教材：

```python
return JSONResponse({"error": str(exc)}, status_code=500)   # ❌ 泄露内部信息
```

> `str(exc)` 可能包含 SQL 片段、文件绝对路径、上游返回体——**都是攻击者想要的信息**。

## 11. 与 NestJS 对照

| FastAPI | NestJS | 说明 |
| --- | --- | --- |
| `HTTPException(status, detail)` | `new HttpException(msg, status)` | 一致 |
| `@app.exception_handler(X)` | `@Catch(X)` + `APP_FILTER` | 全局异常过滤器 |
| `StarletteHTTPException` 处理器 | `@Catch(HttpException)` | 兜住所有 HTTP 异常 |
| `RequestValidationError` 处理器 | `ValidationPipe({ exceptionFactory })` | 校验错误定制 |
| `{statusCode, message, error}` | **Nest 默认就是这形状** | 项目让 FastAPI 对齐 Nest |
| `errors()` 多错误数组 | `ValidationError[]` | 都要压成单文案 |
| 500 兜底 | `@Catch()` 无参 | 全局兜底 |
| `request_id` 关联日志 | `AsyncLocalStorage` | 一致 |

> 值得注意的是：**NestJS 天生就输出 `{statusCode, message, error}`**，FastAPI 默认是 `{detail}`。所以「对齐」的工作量全在 Python 侧——这正是 `errors.py` 存在的意义。

## 12. 验收自测

### 12.1 判断

1. 给 `StarletteHTTPException` 注册处理器，能捕获 `fastapi.HTTPException` 吗？
2. `RequestValidationError` 的 `msg` 可以直接返回给用户吗？
3. 未捕获异常处理器里应该返回堆栈方便排查。
4. 两个错误处理器都注册时，具体类优先于 `Exception`。

<details>
<summary>答案</summary>

1. ✅ 能，FastAPI 的 `HTTPException` 继承自它。
2. ❌ 不稳定、英文、双栈不一致，应映射为契约文案。
3. ❌ 堆栈只进日志；响应给固定文案。
4. ✅ 按继承链找最具体的。

</details>

### 12.2 找错

```python
@app.exception_handler(RequestValidationError)
async def handle(request, exc):
    return JSONResponse({"detail": exc.errors()}, status_code=422)
```

三个问题：

1. 形状不是契约信封；
2. 状态码 422 与 NestJS 的 400 不一致；
3. `exc.errors()` 内含 `input`（可能泄露用户数据），且直接给前端数组。

## 13. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 前端收到的错误形状不一致 | 有的走 `HTTPException`，有的走默认 422 | 统一两个 handler |
| 404 没有被归一化 | 只注册了 `fastapi.HTTPException` | 注册 `StarletteHTTPException` |
| 自定义异常处理器不生效 | 注册在 `app` 启动之后 | 在创建 app 后立即注册 |
| 处理器返回 `None` | 忘了 return `Response` | 必须返回 `Response` |
| 500 响应里出现堆栈 | 开了 `debug=True` 或无兜底 handler | 生产关 debug + 统一兜底 |
| 500 响应里出现 SQL | 直接 `str(exc)` | 固定文案 |
| 校验错误提示是英文长句 | 直接返回 Pydantic 的 `msg` | 按 `type` 映射 |
| 同一请求两次文案顺序不同 | 未排序 | 按（字段序, 规则序）排序 |
| 枚举文案少了中间项 | 按 `" or "` 切 `expected` | 正则抽取引号内容 |
| 422 与 400 双栈不一致 | 未改默认 | 校验异常统一 400 |
| 中文错误乱码 | 响应头无 charset | 自定义 `JSONResponse`（项目已做） |
| 处理器里阻塞 | `async def` 内做同步 IO | 改同步 handler 或 `to_thread` |
| 错误里带 `request_id` 之外的内部 id | 习惯性拼进 message | 只放日志 |
| 业务层直接依赖 FastAPI | 到处 `import HTTPException` | 自定义异常 + 全局映射 |

## 14. 本篇小结

- **三种默认错误**：`HTTPException` → `{detail}`；校验 → 422 + 数组；未捕获 → 500。
- **`detail` 可以是任意 JSON**，但契约项目应统一信封，不要让接口各自发挥。
- **注册 `StarletteHTTPException`** 能连 Starlette 内部抛的 404/405 一起归一化。
- **处理器按继承链匹配**：具体的类优先，`Exception` 兜底。
- **业务层用自定义异常**，HTTP 映射集中在全局处理器里（`AppError` 模式）。
- **`RequestValidationError` 必须自己映射文案**：`msg` 不稳定、英文、双栈不一致。
- **错误契约三硬规则**：形状固定、状态码对齐（422 → 400）、文案可复现。
- **确定性排序** = 字段出现顺序 + 规则优先级；否则同一请求会返回不同文案。
- **解析第三方错误文本要宽松**（`_enum_values` 的正则），并保留兜底分支。
- **对外脱敏、对内详细**：响应固定文案，日志带堆栈 + `request_id`。
- **项目范式**：`_envelope` 统一三字段、两个 handler、`_describe` 文案表、`_build_message` 排序。
- **双栈视角**：NestJS 天生输出 `{statusCode, message, error}`，FastAPI 需要 `errors.py` 才能对齐——**契约一致的成本全在 Python 侧**。
- **下一步**：中间件、CORS 与生命周期。
