## 3. 配置从哪里来

### 3.1 四层优先级

```
① 代码里的默认值（最低优先级）
② .env 文件
③ 进程环境变量（OS / shell / Docker -e）
④ 显式传参 Settings(database_url=...)（最高优先级）
```

`pydantic-settings` 的默认顺序正是这样：**环境变量 > `.env` > 默认值**。

### 3.2 一个具体例子

```python
# config.py
class Settings(BaseSettings):
    jwt_secret: str = "dev-secret"
```

```ini
# .env
JWT_SECRET=from-dotenv
```

```powershell
# shell
$env:JWT_SECRET = "from-shell"
```

| 情况 | `settings.jwt_secret` |
| --- | --- |
| 三者都在 | `from-shell` |
| 只有 `.env` | `from-dotenv` |
| 都没有 | `dev-secret` |

> 这条规则是整个配置体系的基石：**容器/K8s 永远用环境变量覆盖**，`.env` 只服务本地开发。

### 3.3 为什么不用 `os.getenv` 手搓

| 手搓 `os.getenv` | `pydantic-settings` |
| --- | --- |
| 全是 `str`，要自己 `int()` 转换 | 自动按注解转换 |
| 缺值只能拿到 `None`，错误在运行到那行才炸 | 启动即校验，缺必填项立刻失败 |
| 没有默认值/别名机制 | `Field(default=..., validation_alias=...)` |
| 拼写错误静默返回 `None` | 类型不符直接报错 |
| 无法统一 dump/脱敏 | `model_dump()` + `SecretStr` |

> **配置错误要在启动时炸，而不是在第一个请求到来时炸。**

## 4. `pydantic-settings` 实战

### 4.1 最小可用配置

完整文件路径：`apps/api-py/app/config.py`（真实内容，节选）

```python
from pathlib import Path

from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

# 本项目目录（apps/api-py）：无论从哪个 cwd 启动，都读这一份 .env
_PROJECT_DIR = Path(__file__).resolve().parent.parent


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=_PROJECT_DIR / ".env", extra="ignore")

    service_name: str = "api-py"
    version: str = "0.1.0"
    database_url: str = "postgresql+psycopg://postgres:difyai123456@localhost:5432/minidify"
    jwt_secret: str = "dev-jwt-secret-change-me-please"
    access_token_expires_in: int = Field(default=3600, validation_alias="JWT_EXPIRES_IN")
    port: int = 8000
    llm_base_url: str = "https://api.openai.com/v1"
    llm_api_key: str = ""
    llm_model: str = "gpt-4o-mini"
    llm_timeout_ms: int = 60000
    max_tool_rounds: int = 5
    embedding_model: str = "text-embedding-3-small"


settings = Settings()
```

### 4.2 逐行拆解

| 代码 | 作用 |
| --- | --- |
| `_PROJECT_DIR = Path(__file__).resolve().parent.parent` | 从 `app/config.py` 上溯两级 → `apps/api-py` |
| `env_file=_PROJECT_DIR / ".env"` | **绝对路径**，不依赖当前工作目录 |
| `extra="ignore"` | `.env` 里出现未声明字段时**忽略**（如 TS 侧专用键） |
| `access_token_expires_in` | 字段名与变量名不同 |
| `validation_alias="JWT_EXPIRES_IN"` | 读 `JWT_EXPIRES_IN` 而不是 `ACCESS_TOKEN_EXPIRES_IN` |
| `settings = Settings()` | 模块级单例（[00-Python基础/04](../00-Python基础/04-模块、包与导入.md)：模块只执行一次） |

### 4.3 `env_file` 必须用绝对路径

```python
# ❌ 依赖 cwd：从仓库根启动就读不到
model_config = SettingsConfigDict(env_file=".env")

# ✅ 与启动目录无关
_PROJECT_DIR = Path(__file__).resolve().parent.parent
model_config = SettingsConfigDict(env_file=_PROJECT_DIR / ".env")
```

**踩坑现场**：

```powershell
# 在仓库根启动
uv run --project apps/api-py uvicorn app.main:app
```

若写相对路径 `".env"`，pydantic-settings 会在**仓库根**找 `.env` → 找不到 → 全部走默认值 → 连到了错误的数据库，且**没有任何报错**。

> 这就是项目注释里那句「无论从哪个 cwd 启动，都读这一份 .env」的由来。

### 4.4 大小写不敏感

```python
class Settings(BaseSettings):
    database_url: str = ""      # ← 读 DATABASE_URL（大小写不敏感）
```

| 默认行为 | 说明 |
| --- | --- |
| `case_sensitive=False` | 字段名转大写后匹配环境变量名 |
| 要严格区分 | `SettingsConfigDict(case_sensitive=True)` |

> 这解释了项目文档注释：「环境变量名大小写不敏感：`database_url` 对应 `DATABASE_URL`」。

### 4.5 `validation_alias` 的真实用途

场景：Python 侧想用 `access_token_expires_in`（语义清晰），但 TS 侧读的是 `JWT_EXPIRES_IN`——**两侧共用同一份 `.env`**，不能各自改名。

```python
access_token_expires_in: int = Field(default=3600, validation_alias="JWT_EXPIRES_IN")
```

| 别名类型 | 影响 |
| --- | --- |
| `validation_alias` | 只影响**读取**（输入） |
| `serialization_alias` | 只影响**输出**（dump） |
| `alias` | 两者都影响 |

> `validation_alias` 的价值：**内部字段名自由，外部契约稳定**。这是与另一个服务共用配置时的标准做法。

### 4.6 类型转换

```ini
# .env
PORT=8000
MAX_TOOL_ROUNDS=5
```

```python
port: int = 8000                  # "8000" → 8000（自动）
max_tool_rounds: int = 5          # "5" → 5
```

若 `.env` 写 `PORT=abc` → 启动直接报：

```
pydantic_core._pydantic_core.ValidationError: 1 validation error for Settings
port
  Input should be a valid integer, unable to parse string as an integer
```

> 这正是我们想要的：**启动即失败**，而不是运行到某个请求时才发现端口解析出错。

### 4.7 `extra` 策略

| 值 | 行为 | 适用 |
| --- | --- | --- |
| `"ignore"` | 忽略未声明字段 | **默认推荐**（`.env` 常被多个服务共用） |
| `"forbid"` | 未知字段报错 | 强约束环境（能抓出拼写错误） |
| `"allow"` | 保留在 `model_extra` | 动态配置 |

> 项目选 `ignore` 的原因很明显：`.env` 里还有 TS 侧、前端侧的键，Python 侧不该因为不认识就崩。

### 4.8 嵌套配置

```python
class LLMSettings(BaseModel):
    base_url: str = "https://api.openai.com/v1"
    api_key: str = ""
    model: str = "gpt-4o-mini"


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_nested_delimiter="__")
    llm: LLMSettings = LLMSettings()
```

对应 `.env`：

```ini
LLM__BASE_URL=https://api.openai.com/v1
LLM__API_KEY=sk-xxx
LLM__MODEL=gpt-4o-mini
```

> 项目目前用**扁平字段**（`llm_base_url`）——配置项少时更直观；超过 20 个再考虑嵌套。

### 4.9 密钥脱敏：`SecretStr`

```python
from pydantic import SecretStr


class Settings(BaseSettings):
    jwt_secret: SecretStr
    llm_api_key: SecretStr = SecretStr("")
```

| 行为 | 结果 |
| --- | --- |
| `print(settings.jwt_secret)` | `SecretStr('**********')` |
| `settings.jwt_secret.get_secret_value()` | 真实值 |
| `settings.model_dump()` | 仍是 `**********` |
| 日志里 `%s` 打印 | 安全（自动脱敏） |

> 现阶段项目用普通 `str`。一旦开始打印整个 `settings`，密钥就会进日志——这是最常见的泄密路径。**推荐尽早换 `SecretStr`。**

## 5. `.env` 的工程规范

### 5.1 必须有三份文件

| 文件 | 是否提交 | 内容 |
| --- | --- | --- |
| `.env` | ❌ **绝不提交** | 真实密钥、本地连接串 |
| `.env.example` | ✅ 提交 | 全部键 + 占位值 + 注释 |
| `.env.local`（可选） | ❌ | 个人覆盖 |

```gitignore
.env
.env.local
.env.*.local
!.env.example
```

### 5.2 `.env.example` 的写法

```ini
# ---- 服务 ----
SERVICE_NAME=api-py
PORT=8000

# ---- 数据库（Postgres + pgvector）----
DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/minidify

# ---- 认证（与 api-ts 共用密钥，否则 JWT 不互认）----
JWT_SECRET=change-me
JWT_EXPIRES_IN=3600

# ---- LLM（OpenAI 兼容）----
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=
LLM_MODEL=gpt-4o-mini
LLM_TIMEOUT_MS=60000
MAX_TOOL_ROUNDS=5

# ---- 嵌入 ----
EMBEDDING_MODEL=text-embedding-3-small
```

要点：

| 要点 | 原因 |
| --- | --- |
| 每个键都写注释 | 新人不需要读代码猜含义 |
| 占位值不要像真密钥 | 避免误用 |
| 与代码字段一一对应 | 方便核对遗漏 |

### 5.3 「缺配置」应该报错，而不是静默

```python
# 生产必须显式提供
class Settings(BaseSettings):
    jwt_secret: str            # 无默认值 → 缺失即报错
```

| 策略 | 适用 |
| --- | --- |
| 必填（无默认值） | 生产关键项（DB、密钥） |
| 有开发默认值 | 非关键项（`service_name`、`version`） |
| `Field(default=...)` + 校验器 | 需要范围校验 |

```python
from pydantic import field_validator


class Settings(BaseSettings):
    port: int = 8000

    @field_validator("port")
    @classmethod
    def check_port(cls, v: int) -> int:
        if not (1 <= v <= 65535):
            raise ValueError("port 必须在 1~65535 之间")
        return v
```

> 生产环境还应在启动时断言「不是默认密钥」：

```python
if settings.jwt_secret == "dev-jwt-secret-change-me-please" and not settings.debug:
    raise RuntimeError("生产环境必须设置真实 JWT_SECRET")
```

## 6. `logging` 五大概念

### 6.1 概念图

```
代码 → logger.info(...)          ① Logger（按名字分层的记录器）
          │ 检查 level
          ↓
      Handler（决定输出到哪）      ② StreamHandler / FileHandler / RotatingFileHandler
          │
          ↓
      Formatter（决定长什么样）    ③ 时间 + 级别 + logger 名 + 消息
```

四个核心名词：

| 名词 | 作用 |
| --- | --- |
| **Logger** | 代码调用的入口，按名字组成树（`app.rag.service` 是 `app.rag` 的子级） |
| **Handler** | 输出目的地：控制台、文件、HTTP、syslog |
| **Formatter** | 输出格式 |
| **Level** | `DEBUG < INFO < WARNING < ERROR < CRITICAL` |

### 6.2 第一个正确的用法

```python
import logging

logger = logging.getLogger(__name__)      # ← 每个模块顶部


def do_work() -> None:
    logger.info("开始处理")
    try:
        ...
    except Exception:
        logger.exception("处理失败")      # 自动带上 traceback
        raise
```

| 要点 | 说明 |
| --- | --- |
| `getLogger(__name__)` | 名字自动变成 `app.rag.service`，日志能看出模块 |
| 不要 `logging.info(...)` | 那用的是 root logger，无法按模块控制级别 |
| `logger.exception()` | 在 `except` 里用，等价 `error` + traceback |
| 用 `%s` 占位而非 f-string | 见 §6.6 |

### 6.3 为什么必须用 `__name__`

```python
# app/rag/service.py
logger = logging.getLogger(__name__)      # → "app.rag.service"
```

好处：

| 好处 | 说明 |
| --- | --- |
| 精确定位 | 日志前缀直接显示模块路径 |
| 分级控制 | 可以只把 `app.rag` 调到 DEBUG |
| 层级传播 | 子 logger 的日志冒泡到父 logger 的 handler |

### 6.4 `basicConfig` 的坑

```python
logging.basicConfig(level=logging.INFO)     # 只在「root 还没有 handler」时生效
```

**它只生效一次**。以下情况会「配置了但没反应」：

| 情况 | 原因 |
| --- | --- |
| 之前已经调用过 | `basicConfig` 是幂等的，第二次直接返回 |
| 某个库先调用了 | 比如 `uvicorn` 自己配了 handler |
| 给子 logger 加了 handler 但没设 level | level 未继承到预期值 |

> 结论：**入口处配一次，或用 `dictConfig` 显式配**。不要散落在各个模块里。

### 6.5 `dictConfig`：声明式配置

```python
import logging.config

LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,          # 别关掉 uvicorn 的 logger
    "formatters": {
        "default": {
            "format": "%(asctime)s %(levelname)-7s [%(name)s] %(message)s",
            "datefmt": "%Y-%m-%d %H:%M:%S",
        },
        "json": {
            "format": '{"ts":"%(asctime)s","level":"%(levelname)s","logger":"%(name)s","msg":"%(message)s"}',
        },
    },
    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "formatter": "default",
            "level": "INFO",
        },
        "file": {
            "class": "logging.handlers.RotatingFileHandler",
            "filename": "logs/app.log",
            "maxBytes": 10_000_000,
            "backupCount": 5,
            "formatter": "json",
            "encoding": "utf-8",
        },
    },
    "root": {"handlers": ["console"], "level": "INFO"},
    "loggers": {
        "app": {"handlers": ["console", "file"], "level": "DEBUG", "propagate": False},
        "uvicorn": {"handlers": ["console"], "level": "INFO", "propagate": False},
    },
}

logging.config.dictConfig(LOGGING)
```

| 配置项 | 作用 |
| --- | --- |
| `disable_existing_loggers: False` | 保留已创建的 logger（否则 uvicorn 日志消失） |
| `propagate: False` | 有自己 handler 时避免**重复输出** |
| `RotatingFileHandler` | 按大小轮转，防日志撑爆磁盘 |
| `encoding="utf-8"` | Windows 下必须显式指定（默认 GBK） |

### 6.6 `%s` 占位而不是 f-string

```python
logger.info("用户 %s 登录失败", user_id)          # ✅ 延迟格式化
logger.info(f"用户 {user_id} 登录失败")            # ❌ 即使日志被过滤也会先拼字符串
```

| 写法 | 开销 | 何时拼 |
| --- | --- | --- |
| `%s` 占位 | 极低 | 只有真要输出时才拼 |
| f-string | 每次都拼 | 调用时立即 |

> 高频日志（每个请求几条）下，这个差别会变成可观的 CPU 开销。

### 6.7 日志级别怎么选

| 级别 | 用在哪 | 生产默认 |
| --- | --- | --- |
| `DEBUG` | 变量值、SQL、分支细节 | 关闭 |
| `INFO` | 请求开始/结束、关键状态变化 | ✅ 开 |
| `WARNING` | 可恢复的异常情况（重试、降级） | ✅ 开 |
| `ERROR` | 请求失败、外部依赖不可用 | ✅ 开 |
| `CRITICAL` | 进程无法继续 | ✅ 开 |

> 一条经验：**INFO 的量应该与「请求数」同量级**，不要每个循环里打 INFO。

## 7. 结构化日志与 `request_id`

### 7.1 为什么需要

多 worker、多请求交错时，普通文本日志无法回答「这 8 行属于哪个请求」。

```
2026-10-22 10:00:01 INFO  [app.api.run] 开始执行
2026-10-22 10:00:01 INFO  [app.api.run] 开始执行
2026-10-22 10:00:02 INFO  [app.rag] 检索到 3 个片段     ← 属于哪个？
```

### 7.2 用 `extra` 注入字段

```python
import logging

logger = logging.getLogger(__name__)

logger.info("检索完成", extra={"request_id": rid, "chunks": 3, "cost_ms": 42})
```

要让 `extra` 出现在输出里，需要在 formatter 中引用：

```python
"format": "%(asctime)s [%(request_id)s] %(name)s %(message)s"
```

> 若某条日志没有传 `extra`，会报 `KeyError: 'request_id'`。解决办法：用 `LoggerAdapter` 或 `contextvars` + 自定义 Filter 统一注入默认值。

### 7.3 用 `contextvars` 自动带上 `request_id`

```python
import contextvars
import logging

request_id_var: contextvars.ContextVar[str] = contextvars.ContextVar("request_id", default="-")


class RequestIdFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        return True
```

挂到 handler 上：

```python
handler.addFilter(RequestIdFilter())
```

中间件里设置：

```python
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    rid = request.headers.get("x-request-id") or uuid.uuid4().hex[:12]
    token = request_id_var.set(rid)
    try:
        response = await call_next(request)
        response.headers["x-request-id"] = rid
        return response
    finally:
        request_id_var.reset(token)
```

> `contextvars` 在 asyncio 里**每个任务独立**，所以并发请求的 `request_id` 不会串。这是异步场景下的正确做法（对比线程局部变量 `threading.local`）。

### 7.4 JSON 日志的收益

| 收益 | 说明 |
| --- | --- |
| 可检索 | ELK/Loki 按字段过滤 |
| 可聚合 | 按 `status`、`cost_ms` 做指标 |
| 无歧义 | 消息里带换行也不会破坏结构 |
| 易脱敏 | 字段级处理 |

> 生产建议：**控制台保留人类可读格式，文件走 JSON**，两条 handler 各司其职。

## 8. uvicorn 日志接入

### 8.1 一个常见的重复输出

```
INFO:     127.0.0.1 - "GET /health HTTP/1.1" 200 OK
2026-10-22 10:00:01 INFO  [uvicorn.access] 127.0.0.1 - "GET /health HTTP/1.1" 200 OK
```

原因：`uvicorn` 有自己的 logger + handler，你又给 root 或 `uvicorn` 加了 handler 且 `propagate=True`。

| 解法 | 说明 |
| --- | --- |
| `propagate: False` | 给 `uvicorn`/`uvicorn.access` 显式关闭传播 |
| 不重复配 `uvicorn` 的 handler | 让它沿用默认 |
| `--no-access-log` | 只要业务日志时关掉访问日志 |

### 8.2 让 uvicorn 日志走你的 formatter

```python
"loggers": {
    "uvicorn": {"handlers": ["console"], "level": "INFO", "propagate": False},
    "uvicorn.error": {"handlers": ["console"], "level": "INFO", "propagate": False},
    "uvicorn.access": {"handlers": ["console"], "level": "INFO", "propagate": False},
},
```

### 8.3 应用启动/关闭日志放哪

放在 lifespan 里（阶段 5/04 会展开）：

```python
logger = logging.getLogger("app.main")

@asynccontextmanager
async def lifespan(app):
    logger.info("应用启动: %s v%s", settings.service_name, settings.version)
    yield
    logger.info("应用关闭")
```

## 9. `print` vs `logging`

| 维度 | `print` | `logging` |
| --- | --- | --- |
| 级别控制 | ❌ | ✅ |
| 输出目的地 | 只能 stdout | 控制台/文件/网络 |
| 时间戳 | 自己拼 | formatter |
| 关闭 | 只能删代码 | 调 level |
| 多线程/协程 | 交错混乱 | handler 加锁 |
| 结构化 | ❌ | `extra` + JSON |

> 规则：**除了一次性脚本和交互式调试，业务代码里一律用 `logging`**。`print` 留在 `if __name__ == "__main__"` 里最安全。

## 10. 项目实战：给 `config.py` 补上生产级配置

### 10.1 现状（真实文件）

`apps/api-py/app/config.py` 已具备：

| 能力 | 实现 |
| --- | --- |
| 类型校验 | 注解 + `int`/`str` |
| 别名解耦 | `validation_alias="JWT_EXPIRES_IN"` |
| 绝对路径 `.env` | `Path(__file__).resolve().parent.parent / ".env"` |
| 宽容未知键 | `extra="ignore"` |
| 全局单例 | `settings = Settings()` |

### 10.2 建议的三处增强（教学示例）

```python
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=_PROJECT_DIR / ".env",
        extra="ignore",
        case_sensitive=False,
    )

    service_name: str = "api-py"
    # ① 密钥改用 SecretStr，避免误打印
    jwt_secret: SecretStr = SecretStr("dev-jwt-secret-change-me-please")
    llm_api_key: SecretStr = SecretStr("")
    # ② 端口加范围校验
    port: int = Field(default=8000, ge=1, le=65535)
    llm_timeout_ms: int = Field(default=60_000, gt=0)
    # ③ 环境标识，用于区分开发/生产行为
    env: str = Field(default="dev", validation_alias="APP_ENV")


settings = Settings()
```

### 10.3 启动时的安全断言

```python
import logging

logger = logging.getLogger("app.config")

if settings.env != "dev":
    if settings.jwt_secret.get_secret_value().startswith("dev-"):
        raise RuntimeError("生产环境禁止使用开发默认 JWT_SECRET")
    if not settings.llm_api_key.get_secret_value():
        logger.warning("未配置 LLM_API_KEY，LLM 节点将不可用")
```

> 这类「启动自检」比运行期报错便宜得多：**部署 3 秒后就知道配错了**。

### 10.4 日志初始化位置

| 文件 | 职责 |
| --- | --- |
| `app/config.py` | 只读配置，不配日志（纯数据） |
| `app/logging_conf.py` | `dictConfig` 字典 + `setup_logging()` |
| `app/main.py` | 启动最早期调用 `setup_logging()` |

顺序很重要：

```python
# app/main.py 顶部，任何业务 import 之前
from app.logging_conf import setup_logging
setup_logging()

from app.api import ...      # noqa: E402  ← 在配置之后再导入业务模块
```

> 若业务模块在 import 时就打了日志，那日志会先于 handler 配置产生——用 `dictConfig` 的 `disable_existing_loggers: False` 也能兜住，但顺序正确更省心。

## 11. 与 TypeScript 对照

| Python | TypeScript/Node | 说明 |
| --- | --- | --- |
| `pydantic-settings` | `dotenv` + `zod` 校验 | Python 一体化 |
| `SettingsConfigDict(env_file=...)` | `dotenv.config()` | 后者默认读 cwd |
| `validation_alias` | 手动 `process.env.X ?? y` | 别名映射 |
| 类型自动转换 | zod `coerce` | 都要显式或半显式 |
| `SecretStr` | 无内建（靠约定） | Python 有运行时保护 |
| `logging` | `pino` / `winston` | 都是分级 + 多 handler |
| `getLogger(__name__)` | `pino({name})` | 按模块命名 |
| `dictConfig` | pino 配置对象 | 声明式 |
| `extra` + JSON formatter | `pino` 天然结构化 | Node 生态默认 JSON |
| `contextvars` | `AsyncLocalStorage` | 请求上下文透传 |
| `RotatingFileHandler` | `pino-roll` | 日志轮转 |

> 心智迁移：**Node 生态默认 JSON 日志，Python 默认文本**。生产上线前一定要把 Python 侧切成结构化日志，否则接入日志平台会很痛苦。

## 12. 验收自测

### 12.1 预测值

```python
class S(BaseSettings):
    port: int = 8000
```

`.env` 写 `PORT=9000`，shell 里又 `$env:PORT="7000"`，则 `S().port` = ?

<details>
<summary>答案</summary>

`7000`。环境变量优先级高于 `.env`。

</details>

### 12.2 找错

```python
import logging

logging.basicConfig(level=logging.INFO)

from app.utils import helper      # helper 模块里调用了 logging.basicConfig(level=DEBUG)

logging.basicConfig(level=logging.DEBUG)    # 期望生效
logging.debug("调试信息")
```

问题：

1. `basicConfig` 只在首次生效，后面两次都被忽略；
2. 最终级别是第一次调用设的 `INFO`，`debug` 不会输出；
3. 库模块（`app.utils`）里**不该**调用 `basicConfig`。

修复：入口处用 `dictConfig` 一次性配置，库模块只 `getLogger`。

## 13. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `.env` 明明有值却读到默认值 | `env_file` 用相对路径，cwd 不对 | 用 `Path(__file__)` 绝对路径 |
| 环境变量改了不生效 | 进程启动后才 `export` | 改完重启进程 |
| `.env` 改完不生效 | `settings` 是模块级单例，已缓存 | 重启进程 |
| `extra="forbid"` 导致启动崩 | `.env` 有多余键 | 改 `ignore`，或清理 `.env` |
| 端口写 `abc` 启动崩 | 类型校验生效 | 这是**正确行为**，修 `.env` |
| `print(settings)` 泄露密钥 | 普通 `str` | 用 `SecretStr` |
| 日志全变成 `WARNING` | 某处 `basicConfig(level=WARNING)` 先执行 | 统一 `dictConfig` |
| `basicConfig` 不生效 | 已被调用过 / 已存在 handler | 同上 |
| 日志重复两遍 | `propagate=True` 且有双层 handler | 显式 `propagate: False` |
| uvicorn 访问日志消失 | `disable_existing_loggers=True` | 设为 `False` |
| 文件日志中文乱码 | Windows 默认 GBK | `encoding="utf-8"` |
| 日志文件无限增长 | 用 `FileHandler` | `RotatingFileHandler` |
| `KeyError: 'request_id'` | formatter 引用了未注入字段 | Filter 统一注入默认值 |
| 高频 f-string 日志拖慢 | 每次都拼字符串 | `%s` 占位 |
| 生产日志无法检索 | 纯文本多行 | JSON formatter |
| 库代码里 `basicConfig` | 抢走应用配置权 | 库只 `getLogger` |

## 14. 本篇小结

- **配置四层优先级**：默认值 < `.env` < 环境变量 < 显式入参；容器用环境变量覆盖。
- **`pydantic-settings` 的价值**：类型转换 + 启动即校验 + 别名 + 脱敏，远胜手搓 `os.getenv`。
- **`env_file` 必须绝对路径**（`Path(__file__).resolve().parent.parent`），否则 cwd 一变就读不到。
- **`validation_alias`** 解耦「内部字段名」与「外部变量名」，是与 TS 侧共用 `.env` 的关键。
- **`extra="ignore"`** 容忍共享 `.env` 里的多余键；**`SecretStr`** 防日志泄密。
- **`.env` 不提交，`.env.example` 必须提交**；生产关键项用必填字段，让缺失在启动时报错。
- **`settings` 是模块级单例**：配置加载只发生一次，改 `.env` 需重启。
- **`logging` 四件套**：logger（按 `__name__` 分层）、handler（去哪）、formatter（长什么样）、level（多细）。
- **`basicConfig` 只生效一次**：入口处用 `dictConfig`，库模块只 `getLogger`。
- **`propagate: False` + `disable_existing_loggers: False`** 解决重复输出与 uvicorn 日志丢失。
- **结构化日志 + `contextvars` 注入 `request_id`**：并发请求的日志才能串起来。
- **`%s` 占位优于 f-string**；生产文件日志用 JSON + 轮转 + UTF-8。
- **项目范式**：`config.py` 已做对「绝对路径 + 别名 + 宽容未知键 + 单例」，可继续补 `SecretStr`、范围校验与启动自检；日志配置应独立成 `logging_conf.py` 并在 `main.py` 最早期初始化。
- **下一步**：pytest 入门。
