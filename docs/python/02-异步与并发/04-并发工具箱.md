## 3. 竞态条件：`+=` 不是原子操作

### 3.1 复现

```python
import threading

counter = 0


def add():
    global counter
    for _ in range(100_000):
        counter += 1


threads = [threading.Thread(target=add) for _ in range(10)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(counter)      # 期望 1_000_000，实际常是 700_000 ~ 900_000
```

### 3.2 为什么（关键）

`counter += 1` 在字节码层是**三步**：

```
LOAD_GLOBAL  counter     ① 读
LOAD_CONST   1
BINARY_OP    +=          ② 加
STORE_GLOBAL counter     ③ 写
```

GIL 会在字节码之间切换线程，于是可能发生：

```
线程 A: 读 100 → 计算 101 →
线程 B:                    读 100 → 计算 101 → 写 101
线程 A:                                         写 101   ← 丢了一次
```

**GIL 只保证「不并行执行字节码」，不保证「复合操作原子」**——这正是 [01 篇](./01-GIL与并发模型选择.md) 常被误解的地方。

### 3.3 修复：`threading.Lock`

```python
import threading

counter = 0
lock = threading.Lock()


def add():
    global counter
    for _ in range(100_000):
        with lock:              # 进入加锁，退出自动解锁
            counter += 1
```

`with lock:` 等价于：

```python
lock.acquire()
try:
    counter += 1
finally:
    lock.release()             # 异常也保证解锁
```

| 特性 | 说明 |
| --- | --- |
| `Lock` 不可重入 | 同一线程连续 `acquire` 两次 → **自己死锁** |
| `RLock` 可重入 | 同一线程可重复获取，需等量释放 |
| 必须用 `with` | 手写 `acquire/release` 漏掉 `finally` 就是定时炸弹 |

## 4. 线程同步原语

### 4.1 `RLock`：递归函数里的锁

```python
rlock = threading.RLock()


def outer():
    with rlock:
        inner()          # 同一线程再次获取，不阻塞


def inner():
    with rlock:          # ✅ RLock 允许
        ...
```

若换成普通 `Lock`，`inner()` 会永久阻塞——这是「不可重入」的经典表现。

### 4.2 `Event`：线程间「通知」信号

```python
import threading

ready = threading.Event()


def worker():
    print("worker 等信号")
    ready.wait()                   # 阻塞直到 set()
    print("worker 开始工作")


t = threading.Thread(target=worker)
t.start()

print("main 准备数据")
ready.set()                        # 唤醒所有等待者
t.join()
```

| 方法 | 作用 |
| --- | --- |
| `wait(timeout=None)` | 阻塞直到被 `set()` 或超时 |
| `set()` | 置位，唤醒**全部**等待者 |
| `clear()` | 复位 |
| `is_set()` | 查询 |

### 4.3 `Condition`：等待某个条件成立

```python
cond = threading.Condition()
items: list[int] = []


def consumer():
    with cond:
        while not items:                  # 必须用 while 而非 if
            cond.wait()                   # 释放锁并等待
        return items.pop(0)


def producer():
    with cond:
        items.append(1)
        cond.notify()                     # 唤醒一个等待者
```

要点：

| 要点 | 原因 |
| --- | --- |
| 必须在持有锁的 `with cond:` 内调用 `wait`/`notify` | 否则 `RuntimeError` |
| 用 `while` 而非 `if` 检查条件 | 虚假唤醒（spurious wakeup） |
| `notify()` vs `notify_all()` | 只叫醒一个 vs 全部 |

### 4.4 线程版 `Semaphore`

```python
sem = threading.Semaphore(3)

with sem:              # 最多 3 个线程同时进入
    do_io()
```

> 与 [03 篇](./03-异步实战模式.md) 的 `asyncio.Semaphore` 名字相同、**语义相同**、但**所属世界不同**：一个阻塞线程，一个挂起协程。

## 5. 生产者-消费者：`queue.Queue`

### 5.1 为什么不用 list + 锁

| `list` + `Lock` | `queue.Queue` |
| --- | --- |
| 要自己写 `while not items: wait` | 内置阻塞 |
| 要自己处理满/空 | 内置 `maxsize` |
| 容易漏锁 | 内部线程安全 |
| 无法优雅通知结束 | 支持哨兵/`task_done` |

### 5.2 标准结构

```python
import queue
import threading
import time

q: queue.Queue[int | None] = queue.Queue(maxsize=100)


def producer():
    for i in range(20):
        q.put(i)                    # 队列满时自动阻塞
    q.put(None)                     # 哨兵：通知结束


def consumer(name: str):
    while True:
        item = q.get()              # 队列空时自动阻塞
        try:
            if item is None:
                q.put(None)         # 把哨兵传下去，叫醒下一个消费者
                break
            print(f"{name} 处理 {item}")
            time.sleep(0.01)
        finally:
            q.task_done()           # 必须配对


threads = [threading.Thread(target=consumer, args=(f"c{i}",)) for i in range(3)]
for t in threads:
    t.start()
producer()
for t in threads:
    t.join()
q.join()                            # 等全部任务被 task_done
```

> 多消费者时哨兵要「**传下去**」（`q.put(None)`），否则只有一个消费者收到，其余永久阻塞。

### 5.3 `Queue` 方法表

| 方法 | 行为 | 异常 |
| --- | --- | --- |
| `put(item)` | 满则阻塞 | — |
| `put(item, block=False)` | 满则抛 | `queue.Full` |
| `put(item, timeout=1)` | 满则等 1s | `queue.Full` |
| `get()` | 空则阻塞 | — |
| `get(block=False)` | 空则抛 | `queue.Empty` |
| `task_done()` | 标记一个任务完成 | 未 `get` 就调用 → `ValueError` |
| `join()` | 等所有 `get` 都被 `task_done` | 少调一次就永久卡住 |

**`join()` 卡住的三大原因**：

1. `get()` 后忘了 `task_done()`；
2. 异常路径跳过了 `task_done()`（所以要放 `finally`）；
3. 某个消费者提前 `break` 却没处理完自己 `get` 的那条。

## 6. `asyncio.Queue`：协程世界

### 6.1 结构与线程版几乎对称

```python
import asyncio

q: asyncio.Queue[int | None] = asyncio.Queue(maxsize=100)


async def producer():
    for i in range(20):
        await q.put(i)              # 注意 await
    await q.put(None)


async def consumer(name: str):
    while True:
        item = await q.get()        # 注意 await
        try:
            if item is None:
                await q.put(None)
                break
            await asyncio.sleep(0.01)
            print(f"{name} 处理 {item}")
        finally:
            q.task_done()


async def main():
    consumers = [asyncio.create_task(consumer(f"c{i}")) for i in range(3)]
    await producer()
    await q.join()
    await asyncio.gather(*consumers)


asyncio.run(main())
```

### 6.2 差异对照

| 维度 | `queue.Queue` | `asyncio.Queue` |
| --- | --- | --- |
| 阻塞方式 | 阻塞**线程** | 挂起**协程**（`await`） |
| `put`/`get` | 同步 | **必须 `await`** |
| 满/空异常 | `queue.Full`/`queue.Empty` | `asyncio.QueueFull`/`QueueEmpty` |
| `task_done`/`join` | 同步 | 同步（但 `join` 要 `await`） |
| 跨线程使用 | ✅ | ❌（不是线程安全的） |
| 适用 | 线程池任务 | 异步流水线 |

### 6.3 典型异步流水线

```python
async def pipeline(items: list[str]):
    q_in: asyncio.Queue[str | None] = asyncio.Queue(maxsize=50)

    async def split_worker():
        for it in items:
            await q_in.put(it)
        await q_in.put(None)              # 哨兵

    async def embed_worker():
        async for chunk in consume(q_in):  # 自定义异步迭代器
            await embed(chunk)

    await asyncio.gather(split_worker(), embed_worker())
```

> 关键价值：**背压**（backpressure）。`maxsize=50` 意味着上游最多超前 50 条，内存不会暴涨——这是 `gather` 上千任务做不到的。

## 7. 线程与协程的桥接

### 7.1 从协程调阻塞函数：`asyncio.to_thread`

```python
import asyncio
import bcrypt


async def verify(password: str, hashed: str) -> bool:
    return await asyncio.to_thread(bcrypt.checkpw, password.encode(), hashed.encode())
```

| 方案 | 说明 |
| --- | --- |
| `await asyncio.to_thread(fn, *args)` | **推荐**，3.9+，自动用默认线程池 |
| `loop.run_in_executor(pool, fn, *args)` | 可指定自定义线程池/进程池 |
| `starlette.concurrency.run_in_threadpool` | FastAPI 生态，等价 |

```python
import concurrent.futures

pool = concurrent.futures.ProcessPoolExecutor(max_workers=4)

async def compress(path: str):
    loop = asyncio.get_running_loop()
    return await loop.run_in_executor(pool, compress_file, path)   # 进程池也能桥接
```

> 选择：**阻塞 IO → 线程池；CPU 密集 → 进程池**（[01 篇](./01-GIL与并发模型选择.md) 的结论在这里落地）。

### 7.2 从线程回调协程：`call_soon_threadsafe`

```python
import asyncio
import threading

loop = asyncio.get_running_loop()
queue: asyncio.Queue = asyncio.Queue()


def background_thread():
    # 在别的线程里，不能直接 await
    loop.call_soon_threadsafe(queue.put_nowait, "来自线程的消息")


threading.Thread(target=background_thread).start()
msg = await queue.get()
```

| 接口 | 用途 |
| --- | --- |
| `loop.call_soon_threadsafe(cb, *args)` | 线程安全地把回调排进事件循环 |
| `asyncio.run_coroutine_threadsafe(coro, loop)` | 从线程提交协程，返回 `concurrent.futures.Future` |

> 禁止在非事件循环线程里直接 `create_task`/`await`。

### 7.3 两种锁不能混用（高频事故）

```python
import threading

_lock = threading.Lock()


async def bad():
    with _lock:                # ❌ 等待时阻塞整个事件循环
        await do_io()
```

后果分析：

| 情况 | 结果 |
| --- | --- |
| 锁空闲 | 立即拿到，看起来没问题 |
| 锁被占（持锁者也在等 `await`） | 事件循环被卡住 → **整个 worker 死锁**，且无任何报错 |

正确做法：

```python
import asyncio

_lock = asyncio.Lock()


async def good():
    async with _lock:          # ✅ 等待时挂起协程，不阻塞事件循环
        await do_io()
```

| 锁类型 | 所在世界 | 等待方式 | 用错后果 |
| --- | --- | --- | --- |
| `threading.Lock` | 线程 | 阻塞线程 | 在协程里用 → 阻塞事件循环、可能死锁 |
| `asyncio.Lock` | 协程 | 挂起协程（`await`） | 在线程里用 → `RuntimeError: no running event loop` |

> 判断口诀：**这段代码在 `async def` 里吗？在就用 `asyncio.Lock`/`asyncio.Semaphore`/`asyncio.Queue`。**

## 8. 死锁

### 8.1 经典复现

```python
lock_a = threading.Lock()
lock_b = threading.Lock()


def t1():
    with lock_a:
        with lock_b:      # 等 B
            ...


def t2():
    with lock_b:
        with lock_a:      # 等 A → 互相等 → 永久卡住
            ...
```

### 8.2 四个必要条件

| 条件 | 说明 |
| --- | --- |
| 互斥 | 资源一次只能一个持有 |
| 持有并等待 | 拿着 A 去等 B |
| 不可剥夺 | 不能强行抢走 |
| 循环等待 | A 等 B，B 等 A |

### 8.3 避免手段（按优先级）

| 手段 | 做法 |
| --- | --- |
| **固定锁顺序** | 全局约定「永远先 A 后 B」，破坏循环等待 |
| **缩小临界区** | 锁里只做必要操作，绝不在锁里做 IO |
| **加超时** | `lock.acquire(timeout=1)`，失败则回退/重试 |
| **一次只持一把** | 尽量合并成一个锁或改数据结构 |
| **优先无锁** | 用 `queue.Queue`（内部管理锁）而不是自己拼锁 |

> 生产事故里最常见的死锁不是「双锁交叉」，而是**在锁里 `await`/做网络请求**——把临界区扩大到不可控时长。

## 9. 进程间通信（简述）

| 方式 | 用途 | 限制 |
| --- | --- | --- |
| `multiprocessing.Queue` | 传任务/结果 | 需 pickle，大数据慢 |
| `Pipe` | 双进程双向通信 | 只适合两方 |
| `Manager().dict()` | 共享字典 | 慢（走代理进程） |
| `shared_memory` | 大块二进制共享 | 需自己同步 |
| Redis / 消息队列 | 真正的跨进程/跨机器 | 引入外部依赖 |

> 实践建议：**能用队列就用队列，能用外部中间件就别自己造共享内存**。多进程共享可变状态是最容易出错的地方。

## 10. 项目实战：批量向量化的流水线

`app/rag/service.py` 的批量入库，本质是一个三段流水线：

```
文档文本 ──切分──→ chunk 队列 ──批量向量化──→ (chunk, vector) ──批量 insert──→ DB
```

### 10.1 为什么必须限流 + 背压

| 风险 | 不加控制的后果 |
| --- | --- |
| 切分快、嵌入慢 | 内存里堆积上万个 chunk（一个长文档可能切出 500+） |
| 外部 embedding API 限流 | 429 批量失败，整批重来 |
| DB 批量插入过大 | 单事务锁表、WAL 暴涨 |

### 10.2 推荐结构

```python
import asyncio


async def ingest(doc_id: str, text: str) -> None:
    raw_queue: asyncio.Queue[str | None] = asyncio.Queue(maxsize=64)   # 背压
    vec_queue: asyncio.Queue[tuple[str, list[float]] | None] = asyncio.Queue(maxsize=64)

    async def splitter():
        for i, chunk in enumerate(split_text(text)):
            await raw_queue.put(chunk)
        await raw_queue.put(None)

    async def embedder():
        batch: list[str] = []
        while True:
            item = await raw_queue.get()
            try:
                if item is None:
                    if batch:
                        vecs = await embed_batch(batch)      # 批量，非逐条
                        for c, v in zip(batch, vecs):
                            await vec_queue.put((c, v))
                        batch.clear()
                    await vec_queue.put(None)
                    break
                batch.append(item)
                if len(batch) >= 16:
                    vecs = await embed_batch(batch)
                    for c, v in zip(batch, vecs):
                        await vec_queue.put((c, v))
                    batch.clear()
            finally:
                raw_queue.task_done()

    async def writer():
        rows = []
        while True:
            item = await vec_queue.get()
            try:
                if item is None:
                    if rows:
                        await insert_chunks(doc_id, rows)
                    break
                rows.append(item)
                if len(rows) >= 100:
                    await insert_chunks(doc_id, rows)
                    rows.clear()
            finally:
                vec_queue.task_done()

    await asyncio.gather(splitter(), embedder(), writer())
```

三段各自的关键决策：

| 阶段 | 决策 | 原因 |
| --- | --- | --- |
| 切分 | 直接产出，队列 `maxsize` 限压 | 切分是纯 CPU，很快 |
| 向量化 | **攒批 16 条**再调 API | 减少请求数，摊薄延迟 |
| 入库 | **攒批 100 行**再 `insert` | 减少事务/往返次数 |
| 结束 | 哨兵逐段传递 | 保证下游能收尾（flush 最后一批） |

> 这段代码里同时出现了本篇所有主角：`asyncio.Queue`（三段）、哨兵（结束信号）、背压（`maxsize`）、`task_done`（配对）、`gather`（并发三段）、批量（性能）。

### 10.3 与同步版的对比

如果嵌入客户端只有同步版（`requests`），把 `embed_batch` 换成：

```python
vecs = await asyncio.to_thread(embed_batch_sync, batch)
```

流水线结构完全不变——**只有「哪一层被阻塞」变了**。

## 11. 与 TypeScript 对照

| Python | TypeScript/Node | 说明 |
| --- | --- | --- |
| `threading.Lock` | 无（单线程） | Node 需 `worker_threads` + `Atomics` |
| `asyncio.Lock` | `async-mutex` 库 | 语义一致 |
| `queue.Queue` | 无内建（用数组 + 手写） | Node 有 `p-queue` |
| `asyncio.Queue` | `p-queue` / 自定义 Promise 队列 | 都支持并发上限 |
| `asyncio.to_thread` | `worker_threads` / `setImmediate` | 都要显式移出主线程 |
| `task_done`/`join` | 无直接对应 | 需自己计数 |
| 死锁 | 相似（Promise 互相等待） | 原因不同，表现类似 |
| 背压 | `stream.pipeline` 内建 | Node 流更强 |

> 心智迁移：Node 没有「线程锁」的日常，但有「异步锁」。**在 Python 里要额外警惕「把线程锁误用在协程里」**——Node 根本不会遇到这个坑。

## 12. 验收自测

### 12.1 预测结果

```python
import threading

counter = 0
lock = threading.Lock()


def add():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1


ts = [threading.Thread(target=add) for _ in range(10)]
[t.start() for t in ts]
[t.join() for t in ts]
print(counter)
```

<details>
<summary>答案</summary>

`1000000`。`with lock:` 让「读-加-写」三步成为一个互斥整体。

</details>

### 12.2 找错

```python
async def worker(q: asyncio.Queue):
    while True:
        item = await q.get()
        handle(item)
```

三个问题：

1. 无结束条件 → 永远阻塞在 `await q.get()`；
2. 没有 `task_done()` → `q.join()` 永远不返回；
3. 异常时跳过 `task_done`（应放 `finally`）。

### 12.3 动手题

用 `asyncio.Queue` 写「3 个消费者 + 1 个生产者」，生产者发 100 个任务后发哨兵，主协程 `await q.join()` 后再取消消费者。

<details>
<summary>参考实现</summary>

```python
import asyncio


async def main():
    q: asyncio.Queue[int | None] = asyncio.Queue(maxsize=20)
    workers = [asyncio.create_task(consume(q, i)) for i in range(3)]

    for i in range(100):
        await q.put(i)
    for _ in range(len(workers)):
        await q.put(None)          # 每个消费者一个哨兵

    await q.join()
    await asyncio.gather(*workers)


async def consume(q: asyncio.Queue, idx: int):
    while True:
        item = await q.get()
        try:
            if item is None:
                return
            await asyncio.sleep(0.001)
        finally:
            q.task_done()
```

> 注意：这里给**每个消费者各发一个哨兵**，比「传下去」更简单，也是常见写法。二者都要求「哨兵数 = 消费者数」。

</details>

## 13. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 多线程计数少了几万 | `+=` 非原子 | `with lock` |
| 程序卡死无报错 | 死锁（交叉持锁 / 锁里做 IO） | 固定锁顺序、缩小临界区 |
| 同一线程 `acquire` 两次卡死 | `Lock` 不可重入 | 改 `RLock` |
| `Queue.join()` 永久阻塞 | 漏 `task_done` / 提前 break | `finally: q.task_done()` |
| 只有部分消费者退出 | 哨兵没按数量发 | 哨兵数 = 消费者数 |
| `await` 之后拿到过期数据 | 临界区需要覆盖整个「读-改-写」 | 把 `await` 移出临界区，或加版本号/条件检查 |
| `asyncio.Queue` 在多线程里用 | 非线程安全 | 每线程各用 `queue.Queue`，或 `run_coroutine_threadsafe` |
| `threading.Lock` 用在协程里 | 阻塞事件循环 | 换 `asyncio.Lock` |
| `asyncio.Lock` 用在普通线程 | 无运行中的循环 | 换 `threading.Lock` |
| `RuntimeError: This event loop is already running` | 嵌套 `asyncio.run` | 用 `await` 或 `to_thread` |
| 队列内存无限增长 | 没设 `maxsize` | 设上限，形成背压 |
| `task_done()` 抛 `ValueError` | 未 `get` 就调用 | 检查调用配对 |

## 14. 本篇小结

- **GIL 不保证原子性**：`+=` 是「读-加-写」三步，多线程必须用 `Lock`。
- **`Lock` 不可重入，`RLock` 可重入**；一律用 `with lock:`（`finally` 自动释放）。
- **`Event`** 是线程间信号，**`Condition`** 是「等条件成立」（用 `while` 防虚假唤醒）。
- **`queue.Queue`** 自带阻塞、容量、`task_done`/`join`；多消费者时哨兵数要匹配。
- **`asyncio.Queue`** 是协程版：`await put/get`、支持背压（`maxsize`）、不能跨线程。
- **线程 ↔ 协程桥接**：阻塞调用用 `asyncio.to_thread`/`run_in_executor`；从线程回调协程用 `call_soon_threadsafe`。
- **锁不能混用**：`async def` 里只许 `asyncio.Lock`；用错后果是「整个事件循环被卡住」且无报错。
- **死锁避免**：固定锁顺序、缩小临界区、绝不在锁里做 IO/`await`。
- **背压是异步流水线的核心价值**：`maxsize` 让上游不能无限超前。
- **项目范式**：批量向量化 = 切分 → 批量嵌入 → 批量入库，三段用 `asyncio.Queue` + 哨兵 + 批大小控制。
