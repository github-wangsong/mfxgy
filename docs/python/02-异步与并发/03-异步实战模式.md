## 3. 并发限流

### 3.1 问题：`gather` 1000 个会怎样

```python
await asyncio.gather(*(fetch(u) for u in urls_1000))     # ❌ 危险
```

后果：

| 风险 | 说明 |
| --- | --- |
| 下游被打崩 | 1000 个连接同时建立，对方限流/宕机 |
| 本地文件句柄耗尽 | `Too many open files` |
| 内存暴涨 | 1000 个响应体同时在内存 |
| 自己限流 | 被目标方拉黑/封 IP |
| 尾延迟失控 | 少量慢请求拖垮整体 |

**并发不是越大越好**：并发数应由**下游容量**决定，而不是「能开多少」。

### 3.2 `Semaphore`：信号量限流

```python
import asyncio

sem = asyncio.Semaphore(10)          # 最多 10 个同时进行


async def limited_fetch(client, url: str) -> str:
    async with sem:                  # 拿不到就排队等待（不占线程）
        resp = await client.get(url)
        return resp.text
```

| 概念 | 说明 |
| --- | --- |
| `Semaphore(n)` | 内部计数 n |
| `async with sem` | 进入时 `acquire()`（计数 -1，为 0 则挂起等待）；退出时 `release()` |
| 等待代价 | 只是协程挂起，**不消耗线程/CPU** |
| 3.10+ | 可在循环外创建（不再绑定 get_event_loop） |

> 对比线程池：限流 10 的线程池会真有 10 个线程；限流的信号量是「10 个协程在跑，其余挂起」——后者能撑上万个排队任务。

### 3.3 封装：`map_limited`

```python
from typing import Awaitable, Callable, Iterable, TypeVar

T = TypeVar("T")
R = TypeVar("R")


async def map_limited(
    items: Iterable[T],
    fn: Callable[[T], Awaitable[R]],
    limit: int = 10,
) -> list[R]:
    """带并发上限的 map，返回顺序与输入一致。"""
    sem = asyncio.Semaphore(limit)

    async def run(item: T) -> R:
        async with sem:
            return await fn(item)

    return await asyncio.gather(*(run(i) for i in items))
```

两个要点：

1. `gather` 仍会创建全部协程，但**同时执行的只有 `limit` 个**；
2. `gather` 保持输入顺序，所以结果不需要重排。

### 3.4 分批（chunked）：控制「同时在内存里的任务数」

当任务数是 10 万级时，一次创建 10 万个协程对象也有开销：

```python
async def map_chunked(items: list[T], fn, chunk_size: int = 100, limit: int = 10) -> list[R]:
    results: list[R] = []
    for i in range(0, len(items), chunk_size):
        chunk = items[i : i + chunk_size]
        results.extend(await map_limited(chunk, fn, limit))
    return results
```

| 方案 | 控制什么 | 适用 |
| --- | --- | --- |
| `Semaphore` | 同时在执行的请求数 | 任务数 ~千级 |
| 分批 + `Semaphore` | 同时在执行的 + 同时存在的协程对象 | 任务数万级以上 |
| 生产者-消费者队列 | 内存中的待处理量 | 流式/无限任务（下一篇） |

## 4. 重试

### 4.1 朴素重试的三个坑

```python
for _ in range(3):
    try:
        return await call()
    except Exception:          # ❌ 坑 1：什么都重试
        pass                   # ❌ 坑 2：不等待，立即重试
                               # ❌ 坑 3：无上限，最坏时长不可控
```

| 坑 | 后果 |
| --- | --- |
| 什么都重试 | 4xx 参数错误重试 3 次纯浪费；写操作可能重复提交 |
| 立即重试 | 下游正在过载，重试把压力放大 3 倍（重试风暴） |
| 无总预算 | 「3 次 × 30s 超时」= 90s，用户早已超时离开 |

### 4.2 正确写法：退避 + 抖动 + 判定

```python
import asyncio
import random
from typing import Awaitable, Callable, TypeVar

T = TypeVar("T")


async def retry(
    fn: Callable[[], Awaitable[T]],
    *,
    attempts: int = 3,
    base_delay: float = 0.5,
    max_delay: float = 8.0,
    retry_on: tuple[type[Exception], ...] = (asyncio.TimeoutError, OSError),
) -> T:
    """指数退避 + 抖动重试。只对 retry_on 中的异常重试。"""
    for attempt in range(1, attempts + 1):
        try:
            return await fn()
        except retry_on as exc:
            if attempt == attempts:
                raise
            delay = min(max_delay, base_delay * 2 ** (attempt - 1))
            delay *= 0.5 + random.random() / 2          # 抖动：50%~100%
            print(f"[retry] 第 {attempt} 次失败({type(exc).__name__})，{delay:.2f}s 后重试")
            await asyncio.sleep(delay)
    raise AssertionError("unreachable")
```

### 4.3 三次重试的时间线

```
attempt 1 失败 → 等 0.25~0.5s
attempt 2 失败 → 等 0.5~1.0s
attempt 3 失败 → 抛异常
```

| 设计点 | 原因 |
| --- | --- |
| **指数**（`2**(n-1)`） | 给下游恢复时间，避免持续冲击 |
| **抖动**（50%~100%） | 避免所有客户端同一时刻重试（惊群） |
| **上限**（`max_delay`） | 防止指数爆炸到几分钟 |
| **白名单异常** | 只重试网络/超时/5xx，不重试参数错误 |
| **最后一次不再等待** | 少睡一次无用延迟 |

### 4.4 该不该重试？判定表

| 情况 | 重试？ | 说明 |
| --- | --- | --- |
| 连接超时 / 读超时 | ✅ | 网络抖动 |
| 5xx（502/503/504） | ✅ | 服务端瞬时问题（429 也可，但要遵守 `Retry-After`） |
| 429 Too Many Requests | ✅（更长间隔） | 读 `Retry-After` 头 |
| 4xx（400/401/403/404/422） | ❌ | 参数/权限问题，重试结果一样 |
| 写操作（POST 下单/扣款） | ⚠️ 仅幂等 | 无幂等键时重试会重复提交 |
| 本地逻辑异常（`ValueError`/`KeyError`） | ❌ | 代码 bug |
| `asyncio.CancelledError` | ❌ | 必须传播（[02 篇](./02-asyncio核心.md) §6.2） |

> **幂等性**是重试的前提。给写请求带 `Idempotency-Key`，或在 DB 层用唯一约束兜底，才能安全重试。

### 4.5 重试 + 超时的组合

单个请求超时正确写法：

```python
async def call_once():
    async with asyncio.timeout(2.0):        # 单次 2s
        return await client.get(url)
```

重试包裹后，最坏耗时 = `3 × 2s + 退避` ≈ 8s。若业务要求 5s 内必须返回，就要**外层总预算**（下节）。

## 5. 超时预算：双层嵌套

### 5.1 单次超时 vs 整体超时

| 超时层级 | 目的 | 典型值 |
| --- | --- | --- |
| **单次请求** | 一次调用不无限挂 | 2~10s |
| **单批/整体** | 用户等待上限、防止 3 次重试累加超时 | 5~30s |

```python
async def fetch_with_budget(url: str) -> str:
    async with asyncio.timeout(5.0):                     # 外层：总预算 5s
        return await retry(
            lambda: call_with_timeout(url, 2.0),          # 内层：单次 2s
            attempts=3,
            base_delay=0.3,
        )


async def call_with_timeout(url: str, timeout: float) -> str:
    async with asyncio.timeout(timeout):
        resp = await client.get(url)
        return resp.text
```

时序：

```
总预算 5s ────────────────────────────────────────┐
  单次 2s ──────┐                                    │
              退避 0.3s                              │
  单次 2s ──────────────┐                            │
                       总预算到点 → 取消（不再第 3 次）│
```

| 特性 | 说明 |
| --- | --- |
| 外层超时会**取消**内层 | 无论重试到第几次，到点即停 |
| 内层超时被 `retry` 捕获 | 变成「可重试异常」，继续下一次 |
| 两者不冲突 | 一个管「单次」，一个管「整体」 |

### 5.2 并发 + 整体超时

```python
async def batch(urls: list[str]) -> list[str]:
    async with asyncio.timeout(10.0):
        return await map_limited(urls, fetch_one, limit=10)
```

> 注意：`asyncio.timeout` 到点会取消**当前任务**，`gather` 里未完成的任务随之取消——已完成的结丢失。若需要「到点返回部分结果」，需要自己用 `as_completed` + 计时（见 §10 动手题）。

## 6. 连接池：`AsyncClient` 复用

### 6.1 反模式：每次请求新建 client

```python
async def bad(url: str):
    async with httpx.AsyncClient() as client:      # ❌ 每次都新建连接池
        return await client.get(url)
```

后果：

| 问题 | 影响 |
| --- | --- |
| 每次新建 TCP 连接 | TLS 握手开销（几十~几百 ms） |
| 不复用 keep-alive | 高并发时 TIME_WAIT 堆积 |
| 无法统一配置 | 超时/重试/header 到处重复 |
| 连接数不可控 | 每个 client 都有自己的池 |

### 6.2 正确：应用级单例

```python
import httpx

_client: httpx.AsyncClient | None = None


def get_client() -> httpx.AsyncClient:
    global _client
    if _client is None:
        _client = httpx.AsyncClient(
            timeout=httpx.Timeout(connect=2.0, read=10.0, write=10.0, pool=2.0),
            limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
        )
    return _client


async def close_client() -> None:
    global _client
    if _client is not None:
        await _client.aclose()
        _client = None
```

生命周期挂在应用启动/关闭上（FastAPI 的 `lifespan`，阶段 5/04）：

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app):
    yield
    await close_client()          # 应用关闭时释放连接池
```

### 6.3 超时参数含义（httpx）

| 参数 | 含义 | 建议 |
| --- | --- | --- |
| `connect` | 建连超时 | 2~5s |
| `read` | 等待响应数据超时 | 按业务（LLM 可 60s+） |
| `write` | 发送请求体超时 | 10s |
| `pool` | 从连接池取连接的等待超时 | 2~5s（池满时快速失败） |

> `pool` 超时是很多人忽略的一项：高并发下池满，不设就会无限等。

### 6.4 为什么「单例」不等于「一条连接」

`AsyncClient` 内部维护**连接池**：多个并发请求各拿一条连接，用完全归还。单例 client 复用**池**，不是串行化请求。

## 7. 异步缓存

### 7.1 最简单的 TTL 缓存

```python
import time
from dataclasses import dataclass


@dataclass
class _Entry:
    value: object
    expires_at: float


class TTLCache:
    def __init__(self, ttl: float = 60.0):
        self.ttl = ttl
        self._data: dict[str, _Entry] = {}

    def get(self, key: str):
        entry = self._data.get(key)
        if entry is None or entry.expires_at < time.monotonic():
            self._data.pop(key, None)
            return None
        return entry.value

    def set(self, key: str, value) -> None:
        self._data[key] = _Entry(value, time.monotonic() + self.ttl)


cache = TTLCache(ttl=30)
```

> 单进程内缓存的局限：多 worker 之间**不共享**。生产上跨进程共享要用 Redis（阶段 6/04）。

### 7.2 缓存击穿与单飞（singleflight）

场景：缓存刚过期，100 个并发请求同时发现未命中 → 100 次回源。

```python
import asyncio
import time
from typing import Awaitable, Callable, TypeVar

T = TypeVar("T")


class SingleFlightCache:
    def __init__(self, ttl: float = 30.0):
        self.ttl = ttl
        self._value: dict[str, tuple[object, float]] = {}
        self._inflight: dict[str, asyncio.Task] = {}

    async def get_or_load(self, key: str, loader: Callable[[], Awaitable[T]]) -> T:
        hit = self._value.get(key)
        if hit is not None and hit[1] > time.monotonic():
            return hit[0]                       # ① 命中

        task = self._inflight.get(key)
        if task is None:
            task = asyncio.create_task(loader())     # ② 第一个请求负责回源
            self._inflight[key] = task
            try:
                value = await task
                self._value[key] = (value, time.monotonic() + self.ttl)
                return value
            finally:
                self._inflight.pop(key, None)
        else:
            return await asyncio.shield(task)         # ③ 其余请求共享结果
```

| 步骤 | 效果 |
| --- | --- |
| ① 命中 | 直接返回，零 IO |
| ② 首个未命中 | 创建 Task，成为「领队」 |
| ③ 后续未命中 | 等同一个 Task，**不重复回源** |
| `shield(task)` | 防止「一个等待者被取消」把共享 Task 一起取消 |

> 结果：100 个并发请求只产生 **1 次**下游调用。这就是 singleflight。

### 7.3 什么值得缓存

| 适合 | 不适合 |
| --- | --- |
| 配置/字典表/知识库元信息 | 用户私有且强一致的数据 |
| 检索结果（同 query 短时重复） | 计费/库存等写路径 |
| 上游限流严格的外部 API | 分页游标类（key 无限增长） |

> 缓存一定要有 **TTL + 容量上限**，否则内存会无限增长。

## 8. 后台任务与强引用

### 8.1 反模式：丢了引用

```python
async def handler():
    asyncio.create_task(send_audit_log())      # ❌ 引用丢失
```

风险：

| 风险 | 说明 |
| --- | --- |
| 可能被 GC 回收 | 事件循环只持弱引用；任务对象无强引用可能被回收 |
| 异常静默丢失 | 没人 `await` → 只打印 `Task exception was never retrieved` |
| 关闭时被静默取消 | 应用退出时未完成任务被取消，且无处知晓 |

### 8.2 正确：集合持有 + 完成清理

```python
_background: set[asyncio.Task] = set()


def spawn(coro) -> asyncio.Task:
    task = asyncio.create_task(coro)
    _background.add(task)
    task.add_done_callback(_background.discard)
    return task


async def handler():
    spawn(send_audit_log())      # ✅ 强引用，完成即移除
```

```python
async def shutdown():
    if _background:
        await asyncio.gather(*_background, return_exceptions=True)
```

### 8.3 更好的选择：交给框架

| 场景 | 推荐 |
| --- | --- |
| 请求内的小收尾（发通知、写审计） | FastAPI `BackgroundTasks`（阶段 5/04） |
| 长任务（批量导入、重新向量化） | 外部任务队列（Celery/RQ/ARQ，阶段 11） |
| 进程内定时任务 | 独立的调度协程 + 优雅退出 |

> 「fire-and-forget」在 Python 里**没有安全版本**——要么持有引用，要么交给框架/队列。

## 9. 把模式组合起来

生产级的「外部调用」几乎总是这几层叠起来：

```python
async def fetch_embedding(text: str) -> list[float]:
    client = get_client()

    async def once() -> list[float]:
        async with asyncio.timeout(15.0):                 # 单次超时
            resp = await client.post(
                f"{settings.llm_base_url}/embeddings",
                headers={"Authorization": f"Bearer {settings.llm_api_key}"},
                json={"model": "text-embedding-3-small", "input": text},
            )
            resp.raise_for_status()
            return resp.json()["data"][0]["embedding"]

    return await retry(once, attempts=3, base_delay=0.5)   # 重试


async def embed_many(texts: list[str]) -> list[list[float]]:
    async with asyncio.timeout(60.0):                       # 整批预算
        return await map_limited(texts, fetch_embedding, limit=8)   # 限流
```

四层职责：

| 层 | 作用 | 参数来源 |
| --- | --- | --- |
| 限流（`Semaphore`） | 保护下游 | 下游 QPS 配额 |
| 单次超时 | 单请求不挂死 | 下游 P99 × 1.5 |
| 重试 | 扛瞬时故障 | 网络抖动频率 |
| 整批预算 | 保护用户等待 | 接口 SLO |

### 9.1 项目落点

| 位置 | 应套用的层 |
| --- | --- |
| `app/rag/embedding.py` 向量化调用 | 限流 + 超时 + 重试（外部 API 最脆弱） |
| `app/engine/nodes/llm.py` 模型调用 | 读超时放宽（流式），重试**仅限建连阶段**（已开始输出时不能重试） |
| `app/rag/service.py` 检索 | 结果 TTL 缓存 + 单飞（同 query 高频重复） |

> 特别提醒：**流式响应一旦已经推送了 token，就不能重试**——用户已经看到了半截内容。重试只能发生在「尚未产出任何内容」的阶段。

## 10. 与 TypeScript 对照

| Python | TypeScript/Node | 说明 |
| --- | --- | --- |
| `asyncio.Semaphore` | `p-limit(10)` | 语义一致 |
| 手写 `retry` | `p-retry` | 都有退避 + 抖动 |
| `asyncio.timeout` | `AbortSignal.timeout()` | 一致 |
| 单例 `httpx.AsyncClient` | 单例 `axios` 实例 / `undici.Agent` | 都是连接复用 |
| `SingleFlightCache` | `p-memoize` + 自定义 inflight | 需自己实现单飞 |
| `create_task` 持引用 | `void promise`（悬空 promise） | Node 也有未处理拒绝告警 |
| `map_limited` | `Promise.all` + `p-limit` | 一致 |
| `as_completed` | 手写 `Promise.race` 循环 | Python 更顺手 |

> 心智迁移：**限流、重试、超时三件套在任何语言里都是同一个结构**；差异只在 API 名字。

## 11. 验收自测

### 11.1 计算题

某下游接口 P99 = 200ms，你设置「单次超时 2s、重试 3 次、退避 0.5/1.0s」。最坏耗时约多少？如果业务 SLO 是 5s，该怎么改？

<details>
<summary>答案</summary>

最坏 ≈ `2 + 0.5 + 2 + 1.0 + 2 ≈ 7.5s`，**超过 SLO**。

改法：外层加 `asyncio.timeout(5.0)`，或把单次超时降到 1s（`1 + 0.5 + 1 + 1.0 + 1 = 4.5s`）。

</details>

### 11.2 找错

```python
async def fetch_all(urls):
    return await asyncio.gather(*(fetch(u) for u in urls))
```

问题：无并发上限、无超时、无重试、失败会整体抛出。至少改成 `map_limited(urls, fetch, limit=10)` 并加外层预算。

### 11.3 动手题

实现 `batch_with_deadline(urls, deadline=10.0)`：到点返回**已完成**的结果，未完成的取消。

参考实现：

```python
import asyncio
import time


async def batch_with_deadline(urls: list[str], deadline: float = 10.0) -> dict[str, object]:
    started = time.monotonic()
    tasks = {asyncio.create_task(fetch(u)): u for u in urls}
    done: dict[str, object] = {}

    for coro in asyncio.as_completed(list(tasks)):
        remaining = deadline - (time.monotonic() - started)
        if remaining <= 0:
            break
        try:
            result = await asyncio.wait_for(coro, timeout=remaining)
        except (TimeoutError, Exception) as exc:
            done.setdefault("errors", []).append(exc)   # 简化为汇总
            continue
        done[url_of(result)] = result

    for task in tasks:
        if not task.done():
            task.cancel()
    return done
```

> 要点：`as_completed` + 剩余时间做单次 `wait_for`，循环结束后统一 `cancel()` 未完成的。生产代码里建议用 `url → result` 的映射显式保存（示例简化了 `url_of`）。

## 12. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 下游 429/502 雪崩 | 无并发上限 / 无退避 | `Semaphore` + 指数退避 |
| 重试风暴把下游打死 | 立即重试、无抖动 | 退避 + 抖动 + 上限次数 |
| 4xx 也在重试 | 未判定异常类型 | 只重试网络/5xx/429 |
| 写操作重复提交 | 无幂等就重试 | 幂等键或唯一约束 |
| 接口偶发 30s 才返回 | 只有单次超时，重试累加 | 加整体预算 |
| `Too many open files` | 每次新建 client / 无连接池上限 | 单例 client + `Limits` |
| 高并发下大量 `PoolTimeout` | `pool` 超时太短或池太小 | 调 `max_connections`，或加信号量 |
| 缓存过期瞬间打崩下游 | 缓存击穿 | 单飞（singleflight） |
| 缓存内存只增不减 | 无 TTL/容量上限 | TTL + LRU 上限 |
| 后台任务悄悄消失 | `create_task` 丢引用 | 集合持引用 + `done_callback` |
| 流式输出中途重试导致内容重复 | 已在推送后重试 | 仅在未产出时重试 |
| 多 worker 下缓存命中率低 | 进程内缓存不共享 | 用 Redis |

## 13. 本篇小结

- **并发要有上限**：`Semaphore` 限流、分批控制协程对象数量；上限由下游容量决定。
- **重试三要素**：指数退避、随机抖动、可重试判定（且写操作必须幂等）。
- **超时要分两层**：单次超时 + 整体预算；否则「3 次 × 2s」会悄悄击穿 SLO。
- **超时即取消**：外层到点会取消内层任务，别指望「它还在后台跑完」。
- **连接池必须复用**：`AsyncClient` 单例 + `lifespan` 关闭；`pool` 超时别忽略。
- **缓存要防击穿**：TTL 缓存 + singleflight，100 并发只回源 1 次。
- **后台任务必须持引用**：`set` + `add_done_callback`，或交给 `BackgroundTasks`/任务队列。
- **组合顺序**：限流（最外）→ 整批预算 → 重试 → 单次超时（最内）。
- **流式场景**：一旦开始输出就不能重试。
- **下一步**：并发工具箱——锁、队列、生产者-消费者、线程与协程的桥接。
