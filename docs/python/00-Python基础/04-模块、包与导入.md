## 3. 模块：一个 `.py` 文件就是一个模块

### 3.1 最小示例

创建 `D:\practice\py-demo\mathx.py`：

```python
"""一个演示模块。"""

PI = 3.14159


def circle_area(r):
    return PI * r * r


print(f"[mathx] 模块被加载，__name__ = {__name__}")
```

同目录创建 `use_mathx.py`：

```python
import mathx

print(mathx.PI)
print(mathx.circle_area(2))
print(mathx.__name__)
```

运行：

```powershell
python use_mathx.py
```

预期输出：

```
[mathx] 模块被加载，__name__ = mathx
3.14159
12.56636
mathx
```

关键点：**模块被导入时，模块级代码会执行一次**（那个 `print` 就是证据）。函数体不会执行，只有定义。

### 3.2 模块对象与 `__name__`

| 属性 | 含义 |
| --- | --- |
| `__name__` | 模块名；被导入时是模块名，被直接运行时是 `"__main__"` |
| `__file__` | 模块文件路径 |
| `__doc__` | docstring |
| `__dict__` | 模块的命名空间（所有顶层名字） |

```python
import mathx
print(mathx.__file__)          # D:\practice\py-demo\mathx.py
print(sorted(k for k in mathx.__dict__ if not k.startswith("__")))
# ['PI', 'circle_area']
```

> 本项目的 `config.py` 就是用 `__file__` 定位项目目录：
> `_PROJECT_DIR = Path(__file__).resolve().parent.parent`——这样无论从哪个 cwd 启动都能读到同一份 `.env`。

### 3.3 `import` 的四种写法

```python
import mathx                       # ① 导入模块，用 mathx.xxx 访问
import mathx as mx                 # ② 起别名
from mathx import circle_area      # ③ 只导入某个名字
from mathx import circle_area as area
from mathx import *                # ④ 导入全部公开名字（不推荐）
```

对比：

| 写法 | 访问方式 | 评价 |
| --- | --- | --- |
| `import mathx` | `mathx.circle_area` | **最推荐**：来源清晰，不怕重名 |
| `import mathx as mx` | `mx.circle_area` | 名字太长时用（如 `numpy as np`） |
| `from mathx import circle_area` | `circle_area` | 常用，但名字来源不直观 |
| `from mathx import *` | 直接裸名 | **禁止**：污染命名空间、看不出来源、破坏静态分析 |

> 本项目全量使用 `import 模块` 或 `from 模块 import 具体名字`，没有一处 `import *`。

## 4. 导入时发生了什么（首次教学）

以 `import app.config` 为例，Python 依次做：

```
① 查 sys.modules 缓存 —— 有就直接返回（不会重复执行）
② 按 sys.path 顺序找 app/ 目录
③ 找到 app/config.py，编译成字节码（必要时写 __pycache__）
④ 创建模块对象，执行模块级代码
⑤ 把模块对象登记进 sys.modules
⑥ 在当前命名空间绑定名字 app（顶层包）
```

### 4.1 模块只执行一次

```python
import mathx      # 打印一次
import mathx      # 不再打印
import mathx as mx  # 也不再打印
```

原因：第二次导入命中 `sys.modules` 缓存。

```python
import sys
print("mathx" in sys.modules)     # True
```

> 项目里 `settings = Settings()` 写在模块级，所以**全项目共享一个实例**——这正是单例的天然实现方式（阶段 3/02 讲配置时展开）。

### 4.2 `sys.path` 搜索顺序（首次教学）

```python
import sys
for p in sys.path:
    print(p or "<空字符串 = 当前工作目录>")
```

典型输出（Windows + venv）：

```
D:\practice\py-demo          ← 脚本所在目录 或 cwd（由运行方式决定）
C:\Users\...\Python312\python312.zip
C:\Users\...\Python312\DLLs
C:\Users\...\Python312\Lib
C:\Users\...\Python312\Lib\site-packages
D:\practice\py-demo\.venv\Lib\site-packages   ← venv 的包目录
```

查找规则：**按顺序找，第一个匹配的模块胜出**。

| 顺序项 | 来源 | 影响 |
| --- | --- | --- |
| `sys.path[0]` | `python file.py` → 文件所在目录；`python -m` → 当前目录 | 决定了项目根是否在路径里 |
| 标准库路径 | 安装目录 | 内置模块 |
| `site-packages` | 全局 + venv | 第三方包 |
| `PYTHONPATH` | 环境变量 | 额外注入（团队项目慎用） |

> 只有**顶层包所在目录**才会被搜索。若 `app/` 在 `apps/api-py/` 下，则 `sys.path` 必须包含 `apps/api-py/`，`import app.config` 才能成功。

### 4.3 `sys.path[0]` 的两种取值（复习 01 篇）

```powershell
python app/main.py      # sys.path[0] = ...\app\        → import app 失败
python -m app.main      # sys.path[0] = ...\api-py\     → import app 成功
```

这就是「**有包内导入就用 `-m`**」的根本原因。

## 5. 包：带 `__init__.py` 的目录

### 5.1 最小包结构

```
py-demo/
├── shop/
│   ├── __init__.py
│   ├── pricing.py
│   └── inventory.py
└── main.py
```

`shop/__init__.py`：

```python
"""shop 包：演示包结构与导入。"""

from shop.pricing import calc_total

__all__ = ["calc_total"]
```

`shop/pricing.py`：

```python
def calc_total(items):
    return sum(item["price"] * item["qty"] for item in items)
```

`main.py`：

```python
from shop import calc_total

print(calc_total([{"price": 10, "qty": 2}, {"price": 5, "qty": 3}]))   # 35
```

### 5.2 `__init__.py` 的作用（首次教学）

| 作用 | 说明 |
| --- | --- |
| 标识包 | 传统上必须有，否则不是常规包 |
| 初始化 | 包被导入时执行一次（可放版本号、导出） |
| 收口公开 API | 在 `__init__.py` 里 `from ... import ...`，外部只依赖包根 |
| `__all__` | 定义 `from shop import *` 导出哪些名字 |

> **工程建议**：`__init__.py` 尽量**轻**。如果里面写了重逻辑（连数据库、读配置），任何 `import shop.xxx` 都会触发，容易造成启动慢和循环导入。

### 5.3 命名空间包（了解）

PEP 420 允许**没有 `__init__.py`** 的目录也是包（命名空间包）。本项目 `app/` 下各层都带 `__init__.py`，保持传统显式风格，便于工具识别。

### 5.4 导入子模块 vs 导入名字

```python
import shop.pricing                 # 绑定 shop，用 shop.pricing.calc_total
from shop import pricing            # 绑定 pricing
from shop.pricing import calc_total # 绑定 calc_total
```

> `import shop.pricing` 之后，`shop` 会被绑定；`pricing` **不会**直接出现在当前命名空间（除非 `shop/__init__.py` 里导出了它）。

## 6. 绝对导入 vs 相对导入（首次教学）

### 6.1 绝对导入

```python
from app.config import settings
from app.api.auth import router
```

从**包根**写起，与当前文件位置无关。**本项目全部使用绝对导入。**

### 6.2 相对导入

```python
# 在 app/api/auth.py 里
from ..config import settings      # .. 表示上 2 级？不，是上 1 级包 app/
from .deps import get_current_user # . 表示当前包 app/api/
```

规则：

| 写法 | 含义 |
| --- | --- |
| `from . import x` | 当前包 |
| `from .mod import x` | 当前包下的 `mod` |
| `from .. import x` | 上一级包 |

### 6.3 为什么项目选绝对导入

| 维度 | 绝对导入 | 相对导入 |
| --- | --- | --- |
| 可读性 | 一眼看出完整路径 | 要数点数 |
| 重构 | 移动文件时导入路径不变？**会变** | 移动同层文件不改导入 |
| 可执行性 | 支持 `python -m` 与脚本 | **只能在包内使用**，脚本直接运行会报错 |
| 复制代码 | 复制到别处能直接用 | 依赖层级，复制即坏 |

> 相对导入的典型报错：`ImportError: attempted relative import with no known parent package`——因为你用 `python app/api/auth.py` 直接跑了，此时它不属于任何包。这也是坚持用 `-m` 的另一理由。

## 7. `if __name__ == "__main__"`（首次教学）

### 7.1 同一个文件，两种身份

```python
def main():
    print("业务入口")


if __name__ == "__main__":
    main()
```

| 运行方式 | `__name__` | 是否执行 `main()` |
| --- | --- | --- |
| `python tool.py` | `"__main__"` | 执行 |
| `import tool` | `"tool"` | 不执行 |

意义：**让文件既能当脚本跑，又能被当模块导入而不产生副作用**。

### 7.2 不加这个判断会怎样

```python
# bad.py
print("开始执行")
run_everything()      # 导入时就会跑！
```

```python
# 别处
import bad            # 意外触发了整个流程
```

### 7.3 项目实例

完整文件路径：`apps/api-py/app/main.py`（节选）

```python
app = FastAPI(title="mini-dify api-py", version=settings.version)

if __name__ == "__main__":
    import uvicorn

    uvicorn.run("app.main:app", host="127.0.0.1", port=settings.port, reload=True)
```

两个教学点：

1. **`app = FastAPI(...)` 在模块级**：uvicorn 需要 `app.main:app` 这个对象存在，所以创建应用实例必须无条件执行（不能塞进 `if __name__` 里）。
2. **`uvicorn.run` 传的是字符串 `"app.main:app"` 而不是 `app` 对象**：因为 `reload=True` 依赖子进程**重新按字符串导入**模块；传对象在 reload 场景会失效，也不利于多 worker。

> 这也解释了为什么导入位置写成 `from app.api.apps import router as apps_router`——绝对导入 + 别名，避免七个 `router` 重名冲突。

## 8. 循环导入（首次教学）

### 8.1 现象

```python
# a.py
from b import b_func
def a_func(): return "a"

# b.py
from a import a_func
def b_func(): return "b"
```

```python
import a
# ImportError: cannot import name 'a_func' from partially initialized module 'a'
```

原因：`a` 执行到 `from b import b_func` 时开始加载 `b`，`b` 又回头要 `a` 的 `a_func`，但此时 `a` 还没执行到 `def a_func`。

### 8.2 三种解法

| 解法 | 做法 | 适用 |
| --- | --- | --- |
| **① 结构调整**（首选） | 把共用的东西下沉到第三个模块（如 `app/core.py`），两边都依赖它 | 大部分情况 |
| **② 延迟导入** | 把 `import` 放进函数体内，调用时才导入 | 真的无法解耦时 |
| **③ `TYPE_CHECKING`** | 仅类型检查需要时，放进 `if TYPE_CHECKING:` 块 | 只为类型注解 |

示例 ②：

```python
def a_func():
    from b import b_func      # 运行时才导入，打破启动期循环
    return b_func()
```

示例 ③：

```python
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from app.models.app import App   # 仅给类型检查器看，运行时不导入

def handle(app: "App") -> None: ...
```

> 本项目用 **① 分层** 避免了循环导入：`models` 不导入 `api`，`api` 导入 `models`，`engine` 导入 `models`，依赖方向单向。

### 8.3 循环导入是设计信号

出现循环导入，往往意味着**两个模块职责重叠**。先想「该拆出什么」，再考虑延迟导入。

## 9. 模块重载（了解）

```python
import importlib
import mathx

importlib.reload(mathx)
```

只在交互式调试/插件热加载时有意义。**生产代码不要用**：重载不会更新已经 `from mathx import x` 拿到的旧引用，容易产生「一半新一半旧」的诡异状态。

### 10.1 导入关系（单向依赖）

```
main.py
  ├── config.py            （无内部依赖）
  ├── errors.py
  ├── json_response.py
  └── api/*.py
        ├── models/*.py
        ├── engine/*.py
        └── rag/*.py

反向依赖（models 导入 api）不存在 → 无循环导入
```

### 10.2 为什么路由要拆文件

| 好处 | 说明 |
| --- | --- |
| 可读性 | 一个领域一个文件，`main.py` 只负责装配 |
| 可测试性 | 测试可以只导入某个 router |
| 避免巨型 `main.py` | 七个领域合在一起会变成几百行 |

### 10.3 装配模式：`router` 别名

```python
from app.api.apps import router as apps_router
from app.api.auth import router as auth_router
...
app.include_router(apps_router)
```

每个 `api/*.py` 里都定义顶层 `router = APIRouter(...)`，`main.py` 用别名区分。这是 FastAPI 项目的标准装配方式（阶段 5/05 详讲 `APIRouter`）。

## 11. 与 TypeScript / Node 对照

| Python | Node/TS | 说明 |
| --- | --- | --- |
| `mathx.py` 模块 | `mathx.ts` 模块 | 都是一文件一模块 |
| `import mathx` | `import * as mathx from './mathx'` | Python 隐式整模块命名空间 |
| `from mathx import f` | `import { f } from './mathx'` | 接近 |
| `import mathx as mx` | `import * as mx from ...` | 接近 |
| `__init__.py` | `index.ts` | 目录入口 |
| 绝对导入 `app.config` | 路径别名 `@/config` | 都需配置解析根 |
| `sys.path` | `NODE_PATH` / `tsconfig paths` | 模块解析机制 |
| `if __name__ == "__main__"` | `require.main === module` | 同目的：区分入口 |
| `sys.modules` 缓存 | `require.cache` / ESM 缓存 | 模块只执行一次 |
| 循环导入（运行时报错） | 循环依赖（可能 undefined） | 都是设计信号 |

## 13. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'app'` | cwd 不对，或用了 `python app/main.py` | 在包根目录用 `python -m app.main` |
| `attempted relative import with no known parent package` | 直接运行了包内文件 | 用 `-m`；或改绝对导入 |
| `ImportError: cannot import name ... from partially initialized module` | 循环导入 | 拆公共模块 / 延迟导入 / `TYPE_CHECKING` |
| 改代码没生效 | 命中了旧 `.pyc` 或进程未重启 | 删 `__pycache__`；重启服务；`--reload` |
| 导入时意外执行了业务逻辑 | 模块级写了副作用代码 | 放进 `if __name__ == "__main__"` 或函数 |
| 同名模块互相覆盖 | 自己的 `json.py` 遮蔽了标准库 `json` | 不要用标准库名命名文件 |
| `pip` 装的包 import 不到 | 装到了别的解释器 | 用 `python -m pip`；确认 `sys.prefix` 在 venv 内 |
| 包结构变了导入全红 | 移动文件后忘了改导入 | 用 IDE 重构功能；坚持绝对导入便于全局搜索 |
| `__init__.py` 里写了重逻辑导致启动慢 | 导入包即执行 | `__init__.py` 保持轻量，只做导出 |

---

## 14. 本篇小结

- **模块 = `.py` 文件**，导入时执行模块级代码**一次**，之后命中 `sys.modules` 缓存。
- **`sys.path` 决定找哪些目录**：`sys.path[0]` 因运行方式而异（脚本目录 vs 当前目录），这是 `-m` 与直接运行的本质差异。
- **包 = 带 `__init__.py` 的目录**；`__init__.py` 用于标识、初始化和收口公开 API，应保持轻量。
- **绝对导入优先**：项目内一律 `from app.xxx import yyy`；相对导入只在包内且确定用 `-m` 启动时使用。
- **`if __name__ == "__main__"`** 区分「脚本」与「被导入」两种身份；但框架需要的对象（如 `app`）必须放在模块级。
- **循环导入是设计信号**：优先拆公共模块，其次延迟导入，最后才是 `TYPE_CHECKING`。
- **项目结构即依赖方向**：`api → models/engine/rag`，反向不存在，所以本项目没有循环导入。
- **下一步**：异常与文件 IO——`try/except` 的正确姿势、异常链、`with open` 与 `pathlib`。
