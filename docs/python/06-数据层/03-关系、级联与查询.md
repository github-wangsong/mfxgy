## 3. 先画对象图：四种关系

```
User 1 ──── N App 1 ──── N Conversation 1 ──── N Message
  │
  └── 1 Profile                     （一对一语法示例，项目暂无此表）

App N ──── N Tag                    （多对多，中间表 app_tags）
```

| 关系 | 典型例子 | 外键放哪 | 两侧注解 |
| --- | --- | --- | --- |
| **一对多** | `User → App` | 多的一方：`apps.owner_id` | `User.apps: Mapped[list["App"]]` / `App.owner: Mapped["User"]` |
| **多对一** | `App → User` | 同上（就是一对多的反向） | `App.owner: Mapped["User"]` |
| **一对一** | `User → Profile` | 任一方，并加 `unique=True` | `User.profile: Mapped["Profile \| None"]` + `uselist=False` |
| **多对多** | `App ↔ Tag` | 单独的中间表 | 两侧都是 `Mapped[list[...]]` + `secondary=` |

> 口诀：**外键永远在多的一方；`relationship` 两边都要写；多对多必须有中间表。**

## 4. `ForeignKey` 与 `relationship` 的分工

这是 ORM 新手最容易混淆的一点：

| 写法 | 归属 | 作用 | 会进 DDL 吗 |
| --- | --- | --- | --- |
| `ForeignKey("apps.id", ondelete="CASCADE")` | 数据库 | 建外键约束、声明级联删除 | ✅ |
| `index=True` | 数据库 | 给外键列建索引 | ✅ |
| `relationship("App", back_populates="conversations")` | ORM | 生成 `conversation.app` 这个 Python 属性 | ❌ |
| `cascade="all, delete-orphan"` | ORM | 控制 Session 删除父对象时的行为 | ❌ |
| `passive_deletes=True` | ORM | 告诉 ORM「子对象交给数据库级联」 | ❌ |

### 4.1 只有 `ForeignKey`、没有 `relationship`

```python
class Conversation(Base):
    __tablename__ = "conversations"
    app_id: Mapped[str] = mapped_column(
        String, ForeignKey("apps.id", ondelete="CASCADE"), nullable=False, index=True
    )
```

此时数据库有外键，但 Python 里**没有** `conversation.app`。你只能：

```python
app = db.get(App, conversation.app_id)
```

### 4.2 只有 `relationship`、没有 `ForeignKey`

```python
class App(Base):
    conversations: Mapped[list["Conversation"]] = relationship("Conversation")
```

SQLAlchemy 会尝试猜测两表怎么连接；如果没有外键，直接报：

```
NoForeignKeysError: Could not determine join condition between parent/child tables
```

> 结论：**`ForeignKey` 是地基，`relationship` 是楼层。** 先有外键，再写关系。

## 5. 一对多 / 多对一

### 5.1 完整模型：`Conversation` 与 `Message`

**完整文件路径：`apps/api-py/app/models/conversation.py`**

```python
from datetime import datetime
from typing import TYPE_CHECKING

from sqlalchemy import (
    DateTime,
    ForeignKey,
    Integer,
    String,
    Text,
    UniqueConstraint,
    func,
)
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.models.base import Base

if TYPE_CHECKING:
    from app.models.app import App


class Conversation(Base):
    __tablename__ = "conversations"

    id: Mapped[str] = mapped_column(String, primary_key=True)
    app_id: Mapped[str] = mapped_column(
        String, ForeignKey("apps.id", ondelete="CASCADE"), nullable=False, index=True
    )
    owner_id: Mapped[str] = mapped_column(
        String, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True
    )
    title: Mapped[str] = mapped_column(
        String, nullable=False, server_default="新会话"
    )
    created_at: Mapped[datetime] = mapped_column(
        DateTime, nullable=False, server_default=func.now()
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime, nullable=False, default=func.now(), onupdate=func.now()
    )

    # 多对一：一个会话属于一个应用
    app: Mapped["App"] = relationship("App", back_populates="conversations")

    # 一对多：一个会话有多条消息
    messages: Mapped[list["Message"]] = relationship(
        "Message",
        back_populates="conversation",
        cascade="all, delete-orphan",
        passive_deletes=True,
        order_by="Message.seq",
    )


class Message(Base):
    __tablename__ = "messages"
    __table_args__ = (
        UniqueConstraint(
            "conversation_id", "seq", name="uq_messages_conversation_seq"
        ),
    )

    id: Mapped[str] = mapped_column(String, primary_key=True)
    conversation_id: Mapped[str] = mapped_column(
        String,
        ForeignKey("conversations.id", ondelete="CASCADE"),
        nullable=False,
        index=True,
    )
    role: Mapped[str] = mapped_column(String, nullable=False)
    content: Mapped[str] = mapped_column(Text, nullable=False)
    seq: Mapped[int] = mapped_column(Integer, nullable=False)
    run_id: Mapped[str | None] = mapped_column(String, nullable=True)
    created_at: Mapped[datetime] = mapped_column(
        DateTime, nullable=False, server_default=func.now()
    )

    # 多对一：一条消息属于一个会话
    conversation: Mapped["Conversation"] = relationship(
        "Conversation", back_populates="messages"
    )
```

#### 为什么 `messages` 要加 `order_by="Message.seq"`

消息是按 `seq` 递增产生的。如果关系不写 `order_by`，`conversation.messages` 的返回顺序**不保证**——PG 可能按物理顺序返回，看起来「有时对、有时不对」。

```python
# 不写 order_by 时，下面这行可能乱序
print([m.seq for m in conversation.messages])

# 写了 order_by="Message.seq" 后，关系加载自带 ORDER BY
```

> 查询级的 `order_by(...)` 只影响当前查询；关系级的 `order_by` 影响**所有**通过关系加载的场景（包括 `selectinload`）。

#### 为什么 `Message` 要加唯一约束

`(conversation_id, seq)` 唯一约束是 [02 §7](./02-Session生命周期与依赖.md) 中「并发追加消息 → 唯一冲突 → 回滚重试」的前提：

```python
UniqueConstraint("conversation_id", "seq", name="uq_messages_conversation_seq")
```

- 没有唯一约束，两个并发请求可能拿到同一个 `seq`，消息顺序错乱；
- 有了唯一约束，冲突会以 `IntegrityError` 暴露，代码可以重试。

### 5.2 `App` 侧的关系

**完整文件路径：`apps/api-py/app/models/app.py`**

```python
from datetime import datetime
from typing import TYPE_CHECKING, Any

from sqlalchemy import DateTime, ForeignKey, String, func
from sqlalchemy.dialects.postgresql import JSONB
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.models.base import Base

if TYPE_CHECKING:
    from app.models.conversation import Conversation
    from app.models.tag import Tag
    from app.models.user import User


class App(Base):
    __tablename__ = "apps"

    id: Mapped[str] = mapped_column(String, primary_key=True)
    owner_id: Mapped[str] = mapped_column(
        String, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True
    )
    name: Mapped[str] = mapped_column(String, nullable=False)
    description: Mapped[str | None] = mapped_column(String, nullable=True)
    mode: Mapped[str] = mapped_column(
        String, nullable=False, server_default="chatflow"
    )
    created_at: Mapped[datetime] = mapped_column(
        DateTime, nullable=False, server_default=func.now()
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime, nullable=False, default=func.now(), onupdate=func.now()
    )
    graph_json: Mapped[dict[str, Any] | None] = mapped_column(JSONB, nullable=True)
    published_graph_json: Mapped[dict[str, Any] | None] = mapped_column(
        JSONB, nullable=True
    )
    published_at: Mapped[datetime | None] = mapped_column(DateTime(), nullable=True)

    # 多对一：一个应用属于一个用户
    owner: Mapped["User"] = relationship("User", back_populates="apps")

    # 一对多：一个应用有多个会话
    conversations: Mapped[list["Conversation"]] = relationship(
        "Conversation",
        back_populates="app",
        cascade="all, delete-orphan",
        passive_deletes=True,
    )

    # 多对多：一个应用可以有多个标签
    tags: Mapped[list["Tag"]] = relationship(
        "Tag",
        secondary="app_tags",
        back_populates="apps",
        passive_deletes=True,
    )
```

> 字段本身（`server_default`、`JSONB`、应用侧 UUID）已在 [01 §5~§6](./01-SQLAlchemy2.0核心.md) 讲透，这里只补充关系部分。`secondary="app_tags"` 用字符串引用中间表，见 §7。

### 5.3 `User` 侧的关系

**完整文件路径：`apps/api-py/app/models/user.py`（关系节选）**

```python
class User(Base):
    __tablename__ = "users"

    # ... 其他字段见项目模型

    apps: Mapped[list["App"]] = relationship(
        "App",
        back_populates="owner",
        cascade="all, delete-orphan",
        passive_deletes=True,
    )
```

> `back_populates` 两边的字符串必须**严格等于对方属性名**：`App.owner` ↔ `User.apps`，`Conversation.app` ↔ `App.conversations`，`Message.conversation` ↔ `Conversation.messages`。

### 5.4 方向判断口诀

拿到两个模型，按这三步写：

1. **找外键**：`ForeignKey` 写在哪个表，哪个表就是「多」的一方。
2. **多的一方写单数**：`Mapped["Parent"]` + `relationship("Parent", back_populates="children")`。
3. **一的一方写复数**：`Mapped[list["Child"]]` + `relationship("Child", back_populates="parent")`。

| 关系 | 多的一方 | 一的一方 |
| --- | --- | --- |
| `User → App` | `App.owner` | `User.apps` |
| `App → Conversation` | `Conversation.app` | `App.conversations` |
| `Conversation → Message` | `Message.conversation` | `Conversation.messages` |

### 5.5 为什么要用 `TYPE_CHECKING` + 字符串

模型之间会互相引用：

```
app.py        → 需要 Conversation
conversation.py → 需要 App
```

如果两边都在运行时 `import`，就会循环导入。标准写法：

```python
from typing import TYPE_CHECKING

if TYPE_CHECKING:                 # 只在类型检查时导入，运行时不执行
    from app.models.conversation import Conversation

class App(Base):
    conversations: Mapped[list["Conversation"]] = relationship("Conversation", ...)
```

| 写法 | 运行时 | 类型检查 | 说明 |
| --- | --- | --- | --- |
| `Mapped[list["Conversation"]]` | 字符串，不导入 | ✅ | SQLAlchemy 用 registry 解析 |
| `relationship("Conversation")` | 字符串，不导入 | ✅ | 同上 |
| `if TYPE_CHECKING: import ...` | 不执行 | ✅ | 给 mypy / IDE 用 |
| 顶部直接 `import` | 执行 | ✅ | 容易循环导入 |

> 前提：**所有模型都必须被导入一次**（通常由 `app/models/__init__.py` 统一收口），否则 SQLAlchemy 找不到 `"Conversation"`：

```
InvalidRequestError: Expression 'Conversation' failed to locate a name
```

### 5.6 常见映射错误

| 报错 | 原因 | 解决 |
| --- | --- | --- |
| `InvalidRequestError: Mapper ... has no property 'conversation'` | `back_populates` 拼错 | 两边字符串与属性名严格一致 |
| `NoForeignKeysError` | 两表之间没有 FK | 先加 `ForeignKey` |
| `AmbiguousForeignKeysError` | 两张表之间有多个 FK | `relationship(..., foreign_keys=[Conversation.app_id])` |
| `Expression 'X' failed to locate a name` | 模型没被导入 / 名字拼错 | 在 `models/__init__.py` 导入全部模型 |
| `ArgumentError: Mapped[list[X]]` 解析失败 | 用了 `List` 或漏了字符串 | 用 `Mapped[list["X"]]` |

## 6. 一对一

一对一 = 一对多 + **外键唯一**。

> 说明：项目当前没有 `profiles` 表，下面是纯语法示例；理解后可以套到「用户设置」「应用发布配置」等场景。

```python
class User(Base):
    __tablename__ = "users"

    # ... 其他字段

    profile: Mapped["Profile | None"] = relationship(
        "Profile",
        back_populates="user",
        uselist=False,          # 关键：返回单个对象，而不是 list
    )


class Profile(Base):
    __tablename__ = "profiles"

    id: Mapped[str] = mapped_column(String, primary_key=True)
    user_id: Mapped[str] = mapped_column(
        String,
        ForeignKey("users.id", ondelete="CASCADE"),
        unique=True,            # 关键：一个用户最多一个 profile
        nullable=False,
    )
    bio: Mapped[str | None] = mapped_column(Text, nullable=True)

    user: Mapped["User"] = relationship("User", back_populates="profile")
```

| 关键点 | 不写会怎样 |
| --- | --- |
| `unique=True` | 变成一对多，`user.profile` 可能拿到多条 |
| `uselist=False` | 即使唯一，也可能返回 list（取决于注解推断） |
| `Mapped["Profile \| None"]` | 允许用户没有 profile；若写 `Mapped["Profile"]`，类型上不允许空 |

> SQLAlchemy 2.0 能从 `Mapped[Profile | None]` 推断 `uselist=False`，但**显式写出来**更不容易误解。

## 7. 多对多

### 7.1 中间表

**完整文件路径：`apps/api-py/app/models/app_tag.py`**

```python
from sqlalchemy import Column, ForeignKey, String, Table

from app.models.base import Base

app_tags = Table(
    "app_tags",
    Base.metadata,
    Column(
        "app_id",
        String,
        ForeignKey("apps.id", ondelete="CASCADE"),
        primary_key=True,
    ),
    Column(
        "tag_id",
        String,
        ForeignKey("tags.id", ondelete="CASCADE"),
        primary_key=True,
    ),
)
```

| 设计点 | 说明 |
| --- | --- |
| 复合主键 `(app_id, tag_id)` | 防止同一个应用重复绑定同一个标签 |
| 两个 `ondelete="CASCADE"` | 删除应用或标签时，中间表行自动清理 |
| 用 `Table` 而不是模型 | 中间表没有业务字段时，最简写法 |
| 不写 `id` 自增列 | 复合主键已经足够，省一列 |

### 7.2 两侧 `relationship`

**完整文件路径：`apps/api-py/app/models/tag.py`**

```python
from datetime import datetime
from typing import TYPE_CHECKING

from sqlalchemy import DateTime, ForeignKey, String, func
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.models.app_tag import app_tags
from app.models.base import Base

if TYPE_CHECKING:
    from app.models.app import App


class Tag(Base):
    __tablename__ = "tags"

    id: Mapped[str] = mapped_column(String, primary_key=True)
    name: Mapped[str] = mapped_column(String, unique=True, nullable=False)
    owner_id: Mapped[str] = mapped_column(
        String, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True
    )
    created_at: Mapped[datetime] = mapped_column(
        DateTime, nullable=False, server_default=func.now()
    )

    apps: Mapped[list["App"]] = relationship(
        "App",
        secondary=app_tags,
        back_populates="tags",
        passive_deletes=True,
    )
```

`App` 侧（已在上面的完整模型里）：

```python
tags: Mapped[list["Tag"]] = relationship(
    "Tag",
    secondary=app_tags,
    back_populates="apps",
    passive_deletes=True,
)
```

> `App` 侧用的是 `secondary="app_tags"` 字符串；确保 `app_tag.py` 已被导入（通常由 `models/__init__.py` 收口），否则会报 `NoReferencedTableError`。

### 7.3 多对多的三个坑

| 坑 | 说明 | 正确做法 |
| --- | --- | --- |
| 给多对多加 `cascade="all, delete-orphan"` | 删除一个标签可能把应用也删掉 / 语义混乱 | 多对多**不要**用 `delete-orphan`，只靠中间表的 DB 级联 |
| 中间表没有复合主键 | 同一个 `(app_id, tag_id)` 可以插入多次 | 两列都 `primary_key=True` |
| 中间表有业务字段（如 `created_at`、`weight`） | `Table` 无法映射额外字段 | 改用「关联对象模式」：定义一个 `AppTag` 模型，两侧用 `relationship` 指向它 |

#### 关联对象模式（需要额外字段时）

```python
class AppTag(Base):
    __tablename__ = "app_tags"

    app_id: Mapped[str] = mapped_column(
        String, ForeignKey("apps.id", ondelete="CASCADE"), primary_key=True
    )
    tag_id: Mapped[str] = mapped_column(
        String, ForeignKey("tags.id", ondelete="CASCADE"), primary_key=True
    )
    created_at: Mapped[datetime] = mapped_column(
        DateTime, nullable=False, server_default=func.now()
    )

    app: Mapped["App"] = relationship("App", back_populates="tag_links")
    tag: Mapped["Tag"] = relationship("Tag", back_populates="app_links")
```

此时 `App.tags` 不能直接用 `secondary`，需要通过 `App.tag_links` 再取 `link.tag`，或者用 `association_proxy` 封装。**没有额外字段时不要上这套**，复杂度不值得。

### 7.4 多对多查询

```python
# 1) EXISTS：查「带 production 标签」的应用（不会产生重复行）
stmt = select(App).where(App.tags.any(Tag.name == "production"))

# 2) JOIN：需要同时按标签过滤并预加载标签
stmt = (
    select(App)
    .join(App.tags)
    .where(Tag.name == "production")
    .options(selectinload(App.tags))
    .distinct()
)

# 3) 预加载：列表页一次性把标签查出来
stmt = select(App).options(selectinload(App.tags))
```

> `any()` 生成 `EXISTS` 子查询，不会因为一个应用有多个标签而返回重复行；`join` 需要 `distinct()` 去重。二者选一个即可。

## 8. `cascade` 与 `ondelete`：两层删除

### 8.1 两层各管什么

| 层 | 参数 | 执行者 | 触发时机 | 跨栈（Prisma / 裸 SQL）生效 |
| --- | --- | --- | --- | --- |
| **数据库层** | `ForeignKey(..., ondelete="CASCADE")` | PostgreSQL | 删除父行时 | ✅ |
| **ORM 层** | `relationship(cascade="all, delete-orphan")` | SQLAlchemy | `session.delete(parent)`、从集合移除子对象 | ❌ |
| **ORM 层** | `passive_deletes=True` | SQLAlchemy | 删除父对象时，**不加载未加载的子集合** | — |
| **ORM 层** | `passive_deletes="all"` | SQLAlchemy | 完全禁用 ORM 级联，全部交给数据库 | — |

> 记住一句话：**数据库级联是「谁都拦不住」的；ORM 级联只对 `Session` 的操作生效。**

### 8.2 `cascade` 选项表

| 选项 | 含义 |
| --- | --- |
| `save-update` | 父对象加入 Session 时，子对象也加入 |
| `merge` | `Session.merge()` 时级联 |
| `expunge` | 父对象被移出 Session 时，子对象也移出 |
| `delete` | 删除父对象时，删除子对象 |
| `delete-orphan` | 子对象从集合中移除时，标记为删除（隐含 `delete`） |
| `refresh-expire` | 父对象刷新/过期时，子对象同步 |
| `all` | 上面除 `delete-orphan` 外的全部 |

```python
cascade="all, delete-orphan"      # 最常用：父删子删 + 移出集合也删
```

> `delete-orphan` 只适用于「子对象只能有一个父对象」的一对多 / 一对一；**多对多不要用**。

### 8.3 `delete-orphan` 的真实语义

```python
app.conversations.remove(conversation)
db.commit()
# conversation 会被 DELETE（因为 delete-orphan）
```

| 不写 `delete-orphan` | 写了 `delete-orphan` |
| --- | --- |
| 从集合移除只把 `app_id` 置空（列可空时） | 子对象被标记删除 |
| 列 `NOT NULL` 时可能直接报错 | 子对象随父对象一起清理 |

### 8.4 `passive_deletes` 到底省了什么

默认（`passive_deletes=False`）删除父对象时，SQLAlchemy 会：

1. `SELECT` 出所有子对象；
2. 对每个子对象 `UPDATE ... SET parent_id = NULL`（列可空）或 `DELETE`；
3. 最后 `DELETE` 父对象。

子对象多时，这就是典型 N+1。

`passive_deletes=True`：

- 如果子集合**尚未加载**：不 `SELECT`，直接 `DELETE` 父对象，让数据库的 `ON DELETE CASCADE` 清理子表；
- 如果子集合**已经加载**：ORM 仍可能按 `cascade` 处理已加载的对象。

`passive_deletes="all"`：

- 即使子集合已加载，也完全不走 ORM 级联——只发父对象的 `DELETE`，子表全部交给数据库。

| 配置 | 未加载子集合 | 已加载子集合 |
| --- | --- | --- |
| 默认 | `SELECT` 子对象 + 逐条处理 | 逐条处理 |
| `passive_deletes=True` | 只 `DELETE` 父对象（DB 级联） | 可能逐条处理 |
| `passive_deletes="all"` | 只 `DELETE` 父对象 | 只 `DELETE` 父对象 |

> **重要前提**：数据库里必须真的有 `ON DELETE CASCADE`。如果 DDL 由 Prisma 拥有，就要在 Prisma schema 写 `onDelete: Cascade`；SQLAlchemy 模型里的 `ondelete` 只在 SQLAlchemy 自己建表时生效。

### 8.5 四种组合的后果

| 数据库 `ondelete` | ORM 配置 | 删除 `App` 时会发生什么 |
| --- | --- | --- |
| `CASCADE` | `cascade="all, delete-orphan"` + `passive_deletes=True` | 未加载子集合 → 只删父行，DB 级联；已加载 → ORM 可能逐条删 |
| `CASCADE` | `passive_deletes="all"` | 只删父行，子表全部由 DB 级联 |
| `CASCADE` | 默认（无 cascade、无 passive） | ORM `SELECT` 子对象并尝试 `SET NULL` / `DELETE`，可能 N+1 |
| 无 | `cascade="all, delete-orphan"` | ORM 逐条删子对象；裸 SQL / Prisma 删除父行会 FK 冲突 |
| 无 | 默认 | 删除父行可能 FK 冲突（或子表 `parent_id` 被置空） |

### 8.6 项目推荐写法

```python
conversations: Mapped[list["Conversation"]] = relationship(
    "Conversation",
    back_populates="app",
    cascade="all, delete-orphan",   # 移出集合也删
    passive_deletes=True,           # 删除父对象时信任 DB 级联
)
```

Prisma 侧对应：

```prisma
model Conversation {
  id     String @id
  appId  String
  app    App    @relation(fields: [appId], references: [id], onDelete: Cascade)
}
```

> 双栈共表的铁律：**DDL 归 Prisma，SQLAlchemy 里的 `ondelete` 只是映射声明。** 只在 Python 模型里写 `ondelete="CASCADE"`，但 Prisma 没写，数据库里就没有这个约束——删除父行时照样报 FK 冲突。

### 8.7 删除的 SQL 对比

```python
app = db.get(App, app_id)
db.delete(app)
db.commit()
```

**配置正确（DB 级联 + `passive_deletes=True`，且未加载子集合）**：

```sql
DELETE FROM apps WHERE apps.id = %(id)s
```

只有这一条 `DELETE`，子表由 PostgreSQL 级联清理。

**配置为默认（无 `passive_deletes`）**：

```sql
SELECT ... FROM conversations WHERE conversations.app_id IN (...)
UPDATE conversations SET app_id = NULL WHERE conversations.id = ...
DELETE FROM apps WHERE apps.id = ...
```

子对象越多，SQL 越多。

## 9. 加载策略

### 9.1 `lazy` 的五种取值

| `lazy` | 行为 | SQL 数量 | 适用 |
| --- | --- | --- | --- |
| `"select"`（默认） | 访问属性时才查 | 1 + N | 单条详情、子对象很少 |
| `"selectin"` | 先查父对象，再用第二条 `IN` 查子对象 | 2 | 集合，推荐 |
| `"joined"` | 主查询 `LEFT OUTER JOIN` 一起查 | 1 | 多对一 / 一对一 |
| `"raise"` | 访问未加载关系直接报错 | — | 异步、严格模式 |
| `"noload"` | 永不加载，返回空集合 | 0 | 几乎不用（危险） |
| `"dynamic"` | 返回 `Query` 对象（legacy） | — | 2.0 不推荐，改用 `select` |

### 9.2 默认 `select`：N+1 的源头

```python
apps = db.scalars(select(App)).all()
for app in apps:
    print(app.name, len(app.conversations))
```

SQL：

```sql
SELECT ... FROM apps;
SELECT ... FROM conversations WHERE conversations.app_id = 'a1';
SELECT ... FROM conversations WHERE conversations.app_id = 'a2';
...
```

1 条父查询 + N 条子查询 = **N+1**。

### 9.3 `selectinload`：集合的首选

```python
from sqlalchemy.orm import selectinload

stmt = select(App).options(selectinload(App.conversations))
apps = db.scalars(stmt).all()
```

SQL：

```sql
SELECT ... FROM apps;
SELECT ... FROM conversations WHERE conversations.app_id IN ('a1', 'a2', ...);
```

固定 2 条，父对象有多少都不怕。

### 9.4 `joinedload`：多对一 / 一对一的首选

```python
from sqlalchemy.orm import joinedload

stmt = select(Conversation).options(joinedload(Conversation.app))
conversations = db.scalars(stmt).all()
```

SQL：

```sql
SELECT ... FROM conversations
LEFT OUTER JOIN apps ON apps.id = conversations.app_id;
```

1 条查询。多对一时不会产生重复的父对象（每个 `Conversation` 只有一个 `App`）。

### 9.5 `selectinload` vs `joinedload`

| 维度 | `selectinload` | `joinedload` |
| --- | --- | --- |
| SQL 条数 | 2（父 + 子） | 1 |
| 行数膨胀 | 不会 | 集合会产生笛卡尔积，需要去重 |
| 集合 + `LIMIT` | 安全 | 需要子查询包裹，开销更大 |
| 多对一 / 一对一 | 可用 | **最合适** |
| 多对多 | 可用（父 + 中间表 JOIN） | 可用但行数膨胀更明显 |
| 大父集合 | `IN` 参数可能过多 | JOIN 更稳 |

> 默认选型：**集合用 `selectinload`，多对一用 `joinedload`。** 不要给同一个关系同时写两者。

### 9.6 `contains_eager`：复用你手写的 JOIN

如果你已经手写 `JOIN` 并按子表过滤，再让 ORM 发第二条查询就浪费了：

```python
from sqlalchemy.orm import contains_eager

stmt = (
    select(Conversation)
    .join(Conversation.messages)
    .where(Message.role == "user")
    .options(contains_eager(Conversation.messages))
    .order_by(Message.seq)
)
```

| 点 | 说明 |
| --- | --- |
| 必须已有显式 `JOIN` | `contains_eager` 不会自己加 JOIN |
| 只加载 JOIN 到的子行 | 这里只加载 `role="user"` 的消息 |
| 不要和 `selectinload` 同时用 | 同一个关系只能选一种加载方式 |

### 9.7 `lazy="raise"`：把隐式懒加载变成显式错误

```python
conversations: Mapped[list["Conversation"]] = relationship(
    "Conversation",
    back_populates="app",
    cascade="all, delete-orphan",
    passive_deletes=True,
    lazy="raise",
)
```

访问未预加载的 `app.conversations` 会直接报：

```
InvalidRequestError: 'App.conversations' ... lazy='raise'
```

> 好处：在开发阶段就把「忘了预加载」暴露出来，而不是上线后变成 N+1 或 `MissingGreenlet`。查询时用 `selectinload(App.conversations)` 显式覆盖即可。

## 10. N+1 问题：从复现到修复

### 10.1 复现

```python
# ❌ N+1
apps = db.scalars(select(App)).all()
for app in apps:
    print(app.name, len(app.conversations))
```

### 10.2 修复

```python
# ✅ 2 条 SQL
stmt = select(App).options(selectinload(App.conversations))
apps = db.scalars(stmt).all()
for app in apps:
    print(app.name, len(app.conversations))
```

### 10.3 嵌套关系

```python
stmt = (
    select(App)
    .options(
        selectinload(App.conversations).selectinload(Conversation.messages)
    )
)
```

SQL 条数：

| 层级 | 查询 |
| --- | --- |
| 1 | `apps` |
| 2 | `conversations`（`WHERE app_id IN (...)`） |
| 3 | `messages`（`WHERE conversation_id IN (...)`） |

> 嵌套 `selectinload` 是链式的：`selectinload(A.b).selectinload(B.c)`，不是两个平级的 `selectinload`。

### 10.4 如何发现 N+1

| 方法 | 做法 |
| --- | --- |
| `echo=True` | 开发环境打开，肉眼数 SQL |
| 日志 | `logging.getLogger("sqlalchemy.engine").setLevel(logging.INFO)` |
| 性能分析 | 接口耗时随列表长度线性增长 |
| 测试 | 用事件监听统计 `before_cursor_execute` 次数（阶段 9 展开） |

### 10.5 序列化时的 N+1 / `DetachedInstanceError`

```python
# ❌ 在 Session 关闭后访问关系
app = db.get(App, app_id)
db.close()
return AppResponse(conversation_count=len(app.conversations))
```

两种结局：

- 懒加载触发 SQL → Session 已关闭 → `DetachedInstanceError`；
- 异步 Session → `MissingGreenlet`。

正确做法：**在 Session 存活期内完成 DTO 转换**。

```python
def to_app_response(app: App) -> AppResponse:
    return AppResponse(
        id=app.id,
        name=app.name,
        conversation_count=len(app.conversations),
    )

# 视图内：Session 还活着
return to_app_response(app)
```

### 10.6 大集合的边界

`selectinload` 会把所有父 id 塞进 `IN (...)`：

| 风险 | 说明 | 解决 |
| --- | --- | --- |
| 父对象太多 | `IN` 参数过多，SQL 变长 | 分页父对象；分批查询 |
| 子对象太多 | 一次加载几十万条消息 | 子集合单独分页，不要全量预加载 |
| 内存 | 身份映射持有所有对象 | 限制 `limit`，或只查需要的列 |

> 列表页只加载「列表需要的子数据」；详情页再按需加载全量子对象。

## 11. 查询进阶

### 11.1 按关系过滤：`any()` / `has()` / `join`

```python
# 一对多：存在标题包含「预算」的会话
stmt = select(App).where(
    App.conversations.any(Conversation.title.ilike("%预算%"))
)

# 多对一：会话所属应用属于当前用户
stmt = select(Conversation).where(
    Conversation.app.has(App.owner_id == user.id)
)

# JOIN + distinct：需要同时按子表过滤
stmt = (
    select(App)
    .join(App.conversations)
    .where(Conversation.title.ilike("%预算%"))
    .distinct()
)
```

| 写法 | 生成的 SQL | 是否重复 |
| --- | --- | --- |
| `any()` | `EXISTS (...)` | 不会 |
| `has()` | `EXISTS (...)` | 不会 |
| `join()` | `INNER JOIN` | 可能重复，需 `distinct()` |

### 11.2 聚合：`outerjoin` + `group_by` + `having`

```python
from sqlalchemy import func

stmt = (
    select(
        App.id,
        App.name,
        func.count(Conversation.id).label("conversation_count"),
    )
    .outerjoin(App.conversations)
    .group_by(App.id, App.name)
    .order_by(func.count(Conversation.id).desc())
)

rows = db.execute(stmt).all()
for app_id, name, count in rows:
    print(app_id, name, count)
```

| 点 | 说明 |
| --- | --- |
| `outerjoin` 而不是 `join` | 没有会话的应用也要出现，计数为 `0` |
| `count(Conversation.id)` | 只统计非 NULL 的子行；`outerjoin` 的空行不计入 |
| `group_by(App.id, App.name)` | PG 要求 SELECT 的非聚合列都出现在 GROUP BY |
| `having` | 过滤聚合结果，例如 `.having(func.count(Conversation.id) >= 3)` |

### 11.3 分页：`limit` + `offset` + 稳定排序

```python
stmt = (
    select(Conversation)
    .where(Conversation.app_id == app_id)
    .order_by(Conversation.updated_at.desc(), Conversation.id.desc())
    .limit(20)
    .offset(offset)
)
```

| 点 | 说明 |
| --- | --- |
| 排序必须有唯一兜底 | 只按 `updated_at` 排序，同一时间戳的顺序不稳定；加 `id` 做 tiebreaker |
| `offset` 越大越慢 | 深分页用 keyset：`WHERE updated_at < cursor ORDER BY updated_at DESC LIMIT 20` |
| 总数单独查 | `select(func.count()).select_from(Conversation).where(...)` |

### 11.4 `exists()`

```python
from sqlalchemy import exists

stmt = select(exists().where(Conversation.app_id == app_id))
has_conversation = db.scalar(stmt)   # True / False
```

> 比 `select(Conversation.id).limit(1)` 更语义化，PG 会优化成半连接。

### 11.5 只查部分列

```python
stmt = select(Conversation.id, Conversation.title).where(
    Conversation.app_id == app_id
)
rows = db.execute(stmt).all()        # [(id, title), ...]
```

> 只查部分列时用 `execute()`；查整个实体才用 `scalars()`（见 [01 §7.2](./01-SQLAlchemy2.0核心.md)）。

### 11.6 可组合的查询函数

```python
def app_list_query(owner_id: str):
    return select(App).where(App.owner_id == owner_id)


stmt = (
    app_list_query(user.id)
    .options(selectinload(App.conversations))
    .order_by(App.created_at.desc())
    .limit(20)
)
```

> 把「基础过滤」封装成返回 `Select` 的函数，调用方继续 `.options()` / `.order_by()` / `.limit()`，比拼接字符串更安全。

## 12. 异步 Session 下的关系加载

> 本篇只讲「关系在异步下怎么用」；`asyncpg` 引擎与 `AsyncSession` 的完整搭建在下一篇「04 Alembic 迁移与异步驱动」展开。

### 12.1 `MissingGreenlet`

```python
from sqlalchemy.ext.asyncio import AsyncSession

async with AsyncSession(engine) as db:
    app = await db.get(App, app_id)
    print(app.conversations)      # ❌ MissingGreenlet
```

原因：`relationship` 默认 `lazy="select"`，访问 `app.conversations` 会触发同步 SQL；异步 Session 用的是 greenlet，不能在此时阻塞事件循环。

```
sqlalchemy.exc.MissingGreenlet: greenlet_spawn has not been called;
can't call await_only() here. Was IO attempted in an unexpected place?
```

### 12.2 显式预加载

```python
from sqlalchemy.orm import selectinload

async def get_app(db: AsyncSession, app_id: str) -> App | None:
    stmt = (
        select(App)
        .where(App.id == app_id)
        .options(selectinload(App.conversations))
    )
    return (await db.scalars(stmt)).one_or_none()
```

### 12.3 `session.get()` 也能带 `options`

```python
app = await db.get(
    App,
    app_id,
    options=[selectinload(App.conversations)],
)
```

> `AsyncSession.get()` 的 `options` 参数与 `select()` 的 `.options()` 等价。

### 12.4 `refresh` 补加载

```python
app = await db.get(App, app_id)          # 不加载 conversations
await db.refresh(app, ["conversations"]) # 显式补加载
```

> 适合「先拿到对象，再决定要不要加载关系」的场景；列表查询仍然优先 `selectinload`。

### 12.5 用 `lazy="raise"` 提前暴露问题

```python
conversations: Mapped[list["Conversation"]] = relationship(
    "Conversation",
    back_populates="app",
    lazy="raise",
)
```

异步场景下推荐：

| 配置 | 效果 |
| --- | --- |
| `lazy="raise"` | 忘记预加载时立刻报错，不进入 `MissingGreenlet` 的难排查状态 |
| `lazy="selectin"` | 每次查询都自动预加载，省心但可能加载过多 |
| 默认 `lazy="select"` | 同步 Session 可用；异步 Session 容易踩 `MissingGreenlet` |

### 12.6 异步删除

```python
app = await db.get(App, app_id)
await db.delete(app)
await db.commit()
```

配合 `passive_deletes=True` + DB 级联，未加载的子集合不会被逐条删除。

> 异步 Session 不能使用 `session.query()`（legacy）；一律用 `select()` + `await db.execute/scalars`。

## 13. 项目实战：会话列表与删除

### 13.1 会话列表（同步版，项目当前用法）

**完整文件路径：`apps/api-py/app/conversations/service.py`（节选）**

```python
from sqlalchemy import select
from sqlalchemy.orm import Session, selectinload

from app.models import Conversation


def list_conversations(
    db: Session, app_id: str, limit: int = 50
) -> list[Conversation]:
    stmt = (
        select(Conversation)
        .where(Conversation.app_id == app_id)
        .options(selectinload(Conversation.messages))
        .order_by(Conversation.updated_at.desc(), Conversation.id.desc())
        .limit(limit)
    )
    return list(db.scalars(stmt).all())
```

### 13.2 会话详情

```python
def get_conversation(
    db: Session, conversation_id: str
) -> Conversation | None:
    stmt = (
        select(Conversation)
        .where(Conversation.id == conversation_id)
        .options(selectinload(Conversation.messages))
    )
    return db.scalars(stmt).one_or_none()
```

> 用 `one_or_none()` 而不是 `first()`：主键查询如果返回多条，说明数据已经异常，应该暴露而不是掩盖。

### 13.3 删除应用

```python
from app.models import App


def delete_app(db: Session, app: App) -> None:
    db.delete(app)
    db.commit()
```

前提：

1. `App.conversations` 写了 `passive_deletes=True`；
2. Prisma schema 里 `Conversation.app` 写了 `onDelete: Cascade`；
3. 删除前没有加载 `app.conversations`（否则 ORM 可能逐条删）。

### 13.4 DTO 转换必须在 Session 内

```python
def to_conversation_response(conversation: Conversation) -> ConversationResponse:
    return ConversationResponse(
        id=conversation.id,
        title=conversation.title,
        messages=[
            MessageResponse(
                id=m.id,
                role=m.role,
                content=m.content,
                seq=m.seq,
            )
            for m in conversation.messages
        ],
    )
```

> 如果 `messages` 没预加载，这一行会触发懒加载；Session 已关闭就 `DetachedInstanceError`。所以：**查询时 `selectinload`，转换时 Session 还活着。**

### 13.5 SQL 验证

开发环境临时打开 SQL 日志：

```python
import logging

logging.basicConfig()
logging.getLogger("sqlalchemy.engine").setLevel(logging.INFO)
```

调用 `list_conversations` 后，预期看到：

```sql
SELECT ... FROM conversations WHERE conversations.app_id = ... ORDER BY ... LIMIT ...;
SELECT ... FROM messages WHERE messages.conversation_id IN (...) ORDER BY messages.seq;
```

**2 条 SELECT**，没有「每条会话再查一次消息」。

## 14. 与 Prisma / NestJS 对照

| SQLAlchemy | Prisma | 说明 |
| --- | --- | --- |
| `relationship` + `back_populates` | `@relation(fields: [...], references: [...])` | 关系声明 |
| `ForeignKey(ondelete="CASCADE")` | `onDelete: Cascade` | 数据库级联 |
| `cascade="all, delete-orphan"` | `onDelete: Cascade` + 业务层删除 | ORM 级联 vs DB 级联 |
| `passive_deletes=True` | 默认依赖 DB 级联 | Prisma 不维护 ORM 级联 |
| `selectinload` | `include: { conversations: true }` | 预加载，避免 N+1 |
| `joinedload` | `relationLoadStrategy: "join"` / `include` | 两种策略 |
| `select(...).join(...)` | `where: { conversations: { some: ... } }` | 关系过滤 |
| `any()` | `some` | EXISTS 语义 |
| `outerjoin` + `group_by` | `groupBy` | 聚合 |
| `limit` / `offset` | `take` / `skip` | 分页 |

Prisma 写法：

```ts
const apps = await prisma.app.findMany({
  where: {
    ownerId: userId,
    conversations: { some: { title: { contains: '预算' } } },
  },
  include: {
    conversations: {
      include: { messages: true },
    },
  },
  orderBy: { createdAt: 'desc' },
  take: 20,
  skip: 0,
});
```

| 点 | Prisma | SQLAlchemy |
| --- | --- | --- |
| 预加载 | `include` 默认用额外查询（类似 `selectinload`） | `selectinload` |
| JOIN 策略 | `relationLoadStrategy: "join"` | `joinedload` / `contains_eager` |
| 关系过滤 | `some` / `every` / `none` | `any()` / `has()` / `~any()` |
| 级联删除 | `onDelete: Cascade`（DB 层） | `ondelete="CASCADE"` + `passive_deletes` |
| 事务 | `$transaction` | `Session.commit/rollback` |

> 关键差异：**Prisma 没有「ORM 级联」这一层，删除行为几乎完全由数据库约束决定；SQLAlchemy 则同时有 ORM 级联与 DB 级联。** 双栈共表时，以 Prisma 的 `onDelete` 为准，Python 侧用 `passive_deletes` 对齐。

## 15. 验收自测

### 15.1 判断

1. `relationship()` 会在数据库里创建外键吗？
2. `selectinload` 加载一个集合通常发几条 SQL？
3. `joinedload` 加载集合时有什么代价？
4. `passive_deletes=True` 的作用是什么？
5. 异步 Session 里访问未预加载的关系会怎样？

<details>
<summary>答案</summary>

1. ❌ 不会；外键由 `ForeignKey` 创建。
2. 2 条：父对象 1 条 + 子对象 `IN` 查询 1 条。
3. 会产生 JOIN 行数膨胀，集合 + `LIMIT` 还需要子查询包裹，开销更大。
4. 删除父对象时，不加载未加载的子集合，交给数据库 `ON DELETE CASCADE` 清理。
5. 触发 `MissingGreenlet`（隐式懒加载在异步里不允许）。

</details>

### 15.2 找错

```python
class App(Base):
    __tablename__ = "apps"

    conversations: Mapped[list["Conversation"]] = relationship("Conversation")
```

问题：

1. 没有 `back_populates`，`Conversation.app` 不存在，关系是单向的；
2. 没有 `ForeignKey` 的配合说明（`Conversation.app_id` 必须存在）；
3. 没有 `cascade` / `passive_deletes`，删除父对象时可能逐条 `UPDATE` / `DELETE`；
4. 没有 `order_by`（如果业务依赖顺序）；
5. 没有 `TYPE_CHECKING` 导入，mypy 可能找不到 `Conversation`。

### 15.4 运行实验脚本

**完整文件路径：`apps/api-py/scripts/relations_lab.py`**

```python
import logging
import uuid

from sqlalchemy import select
from sqlalchemy.orm import selectinload

from app.db import SessionLocal
from app.models import App, Conversation, Message, User

logging.basicConfig()
logging.getLogger("sqlalchemy.engine").setLevel(logging.INFO)


def main() -> None:
    with SessionLocal() as db:
        user = db.scalars(select(User)).first()
        if user is None:
            print("数据库里没有 user，请先注册一个用户再运行")
            return

        app = App(id=str(uuid.uuid4()), owner_id=user.id, name="relation-lab")
        conversation = Conversation(
            id=str(uuid.uuid4()),
            app_id=app.id,
            owner_id=user.id,
            title="关系实验",
        )
        message = Message(
            id=str(uuid.uuid4()),
            conversation_id=conversation.id,
            role="user",
            content="hello",
            seq=1,
        )
        db.add_all([app, conversation, message])
        db.commit()

        stmt = (
            select(App)
            .where(App.id == app.id)
            .options(
                selectinload(App.conversations).selectinload(
                    Conversation.messages
                )
            )
        )
        loaded = db.scalars(stmt).one()
        print("app:", loaded.name)
        print("conversations:", len(loaded.conversations))
        print("messages:", len(loaded.conversations[0].messages))

    # 新开一个 Session：确保 conversations 没有被加载，
    # 这样才能观察到 passive_deletes + DB 级联的效果。
    with SessionLocal() as db:
        app_to_delete = db.get(App, app.id)
        db.delete(app_to_delete)
        db.commit()

        print("conversation deleted:", db.get(Conversation, conversation.id) is None)
        print("message deleted:", db.get(Message, message.id) is None)


if __name__ == "__main__":
    main()
```

## 16. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `Mapper ... has no property 'conversation'` | `back_populates` 拼错 | 两边字符串与属性名严格一致 |
| `Expression 'Conversation' failed to locate a name` | 模型没被导入 | 在 `models/__init__.py` 导入全部模型 |
| `NoForeignKeysError` | 两表之间没有外键 | 先写 `ForeignKey` |
| `AmbiguousForeignKeysError` | 同一对表有多个 FK | `relationship(..., foreign_keys=[...])` |
| 循环导入 | 模型互相 `import` | `TYPE_CHECKING` + 字符串前向引用 |
| 列表接口 N+1 | 默认 `lazy="select"` | `selectinload` / `joinedload` |
| `MissingGreenlet` | 异步 Session 隐式懒加载 | 查询时 `selectinload`，或 `refresh` |
| `DetachedInstanceError` | Session 关闭后访问关系 | Session 内转 DTO，或预加载 |
| 删除父对象很慢 | 默认逐条 `UPDATE` / `DELETE` 子对象 | DB `ondelete="CASCADE"` + `passive_deletes=True` |
| 删除父对象报 FK 冲突 | 数据库没有 `ON DELETE CASCADE` | 在 Prisma schema 补 `onDelete: Cascade` |
| 多对多删标签把应用删了 | 给多对多写了 `delete-orphan` | 去掉 `delete-orphan`，只靠中间表级联 |
| 中间表出现重复行 | 没有复合主键 | 两列都 `primary_key=True` |
| 一对多返回多条 | 一对一忘了 `unique=True` | 外键加 `unique=True` |
| `joinedload` + `limit` 很奇怪 | 集合 + JOIN 行数膨胀 | 集合改用 `selectinload` |
| `selectinload` 参数过多 | 父对象太多，`IN` 太长 | 分页父对象 / 分批查询 |
| 消息顺序不稳定 | 没写 `order_by` | 关系写 `order_by="Message.seq"`，或查询排序 |
| `lazy="dynamic"` 报 deprecation | 2.0 不推荐 | 改用 `select()` 查询 |
| `Mapped[list[X]]` 报解析错误 | 用了 `List` 或漏了字符串 | `Mapped[list["X"]]` |

## 17. 本篇小结

- **`ForeignKey` 管数据库，`relationship` 管对象**；外键永远在多的一方。
- **双向关系用 `back_populates`**：`App.owner ↔ User.apps`、`App.conversations ↔ Conversation.app`、`Conversation.messages ↔ Message.conversation`。
- **循环导入用 `TYPE_CHECKING` + 字符串前向引用**；所有模型必须在 `models/__init__.py` 统一导入。
- **一对多用 `Mapped[list["Child"]]`，多对一用 `Mapped["Parent"]`，一对一加 `unique=True` + `uselist=False`，多对多用 `secondary` 中间表**。
- **多对多不要用 `delete-orphan`**；中间表用复合主键 + 两侧 `ondelete="CASCADE"`。
- **`cascade` 是 ORM 级，`ondelete` 是 DB 级**；跨栈删除只有 DB 级联靠得住。
- **`passive_deletes=True` 只跳过未加载的子集合**；`"all"` 连已加载的也不管，完全交给 DB。
- **DDL 归 Prisma**：Python 模型里的 `ondelete` 只是声明，Prisma schema 没写 `onDelete: Cascade` 就没有真正的级联。
- **集合用 `selectinload`，多对一用 `joinedload`**；手写 JOIN 用 `contains_eager`。
- **N+1 的典型信号**：列表长度越大接口越慢；`echo=True` 能看到 1 + N 条 SQL。
- **异步 Session 不能隐式懒加载**：`MissingGreenlet` 的解法是查询时 `selectinload` / `joinedload`，或 `refresh` 补加载。
- **DTO 转换要在 Session 存活期内完成**，否则关系懒加载会变成 `DetachedInstanceError`。
- **分页要稳定排序**：`order_by(updated_at.desc(), id.desc())`，不要只按时间。
- **下一步**：Alembic 迁移与异步驱动——把模型变成真正的 DDL，并用 `asyncpg` 跑起来。
