## 3. 索引是成本决策

### 3.1 一句话原理

```
没有索引：逐行扫描（Seq Scan），读完整张表
有索引：先查索引定位行，再取行（可能还要回表）
```

索引不是「免费的加速器」，它用**写放大 + 空间 + 维护成本**换读性能。

| 维度 | 建索引 | 不建 |
| --- | --- | --- |
| 读 | 快（高选择率时） | 慢 |
| 写 | 慢（每次维护索引） | 快 |
| 空间 | 变大 | 小 |
| 低频查询 | 不值得 | 正确 |

> 判断标准：**这条查询够不够高频、够不够慢、过滤条件够不够「挑」**。三者都满足才建。

### 3.2 选择率

```
选择率 = 命中行数 / 总行数
```

| 选择率 | 优化器倾向 | 例子 |
| --- | --- | --- |
| 很低（如 0.1%） | Index Scan | 按主键、按唯一邮箱 |
| 中等（1% ~ 10%） | Bitmap Heap Scan | 按状态 + 时间范围 |
| 很高（> 20%） | Seq Scan | 查「未删除」几乎全表 |

> 所以「`status != 'done'` 没走索引」不一定是索引失效，而是**走索引更慢**。

### 3.3 B-tree 的三个数字

| 指标 | 数量级 |
| --- | --- |
| 页大小 | 8 KB（PG 默认） |
| 单页可存索引项 | 数百 |
| 3 层可索引行数 | 千万 ~ 上亿 |

树高每增加一层，就是多一次随机 IO——这就是「索引要尽量窄」的原因。

## 4. PostgreSQL 的五种索引

| 类型 | 结构 | 适合 | 不适合 |
| --- | --- | --- | --- |
| B-tree | 平衡树 | 等值、范围、排序、前缀匹配 | 数组包含、全文 |
| Hash | 哈希表 | 纯等值 | 范围、排序 |
| GIN | 倒排 | JSONB、数组、全文检索 | 范围 |
| GiST | 通用搜索树 | 几何、范围类型、模糊匹配 | 普通等值 |
| BRIN | 块范围摘要 | 超大表的时序数据 | 随机分布 |

```sql
-- B-tree（默认）
CREATE INDEX ix_apps_owner_created ON apps (owner_id, created_at DESC);

-- Hash（只等值）
CREATE INDEX ix_users_email_hash ON users USING hash (email);

-- GIN（JSONB）
CREATE INDEX ix_apps_graph_gin ON apps USING gin (graph_json jsonb_path_ops);

-- BRIN（时序大表）
CREATE INDEX ix_messages_created_brin ON messages USING brin (created_at);
```

> 项目里 95% 的索引都是 B-tree；GIN 只给 JSONB / 数组 / 全文；BRIN 只在「按时间追加大表」时考虑。

## 5. 读执行计划

### 5.1 `EXPLAIN` vs `EXPLAIN ANALYZE`

| 命令 | 是否执行 | 拿到什么 |
| --- | --- | --- |
| `EXPLAIN` | ❌ | 预估计划与成本 |
| `EXPLAIN ANALYZE` | ✅ **真执行** | 真实耗时、真实行数 |
| `EXPLAIN (ANALYZE, BUFFERS)` | ✅ | 再加缓存命中/磁盘读 |

> `EXPLAIN ANALYZE` 会真的跑 SQL。**在线上先加 `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`**，或只对只读查询用。

### 5.2 一个真实例子

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name
  FROM apps
 WHERE owner_id = 'user-1'
 ORDER BY created_at DESC
 LIMIT 20;
```

```
Limit  (cost=0.42..8.44 rows=20 width=32) (actual time=0.030..0.045 rows=20 loops=1)
  ->  Index Scan using ix_apps_owner_created on apps
        (cost=0.42..4021.00 rows=10000 width=32) (actual time=0.025..0.038 rows=20 loops=1)
        Index Cond: (owner_id = 'user-1'::text)
        Buffers: shared hit=5
Planning Time: 0.120 ms
Execution Time: 0.060 ms
```

| 字段 | 怎么读 |
| --- | --- |
| `cost=0.42..8.44` | 启动代价..总代价（相对单位，不是毫秒） |
| `rows=20` | 优化器**预估**返回行数 |
| `actual rows=20` | 真实行数；与预估差 10 倍以上要 `ANALYZE` |
| `loops=1` | 节点执行次数（嵌套循环里内表会大于 1） |
| `Buffers: shared hit=5` | 命中缓存页数；`read` 才是磁盘读 |
| `Index Cond` | 用于定位的索引条件 |
| `Filter` | 取到行之后再过滤（说明索引没完全覆盖条件） |

### 5.3 常见扫描节点

| 节点 | 含义 | 何时出现 |
| --- | --- | --- |
| `Seq Scan` | 全表顺序扫描 | 无索引 / 选择率太高 / 小表 |
| `Index Scan` | 沿索引逐行取 | 选择率低、需要排序 |
| `Index Only Scan` | 只读索引 | 覆盖索引 + 可见性地图 |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | 先建位图再按页取行 | 中等选择率、多条件 |
| `Sort` | 显式排序 | 索引不满足 `ORDER BY` |
| `Hash Join` / `Merge Join` / `Nested Loop` | 连接算法 | 取决于表大小与索引 |

> `Sort` 出现在 `LIMIT` 下面且数据量大，通常是「索引顺序不匹配 `ORDER BY`」——把排序列放进联合索引。

### 5.4 `Index Only Scan` 为什么还读堆

```
Index Only Scan  (actual rows=20 loops=1)
  Heap Fetches: 1200
```

`Heap Fetches` 不为 0，说明可见性地图没覆盖这些页——**表还没 VACUUM**。索引里虽然有值，但 PG 不敢确定行对当前事务可见，只能回堆确认。

> 修复：`VACUUM (ANALYZE) 表名`；长期靠 `autovacuum`。

## 6. 索引设计六条

### 6.1 列顺序：等值在前，范围在后，排序跟着等值

需求：

```sql
SELECT id, title
  FROM conversations
 WHERE app_id = 'a1' AND user_id = 'u1'
   AND created_at >= now() - interval '7 days'
 ORDER BY created_at DESC
 LIMIT 20;
```

正确索引：

```sql
CREATE INDEX ix_conv_app_user_created
    ON conversations (app_id, user_id, created_at DESC);
```

| 列 | 角色 |
| --- | --- |
| `app_id` | 等值 |
| `user_id` | 等值 |
| `created_at` | 范围 + 排序（放最后） |

> 如果把 `created_at` 放中间，后面的列就无法再用于定位。

### 6.2 覆盖索引：`INCLUDE` vs 放进键

```sql
-- 方案 A：把 title 放进索引键（会参与排序与定位）
CREATE INDEX ix_conv_cover_a ON conversations (app_id, created_at DESC, title);

-- 方案 B：INCLUDE（只存值，不参与定位）
CREATE INDEX ix_conv_cover_b ON conversations (app_id, created_at DESC) INCLUDE (title);
```

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| A | 兼容旧版本 | 索引键变宽，可能影响排序与前缀匹配 |
| B | 语义清晰、键更窄 | 需要 PG 11+ |

> `INCLUDE` 里的列**不能**用于 `WHERE` 定位，只用于「免回表」。

### 6.3 部分索引

```sql
-- 只索引「已发布」的应用（占比可能只有 1%）
CREATE INDEX ix_apps_published
    ON apps (owner_id, published_at DESC)
 WHERE published_at IS NOT NULL;
```

| 收益 | 前提 |
| --- | --- |
| 索引小、写入轻 | 查询必须带同样的 `WHERE` 条件，否则用不上 |

### 6.4 表达式索引

```sql
-- 查询按邮箱小写匹配
CREATE INDEX ix_users_email_lower ON users (lower(email));

SELECT * FROM users WHERE lower(email) = 'a@b.com';   -- ✅ 命中
SELECT * FROM users WHERE email = 'A@B.COM';          -- ❌ 不命中
```

> 表达式索引要求查询**写法与索引表达式完全一致**。这也是「列上套函数会失效」的根因。

### 6.5 冗余索引要删

| 冗余组合 | 原因 |
| --- | --- |
| `(a)` 与 `(a, b)` | 前者可被后者覆盖（最左前缀） |
| `(a, b)` 与 `(b, a)` | 只在两种查询模式都高频时才都保留 |
| 唯一索引与普通索引同列 | 唯一索引已能等值查找 |

```sql
-- 找长期没人用的索引
SELECT relname AS table, indexrelname AS index, idx_scan
  FROM pg_stat_user_indexes
 WHERE idx_scan = 0
 ORDER BY pg_relation_size(indexrelid) DESC;
```

> `idx_scan = 0` 也可能是统计周期问题；先观察再删，别直接下手。

### 6.6 索引数量

| 表类型 | 建议 |
| --- | --- |
| 读多写少 | 5 ~ 8 个 |
| 写多（消息、事件） | 3 ~ 5 个，优先覆盖核心查询 |
| 日志/时序 | 2 ~ 3 个 + BRIN |

## 7. 项目实战：四类查询

### 7.1 会话列表（等值 + 排序 + 分页）

```sql
SELECT id, title, created_at
  FROM conversations
 WHERE app_id = 'a1'
 ORDER BY created_at DESC, id DESC
 LIMIT 20;
```

```sql
CREATE INDEX ix_conversations_app_created
    ON conversations (app_id, created_at DESC, id DESC);
```

> 排序键加上 `id` 是为了**稳定分页**：同一毫秒创建的两条记录也有确定顺序。

### 7.2 消息分页（会话内序号）

模型里已有 `UniqueConstraint(conversation_id, seq)`，它同时是一个可用的 B-tree 索引：

```sql
SELECT id, role, content
  FROM messages
 WHERE conversation_id = 'c1' AND seq > 100
 ORDER BY seq
 LIMIT 50;
```

> 复合唯一约束的左前缀 `(conversation_id)` + `seq` 正好支持这个查询，不需要额外索引。

### 7.3 JSONB 查询（GIN）

```sql
-- 图里是否包含某个节点 id
SELECT id FROM apps
 WHERE graph_json @> '{"nodes":[{"id":"n1"}]}'::jsonb;
```

```sql
CREATE INDEX ix_apps_graph_gin ON apps USING gin (graph_json jsonb_path_ops);
```

| 运算符 | 索引 |
| --- | --- |
| `@>` / `<@` | GIN（`jsonb_path_ops` 更小更快） |
| `->>` 取字段后比较 | 需要**表达式索引**，如 `((graph_json ->> 'mode'))` |
| `jsonb_path_query` | 视表达式而定，常需函数索引 |

> 高频按某个固定字段过滤时，别只建 GIN——加一个表达式 B-tree 更稳。

### 7.4 向量检索（pgvector）

```sql
CREATE INDEX ix_chunks_embedding_hnsw
    ON knowledge_chunks USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

SELECT id, content
  FROM knowledge_chunks
 ORDER BY embedding <=> :query_vec
 LIMIT 8;
```

| 参数 | 含义 |
| --- | --- |
| `m` | 每个节点的连接数（越大召回高、内存大） |
| `ef_construction` | 建索引时的搜索宽度（越大越准、构建越慢） |
| `ef_search` | 查询时宽度（会话级 `SET hnsw.ef_search = 100`） |

> HNSW 是**近似**检索：召回率与延迟要调参权衡；数据量小直接用顺序扫描更准。

## 8. SQLAlchemy 里声明与验证

### 8.1 在模型上声明

**完整文件路径：`apps/api-py/app/models/conversation.py`（节选）**

```python
from sqlalchemy import Index

class Conversation(Base):
    __tablename__ = "conversations"
    __table_args__ = (
        Index("ix_conversations_app_created", "app_id", "created_at"),
    )
```

| 写法 | 注意 |
| --- | --- |
| `Index("名字", "列1", "列2")` | 列用字符串，避免类属性顺序问题 |
| `Index(..., postgresql_using="gin")` | 方言参数 |
| `Index(..., postgresql_where=text("published_at IS NOT NULL"))` | 部分索引 |
| `Index(..., postgresql_ops={"embedding": "vector_cosine_ops"})` | 向量索引 |

> 声明后必须**生成迁移**（04 篇），否则模型与库不一致，`alembic check` 会报错。

### 8.2 看真实执行计划

```python
from sqlalchemy import text

def explain(db, sql: str, params: dict | None = None) -> str:
    rows = db.execute(
        text(f"EXPLAIN (ANALYZE, BUFFERS) {sql}"), params or {}
    ).all()
    return "\n".join(row[0] for row in rows)
```

```python
print(explain(db, """
    SELECT id, name FROM apps
     WHERE owner_id = :owner
     ORDER BY created_at DESC
     LIMIT 20
""", {"owner": "user-1"}))
```

| 要点 | 说明 |
| --- | --- |
| 别拼用户输入 | 这里的 `sql` 必须是代码内常量 |
| `ANALYZE` 会执行 | 写操作要包事务回滚 |
| 异步 Session | `await db.execute(...)`，其余相同 |

## 9. 统计信息与维护

### 9.1 为什么计划会「突然变了」

优化器靠**统计信息**估算行数。统计过期 → 估算错 → 选错计划。

| 现象 | 处理 |
| --- | --- |
| 刚导入大量数据后变慢 | `ANALYZE 表名` |
| 某列分布极不均匀 | 提高该列统计目标 |
| 计划里 `rows` 与 `actual` 差很多 | 先 `ANALYZE`，再看是否需要表达式索引 |

```sql
ALTER TABLE apps ALTER COLUMN mode SET STATISTICS 500;
ANALYZE apps;
```

### 9.2 autovacuum 与膨胀

| 概念 | 说明 |
| --- | --- |
| dead tuple | 被删除/更新的旧版本，等待回收 |
| bloat | 表/索引膨胀，扫描变慢、空间变大 |
| autovacuum | 自动清理；长事务会阻止它 |
| `VACUUM FULL` | 重写表，**锁表**，别在线上随便跑 |
| `REINDEX CONCURRENTLY` | 在线重建索引 |

```sql
-- 看表的死元组比例
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0 / greatest(n_live_tup + n_dead_tup, 1), 2) AS dead_pct
  FROM pg_stat_user_tables
 ORDER BY n_dead_tup DESC
 LIMIT 10;
```

> 长事务 = autovacuum 的敌人（02 篇讲过）。一个 30 分钟的报表事务，能让整表膨胀。

## 10. 定位慢 SQL

### 10.1 `pg_stat_statements`

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT round(total_exec_time::numeric, 1) AS total_ms,
       calls,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       rows,
       left(query, 80) AS query
  FROM pg_stat_statements
 ORDER BY total_exec_time DESC
 LIMIT 10;
```

| 看法 | 说明 |
| --- | --- |
| 按 `total_exec_time` 排 | 找「最贵」的，不一定是「最慢」的 |
| 按 `mean_exec_time` 排 | 找「单次很慢」的 |
| 看 `calls` | 高频小查询也可能拖垮整体 |

### 10.2 日志与 `auto_explain`

```sql
-- 记录超过 200ms 的语句
ALTER SYSTEM SET log_min_duration_statement = '200ms';
SELECT pg_reload_conf();

-- 自动记录慢查询的执行计划
LOAD 'auto_explain';
SET auto_explain.log_min_duration = '200ms';
SET auto_explain.log_analyze = on;
```

> 生产上先开慢日志，再有针对性地 `EXPLAIN`。**不要**在生产随手 `EXPLAIN ANALYZE` 写操作。

## 11. 分页：`OFFSET` 与 keyset

### 11.1 深分页为什么慢

```sql
-- 第 5001 页：先扫 100000 行，再丢掉前 100000 行
SELECT * FROM messages
 WHERE conversation_id = 'c1'
 ORDER BY seq
 LIMIT 20 OFFSET 100000;
```

```
Limit
  ->  Index Scan（实际读了 100020 行，只返回 20 行）
```

### 11.2 keyset 分页

```sql
-- 第一页
SELECT id, seq, content FROM messages
 WHERE conversation_id = 'c1'
 ORDER BY seq
 LIMIT 20;

-- 下一页：带上上一页最后一行的 seq
SELECT id, seq, content FROM messages
 WHERE conversation_id = 'c1' AND seq > 120
 ORDER BY seq
 LIMIT 20;
```

| 要点 | 说明 |
| --- | --- |
| 排序键必须能唯一确定顺序 | `seq` 唯一；若用 `created_at` 要加 `id` |
| 不能跳页 | 只能「上一页/下一页」 |
| 适合无限滚动 | 聊天、Feed、日志 |

### 11.3 SQLAlchemy 写法

```python
def list_messages(db, conversation_id: str, after_seq: int = 0, limit: int = 50):
    stmt = (
        select(Message)
        .where(Message.conversation_id == conversation_id, Message.seq > after_seq)
        .order_by(Message.seq)
        .limit(limit)
    )
    return list(db.scalars(stmt))
```

> 返回体里带 `next_cursor = rows[-1].seq`，前端下次带上即可。

## 12. 与 Prisma 对照

| 目的 | SQLAlchemy / PG | Prisma |
| --- | --- | --- |
| 建索引 | `Index(...)` + 迁移 | `@@index([a, b])` |
| 唯一索引 | `UniqueConstraint(...)` | `@@unique([a, b])` |
| 部分索引 | `postgresql_where` | 原生 SQL / `migrate` 手写 |
| 表达式索引 | `Index("...", text("lower(email)"))` | 原生 SQL |
| 查询计划 | `EXPLAIN` / `pg_stat_statements` | 同样走 PG，工具链无差别 |
| 分页 | `limit` + keyset | `take` + `skip`（深翻同样慢） |

> ORM 只负责「生成 SQL」，**优化永远发生在 SQL 层**。Prisma 的 `skip` 和 `OFFSET` 一样会深翻慢。

## 13. 验收自测

### 13.1 判断

1. 索引越多，查询一定越快吗？
2. `EXPLAIN` 会执行 SQL 吗？
3. 联合索引 `(a, b, c)` 能支持 `WHERE b = ?` 吗？
4. `Index Only Scan` 一定不读堆表吗？
5. 部分索引在查询不带同样条件时能用吗？
6. `status != 'done'` 不走索引，一定是索引失效吗？

<details>
<summary>答案</summary>

1. ❌ 写放大、空间、优化器负担都会变差。
2. ❌ 只估算；`EXPLAIN ANALYZE` 才执行。
3. ❌ 缺最左列，用不上。
4. ❌ 还要看可见性地图；`Heap Fetches` 不为 0 就回堆了。
5. ❌ 必须带相同的 `WHERE` 条件，否则优化器不会选它。
6. ❌ 选择率太高的查询，全表扫描可能更快，这是正确决策。

</details>

### 13.2 找错

```sql
CREATE INDEX ix_bad ON conversations (created_at, app_id);
```

查询：

```sql
SELECT * FROM conversations
 WHERE app_id = 'a1'
 ORDER BY created_at DESC
 LIMIT 20;
```

**问题**：`app_id` 是等值条件却放在第二列，违反「等值在前」；`created_at` 放第一列会让索引先按时间全局排序，`app_id` 无法用于定位。

**改法**：

```sql
CREATE INDEX ix_conv_app_created ON conversations (app_id, created_at DESC, id DESC);
```

## 14. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 建了索引却没走 | 列顺序错 / 选择率太高 / 统计过期 | 调列顺序、`ANALYZE`、看 `EXPLAIN` |
| `LIKE '%x%'` 用不上索引 | 前导通配符 | 全文检索 / trigram（`pg_trgm`） |
| 函数条件不走索引 | 列被包裹 | 表达式索引 |
| 索引体积巨大 | 把大字段放进键 | 用 `INCLUDE` 或只索引必要列 |
| `Index Only Scan` 仍慢 | `Heap Fetches` 高 | `VACUUM` / 调 autovacuum |
| 导入数据后查询变慢 | 统计信息过期 | `ANALYZE` |
| 深分页越来越慢 | `OFFSET` 扫描并丢弃 | keyset 分页 |
| 部分索引没生效 | 查询缺 `WHERE` 条件 | 查询与索引条件保持一致 |
| 唯一约束和索引重复 | 以为要单独建 | 唯一约束自带索引 |
| 索引建了但写入变慢 | 索引过多 | 删冗余索引 |
| JSONB `->>` 查询慢 | GIN 不支持该写法 | 表达式 B-tree 索引 |
| 向量检索召回低 | `ef_search` 太小 / 数据未归一化 | 调参、统一距离度量 |
| 迁移里索引名冲突 | 没设命名约定 | 见 04 篇 `naming_convention` |
| 在线建大索引锁写 | 普通 `CREATE INDEX` | `CONCURRENTLY` + `autocommit_block()` |

## 15. 本篇小结

- **索引是成本决策**：选择率、查询频率、写入代价三者一起看。
- **B-tree 是默认答案**；GIN 给 JSONB/全文/数组，BRIN 给时序大表，Hash 只做等值。
- **读计划三步**：看扫描节点 → 对比 `rows` 与 `actual rows` → 看 `Buffers` / `Heap Fetches`。
- **列顺序口诀**：等值在前、范围在后、排序列跟着等值列；最后补唯一列保证分页稳定。
- **覆盖索引**优先用 `INCLUDE`；部分索引与表达式索引都要「查询写法匹配」。
- **统计信息与 VACUUM** 是计划稳定的前提；长事务会拖垮 autovacuum。
- **慢 SQL 靠数据找**：`pg_stat_statements` + 慢日志 + `auto_explain`，不要猜。
- **分页用 keyset**；`OFFSET` 只适合浅页。
- **ORM 不负责优化**：索引声明进模型与迁移，验证永远在 SQL 层。
