**验收标准**

| # | 检查项 | 预期 |
| --- | --- | --- |
| 1 | 不可重复读 | 会话 A 两次读同一行，会话 B 在中间提交，RC 下读到不同值 |
| 2 | 可重复读 | 切到 RR 后两次读一致；更新冲突时报 `40001` |
| 3 | 行锁 | `FOR UPDATE` 后另一个会话的更新被阻塞，直到提交 |
| 4 | 跳过锁 | 两个 worker 同时领取任务，各自拿到不同行 |
| 5 | 死锁 | 两个会话交叉加锁，PG 报 `40P01` 并回滚一个 |
| 6 | 超时 | 被阻塞的语句在 `lock_timeout` 到点后失败，而不是一直等 |
| 7 | 幂等 | 并发插入同一 `(conversation_id, seq)` 只有一个成功，另一个返回已有行 |
| 8 | 租约 | worker 崩溃后，过期租约被其他 worker 回收并重新执行 |

## 3. 并发写会出什么问题

### 3.1 四类异常

| 异常 | 场景 | 后果 |
| --- | --- | --- |
| 脏读 | 读到别人未提交的数据 | 别人回滚 → 你基于幻觉做决策 |
| 不可重复读 | 同一事务两次读同一行，值变了 | 事务内逻辑不一致 |
| 幻读 | 同一范围两次查，行数变了 | 统计/校验错 |
| 丢失更新 | 两人同时「读-改-写」，后写覆盖前写 | 数据被静默覆盖 |

### 3.2 丢失更新的真实例子

```
时刻  T1                          T2
t1    SELECT credits = 100
t2                                SELECT credits = 100
t3    UPDATE credits = 100 - 10
t4                                UPDATE credits = 100 - 20   ← 用旧值算的
结果  credits = 80（少扣了 10）
```

> 这不是「数据库的 bug」，而是**应用层读-算-写**的经典竞态。解法见 §9 与 §10。

### 3.3 SQL 标准隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| Read Uncommitted | 可能 | 可能 | 可能 |
| Read Committed | ❌ | 可能 | 可能 |
| Repeatable Read | ❌ | ❌ | 标准里可能（PG 实际不会） |
| Serializable | ❌ | ❌ | ❌ |

| 数据库 | 默认 |
| --- | --- |
| PostgreSQL | **Read Committed** |
| MySQL InnoDB | Repeatable Read |

> 面试常问「PG 默认级别是什么」——答读已提交，并补一句「MySQL 默认可重复读」，对比很加分。

## 4. PostgreSQL 的 MVCC

### 4.1 行的两个隐藏字段

```
xmin：创建这行版本的事务 id
xmax：删除/更新这行版本的事务 id（0 表示未删除）
```

| 操作 | 实际发生 |
| --- | --- |
| `UPDATE` | 不修改原行，而是写一个**新版本**，旧版本 `xmax` 指向当前事务 |
| `DELETE` | 给旧版本打上 `xmax`，不是立刻物理删除 |
| `SELECT` | 按快照判断哪个版本「对我可见」 |

> 所以 PG 的更新 = 插入新版本 + 标记旧版本；清理靠 `VACUUM`（05 篇讲过膨胀）。

### 4.2 读已提交 vs 可重复读

| 级别 | 快照粒度 | 表现 |
| --- | --- | --- |
| Read Committed | **每条语句**开始时取新快照 | 同一事务两次查询可能不同 |
| Repeatable Read | **整个事务**共用第一个快照 | 两次查询一致；更新冲突时报错 |
| Serializable | RR + SSI 冲突检测 | 冲突时主动 abort（`40001`） |

### 4.3 可重复读下的「更新冲突」

```sql
-- 会话 A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT credits FROM accounts WHERE id = 1;   -- 100

-- 会话 B
UPDATE accounts SET credits = 90 WHERE id = 1;
COMMIT;

-- 会话 A
UPDATE accounts SET credits = 80 WHERE id = 1;
-- ERROR: could not serialize access due to concurrent update (SQLSTATE 40001)
```

> RR 不是「不会冲突」，而是「冲突时让你重来」。**应用必须捕获 `40001` 并重试整个事务**。

### 4.4 可重复读也挡不住写偏斜

```
约束：至少一名医生在岗
T1：查在岗人数 = 2 → 把自己的值班取消
T2：查在岗人数 = 2 → 把自己的值班取消
结果：0 人在岗
```

两个事务读的是同一份快照，各自都「合法」，但合起来违反约束。这就是**写偏斜（write skew）**，只有 `SERIALIZABLE`（SSI）能自动检测。

> 面试加分点：能说出「RR 防幻读但不防写偏斜，PG 用 SSI 在 Serializable 下检测」。

## 5. 两个会话复现隔离级别

```sql
-- 准备
DROP TABLE IF EXISTS iso_lab;
CREATE TABLE iso_lab (id int PRIMARY KEY, v int);
INSERT INTO iso_lab VALUES (1, 100);
```

**会话 A（读已提交，默认）**

```sql
BEGIN;
SELECT v FROM iso_lab WHERE id = 1;   -- 100
-- 此时去会话 B 执行 UPDATE + COMMIT
SELECT v FROM iso_lab WHERE id = 1;   -- 90  ← 不可重复读
COMMIT;
```

**会话 B**

```sql
UPDATE iso_lab SET v = 90 WHERE id = 1;
COMMIT;
```

**会话 A（可重复读）**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT v FROM iso_lab WHERE id = 1;   -- 100
-- 会话 B 再改一次并提交
SELECT v FROM iso_lab WHERE id = 1;   -- 仍是 100
COMMIT;
```

| 观察 | 说明 |
| --- | --- |
| RC 下第二次读到新值 | 每条语句新快照 |
| RR 下两次一致 | 事务级快照 |
| RR 下 `UPDATE` 会报 `40001` | 快照太旧，不能覆盖新版本 |

## 6. 显式锁

### 6.1 `FOR UPDATE` 锁的是什么

```sql
BEGIN;
SELECT * FROM agent_runs WHERE id = 'run-1' FOR UPDATE;
-- 其他会话对 run-1 的 UPDATE / DELETE / FOR UPDATE 会阻塞
COMMIT;   -- 锁释放
```

| 锁模式 | 强度 | 用途 |
| --- | --- | --- |
| `FOR UPDATE` | 最强 | 准备修改，阻止其他写与加锁 |
| `FOR NO KEY UPDATE` | 较弱 | 修改非键列（PG 优化） |
| `FOR SHARE` | 共享 | 允许别人也读锁，阻止写 |
| `FOR KEY SHARE` | 最弱 | 只保护主键/唯一键不被改 |

> **行锁不锁表**：只锁命中的行；但没走索引的 `FOR UPDATE` 可能锁住大量行（甚至全表），和 05 篇的索引直接相关。

### 6.2 三个修饰符

| 修饰符 | 行为 | 场景 |
| --- | --- | --- |
| `NOWAIT` | 拿不到锁立刻报错 | 快速失败，避免排队 |
| `SKIP LOCKED` | 跳过已被锁的行 | **任务队列**（见 §11） |
| 无 | 一直等（受 `lock_timeout` 约束） | 普通「读-改-写」 |

```sql
-- 等不到就马上告诉用户「稍后再试」
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;

-- 队列消费者：不抢别人正在处理的行
SELECT * FROM agent_runs
 WHERE status = 'queued'
 ORDER BY created_at
 FOR UPDATE SKIP LOCKED
 LIMIT 1;
```

### 6.3 表锁

```sql
LOCK TABLE messages IN SHARE MODE;          -- 阻止写
LOCK TABLE messages IN ACCESS EXCLUSIVE MODE; -- 阻止一切（DDL 用）
```

> 应用代码几乎不该用表锁。DDL 自己会拿 `ACCESS EXCLUSIVE`，这也是「大表加列要小心」的原因（04 篇 §10）。

### 6.4 Advisory lock：锁「业务概念」

```sql
-- 会话级：连接断开才释放
SELECT pg_advisory_lock(731245);
SELECT pg_advisory_unlock(731245);

-- 事务级：事务结束自动释放
BEGIN;
SELECT pg_advisory_xact_lock(731245);
COMMIT;
```

| 用途 | 说明 |
| --- | --- |
| 迁移串行化 | 多副本启动时只让一个跑 `alembic upgrade`（04 篇 §14.4） |
| 定时任务防重 | 同一时刻只有一个实例执行 |
| 幂等窗口 | 按业务 key 加锁，避免并发重复处理 |

> advisory lock 是**数据库连接级**的约定，不阻塞任何行；拿锁的会话崩了会自动释放。

## 7. 死锁

### 7.1 复现

```sql
-- 会话 A
BEGIN;
UPDATE accounts SET credits = credits - 10 WHERE id = 1;
UPDATE accounts SET credits = credits + 10 WHERE id = 2;

-- 会话 B（几乎同时）
BEGIN;
UPDATE accounts SET credits = credits - 10 WHERE id = 2;
UPDATE accounts SET credits = credits + 10 WHERE id = 1;
```

```
ERROR: deadlock detected
DETAIL: Process 12345 waits for ShareLock on transaction 6789; blocked by process 67890.
HINT: See server log for query details.
SQLSTATE: 40P01
```

| 事实 | 说明 |
| --- | --- |
| PG 会检测 | 等 `deadlock_timeout`（默认 1 s）后检查等待图 |
| 处理方式 | 回滚其中一个事务（通常代价小的） |
| 应用要做的 | 捕获 `40P01` → 回滚 → 重试整个事务 |

### 7.2 避免

| 手段 | 说明 |
| --- | --- |
| 固定加锁顺序 | 永远按主键升序加锁 |
| 一次锁够 | `WHERE id IN (...) ORDER BY id FOR UPDATE` |
| 缩短事务 | 不要在事务里调外部 API / 等用户输入 |
| 用唯一约束替代「先查再插」 | 让数据库做原子判断 |
| 降低隔离级别（能接受时） | RR 比 RC 更容易冲突 |

```python
# ✅ 固定顺序：一次按 id 排序加锁
ids = sorted([from_id, to_id])
rows = db.execute(
    select(Account).where(Account.id.in_(ids)).order_by(Account.id).with_for_update()
).scalars().all()
```

## 8. 三种 timeout

| 参数 | 管什么 | 建议 |
| --- | --- | --- |
| `statement_timeout` | 单条语句最长执行时间 | API 5 ~ 30 s；报表单独放宽 |
| `lock_timeout` | 等锁的最长时间 | 1 ~ 3 s，避免无限排队 |
| `idle_in_transaction_session_timeout` | 事务开着却不干活 | 30 ~ 60 s，防连接被占 |
| `deadlock_timeout` | 死锁检测前的等待 | 默认 1 s，通常不动 |

```sql
-- 会话级设置
SET statement_timeout = '10s';
SET lock_timeout = '2s';

-- 只对当前事务生效
BEGIN;
SET LOCAL lock_timeout = '2s';
...
COMMIT;
```

> `lock_timeout` 超时报 `55P03`（lock_not_available），应用可以转成 503「稍后重试」，比请求全部卡死好。

### 8.1 查看谁在等谁

```sql
SELECT pid,
       state,
       wait_event_type,
       wait_event,
       pg_blocking_pids(pid) AS blockers,
       left(query, 60) AS query
  FROM pg_stat_activity
 WHERE state <> 'idle'
 ORDER BY query_start;
```

| 列 | 含义 |
| --- | --- |
| `wait_event_type = Lock` | 正在等锁 |
| `pg_blocking_pids` | 谁挡住了它 |
| `state = idle in transaction` | 事务开着不干活，重点怀疑对象 |

> 线上「突然全部超时」时，先看 `idle in transaction` 和长事务，再看锁等待链。

## 9. 幂等写入

### 9.1 唯一约束是最后一道防线

```sql
-- messages 上已有 (conversation_id, seq) 唯一约束
INSERT INTO messages (id, conversation_id, seq, role, content, created_at)
VALUES ('m1', 'c1', 7, 'user', 'hello', now());
-- 并发第二次插入同一 (c1, 7) → ERROR 23505 duplicate key
```

> 应用层「先查再插」在并发下必错——两个请求可能同时查到「不存在」。**让数据库原子判断**。

### 9.2 `ON CONFLICT`

```sql
-- 冲突就忽略，返回空
INSERT INTO messages (id, conversation_id, seq, role, content, created_at)
VALUES ('m1', 'c1', 7, 'user', 'hello', now())
ON CONFLICT (conversation_id, seq) DO NOTHING;

-- 冲突就更新，并返回最终行
INSERT INTO messages (id, conversation_id, seq, role, content, created_at)
VALUES ('m1', 'c1', 7, 'user', 'hello', now())
ON CONFLICT (conversation_id, seq)
DO UPDATE SET content = EXCLUDED.content
RETURNING *;
```

### 9.3 SQLAlchemy 写法

```python
from sqlalchemy.dialects.postgresql import insert

stmt = (
    insert(Message)
    .values(
        id="m1",
        conversation_id="c1",
        seq=7,
        role="user",
        content="hello",
    )
    .on_conflict_do_nothing(index_elements=["conversation_id", "seq"])
    .returning(Message)
)
row = db.execute(stmt).scalar_one_or_none()
if row is None:
    row = db.execute(
        select(Message).where(
            Message.conversation_id == "c1", Message.seq == 7
        )
    ).scalar_one()
```

| 要点 | 说明 |
| --- | --- |
| `on_conflict_do_nothing` | 只适合「重复就当我来过」 |
| `on_conflict_do_update` | 适合 upsert，但注意别覆盖别人刚写的值 |
| `returning` | 冲突时可能没有返回行，要补一次查询 |
| 异步 | `await db.execute(...)` |

> `ON CONFLICT` 只能处理**唯一/排他约束**冲突，不能处理业务规则冲突。

## 10. 乐观锁与悲观锁

### 10.1 悲观锁：先锁再改

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;   -- 锁住
UPDATE accounts SET credits = credits - 10 WHERE id = 1;
COMMIT;
```

| 优点 | 缺点 |
| --- | --- |
| 逻辑简单、冲突早暴露 | 锁等待、可能死锁、吞吐低 |

### 10.2 乐观锁：版本号 + 受影响行数

```sql
UPDATE accounts
   SET credits = credits - 10, version = version + 1
 WHERE id = 1 AND version = 7;
-- rowcount = 0 → 说明被别人改过，重读后重试
```

```python
result = db.execute(
    update(Account)
    .where(Account.id == account_id, Account.version == expected_version)
    .values(credits=Account.credits - 10, version=Account.version + 1)
)
if result.rowcount == 0:
    raise ConflictError("数据已被修改，请重试")
```

| 优点 | 缺点 |
| --- | --- |
| 无锁等待、适合读多写少 | 冲突多时重试成本高；要改表结构 |

### 10.3 怎么选

| 场景 | 选择 |
| --- | --- |
| 冲突频繁、必须强一致 | 悲观锁（`FOR UPDATE`） |
| 冲突少、Web 表单编辑 | 乐观锁（版本号） |
| 计数/库存扣减 | `UPDATE ... SET x = x - ? WHERE x >= ?`（条件更新，原子） |
| 分布式任务 | 唯一约束 + 状态机 |

```sql
-- 条件更新：不需要先查，天然原子
UPDATE accounts SET credits = credits - 10
 WHERE id = 1 AND credits >= 10;
-- rowcount = 0 → 余额不足或行不存在
```

## 11. 用 `SKIP LOCKED` 做任务队列

### 11.1 领取任务

```sql
WITH claimed AS (
    SELECT id
      FROM agent_runs
     WHERE status = 'queued'
     ORDER BY created_at
     FOR UPDATE SKIP LOCKED
     LIMIT 1
)
UPDATE agent_runs r
   SET status = 'running',
       worker_id = :worker_id,
       lease_until = now() + interval '5 minutes',
       started_at = now()
  FROM claimed c
 WHERE r.id = c.id
RETURNING r.*;
```

| 关键点 | 作用 |
| --- | --- |
| `SKIP LOCKED` | 多个 worker 不抢同一行，天然并行 |
| `status = 'queued'` | 状态机只允许从队列领取 |
| `lease_until` | 崩溃后租约过期可被回收 |
| `RETURNING` | 一次拿到任务详情，少一次查询 |

### 11.2 回收过期租约

```sql
UPDATE agent_runs
   SET status = 'queued', worker_id = NULL, lease_until = NULL
 WHERE status = 'running'
   AND lease_until < now();
```

> 回收条件必须是 `lease_until < now()`，不能用「运行时间超过 N 分钟」——长任务会被误杀。

### 11.3 心跳续租

```sql
UPDATE agent_runs
   SET lease_until = now() + interval '5 minutes'
 WHERE id = :run_id AND worker_id = :worker_id AND status = 'running';
-- rowcount = 0 → 任务已被回收或被取消，应立即停止执行
```

### 11.4 为什么不用内存队列

| 方案 | 重启丢任务 | 多实例 | 事务一致 |
| --- | --- | --- | --- |
| 内存 `asyncio.Queue` | ✅ 丢 | ❌ | ❌ |
| Redis 队列 | 可能丢（未持久化） | ✅ | 弱 |
| DB 表 + `SKIP LOCKED` | ❌ | ✅ | ✅（与业务同库） |
| Kafka | ❌ | ✅ | 最终一致 |

> Agent Run 这类「数量不大但绝不能丢」的任务，**DB 队列足够且最简单**。

## 12. 项目实战

### 12.1 `append_message`：并发写同一 seq

**完整文件路径：`apps/api-py/app/conversations/service.py`（节选）**

```python
from sqlalchemy.exc import IntegrityError

def append_message(db: Session, conversation_id: str, role: str, content: str) -> Message:
    for attempt in range(1, 4):
        try:
            next_seq = db.scalar(
                select(func.coalesce(func.max(Message.seq), 0) + 1).where(
                    Message.conversation_id == conversation_id
                )
            )
            msg = Message(
                id=new_id(),
                conversation_id=conversation_id,
                seq=next_seq,
                role=role,
                content=content,
            )
            db.add(msg)
            db.commit()
            return msg
        except IntegrityError:
            db.rollback()          # 必须先回滚，否则 Session 不可用
            if attempt == 3:
                raise
    raise RuntimeError("unreachable")
```

| 设计点 | 说明 |
| --- | --- |
| 唯一约束 `(conversation_id, seq)` | 并发下只有一个能成功 |
| 每次重试都重新 `max(seq)` | 不能复用上次算出的值 |
| 上限 3 次 | 避免无限重试 |
| `rollback` 必须在重试前 | 02 篇讲过的 `PendingRollbackError` |

> 更好的做法：用 `ON CONFLICT` + 重算，或直接让 DB 生成 `seq`（序列/计数表）。**先保证正确，再谈性能**。

### 12.2 领取 Run：多 worker 不重复

```python
def claim_run(db: Session, worker_id: str) -> AgentRun | None:
    stmt = (
        select(AgentRun)
        .where(AgentRun.status == "queued")
        .order_by(AgentRun.created_at)
        .with_for_update(skip_locked=True)
        .limit(1)
    )
    run = db.scalars(stmt).first()
    if run is None:
        return None
    run.status = "running"
    run.worker_id = worker_id
    run.lease_until = datetime.now(timezone.utc) + timedelta(minutes=5)
    db.commit()
    return run
```

```python
def cancel_run(db: Session, run_id: str) -> None:
    db.execute(
        update(AgentRun)
        .where(AgentRun.id == run_id, AgentRun.status.in_(["queued", "running"]))
        .values(status="canceled", finished_at=func.now())

```

| 规则 | 说明 |
| --- | --- |

## 13. 与 Prisma / NestJS 对照

| 目的 | SQLAlchemy / PG | Prisma |
| --- | --- | --- |
| 事务 | `with db.begin():` | `prisma.$transaction([...])` / 交互式事务 |
| 行锁 | `.with_for_update()` | 原生 SQL `$queryRaw` |
| 跳过锁 | `skip_locked=True` | 原生 SQL |
| 幂等插入 | `on_conflict_do_nothing` | `createMany({ skipDuplicates: true })` 或原生 SQL |
| 乐观锁 | `version` 列 + `rowcount` | `updateMany` 带 `version` 条件 |
| 隔离级别 | `isolation_level=` / `SET TRANSACTION` | `$transaction` 的 `isolationLevel` |
| 唯一冲突 | 捕获 `IntegrityError`（`23505`） | 捕获 `P2002` |

> Prisma 的 `P2002` 就是 PG 的 `23505`。跨栈写同一张表时，错误语义要对齐，否则重试逻辑一边有一边没有。

## 14. 验收自测

### 14.1 判断

1. PG 默认可重复读吗？
2. 可重复读下读到的数据一定是最新提交的吗？
3. `FOR UPDATE` 会锁整张表吗？
4. `SKIP LOCKED` 适合「必须按顺序处理」的队列吗？
5. `ON CONFLICT DO NOTHING` 能处理所有业务冲突吗？
6. 捕获 `40001` 后只重试失败的那条语句可以吗？
7. `idle in transaction` 会一直占着锁吗？

<details>
<summary>答案</summary>

1. ❌ 默认读已提交；MySQL 默认才是可重复读。
2. ❌ 看到的是事务开始时的快照，可能落后于最新提交。
3. ❌ 只锁命中的行；但不走索引时可能锁大量行。
4. ❌ 它会让消费者乱序跳过，只适合「每条任务独立」的场景。
5. ❌ 只处理唯一/排他约束冲突，业务规则冲突要自己在事务里判断。
6. ❌ 必须**整个事务重试**，因为快照已失效。
7. ✅ 事务没结束，锁不会释放（除非配了 `idle_in_transaction_session_timeout`）。

</details>

### 14.2 找错

```python
def transfer(db: Session, from_id: str, to_id: str, amount: int) -> None:
    src = db.get(Account, from_id)
    dst = db.get(Account, to_id)
    src.credits -= amount
    dst.credits += amount
    db.commit()
```

**问题**：

1. 没有锁或条件更新 → 并发下丢失更新；
2. 两个事务以相反顺序转账会死锁；
3. 没有校验余额；
4. 没处理 `IntegrityError` 之外的并发异常。

**改法（悲观锁 + 固定顺序）**：

```python
def transfer(db: Session, from_id: str, to_id: str, amount: int) -> None:
    ids = sorted([from_id, to_id])
    accounts = {
        a.id: a
        for a in db.scalars(
            select(Account).where(Account.id.in_(ids)).order_by(Account.id).with_for_update()
        )
    }
    src, dst = accounts[from_id], accounts[to_id]
    if src.credits < amount:
        raise InsufficientBalance()
    src.credits -= amount
    dst.credits += amount
    db.commit()
```

<details>
<summary>参考</summary>

```python
import time
import random
from functools import wraps
from sqlalchemy.exc import DBAPIError

RETRYABLE = {"40001", "40P01"}

def retry_on_serialization(fn):
    @wraps(fn)
    def wrapper(*args, **kwargs):
        for attempt in range(1, 4):
            try:
                return fn(*args, **kwargs)
            except DBAPIError as exc:
                code = getattr(exc.orig, "sqlstate", None)
                if code not in RETRYABLE or attempt == 3:
                    raise
                time.sleep(min(0.2 * 2 ** attempt, 2) * random.uniform(0.5, 1.5))
        raise RuntimeError("unreachable")
    return wrapper
```

## 15. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 并发下数据被覆盖 | 读-改-写竞态 | `FOR UPDATE` / 条件更新 / 版本号 |
| `could not serialize access` | RR 或 Serializable 冲突 | 捕获 `40001`，整事务重试 |
| 死锁偶发 | 加锁顺序不一致 | 固定按主键排序加锁 |
| 请求全部卡住 | 长事务持有锁 | 查 `pg_stat_activity` + `lock_timeout` |
| `idle in transaction` 一堆 | 代码忘了 commit/rollback | 加 `idle_in_transaction_session_timeout` |
| 重试后报 `PendingRollbackError` | 没先 `rollback` | 捕获异常后立即回滚 |
| 唯一冲突把事务打挂 | 异常后继续用同一 Session | `rollback` 后再重试 |
| `SKIP LOCKED` 任务乱序 | 队列语义不要求顺序 | 需要顺序就按业务键串行 |
| 任务永远 `running` | 没有租约/回收 | `lease_until` + 定期回收 |
| 回收误杀长任务 | 用「运行时长」判断 | 用心跳续租 + 租约过期 |
| 锁住了整表 | `FOR UPDATE` 没走索引 | 补索引，确认 `Index Scan` |
| `ON CONFLICT` 不生效 | 没有对应唯一约束 | 建约束或改用幂等键表 |
| 迁移并发执行 | 多副本同时启动 | advisory lock 串行化 |
| 报表事务拖垮 autovacuum | 长事务 | 拆小事务 / 只读副本 |

## 16. 本篇小结

- **PG 默认读已提交**：每条语句一个新快照；可重复读是事务级快照，冲突时报 `40001`。
- **MVCC 读写不阻塞**，代价是旧版本堆积与长事务阻碍清理。
- **行锁锁行不锁表**：`FOR UPDATE` / `NOWAIT` / `SKIP LOCKED` 各有明确场景。
- **死锁靠顺序避免**；PG 检测后回滚一方（`40P01`），应用要整事务重试。
- **三种 timeout 各管一段**：语句执行、等锁、事务空闲。
- **并发幂等靠数据库**：唯一约束 + `ON CONFLICT`，不要「先查再插」。
- **写冲突两种解法**：悲观锁（先锁再改）与乐观锁（版本号 + `rowcount`）。
- **DB 也能当队列**：`SKIP LOCKED` + 状态机 + 租约，适合 Agent Run 这种「不能丢、量不大」的任务。
- **所有重试的前提**：先 `rollback`，再重读状态，最后整事务重来。
