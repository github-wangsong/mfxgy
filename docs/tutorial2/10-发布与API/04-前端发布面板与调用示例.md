## 2. 数据形状

### 2.1 Zod schema

**完整文件路径：`apps/web/lib/schemas.ts`**（阶段 10 新增）

```ts
// ---------------------------------------------------------------------------
// API Key
// ---------------------------------------------------------------------------

/** API Key 对外视图（不含明文）。 */
export const apiKeyResponseSchema = z.strictObject({
  id: z.string(),                                   // key 主键
  appId: z.string(),                                // 所属应用
  name: z.string(),                                 // 人读名称
  prefix: z.string(),                               // 明文前 11 字符（不是密钥本身）
  createdAt: utcTimestampSchema,                    // UTC + 毫秒 + Z
  lastUsedAt: utcTimestampSchema.nullable(),        // 从未使用为 null
  revokedAt: utcTimestampSchema.nullable(),         // 未撤销为 null
})

/** GET /apps/{id}/api-keys 的响应体。 */
export const apiKeyListResponseSchema = z.strictObject({
  items: z.array(apiKeyResponseSchema),
})

/** POST /apps/{id}/api-keys 的响应体：额外附带一次性明文 key。 */
export const createApiKeyResponseSchema = apiKeyResponseSchema.extend({
  key: z.string(),                                  // 明文只在创建响应出现
})

export type ApiKeyResponse = z.infer<typeof apiKeyResponseSchema>
export type ApiKeyListResponse = z.infer<typeof apiKeyListResponseSchema>
export type CreateApiKeyResponse = z.infer<typeof createApiKeyResponseSchema>
```

三个写法上的选择：

| 选择 | 原因 |
| --- | --- |
| `z.strictObject` | 对应契约 `additionalProperties: false`；多字段说明后端/前端契约漂移 |
| `utcTimestampSchema.nullable()` | 契约是 `type: ["string", "null"]`；`null` 必须显式允许 |
| `createApiKeyResponseSchema = apiKeyResponseSchema.extend({ key })` | 创建响应 = 列表项 + 一个字段；复用避免字段漂移 |

为什么不用 `z.object`（非 strict）：

- 列表/创建都是**完整响应体**，不是「只取部分字段」；
- strict 能在后端误加字段时立即报错，提前发现契约变更；
- 页面里只有 `appDetailSchema` 这种「只取部分字段」的场景才用非 strict。

### 2.3 发布状态的四种取值

```ts
/**
 * 发布状态：`GET /apps/{id}/graph/published` 只返回图（没有 publishedAt），
 * 所以进入页面时只能区分「已发布 / 从未发布」；`at` 来自本页发布接口的响应。
 */
type PublishState = {
  status: 'loading' | 'published' | 'never' | 'error'
  at: string | null
}
```

| 状态 | 触发条件 | UI |
| --- | --- | --- |
| `loading` | 页面刚进入 / 请求未返回 | 「读取中…」 |
| `published` | `GET .../published` 返回 200 | 「已发布」+ 可选的发布时间 |
| `never` | 返回 404 | 「从未发布」 |
| `error` | 401 以外的失败、网络错误 | 「状态不可用」 |

为什么 `at` 和 `status` 分开：

- `GET .../published` 的响应里**没有** `publishedAt`（阶段 3 的契约只返回图）；
- 进入页面时只能知道「有快照」，不知道「什么时候发的」；
- 只有本页点过发布后，`POST .../publish` 的响应才带回 `publishedAt`；
- 所以 `at` 是「本页已知的发布时间」，刷新页面后会丢——此时显示「已发布快照可用」而不是编一个时间。

> **面试考点 · 为什么不在前端编一个「发布时间」？**
> 前端没有可信的时间源。`Date.now()` 是浏览器本地时间，可以随意改；用它冒充服务端发布时间，会得到一个「看起来精确、实际不可信」的字段。
>
> 正确做法：要么后端返回，要么不显示。**不要在展示层伪造业务数据**。

## 3. 进入页面：并行读发布状态与 key 列表

### 3.1 读发布状态

```ts
/** 进入页面时读发布状态：200 = 已发布（无 publishedAt），404 = 从未发布。 */
const loadPublishState = useCallback(
  async (token: string): Promise<void> => {
    const res = await fetch(`${API_BASE}/apps/${appId}/graph/published`, {
      headers: { Authorization: `Bearer ${token}` },
    })
    // 401：登录态失效 → 回登录页
    if (res.status === 401) {
      router.replace('/login')
      return
    }
    // 404：从未发布（不是错误）；这里用状态码而不是错误体判断
    if (res.status === 404) {
      setPublishState({ status: 'never', at: null })
      return
    }
    // 其他非 2xx：状态不可用（网络/服务异常），不阻塞画布
    if (!res.ok) {
      setPublishState({ status: 'error', at: null })
      return
    }
    // 200：已发布。GET 只返回图，没有 publishedAt——保留本页发布成功后拿到的 at
    setPublishState((prev) => ({ status: 'published', at: prev.at }))
  },
  [appId, router],
)
```

为什么用 `res.status === 404` 判断「从未发布」而不是解析错误体：

- 阶段 3 的 `GET .../published` 在未发布时返回 404；
- 404 的语义就是「没有这个资源（快照）」；
- 解析错误体拿 `message` 也能判断，但多一次 JSON 解析，且文案可能变。

`setPublishState((prev) => ...)` 而不是直接 `{ status: 'published', at: null }`：

- 进入页面时 `at` 本来就是 `null`，直接设也等价；
- 但如果将来在页面内重新调用 `loadPublishState`（比如保存后刷新状态），要保留已经拿到的 `at`；
- 用函数式更新是**防御性**写法，避免以后加调用点时丢时间。

### 3.2 读 key 列表

```ts
/** 拉取 API Key 列表（含已撤销的；不含明文）。 */
const loadApiKeys = useCallback(
  async (token: string): Promise<void> => {
    const res = await fetch(`${API_BASE}/apps/${appId}/api-keys`, {
      headers: { Authorization: `Bearer ${token}` },
    })
    if (res.status === 401) {
      router.replace('/login')
      return
    }
    // 非 2xx：静默降级（面板显示空列表），不打断画布
    if (!res.ok) return

    // 宽容解析：结构不符时返回 null，不抛错
    const body = await parseResponseOrNull(res, apiKeyListResponseSchema)
    if (body !== null) setApiKeys(body.items)
  },
  [appId, router],
)
```

为什么列表用 `parseResponseOrNull`，而创建用 `parseResponse`：

| 接口 | 解析方式 | 理由 |
| --- | --- | --- |
| 列表 | `parseResponseOrNull` | 辅助数据；失败时显示空列表即可，不该让整页报错 |
| 创建 | `parseResponse` | 主操作；响应不符契约必须显式报错，否则用户以为创建成功 |

这是「**主流程严格、辅助流程宽容**」的统一原则，与阶段 5 的工具清单、阶段 7 的知识库列表一致。

### 3.3 并行读取

```ts
// 进入页面时并行读取发布状态与 API Key 列表；失败不阻塞画布。
useEffect(() => {
  const token = localStorage.getItem('accessToken')
  if (token === null) return

  // 发布状态失败 → 显示「状态不可用」
  void loadPublishState(token).catch(() => setPublishState({ status: 'error', at: null }))

  // key 列表失败 → 静默（面板保持空列表）
  void loadApiKeys(token).catch(() => {
    // 静默降级：API Key 列表不可用时只显示空列表。
  })
}, [loadPublishState, loadApiKeys])
```

两个请求**并行**，不是串行：

- 二者互不依赖；
- 发布状态失败不影响 key 列表；
- 画布本身不等这两个请求（`loading` 只控制页面主体的加载提示）。

## 4. 发布

### 4.1 `handlePublish` 全文

```ts
async function handlePublish(): Promise<void> {
  const token = localStorage.getItem('accessToken')
  if (token === null) {
    router.replace('/login')
    return
  }

  // 清掉上一次的提示
  setError(null)
  setMessage(null)
  setBusy(true)
  try {
    // 1. 先把当前画布存成草稿（发布读的是数据库里的 graph_json，不是 React state）
    const err = await putDraft(token)
    if (err !== null) {
      setError(err)
      return
    }

    // 2. 发布：把草稿复制成已发布快照
    const res = await fetch(`${API_BASE}/apps/${appId}/graph/publish`, {
      method: 'POST',
      headers: { Authorization: `Bearer ${token}` },
    })
    if (!res.ok) {
      if (res.status === 401) {
        router.replace('/login')
        return
      }
      setError(await readApiErrorMessage(res))
      return
    }

    // 3. 严格校验响应：publishedAt + graph
    const data = await parseResponse(res, publishGraphResponseSchema, 'POST /graph/publish')

    // 4. 更新状态与提示
    setPublishState({ status: 'published', at: data.publishedAt })
    setMessage(`已发布 · ${data.publishedAt}`)
  } catch (err: unknown) {
    setError(err instanceof Error ? err.message : String(err))
  } finally {
    setBusy(false)
  }
}
```

### 4.2 为什么必须先 `putDraft`

```text
React state（nodes / edges）
        │  用户拖拽、改参数
        ▼
   画布内存中的图  ── 不保存就发布 ──→ 后端读的是旧 graph_json
        │
        │ putDraft()
        ▼
   PUT /apps/{id}/graph  → 数据库 graph_json
        │
        │ POST /graph/publish
        ▼
   published_graph_json（复制）
```

发布接口只认数据库里的 `graph_json`。如果只点「发布」不先保存：

- 用户刚改的 prompt 不会上线；
- 线上跑的是上一次保存的版本；
- 用户会以为「发布没生效」。

所以 `handlePublish` 的第一件事永远是 `putDraft(token)`。`putDraft` 返回 `string | null`：`null` 表示成功，字符串是错误文案。

### 4.3 两个发布入口共用一套逻辑

页头：

```tsx
<button className="btn" onClick={() => void handlePublish()} disabled={busy}>
  {busy ? '发布中…' : '发布'}
</button>
```

面板底部：

```tsx
<button
  className="btn btn-primary btn-block"
  type="button"
  onClick={() => void handlePublish()}
  disabled={busy}
>
  {busy ? '发布中…' : '发布当前草稿'}
</button>
```

两个按钮调用同一个 `handlePublish`，共用 `busy`：

- 任意一个在发布中，两个都禁用；
- 避免「页头点一次、面板再点一次」触发两次发布；
- `busy` 是页面级状态（保存草稿也用它），所以发布时保存按钮也会禁用。

## 5. API Key 管理

### 5.1 创建

```ts
/** 新建 API Key：成功后把**一次性明文 key**放进醒目区块，并刷新列表。 */
async function handleCreateApiKey(event: FormEvent<HTMLFormElement>): Promise<void> {
  event.preventDefault()                       // 阻止表单默认提交（页面刷新）
  const name = newKeyName.trim()               // 首尾空白不算名字
  if (name === '') return                      // 空名不请求（按钮本身也 disabled）

  const token = localStorage.getItem('accessToken')
  if (token === null) {
    router.replace('/login')
    return
  }

  setApiKeyError(null)
  setCopyHint(null)                            // 清掉上一次「已复制」提示
  setApiKeyBusy(true)
  try {
    const res = await fetch(`${API_BASE}/apps/${appId}/api-keys`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
      body: JSON.stringify({ name }),
    })
    if (res.status === 401) {
      router.replace('/login')
      return
    }
    if (!res.ok) {
      setApiKeyError(await readApiErrorMessage(res))
      return
    }

    // 严格校验：创建响应必须包含一次性明文 key
    const created = await parseResponse(res, createApiKeyResponseSchema, 'POST /api-keys')

    // 明文只进 state（当前页面内存），不写 localStorage
    setNewKeyPlain({ name: created.name, key: created.key })
    setNewKeyName('')                          // 清空输入框
    await loadApiKeys(token)                   // 重拉列表（新 key 出现在第一行）
  } catch (err: unknown) {
    setApiKeyError(err instanceof Error ? err.message : String(err))
  } finally {
    setApiKeyBusy(false)
  }
}
```

### 5.2 一次性明文区块

```tsx
{/* 一次性明文 key：只在这里显示，关闭后列表只留 prefix。 */}
{newKeyPlain !== null && (
  <div data-testid="new-api-key" className="alert alert-warn stack stack--sm">

      <span className="badge badge-danger">仅显示一次</span>
    </div>
    <div className="faint">此密钥只显示这一次，关闭后无法再次查看</div>

    {/* 明文 key：等宽字体，便于选中复制 */}
    <pre className="code-block">{newKeyPlain.key}</pre>

    <div className="row">
      <button
        className="btn btn-sm"
        type="button"
        onClick={() => void copyToClipboard(newKeyPlain.key, 'API Key ')}
      >
        复制
      </button>
      <button
        className="btn btn-sm btn-ghost"
        type="button"
        onClick={() => {
          setNewKeyPlain(null)                 // 关闭区块 = 丢弃内存中的明文
          setCopyHint(null)
        }}
      >
        我已保存，关闭
      </button>
    </div>

    {copyHint !== null && <div className="faint">{copyHint}</div>}
  </div>

```

明文 key 的三个生命周期节点：

```text
POST /api-keys 响应
   ↓ parseResponse 校验
newKeyPlain（React state，内存）
   ↓ 用户点「复制」
剪贴板
   ↓ 用户点「我已保存，关闭」/ 刷新页面 / 关闭标签页
消失（state 重置，服务端也没有明文）
```

为什么**不**放进 `localStorage`：

| 存储位置 | XSS 可读 | 刷新后还在 | 结论 |
| --- | --- | --- | --- |
| React state | 是（XSS 能读内存） | 否 | 生命周期最短，够用 |
| `localStorage` | 是 | 是 | 扩大泄露窗口，没必要 |
| 后端数据库 | — | 是 | 只存哈希，存不了明文 |

任何前端存储都无法防御 XSS；能做的是**缩短明文存在的时间**。刷新即消失，是这里最合适的选择。

### 5.3 撤销

```ts
/** 撤销 API Key（DELETE /api-keys/{id}），成功后刷新列表以显示「已撤销」。 */
async function handleRevokeApiKey(id: string): Promise<void> {
  const token = localStorage.getItem('accessToken')
  if (token === null) {
    router.replace('/login')
    return
  }

  setApiKeyError(null)
  setApiKeyBusy(true)
  try {
    const res = await fetch(`${API_BASE}/api-keys/${id}`, {
      method: 'DELETE',
      headers: { Authorization: `Bearer ${token}` },
    })
    if (res.status === 401) {
      router.replace('/login')
      return
    }
    if (!res.ok) {
      setApiKeyError(await readApiErrorMessage(res))
      return
    }

    // 204 无响应体：不解析，直接重拉列表
    await loadApiKeys(token)
  } catch (err: unknown) {
    setApiKeyError(err instanceof Error ? err.message : String(err))
  } finally {
    setApiKeyBusy(false)
  }
}
```

为什么撤销后**重拉列表**，而不是本地把 `revokedAt` 改成 `new Date()`：

- `revokedAt` 的权威值来自服务端（服务端时钟）；
- 本地改状态会出现「前端显示的时间 ≠ 数据库里的时间」；
- 重拉一次只多一个 GET，换来状态一致；
- 这也是「写操作后用服务端响应/重拉校准」的通用做法。

```tsx

```

列表同时承担三个信息：

| 列 | 回答的问题 |
| --- | --- |
| 名称 + 已撤销标签 | 这把 key 叫什么、还能不能用 |
| `prefix…` | 哪把 key 是当前应用在用的 |
| 创建 / 最后使用 / 撤销时间 | 什么时候签发、有没有被调用过、什么时候失效 |

`lastUsedAt === null` 显示「从未使用」，而不是显示 `-` 或空：

- 明确告诉用户「这把 key 从没被用过」；
- 这也间接验证了对外运行是否真的走了认证（用过就会变）。

## 6. 调用示例

### 6.1 生成逻辑

```ts
// 对外调用示例：端口跟随当前 API_BASE；key 位用未撤销 key 的 prefix 占位。
const activeApiKey = apiKeys.find((item) => item.revokedAt === null) ?? null
const keyPlaceholder = activeApiKey === null ? '<你的 key>' : `<${activeApiKey.prefix}…>`
const firstInputName = startInputs[0]?.name ?? 'topic'
const curlExample = `curl -N -X POST ${API_BASE}/public/apps/${appId}/run \\
  -H "X-API-Key: ${keyPlaceholder}" -H "Content-Type: application/json" \\
  -d '{"inputs":{"${firstInputName}":"你好"}}'`
```

四个变量各自的作用：

| 变量 | 来源 | 为什么 |
| --- | --- | --- |
| `activeApiKey` | 列表里第一个 `revokedAt === null` 的 | 优先展示可用的 key |
| `keyPlaceholder` | `prefix…` 或 `<你的 key>` | 前端拿不到完整明文，只能给占位 |
| `firstInputName` | start 节点第一个输入，缺省 `topic` | 示例必须能直接跑；输入名错了会 400 |
| `API_BASE` | `NEXT_PUBLIC_API_BASE` | 切到 Python 8000 时示例跟着变 |

### 6.2 为什么用 `prefix` 占位

前端**永远拿不到完整 key**：

- 列表只有 `prefix`；
- 创建响应的明文只在 `newKeyPlain` 里，关闭就丢；
- 所以示例只能写 `<sk-1a2b3c4d…>`，提示用户「把这里换成你的完整 key」。

如果示例里写完整 key：

- 需要把明文长期保存在页面状态里（刷新就没了，做不到）；
- 就算做到了，也等于把密钥渲染进 DOM，XSS 可直接读取。

**示例的作用是告诉用户「怎么调用」，不是「替你保管密钥」。**

### 6.3 模板字符串里的 `\\`

```ts
const curlExample = `curl -N -X POST ${API_BASE}/public/apps/${appId}/run \\
  -H "X-API-Key: ${keyPlaceholder}" ...`
```

- 在 JS 模板字符串里，`\\` 表示**一个**反斜杠；
- 渲染出来是：

```bash
curl -N -X POST http://localhost:3001/public/apps/xxx/run \
  -H "X-API-Key: <sk-1a2b3c4d…>" -H "Content-Type: application/json" \
  -d '{"inputs":{"topic":"你好"}}'
```

- 行尾的 `\` 是 shell 的续行符；
- 如果写成单个 `\`，JS 会把它当成转义字符，可能把换行吃掉或产生语法错误。

### 6.4 示例区 JSX

```tsx
<div className="stack stack--sm">
  <div className="label">调用示例</div>
  <div className="faint">
    对外接口无需登录，用 <code>X-API-Key</code>（或 <code>Authorization: Bearer</code>）鉴权，
    返回与调试运行一致的 SSE。
  </div>

  {/* 等宽 + 可换行：长 URL 不会撑破面板 */}
  <pre className="code-block">{curlExample}</pre>

  <div className="row">
    <button
      className="btn btn-sm"
      type="button"
      onClick={() => void copyToClipboard(curlExample, 'curl ')}
    >
      复制 curl
    </button>
  </div>

  {copyHint !== null && <div className="faint">{copyHint}</div>}
</div>
```

## 7. 交互细节

### 7.1 复制到剪贴板

```ts
/** 复制到剪贴板，并在按钮旁给出结果提示（失败时提示手动复制）。 */
async function copyToClipboard(text: string, label: string): Promise<void> {
  try {
    await navigator.clipboard.writeText(text)
    setCopyHint(`${label}已复制`)
  } catch {
    // 非安全上下文（http + 非 localhost）、权限被拒、旧浏览器都会走到这里
    setCopyHint('复制失败，请手动选择文本复制')
  }
}
```

为什么必须有失败分支：

- `navigator.clipboard` 只在**安全上下文**（HTTPS 或 `localhost`）可用；
- 用户把前端部署到 `http://192.168.x.x:3000` 时，`writeText` 会抛错；
- 静默失败会让用户以为复制成功，粘贴出来却是旧内容。

失败时提示「手动选择文本复制」，而不是弹 toast 报错：

- 复制不是主流程，失败不该打断；
- `<pre>` 里的文本本来就可以手动选中。

### 7.2 `copyHint` 为什么是页面级状态

```ts
const [copyHint, setCopyHint] = useState<string | null>(null)
```

两个区块（一次性明文、curl 示例）共用同一个提示：

- 同一时刻只会有一个「已复制」；
- 切换操作时先 `setCopyHint(null)`，避免旧提示残留；
- 如果各自维护一个 state，会同时出现两条提示，视觉噪音。

### 7.3 `apiKeyBusy` 共用一个 busy

```ts
const [apiKeyBusy, setApiKeyBusy] = useState(false)
```

创建和撤销共用一个：

- 防止「创建请求还没回来，又点撤销」；
- 代价是创建时不能撤销（可接受，操作频率低）；
- 与页面级 `busy`（保存/发布）分开，避免「发布时不能建 key」这种无关阻塞。

### 7.4 `maxLength={60}` 与后端校验

```tsx
<input
  className="form-input grow"
  value={newKeyName}
  onChange={(e) => setNewKeyName(e.target.value)}
  placeholder="key 名称，如 ui-demo"
  maxLength={60}                 // 前端体验：超长直接输不进去
  disabled={apiKeyBusy}
/>
```

`maxLength` 只是**输入体验**：

- 它按 UTF-16 码元计数，而契约按码点计数（emoji 会被多算）；
- 用户可以粘贴超长文本，浏览器会截断到 60；
- 真正的约束在服务端：`[...name].length > 60` → 400 `API key name is too long`。

**前端校验永远不是安全边界**，它只是减少无效请求、改善体验。

## 8. 验证

> 前置：api-ts `:3001` 已启动；前端 `:3000`；已登录；应用里有至少一个 start 节点。

### 8.1 启动前端

```powershell
pnpm --filter @mini-dify/web dev
```

打开 `http://localhost:3000/apps/{appId}`，右侧面板切到「发布与 API」。

### 8.2 发布流程

1. 在画布上改一个 llm 节点的 prompt；
2. 直接点页头「发布」（不点保存）；
3. 观察：
   - 按钮变「发布中…」；
   - 页头状态从「未发布」变「已发布」；
   - 页面顶部出现 `已发布 · 2026-…Z`；
   - 面板里显示「发布时间：…」。

这一步验证「发布前先 `putDraft`」：只点发布，改动也会被保存并上线。

### 8.3 创建 key

1. 输入 `ui-demo`，点「新建 Key」；
2. 出现黄色区块「新 API Key 已生成（ui-demo）」+「仅显示一次」；
3. `pre` 里的 key 长度应为 35，以 `sk-` 开头；
4. 点「复制」→ 提示「API Key 已复制」；
5. 点「我已保存，关闭」→ 区块消失；
6. 列表新增一行：名称 `ui-demo`、前缀 `sk-xxxxxxxx…`、创建时间、最后使用「从未使用」。

### 8.4 刷新页面

```text
F5 刷新
  → 一次性明文区块消失（state 重置）
  → key 列表仍在（数据来自 GET）
  → 发布状态显示「已发布 / 已发布快照可用」
```

这一步验证：**明文只存在于当前页面内存**，刷新后不可恢复。

### 8.5 撤销

1. 点某一行的「撤销」；
2. 行内出现红色「已撤销」标签；
3. 「撤销」按钮消失；
4. 「最后使用」旁出现撤销时间。

撤销后再点一次（如果有旧页面残留的按钮）会得到 404，页面显示 `操作失败：API key not found`。

### 8.6 复制 curl 并实际调用

1. 点「复制 curl」；
2. 把 `<sk-xxxxxxxx…>` 换成刚才保存的完整 key；
3. 粘贴到终端执行（Windows 用 `curl.exe`）：

```powershell
curl.exe -N -X POST http://localhost:3001/public/apps/{appId}/run `
  -H "X-API-Key: sk-..." `
  -H "Content-Type: application/json" `
  -d '{"inputs":{"topic":"你好"}}'
```

预期：

- 终端逐帧打印 `event:` / `data:`；
- 最后 `run_finished` 的 `outputs` 里有 end 节点声明的字段。

### 8.7 切 Python 8000

```powershell
# 改 apps/web/.env.local（或重启时临时设置）
$env:NEXT_PUBLIC_API_BASE = "http://localhost:8000"
pnpm --filter @mini-dify/web dev
```

刷新页面后：

- 「调用示例」里的 URL 变成 `http://localhost:8000/public/apps/{appId}/run`；
- 同一把 key 仍然可用（同一数据库 + 同一 SHA-256）；
- 发布状态 / key 列表仍然正常（Python 也实现了这三个管理接口）。

### 8.8 失败路径

| 操作 | 预期 |
| --- | --- |
| 创建同名（未撤销）key | 面板显示 `操作失败：API key name already exists` |
| 创建名称为空 | 按钮 disabled，不发请求 |
| 名称输入 61 个字符 | 浏览器 `maxLength` 截断到 60，实际发不出去 |
| key 已撤销后再用于调用 | 401 `Invalid API key` |
| 未发布时调用 | 400 `App is not published` |

## 9. 面试考点汇总

| 问题 | 答案要点 |
| --- | --- |
| 发布前为什么必须 `putDraft` | 发布读数据库草稿，不读 React state；不保存就发旧版本 |
| `GET published` 为什么没有 `publishedAt` | 阶段 3 的契约只返回图；时间只在发布响应里 |
| 发布状态为什么四态 | loading / published / never（404）/ error（其他失败） |
| 404 为什么表示「从未发布」 | 快照资源不存在；不是网络错误 |
| 列表为什么用 `parseResponseOrNull` | 辅助数据，失败降级为空列表，不阻塞画布 |
| 创建为什么用 `parseResponse` | 主操作，响应不符契约必须显式报错 |
| `createApiKeyResponseSchema` 为什么 `.extend` | 创建响应 = 列表项 + `key`，复用避免字段漂移 |
| 明文 key 存哪 | 只在 `newKeyPlain` state；关闭/刷新即丢 |
| 为什么不放 `localStorage` | XSS 可读 + 刷新后仍在，扩大泄露窗口 |
| key 占位为什么用 `prefix` | 前端拿不到完整 key；示例只教怎么调 |
| `curl` 里 `\\` 是什么 | JS 模板字符串转义，渲染成一个 shell 续行符 |
| 撤销后为什么重拉列表 | `revokedAt` 以服务端时间为准；本地改会不一致 |
| `maxLength` 算安全边界吗 | 不算；按 UTF-16 计数，且可绕过；服务端才是契约 |
| 剪贴板失败怎么办 | 提示手动复制；非安全上下文下 `clipboard` 不可用 |
| `busy` 为什么要分页面级和面板级 | 发布/保存与 key 操作互不阻塞 |
