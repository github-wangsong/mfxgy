> 阶段 9 · 第 1 步

>
> **本篇面试考点**：会话与记忆为什么是两条线 · 会话为什么同时挂 `app_id` 和 `owner_id` · `seq` 为什么不用自增主键 · `(conversation_id, seq)` 唯一约束与并发重试 · `updated_at` 为什么要在追加消息时手动刷新 · 为什么不用 LangGraph checkpointer 当唯一真源 · `title` 为什么可空、`null` 与 `""` 的区别 · 标题长度按码点还是字节 · 消息 `role` 为什么枚举三种 · 为什么 `runId` 可空。

---

## 1. 两条线：界面历史 vs 引擎上下文

“会话与记忆”在同一批表上支撑两个完全不同的消费者：

```text
                         conversations / messages
                         ┌──────────────────────┐
界面（会话面板）  ←──────│ GET /apps/{id}/conversations
                         │ GET /conversations/{id}/messages
                         └──────────────────────┘
                                     ↑ 写
引擎（多轮对话）  ←── pool.conversation ──┘
       │
       └→ llm.useHistory → 历史消息 + 本轮消息 → 模型
```

| 线 | 需要什么 | 不关心什么 |
| --- | --- | --- |
| 界面 | 列表、消息、`messageCount`、排序 | 历史窗口、消息如何进 prompt |
| 引擎 | 最近 N 条、`role/content`、`pool.conversation` | 标题、列表排序、`messageCount` |

两条线共用同一张表，但**接口与字段不同**：

- 界面要 `messageCount`（列表展示“3 条消息”）；
- 引擎只要 `role/content`（进 prompt 不需要 id、时间）。

> **面试考点 · 为什么不给引擎单独建一张 `chat_history` 表？**
> 因为那会要求**写两次、删两次、保持一致**：
>
> - 用户删会话 → 两张表都要删；
> - 消息写入失败 → 要么双写事务，要么最终一致；
> - 查询“这个会话有几条消息”要跨表。
>
> 一张表 + 两个读取视图（HTTP 响应 / `pool.conversation`）是更简单的结构。
> **存储归一，视图分离**。

---

## 2. 九条决策

| # | 决策 | 理由 |
| --- | --- | --- |
| 1 | 会话属于 `app` + `owner` | 应用内的会话才有意义；用户隔离 |
| 2 | 消息属于 `conversation`，级联删除 | 删会话即删消息，不留孤儿 |
| 3 | `seq` 会话内从 1 递增，`(conversation_id, seq)` 唯一 | 顺序稳定、可分页、抗并发 |
| 4 | 历史窗口默认 20 条（`MAX_HISTORY_MESSAGES`） | 控制 token 成本 |
| 5 | 先读历史、再写本轮用户消息 | 否则本轮 user 会混进历史 |
| 6 | 助手消息在 `run_finished` **之前**写入 | 终态帧唯一 |
| 7 | `run_failed` 不写助手消息 | 失败没有可记录的答案 |
| 8 | `title` 可空（`null`），长度上限 120 码点 | 用户不一定命名；空标题用 `null` 表达 |
| 9 | 会话 `updated_at` 在追加消息时手动刷新 | 列表按“最近活跃”排序 |

第 3、6、9 条是后面三篇的核心，本篇先把模型与契约定下来。

为什么 `/apps/{id}/conversations` 与 `/conversations/{id}` 分成两种前缀：

- 列表/创建必须知道“哪个应用” → 挂应用；
- 详情/删除只需要会话 id（会话已含 `appId`）→ 挂会话。

这是 REST 资源层级的常规做法：**集合归属父资源，单体按自身 id**。

### 3.2 `RunRequest` 扩展

```yaml
    RunRequest:
      type: object
      additionalProperties: false
      required: [inputs]
      properties:
        inputs:
          type: object
          additionalProperties: true
          description: 运行输入，键为输入变量名
        conversationId:
          type: string
          description: >-
            可选。会话 id；提供时引擎先写入用户消息、再按该会话的历史构造
            `pool.conversation`（见 sse-events.md §4.2）。
        userMessage:
          type: string
          maxLength: 4000
          description: 可选。本轮的原始用户消息（写入会话时使用）。
```

两个字段**都可选**：

- 不传 `conversationId` → 单轮运行，行为与阶段 8 完全一致（零破坏）；
- 传 `conversationId` 但不传 `userMessage` → 只读历史、不写用户消息（适合“重新生成”场景）；
- 传 `userMessage` 但不传 `conversationId` → **不会写消息**（没有会话可写），也不会报错。

> **面试考点 · 为什么不做成“三者必须同时出现”的强校验？**
> 因为组合各有用途：
>
> | conversationId | userMessage | 场景 |
> | --- | --- | --- |
> | ✗ | ✗ | 单轮调试 |
> | ✓ | ✗ | 基于已有历史重新生成 / 继续但不追加用户话 |
> | ✓ | ✓ | 正常多轮对话 |
> | ✗ | ✓ | 无意义，但不该报错（忽略即可） |
>
> 强校验会把“无意义但无害”的请求变成 400，增加客户端负担。
> **校验应该拦住“会导致错误”的组合，而不是“看起来奇怪”的组合。**

### 3.3 `LlmNodeData.useHistory`

```yaml
        useHistory:
          type: boolean
          default: false
          description: >-
            为 `true` 时把会话历史前置为真实消息（`user`→Human、`assistant`→AI、
            `system`→System，`tool` 角色跳过），再接本轮的 system/user 消息。
            需要请求带 `conversationId`，否则运行前预检 400。
```

为什么是**节点级开关**而不是全局开关：

- 一张图可能有多个 `llm` 节点，只有“对话节点”需要历史；
- 摘要/分类节点拿历史反而会污染判断；
- 开关放在 `data` 里，随图保存，不需要额外的运行参数。

三个细节：

1. **`title` 是 `["string", "null"]` 且 required**：字段一定存在，值可以是 `null`。这样前端不用区分“字段缺失”与“空标题”。
2. **`messageCount` 是派生字段**：数据库没有这一列，由 `_count` 聚合得到。契约把它当普通字段，因为**客户端不关心数据怎么来**。
3. **`runId` 可空**：用户消息没有 run（它先于运行写入）；助手消息有 run；`system` 消息可能没有。

> **面试考点 · `title` 用 `null` 还是 `""`？**
> 选 `null`：
>
> - `""` 是“用户输入了空标题”，`null` 是“没有标题”，语义不同；
> - 前端可以显示“未命名”而不是空白；
> - 数据库列可空，直接映射，不需要“空串转 null”的转换层。
>
> 反例：如果契约写 `type: string`，数据库就必须 `NOT NULL DEFAULT ''`，读的时候永远不知道“是真的空还是没填”。

### 4.1 为什么 `owner_id` 和 `app_id` 都要存

`conversation.app_id → app.owner_id → user.id` 已经能推出归属用户，为什么还冗余存 `owner_id`：

| 方案 | 查“我的会话” | 越权校验 | 应用转移所有者 |
| --- | --- | --- | --- |
| 只存 `app_id` | 需要 join `apps` | 需要 join `apps` | 自动跟随 |
| 存 `owner_id`（本项目） | 单表 `where ownerId` | 单表比较 | **需同步更新** |

取舍：

- 读多写少 → 冗余换查询简单；
- 但“应用转移所有者”必须同时更新 `conversations.owner_id`，否则会话会“留在旧所有者名下”；
- 当前没有转移功能，所以没有这个问题。

> **面试考点 · 冗余字段怎么保证一致？**
> 三条防线：
>
> 1. **写入只通过 Service**：创建会话时 `ownerId` 从 token 取，不允许客户端传；
> 2. **外键约束**：`owner_id` 必须存在于 `users`；
> 3. **测试覆盖**：越权查询必须 404（阶段 9 验收用例）。
>
> 但**数据库层面无法保证** `conversation.owner_id === app.owner_id`——这需要触发器或应用层校验。
> 这是“反范式”的代价：**查询简单了，一致性责任转移到应用层**。

### 4.2 `seq` 为什么不用自增列

候选方案：

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| `AUTO_INCREMENT` / `SERIAL` 全局自增 | 数据库保证唯一 | 全局不连续（不同会话交错），不能表达“会话内第几条” |
| `seq = count(*) + 1` | 语义直观 | 并发下两个请求读到同一个 count → 冲突 |
| `seq = max(seq) + 1` + 唯一约束（本项目） | 会话内连续、并发可检测 | 需要事务 + 重试 |

SQL 层面对应：

```sql
CREATE UNIQUE INDEX "messages_conversation_id_seq_key" ON "messages"("conversation_id", "seq");

-- 事务内
SELECT seq FROM messages WHERE conversation_id = $1 ORDER BY seq DESC LIMIT 1;
INSERT INTO messages (..., seq) VALUES (..., $last + 1);
```

并发写同一会话时：

```text
T1: SELECT max = 5  ─┐
T2: SELECT max = 5  ─┴→ 都准备插入 seq=6
T1: INSERT 6 ✅
T2: INSERT 6 ❌ 唯一约束冲突（P2002）
```

第二个请求捕获 `P2002` 后重试（重新读 max），最多 3 次。

> **面试考点 · 为什么不用数据库序列（sequence）？**
> 序列是**全局**的：
>
> ```text
> 会话 A: 1, 3, 4
> 会话 B: 2, 5
> ```
>
> 每个会话的 `seq` 不连续，前端无法用 `seq` 做“第 n 条”分页，也无法用 `seq = count` 判断完整性。
> 序列适合“全局唯一 id”，不适合“会话内序号”。
>
> **“唯一”与“连续”是两个需求**，前者可以靠约束，后者必须靠“读最大值 + 写”的临界区。

### 4.3 `updated_at` 为什么要手动刷新

Prisma 的 `@updatedAt` 只在**这一行被更新**时生效。
追加消息只写 `messages` 表，`conversations` 行没变 → `updatedAt` 不会动 → 列表排序失效（刚聊过的会话还排在后面）。

所以 `appendMessage` 在同一个事务里：

```ts
await tx.message.create({ ... })
await tx.conversation.update({
  where: { id: conversationId },
  data: { updatedAt: new Date() },
})
```

为什么放在同一事务：

- 只写消息不更新会话 → 排序错；
- 只更新会话不写消息 → 时间戳虚高；
- 两者必须**同时成功或同时失败**。

> **面试考点 · 用数据库触发器更新 `updated_at` 不是更好？**
> 触发器能保证“任何写入都刷新”，但：
>
> - 触发器逻辑对应用不可见（排查困难）；
> - Prisma 迁移不知道触发器的存在（`migrate dev` 可能删除/重建）；
> - 本项目阶段 2 已经用触发器维护 `apps.updated_at`，但 `conversations` 没有加触发器——**同一项目里两种风格并存**，是历史演进的结果。
>
> 更一致的做法是二选一：要么全部触发器，要么全部应用层。
> 当前选择应用层，是因为“追加消息”本身就在事务里，多一条 `update` 成本可忽略。

### 4.4 为什么不用 LangGraph checkpointer

LangGraph 自带 checkpointer（`MemorySaver`、`PostgresSaver`），能把整个 state 按 `thread_id` 存下来。为什么还自建表：

| 需求 | checkpointer | 自建表 |
| --- | --- | --- |
| 列出用户的会话 | 需要反查 thread 元数据 | 一条 SQL |
| 删除会话 | 需要 checkpointer API | `DELETE` |
| 展示消息给用户 | 解析内部 state 结构 | 直接读 `role/content` |
| 多后端共享 | 依赖 Python/TS 两套 checkpointer 行为一致 | 同一张表 |
| 历史窗口 | 内部实现（不可控） | `LIMIT 20` |

核心原因：**checkpointer 是“引擎内部状态”的持久化，不是“产品数据”的模型**。
本项目把消息当产品数据（可列表、可删除、可导出），引擎只是它的一个消费者。

> **面试考点 · 那 checkpointer 的价值是什么？**
> 它适合：
>
> - 中断/恢复（human-in-the-loop）；
> - 长时间运行的 Agent（阶段 11 的 Run 事件重放）；
> - 保存“图执行到哪一步”的中间状态。
>
> 本项目阶段 11 用自建 `agent_runs` + `agent_run_events` 做重放，也是同一思路：**产品语义自己定义，不用框架的内部格式**。

## 5. 迁移

**完整文件路径：`apps/api-ts/prisma/migrations/20261022140744_add_conversations/migration.sql`**

```sql
-- CreateTable
CREATE TABLE "conversations" (
    "id" TEXT NOT NULL,
    "app_id" TEXT NOT NULL,
    "owner_id" TEXT NOT NULL,
    "title" TEXT,
    "created_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    "updated_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "conversations_pkey" PRIMARY KEY ("id")
);

-- CreateTable
CREATE TABLE "messages" (
    "id" TEXT NOT NULL,
    "conversation_id" TEXT NOT NULL,
    "role" TEXT NOT NULL,
    "content" TEXT NOT NULL,
    "seq" INTEGER NOT NULL,
    "run_id" TEXT,
    "created_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "messages_pkey" PRIMARY KEY ("id")
);

-- CreateIndex
CREATE INDEX "conversations_app_id_idx" ON "conversations"("app_id");

-- CreateIndex
CREATE INDEX "messages_conversation_id_idx" ON "messages"("conversation_id");

-- CreateIndex
CREATE UNIQUE INDEX "messages_conversation_id_seq_key" ON "messages"("conversation_id", "seq");

-- AddForeignKey
ALTER TABLE "conversations" ADD CONSTRAINT "conversations_app_id_fkey" FOREIGN KEY ("app_id") REFERENCES "apps"("id") ON DELETE CASCADE ON UPDATE CASCADE;

-- AddForeignKey
ALTER TABLE "conversations" ADD CONSTRAINT "conversations_owner_id_fkey" FOREIGN KEY ("owner_id") REFERENCES "users"("id") ON DELETE CASCADE ON UPDATE CASCADE;

-- AddForeignKey
ALTER TABLE "messages" ADD CONSTRAINT "messages_conversation_id_fkey" FOREIGN KEY ("conversation_id") REFERENCES "conversations"("id") ON DELETE CASCADE ON UPDATE CASCADE;
```

三个索引：

| 索引 | 支撑的查询 |
| --- | --- |
| `conversations_app_id_idx` | `WHERE app_id = ? AND owner_id = ? ORDER BY updated_at DESC` |
| `messages_conversation_id_idx` | `WHERE conversation_id = ? ORDER BY seq` |
| `messages_conversation_id_seq_key`（唯一） | 顺序唯一性 + 按 `seq` 读取 |

为什么唯一索引也管查询：`(conversation_id, seq)` 的最左前缀是 `conversation_id`，`WHERE conversation_id = ? ORDER BY seq` 可以直接走它，无需再建普通索引。
**唯一约束与查询索引可以复用同一个索引**——多建一个只会增加写放大。

> 注：Prisma 仍会为 `@@index([conversationId])` 生成单独的索引。严格说它可以省略（唯一索引的最左前缀已覆盖），但保留它让 `EXPLAIN` 更直观，成本是每次插入多维护一棵 B 树。

## 7. 面试考点汇总

| 问题 | 答案要点 |
| --- | --- |
| 会话与记忆两条线 | 界面读列表/消息，引擎读窗口上下文，同一张表 |
| 为什么要 `owner_id` 冗余 | 单表查询与鉴权；代价是一致性靠应用层 |
| `seq` 不用全局自增 | 会话内需要连续序号；全局序列会跳号 |
| 并发写 `seq` | `max+1` + 唯一约束 + 捕获 `P2002` 重试 |
| 为什么同事务更新会话 | 消息与会话时间戳必须一起成功/失败 |
| 为什么不用 checkpointer | 产品数据 vs 引擎内部状态；可列表/可删/跨语言一致 |
| `title` 用 `null` | 区分“没填”与“空串”；可空列直接映射 |
| 标题长度 120 | JSON Schema `maxLength` 按码点；JS 用 `[...s].length` 对齐 |
| `role` 枚举三种 | 与 OpenAI 消息角色对齐；`tool` 不进用户可见消息 |
| `runId` 可空 | 用户消息先于运行写入；`system` 可能无 run |
| 三种 404 同一文案 | 不泄露会话存在性 |
| 唯一索引复用查询 | 最左前缀覆盖 `WHERE conversation_id` |
