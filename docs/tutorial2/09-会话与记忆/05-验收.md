# 05 · 验收（会话与记忆）

> 阶段 9 · 收尾
>
> 验收目标：**同一段对话，两端的消息序列、时间字段、事件序列逐字节一致**；历史确实被注入模型（而不是只写进了库）；`useHistory` 关闭时行为与阶段 8 完全相同；失败运行只留下真实发生过的 user 消息。
>
> **本篇面试考点**：怎样证明「历史真的进了 prompt」而不只是「写进了表」 · 为什么用 mock 的 `prompt_tokens` 做差分断言 · 为什么注入对照要放在同一张图里 · 截断验收为什么必须重启进程 · `run_failed` 为什么只允许出现一次 · 跨端事件级 diff 应该比哪些字段、忽略哪些字段 · 失败后的下一轮为什么仍能看到那条 user 消息 · 阶段 9 的回归重点是哪些旧用例。

## 3. 四张固定测试图

四张图都存到**同一个应用**（TS 端创建，两端共用数据库）。每张图都用 `PUT /apps/{id}/graph` 保存；本阶段只跑草稿，不需要发布。

### 3.1 G1：注入对照（同一张图里两开两关）

```text
s1 ──► l1（useHistory: true）──► l2（useHistory: false）──► e1
```

```json
{
  "version": "1",
  "nodes": [
    { "id": "s1", "type": "start", "position": { "x": 0, "y": 0 },
      "data": { "inputs": [ { "name": "topic", "type": "string", "required": true } ] } },
    { "id": "l1", "type": "llm", "position": { "x": 1, "y": 0 },
      "data": { "title": "带历史", "prompt": "{{ inputs.topic }}", "useHistory": true } },
    { "id": "l2", "type": "llm", "position": { "x": 2, "y": 0 },
      "data": { "title": "不带历史", "prompt": "{{ inputs.topic }}", "useHistory": false } },
    { "id": "e1", "type": "end", "position": { "x": 3, "y": 0 },
      "data": { "outputs": [
        { "name": "withHistory", "value": "{{ l1.text }}" },
        { "name": "withoutHistory", "value": "{{ l2.text }}" }
      ] } }
  ],
  "edges": [
    { "id": "e-s-l1", "source": "s1", "target": "l1" },
    { "id": "e-l1-l2", "source": "l1", "target": "l2" },
    { "id": "e-l2-e", "source": "l2", "target": "e1" }
  ]
}
```

为什么把两开两关放进**同一次运行**：

- 历史在运行期间不会变化（注入只读 `pool.conversation`，不回写），所以两次调用看到的会话完全相同；
- 于是「`l1.promptTokens - l2.promptTokens`」就是**历史贡献的 token 数**，不受时间、并发、其他客户端影响；
- 如果拆成两次运行，第二次运行的历史已经多了第一条回答，差值就不再是干净的历史长度。

两个节点的输出**必须相同**（mock 只回显最后一条 user 消息），这本身也是一条断言：**历史是前置的，不是追加的**。

### 3.2 G2：让历史「肉眼可见」

```json
{
  "version": "1",
  "nodes": [
    { "id": "s1", "type": "start", "position": { "x": 0, "y": 0 },
      "data": { "inputs": [ { "name": "topic", "type": "string", "required": true } ] } },
    { "id": "l1", "type": "llm", "position": { "x": 1, "y": 0 },
      "data": { "title": "历史回显", "prompt": "历史：\n{{ conversation.history }}\n本轮：{{ inputs.topic }}", "useHistory": false } },
    { "id": "e1", "type": "end", "position": { "x": 2, "y": 0 },
      "data": { "outputs": [ { "name": "answer", "value": "{{ l1.text }}" } ] } }
  ],
  "edges": [
    { "id": "e-s-l", "source": "s1", "target": "l1" },
    { "id": "e-l-e", "source": "l1", "target": "e1" }
  ]
}
```

`useHistory` 为 `false`，靠模板直接引用 `{{ conversation.history }}`；mock 回显最后一条 user 消息，于是 `answer` 里会原样带上历史文本。

这解决了 mock 的一个局限：**它只回显最后一条 user 消息**，而 `useHistory` 注入的历史是更早的消息，不会出现在回显里。所以：

- 历史**内容**用 G2 验（可见）；
- 历史**注入动作**用 G1 的 token 差值验（可计量）。

## 4. 用例矩阵

### 4.1 会话 CRUD 与归属

| # | 操作 | 期望 |
| --- | --- | --- |
| C1 | `POST /apps/{id}/conversations {}` | `201`，`messageCount=0`，`title=null` |
| C2 | `POST` 带 `title="测试会话"` | `201`，`title="测试会话"` |
| C3 | `GET /apps/{id}/conversations` | `200`，`items` 按 `updatedAt` 倒序 |
| C4 | `GET /conversations/{id}` | `200`，字段与 C2 完全一致 |
| C5 | `DELETE /conversations/{id}` | `204`，无响应体 |
| C6 | 删除后再 `GET` | `404 Conversation not found` |
| C7 | 用**另一个用户**的 token `GET` | `404 Conversation not found`（不是 403） |
| C8 | 把属于 app1 的会话拿去 `POST /apps/{app2}/run` | `404 Conversation not found` |
| C9 | `POST` 121 个字符的标题 | `400 Conversation title is too long` |
| C10 | `POST` 120 个 emoji 的标题 | `201`（码点计数，不是 UTF-16 码元） |

C10 是 C9 的对照：如果实现用错了 `title.length`（UTF-16），120 个 emoji 会被算成 240 而误拒。

### 4.2 历史注入

在一个**新建会话**里按顺序执行：

| # | 图 | 输入 | 期望 |
| --- | --- | --- | --- |
| H1 | G2 | `topic="第一轮"`，`userMessage="第一轮"` | `answer` 含 `历史：` 与 `本轮：第一轮`；历史部分为空 |
| H2 | G2 | `topic="第二轮"`，`userMessage="第二轮"` | `answer` 含 `user: 第一轮` 与 `assistant: echo: ...` |
| H3 | G1 | `topic="第三轮"`，`userMessage="第三轮"` | `withHistory` 与 `withoutHistory` 文本**完全相同** |
| H4 | G1（同一轮） | — | `node_finished(l1).output.usage.promptTokens - node_finished(l2).output.usage.promptTokens` = 前 4 条消息的字符数之和 |
| H5 | G1 | 不传 `conversationId` | `400 llm node l1 useHistory requires a conversation` |

H4 的算法（mock 的 `prompt_tokens` 是请求里**所有消息** `content.length` 之和）：

```text
l1 请求 = [历史 Human/AI ...] + [Human(渲染后的 prompt)]
l2 请求 =                      [Human(渲染后的 prompt)]
差值   = 历史所有消息的 content 长度之和
```

用实测消息表来算期望值：

```powershell
$msgs = (Invoke-RestMethod -Method Get "http://localhost:3001/conversations/$convId/messages" -Headers $TH).items
# 运行完 H3 后，消息序列是：
# 1 user 第一轮 | 2 assistant ... | 3 user 第二轮 | 4 assistant ... | 5 user 第三轮 | 6 assistant ...
# H3 运行时读到的历史是前 4 条（不含本轮 user）
$historyLen = ($msgs[0..3] | ForEach-Object { $_.content.Length } | Measure-Object -Sum).Sum
```

断言：

```powershell
$l1 = Get-NodeOutput "_sse.txt" "l1"
$l2 = Get-NodeOutput "_sse.txt" "l2"
($l1.usage.promptTokens - $l2.usage.promptTokens) -eq $historyLen
```

预期：`True`。

### 4.3 截断窗口

| # | 操作 | 期望 |
| --- | --- | --- |
| T1 | 两端 `.env` 设 `MAX_HISTORY_MESSAGES=4`，**重启两端** | 历史只取最近 4 条 |
| T2 | 在已有 6 条消息的会话里再跑 G1 | 差值 = 第 3~6 条消息的字符数之和（不是前 4 条） |
| T3 | 设 `MAX_HISTORY_MESSAGES=0`（非法值） | 回退默认 20（对比 T2 的差值变大） |
| T4 | 两端都不设该变量 | 默认 20，与阶段 9 文档一致 |

T2 是「最近」而不是「最早」的实证：如果实现写成 `asc + limit`，差值会等于前 4 条，和期望值不符。

> **注意**：TS 的 `maxHistoryMessages()` 在**每次调用时**读 `process.env`，Python 的 `settings` 在进程启动时加载。为了保证两端口径一致，改完 env 必须**重启两端**再测；只重启一端会出现「一端 4 条、一端 20 条」的假分叉。

### 4.4 错误路径

| # | 请求 | HTTP | message |
| --- | --- | --- | --- |
| E1 | `POST /apps/{id}/run`，G1，无 `conversationId` | `400` | `llm node l1 useHistory requires a conversation` |
| E2 | `conversationId` 是不存在的 uuid | `404` | `Conversation not found` |
| E3 | `conversationId` 属于另一个应用 | `404` | `Conversation not found` |
| E4 | 另一个用户运行你的应用 | `404` | `App not found`（先命中应用归属） |
| E5 | `conversationId` 显式传 `null` | `400` | 类型校验（两端同状态码） |
| E6 | `userMessage` 超过 4000 字符 | `400` | 类型校验（两端同状态码） |

E5 专门验「显式 `null` 与缺省不同」：缺省是合法的，`null` 必须被拒。两端各测一次：

```powershell
$body = @{ inputs = @{ topic = "x" }; conversationId = $null } | ConvertTo-Json -Depth 5
Write-Json "_null.json" $body
foreach ($port in 3001, 8000) {
  curl.exe -s -o _e.txt -w "$port => %{http_code}`n" -X POST "http://127.0.0.1:$port/apps/$appId/run" `
    -H "Authorization: Bearer $(if ($port -eq 3001) { $tsToken } else { $pyToken })" `
    -H "Content-Type: application/json" --data-binary "@_null.json"
  Get-Content _e.txt
}
```

预期：两端都是 `4xx`（具体形状不同：Nest 是 `{"statusCode":400,...}`，FastAPI 是 `{"detail":[...]}`，但**状态码类别一致**）。

### 4.5 失败留痕

| # | 操作 | 期望 |
| --- | --- | --- |
| F1 | 在会话里跑 G3（401） | SSE 终态是 `run_failed`，`message="llm request unauthorized"`；`l1` **没有** `node_finished` |
| F2 | 立刻查消息 | 只多了一条 `user`，**没有** assistant |
| F3 | 再跑 G1（正常图） | 历史里包含 F1 那条 user（失败不删除已发生的事实） |
| F4 | 查会话 `messageCount` | 等于实际消息数，不把失败算成一轮完整对话 |

F3 是一个容易被忽略的断言：失败运行留下的 user 消息会进入下一轮历史。如果产品上不希望如此，应该在「失败后回滚用户消息」——本项目**刻意不回滚**，因为用户确实说过那句话。

## 5. 跨端一致性

### 5.1 五个接口逐字节对比

```powershell
# 两端各建一个会话（共用同一张表，id 不同）
$convTs = (Invoke-RestMethod -Method Post "http://localhost:3001/apps/$appId/conversations" -Headers $TH `
  -ContentType "application/json" -Body (@{ title = "跨端" } | ConvertTo-Json)).id

foreach ($path in "/conversations/$convTs", "/apps/$appId/conversations", "/conversations/$convTs/messages") {
  $a = (curl.exe -s -H "Authorization: Bearer $tsToken" "http://127.0.0.1:3001$path") | Out-String
  $b = (curl.exe -s -H "Authorization: Bearer $pyToken" "http://127.0.0.1:8000$path") | Out-String
  "$path => $(if (Compare-Object $a $b) { 'DIFF' } else { 'SAME' })"
}
```

预期三行都是 `SAME`。

> 先确认不是 401：如果 token 失效，两边返回同样的 401 体，`Compare-Object` 也会说 `SAME`（假阳性）。用 `$a.Substring(0, 20)` 看一眼前缀。

### 5.2 事件级 diff（同一张 G1，两端各跑一次）

比较**事件名序列**与**每帧 payload 的键集合**，忽略具体值（`runId`、`elapsedMs`、`text` 里的随机无关内容）。

```powershell
function Get-EventShape($file) {
  $shape = @()
  foreach ($line in Get-Content $file) {
    if ($line -like 'event: *') {
      $shape += $line.Substring(7)
    } elseif ($line -like 'data: *') {
      $obj = $line.Substring(6) | ConvertFrom-Json
      # 只保留键名并排序：值里的 runId / elapsedMs 天然不同
      $shape += (($obj.PSObject.Properties.Name | Sort-Object) -join ',')
    }
  }
  return $shape
}

# TS 跑一次
curl.exe -sS -N -X POST "http://127.0.0.1:3001/apps/$appId/run" -H "Authorization: Bearer $tsToken" `
  -H "Content-Type: application/json" --data-binary "@_run_g1_ts.json" -o _sse_ts.txt

# Python 跑一次（独立会话，避免互相影响）
$convPy = (Invoke-RestMethod -Method Post "http://localhost:8000/apps/$appId/conversations" -Headers $PH `
  -ContentType "application/json" -Body (@{ title = "跨端-py" } | ConvertTo-Json)).id
# 把 _run_g1_py.json 里的 conversationId 换成 $convPy 后再跑
curl.exe -sS -N -X POST "http://127.0.0.1:8000/apps/$appId/run" -H "Authorization: Bearer $pyToken" `
  -H "Content-Type: application/json" --data-binary "@_run_g1_py.json" -o _sse_py.txt

Compare-Object (Get-EventShape _sse_ts.txt) (Get-EventShape _sse_py.txt)
```

预期：无输出。事件序列应类似：

```text
run_started              appId,conversationId,runId
node_started             nodeId,nodeType
node_finished            nodeId,nodeType,output
node_started             nodeId,nodeType
node_finished            nodeId,nodeType,output
node_started             nodeId,nodeType
node_finished            nodeId,nodeType,output
run_finished             elapsedMs,outputs,runId
```

`node_finished.output` 的内部键（`text` / `model` / `usage`）也会因为 `output` 是一个对象而被整体比较——这里只比到 `output` 这一层；要更细就得递归取键，属于阶段 4 已经做过的深度 diff。

### 5.3 消息表同库对比

两端写的是**同一张表**，所以「跨端一致」在这里等价于「读出来一样」：

```powershell
$a = (curl.exe -s -H "Authorization: Bearer $tsToken" "http://127.0.0.1:3001/conversations/$convTs/messages") | Out-String
$b = (curl.exe -s -H "Authorization: Bearer $pyToken" "http://127.0.0.1:8000/conversations/$convTs/messages") | Out-String
Compare-Object $a $b
```

预期：无输出。`createdAt` 都带 `Z`、毫秒三位；`runId` 为 `null` 时键仍然存在。

## 7. 前端手工验收

1. 打开 `http://localhost:3000/apps/{appId}`，保存 G2 到画布；
2. 「会话调试（多轮）」→「新建会话」，下拉框出现 `会话 xxxxxxxx（0 条）`；
3. 输入「第一轮」发送：立刻出现 user 气泡与 `…`，随后 assistant 逐字增长；
4. 结束后条数变 2，时间显示为**本地时间**（不是裸 UTC 字符串）；
5. 输入「第二轮」发送：回答里能看到 `user: 第一轮`；
6. 切到「（未选会话 · 不保存历史）」再发送：出现提示，且**不产生**新记录，条数仍是 4；
7. 「删除当前会话」→ 回到未选状态，下拉框里该会话消失；
8. 把 `apps/web/.env.local` 的 `NEXT_PUBLIC_API_BASE` 从 `3001` 改成 `8000`，重启前端，刷新：同一会话的消息、条数、时间显示完全一致；
9. 断网 / 停掉后端后再发送：出现错误提示，`running` 恢复为 `false`，气泡不残留「`…`」。

第 8 步是本阶段的最终验收动作：**换后端，前端零改动，会话不断档**。

## 10. 面试考点汇总

| 问题 | 一句话答案 |
| --- | --- |
| 怎么证明历史真进了 prompt？ | 让模板引用 `{{ conversation.history }}` 看回显；再用 `prompt_tokens` 差值精确计量 |
| 为什么用 mock 的 `prompt_tokens` 做差分？ | mock 按请求里所有消息的 `content.length` 求和，差值恰好等于历史贡献 |
| 为什么对照要放在同一张图里？ | 同一次运行内历史不变，差值不受并发与其他客户端影响 |
| 为什么注入对照的两个节点输出必须相同？ | 历史是前置的，最后一条 user 仍是本轮 prompt，mock 只回显它 |
| 截断验收为什么要重启？ | TS 每次调用读 `process.env`，Python 在启动时读 Settings；只重启一端会假分叉 |
| `run_failed` 为什么只能出现一次？ | 前端靠首个终态关闭 loading，第二个终态会让 UI 同时显示成功与错误 |
| 事件 diff 忽略哪些字段？ | `runId` / `elapsedMs` / 具体文本；比事件名序列与 payload 键集合 |
| 失败后下一轮还能看到那条 user 吗？ | 能。写入发生在开流前，失败不回滚——用户确实说过那句话 |
| 为什么要验 `null` 与「缺省」？ | 两端对显式 `null` 的判定必须一致，否则契约测试分叉 |
| 工具节点的历史为什么只存最终文本？ | `ToolMessage` 缺 `tool_call_id` 上下文，回放会被 provider 拒绝 |

## 11. 阶段收尾

阶段 9 交付的完整链路：

```text
契约（0.9.0）
  └── 5 个会话接口 + RunRequest.conversationId/userMessage + LlmNodeData.useHistory
        │
Prisma 迁移（DDL 唯一所有者）
  └── conversations / messages + (conversation_id, seq) 唯一 + ON DELETE CASCADE
        │
api-ts
  └── ConversationsModule + run() 先读后写 + pool.conversation + useHistory + 助手消息先于终态
        │
api-py
  └── SQLAlchemy 映射 + 相关子查询 + IntegrityError 重试 + 同一顺序与文案
        │
web
  └── Zod 校验 + 会话面板 + 乐观气泡 + finally 重拉纠正
```

下一篇进入阶段 10「发布与 API」：

- `POST /apps/{id}/publish` 的快照语义与 `published_graph_json`；
- API Key 的生成、哈希存储与撤销；
- 对外 `POST /public/apps/{appId}/run`（API Key 鉴权 + 只读已发布快照 + SSE）；
- 发布面板与 curl 调用示例。

阶段 9 留下的唯一「已知缺口」也将在那里被明确：**对外运行不带会话**（`hasConversation = false`），带 `useHistory` 的图在发布后走公开接口会 400——这是刻意的边界，不是遗漏。
