## 1. 图的形状

画布不是“一张图片”，是一份 JSON：

```text
Graph
├── version: "1"          ← 结构版本，不是应用版本
├── nodes[]
│   ├── id                ← 前端生成，图内唯一
│   ├── type              ← start | end | llm | knowledge | condition | aggregator | iteration
│   ├── position {x, y}   ← 画布坐标
│   └── data {}           ← 节点配置，自由结构；由执行引擎按类型解释
└── edges[]
    ├── id
    ├── source / target   ← 节点 id
    └── sourceHandle      ← 分支节点的出口标识（如 condition 的 caseId / else）
```

三条边界：

| 层 | 谁负责 | 内容 |
| --- | --- | --- |
| HTTP 结构 | `GraphDto` + class-validator | 字段类型、枚举、嵌套对象 |
| 图语义 | `validateGraph` | 唯一性、连通性、自环、分支出口 |
| 节点配置 | 执行引擎 | `data` 里 `prompt` / `topK` / `conditions` 的具体含义 |

**本篇只做前两层。`data` 内部结构留到各节点自己的阶段**——现在校验它，等于把执行引擎的规则提前抄一遍，改一处要改两处。

> **面试考点 · 为什么 `version` 是字符串 `"1"` 而不是数字？**
> 字符串可以承载 `"1"`、`"2"`、`"1.1"`、`"2026-10"` 等任意形态，比较时不会遇到浮点精度问题（`1.10 === 1.1`），也不会因为 JSON 数字被反序列化成 `number` / `bigint` 而分叉。
> 更重要的是：**它是“结构版本”而不是“应用版本”**。将来节点结构不兼容变更时，读到 `"1"` 的老图可以做迁移，读到 `"2"` 的才按新规则解析。现在固定 `"1"`，是为了给未来留一个显式的判断点。

> **面试考点 · 为什么 GET 草稿不校验，PUT / publish 才校验？**
> - 草稿是“半成品”：用户可能只放了一个 `start` 节点就保存，此时不可能满足“至少一个 end”。
> - 如果 GET 也校验，历史脏数据会让画布**打不开**，用户连修的机会都没有。
> - PUT 校验的是“你要存进来的东西”，publish 校验的是“你要上线的东西”——后者才是必须完整的时刻。
>
> **一句话：读宽容、写严格；进生产最严格。**

## 3. 结构校验：`GraphDto`

**完整文件路径：`apps/api-ts/src/graph/dto/graph.dto.ts`**

```ts
import { Type } from 'class-transformer'
import { IsArray, IsDefined, IsIn, IsNumber, IsObject, IsOptional, IsString, ValidateNested } from 'class-validator'

const NODE_TYPES = ['start', 'end', 'llm', 'knowledge', 'condition', 'aggregator', 'iteration'] as const

/** 对应契约 `NodePosition`。 */
class NodePositionDto {
  @IsNumber()
  x!: number

  @IsNumber()
  y!: number
}

/** 对应契约 `GraphNode`。`data` 为节点各自的配置（自由结构，不做内部约束）。 */
class GraphNodeDto {
  @IsString()
  id!: string

  @IsIn(NODE_TYPES)
  type!: (typeof NODE_TYPES)[number]

  // @ValidateNested 只声明“要递归校验”，
  // @Type 才告诉 class-transformer 把普通对象转成 NodePositionDto 实例
  @IsDefined()
  @ValidateNested()
  @Type(() => NodePositionDto)
  position!: NodePositionDto

  @IsObject()
  data!: Record<string, unknown>
}

/** 对应契约 `GraphEdge`（`sourceHandle` / `targetHandle` 可选，可为 null）。 */
class GraphEdgeDto {
  @IsString()
  id!: string

  @IsString()
  source!: string

  @IsString()
  target!: string

  // 可选 + 可为 null：契约类型是 ["string", "null"]
  @IsOptional()
  @IsString()
  sourceHandle?: string | null

  @IsOptional()
  @IsString()
  targetHandle?: string | null
}

/** PUT /apps/{id}/graph 的请求体 —— 对应契约 `Graph`。 */
export class GraphDto {
  @IsString()
  version!: string

  @IsArray()
  @ValidateNested({ each: true })
  @Type(() => GraphNodeDto)
  nodes!: GraphNodeDto[]

  @IsArray()
  @ValidateNested({ each: true })
  @Type(() => GraphEdgeDto)
  edges!: GraphEdgeDto[]
}
```

> **面试考点 · 为什么 `@ValidateNested()` 必须配 `@Type()`？**
> `ValidationPipe` 拿到的是 `JSON.parse` 出来的**普通对象**，`nodes` 里每一项的 `position` 也是普通对象，没有 `NodePositionDto` 的原型，也就没有装饰器元数据。
> `@Type(() => GraphNodeDto)` 让 class-transformer 先做实例化，`@ValidateNested` 才能递归找到子属性上的 `@IsNumber()`。少了 `@Type`，嵌套校验会**静默失效**——最难查的一类 bug：看起来写了校验，实际什么都没校验。
>
> **追问：`each: true` 是什么？**
> 告诉 class-validator 对数组的**每个元素**执行该规则，而不是把数组当成一个整体。

> **面试考点 · `data` 为什么只写 `@IsObject()`？**
> 因为它的结构依赖节点类型：`start` 有 `inputs`，`llm` 有 `prompt`，`condition` 有 `conditions`。在 DTO 层穷举会写出一个巨大的条件校验，而且每加一种节点就要改 DTO。
> 拆开之后职责清晰：**DTO 保证“data 是个对象”，`validateGraph` 保证“图整体自洽”，执行引擎保证“这种节点的 data 能跑”。**

## 4. 语义校验：`validateGraph`（阶段 3 的规则 1~7）

**完整文件路径：`apps/api-ts/src/graph/graph.validator.ts`**

```ts
import type { Graph } from '@mini-dify/contract'

/**
 * 图**语义**校验（纯函数）。
 *
 * 与 api-py 的 `app/graph/validator.py::validate_graph` 逐条对齐：
 * 规则顺序、同规则内的遍历顺序、文案模板完全一致，见
 * `packages/contract/error-messages.md` §3。
 *
 * 返回错误文案数组（可能为空）；调用方用 `"; "` 连接成一个 `message`。
 * 注意：本函数**不含**「读取草稿」时的豁免 —— 草稿为 null 时读取返回合法空图，
 * 不走本校验；只有 `PUT` / `publish` 才调用本函数（空图会因规则 3/4 不通过）。
 */
export function validateGraph(graph: Graph): string[] {
  const errors: string[] = []

  // 规则 1：version 必须为 "1"
  if (graph.version !== '1') {
    errors.push('graph version must be 1')
  }

  // 规则 2：节点 id 必须唯一（按数组顺序，每个重复 id 只报一次）
  const seenNodeIds = new Set<string>()
  const reportedNodeIds = new Set<string>()
  for (const node of graph.nodes) {
    if (seenNodeIds.has(node.id) && !reportedNodeIds.has(node.id)) {
      errors.push(`node id must be unique: ${node.id}`)
      reportedNodeIds.add(node.id)
    }
    seenNodeIds.add(node.id)
  }

  // 规则 3：恰好一个 start 节点（0 个或 ≥2 个都报此条）
  if (graph.nodes.filter((node) => node.type === 'start').length !== 1) {
    errors.push('graph must contain exactly one start node')
  }

  // 规则 4：至少一个 end 节点
  if (graph.nodes.filter((node) => node.type === 'end').length === 0) {
    errors.push('graph must contain at least one end node')
  }

  // 规则 5：边 id 必须唯一（按数组顺序，每个重复 id 只报一次）
  const seenEdgeIds = new Set<string>()
  const reportedEdgeIds = new Set<string>()
  for (const edge of graph.edges) {
    if (seenEdgeIds.has(edge.id) && !reportedEdgeIds.has(edge.id)) {
      errors.push(`edge id must be unique: ${edge.id}`)
      reportedEdgeIds.add(edge.id)
    }
    seenEdgeIds.add(edge.id)
  }

  // 规则 6：边的 source/target 必须指向存在的节点（先 source 后 target）
  const nodeIds = new Set(graph.nodes.map((node) => node.id))
  for (const edge of graph.edges) {
    if (!nodeIds.has(edge.source)) {
      errors.push(`edge ${edge.id} references unknown node: ${edge.source}`)
    }
    if (!nodeIds.has(edge.target)) {
      errors.push(`edge ${edge.id} references unknown node: ${edge.target}`)
    }
  }

  // 规则 7：不允许自环（source === target）
  for (const edge of graph.edges) {
    if (edge.source === edge.target) {
      errors.push(`edge ${edge.id} must not connect a node to itself`)
    }
  }

  return errors
}
```

> 规则 8~10（`condition` / `aggregator` / `iteration` 的专项校验）在阶段 8 追加，本篇不写。

### 4.1 规则一览

| # | 规则 | 文案 |
| --- | --- | --- |
| 1 | `version === "1"` | `graph version must be 1` |
| 2 | 节点 id 唯一 | `node id must be unique: {id}` |
| 3 | 恰好一个 `start` | `graph must contain exactly one start node` |
| 4 | 至少一个 `end` | `graph must contain at least one end node` |
| 5 | 边 id 唯一 | `edge id must be unique: {id}` |
| 6 | 边的端点存在 | `edge {edgeId} references unknown node: {nodeId}` |
| 7 | 禁止自环 | `edge {edgeId} must not connect a node to itself` |

调用方把数组用 `"; "` 拼起来放进统一错误体的 `message`：

```ts
const errors = validateGraph(graph)
if (errors.length > 0) {
  throw new BadRequestException(errors.join('; '))
}
```

> **面试考点 · 为什么校验函数返回数组，而不是抛第一个错？**
> 用户改图时希望一次看到所有问题，而不是“改一个、再报一个”。
> 但代价是**顺序必须稳定**：两套后端如果遍历顺序不同，`message` 的拼接结果就不同，契约测试会红。所以规则顺序、同一规则内的数组遍历顺序、重复项只报一次，全部写进 `error-messages.md`。**错误文案的顺序也是契约的一部分。**

> **面试考点 · 重复 id 为什么只报一次？**
> 三个节点都叫 `a` 时，朴素写法会报两次“duplicate id: a”。用户看到两条一样的错误，会以为有两处不同的问题。
> 实现用两个 `Set`：`seen` 记录出现过，`reported` 记录已报过。**只对“第一次发现重复”的那一刻报错。** 这也让两套后端的输出可以逐字节比对。

> **面试考点 · 为什么禁止自环，却允许成环？**
> - 自环（`a → a`）没有业务意义，一定是误操作（拖线拖回自己）。
> - 成环是**功能**：阶段 6 的 ReAct 就是“LLM → 工具 → LLM”的循环，阶段 8 的迭代节点也需要回边。
>
> 所以规则 7 只拦 `source === target`，不做拓扑排序、不检测环。**校验要拦住“确定的错误”，不要拦住“看起来奇怪但合法”的结构。**

> **面试考点 · 为什么规则 6 对一条边可能报两条错？**
> `source` 和 `target` 是两个独立检查。一条边两端都指向不存在的节点时，用户需要知道两端都错了，而不是只看到 source 的错误。文案里带 `edge.id` 和具体缺失的 `node id`，才能定位。
> **报错要带“哪个对象的哪个字段”，而不是只说“图非法”。**

```text
graph version must be 1; graph must contain exactly one start node; graph must contain at least one end node
```

> **面试考点 · 怎么保证两套后端“逐字节一致”？**
> 不能靠“照着写一遍”的自觉。做法是：
>
> 1. 文案模板写进 `packages/contract/error-messages.md`，两边都引用同一份文档；
> 2. 用同一组测试图分别喂给 TS 与 Python 的 `validateGraph`，比较 `join('; ')` 的字符串；
> 3. 把它放进契约测试，任何一边改了顺序或标点，CI 立刻失败。
>
> 这是“契约优先”的真正含义：**共享的不只是 OpenAPI 结构，还有所有对外可见的行为细节。**
