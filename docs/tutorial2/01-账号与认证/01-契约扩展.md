# 01 · 契约扩展（账号与认证）

> 阶段 1 · 第 1 步
>
> 做完：`openapi.yaml` 增加 `/auth/register`、`/auth/login`、`/auth/me`，定义 Bearer 安全方案、3 种错误响应和 5 个 schema；`packages/contract/src/index.ts` 同步类型。下一课两套后端照这份契约实现。

## 1. 先把三个决策定下来

写 YAML 之前先想清楚，否则后面两端实现一定会各写各的。

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 注册返回什么 | `201` + `UserResponse` | 创建了用户资源；不自动发 token，注册与登录职责分开 |
| 登录返回什么 | `200` + `TokenResponse` | 登录不创建资源，只是换取凭证 |
| 当前用户怎么取 | `GET /auth/me` + Bearer | 前端刷新页面后用 token 换回用户信息 |
| 邮箱重复 | `409 Conflict` | 请求本身合法，但与现有资源冲突 |
| 密码规则 | 仅注册要求 ≥ 8 位 | 登录只校验“对不对”，不重复做格式校验 |
| 响应里有没有密码 | 永远没有 | `UserResponse` 只暴露 `id/email/role/createdAt` |

## 2. 改 `openapi.yaml`

**完整文件路径：`packages/contract/openapi.yaml`**

### 2.1 先递增版本号

```yaml
info:
  title: mini-dify API
  # 阶段 0 是 0.1.0；新增认证接口后递增到 0.2.0
  # 必须与 src/index.ts 的 CONTRACT_VERSION 同步
  version: 0.2.0
```

### 2.2 在 `paths` 下追加三个接口

```yaml
paths:
  # /health 保持阶段 0 的定义不变，这里省略

  # -------------------------------------------------------------------------
  # 阶段 1 新增：注册 / 登录 / 当前用户
  # -------------------------------------------------------------------------

  /auth/register:
    post:
      # operationId 两端保持一致，便于按名字对照实现
      operationId: register
      summary: 注册
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/RegisterRequest"
      responses:
        # 201：创建了用户资源（不是 200）
        "201":
          description: 注册成功
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/UserResponse"
        # 400：字段缺失 / 邮箱格式错 / 密码太短 / 多传字段
        "400":
          $ref: "#/components/responses/BadRequest"
        # 409：邮箱已被注册（请求合法，但与现有资源冲突）
        "409":
          $ref: "#/components/responses/Conflict"

  /auth/login:
    post:
      operationId: login
      summary: 登录
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/LoginRequest"
      responses:
        "200":
          description: 登录成功
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/TokenResponse"
        "400":
          $ref: "#/components/responses/BadRequest"
        # 401：邮箱不存在或密码错误，统一文案，不告诉调用方是哪一种
        "401":
          $ref: "#/components/responses/Unauthorized"

  /auth/me:
    get:
      operationId: getCurrentUser
      summary: 当前登录用户
      # security 引用下面的 bearerAuth；[] 表示 HTTP Bearer 没有 scope 概念
      security:
        - bearerAuth: []
      responses:
        "200":
          description: 当前用户
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/UserResponse"
        "401":
          $ref: "#/components/responses/Unauthorized"
```

> **面试考点 · 为什么注册返回 `201`，登录返回 `200`？**
>
> - `201 Created` 的语义是“服务器创建了一个新资源”。注册创建了 user，所以是 201；登录只是校验凭证并签发 token，没有创建资源，所以是 200。
> - `201` 可以带 `Location` 头指向新资源；本项目前端不依赖它，所以省略。
> - 不要把“注册成功”也写成 200：状态码是契约的一部分，客户端、网关、监控都按它判断行为。
>
> **追问：注册成功要不要直接返回 token？**
> 两种设计都常见。本项目选择“注册只建用户，登录才发 token”，让两条路径职责单一，也方便以后加邮箱验证、邀请制等流程。如果产品要求注册即登录，就把 `201` 的响应改成 `TokenResponse`，契约同步改，两端一起改。

### 2.3 在 `components` 下增加安全方案

> 2.3~2.5 三段都挂在**同一个** `components:` 下；示例为了聚焦各自内容重复写了 `components:`，实际文件只保留一个，`securitySchemes`、`responses`、`schemas` 是它的三个子块。

```yaml
components:
  securitySchemes:
    # 前端请求头：Authorization: Bearer <accessToken>
    bearerAuth:
      type: http
      scheme: bearer
      # 只是文档提示，告诉读者这里放的是 JWT
      bearerFormat: JWT
```

### 2.4 在 `components.responses` 下增加三种错误响应

```yaml
components:
  responses:
    # 400：请求体结构校验失败（缺字段、类型错、多字段）
    BadRequest:
      description: 参数校验失败
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/ErrorResponse"

    # 401：没带 token、token 无效/过期、登录凭证错误
    Unauthorized:
      description: 未认证或凭证无效
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/ErrorResponse"

    # 409：邮箱已注册
    Conflict:
      description: 资源冲突（如邮箱已存在）
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/ErrorResponse"
```

> **面试考点 · `400` / `401` / `409` 到底怎么选？**
>
> - `400 Bad Request`：请求本身不合法，重发多少次都一样。缺字段、邮箱格式错、密码太短、出现契约未声明的字段，都属于这一种。
> - `401 Unauthorized`：身份没通过。登录时“邮箱不存在”和“密码错误”必须返回**同一句** `Invalid email or password`，否则攻击者可以拿它枚举已注册邮箱。
> - `409 Conflict`：请求合法，但与服务器当前状态冲突。注册时邮箱已存在是典型场景。
> - 为什么不用 `403`？`403` 是“身份已认证，但没权限”。本项目阶段 1 还没有角色权限，所有登录用户权限相同，所以用不到。
>
> **追问：登录失败为什么不能返回 404？**
> `404 User not found` 会直接泄露“这个邮箱注册过没有”。统一 401 + 统一文案，才能避免账号枚举。

### 2.5 在 `components.schemas` 下增加五个结构

```yaml
components:
  schemas:
    # 统一错误体：两套后端必须逐字节一致
    ErrorResponse:
      type: object
      additionalProperties: false
      required: [statusCode, message, error]
      properties:
        statusCode:
          type: integer
          examples: [401]
        message:
          # 多条校验错误用 "; " 连接成一个字符串
          type: string
          examples: [Invalid email or password]
        error:
          # HTTP 状态码对应的短语，如 Bad Request / Unauthorized / Conflict
          type: string
          examples: [Unauthorized]

    # 注册请求：只允许 email + password
    RegisterRequest:
      type: object
      # 多传任何字段都会 400（两端都要拒绝）
      additionalProperties: false
      required: [email, password]
      properties:
        email:
          type: string
          format: email
        password:
          type: string
          # 只有注册校验长度；登录不校验，避免规则变更后老用户登不进来
          minLength: 8

    # 登录请求：只校验“像不像邮箱”，不校验密码长度
    LoginRequest:
      type: object
      additionalProperties: false
      required: [email, password]
      properties:
        email:
          type: string
          format: email
        password:
          type: string

    # 用户对外视图：绝不包含 passwordHash
    UserResponse:
      type: object
      additionalProperties: false
      required: [id, email, role, createdAt]
      properties:
        id:
          type: string
        email:
          type: string
        role:
          # 枚举而不是任意字符串：两端类型都能收窄，前端也能穷举
          type: string
          enum: [admin, member]
        createdAt:
          type: string
          format: date-time
          description: >-
            时间戳。必须为 UTC、ISO-8601、毫秒精度、以 `Z` 结尾
            （形如 2026-10-18T02:36:24.278Z，固定 24 字符）。

    # 登录响应：token + 用户信息
    TokenResponse:
      type: object
      additionalProperties: false
      required: [accessToken, tokenType, expiresIn, user]
      properties:
        accessToken:
          type: string
        tokenType:
          type: string
          # 固定 Bearer，前端拼 Authorization 头时不用猜
          enum: [Bearer]
        expiresIn:
          type: integer
          description: 有效期（秒）
        user:
          # 直接复用 UserResponse，避免两份用户结构漂移
          $ref: "#/components/schemas/UserResponse"
```

> **面试考点 · 为什么不能直接把数据库实体返回给前端？**
>
> - **会泄露敏感字段**：Prisma 的 `User` / SQLAlchemy 的 `User` 都有 `passwordHash`，直接序列化就把密码哈希发出去了。`UserResponse` 是“对外视图”，只包含允许公开的字段。
> - **会被批量赋值（mass assignment）**：如果请求 DTO 和数据库实体是同一个类，攻击者多传 `role: "admin"` 就可能被直接写进数据库。`RegisterRequest` 只有 `email/password`，从结构上堵死这条路。
> - **契约会跟着数据库漂移**：数据库加一列内部字段，接口响应就变了，前端和契约测试都会被动受影响。对外视图是稳定的边界。
> - 本项目的做法：请求用 `RegisterRequest` / `LoginRequest`，响应用 `UserResponse` / `TokenResponse`，数据库实体只在服务层内部使用。

> **面试考点 · Bearer Token 应该存在哪里？**
>
> - **`localStorage` + `Authorization: Bearer`**（本项目教学实现）：实现简单，跨标签页共享；缺点是任何 XSS 都能读走 token。
> - **`httpOnly` Cookie**：JS 读不到，XSS 偷不走；但浏览器会自动带上，必须额外处理 CSRF（SameSite、CSRF token）。
> - **内存 + refresh token**：access token 只放内存，刷新页面用 httpOnly 的 refresh token 换新；安全性最好，实现也最复杂。
> - 没有“绝对安全”的选项，只有取舍。教学项目选第一种是为了把 JWT 认证链路讲清楚；生产环境至少要配 httpOnly + SameSite，并加 CSP。
>
> **追问：JWT 能不能主动失效？**
> 纯 JWT 是无状态的，签发后在过期前一直有效。要支持“立即踢下线”，就得引入黑名单（Redis）或把 token 版本号写进用户表；本项目阶段 1 不做，靠短有效期控制风险。

## 3. 同步 TS 契约类型

**完整文件路径：`packages/contract/src/index.ts`**

阶段 1 的完整内容如下（后续阶段继续往下追加）：

```ts
/**
 * 契约 TS 类型（由 openapi.yaml 派生）。
 *
 * 唯一真源是 `packages/contract/openapi.yaml`；此文件保持与其逐字段一致。
 * 两套后端（NestJS / FastAPI）都必须返回符合本结构的数据。
 */

/** 契约版本；修改契约时递增，并与 openapi.yaml 的 info.version 保持同步。 */
export const CONTRACT_VERSION = '0.2.0'

/** GET /health 的响应体。 */
export interface HealthResponse {
  /** 固定为 'ok' */
  status: 'ok'
  /** 服务标识：api-ts | api-py */
  service: string
  /** 服务版本 */
  version: string
  /** 时间戳：UTC、ISO-8601、毫秒精度、以 `Z` 结尾（24 字符） */
  time: string
}

/** POST /auth/register 请求体。 */
export interface RegisterRequest {
  email: string
  /** 至少 8 位 */
  password: string
}

/** POST /auth/login 请求体。 */
export interface LoginRequest {
  email: string
  password: string
}

/** 用户对外视图（**绝不包含密码哈希**）。 */
export interface UserResponse {
  id: string
  email: string
  /** 角色：阶段 1 固定为 member，admin 预留给后续管理功能 */
  role: 'admin' | 'member'
  /** 时间戳：UTC、ISO-8601、毫秒精度、以 `Z` 结尾（24 字符） */
  createdAt: string
}

/** POST /auth/login 的响应体。 */
export interface TokenResponse {
  accessToken: string
  /** 固定为 'Bearer' */
  tokenType: 'Bearer'
  /** 有效期（秒） */
  expiresIn: number
  user: UserResponse
}

/**
 * 统一错误体。
 *
 * NestJS 默认抛 `{ statusCode, message, error }`；FastAPI 默认抛 `{ detail }`，
 * 所以 Python 侧需要自定义异常处理器把结构归一化。
 */
export interface ErrorResponse {
  statusCode: number
  message: string
  error: string
}
```

> 注意：`UserResponse.role` 写成字面量联合 `'admin' | 'member'`，而不是 `string`。这样前端 `switch (user.role)` 能穷举，新增角色时 TypeScript 会强制你处理所有分支。

> **面试考点 · 契约怎么增量演进才不破坏旧客户端？**
>
> - **只做加法**：新增接口、新增可选字段、新增枚举值通常安全；删字段、改字段类型、把可选改成必填都是破坏性变更。
> - **`required` 要保守**：一旦写进 `required`，两端就必须永远返回它。阶段 0 的 `AppResponse.description` 就没放进 `required`，正是这个原因。
> - **枚举扩展要通知消费方**：给 `role` 加 `'editor'` 时，前端如果有 `switch` 的 `default` 分支要能兜底，否则新值会走进未处理路径。
> - **版本号不是装饰**：`info.version` 与 `CONTRACT_VERSION` 同步递增，契约测试、发布记录、前端 SDK 都靠它对齐。
> - **破坏性变更的正确做法**：新增 `/v2/auth/login`，旧接口保留一个过渡期；不要直接改 `/v1` 的字段含义。
