# 02 · 文档切分与向量化（知识库 RAG）

> 阶段 7 · 第 2 步
>
> 做完：`POST /knowledge-bases/{id}/documents` 能接收 multipart 文件，校验类型与大小，按固定参数切分，批量向量化，在一个事务里写入 `documents` + `chunks`，返回 `DocumentResponse`；删除文档级联删分块。
>
> **本篇面试考点**：Multer 内存存储与 1MB 三重防线 · 扩展名 vs MIME 判定 · `RecursiveCharacterTextSplitter` 参数语义（字符不是 token）· `keepSeparator` · 中文分隔符 · 切分参数为什么必须两端一致 · 批量 embedding · 为什么先嵌入再开事务 · `$executeRaw` 参数化与 `::vector` 字面量 · `chunkCount` 冗余的一致性 · `status` 为什么几乎总是 `ready`。

## 1. 上传链路

```text
POST /knowledge-bases/:id/documents  (multipart/form-data, field=file)
  → JwtAuthGuard（401）
  → FileInterceptor('file', { limits: 1MB })   ← 内存缓冲；超限抛 PayloadTooLarge
  → UploadTooLargeFilter（413 → 400 Document too large）
  → KbService.upload()
      1. findOwned(kb)                          → 404
      2. file === undefined                     → 400 Document is empty
      3. isSupportedDocument(name, mime)        → 400 Unsupported document type: xxx
      4. file.size > 1MB                        → 400 Document too large
      5. buffer.toString('utf8') 去空            → 400 Document is empty
      6. splitText(content) 过滤空白 chunk
      7. embedTexts(chunks)                     → 400 规范嵌入错误
      8. $transaction: 插 document + 逐条插 chunk + 更新 chunkCount
      9. 重新查询 document → DocumentResponse
```

三个“先于业务”的关卡（401 / 404 / 400）都在写库之前，**失败不会留下半条数据**。

## 2. DTO

**完整文件路径：`apps/api-ts/src/rag/dto/create-knowledge-base.dto.ts`**

```ts
import { IsOptional, IsString, MaxLength } from 'class-validator'

/** POST /knowledge-bases 请求体 —— 对应契约 `CreateKnowledgeBaseRequest`。 */
export class CreateKnowledgeBaseDto {
  // 名字的「空 / 过长」由服务层给出契约文案（见 error-messages.md §7.1）
  @IsOptional()
  @IsString()
  name?: string

  @IsOptional()
  @IsString()
  @MaxLength(500)
  description?: string
}
```

注意 `name` 没有 `@MinLength(1)`、也没有 `!`：

- 缺省时交给 Service 抛 `Knowledge base name is required`（契约文案）；
- 如果这里加 `@IsString()` + `!`，缺字段会先被 ValidationPipe 拦成“字段类型错误”，**文案就不是契约里那条了**。

**完整文件路径：`apps/api-ts/src/rag/dto/search-knowledge-base.dto.ts`**

```ts
import { Type } from 'class-transformer'
import { IsInt, IsOptional, IsString, Length, Max, Min } from 'class-validator'

/** POST /knowledge-bases/{id}/search 请求体 —— 对应契约 `SearchKnowledgeBaseRequest`。 */
export class SearchKnowledgeBaseDto {
  @IsString()
  @Length(1, 2000)
  query!: string

  @IsOptional()
  @Type(() => Number)
  @IsInt()
  @Min(1)
  @Max(20)
  topK?: number
}
```

`@Type(() => Number)`：JSON 里传 `"4"`（字符串）时先转数字，否则 `@IsInt()` 直接拒绝。这是**宽进严出**的取舍——契约说 `integer`，但转换一次成本很低、用户体验更好；真正的范围仍由 `@Min/@Max` 保证。

> **面试考点 · `@IsOptional()` 对 `null` 有效吗？**
> 有效，而且过头：`@IsOptional()` 会跳过 `undefined` **和** `null`。
> 所以 `{"topK": null}` 会通过校验，`dto.topK` 是 `null`，Service 里 `topK ?? 4` 又把它变回 4——**结果正确，但语义上“显式传 null”被静默接受了**。
> 阶段 2 的 `name: null` 是 500（Prisma 拒绝），这里因为用了 `??` 才没炸。**同一个装饰器，在不同字段上后果不同，要看下游怎么处理空值。**

**完整文件路径：`apps/api-ts/src/rag/upload-too-large.filter.ts`**

```ts
import {
  type ArgumentsHost,
  Catch,
  type ExceptionFilter,
  PayloadTooLargeException,
} from '@nestjs/common'
import type { Response } from 'express'

/**
 * 把上传超过 1MB 时的 `413 PayloadTooLargeException` 归一为契约要求的
 * `400` + `Document too large`（见 error-messages.md §7.1）。
 *
 * 只作用于上传路由（局部过滤器）；Multer 的 size 限制在拦截器里触发，
 * 业务层的二次检查抛的是普通 `BadRequestException`。
 */
@Catch(PayloadTooLargeException)
export class UploadTooLargeFilter implements ExceptionFilter {
  catch(_exception: PayloadTooLargeException, host: ArgumentsHost): void {
    const response = host.switchToHttp().getResponse<Response>()
    response.status(400).json({ statusCode: 400, message: 'Document too large', error: 'Bad Request' })
  }
}
```

### 3.1 为什么 413 要改成 400

契约里上传只声明了 `400 / 401 / 404`。Multer 超限抛的是 `PayloadTooLargeException`（413），如果不转换：

- 前端拿到的状态码契约里没有；
- Python 侧（自己读流）返回 400，两端不一致。

**状态码也是契约的一部分**，所以要用局部过滤器把它“拉回”契约。

> **面试考点 · 为什么 `FileInterceptor` 用默认的内存存储？**
> Multer 默认 `memoryStorage`：文件被读进 `file.buffer`。
> 本项目的文件上限 1MB，直接放内存最简单：
>
> - 不需要临时目录、不需要清理；
> - 切分与嵌入都是纯内存操作。
>
> 如果上限是 100MB，就必须用磁盘存储或流式处理——**内存存储的合理性取决于上限**。
> 另外 1MB × 并发上传数 = 峰值内存，这也是为什么上限不能随便调大。

## 4. 切分

**完整文件路径：`apps/api-ts/src/rag/splitter.ts`**

```ts
import { RecursiveCharacterTextSplitter } from '@langchain/textsplitters'

/**
 * 文档切分配置（**两端必须同参数**，见阶段 7 笔记）。
 *
 * 作为导出常量供文档/笔记引用；修改这里必须同步 Python 侧。
 */
export const SPLITTER_CONFIG = {
  chunkSize: 500,
  chunkOverlap: 80,
  separators: ['\n\n', '\n', '。', '！', '？', '. ', ' ', ''],
  keepSeparator: true,
} as const

/** 按 `SPLITTER_CONFIG` 把文本切成若干块（保持原顺序）。 */
export async function splitText(text: string): Promise<string[]> {
  const splitter = new RecursiveCharacterTextSplitter({
    chunkSize: SPLITTER_CONFIG.chunkSize,
    chunkOverlap: SPLITTER_CONFIG.chunkOverlap,
    separators: [...SPLITTER_CONFIG.separators],
    keepSeparator: SPLITTER_CONFIG.keepSeparator,
  })
  return splitter.splitText(text)
}
```

### 4.1 参数语义

| 参数 | 值 | 含义 |
| --- | --- | --- |
| `chunkSize` | 500 | 单块**最大字符数**（不是 token） |
| `chunkOverlap` | 80 | 相邻块重叠字符数，保证跨块语义不断裂 |
| `separators` | `['\n\n', '\n', '。', '！', '？', '. ', ' ', '']` | 递归切分优先级：先段落、再行、再中文句号、再英文句号、再空格、最后硬切 |
| `keepSeparator` | `true` | 分隔符留在块尾（`"第一句。"`），而不是被丢掉 |

`RecursiveCharacterTextSplitter` 的行为：

```text
1. 先用 "\n\n" 切 → 每个片段都 ≤ 500？是则结束
2. 还有超长片段 → 用 "\n" 继续切
3. 再超长 → 用 "。" / "！" / "？" / ". " / " "
4. 最后兜底 ""（逐字符硬切）
```

**先按语义边界切，再按长度兜底**——这是它比“固定长度切片”好的地方。

> **面试考点 · `chunkSize: 500` 是什么单位？**
> **字符**（LangChain JS 的 `splitText` 按字符串长度算）。
> 不是 token，也不是字节。
>
> - 中文 500 字 ≈ 350~500 token；
> - 英文 500 字符 ≈ 100~130 token。
>
> 所以“中文块”和“英文块”的实际 token 数差很多。真正要控 token，得用 tokenizer 计数，成本更高。
> 本项目的取舍：**用字符数换简单与两端一致**（Python 侧同样按字符）。若要精确控 token，应把切分参数改成“按 token 计”，并让两端用同一个 tokenizer。

> **面试考点 · `chunkOverlap` 为什么要有？**
> 假设一句话被切在两块之间：
>
> ```text
> 块1: "...订单在支付后 30 分钟内可以..."
> 块2: "...申请退款，超过 30 分钟不支持..."
> ```
>
> 检索时只命中块 2，模型看到的是“超过 30 分钟不支持”，缺少“30 分钟内”的上下文。
> 重叠 80 个字符，让关键句在两块里都出现一部分，**降低“语义被切断”的概率**。
>
> 代价：存储与 embedding 成本增加（约 `overlap / chunkSize` 的冗余）。80/500 = 16%，可接受。

> **面试考点 · 为什么分隔符里既有中文标点又有英文 `". "`？**
> 因为语料是中英混合：
>
> - 中文句子以 `。！？` 结尾；
> - 英文句子以 `. `（句号+空格）结尾——**只写 `.` 会误伤小数 `3.14` 和网址**。
>
> `keepSeparator: true` 保证切出来的块读起来是完整句子，而不是缺标点的碎片。

### 4.2 两端必须同参

切分结果决定 `chunk_index` 与 `content`，而这两者会进检索结果。如果两端参数不同：

- 同一个文件在 api-ts 上传后切成 12 块，在 api-py 上传后切成 9 块；
- 同一句 query 检索，两端返回的 `content` 不同；
- 契约测试无法逐字节对比。

所以 `SPLITTER_CONFIG` 是**跨语言契约的一部分**，不是实现细节。Python 侧（`04` 篇）必须逐项复刻：

```python
SPLITTER_CONFIG = {
    "chunk_size": 500,
    "chunk_overlap": 80,
    "separators": ["\n\n", "\n", "。", "！", "？", ". ", " ", ""],
    "keep_separator": True,
}
```

> **注意**：即使参数相同，两套 LangChain 的分块算法实现也可能有细微差异（版本、边界处理）。
> 所以验收时**不要假设“参数一致 ⇒ 切分一致”**，要拿同一个文件实际比一次 `chunk_count` 与 `content`（见 `05` 篇）。

## 5. 上传与入库

**完整文件路径：`apps/api-ts/src/rag/kb.service.ts`**（阶段 7 核心）

```ts
/** 单文档大小上限：1MB（FileInterceptor 与本服务各兜一层）。 */
export const MAX_DOCUMENT_BYTES = 1024 * 1024

/** 允许的扩展名（大小写不敏感）。 */
const ALLOWED_EXTENSIONS = ['.txt', '.md', '.markdown']

  /**
   * 上传并处理：校验类型/大小/空 → 切分 → 批量嵌入 → 事务写 `documents` + `chunks` → 更新 `chunkCount`。
   *
   * 嵌入失败（含未配置密钥）映射为 400 规范文案（见 error-messages.md §7）。
   */
  async upload(
    ownerId: string,
    knowledgeBaseId: string,
    file: UploadedDocument | undefined,
  ): Promise<DocumentResponse> {
    await this.findOwned(ownerId, knowledgeBaseId)
    if (file === undefined) {
      throw new BadRequestException('Document is empty')
    }
    const mimeType = file.mimetype && file.mimetype !== '' ? file.mimetype : 'application/octet-stream'
    if (!isSupportedDocument(file.originalname, mimeType)) {
      throw new BadRequestException(`Unsupported document type: ${mimeType}`)
    }
    if (file.size > MAX_DOCUMENT_BYTES) {
      throw new BadRequestException('Document too large')
    }
    const content = file.buffer.toString('utf8')
    if (content.trim() === '') {
      throw new BadRequestException('Document is empty')
    }

    const chunks = (await splitText(content)).filter((chunk) => chunk.trim() !== '')
    if (chunks.length === 0) {
      throw new BadRequestException('Document is empty')
    }
    const vectors = await embedOrBadRequest(chunks)

    const documentId = randomUUID()
    await this.prisma.$transaction(async (tx) => {
      await tx.document.create({
        data: {
          id: documentId,
          knowledgeBaseId,
          name: file.originalname,
          mimeType,
          sizeBytes: file.size,
          status: 'ready',
        },
      })
      for (let index = 0; index < chunks.length; index += 1) {
        // 向量写入只能走原生 SQL（Prisma 不支持 vector 类型）；字符串字面量再 ::vector。
        await tx.$executeRaw`
          INSERT INTO chunks (id, document_id, knowledge_base_id, chunk_index, content, embedding, created_at)
          VALUES (${randomUUID()}, ${documentId}, ${knowledgeBaseId}, ${index}, ${chunks[index]}, ${toVectorLiteral(vectors[index])}::vector, now())
        `
      }
      await tx.document.update({ where: { id: documentId }, data: { chunkCount: chunks.length } })
    })

    const document = await this.prisma.document.findUniqueOrThrow({ where: { id: documentId } })
    return toDocumentResponse(document)
  }
```

辅助函数：

```ts
/** 允许的类型：扩展名 `.txt` / `.md` / `.markdown`，或 `content-type` 以 `text/` 开头。 */
function isSupportedDocument(fileName: string, mimeType: string): boolean {
  const lower = fileName.toLowerCase()
  if (ALLOWED_EXTENSIONS.some((extension) => lower.endsWith(extension))) {
    return true
  }
  return mimeType.startsWith('text/')
}

/** 嵌入失败：`RunError` 在对外的普通 JSON 接口里映射为 400 规范文案。 */
async function embedOrBadRequest(texts: string[]): Promise<number[][]> {
  try {
    return await embedTexts(texts)
  } catch (error) {
    throw new BadRequestException(error instanceof Error ? error.message : 'embedding request failed: unknown')
  }
}
```

### 5.1 校验顺序

```text
file 缺失 → 类型不支持 → 大小超限 → 内容为空 → 切分为空
```

顺序有意义：

- **先看类型再看大小**：一个 2MB 的 `.exe` 应报 “Unsupported document type”，而不是 “too large”（用户更该知道“格式不对”）；
- **先看大小再看内容**：`buffer.toString()` 对超大文件是浪费；
- **切分为空**：只有空白字符的文件，`content.trim()` 已经拦住；切分后仍可能为空（比如只有分隔符），所以再兜一次。

> **面试考点 · 扩展名和 MIME 判断，哪个更可信？**
> 都不可信，但用于不同目的：
>
> | 来源 | 可否伪造 | 用途 |
> | --- | --- | --- |
> | 文件名扩展名 | 客户端随便写 | 用户体验（“我是 .md”） |
> | `Content-Type` | 客户端随便写 | 同上 |
> | **文件内容** | 最终真相 | 真正的安全判定 |
>
> 本项目只接受纯文本，所以**只看扩展名/MIME 足够**（最坏情况是上传一个二进制但解码成乱码，随后被切分/嵌入，不会执行）。
> 如果允许图片/PDF，就必须做**魔术字节（magic bytes）**校验，不能信扩展名。
> **“能不能伪造”与“要不要防”是两件事——先问这个字段被用来做什么。**

### 5.2 为什么先嵌入、后开事务

```text
embedTexts(chunks)          ← 外部 HTTP 调用，可能 100ms ~ 数秒
$transaction(...)           ← 数据库事务，毫秒级
```

如果反过来把 `embedTexts` 放进事务里：

- 事务长时间持有连接与锁（`documents` 行、`chunks` 的写入）；
- 外部 API 超时会让事务悬挂；
- 并发上传时连接池很快被打满（Prisma 默认连接数有限）。

**事务里只放数据库操作**，是所有“先调外部服务再写库”场景的通则。

> 代价：嵌入成功但写库失败时，向量白算了（没有副作用，只是浪费）。
> 反过来“先写库再嵌入”会产生 `status='ready'` 但 `chunk_count=0` 的坏数据，更糟。

> **面试考点 · 那 `status: 'failed'` 什么时候用？**
> 当前实现是同步处理：失败就直接 400，**不落库**，所以永远写不进 `failed`。
> 保留这个枚举值是为了**将来改异步处理**：
>
> ```text
> 上传 → 立刻返回 document(status='processing') → 后台切分/向量化
>      → 成功 status='ready'，失败 status='failed' + error_message
> ```
>
> 契约提前留了字段，实现可以后补。**枚举值超前于实现是合理的，但要写清楚“当前不会出现”。**

### 5.3 原生 SQL 写向量

Prisma 的 `Chunk.embedding` 是 `Unsupported("vector(1536)")`：

- 可以出现在 schema 里（用于建列）；
- **不能**在 `create` / `update` 的 `data` 里赋值。

所以向量只能走 `$executeRaw`：

```ts
await tx.$executeRaw`
  INSERT INTO chunks (...)
  VALUES (${randomUUID()}, ${documentId}, ${knowledgeBaseId}, ${index}, ${chunks[index]}, ${toVectorLiteral(vectors[index])}::vector, now())
`
```

`toVectorLiteral`：

```ts
export function toVectorLiteral(vector: number[]): string {
  return `[${vector.join(',')}]`
}
```

### 5.4 `::vector` 与参数化

`${...}` 是 Prisma 的**参数占位**（底层是 `$1`），不是字符串拼接——所以 `content` 里带引号、换行都安全（**防注入**）。

但 `vector` 类型没有原生 JS 映射，只能：

1. 把数组转成字符串 `"[0.1,0.2,...]"`；
2. 交给 PG，再显式 `::vector` 转换。

```sql
-- 实际执行的 SQL（示意）
INSERT INTO chunks (..., embedding, ...) VALUES ($1, $2, ..., $6::vector, now())
```

> **面试考点 · 为什么不能 `'[...]'::vector(1536)` 一起写？**
> 可以写，但没必要：列已经是 `vector(1536)`，PG 会自动校验维度。
> 显式写 `::vector` 是为了让 PG 知道“这个参数是向量”，否则它会把参数当 `text`，`vector` 列与 `text` 之间没有隐式转换，报错：
>
> ```text
> column "embedding" is of type vector but expression is of type text
> ```

> **面试考点 · 逐条 INSERT 会不会太慢？**
> 500 字符一块、1MB 文本最多约 2000 块，逐条插入确实不快（几十到几百毫秒）。
> 可选优化：
>
> - `INSERT ... VALUES (...), (...), ...` 批量插入（注意参数数量上限 65535）；
> - `COPY`（最快，但 Prisma 不直接支持）。
>
> 当前规模（1MB）下逐条足够，且代码最清晰。**先正确，再优化；并且要知道优化的方向在哪。**

### 5.5 `chunkCount` 为什么更新两次

```ts
create document（chunkCount 默认 0）
  → 插 chunks
  → update document.chunkCount = chunks.length
```

能不能创建时就写 `chunkCount: chunks.length`？

- 能，因为切分在事务前就完成了；
- 但那样 `create` 与 `chunks` 的写入**不在同一个“事实”上**——如果将来改成流式切分/分批写入，`chunkCount` 就得最后算。

当前实现选择“最后更新”，是为了让不变量清晰：**`chunkCount` 永远等于实际插入的行数**。

> **面试考点 · `chunkCount` 是冗余字段，为什么不用 `_count`？**
> `DocumentResponse.chunkCount` 在列表里也要返回。如果用 `_count: { select: { chunks: true } }`：
>
> - 列表 N 个文档就多一次聚合查询（或 join）；
> - 文档列表是高频接口。
>
> 冗余一个整数，换列表查询更简单。代价是**写入时必须维护**——这里在同一事务里更新，保证一致。
> 与阶段 7 `01` 篇的 `chunks.knowledge_base_id` 是同一类取舍：**读多写少 → 冗余；写多读少 → 聚合。**

### 6.7 列表顺序


## 7. 面试考点汇总

| 问题 | 答案要点 |
| --- | --- |
| Multer 内存存储 | 1MB 上限下合理；上限 × 并发 = 峰值内存 |
| 三重大小防线 | 拦截器 limits、业务层二次检查、前端提示 |
| 413 → 400 | 状态码也是契约；局部过滤器归一 |
| 扩展名 vs MIME | 都可伪造；纯文本场景足够；二进制需 magic bytes |
| `chunkSize` 单位 | 字符，不是 token；中英文 token 密度不同 |
| `chunkOverlap` | 降低跨块语义断裂；成本约 overlap/chunkSize |
| 中文分隔符 | `。！？` + 英文 `. `（避免误伤小数点） |
| `keepSeparator` | 块尾保留标点，读起来完整 |
| 两端同参 | 分块结果进检索结果，是契约的一部分 |
| 先嵌入后事务 | 事务内只放 DB 操作，避免长事务与悬挂 |
| 向量写入 | `Unsupported` 只能用 `$executeRaw` |
| `::vector` | 参数是 text，需显式转 vector |
| `chunkCount` 冗余 | 列表高频读；同事务维护一致性 |
| `status: failed` | 为异步处理预留；当前同步失败不落库 |
| 文档/库排序不同 | 导航用倒序，内容用正序 |
