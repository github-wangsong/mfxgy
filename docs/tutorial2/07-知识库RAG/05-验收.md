# 05 · 验收（知识库 RAG）

> 阶段 7 · 收尾
>
> 验收目标：**同一份文件，两套后端切出同样的块、检索出同样的命中；上传失败不落库；删除不留孤儿。**
>
> **本篇面试考点**：为什么要用确定性 mock embedding · 为什么比 `md5(content)` 而不是比 `chunkCount` · 浮点分数怎么比 · 如何验证“失败不落库” · 为什么验收脚本要进仓库 · 共享数据库下两套后端的权限边界 · 近似检索的验收不能只看 top-1。

```dotenv
EMBEDDING_MODEL=mock-embedding
```

`tools/mock-llm/server.mjs` 的 `/v1/embeddings` 是**确定性哈希向量器**：

```text
同一段文本 → 同一组 token → 同一个 1536 维向量
```

这是跨后端对比成立的前提：两端各自调用一次嵌入，但拿到的是**逐位相同的向量**。

> **面试考点 · 为什么不用真实 embedding 模型做验收？**
> 真实模型的输出可能因为：
>
> - 服务端版本升级；
> - 批大小不同导致的浮点归约顺序差异；
> - 限流/重试后的不同快照。
>
> 而向量只要有 `1e-7` 的差异，余弦分数就会变，排序在“两条分数接近”时可能翻转。
> 验收要验证的是**逻辑一致**，不是“模型是否稳定”。用确定性 mock 把变量固定住，才能断言“两端实现一致”。
> 真实模型做**冒烟**（能跑通、维度对），mock 做**回归**（逐字节比对）——分工不同。

## 3. 对比脚本

**完整文件路径：`scripts/p7-compare.ps1`**

```powershell
# 阶段 7 验收：同一文件两端切分/检索对比
# 用法：pwsh scripts/p7-compare.ps1 -TsToken <token> -PyToken <token>
param(
  [Parameter(Mandatory = $true)] [string] $TsToken,
  [Parameter(Mandatory = $true)] [string] $PyToken,
  [string] $Fixture = "p7-fixtures/refund.md"
)

$ErrorActionPreference = "Stop"
$ts = "http://localhost:3001"
$py = "http://localhost:8000"

function New-Kb([string] $base, [string] $token, [string] $name) {
  $body = @{ name = $name; description = "p7" } | ConvertTo-Json
  return Invoke-RestMethod -Method Post -Uri "$base/knowledge-bases" `
    -Headers @{ Authorization = "Bearer $token" } -ContentType "application/json" -Body $body
}

function Send-Doc([string] $base, [string] $token, [string] $kbId, [string] $path) {
  # PowerShell 5 的 Invoke-RestMethod 上传 multipart 不稳定，统一用 curl.exe
  $json = curl.exe -s -X POST "$base/knowledge-bases/$kbId/documents" `
    -H "Authorization: Bearer $token" -F "file=@$path"
  return $json | ConvertFrom-Json
}

$kbTs = New-Kb $ts $TsToken "p7-ts"
$kbPy = New-Kb $py $PyToken "p7-py"

$docTs = Send-Doc $ts $TsToken $kbTs.id $Fixture
$docPy = Send-Doc $py $PyToken $kbPy.id $Fixture

"TS chunkCount = $($docTs.chunkCount)"
"PY chunkCount = $($docPy.chunkCount)"
if ($docTs.chunkCount -ne $docPy.chunkCount) {
  throw "chunkCount mismatch: $($docTs.chunkCount) vs $($docPy.chunkCount)"
}

# 逐块对比内容（md5）
$tsRows = docker compose exec -T postgres psql -U minidify -d minidify -t -A -F ',' -c `
  "select chunk_index, md5(content) from chunks where document_id = '$($docTs.id)' order by chunk_index;"
$pyRows = docker compose exec -T postgres psql -U minidify -d minidify -t -A -F ',' -c `
  "select chunk_index, md5(content) from chunks where document_id = '$($docPy.id)' order by chunk_index;"

$diff = Compare-Object $tsRows $pyRows
if ($diff) {
  $diff | Format-Table | Out-String | Write-Host
  throw "chunk content mismatch"
}
"chunk content: identical ($($docTs.chunkCount) blocks)"

# 检索对比：只比 documentId/chunkIndex 顺序
$query = @{ query = "退款要多久到账"; topK = 4 } | ConvertTo-Json
$hitTs = (Invoke-RestMethod -Method Post -Uri "$ts/knowledge-bases/$($kbTs.id)/search" `
  -Headers @{ Authorization = "Bearer $TsToken" } -ContentType "application/json" -Body $query).hits
$hitPy = (Invoke-RestMethod -Method Post -Uri "$py/knowledge-bases/$($kbPy.id)/search" `
  -Headers @{ Authorization = "Bearer $PyToken" } -ContentType "application/json" -Body $query).hits

$orderTs = ($hitTs | ForEach-Object { "$($_.chunkIndex)" }) -join ","
$orderPy = ($hitPy | ForEach-Object { "$($_.chunkIndex)" }) -join ","
"TS hit order = $orderTs"
"PY hit order = $orderPy"
if ($orderTs -ne $orderPy) {
  throw "hit order mismatch"
}

"score(TS) = " + (($hitTs | ForEach-Object { $_.score.ToString('F6') }) -join ",")
"score(PY) = " + (($hitPy | ForEach-Object { $_.score.ToString('F6') }) -join ",")

"PASS"
```

> **面试考点 · 为什么比 `md5(content)`，而不是只比 `chunkCount`？**
> `chunkCount` 相同只说明“块数一样”，完全可能：
>
> - 在错误的位置切开（两块换了边界）；
> - 内容被不同地规范化（少一个换行）。
>
> `md5` 比的是**每块内容逐字节一致**，能定位到“第几块开始不同”。
> 比起打印全文，`md5` 输出短、可直接 `Compare-Object`。
> **验收要选“能定位”的粒度，而不是“能通过”的粒度。**

## 4. 用例矩阵

| # | 用例 | 期望 |
| --- | --- | --- |
| R1 | 建库 `{name:"退款政策"}` | 201，`documentCount: 0` |
| R2 | 建库 `{name:""}` | 400 `Knowledge base name is required` |
| R3 | 列表 | 200，按 `createdAt` 倒序 |
| R4 | 上传 `refund.md` | 201，`status:"ready"`，`chunkCount > 0` |
| R5 | 同一文件两端上传 | `chunkCount` 与每块 `md5` 完全一致 |
| R6 | 文档列表 | 200，按 `createdAt` **正序** |
| R7 | 检索「退款要多久到账」 | 200，`hits` 按 `score` 降序，命中含“30 分钟”那段 |
| R8 | 省略 `topK` | 响应 `topK: 4` |
| R9 | `topK: 0 / 21` | 400 |
| R10 | 空知识库检索 | 200，`hits: []` |
| R11 | 越权检索/上传/删除 | 404 `Knowledge base not found` |
| R12 | 无 token | 401 |
| R13 | 上传 `.exe` / 空文件 / >1MB | 400，三种规范文案 |
| R14 | 删除文档 | 204，`chunks` 计数 0 |
| R15 | 删除含文档的知识库 | 204（Python 侧验证 `passive_deletes`） |
| R16 | 无 `LLM_API_KEY` 上传 | 400，且 `documents` 行数不变 |
| R17 | 画布 `start → knowledge → end` | `retrieval` 事件一次，`context` 非空 |

### 4.1 R7：命中质量

```powershell
$hits = (curl.exe -s -X POST "http://localhost:3001/knowledge-bases/$kbId/search" `
  -H "Authorization: Bearer $token" -H "Content-Type: application/json" `
  -d '{"query":"退款多久到账"}' | ConvertFrom-Json).hits
$hits | Select-Object chunkIndex, score, @{n='head';e={$_.content.Substring(0,[Math]::Min(30,$_.content.Length))}}
```

用确定性哈希向量时，**不要期待“语义相似”**：

- 哈希向量只按 token 重合度产生相似性；
- 检索结果能验证“链路通、排序对、分数公式对”，**不能验证“语义质量”**；
- 语义质量要用真实 embedding 做冒烟（看命中是否包含“到账时间”那段）。

> **面试考点 · 近似检索的验收为什么不能只看 top-1？**
> HNSW 是近似算法：
>
> - 插入顺序、`ef_search`、数据量都会影响结果；
> - 小数据集下往往“恰好精确”，数据一多就可能漏掉真实最近邻。
>
> 验收应关注：
>
> 1. **同一数据 + 同一查询，两端结果一致**（确定性）；
> 2. **分数单调**（`ORDER BY` 与 `score` 方向一致）；
> 3. **召回率**（用一批标注 query 统计 top-k 命中比例），而不是单条 top-1。
>
> 本项目只做 1、2；第 3 点需要离线评测集，属于“生产化”范畴。

### 4.2 R9：`topK` 越界

```powershell
# 两端应都返回 400，message 文案一致
curl.exe -s -i -X POST "http://localhost:3001/knowledge-bases/$kbId/search" `
  -H "Authorization: Bearer $token" -H "Content-Type: application/json" -d '{"query":"x","topK":0}'
curl.exe -s -i -X POST "http://localhost:8000/knowledge-bases/$kbId/search" `
  -H "Authorization: Bearer $pyToken" -H "Content-Type: application/json" -d '{"query":"x","topK":0}'
```

注意：`topK` 校验分别由 class-validator 与 Pydantic 完成，**文案可能不同**（阶段 2 已记录同类差异）。
本阶段验收以 **状态码 + 结构** 为准；文案统一留到契约测试收口。

### 4.3 R16：失败不落库

```powershell
# 记录行数
docker compose exec postgres psql -U minidify -d minidify -t -A -c `
  "select count(*) from documents where knowledge_base_id = '$kbId';"

# 把 api-py 的 LLM_API_KEY 置空、重启
# 上传 → 400
curl.exe -s -X POST "http://localhost:8000/knowledge-bases/$kbId/documents" `
  -H "Authorization: Bearer $pyToken" -F "file=@p7-fixtures/refund.md"

# 再查行数，应不变
```

同样对 api-ts 验证一次。

> **为什么这条必须验？**
> 因为“先嵌入、后写库”的顺序是本篇的核心决策。如果哪天有人把 `embedTexts` 挪进 `$transaction`，表面仍能工作，但失败时会留下半条数据或长时间持有连接。
> 验收是**对决策的回归测试**。

### 4.4 R17：节点

```powershell
curl.exe -s -N -X POST http://localhost:3001/apps/<APP_ID>/run `
  -H "Authorization: Bearer $token" -H "Content-Type: application/json" `
  -d '{"inputs":{"question":"退款多久到账"}}'
```

检查：

- `retrieval` 只出现一次；
- `retrieval.data.hits` 与直接调 `/search` 的结果一致（同一库、同一 topK）；
- `node_finished( knowledge ).output.context` = 各 `content` 以 `\n\n` 连接（可用 PowerShell 自行 join 后比对）；
- Python 侧重跑一次，`retrieval` 的 `hits` 顺序一致。

| 4 | SSE 事件序 | `curl -N` 看 `run_started → node_* → run_finished` |

检查方式：用阶段 4 的那个 `start → llm1 → end1` 图跑一次，应完全正常。

## 6. 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `type "vector" does not exist` | 迁移没执行 `CREATE EXTENSION` | 手工 `psql -c "CREATE EXTENSION vector"`，修迁移并重建库 |
| `expected 1536 dimensions, not 1024` | 换了 embedding 模型但没改列 | 改回 1536 模型，或写迁移改列 + 重算 |
| `column "embedding" is of type vector but expression is of type text` | 少了 `::vector` / `CAST` | 补类型转换 |
| 删除知识库 500 `NotNullViolation` | Python 少了 `passive_deletes=True` | 补上并重启 |
| 检索结果一直空 | 上传失败但前端没提示 / 没提交事务 | 查 `chunks` 行数；查 `documents.chunk_count` |
| `chunkCount` 两端不同 | 切分参数或库版本不同 | 对比 `SPLITTER_CONFIG`；用 `md5` 定位第一处差异 |
| 索引消失 | `migrate dev` 生成了 `DROP INDEX` | 删迁移目录 + `db:index` |
| 上传返回 422 | FastAPI 把缺文件当参数校验失败 | 确认 `file: UploadFile \| None = File(default=None)` |
| `documents` 有行但 `chunks` 为 0 | 先写了文档再嵌入失败 | 检查是否把写库提前到了嵌入之前 |
| 前端检索 400 但 curl 正常 | `topK` 是字符串 / `NaN` | 提交前 `Number.isInteger` 校验 |

## 8. 面试考点汇总

| 问题 | 答案要点 |
| --- | --- |
| 为什么确定性 mock | 固定变量，验证“实现一致”而非“模型稳定” |
| mock 能验什么 | 链路、维度、排序、分数公式、跨端一致 |
| mock 不能验什么 | 语义相关性、召回率、真实延迟 |
| 比 `md5` 而非 `chunkCount` | 能定位到具体块；块数相同不代表内容相同 |
| 浮点分数怎么比 | 按精度（6 位）或只比顺序；不逐位比 |
| 近似检索验收 | 一致性 + 单调性；召回率需离线评测集 |
| 失败不落库怎么验 | 记录行数 → 制造失败 → 行数不变 |
| 脚本进仓库 | 验收可重复、可 CI、可交接 |
| 共享库的权限边界 | 归属由每条 SQL/ORM 查询保证；两套后端都必须校验 |
| 旧图回归 | `knowledge` 预检只对知识库节点生效，不污染旧图 |

## 9. 阶段 7 小结

```text
契约（01）
  → 表与向量列（01）
  → 切分 + 嵌入 + 入库（02）
  → 检索 + 节点（03）
  → Python 复刻 + 前端页（04）
  → 同一文件、同一查询，两端一致（05）
```

阶段 7 的核心不是“RAG 能跑”，而是：

1. **向量维度是数据库约束**，不是配置项；
2. **切分参数是跨语言契约**，必须固定并对比；
3. **外部调用在事务之外**，失败不留半条数据；
4. **近似检索的一致性**要靠确定性输入来验证。

下一阶段：**分支与循环**（Condition / Aggregator / Iteration），会第一次引入“一条图有多个出口”和“跨语言数值序列化对齐”。
