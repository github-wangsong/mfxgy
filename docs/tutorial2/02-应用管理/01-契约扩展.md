# 01 · 契约扩展（应用管理）

> 阶段 2 · 第 1 步
>
> 做完：`openapi.yaml` 从 `0.2.0` 升到 `0.3.0`，新增 5 个 `/apps` 操作与 4 个 schema；`packages/contract/src/index.ts` 里 `AppResponse` / `CreateAppRequest` / `UpdateAppRequest` / `AppListResponse` 可直接被两套后端引用。
>
> **本篇面试考点**：REST 的状态码语义（201 / 200 / 204）· PATCH 与 PUT 的区别 · 越权为什么返回 404 而不是 403 · `additionalProperties: false` · 默认值放服务端还是客户端 · 契约的增量演进。

## 1. 先定接口形状

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 路径 | `/apps`、`/apps/{id}` | 资源复数 + 路径参数，REST 惯例 |
| 创建返回 | `201` + `AppResponse` | 创建了资源，且要回传服务端生成的 id / 时间 |
| 更新方式 | `PATCH` + 全字段可选 | 只改传了的字段，避免 PUT 那种“整体覆盖” |
| 删除返回 | `204` 无响应体 | 删除后没有内容可返回 |
| 归属校验 | 只操作 `ownerId = 当前用户` 的应用；否则 `404` | 不泄露“这个 id 存在但不属于你” |
| `ownerId` 从哪来 | **只从 token 取**，请求体不接受 | 否则客户端可以伪造归属，越权创建/转移 |
| `mode` 默认值 | 服务端默认 `chatflow` | 客户端不传也能得到确定行为；默认值属于业务规则 |
| 列表排序 | `createdAt` 倒序（实现约定） | 契约不约束顺序，但两端必须一致，否则联调对不上 |
| 空描述 | 统一序列化成 `null` | 避免 `""` / `null` / 缺键三种状态 |

> `ownerId` 不进 `CreateAppRequest` 是这一阶段最重要的安全设计。**凡是“我是谁”的信息，都只能来自认证凭证，不能来自请求体。**

## 3. `/apps`：列表与创建

**完整文件路径：`packages/contract/openapi.yaml`**（`paths` 下的 `/apps`）

```yaml
  /apps:
    get:
      # operationId 是生成客户端 / 契约测试的锚点，命名一旦发布就不要改
      operationId: listApps
      summary: 列出当前用户的应用
      security:
        - bearerAuth: []
      responses:
        "200":
          description: 应用列表
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/AppListResponse"
        "401":
          $ref: "#/components/responses/Unauthorized"

    post:
      operationId: createApp
      summary: 创建应用
      security:
        - bearerAuth: []
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/CreateAppRequest"
      responses:
        # 创建成功 → 201，并回传完整资源
        "201":
          description: 创建成功
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/AppResponse"
        "400":
          $ref: "#/components/responses/BadRequest"
        "401":
          $ref: "#/components/responses/Unauthorized"
```

要点：

- 列表**只返回当前用户的应用**，`ownerId` 不在查询参数里出现——服务端从 token 取。
- `POST` 没有 `404`：创建不依赖任何已有资源。
- `POST` 有 `400`：`name` 必填、`mode` 枚举、多余字段都要在这里报错。

## 4. `/apps/{id}`：详情、更新、删除

**完整文件路径：`packages/contract/openapi.yaml`**（`paths` 下的 `/apps/{id}`）

```yaml
  /apps/{id}:
    get:
      operationId: getApp
      summary: 获取应用详情（仅限本人）
      security:
        - bearerAuth: []
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        "200":
          description: 应用详情
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/AppResponse"
        "401":
          $ref: "#/components/responses/Unauthorized"
        # 不存在，或存在但不属于当前用户 —— 都用 404
        "404":
          $ref: "#/components/responses/NotFound"

    patch:
      operationId: updateApp
      summary: 更新应用（仅限本人）
      security:
        - bearerAuth: []
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/UpdateAppRequest"
      responses:
        "200":
          description: 更新成功
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/AppResponse"
        "400":
          $ref: "#/components/responses/BadRequest"
        "401":
          $ref: "#/components/responses/Unauthorized"
        "404":
          $ref: "#/components/responses/NotFound"

    delete:
      operationId: deleteApp
      summary: 删除应用（仅限本人）
      security:
        - bearerAuth: []
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        # 204 必须没有 content：有 body 的 204 是协议错误
        "204":
          description: 删除成功
        "401":
          $ref: "#/components/responses/Unauthorized"
        "404":
          $ref: "#/components/responses/NotFound"
```

`404` 复用阶段 1 就定义好的公共响应：

**完整文件路径：`packages/contract/openapi.yaml`**（`components.responses.NotFound`）

```yaml
    NotFound:
      # 描述里明确写上了「或不属于当前用户」，这是对实现者的约定
      description: 资源不存在或不属于当前用户
      content:
        application/json:
          schema:
            $ref: "#/components/schemas/ErrorResponse"
```

> **面试考点 · 为什么“不是你的应用”返回 404 而不是 403？**
>
> - `403` 等于告诉攻击者：**这个 id 真实存在**，只是你没权限。配合遍历 id，就能枚举出系统里有哪些应用。
> - `404` 把“不存在”和“无权限”合并成同一种回答，不泄露资源存在性。这是 OWASP 推荐的**防枚举**做法。
> - 代价：真的写错 id 的用户也只会看到“不存在”，排查时少一点信息。安全优先。
>
> **追问：那什么时候该用 403？**
> 当资源本身是公开的（比如公开模板），但某个操作需要更高角色时。本项目阶段 2 所有应用都是私有的，所以统一 404。

> **面试考点 · PATCH 和 PUT 到底怎么选？**
>
> | | PUT | PATCH |
> | --- | --- | --- |
> | 语义 | 用请求体**整体替换**资源 | 只**部分修改** |
> | 没传的字段 | 被清空 / 置默认 | 保持不变 |
> | 幂等 | 是 | 是（本项目的实现） |
>
> 本项目改名字只传 `{"name": "..."}`，其余字段不该丢，所以用 PATCH。注意：`UpdateAppRequest` 没有必填字段，因此 `{}` 也是合法请求——服务端会原样返回。如果要禁止空更新，得在 schema 加 `minProperties: 1`，并同步两套后端；这一阶段先不做。

## 5. 四个 schema

**完整文件路径：`packages/contract/openapi.yaml`**（`components.schemas`）

```yaml
    AppResponse:
      type: object
      # 对应 class-validator 的 forbidNonWhitelisted / Pydantic 的 extra="forbid"
      additionalProperties: false
      # description 故意不在 required 里：空描述时实现应返回 null，而不是省略键
      required: [id, name, mode, ownerId, createdAt, updatedAt]
      properties:
        id:
          type: string
        name:
          type: string
        description:
          type: ["string", "null"]
        mode:
          type: string
          enum: [chatflow, workflow]
        # 归属用户 id；由服务端根据 token 写入
        ownerId:
          type: string
        createdAt:
          type: string
          format: date-time
          description: >-
            时间戳。必须为 UTC、ISO-8601、毫秒精度、以 `Z` 结尾
            （形如 2026-10-18T02:36:24.278Z，固定 24 字符）。
        updatedAt:
          type: string
          format: date-time
          description: >-
            时间戳。必须为 UTC、ISO-8601、毫秒精度、以 `Z` 结尾
            （形如 2026-10-18T02:36:24.278Z，固定 24 字符）。

    CreateAppRequest:
      type: object
      additionalProperties: false
      # 只有 name 必填
      required: [name]
      properties:
        name:
          type: string
          minLength: 1
          maxLength: 64
        description:
          type: string
          maxLength: 256
        mode:
          type: string
          enum: [chatflow, workflow]

    UpdateAppRequest:
      type: object
      additionalProperties: false
      # 全字段可选：PATCH 的语义就是“传什么改什么”
      properties:
        name:
          type: string
          minLength: 1
          maxLength: 64
        description:
          type: string
          maxLength: 256
        mode:
          type: string
          enum: [chatflow, workflow]

    AppListResponse:
      type: object
      additionalProperties: false
      required: [items]
      properties:
        items:
          type: array
          items:
            $ref: "#/components/schemas/AppResponse"
```

三个容易忽略的点：

1. **`description` 不在 `required`**，但实现应该恒定返回这个键（空值为 `null`）。所以前端 Zod 写成 `z.string().nullable().optional()`，兼容“键可能缺失”的契约字面含义。
2. **`mode` 在 `CreateAppRequest` 里没有默认值**。OpenAPI 的 `default` 只是文档，不会让服务端自动填；默认值必须写在业务代码里（NestJS 侧 `mode ?? 'chatflow'`）。
3. **`UpdateAppRequest` 允许 `description: ""`**：类型是 string，空串合法。服务端统一把空串归一化成 `null` 再入库，避免库里出现两种“空”。

## 6. TS 类型

**完整文件路径：`packages/contract/src/index.ts`**（追加在 `TokenResponse` 之后）

```ts
/** 应用对外视图（只暴露契约字段，不含内部实现细节）。 */
export interface AppResponse {
  id: string
  name: string
  /** 空描述统一序列化为 `null` */
  description: string | null
  /** 应用形态：chatflow（对话流） | workflow（工作流） */
  mode: 'chatflow' | 'workflow'
  /** 归属用户 id */
  ownerId: string
  /** 时间戳：UTC、ISO-8601、毫秒精度、以 `Z` 结尾（24 字符） */
  createdAt: string
  /** 时间戳：UTC、ISO-8601、毫秒精度、以 `Z` 结尾（24 字符） */
  updatedAt: string
}

/** POST /apps 请求体。 */
export interface CreateAppRequest {
  /** 1-64 位 */
  name: string
  /** 最多 256 位 */
  description?: string
  /** 不传时服务端默认 `chatflow` */
  mode?: 'chatflow' | 'workflow'
}

/** PATCH /apps/{id} 请求体（字段均可选）。 */
export interface UpdateAppRequest {
  /** 1-64 位 */
  name?: string
  /** 最多 256 位 */
  description?: string
  mode?: 'chatflow' | 'workflow'
}

/** GET /apps 的响应体。 */
export interface AppListResponse {
  items: AppResponse[]
}
```

> 注意 `AppResponse.description` 写成了必选：**两套后端实现都会返回这个键**（空值为 `null`），TS 侧按“实际行为”收紧，前端 Zod 按“契约字面”放宽。两者不冲突，但要知道为什么。

> **面试考点 · 契约里加接口，为什么先改 `openapi.yaml` 再写代码？**
>
> - 契约是**两套后端 + 一个前端**的共同输入。先改契约，三个人可以并行：TS 写 Nest、Python 写 FastAPI、前端写页面，谁也不用等谁。
> - 契约评审的成本远低于代码评审：加一个字段、改一个状态码，在 YAML 里一眼能看出来；等三份代码都写完再对齐，返工量是数倍。
> - 契约测试拿 `openapi.yaml` 当断言来源，**代码与契约不一致时测试直接红**，不靠人肉 review。
>
> **追问：`additionalProperties: false` 会不会太严格，以后加字段就破坏兼容？**
> 对**响应**来说，加字段本来就不该让老客户端崩——所以前端 Zod 对完整响应用 `strictObject` 是“开发期发现漂移”，对局部消费用 `z.object` 是“向前兼容”。对**请求**来说，严格是好事：客户端多传字段说明它理解错了契约，早报错早修。严格与兼容要分开讨论，不能一句“加字段没事”带过。
