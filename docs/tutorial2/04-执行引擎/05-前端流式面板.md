> **面试考点 · 为什么这里的字段全是 `optional()`，而普通响应 schema 是必填？**
> 两种校验的**目的不同**：
>
> - 普通响应（`GET /apps`）是完整对象，缺字段说明契约被破坏，必须报错；
> - SSE 的 `data` 是**增量片段**，它只用于“尽可能渲染”：`token` 帧缺 `text` 时跳过这一次追加即可，没必要让整个运行失败。
>
> 但要注意：**宽容解析 ≠ 不校验**。`parseEventData` 仍然会跑 Zod（类型错、不是 JSON 都返回 `null`），只是把“缺字段”降级成“这一帧不渲染”。
> 如果这是金融/计费场景，就应该反过来——缺字段必须中止。**校验的严格程度由失败代价决定。**

## 2. 分帧解析器

**完整文件路径：`apps/web/lib/sse.ts`**

```ts
/**
 * SSE 分帧解析。
 *
 * 为什么不用 `EventSource`？—— 浏览器的 `EventSource` **不能携带 `Authorization` 头**，
 * 而运行接口需要 `Bearer token` 且是 `POST`。因此改用
 * `fetch` + `response.body.getReader()`，自己按帧解析。
 *
 * 服务端帧格式：
 * - 工作流：`event: <name>\n` + `data: <单行 JSON>\n\n`
 * - Agent：`id: <seq>\n` + `event: <name>\n` + `data: <单行 JSON>\n\n`
 *
 * 解析要点：
 * - 以**空行**分隔事件；
 * - 同一事件的多个 `data:` 行按 `\n` 拼接（本协议每条只有一行，通用实现要支持）；
 * - 网络分块会**在任意字节处切断**：一个帧、甚至一行可能跨两个 chunk；
 * - 名称后的冒号可跟一个可选空格，需要剥掉；
 * - `id:` 行是事件的 `seq`（阶段 11 断线重连用），必须保留。
 */

/** 解析后的单个 SSE 事件。 */
export interface SseEvent {
  /** 事件名（缺省为 `message`）。 */
  event: string
  /** 拼接后的原始 payload 文本。 */
  data: string
  /** 帧的 `id:` 值；工作流帧没有该行，为 `null`。 */
  id: string | null
}

/** 把 `Response.body` 逐帧解析成 {@link SseEvent}。 */
export async function* parseSseStream(
  body: ReadableStream<Uint8Array>,
): AsyncGenerator<SseEvent, void, void> {
  const reader = body.getReader()
  // stream: true —— 关键。多字节 UTF-8 字符被 chunk 切断时，解码器会暂存残片。
  const decoder = new TextDecoder()
  // 尚未成完整行的残余文本（跨 chunk 拼接）。
  let buffer = ''
  // 当前事件累积的字段。
  let eventName = ''
  let eventId: string | null = null
  const dataLines: string[] = []
  let hasField = false

  /** 遇到空行：若已有字段则产出一个事件并重置状态。 */
  const flushFrame = (): SseEvent | null => {
    if (!hasField) return null
    const frame: SseEvent = {
      event: eventName === '' ? 'message' : eventName,
      data: dataLines.join('\n'),
      id: eventId,
    }
    eventName = ''
    eventId = null
    dataLines.length = 0
    hasField = false
    return frame
  }

  /** 处理一整行（不含行尾换行符）。 */
  const handleLine = (rawLine: string): SseEvent | null => {
    // 兼容 CRLF
    const line = rawLine.endsWith('\r') ? rawLine.slice(0, -1) : rawLine
    if (line === '') return flushFrame()
    if (line.startsWith(':')) return null // 注释行（心跳）忽略

    const colon = line.indexOf(':')
    const field = colon === -1 ? line : line.slice(0, colon)
    const rawValue = colon === -1 ? '' : line.slice(colon + 1)
    // 冒号后的第一个空格是分隔符，不属于值
    const value = rawValue.startsWith(' ') ? rawValue.slice(1) : rawValue

    if (field === 'id') {
      eventId = value
      hasField = true
    } else if (field === 'event') {
      eventName = value
      hasField = true
    } else if (field === 'data') {
      dataLines.push(value)
      hasField = true
    }
    return null
  }

  try {
    for (;;) {
      const { value, done } = await reader.read()
      if (done) break
      buffer += decoder.decode(value, { stream: true })

      // 每次只截取一个完整行，残余留在 buffer 等下一 chunk
      let newlineIndex: number
      while ((newlineIndex = buffer.indexOf('\n')) !== -1) {
        const line = buffer.slice(0, newlineIndex)
        buffer = buffer.slice(newlineIndex + 1)
        const frame = handleLine(line)
        if (frame !== null) yield frame
      }
    }

    // 流结束：冲掉解码器残片，处理最后一行（可能没有换行结尾）
    buffer += decoder.decode()
    if (buffer !== '') {
      const frame = handleLine(buffer)
      if (frame !== null) yield frame
      buffer = ''
    }
    // 末尾没有空行收尾时，把已累积字段作为最后一个事件产出
    const tail = flushFrame()
    if (tail !== null) yield tail
  } finally {
    reader.releaseLock()
  }
}
```

为什么不能“读一块、`split('\\n\\n')`”了事：

```text
chunk 1: "event: token\ndata: {\"text\":\"你"
chunk 2: "好\"}\n\nevent: node_finished\n..."
                ↑ 一个汉字被切成 3 字节，可能正好跨 chunk
```

- 按字节切会得到乱码；
- 按 `\n\n` 切会把半个事件当完整事件；
- 所以必须**文本缓冲 + 逐行处理 + 空行成帧**。

> **面试考点 · `TextDecoder` 不加 `{ stream: true }` 会怎样？**
> 默认解码把每个 chunk 当成**独立的完整文本**。UTF-8 的中文/emoji 占 3~4 字节，被网络切断时，前一个 chunk 末尾是半个字符，解码器会输出替换字符 `�`，而且**残片直接丢失**，后一个 chunk 也拼不回来。
> `{ stream: true }` 告诉解码器“后面还有”，它会暂存不完整序列，等下一个 chunk 补齐。
> 流结束时必须再调一次 `decoder.decode()`（无参数）把残片冲出来。
> **这是所有流式文本解析的第一课，与 SSE 无关——任何 `fetch` 流式响应都适用。**

> **面试考点 · 为什么 `id:` 现在没用还要保留？**
> 阶段 11 的 Agent 运行支持 `Last-Event-ID` 断线重连：浏览器/客户端重连时带上最后收到的 `id`，服务端从 `seq + 1` 继续推。
> 现在的工作流帧没有 `id:`，解析器返回 `null`；保留字段与解析逻辑，阶段 11 直接复用，不用改这个文件。
> **解析器要按“协议全集”实现，而不是按当前用到的最小子集。**

**完整文件路径：`apps/web/app/apps/[id]/page.tsx`**（阶段 4 新增部分）

```tsx
  // 调试运行面板状态
  const [runInputs, setRunInputs] = useState<Record<string, string>>({})
  const [running, setRunning] = useState(false)
  const [log, setLog] = useState<RunLogEntry[]>([])
  const [liveText, setLiveText] = useState('')
  const [runOutputs, setRunOutputs] = useState<Record<string, unknown> | null>(null)
  const [runError, setRunError] = useState<string | null>(null)
  // 日志序号用 ref：不参与渲染，避免每次自增都触发额外更新
  const seqRef = useRef(0)
```

### 3.1 输入收集

```tsx
  /** start 节点声明的输入变量。 */
  const startInputs: Array<{ name: string; type: 'string'; required: boolean }> = useMemo(() => {
    const start = nodes.find((node) => node.type === 'start')
    const declared = start?.data.inputs
    if (!Array.isArray(declared)) return []
    const result: Array<{ name: string; type: 'string'; required: boolean }> = []
    for (const item of declared) {
      if (typeof item !== 'object' || item === null) continue
      const row = item as Record<string, unknown>
      if (typeof row.name !== 'string' || row.name === '') continue
      result.push({ name: row.name, type: 'string', required: row.required === true })
    }
    return result
  }, [nodes])

  /** 运行输入：由 start 节点声明的变量生成（缺省空串）。 */
  function collectRunInputs(): Record<string, unknown> {
    const inputs: Record<string, unknown> = {}
    for (const decl of startInputs) {
      // 表单值始终是字符串；必填校验交给浏览器的 required + 后端的 start 节点
      inputs[decl.name] = runInputs[decl.name] ?? ''
    }
    return inputs
  }
```

> 这里的 `row as Record<string, unknown>` 是**节点 data 的内部形状**，不是网络响应。节点 `data` 在契约里是 `Record<string, unknown>`（自由结构），只能在消费点逐个字段判断类型。**契约说“自由”，消费方就必须自己收窄。**

### 3.2 消费事件

```tsx
  /**
   * 调试运行：`POST /apps/{id}/run`。
   *
   * 不能用 EventSource，改用 fetch + parseSseStream。
   * 预检失败时后端返回的是**普通 JSON 400**（不是流），
   * 因此先判断 `content-type`：非 `text/event-stream` 就按 JSON 读 message。
   */
  async function executeRun(token: string, inputs: Record<string, unknown>): Promise<void> {
    setRunning(true)
    setLog([])
    setLiveText('')
    setRunOutputs(null)
    setRunError(null)
    try {
      const res = await fetch(`${API_BASE}/apps/${appId}/run`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${token}` },
        body: JSON.stringify({ inputs }),
      })
      if (res.status === 401) {
        router.replace('/login')
        return
      }
      const contentType = res.headers.get('content-type') ?? ''
      // 三个条件缺一不可：HTTP 成功 + 是事件流 + 有 body
      if (!res.ok || !contentType.includes('text/event-stream') || res.body === null) {
        setRunError(await readApiErrorMessage(res))
        return
      }

      for await (const frame of parseSseStream(res.body)) {
        // 事件日志：每条都记，便于排查顺序
        setLog((prev) => [
          ...prev,
          { seq: seqRef.current++, name: frame.event, detail: summarizeFrame(frame.event, frame.data) },
        ])

        if (frame.event === 'token') {
          const parsed = parseEventData(frame.data, tokenEventSchema)
          if (parsed !== null && typeof parsed.text === 'string') {
            // 增量拼接：每次只追加，不做字符串查找/替换
            setLiveText((prev) => prev + parsed.text)
          }
        } else if (frame.event === 'run_finished') {
          const parsed = parseEventData(frame.data, runFinishedEventSchema)
          if (parsed !== null) setRunOutputs(parsed.outputs ?? {})
        } else if (frame.event === 'run_failed') {
          const parsed = parseEventData(frame.data, runFailedEventSchema)
          if (parsed !== null) setRunError(parsed.message ?? 'run failed')
        }
        // 其余事件（node_started / node_finished）阶段 4 只记日志，不做额外渲染

        // 逐事件让出一次，保证 React 能提交并绘制（token 才会一段段出现）
        await yieldToPaint()
      }
    } catch (err: unknown) {
      setRunError(err instanceof Error ? err.message : String(err))
    } finally {
      setRunning(false)
    }
  }

  /** 「调试运行」表单提交。 */
  async function handleRun(event: FormEvent<HTMLFormElement>): Promise<void> {
    event.preventDefault()
    const token = localStorage.getItem('accessToken')
    if (token === null) {
      router.replace('/login')
      return
    }
    await executeRun(token, collectRunInputs())
  }
```

```tsx
/** token 事件的 payload 摘要（`节点id · "文本"`），其余事件直接用原始 data 文本。 */
function summarizeFrame(name: string, data: string): string {
  if (name === 'token') {
    const parsed = parseEventData(data, tokenEventSchema)
    if (parsed === null) return data
    return `${parsed.nodeId ?? ''} · ${JSON.stringify(parsed.text ?? '')}`
  }
  return data
}

/** 让出一次宏任务，确保 React 能在每个事件之间提交更新。 */
function yieldToPaint(): Promise<void> {
  return new Promise((resolve) => {
    setTimeout(resolve, 0)
  })
}
```

> **面试考点 · React 19 已经自动批处理，为什么还要 `yieldToPaint`？**
> 自动批处理解决的是“**同一次**任务里的多次 `setState` 合并成一次渲染”，不是“让浏览器有机会绘制”。
> `for await` 的循环体如果一直不 `await` 宏任务，微任务会连续执行完，React 的更新虽然被调度，但浏览器可能直到流结束才获得一帧。表现就是：**转圈很久，然后文字一次性全出现**。
> `setTimeout(0)` 把控制权交回事件循环，浏览器可以绘制。替代方案：
>
> - 每 N 个 token 让出一次（减少开销）；
> - `requestAnimationFrame`（与刷新率对齐）；
> - 用 `startTransition` 降低优先级（不保证逐帧）。
>
> 这不是“React 的 bug”，而是**流式 UI 必须主动把渲染机会还给浏览器**。

> **面试考点 · 为什么 `setLog((prev) => [...prev, entry])` 在长流下会变慢？**
> 每次事件都复制整个数组，复杂度 O(n²)。几百条事件没问题；几千条就会明显卡顿。
> 更稳的写法：用 `useRef<RunLogEntry[]>` 累积，配合节流 `setLog([...ref.current])`；或用虚拟列表只渲染可视区。
> 这里保留简单写法，是因为调试面板的事件量在几十条量级。**知道复杂度，才知道什么时候该换实现。**

## 4. 面板 JSX

```tsx
<div className="stack stack--sm">
  <div className="label">运行输入</div>
  <div className="faint">由 start 节点的输入变量自动生成；带 * 为必填。</div>
  {startInputs.length === 0 && <div className="empty">start 节点未声明输入变量。</div>}

        />

    ))}
    <button className="btn btn-primary" type="submit" disabled={running}>

{runError !== null && <div className="alert alert-error">运行失败：{runError}</div>}

<div className="stack stack--sm">
  <div className="label">流式输出（token 累加）</div>
  <div className="output-box">{liveText}</div>

{runOutputs !== null && (
  <div className="stack stack--sm">
    <div className="label">运行输出（run_finished.outputs）</div>
    <pre className="code-block">{JSON.stringify(runOutputs, null, 2)}</pre>
  </div>

<div className="stack stack--sm">
  <div className="label">事件日志</div>
  <div className="event-list">

      <div key={entry.seq} className="event-row">
        <span className="event-name">{entry.name}</span>
        <span className="event-body">{entry.detail}</span>
      </div>
    ))}
  </div>
</div>
```

## 7. 面试考点汇总

| 问题 | 答案要点 |
| --- | --- |
| 为什么不用 `EventSource` | 只能 GET、不能带 `Authorization`；运行是 POST |
| 分帧为什么不能 `split('\\n\\n')` | chunk 在任意字节切断，可能切在帧中间、行中间、多字节字符中间 |
| `TextDecoder({ stream: true })` | 暂存不完整的多字节序列；结束时再 `decode()` 冲残片 |
| CRLF | 行尾 `\r` 要剥掉；空行仍是帧边界 |
| 多行 `data:` | 按 `\n` 拼接（协议只有一行，但解析器要通用） |
| `id:` | 阶段 11 断线重连用；现在保留 |
| 为什么要 `yieldToPaint` | 让浏览器获得绘制机会；批处理不等于绘制 |
| 每个事件都 `setLog` | O(n²) 复制，长流应改 ref + 节流/虚拟列表 |
| 流提前结束 | `for await` 正常结束但没收到终态 → 应提示“连接中断”；当前未检测 |
| 卸载清理 | 应 `AbortController` 中止 fetch；当前未实现 |
| schema 全 optional | 增量片段宽容解析；失败代价低的场景才这么做 |
| `content-type` 判断 | 区分 JSON 预检错误与事件流；`res.body === null` 也要防 |

> **面试考点 · 流“正常结束”但没收到 `run_finished` / `run_failed`，发现得了吗？**
> 现在的 `for await` 循环在 `reader` 报 `done` 时自然结束，`finally` 把 `running` 置 `false`。如果服务端进程被杀、代理断开，客户端只会看到“运行中… → 结束”，**没有任何错误提示**。
> 正确做法：维护 `sawTerminal` 标志，循环结束后若为 `false` 且没有 `runError`，设置“连接中断，请重试”。
> 这是一个真实的健壮性缺口——**终态唯一不仅约束服务端，也约束客户端必须等到终态。**

> **面试考点 · 组件卸载后还在 `setState` 会怎样？**
> React 18 起不再打印“setState on unmounted component”警告，但更新会被丢弃，网络请求仍在继续（浪费带宽/服务端 token）。
> 正确做法：
>
> ```tsx
> const controller = new AbortController()
> fetch(url, { signal: controller.signal, ... })
> // useEffect cleanup / 组件卸载
> controller.abort()
> ```
>
> `abort()` 会让 `reader.read()` 抛 `AbortError`，`for await` 退出，进入 `catch`。
> 后端的配合是监听 `request.close` 取消执行（见 03 篇）。**前端中止只是第一步，服务端不取消就仍然在烧钱。**
