## 1. 为什么先写契约

双后端项目最怕「TS 返回一个形状、Python 返回另一个形状」。所以先把接口写死在一个语言无关的文件里，再让两边照着实现。

- 唯一真源：`packages/contract/openapi.yaml`
- TS 侧同步一份类型：`packages/contract/src/index.ts`
- Python 侧不生成代码，按 YAML 手写 Pydantic 模型（阶段 1 起）

## 3. OpenAPI：先只写 /health

**完整文件路径：`packages/contract/openapi.yaml`**

```yaml
# OpenAPI 3.1：契约的唯一真源
openapi: 3.1.0

info:
  # 文档标题
  title: mini-dify API
  # 契约版本；每次改接口都递增，并与 src/index.ts 的 CONTRACT_VERSION 同步
  version: 0.1.0
  description: >-
    唯一契约。NestJS（api-ts）与 FastAPI（api-py）都必须实现本规范，
    并由同一套请求校验两者的响应结构、状态码与错误体一致。

servers:
  # 同一个前端可以指向任意一个后端
  - url: http://localhost:3001
    description: api-ts (NestJS)
  - url: http://localhost:8000
    description: api-py (FastAPI)

paths:
  /health:
    get:
      # operationId 在两端保持一致，便于对照与生成客户端
      operationId: getHealth
      summary: 健康检查
      responses:
        "200":
          description: 服务健康
          content:
            application/json:
              schema:
                # 引用下面的组件，避免重复定义
                $ref: "#/components/schemas/HealthResponse"

components:
  schemas:
    HealthResponse:
      type: object
      # additionalProperties=false：两端都不允许多返回字段
      additionalProperties: false
      # required：四个字段必须全部出现
      required: [status, service, version, time]
      properties:
        status:
          type: string
          # 健康检查成功只允许这一个值
          enum: [ok]
        service:
          type: string
          description: 服务标识，只能是 api-ts 或 api-py
        version:
          type: string
          description: 服务版本
        time:
          type: string
          format: date-time
          # 两端时间格式必须一致，否则契约测试会失败
          description: UTC、ISO-8601、毫秒精度、以 Z 结尾（24 字符）
```

> 后续阶段只往这个文件里「加」paths 与 schemas，不改已有形状；改了就要同步两套后端。

> **面试考点 · OpenAPI 里哪些字段是真会卡住联调的？**
>
> - **`required`**：只写属性不写 required，字段默认可选；两端都可能漏返回。
> - **`additionalProperties: false`**：禁止额外字段。NestJS 默认可能把多余字段一起返回，Pydantic 默认允许 extras；不写 false 就可能一边多字段、一边少字段。
> - **`enum`**：`status` 只能是 `ok`，把「口头约定」变成「可校验约束」。
> - **`$ref`**：引用组件而不是复制粘贴；改一处，所有引用同步，避免 schema 漂移。
> - **`format: date-time`**：只表达语义，不强制时区；真正的「UTC + 毫秒 + Z」要靠两端实现与契约测试保证。
> - **OpenAPI 3.1**：schema 对齐 JSON Schema 2020-12，支持 `const`、`type` 数组等；3.0 与 3.1 的写法别混用。
>
> **追问：契约版本号为什么独立于应用版本？**
> 应用可以只改内部实现（0.1.1），接口不变；契约版本只在「字段/状态码/错误体变化」时递增。两者混在一起，消费方无法判断升级是否破坏兼容。

## 4. TS 类型：与 YAML 逐字段对应

**完整文件路径：`packages/contract/src/index.ts`**

```ts
/**
 * 契约 TS 类型（由 openapi.yaml 派生）。
 *
 * 唯一真源是 packages/contract/openapi.yaml；本文件必须与它逐字段一致。
 * 两套后端（NestJS / FastAPI）返回的数据都必须符合这些类型。
 */

/** 契约版本；改契约时递增，并与 openapi.yaml 的 info.version 保持同步。 */
export const CONTRACT_VERSION = '0.1.0'

/** GET /health 的响应体。 */
export interface HealthResponse {
  /** 固定为 'ok'：类型层面也只允许这个字面量 */
  status: 'ok'
  /** 服务标识：api-ts 或 api-py */
  service: string
  /** 服务版本 */
  version: string
  /** 时间戳：UTC、ISO-8601、毫秒精度、以 Z 结尾（24 字符） */
  time: string
}
```

> **面试考点 · `interface HealthResponse` 能保证后端返回的数据吗？**
>
> **不能。** TypeScript 的类型只存在于编译期，编译成 JS 后 `interface`、`type`、泛型全部被擦除。`res.json() as HealthResponse` 只是一句「你相信我」，运行期就算少字段、类型错，也不会报错。
>
> - **编译期**：`HealthResponse` 约束开发者写的代码，编辑器能补全、能报错。
> - **运行期**：没有任何校验。真正的边界（HTTP 响应、用户输入、环境变量）必须用运行期校验：NestJS 用 `class-validator` + `ValidationPipe`，Python 用 Pydantic，前端用 Zod（落在 `apps/web/lib/schemas.ts`，具体见 05 篇的「运行期校验」考点）。
> - **`import type`**：只导入类型，编译后整行消失，不会把契约包打进运行时代码；这也是「`main` 字段存在，但 `HealthResponse` 运行时不可用」的原因。
>
> **追问：那 `CONTRACT_VERSION` 为什么能 import？**
> 它是 `const` 值，不是类型；编译后会生成真实的 JS 变量。`interface` 没有运行时产物，`const` 有——这就是「值 vs 类型」的区别。
>
> **追问：`status: 'ok'` 与 `status: string` 的区别？**
> 字面量类型把范围缩到一个值；`string` 允许任意字符串。契约里的 `enum: [ok]` 必须落成字面量类型，否则 TS 侧允许传 `status: 'error'`，与契约不一致。
