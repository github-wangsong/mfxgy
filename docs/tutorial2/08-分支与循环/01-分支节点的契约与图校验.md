# 01 · 分支节点的契约与图校验（分支与循环）

> 阶段 8 · 第 1 步
>
> 做完：契约新增 `condition` / `aggregator` / `iteration` 三种节点的 `data` 形状；图校验新增规则 8/9/10，能拦住“分支缺边、`else` 缺失、`sourceHandle` 非法、同分支多条边、聚合输出为空、迭代上限越界”。
>
> **本篇面试考点**：一个节点多出口为什么用 `sourceHandle` 而不是拆成多个节点 · `else` 为什么是保留字 · 为什么“同分支多条边”必须报错 · 分支匹配为什么按数组顺序 · 图校验与运行时校验的边界 · `additionalProperties: true` 的取舍 · 跨语言校验规则必须“逐条同序” · `maxIterations` 为什么上限是 100。

---

## 1. 三个节点各自解决什么

```text
condition   按变量值选一条出边（if / else if / else）
aggregator  多个分支的结果汇合，按顺序取第一个非空值（coalesce）
iteration   对数组逐项渲染模板（map），输出 results / count / joined
```

它们共同构成“流程控制”：

```text
        ┌── condition ──(case a)──→ llm_a ──┐
start ──┤                ──(case b)──→ llm_b ──┼──→ aggregator ──→ end
        └                ──(else)────→ llm_c ──┘

        ┌── iteration ──→ end
start ──┘   （对 inputs.topics 逐项生成）
```

> **注意**：`condition` 的“多出口”与阶段 6 ReAct 的“条件边 + 环”是**两种不同机制**：
>
> - ReAct 的条件边由**引擎内部**决定（`__tools` 是否需要回环），图上看不到分支；
> - `condition` 的分支由**用户画布**配置，每个分支有名字。
>
> 本篇只做后者。

---

## 2. 决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 多出口表达 | 一个节点 + 多条出边，用 `sourceHandle` 区分 | 图模型简单；React Flow 原生支持 |
| 分支匹配 | 按 `conditions` 数组顺序取**第一个**匹配 | 与 `if / else if` 语义一致，可预测 |
| 兜底 | 必须有 `else` 出边 | 否则“全部不匹配”时流程中断，且没有报错 |
| `else` 标识 | 保留字 `"else"` | 简单；校验器禁止用它作 case id |
| 同分支多条边 | 报错 | 运行时只能选一条，多出来的边是死配置 |
| `aggregator` 取值 | 每个 `name` 取第一个非空 | 汇合分支的标准语义 |
| `iteration` 上限 | `maxIterations` 默认 20、范围 1~100 | 防止用户配置出“百万次循环” |
| 节点 `data` 校验 | 契约 `additionalProperties: true` | 各节点配置自由扩展；严格校验放在运行时 |

> **面试考点 · 为什么用 `sourceHandle`，而不是给每个分支建一个“分支节点”？**
> 方案对比：
>
> | 方案 | 优点 | 缺点 |
> | --- | --- | --- |
> | 一个 `condition` + 多个 `sourceHandle` | 图紧凑、语义集中、React Flow 原生 | 需要校验 handle 合法性 |
> | 每个分支一个节点 | 图结构直观 | 节点数爆炸、需要“分支组”概念、汇合逻辑更复杂 |
> | 边属性 `condition: "a"` | 不需要 handle | 与 React Flow 的连线模型不一致，前端实现别扭 |
>
> 选 `sourceHandle` 的关键原因：**它本来就是 React Flow 的连线标识**（一个节点可以有多个 source handle），前端画布与后端图模型能一一对应，不需要额外映射层。

### 3.2 为什么 `data` 是 `additionalProperties: true`

`GraphNode.data` 是**各节点自定义的配置**：

- `llm` 有 `model/prompt/tools`；
- `condition` 有 `conditions`；
- 未来可能加 `http` / `code` 节点。

如果用 `oneOf` 严格约束，OpenAPI 的校验器会要求“所有分支都能通过”，而 `data` 里常带 UI 辅助字段（`title` 之外，前端可能存 `collapsed`）。

取舍：

- **契约层宽松**（`additionalProperties: true`）：只规定“必须有 `data` 这个对象”；
- **运行时严格**：每个节点在 `validateNodeData` 里按自己的形状校验（`03` 篇）。

> **面试考点 · 那契约还有意义吗？**
> 有，而且分工清楚：
>
> - 契约保证**跨端结构**：`Graph` 的 `nodes/edges` 形状、`type` 枚举、`sourceHandle` 语义；
> - 运行时保证**配置正确性**：`condition` 的 `conditions` 是否为空、运算符是否合法。
>
> 如果什么都塞进契约 schema，会得到几百行的 `oneOf`，前后端生成类型极难用。
> **契约管“骨架”，运行时管“内脏”。**

## 4. 图校验：规则 8/9/10

**完整文件路径：`apps/api-ts/src/graph/graph.validator.ts`**（阶段 8 增量）

```ts
  // 规则 8：condition 节点（分支标识 / 运算符 / 出边 sourceHandle）
  for (const node of graph.nodes) {
    if (node.type === 'condition') {
      errors.push(...validateConditionNode(node, graph.edges))
    }
  }

  // 规则 9：aggregator 节点（outputs 与各自 values 非空）
  for (const node of graph.nodes) {
    if (node.type !== 'aggregator') {
      continue
    }
    const data = (node.data ?? {}) as Record<string, unknown>
    const outputs = data.outputs
    // 「不是数组」由 validateNodeData 负责（避免同一条文案重复出现）
    if (Array.isArray(outputs) && outputs.length === 0) {
      errors.push(`aggregator node ${node.id} must have at least one output`)
      continue
    }
    if (!Array.isArray(outputs)) {
      continue
    }
    for (const item of outputs) {
      const output = isPlainObject(item) ? item : {}
      const name = typeof output.name === 'string' ? output.name : String(output.name)
      const values = output.values
      if (Array.isArray(values) && values.length === 0) {
        errors.push(`aggregator node ${node.id} output ${name} must have at least one value`)
      }
    }
  }

  // 规则 10：iteration 节点（inputArray / maxIterations）
  for (const node of graph.nodes) {
    if (node.type !== 'iteration') {
      continue
    }
    const data = (node.data ?? {}) as Record<string, unknown>
    if (typeof data.inputArray === 'string' && data.inputArray.trim() === '') {
      errors.push(`iteration node ${node.id} inputArray is required`)
    }
    const maxIterations = data.maxIterations
    if (
      typeof maxIterations === 'number' &&
      !(Number.isInteger(maxIterations) && maxIterations >= 1 && maxIterations <= 100)
    ) {
      errors.push(`iteration node ${node.id} maxIterations must be between 1 and 100`)
    }
  }
```

### 4.1 规则 8 的八条细节

```ts
/** `condition` 节点支持的运算符（与契约 `ConditionOperator` 一致）。 */
const CONDITION_OPERATORS = new Set<ConditionOperator>([
  'equals', 'not_equals', 'contains', 'not_contains',
  'starts_with', 'ends_with', 'is_empty', 'is_not_empty',
  'gt', 'gte', 'lt', 'lte',
])

function validateConditionNode(
  node: Graph['nodes'][number],
  edges: Graph['edges'],
): string[] {
  const errors: string[] = []
  const data = (node.data ?? {}) as Record<string, unknown>
  const conditions = data.conditions
  // 「不是数组」由 validateNodeData 负责（避免同一条文案重复出现）
  if (!Array.isArray(conditions)) {
    return []
  }
  if (conditions.length === 0) {
    return [`condition node ${node.id} must have at least one condition`]
  }
  // ...
}
```

顺序（与 error-messages.md §8.1 一致）：

| 序号 | 检查 | 文案 |
| --- | --- | --- |
| 8.1.1 | `conditions` 为空 | `condition node X must have at least one condition`（命中后**跳过**该节点其余规则） |
| 8.1.2 | case id 重复 / 用了 `else` | `... has duplicate case id: a` / `... case id "else" is reserved` |
| 8.1.3 | 运算符非法 | `... has invalid operator: foo` |
| 8.1.4 | `variable` 为空 | `... case a variable is required` |
| 8.1.5 | case 没有出边 | `... case a has no outgoing edge` |
| 8.1.6 | `else` 没有出边 | `... else branch has no outgoing edge` |
| 8.1.7 | 出边 `sourceHandle` 非法 | `edge E from condition node X has invalid sourceHandle: null` |
| 8.1.8 | 同一分支多条边 | `... has duplicate edge for case a` |

实现要点：

```ts
  // 8.1.5：每个 caseId 必须有一条出边
  for (const caseId of caseIds) {
    if (!outgoing.some((edge) => edge.sourceHandle === caseId)) {
      errors.push(`condition node ${node.id} case ${caseId} has no outgoing edge`)
    }
  }

  // 8.1.6：else 分支必须有一条出边
  if (!outgoing.some((edge) => edge.sourceHandle === 'else')) {
    errors.push(`condition node ${node.id} else branch has no outgoing edge`)
  }

  // 8.1.7：出边的 sourceHandle 必须是某个 caseId 或 "else"（缺失写作 null）
  const validHandles = new Set<string>([...caseIds, 'else'])
  for (const edge of outgoing) {
    const handle = edge.sourceHandle
    if (typeof handle !== 'string' || !validHandles.has(handle)) {
      const shown = handle === null || handle === undefined ? 'null' : String(handle)
      errors.push(
        `edge ${edge.id} from condition node ${node.id} has invalid sourceHandle: ${shown}`,
      )
    }
  }

  // 8.1.8：同一分支多条边（分支按 conditions 顺序，else 最后）
  const edgeCounts = new Map<string, number>()
  for (const edge of outgoing) {
    const handle = edge.sourceHandle
    if (typeof handle === 'string' && validHandles.has(handle)) {
      edgeCounts.set(handle, (edgeCounts.get(handle) ?? 0) + 1)
    }
  }
  for (const caseId of new Set(caseIds)) {
    if ((edgeCounts.get(caseId) ?? 0) > 1) {
      errors.push(`condition node ${node.id} has duplicate edge for case ${caseId}`)
    }
  }
  if ((edgeCounts.get('else') ?? 0) > 1) {
    errors.push(`condition node ${node.id} has duplicate edge for case else`)
  }
```

> **面试考点 · 为什么“同分支多条边”要报错，而不是“跑第一条”？**
> 如果允许多条：
>
> - 运行时只能选一条（比如第一条），其余是**永远不会执行的死配置**；
> - 用户在图上看不出哪条生效；
> - 改顺序会悄悄改变行为（如果实现改成“最后一条”）。
>
> 报错把“不确定性”提前到保存阶段。**图保存成功 = 图可执行**，这是本项目的一条硬约束。**

> **面试考点 · 为什么 `else` 必须存在？**
> 没有 `else` 时，“所有条件都不匹配”会怎样？
>
> - 方案 A：流程静默结束（用户以为跑完了，其实后半段没执行）；
> - 方案 B：运行时报错（图能保存，但一跑就失败）；
> - 方案 C：保存时就要求有 `else`（本项目）。
>
> C 的代价是“用户必须先画一条兜底边”，收益是**图始终可完整执行**。
> 与 TypeScript 的 `switch` 要求 `default` 是同一类设计：**穷尽性检查放在编译期/保存期，而不是运行期。**

> **面试考点 · `else` 为什么不能作为 case id？**
> 因为条件边的路由 key 是 `sourceHandle`：
>
> ```text
> case "vip"   → sourceHandle "vip"
> case "else"  → sourceHandle "else"（兜底）
> ```
>
> 如果允许某个 case 的 `id` 也叫 `else`，图上会有两条 `sourceHandle === "else"` 的边：
>
> - 校验规则 8.1.8 会报“重复边”，但用户看不懂为什么；
> - 运行时无法区分“这是显式 case 还是兜底”。
>
> 直接保留 `else`，语义清晰。**保留字的价值在于消除歧义，代价是禁止一个名字——非常划算。**

## 5. 运行时校验的边界

图校验（保存时）与节点校验（运行时）**不是一回事**：

| 检查 | 图校验 | 运行时 `validateNodeData` |
| --- | --- | --- |
| `conditions` 是数组 | ✗ | ✓ |
| `conditions` 非空 | ✓ | ✓（不重复报） |
| 运算符在枚举内 | ✓ | ✓ |
| `variable` 非空 | ✓ | — |
| 每个 case 有出边 | ✓ | — |
| `outputs` 是数组 | ✗ | ✓ |
| `outputs` 非空 | ✓ | — |
| `inputArray` 是字符串 | ✗ | ✓ |
| `maxIterations` 范围 | ✓ | ✓ |

原则：

1. **图结构问题**（边、handle、节点数）只在保存时查——运行时图已定型；
2. **配置类型问题**（是不是数组/字符串）在运行时查——因为 `data` 来自 JSONB，历史数据可能不合规；
3. **两者都查的**（非空、范围）文案相同，避免用户看到两种说法。

> **面试考点 · 为什么不把所有校验都放在保存时？**
> 因为**旧数据**：
>
> - 契约升级前保存的图，`data` 可能是旧形状；
> - 用户可以直接改数据库（`apps.graph_json`）；
> - 前端有 bug 时可能提交缺字段的 `data`。
>
> 保存时校验只保护“新写入”；运行时校验保护“所有读取”。
> **入口校验是体验，出口校验是安全。**

## 6. 两端逐条对齐

Python 侧 `app/graph/validator.py` 必须：

- 规则顺序相同（1→10）；
- 同一规则内遍历顺序相同（`graph.nodes` 数组顺序、`conditions` 数组顺序）；
- 文案模板逐字节相同（含 `null` 的显示方式）；
- 重复 id 只报一次的实现相同（`Set` 记录已报）。

**完整文件路径：`apps/api-py/app/graph/validator.py`**（规则 8 节选）

```python
def _validate_condition_node(
    node: dict[str, Any], edges: list[dict[str, Any]]
) -> list[str]:
    """规则 8：condition 节点（见 error-messages.md §8.1）。"""
    errors: list[str] = []
    data = node.get("data") or {}
    conditions = data.get("conditions")
    # 「不是数组」由 validate_node_data 负责（避免同一条文案重复出现）
    if not isinstance(conditions, list):
        return []
    if len(conditions) == 0:
        return [f"condition node {node['id']} must have at least one condition"]

    cases = [item if isinstance(item, dict) else {} for item in conditions]
    case_ids = [_js_string(item.get("id")) for item in cases]

    seen: set[str] = set()
    reported: set[str] = set()
    reported_reserved: set[str] = set()
    for case_id in case_ids:
        if case_id == "else" and case_id not in reported_reserved:
            errors.append(f'condition node {node["id"]} case id "else" is reserved')
            reported_reserved.add(case_id)
        if case_id in seen and case_id not in reported:
            errors.append(
                f"condition node {node['id']} has duplicate case id: {case_id}"
            )
            reported.add(case_id)
        seen.add(case_id)

    for index, item in enumerate(cases):
        operator = item.get("operator")
        if operator not in CONDITION_OPERATORS:
            errors.append(
                f"condition node {node['id']} has invalid operator: {_js_string(operator)}"
            )
        variable = item.get("variable")
        if not isinstance(variable, str) or variable.strip() == "":
            errors.append(
                f"condition node {node['id']} case {case_ids[index]} variable is required"
            )

    outgoing = [edge for edge in edges if edge.get("source") == node["id"]]
    # 8.1.5 / 8.1.6 / 8.1.7 / 8.1.8 与 TS 逐个对应
    ...
    return errors
```

> **面试考点 · 规则顺序也算契约吗？**
> 算。因为调用方（前端）会把 `errors` 用 `"; "` 拼成一个字符串展示：
>
> ```text
> condition node c1 case a has no outgoing edge; condition node c1 else branch has no outgoing edge
> ```
>
> 如果两端顺序不同，同一张图会得到**不同的错误文案**，契约测试直接失败。
> 所以 `error-messages.md` 不只写“有哪些文案”，还要写**顺序与遍历方向**。

### 7.2 八条规则各触发一次

按顺序构造：

```text
1. conditions: []                         → must have at least one condition
2. 两个 case 同 id "vip"                   → has duplicate case id: vip
3. case id = "else"                       → case id "else" is reserved
4. operator = "between"                   → has invalid operator: between
5. variable = ""                          → case vip variable is required
6. 删掉 vip 的出边                         → case vip has no outgoing edge
7. 删掉 else 的出边                        → else branch has no outgoing edge
8. 加一条 sourceHandle = null 的边          → invalid sourceHandle: null
9. 同一 vip 再加一条边                      → has duplicate edge for case vip
```

一次性触发多条时，**注意顺序**：

```text
case id "else" is reserved
condition node c1 has duplicate case id: else
condition node c1 has invalid operator: ...
...
```

`else` 保留字检查在重复检查**之前**，所以 `["vip","else","else"]` 会先报保留字，再报重复。

## 8. 面试考点汇总

| 问题 | 答案要点 |
| --- | --- |
| 为什么 `sourceHandle` | 与 React Flow 多出口模型一一对应，无需映射层 |
| 分支匹配顺序 | 按 `conditions` 数组顺序，第一个匹配生效 |
| `else` 必填 | 保证图穷尽可执行；否则静默中断 |
| `else` 保留字 | 避免与兜底 handle 歧义；校验期就拒绝 |
| 同分支多条边 | 运行时只能选一条，多余是死配置 → 保存时报错 |
| `additionalProperties: true` | 契约管骨架，运行时管内脏 |
| 图校验 vs 运行时校验 | 入口保体验，出口保历史数据安全 |
| 规则顺序 | 也是契约：错误文案拼接后的顺序必须一致 |
| `maxIterations` 上限 | 100 次是“防手滑”而非性能边界 |
| 重复 id 只报一次 | 避免一张图刷出几十条同文案 |
