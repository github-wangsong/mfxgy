## 1. 一张图：从源码到 CPU

```
hello.py
  ↓ CPython 编译
字节码 hello.pyc
  ↓ 解释器逐条执行（或 JIT 编译）
机器码
  ↓
CPU：取指 → 译码 → 执行 → 写回
  ↓
寄存器 → L1/L2/L3 缓存 → 主存 → SSD/HDD → 网络
```

| 层 | 速度量级 | 你要记住的一句话 |
| --- | --- | --- |
| 寄存器 | 约 1 ns | CPU 直接操作 |
| L1 缓存 | 约 1~2 ns | 每核私有，命中率最高 |
| L2 缓存 | 约 4~10 ns | 每核私有 |
| L3 缓存 | 约 20~40 ns | 多核共享 |
| 主存 | 约 100 ns | 一次内存访问约 100ns |
| SSD 随机读 | 约 100 µs | 比内存慢约 1000 倍 |
| HDD 随机读 | 约 10 ms | 寻道是主要成本 |
| 同机房网络 | 约 0.5~1 ms | 跨机器调用 |
| 跨地域网络 | 约 30~100 ms | LLM API 常见量级 |

> 面试时不需要背精确值，记住**数量级**即可：内存 100ns、SSD 100µs、HDD 10ms、网络 1ms~100ms。

## 2. CPU 与内存

### 2.1 CPU 在做什么

| 概念 | 一句话 |
| --- | --- |
| 核心 / 超线程 | 物理核心并行执行；超线程让一个物理核挂两个逻辑核，提升吞吐但不等于双倍性能 |
| 寄存器 | CPU 内部最快的存储，容量极小 |
| 指令周期 | 取指、译码、执行、访存、写回 |
| 流水线 | 多条指令重叠执行，提高吞吐 |
| 分支预测 | 预测 `if` 走向；预测失败会清空流水线 |
| 用户态 / 内核态 | 应用不能直接碰硬件，系统调用会切换态 |

### 2.2 缓存与局部性

| 局部性 | 含义 | 例子 |
| --- | --- | --- |
| 时间局部性 | 刚访问的数据还会再访问 | 循环里反复读同一个变量 |
| 空间局部性 | 相邻地址的数据会被一起访问 | 顺序遍历数组 |

- 缓存以 **cache line** 为单位加载，常见 64 字节。
- 顺序访问数组比随机访问链表快，很大一部分原因是缓存友好。
- 多核缓存需要一致性协议，常见 **MESI**：Modified / Exclusive / Shared / Invalid。
- **伪共享**：两个线程分别写同一 cache line 里的不同变量，缓存行反复失效，性能骤降。

```python
# 伪共享示意（概念代码）：两个线程写同一缓存行
# 真实 Python 里很难观察到，C/Java/Go 更常见
a = 0
b = 0  # 如果 a、b 恰好落在同一 cache line，两个线程各写一个也会互相拖慢
```

> 解决伪共享：填充（padding）让变量落在不同缓存行，或按线程分片累加。

### 2.3 32 位与 64 位

| 点 | 32 位 | 64 位 |
| --- | --- | --- |
| 地址空间 | 约 4 GB | 理论上极大 |
| 指针大小 | 4 字节 | 8 字节 |
| 兼容性 | 老系统/嵌入式 | 现代服务器默认 |

## 3. 程序如何运行

### 3.1 编译型 / 解释型 / JIT

| 方式 | 过程 | 代表 | 特点 |
| --- | --- | --- | --- |
| 编译型 | 源码 → 机器码，运行前完成 | C / C++ / Rust / Go | 启动快、运行快、需按平台编译 |
| 解释型 | 源码 → 字节码 → 解释执行 | Python / Ruby | 跨平台、启动快、运行慢 |
| JIT | 运行中把热点代码编译成机器码 | Java / JS(V8) / PyPy | 兼顾启动与运行，预热后快 |

> Python 不是「纯解释」：CPython 会先把 `.py` 编译成字节码（`.pyc`），再由虚拟机解释执行。

### 3.2 栈与堆

| 区域 | 存什么 | 特点 |
| --- | --- | --- |
| 栈 | 函数调用帧、局部变量、返回地址 | 自动分配释放，速度快，容量有限 |
| 堆 | 对象、容器、动态内存 | 手动/GC 管理，速度慢，容量大 |

```python
def f(n: int) -> int:
    return f(n + 1)  # 递归没有终止条件 → RecursionError（栈溢出）

# Python 默认递归深度约 1000，可用 sys.setrecursionlimit 调整，但不建议靠它解决深递归
```

### 3.3 垃圾回收

| 语言 | 机制 | 关键点 |
| --- | --- | --- |
| Python | 引用计数 + 分代循环 GC | 引用计数为主，循环引用靠 GC |
| Java | 分代 GC（Young/Old） | 对象晋升、Stop-The-World |
| JS | 分代 GC | 标记清除/整理，V8 有增量与并发 GC |

**内存泄漏常见原因**：

- 全局缓存无上限（`dict` 只增不减）；
- 事件监听/回调未移除；
- 闭包长期持有大对象；
- 队列/日志无界增长；
- 连接/文件句柄未关闭。

## 4. 数据表示与编码

### 4.1 位、字节与进制

| 单位 | 换算 |
| --- | --- |
| 1 bit | 0 或 1 |
| 1 byte | 8 bit |
| 1 KB | 1024 B（工程上常按 1000 估算） |
| 1 MB | 1024 KB |
| 1 GB | 1024 MB |

- 十六进制 1 位 = 4 bit；`0xFF` = 255。
- 整数溢出：C/Java 的 `int` 有范围；Python 的 `int` 任意精度，不会溢出。
- 浮点数：IEEE 754；`0.1 + 0.2 != 0.3` 是二进制无法精确表示 0.1 导致的。

```python
0.1 + 0.2            # 0.30000000000000004
round(0.1 + 0.2, 2)  # 0.3
```

> 金额不要用 `float`，用 `Decimal` 或整数分。

### 4.2 Unicode 与 UTF-8

| 概念 | 含义 |
| --- | --- |
| Unicode | 字符集，给每个字符一个码点（code point），如 `U+4E2D` |
| UTF-8 | Unicode 的一种变长编码，1~4 字节 |
| GBK | 中文编码，常见 2 字节 |
| ASCII | 7 bit，0~127；UTF-8 完全兼容 ASCII |

| 字符 | UTF-8 字节数 |
| --- | --- |
| `A` | 1 |
| `é` | 2 |
| `中` | 3 |
| `😀` | 4 |

**乱码原因**：用 A 编码写入、用 B 编码读取。例如 UTF-8 的中文用 GBK 解码，就会出现「锟斤拷」或问号。

```python
s = "你好"
len(s)            # 2：Python 的 str 按字符计数
len(s.encode())   # 6：UTF-8 下每个中文 3 字节
```

> Python 的 `str` 是 Unicode 码点序列；`bytes` 才是字节序列。网络/文件读写要明确 `encoding="utf-8"`。

### 4.3 大小端

| 模式 | 高位字节位置 | 常见场景 |
| --- | --- | --- |
| 大端（Big-endian） | 高位在低地址 | 网络字节序 |
| 小端（Little-endian） | 高位在高地址 | x86 / ARM 常见 |

```python
(0x12345678).to_bytes(4, "big")    # b'\x12\x34\x56\x78'
(0x12345678).to_bytes(4, "little") # b'xV4\x12'
```

## 5. 存储与 IO

| 介质 | 随机 IO | 顺序 IO | 特点 |
| --- | --- | --- | --- |
| HDD | 约 10 ms | 高吞吐 | 寻道 + 旋转延迟 |
| SSD | 约 100 µs | 更高吞吐 | 无机械寻道，有写放大 |
| 内存 | 约 100 ns | 极高 | 容量小、贵 |
| 网络 | 1 ms~100 ms | 看带宽 | 受 RTT、带宽、拥塞影响 |

- **页**：操作系统与磁盘交互的基本单位，常见 4 KB。
- **page cache**：内核把磁盘数据缓存到内存，读命中时不走磁盘。
- **顺序写**通常比随机写快：日志、LSM-Tree、Kafka 都利用这一点。
- **fsync**：把数据真正刷到磁盘；数据库提交时常见，代价高。

> Agent 场景：向量索引、会话日志、checkpoint 都是 IO 密集；能顺序写就不要随机写，能批量就不要逐条。

## 6. 性能基础

### 6.1 延迟 vs 吞吐

| 指标 | 含义 | 优化方向 |
| --- | --- | --- |
| 延迟（Latency） | 一次请求多久返回 | 减少等待、缓存、并行 |
| 吞吐（Throughput） | 单位时间能处理多少 | 批处理、并发、连接池 |

> LLM 应用里，**首 token 延迟**和**总生成时间**是两个指标；流式输出主要优化「感知延迟」，不一定减少总耗时。

### 6.2 性能优化顺序

1. **测量**：先 profiling / 日志 / 火焰图，找到瓶颈。
2. **定位**：是 CPU、内存、IO 还是网络？
3. **优化**：只改瓶颈，不同时改十处。
4. **验证**：用同一基准测试对比前后。

> 没有测量的优化，通常只是「换个地方慢」。

## 7. 面试真题

### Q1. 为什么 CPU 缓存能加速？什么是伪共享？

**结论**：缓存利用时间/空间局部性，把热数据放在更快的 SRAM；伪共享是多线程写同一缓存行的不同变量，导致缓存行反复失效。

**展开**：

- L1/L2 每核私有，L3 多核共享，主存最慢。
- 缓存按 cache line（常见 64B）加载，顺序访问更友好。
- 多核写同一行会触发一致性协议（MESI）的失效与同步。
- 解决：padding、线程本地累加、避免高频写共享变量。

### Q2. 编译型、解释型、JIT 的区别？Python 为什么慢？

**结论**：编译型提前生成机器码；解释型边解释边执行；JIT 在运行中编译热点代码。Python 慢在动态类型、字节码解释和 GIL。

**展开**：

- CPython 先把源码编译为字节码，再逐条解释。
- 动态类型导致每次操作都要查类型、查属性。
- GIL 让同一进程内的多线程无法并行执行 Python 字节码。
- 优化：C 扩展/NumPy、多进程、异步 IO、PyPy。

### Q3. `0.1 + 0.2` 为什么不等于 `0.3`？

**结论**：IEEE 754 二进制浮点无法精确表示 0.1 和 0.2，相加后有舍入误差。

**展开**：

- 0.1 的二进制是无限循环小数，只能近似存储。
- 比较浮点用 `math.isclose` / 误差范围，不要用 `==`。
- 金额用 `Decimal` 或整数分。

### Q4. UTF-8 为什么兼容 ASCII？中文占几个字节？

**结论**：UTF-8 的 0~127 编码与 ASCII 完全一致；中文通常占 3 字节，emoji 占 4 字节。

**展开**：

- UTF-8 是变长编码：1~4 字节。
- ASCII 字符只占 1 字节，所以老 ASCII 文件用 UTF-8 读不会乱。
- 乱码本质是「写入编码」与「读取编码」不一致。
- Python `len(str)` 是字符数，`len(str.encode())` 是字节数。

### Q5. 大端和小端的区别？网络字节序是什么？

**结论**：大端把高位字节放在低地址，小端相反；网络字节序统一用大端。

**展开**：

- x86 通常是小端。
- `htons` / `htonl` 用于主机序转网络序。
- 跨平台二进制协议必须约定字节序。

### Q6. 栈溢出和内存泄漏分别是什么？

**结论**：栈溢出是调用栈超过上限（常见于无限递归）；内存泄漏是对象不再使用却仍被引用，无法回收。

**展开**：

- 栈溢出：检查递归终止条件，或改用迭代。
- 内存泄漏：全局缓存、未移除监听、闭包持有大对象、无界队列。
- Python 可用 `tracemalloc`、`gc` 模块排查。

### Q7. 顺序 IO 为什么比随机 IO 快？

**结论**：顺序 IO 减少寻道/页切换，能利用预读与批量传输；随机 IO 每次都要定位。

**展开**：

- HDD 的寻道和旋转延迟是主要成本。
- SSD 虽无寻道，但随机写仍有写放大与 GC 开销。
- 日志、LSM-Tree、Kafka 都用顺序写提升吞吐。

### Q8. 什么是缓存局部性？如何写出缓存友好的代码？

**结论**：尽量访问相邻内存、复用刚访问的数据；数组顺序遍历比链表随机跳转更缓存友好。

**展开**：

- 时间局部性：循环内复用变量。
- 空间局部性：连续内存、紧凑结构。
- 避免大对象指针跳转、减少高频共享写。

### Q9. 为什么 LLM 应用更关注首 token 延迟？

**结论**：用户感知的是「多久看到第一个字」，流式输出能显著降低感知延迟，但总生成时间不变。

**展开**：

- 首 token 延迟受网络、排队、prefill 影响。
- 流式输出用 SSE 逐段推送。
- 优化：连接复用、减少 prompt 长度、并发预检、缓存。

### Q10. 线上 CPU 高，怎么排查？

**结论**：先看是用户态还是内核态，再定位进程/线程/热点函数。

**展开**：

- `top` 看整体，`pidstat` 看进程，`perf top` / 火焰图看热点。
- 用户态高：死循环、正则回溯、序列化、GC。
- 内核态高：系统调用频繁、网络/磁盘 IO、锁竞争。
- 结合 `strace`、`iostat`、`ss` 继续定位。

## 8. 速记卡

| 关键词 | 记住这一句 |
| --- | --- |
| 缓存层级 | 寄存器 → L1 → L2 → L3 → 内存 → SSD → HDD → 网络 |
| 延迟数量级 | 内存 100ns，SSD 100µs，HDD 10ms，网络 1~100ms |
| 局部性 | 时间复用、空间相邻 |
| 伪共享 | 同 cache line 不同变量被多线程写 |
| 编译/解释/JIT | 提前编译 / 边解释边跑 / 热点编译 |
| Python 慢 | 动态类型 + 字节码解释 + GIL |
| 浮点 | 0.1+0.2 有误差，比较用 isclose |
| UTF-8 | ASCII 兼容，中文 3 字节，emoji 4 字节 |
| 大小端 | 网络大端，x86 小端 |
| IO | 顺序快于随机，page cache 很关键 |
| 性能 | 先测量，再优化，再验证 |
