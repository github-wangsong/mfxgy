# 05 · 数据库与存储

> 定位：Agent 平台的会话、消息、图、向量、缓存最终都要落到存储。面试不会让你建整库，但一定会问 **索引、事务、缓存一致性、向量检索**。
> 面试权重：★★★★★
> 关联：[04 数据结构](./04-数据结构.md)（B+ 树 / 哈希 / 堆）、[03 操作系统](./03-操作系统.md)（page cache / IO / 文件描述符）。

---

## 1. 一张图：数据放哪

```
结构化事实（用户 / 应用 / 会话 / 消息） → 关系库（PostgreSQL / MySQL）
热点读 + 计数 + 限流               → Redis
语义检索（RAG 知识库）             → pgvector / 向量库
文件（文档 / 图片 / 音频）          → 对象存储（S3 / OSS / MinIO）
全文检索（关键词）                 → PostgreSQL 全文 / Elasticsearch
异步任务与事件                     → 消息队列（Redis Stream / Kafka / RabbitMQ）
```

| 选型原则 | 说明 |
| --- | --- |
| 先问访问模式 | 按主键、按时间范围、按向量相似度，决定存储类型 |
| 先单库，后拆分 | 索引、缓存、读写分离能撑住的量级，别上分库分表 |
| 一致性要求分级 | 余额强一致；聊天记录最终一致可接受；日志可丢 |
| 成本排序 | 内存 > SSD > 对象存储 > 冷归档 |

## 2. 关系库：一次查询发生了什么

### 2.1 SQL 的逻辑执行顺序

```
FROM / JOIN  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT  →  DISTINCT
             →  ORDER BY  →  LIMIT / OFFSET
```

| 结论 | 原因 |
| --- | --- |
| `WHERE` 里不能用 `SELECT` 起的别名 | `SELECT` 在 `WHERE` 之后才执行 |
| `HAVING` 过滤聚合后的结果 | `GROUP BY` 之后才有聚合值 |
| `COUNT(*)` 在 `WHERE` 过滤后统计 | 顺序决定语义 |

> MySQL 里 `HAVING` 可以用别名，PG 不允许——**写两边都能跑的 SQL**，别依赖方言特性。

### 2.2 三种连接算法

| 算法 | 适用 | 复杂度 |
| --- | --- | --- |
| Nested Loop | 外表小、内表有索引 | 外表行数 × 内表查找 |
| Hash Join | 大表等值连接、无索引 | 建哈希表 O(n+m) |
| Merge Join | 两边都已按连接键排序 | O(n+m)，需有序 |

> `EXPLAIN` 里看到 `Nested Loop` 且内表 `rows` 很大，通常意味着「缺索引」或「统计信息过期」。

### 2.3 执行计划要看什么

| MySQL `EXPLAIN` 字段 | 关注点 |
| --- | --- |
| `type` | `ALL`（全表）最差，`index`、`range`、`ref`、`eq_ref`、`const` 依次更好 |
| `key` | 实际用了哪个索引；`NULL` = 没走索引 |
| `rows` | 预估扫描行数（不是返回行数） |
| `Extra` | `Using filesort`（额外排序）、`Using temporary`（临时表）、`Using index`（覆盖索引） |

| PG `EXPLAIN` 节点 | 关注点 |
| --- | --- |
| `Seq Scan` | 全表扫描；小表正常，大表要查原因 |
| `Index Scan` / `Bitmap Heap Scan` | 走索引；后者适合中等选择率 |
| `cost=0.00..12.34` | 启动代价..总代价（估算单位） |
| `actual time=... rows=...` | `EXPLAIN ANALYZE` 才有，真实耗时与行数 |

> 对比 `rows` 估算与 `actual rows`：差 10 倍以上 → `ANALYZE` 更新统计信息，或考虑表达式索引。

## 3. 索引

### 3.1 为什么是 B+ 树

| 结构 | 磁盘友好 | 范围查询 | 说明 |
| --- | --- | --- | --- |
| 哈希 | ❌（随机 IO） | ❌ | 只适合等值 |
| 二叉搜索树 | ❌（树高、节点小） | ✅ | 磁盘上树高不可接受 |
| B+ 树 | ✅（节点 = 页，扇出大） | ✅（叶子链表） | 3~4 层可索引千万级 |
| LSM-Tree | ✅（顺序写） | 部分 | 写多读少（RocksDB / ClickHouse 系） |

三个数字：**页 16 KB、扇出约 500、3 层 ≈ 1.25 亿行**。这就是「B+ 树 3~4 次 IO 命中一条记录」的来源。

### 3.2 聚簇索引与二级索引

| 数据库 | 存储方式 | 二级索引查到什么 |
| --- | --- | --- |
| MySQL InnoDB | 聚簇索引：数据按主键组织 | 二级索引叶子存**主键值** → 需回表 |
| PostgreSQL | 堆表 + 独立索引 | 索引叶子存**行指针（ctid）** → 回表 |

```sql
-- 联合索引 (owner_id, created_at, id)
select id, title from conversations
 where owner_id = 'u1'
 order by created_at desc
 limit 20;
-- 覆盖索引：索引里已有 owner_id/created_at/id，但 title 不在 → 仍需回表
```

| 概念 | 含义 |
| --- | --- |
| 回表 | 二级索引拿到主键/指针后，再去聚簇索引/堆表取整行 |
| 覆盖索引 | 查询所需列全在索引里，免回表（`Using index`） |
| 索引下推 | 过滤条件下推到存储引擎层，减少回表次数 |

### 3.3 联合索引与最左前缀

索引 `(a, b, c)` 相当于排好序的「字典」：先按 a，再按 b，再按 c。

| 查询条件 | 能用到的部分 |
| --- | --- |
| `a = ?` | a |
| `a = ? and b = ?` | a, b |
| `a = ? and b = ? and c = ?` | a, b, c |
| `b = ?` | ❌ 用不上（缺最左列） |
| `a = ? and c = ?` | 只用 a（c 无法用于定位） |
| `a = ? and b > ? and c = ?` | a、b 用于定位，c 无法再缩小范围 |
| `a = ? order by b` | ✅ 索引本身有序，免排序 |

**设计口诀**：等值列放前、范围列放后、排序列跟着等值列。

### 3.4 索引失效的六种典型

| 写法 | 为什么失效 |
| --- | --- |
| `where date(created_at) = '2026-10-25'` | 列上套函数 |
| `where owner_id = 123`（列是字符串） | 隐式类型转换 |
| `where name like '%abc'` | 前导 `%` 无法定位 |
| `where a = 1 or b = 2`（b 无索引） | OR 要求两边都可索引，否则全表 |
| `where status != 'done'` | 选择率太高时优化器放弃索引 |
| 联合索引 `(a, b)` 却只查 `b` | 最左前缀缺失 |

> 例外：`status` 只有两个值且各占一半时，走索引反而更慢——**优化器选择全表是正确的**，不是「索引失效」。

### 3.5 索引的代价

| 代价 | 说明 |
| --- | --- |
| 写放大 | 每次 INSERT/UPDATE/DELETE 都要维护索引 |
| 空间 | 索引可能比数据还大 |
| 优化器负担 | 索引太多，选错计划的概率上升 |

> 索引数量经验：**单表 5~8 个以内**；写多读少的表更要克制。

## 4. 事务

### 4.1 ACID

| 字母 | 含义 | 靠什么实现 |
| --- | --- | --- |
| A 原子性 | 要么全做、要么全不做 | undo log / 回滚 |
| C 一致性 | 约束与业务规则不被破坏 | 约束 + 应用逻辑 |
| I 隔离性 | 并发事务互不干扰 | 锁 + MVCC |
| D 持久性 | 提交后不丢 | redo log / WAL + fsync |

### 4.2 隔离级别与三个异常

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | ✅ 可能 | ✅ | ✅ |
| 读已提交 | ❌ | ✅ | ✅ |
| 可重复读 | ❌ | ❌ | 标准里可能；InnoDB 用 Next-Key Lock 基本消除 |
| 串行化 | ❌ | ❌ | ❌ |

| 数据库默认 | 级别 |
| --- | --- |
| MySQL InnoDB | 可重复读（RR） |
| PostgreSQL | 读已提交（RC） |
| Oracle | 读已提交（RC） |

> 面试高频：**「RR 下幻读怎么解决的？」** 答两层——快照读靠 MVCC（一致性视图），当前读靠 Next-Key Lock（记录锁 + 间隙锁）。

### 4.3 MVCC 一句话版本

```
InnoDB：每行有隐藏的 DB_TRX_ID / DB_ROLL_PTR；读时按 ReadView 判断哪个版本可见。
PostgreSQL：每行有 xmin / xmax；读时按快照判断元组是否可见。
```

| 好处 | 代价 |
| --- | --- |
| 读写不互相阻塞 | 旧版本堆积 → undo 膨胀 / 表膨胀 |
| 读不加锁，吞吐高 | 长事务会阻止清理（03 篇讲过） |

### 4.4 锁

| 锁 | 粒度 | 说明 |
| --- | --- | --- |
| 行锁 | 一行 | InnoDB 默认；PG 行锁在元组上 |
| 表锁 | 整表 | DDL、`LOCK TABLE` |
| 间隙锁 | 索引区间 | 防幻读；只在 RR 生效 |
| Next-Key Lock | 记录 + 前面的间隙 | RR 的默认加锁方式 |
| 意向锁 | 表级标记 | 快速判断表里有无行锁 |

### 4.5 死锁

| 问题 | 答案 |
| --- | --- |
| 怎么产生 | 两个事务以相反顺序拿两把锁 |
| 怎么发现 | InnoDB 主动检测并回滚代价小的事务；PG 等 `deadlock_timeout` 后检测 |
| 怎么避免 | 固定加锁顺序、缩短事务、一次锁定所需行、用唯一约束替代「先查再插」 |
| 应用层怎么处理 | 捕获死锁错误 → 回滚 → 重试（重试要重新读状态） |

```sql
-- 固定顺序：永远先锁小 id
select * from accounts where id in (1, 2) order by id for update;
```

## 5. 查询优化

### 5.1 排查顺序

```
慢 → 慢查询日志/APM 找到 SQL
   → EXPLAIN ANALYZE 看计划
   → 是否全表 / 回表过多 / 排序临时表
   → 加索引 / 改写法 / 改分页
   → 再压测验证
```

| 手段 | 适用 |
| --- | --- |
| 加联合索引 | 固定过滤 + 排序组合 |
| 覆盖索引 | 只查少数列且高频 |
| 改写 SQL | 避免函数、隐式转换、前导 `%` |
| keyset 分页 | 深翻页 |
| 预聚合 / 物化视图 | 统计报表 |
| 读写分离 | 读远多于写 |
| 分库分表 | 单表 > 千万级且已用尽上面手段 |

### 5.2 深分页

```sql
-- ❌ 越翻越慢：先扫 100020 行再丢 100000 行
select * from messages order by created_at desc limit 20 offset 100000;

-- ✅ keyset：从上一页最后一条继续
select * from messages
 where conversation_id = 'c1' and created_at < :last_created_at
 order by created_at desc
 limit 20;
```

> keyset 分页要求**排序键唯一或带上唯一列**（如 `created_at, id`），否则会漏行/重复。

### 5.3 批量写

| 做法 | 说明 |
| --- | --- |
| 多值 INSERT | 一次 500~1000 行，别一条条发 |
| `COPY`（PG） | 大批量导入最快 |
| upsert | `INSERT ... ON CONFLICT DO UPDATE`（PG）/ `ON DUPLICATE KEY UPDATE`（MySQL） |
| 事务分批 | 每批提交，避免长事务 |

## 6. Redis 与缓存

### 6.1 五种结构够用

| 结构 | 典型场景 |
| --- | --- |
| String | 缓存 JSON、计数器、分布式锁 |
| Hash | 对象字段局部更新（会话状态） |
| List | 简单队列、最新 N 条 |
| Set | 去重、标签集合、共同好友 |
| ZSet | 排行榜、延迟队列（score = 时间戳）、滑动窗口限流 |

### 6.2 过期与淘汰

| 机制 | 说明 |
| --- | --- |
| 惰性删除 | 访问时才检查过期 |
| 定期删除 | 周期性抽样删除 |
| 淘汰策略 | `noeviction` / `allkeys-lru` / `allkeys-lfu` / `volatile-*` |

> 面试问「Redis 过期 key 到点就删吗？」答：**不是**。惰性 + 定期，所以内存可能短暂偏高。

### 6.3 缓存三问题

| 问题 | 现象 | 解法 |
| --- | --- | --- |
| 穿透 | 查不存在的数据，每次都打到 DB | 缓存空值（短 TTL）、布隆过滤器、参数校验 |
| 击穿 | 热点 key 过期瞬间，大量请求打到 DB | 互斥锁重建、逻辑过期 + 异步刷新 |
| 雪崩 | 大量 key 同时过期 / Redis 宕机 | 随机 TTL、多级缓存、熔断限流、集群 |

### 6.4 缓存一致性

| 方案 | 一致性 | 复杂度 |
| --- | --- | --- |
| 先更新 DB，再删缓存（Cache Aside） | 较好，仍有短暂脏读 | ✅ 推荐 |
| 先删缓存，再更新 DB | 差（并发读会回填旧值） | ❌ |
| 延迟双删 | 较好 | 中 |
| 订阅 binlog 异步删 | 最终一致 | 高 |

```
写：update DB → delete cache
读：get cache → miss → 查 DB → set cache（TTL 加随机）
```

> **不要**「更新 DB 后写缓存」——并发下容易写进旧值，且缓存里可能有别人刚回填的数据。

### 6.5 分布式锁

```bash
SET lock:job:42 <token> NX PX 30000      # 加锁（value 必须唯一）
# 释放：Lua 比较 token 再 del，防止误删别人的锁
```

| 问题 | 处理 |
| --- | --- |
| 业务超时但锁过期 | 看门狗续期（Redisson）；或把 TTL 设得足够长 |
| 主从切换丢锁 | Redlock（仍有争议）；强一致场景用 etcd/ZK 或 DB 唯一约束 |
| 锁误删 | value 存唯一 token，Lua 原子比较删除 |

## 7. 向量存储与检索

### 7.1 基础概念

| 概念 | 说明 |
| --- | --- |
| embedding | 文本 → 固定维度向量（如 1536 维） |
| 距离度量 | 余弦相似度（语义常用）、L2（欧氏）、内积 |
| 归一化 | 向量归一化后，余弦与内积等价 |
| 维度 | 维度越高表达越强，但存储与计算成本线性上升 |

### 7.2 索引类型

| 类型 | 原理 | 特点 |
| --- | --- | --- |
| Flat | 暴力全量比较 | 100% 召回，慢；小库可用 |
| IVF | 聚类分桶，只查 nprobe 个桶 | 快，召回受 nprobe 影响 |
| HNSW | 多层图，贪心搜索 | 召回高、延迟低，内存占用大 |
| PQ | 向量压缩编码 | 省内存，召回下降 |

```sql
-- pgvector
create index on knowledge_chunks using hnsw (embedding vector_cosine_ops);
select id, content from knowledge_chunks
 order by embedding <=> :query_vec
 limit 8;
```

### 7.3 生产 RAG 的检索链路

```
query → 改写/扩展 → 向量检索 Top-50 + 关键词检索 Top-50
      → RRF 融合去重 → rerank 精排 Top-8 → 拼上下文
```

| 环节 | 为什么需要 |
| --- | --- |
| 混合检索 | 向量擅长语义，BM25 擅长专有名词/编号 |
| RRF | 两路分数不可比，用排名融合更稳 |
| rerank | 粗排召回多，精排提升准确率 |
| 元数据过滤 | 先按租户/文档类型过滤，再算相似度 |

> 向量检索不是「越像越好」，而是「**先过滤、再召回、后精排**」。纯向量在数字、代码、人名上经常翻车。

## 9. 容量与选型

```
日活 10 万，人均 20 条消息 → 200 万条/天
每条 1 KB → 2 GB/天 → 一年约 700 GB（未压缩、未归档）
峰值 QPS 假设 500 → 单实例 PG 可扛，但连接池要按 worker 核算
```

| 问题 | 先做什么 |
| --- | --- |
| 查询慢 | 索引 + 改写 + 分页 |
| 写入慢 | 批量 + 减少索引 + 异步 |
| 连接打满 | 池化 + 降并发 + PgBouncer |
| 单表太大 | 分区（按时间）→ 归档 → 分表 |
| 读多 | 缓存 → 只读副本 |

> 面试答题顺序：**先算量，再说瓶颈，最后给演进路线**。直接说「上 Kafka、分库分表」会被追问「为什么」。

## 10. 面试真题

### Q1. 为什么数据库索引用 B+ 树而不是哈希或红黑树？

**结论**：B+ 树为磁盘设计——节点大小等于页、扇出极大、树高低，范围查询靠叶子链表。

**展开**：
1. 哈希只支持等值，不支持范围与排序；
2. 红黑树是二叉，千万行树高约 20+，每次节点访问几乎都是一次随机 IO；
3. B+ 树扇出约 500，3 层可覆盖上亿行，且非叶子只存键、叶子存数据/指针，缓存命中率高；
4. 叶子间有链表，范围扫描顺序 IO。

### Q2. 什么是回表？怎么避免？

**结论**：二级索引只存主键（InnoDB）或行指针（PG），要取其他列就得回原表，这就是回表。

**展开**：把查询需要的列都放进联合索引 → 覆盖索引，`EXPLAIN` 出现 `Using index`。代价是索引变宽、写入变慢，所以只对高频查询做覆盖。

### Q3. 联合索引的最左前缀原则是什么？

**结论**：索引 `(a, b, c)` 只能从最左列开始连续使用。

**展开**：`a`、`a+b`、`a+b+c` 可用；`b`、`b+c` 不可用；`a + c` 只用 `a`；`a = ? and b > ? and c = ?` 中 `c` 无法参与定位。设计时等值列在前、范围列在后。

### Q4. 索引什么时候会失效？

**结论**：列被函数/运算包裹、隐式类型转换、前导 `%`、违反最左前缀、OR 连接无索引列、选择率过高。

**展开**：补一句「优化器基于成本，有时不走索引是正确选择」，再举 `status` 只有两个值的例子，体现理解深度。

### Q5. 事务的隔离级别有哪些？MySQL 默认哪个？

**结论**：读未提交、读已提交、可重复读、串行化；InnoDB 默认可重复读，PG 默认读已提交。

**展开**：把脏读/不可重复读/幻读的表格说清；RR 下快照读靠 MVCC，当前读靠 Next-Key Lock。

### Q6. MVCC 是怎么实现的？

**结论**：多版本 + 可见性判断，读不加锁。

**展开**：InnoDB 用隐藏事务 id + undo log，读时按 ReadView 判断版本可见；PG 用元组 `xmin/xmax` + 快照。代价是旧版本堆积，长事务会阻止清理。

### Q7. 缓存穿透、击穿、雪崩的区别？

**结论**：穿透是「数据不存在」，击穿是「单个热点过期」，雪崩是「大量 key 同时失效或 Redis 挂了」。

**展开**：分别给解法——空值/布隆、互斥锁/逻辑过期、随机 TTL/多级缓存/熔断。再补一句监控：命中率、DB QPS 突增。

### Q8. 缓存和数据库怎么保持一致？

**结论**：Cache Aside——先更新 DB，再删除缓存；读时 miss 回填。

**展开**：说明为什么不是「更新缓存」（并发写旧值）；延迟双删适用于「删缓存后仍有并发读回填」；强一致只能靠加锁或读穿 DB。

### Q9. Redis 分布式锁怎么实现？有什么坑？

**结论**：`SET key token NX PX ttl` 加锁，Lua 比较 token 后删除。

**展开**：坑一，业务超过 TTL → 看门狗续期；坑二，主从切换丢锁 → Redlock 或 etcd；坑三，误删 → token 校验。再补：锁只是效率工具，正确性最终要靠唯一约束/状态机。

### Q10. 深分页为什么慢？怎么优化？

**结论**：`OFFSET 100000` 要先扫描并丢弃 10 万行。

**展开**：keyset 分页（带上一页最后一条的排序键）；或先查主键再回表；或限制最大翻页深度。排序键要加唯一列保证稳定。

### Q11. 向量检索为什么需要 HNSW？和 IVF 怎么选？

**结论**：HNSW 用图结构近似搜索，召回高、延迟低；IVF 用聚类分桶，内存更省、构建更快。

**展开**：数据量小用 Flat；百万级、内存充足用 HNSW；超大规模或内存敏感用 IVF-PQ。再说 pgvector 的 `hnsw` / `ivfflat` 与 `<=>` 余弦距离。

### Q12. RAG 检索效果差，怎么排查？

**结论**：先分层——分块、召回、精排、上下文、生成，逐层验证。

**展开**：
1. 分块是否切断语义、块太大或太小；
2. 只走向量 → 加 BM25 混合与 RRF；
3. 召回数量是否够（Top-K）、是否被元数据过滤误杀；
4. 加 rerank；
5. 上下文是否超长被截断、是否带引用；
6. 最后才怀疑 embedding 模型与 prompt。

## 11. 速记卡

- **B+ 树三个数字**：页 16 KB、扇出约 500、3 层约上亿行。
- **索引口诀**：等值在前、范围在后、排序列跟着等值列。
- **失效六因**：函数、隐转、前导 `%`、最左缺失、OR 无索引、选择率过高。
- **隔离级别**：RU / RC / RR / Serializable；MySQL 默认 RR，PG 默认 RC。
- **MVCC**：InnoDB 看 undo + ReadView，PG 看 xmin/xmax + 快照。
- **缓存三问题**：穿透（不存在）、击穿（单个热点）、雪崩（大面积）。
- **一致性**：先更 DB 再删缓存，读 miss 回填。
- **分布式锁**：`SET NX PX` + token + Lua 释放。
- **向量**：先过滤、再召回、后精排；混合检索 + RRF + rerank。
- **选型顺序**：索引 → 缓存 → 读写分离 → 分区 → 分表。
