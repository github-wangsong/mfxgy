## 1. 一张图：一次 HTTPS 请求

```
浏览器
  ↓ 1. DNS 解析：域名 → IP
  ↓ 2. TCP 三次握手：建立连接
  ↓ 3. TLS 握手：协商密钥、校验证书
  ↓ 4. HTTP 请求：GET /v1/apps
  ↓ 5. 服务端处理：NestJS / FastAPI
  ↓ 6. HTTP 响应：状态码 + Header + Body
  ↓ 7. 浏览器渲染 / 前端更新
```

> 面试题「输入 URL 到页面展示发生了什么」，就是按这 7 步展开，再补缓存、CDN、渲染。

## 2. 分层模型

| OSI 七层 | TCP/IP 四层 | 常见协议 | 典型设备/组件 |
| --- | --- | --- | --- |
| 应用层 | 应用层 | HTTP、HTTPS、DNS、SSE、WebSocket | 应用服务、Nginx |
| 表示层 | 应用层 | TLS、编码 | — |
| 会话层 | 应用层 | 会话管理 | — |
| 传输层 | 传输层 | TCP、UDP、QUIC | 四层负载均衡 |
| 网络层 | 网络层 | IP、ICMP、路由 | 路由器、三层交换机 |
| 数据链路层 | 网络接口层 | Ethernet、ARP | 交换机 |
| 物理层 | 网络接口层 | 光纤、网线、无线电 | 网卡、光模块 |

| 概念 | 一句话 |
| --- | --- |
| 四层负载均衡 | 按 IP + 端口转发，性能高，不懂 HTTP |

| NAT | 内网地址 ↔ 公网地址转换 |
| CDN | 把静态资源缓存到离用户近的节点 |

## 3. TCP 与 UDP

### 3.1 TCP 三次握手

```
客户端                          服务端
  SYN (seq=x)        ────────>
                     <────────  SYN + ACK (seq=y, ack=x+1)
  ACK (ack=y+1)      ────────>
  连接建立
```

**为什么是三次，不是两次？**

- 双方都要确认「自己的发送能力」和「对方的接收能力」。
- 防止历史重复的 SYN 包建立错误连接。
- 同步双方的初始序列号（ISN）。

### 3.2 TCP 四次挥手

```
主动关闭方                     被动关闭方
  FIN                ────────>
                     <────────  ACK
                     <────────  FIN
  ACK                ────────>
  主动关闭方进入 TIME_WAIT，等待 2MSL
```

| 问题 | 答案 |
| --- | --- |
| 为什么四次？ | TCP 是全双工，两个方向要分别关闭；被动方可能还有数据要发 |
| 为什么有 TIME_WAIT？ | 保证最后一个 ACK 能到达；让旧连接的数据包在网络中过期 |
| TIME_WAIT 过多怎么办？ | 连接池复用、`SO_REUSEADDR`、调小 `tcp_fin_timeout`（谨慎）、减少短连接 |
| 谁进入 TIME_WAIT？ | **主动关闭方** |

### 3.3 TCP 如何保证可靠

| 机制 | 作用 |
| --- | --- |
| 序列号 + 确认号 | 排序、去重、确认 |
| 超时重传 | 丢包后重发 |
| 校验和 | 检测数据损坏 |
| 滑动窗口 | 流量控制，避免接收方被压垮 |
| 拥塞控制 | 避免把网络压垮：慢启动、拥塞避免、快重传、快恢复 |
| 粘包/拆包 | 应用层要自己划分消息边界（长度前缀、JSON 帧、分隔符） |

> TCP 是**字节流**，没有消息边界；「粘包」不是 TCP 的 bug，是应用层没定义边界。

### 3.4 TCP vs UDP

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠（重传/确认） | 不可靠 |
| 顺序 | 保证 | 不保证 |
| 速度/开销 | 较慢、头部 20B+ | 快、头部 8B |
| 适用 | HTTP/1.1、HTTP/2、数据库 | DNS、音视频、游戏、QUIC/HTTP/3 |

## 4. HTTP

### 4.1 版本演进

| 版本 | 关键特性 | 解决的问题 | 遗留问题 |
| --- | --- | --- | --- |
| HTTP/1.0 | 短连接 | — | 每个请求新建 TCP |
| HTTP/1.1 | keep-alive、管线化、Host | 连接复用 | 队头阻塞（HOL） |
| HTTP/2 | 二进制分帧、多路复用、HPACK | 应用层 HOL | TCP 层 HOL、连接级阻塞 |
| HTTP/3 | QUIC（UDP）、0-RTT、独立流 | TCP 层 HOL | 部署/兼容性 |

> HTTP/2 的「多路复用」是在**一个 TCP 连接**上并行多个 stream；丢一个包仍可能阻塞所有 stream，所以 HTTP/3 改用 UDP + QUIC。

### 4.2 方法与状态码

| 方法 | 语义 | 幂等 |
| --- | --- | --- |
| GET | 查询 | ✅ |
| POST | 创建/提交 | ❌ |
| PUT | 全量替换 | ✅ |
| PATCH | 局部更新 | ❌（通常） |
| DELETE | 删除 | ✅ |

| 状态码 | 含义 | 常见坑 |
| --- | --- | --- |
| 200 / 201 / 204 | 成功 / 已创建 / 无内容 | 204 不能带 body |
| 301 / 308 | 永久重定向 | 308 保留方法 |
| 302 / 307 | 临时重定向 | 307 保留方法 |
| 400 / 422 | 请求错误 / 校验失败 | 400 与 422 的语义要团队统一 |
| 401 / 403 | 未认证 / 无权限 | 401 是「你是谁」，403 是「你不能」 |
| 404 | 不存在 | 归属校验常用 404，避免泄露资源存在性 |
| 409 | 冲突 | 唯一键冲突、并发写 |
| 429 | 限流 | 配合 `Retry-After` |
| 499 | 客户端主动断开（Nginx） | 常见于用户取消、超时 |
| 502 / 504 | 网关错误 / 网关超时 | 502 上游挂了，504 上游太慢 |

### 4.3 缓存

| Header | 作用 |
| --- | --- |
| `Cache-Control` | `max-age`、`no-cache`、`no-store`、`private/public` |
| `ETag` / `If-None-Match` | 内容指纹，命中返回 304 |
| `Last-Modified` / `If-Modified-Since` | 时间戳校验 |
| `Vary` | 按 Header 区分缓存（如 `Accept-Encoding`） |

> `no-cache` 不是不缓存，而是「每次用前必须校验」；`no-store` 才是完全不存。

### 4.4 CORS

| 点 | 说明 |
| --- | --- |
| 同源 | 协议 + 域名 + 端口都相同 |
| 简单请求 | 不触发预检 |
| 预检 | `OPTIONS`，带 `Access-Control-Request-Method/Headers` |
| 凭证 | `allow_credentials=true` 时，`Allow-Origin` 不能是 `*` |
| 常见漏项 | `expose_headers`、`max_age`、自定义 Header |

## 5. HTTPS / TLS

### 5.1 握手要解决什么

1. **身份认证**：确认服务端证书由受信任 CA 签发。
2. **密钥协商**：双方协商出对称会话密钥。
3. **完整性**：后续数据不能被篡改。

### 5.2 简化流程

```
客户端 → 服务端：ClientHello（支持的版本、加密套件、随机数）
服务端 → 客户端：ServerHello + 证书链
客户端：校验证书链，生成预主密钥，用服务端公钥加密后发送
双方：用随机数 + 预主密钥推导会话密钥
后续：用对称密钥加密通信
```

| 问题 | 答案 |
| --- | --- |
| 为什么不用非对称加密传所有数据？ | 非对称加密慢，只用于握手协商；数据传输用对称加密 |
| HTTPS 一定安全吗？ | 只能防「传输被窃听/篡改」；不能防服务端作恶、客户端被入侵、证书被误信 |
| 中间人攻击怎么防？ | 校验证书链、域名、有效期；不要忽略证书错误 |
| TLS 1.3 快在哪？ | 1-RTT 握手（甚至 0-RTT），减少往返；淘汰不安全算法 |

## 6. DNS

```
浏览器缓存 → 系统缓存 → 本地 DNS 服务器（递归）
  → 根域名服务器 → 顶级域服务器 → 权威域名服务器
  → 返回 IP → 缓存（TTL）
```

| 记录 | 含义 |
| --- | --- |
| A | 域名 → IPv4 |
| AAAA | 域名 → IPv6 |
| CNAME | 别名 → 另一个域名 |
| MX | 邮件服务器 |
| TXT | 验证、SPF、安全策略 |

| 问题 | 答案 |
| --- | --- |
| 为什么 DNS 常用 UDP？ | 请求小、快，省握手；响应过大或区域传送用 TCP |
| DNS 劫持怎么防？ | DoH / DoT、DNSSEC、可信 DNS |
| TTL 有什么用？ | 控制缓存时长；太大切换慢，太小解析压力大 |

## 7. 实时通信：SSE / WebSocket / 长轮询

| 方案 | 方向 | 协议 | 适用 |
| --- | --- | --- | --- |
| 短轮询 | 客户端反复问 | HTTP | 简单但浪费 |
| 长轮询 | 服务端 hold 请求 | HTTP | 兼容性最好 |
| SSE | 服务端 → 客户端单向 | HTTP `text/event-stream` | LLM 流式输出、通知 |
| WebSocket | 双向 | HTTP Upgrade → WS | 聊天、协同编辑、游戏 |

### 7.1 SSE 帧格式

```
event: token
data: {"text":"你"}

event: token
data: {"text":"好"}

event: done
data: {"finishReason":"stop"}
```

| 字段 | 作用 |
| --- | --- |
| `event` | 事件名，前端 `addEventListener` 订阅 |
| `data` | 数据，按行拼接；一个事件可多行 |
| `id` | 事件 ID，断线重连时通过 `Last-Event-ID` 续传 |
| `retry` | 重连间隔（毫秒） |

### 7.2 SSE 的工程坑

- 响应头必须是 `Content-Type: text/event-stream`、`Cache-Control: no-cache`。
- Nginx 默认缓冲会「攒着不发」：加 `X-Accel-Buffering: no` 或关闭 `proxy_buffering`。
- 心跳：定期发注释行 `: ping`，防止连接被中间设备断开。
- 断线重连：前端用 `EventSource` 自动重连；服务端支持 `Last-Event-ID`。
- 连接数：HTTP/1.1 下同域并发连接有限，建议 HTTP/2 或独立域名。

> 为什么 LLM 流式常用 SSE 而不是 WebSocket？因为它是**单向**推送，走普通 HTTP，兼容代理/鉴权/日志，成本更低。

## 8. 线上排障

| 现象 | 常见原因 | 排查 |
| --- | --- | --- |
| 502 Bad Gateway | 上游服务挂了 / 端口不对 / 健康检查失败 | 看上游日志、`curl` 直连、Nginx error log |
| 504 Gateway Timeout | 上游处理超时 | 查慢查询、线程池、LLM 调用超时 |
| 499 | 客户端主动断开 | 用户取消、前端超时、流式被中断 |
| 连接建立慢 | DNS、TCP 握手、TLS 握手 | `curl -w` 分阶段计时 |
| 大量 TIME_WAIT | 短连接过多 | 连接池、keep-alive、`ss -s` |
| 吞吐上不去 | 连接池太小、带宽、锁 | 压测、`ss`、`top`、`iostat` |
| 文件描述符耗尽 | 连接/文件未关闭 | `ulimit -n`、`lsof -p` |

```bash
# 查看连接状态分布
ss -s
ss -tan state time-wait | wc -l

# 查看某进程打开的文件/连接
lsof -p <pid>

# curl 分阶段计时
curl -o /dev/null -s -w "dns:%{time_namelookup} tcp:%{time_connect} tls:%{time_appconnect} ttfb:%{time_starttransfer}\n" https://example.com
```

> 注意：上面命令里的 `<pid>` 只是占位符，实际执行时替换成进程号。

## 9. 面试真题

### Q1. 输入 URL 到页面展示发生了什么？

**结论**：DNS 解析 → TCP 握手 → TLS 握手 → HTTP 请求 → 服务端处理 → 响应 → 浏览器解析渲染。

**展开**：

- 先查浏览器/系统/DNS 缓存，未命中再递归解析。
- 建立 TCP 连接；HTTPS 还要 TLS 握手。
- 发 HTTP 请求，服务端可能经过负载均衡、网关、应用。
- 浏览器解析 HTML、构建 DOM/CSSOM、布局、绘制。
- 静态资源可能走 CDN/强缓存。

### Q2. TCP 为什么三次握手？两次行不行？

**结论**：三次才能让双方都确认「自己的发送 + 对方的接收」正常，并同步初始序列号；两次无法确认客户端的接收能力。

**展开**：

- 防止历史重复 SYN 建立错误连接。
- 同步双方 ISN。
- 四次挥手的对称性也说明连接是双向确认的。

### Q3. TCP 四次挥手为什么有 TIME_WAIT？

**结论**：主动关闭方等待 2MSL，保证最后一个 ACK 能到达，并让旧连接的数据包在网络中过期。

**展开**：

- 如果 ACK 丢失，被动方会重发 FIN，主动方还能再回 ACK。
- 2MSL 确保旧连接的重复包不会干扰新连接。
- TIME_WAIT 过多会占用本地端口；用连接池/keep-alive 缓解。

### Q4. TCP 和 UDP 的区别？什么时候用 UDP？

**结论**：TCP 可靠、有序、面向连接；UDP 无连接、不可靠、开销小。实时音视频、游戏、DNS、QUIC 用 UDP。

**展开**：

- TCP 有重传、确认、流量/拥塞控制。
- UDP 把可靠性交给应用层（或 QUIC）。
- HTTP/3 用 UDP 是为了避免 TCP 层队头阻塞。

### Q5. HTTP/2 为什么快？HTTP/3 为什么用 UDP？

**结论**：HTTP/2 用二进制分帧 + 多路复用 + HPACK 头压缩，减少连接与头部开销；HTTP/3 用 QUIC 解决 TCP 层队头阻塞。

**展开**：

- HTTP/1.1 管线化仍有应用层 HOL。
- HTTP/2 一个 TCP 连接并行多 stream，但丢包仍阻塞所有 stream。
- QUIC 在 UDP 上实现可靠传输与独立流，支持 0-RTT。

### Q6. HTTPS 的握手过程？为什么还要非对称加密？

**结论**：非对称加密用于身份认证与密钥协商，后续数据用对称加密；对称加密快，非对称加密解决「密钥怎么安全交换」。

**展开**：

- 证书链校验服务端身份。
- 客户端用服务端公钥加密预主密钥。
- 双方用随机数推导会话密钥。
- TLS 1.3 减少往返，支持 1-RTT/0-RTT。

### Q7. SSE 和 WebSocket 的区别？为什么 LLM 流式用 SSE？

**结论**：SSE 是服务端到客户端的单向 HTTP 流；WebSocket 是双向长连接。LLM 只需要服务端推送 token，SSE 更简单、兼容性更好。

**展开**：

- SSE 走普通 HTTP，天然支持鉴权、代理、日志。
- WebSocket 需要 Upgrade，双向能力更强但运维复杂。
- SSE 要处理代理缓冲、心跳、断线重连。

### Q8. TCP 粘包是怎么回事？

**结论**：TCP 是字节流，不保留消息边界；应用层需要自己定义边界（长度前缀、分隔符、JSON 帧）。

**展开**：

- 发送方一次 write 可能被拆成多个包，多次 write 也可能合并。
- UDP 面向报文，不存在粘包。
- HTTP 用 Content-Length / chunked 划分 body。

### Q9. 502 和 504 的区别？

**结论**：502 是网关从上游收到无效响应/连不上；504 是网关等待上游响应超时。

**展开**：

- 502 常见于上游进程挂了、端口错、健康检查失败。
- 504 常见于上游太慢、线程池满、数据库/LLM 调用超时。
- 499 是客户端先断开，Nginx 记录为 499。

### Q10. 为什么需要连接池？

**结论**：复用 TCP/TLS 连接，减少握手与 TIME_WAIT，控制并发和资源上限。

**展开**：

- 每次新建连接要 DNS + TCP + TLS，成本高。
- 连接池限制最大连接数，保护数据库/上游。
- 池太小会排队，池太大可能打满上游。

### Q11. DNS 解析过程？为什么用 UDP？

**结论**：浏览器/系统缓存 → 本地 DNS 递归查询 → 根/TLD/权威服务器；UDP 快、请求小。

**展开**：

- 递归查询由本地 DNS 代劳；迭代查询是 DNS 服务器之间。
- 响应过大或区域传送用 TCP。
- DoH/DoT 加密 DNS，防劫持。

### Q12. 线上接口慢，怎么排查？

**结论**：先分段计时，再定位 DNS、TCP、TLS、服务端处理、下游依赖。

**展开**：

- `curl -w` 看 DNS/TCP/TLS/TTFB。
- 看 Nginx 日志状态码与 upstream 时间。
- 服务端看慢查询、锁、线程池、LLM/外部 API。
- 结合 `ss`、`top`、`iostat`、链路追踪。
