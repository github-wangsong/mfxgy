# 06 · 系统设计与分布式

> 定位：Agent 平台天生是分布式系统——长耗时 LLM 调用、流式输出、多租户配额、外部 API 不稳定。系统设计题考的不是背组件，而是**估算 → 取舍 → 演进**。
> 面试权重：★★★★★
> 关联：[02 计算机网络](./02-计算机网络.md)（超时/连接）、[05 数据库与存储](./05-数据库与存储.md)（事务/缓存）。

## 2. 容量估算

### 2.1 常用数量级

| 指标 | 数量级 |
| --- | --- |
| 单机 QPS（简单查询 + 缓存） | 1k ~ 10k |
| 单条 SQL 延迟（索引命中） | 0.5 ~ 5 ms |
| Redis 单次操作 | 0.1 ~ 1 ms |
| 同机房 HTTP 往返 | 1 ~ 5 ms |
| 跨地域往返 | 30 ~ 100 ms |
| 单条 LLM 响应 | 1 ~ 30 s（流式首 token 0.3 ~ 2 s） |

### 2.2 估算模板

```
日活 DAU = 10 万
人均请求 = 20 次/天
QPS 平均 = 10 万 × 20 / 86400 ≈ 23
峰值 QPS ≈ 平均 × 3 ~ 5 ≈ 100
存储 = 日增数据 × 保留天数 × 副本数
带宽 = 峰值 QPS × 平均响应大小
```

> LLM 场景额外算 **token 成本**：`请求数 × 平均输入 token × 单价 + 输出 token × 单价`。成本常常比服务器贵。

## 3. CAP 与一致性

### 3.1 CAP 的正确理解

| 字母 | 含义 |
| --- | --- |
| C | 所有节点同一时刻看到同一份数据（线性一致） |
| A | 每个请求都能得到非错误响应 |
| P | 网络分区时系统仍能工作 |

网络分区是**客观事实**，所以真正的选择是：

| 选择 | 行为 | 例子 |
| --- | --- | --- |
| CP | 分区时拒绝部分请求，保一致 | 支付、库存扣减、分布式锁 |
| AP | 分区时继续服务，接受不一致 | 聊天记录、Feed、点赞数 |

> 补充 PACELC：即使没有分区（P），也要在延迟（L）与一致（C）之间取舍——强一致通常意味着多副本同步写，延迟更高。

### 3.2 一致性模型从强到弱

```
线性一致 > 顺序一致 > 因果一致 > 最终一致
```

| 场景 | 够用的一致性 |
| --- | --- |
| 余额、库存 | 强一致（事务 / 条件更新） |
| 会话消息 | 读写自己的写（read-your-writes）即可 |
| 搜索索引、推荐 | 最终一致 |
| 统计计数 | 最终一致 + 定期校准 |

## 4. 幂等：分布式的第一课

### 4.1 为什么必须幂等

```
客户端超时 → 重试 → 服务端其实已成功 → 重复扣款 / 重复发消息
```

### 4.2 四种实现

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 幂等键 | 客户端传 `Idempotency-Key`，服务端存结果 | 支付、创建类接口 |
| 唯一约束 | `unique(user_id, request_id)`，重复插入报冲突后返回原结果 | 简单可靠 |
| 状态机 | 只允许 `pending → running → done`，重复请求直接返回当前状态 | 长任务 |
| 去重表 + TTL | 处理过的消息 id 存 Redis/表，过期清理 | 消息消费 |

```python
# 幂等消费的典型形状
if not dedup.acquire(message_id, ttl=86400):
    return  # 已处理过，直接确认
try:
    handle(message)
finally:
    dedup.release_on_failure(message_id)  # 失败要允许重试
```

> 幂等的边界：**先落「已接收」再处理**，还是「处理完再标记」？前者防重更稳，后者防丢更稳——通常用「处理中」状态 + 超时回收。

## 5. 超时、重试与退避

### 5.1 超时要分层

| 层 | 示例 |
| --- | --- |
| 连接超时 | TCP/TLS 建连，1 ~ 3 s |
| 读超时 | 等待响应，按接口定 |
| 总超时 / deadline | 整个请求预算，向下传递 |
| 幂等窗口 | 重试总时长不能超过上游 deadline |

> 没有 deadline 的重试会「越重试越慢」，最后上游早已超时，下游还在跑。

### 5.2 重试的三条铁律

1. **只重试幂等操作**（或先做幂等）；
2. **指数退避 + 抖动**：`sleep = min(cap, base × 2^attempt) × random(0.5, 1.5)`；
3. **重试预算**：重试次数 / 重试流量占比设上限，避免重试风暴。

| 不该重试 | 该重试 |
| --- | --- |
| 400 参数错误 | 429 限流（带 `Retry-After`） |
| 401 / 403 | 500 / 502 / 503 / 504 |
| 业务规则拒绝 | 连接超时、网络抖动 |

### 5.3 重试风暴

```
下游变慢 → 上游超时重试 → 下游请求翻倍 → 更慢 → 雪崩
```

| 手段 | 说明 |
| --- | --- |
| 重试预算 | 只允许 10% 的请求重试 |
| 熔断 | 下游错误率超阈值直接快速失败 |
| 单飞（singleflight） | 相同请求合并为一次 |
| 随机化 | 避免所有客户端同时重试 |

## 6. 限流

### 6.1 四种算法

| 算法 | 特点 | 场景 |
| --- | --- | --- |
| 固定窗口 | 简单；窗口边界可能双倍突发 | 粗粒度配额 |
| 滑动窗口 | 精确，需存请求时间 | 中等精度 |
| 令牌桶 | 允许突发，按速率补充 | API 限流（最常用） |
| 漏桶 | 输出恒定平滑 | 保护下游 |

### 6.2 分布式限流

```lua
-- Redis + Lua：令牌桶（原子）
local key = KEYS[1]
local rate = tonumber(ARGV[1])       -- 每秒补充
local burst = tonumber(ARGV[2])      -- 桶容量
local now = tonumber(ARGV[3])
local data = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1]) or burst
local ts = tonumber(data[2]) or now
tokens = math.min(burst, tokens + (now - ts) * rate)
if tokens < 1 then return 0 end
redis.call('HMSET', key, 'tokens', tokens - 1, 'ts', now)
return 1
```

| 要点 | 说明 |
| --- | --- |
| 原子性 | 读-算-写必须在一个 Lua 脚本里 |
| 时钟 | 用 Redis 时间或传入时间，避免各机器时钟漂移 |
| 维度 | 按用户 / 按租户 / 按 IP / 按 API Key |
| 拒绝方式 | 429 + `Retry-After`；或排队（要有上限） |

> 限流的目的不是「拒绝」，而是**保护系统**。超过配额时给明确错误，比让所有人一起变慢更好。

## 7. 熔断与降级

### 7.1 熔断三态

```
CLOSED（正常） --错误率超阈值--> OPEN（快速失败）
OPEN --冷却时间到--> HALF_OPEN（放少量试探）
HALF_OPEN --成功--> CLOSED
HALF_OPEN --失败--> OPEN
```

| 参数 | 说明 |
| --- | --- |
| 统计窗口 | 最近 10 s / 100 次请求 |
| 失败率阈值 | 例如 50% |
| 最小请求数 | 样本太少不熔断 |
| 冷却时间 | 5 ~ 30 s |

### 7.2 降级策略

| 场景 | 降级 |
| --- | --- |
| 主模型超时 | 切备用模型 / 更小模型 |
| RAG 检索失败 | 只用对话上下文，标注「未检索」 |
| 向量库不可用 | 退化为关键词检索 |
| 限流触发 | 返回缓存答案或排队提示 |
| 非核心功能 | 直接关闭（评论、推荐） |

> 舱壁模式：不同下游用不同线程池/连接池，一个慢下游不拖垮全部。

## 8. 消息队列

### 8.1 三个价值

| 价值 | 例子 |
| --- | --- |
| 解耦 | 运行结束后发事件，通知/计费/审计各自订阅 |
| 削峰 | 大量文档解析任务排队慢慢消费 |
| 异步 | 长任务不阻塞 HTTP 请求 |

### 8.2 投递语义

| 语义 | 实现方式 | 现实 |
| --- | --- | --- |
| 至多一次 | 发完就不管 | 可能丢 |
| 至少一次 | ACK + 重投 | 可能重复 → **靠幂等** |
| 恰好一次 | 事务 + 去重 / 幂等 | 代价高，通常是「至少一次 + 幂等」 |

> 面试标准答案：**「不追求恰好一次，追求至少一次 + 消费端幂等」**。

### 8.3 顺序与积压

| 问题 | 处理 |
| --- | --- |
| 顺序 | 按业务键分区（同一会话进同一 partition / 同一队列） |
| 积压 | 加消费者、批量消费、临时扩容、降级非核心消费 |
| 死信 | 重试 N 次后进 DLQ，人工/定时处理 |
| 重复 | 去重表 + 唯一键 + 状态机 |

### 8.4 事务消息与 Outbox

「更新数据库 + 发消息」不能直接双写：

```
❌ update DB; publish MQ   → 一个成功一个失败就不一致
✅ 本地事务里写 outbox 表；由 relay/CDC 投递到 MQ
```

| 方案 | 说明 |
| --- | --- |
| Outbox | 业务表 + 事件表同事务提交，后台投递 |
| CDC | 订阅 binlog/WAL，自动同步 |
| 本地消息表 | 定时扫表补发，简单可靠 |

## 9. 分布式事务

| 方案 | 一致性 | 复杂度 | 场景 |
| --- | --- | --- | --- |
| 2PC | 强 | 高，阻塞 | 传统数据库跨库 |
| TCC | 较强 | 高，要写 Try/Cancel | 支付、库存 |
| Saga | 最终 | 中，要补偿 | 长流程、微服务 |
| 本地消息表 / Outbox | 最终 | 低 | 大多数业务 |
| 事务消息（RocketMQ） | 最终 | 中 | 有 MQ 时 |

> 原则：**能在单库事务里解决就不要分布式事务**；必须拆时，优先「最终一致 + 幂等 + 对账」。

## 10. 分布式 ID 与锁

### 10.1 ID 方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 自增 ID | 简单、有序 | 暴露规模；分库分表难 |
| UUID v4 | 本地生成、无冲突 | 无序（B+ 树插入抖动）、占空间 |
| UUID v7 | **时间有序**、本地生成 | 仍是 128 位 |
| 雪花（Snowflake） | 趋势递增、可排序 | 依赖时钟；worker id 要分配 |
| 号段（segment） | 批量取号、性能好 | 依赖 DB/中心服务 |

```
Snowflake：1 位符号 + 41 位毫秒时间 + 10 位机器 + 12 位序列（每毫秒 4096 个）
```

> 时钟回拨是雪花的经典坑：等待、抛错或切换备用 worker。

### 10.2 锁与 fencing token

```
拿锁 → 得到单调递增的 fencing token → 写存储时校验 token 更大才允许
```

> 解决「锁过期了但旧持有者还在写」：存储层拒绝旧 token。单纯靠 Redis 锁无法根治。

## 11. 长任务编排（Agent Run）

### 11.1 为什么不能只用 HTTP 同步

| 问题 | 后果 |
| --- | --- |
| LLM 调用 30 s+ | 网关/浏览器超时 |
| 步骤多、可能失败 | 需要重试与断点续跑 |
| 用户要实时看进度 | 需要事件流 |
| 进程重启 | 内存里的状态全丢 |

### 11.2 推荐结构

```
run 表（状态机：queued → running → succeeded / failed / canceled）
run_events 表（追加写：step_started / token / tool_call / step_finished / run_finished）
业务数据表（会话、消息）
```

| 能力 | 做法 |
| --- | --- |
| 断点续跑 | 每步结束写 checkpoint（已完成节点、变量快照） |
| 崩溃恢复 | worker 租约（lease）+ 心跳；租约过期由其他 worker 接管 |
| 事件重放 | 客户端带 `Last-Event-ID`，从事件表补发 |
| 取消 | 置 `canceled` 标志，worker 在安全点检查 |
| 幂等 | 每个 step 有唯一 key，重复执行不产生副作用 |

> 这就是项目阶段 11 的「Run 模型 + 事件重放」：**状态持久化 + 事件追加 + 可重放**，比「一个长连接撑到底」稳得多。

### 11.3 状态机约束

| 规则 | 原因 |
| --- | --- |
| 只能向前流转 | 避免 `done → running` 的重复执行 |
| 终态不可变 | 保证重放结果稳定 |
| 每次流转写事件 | 可审计、可回放 |
| 超时自动失败 | 防止永久 `running` 占资源 |

## 12. 可观测性

### 12.1 三件套

| 类型 | 回答的问题 | 常用 |
| --- | --- | --- |
| 日志 | 发生了什么 | 结构化 JSON + `trace_id` |
| 指标 | 整体健康度 | QPS、P95/P99、错误率、饱和度 |
| 链路追踪 | 慢在哪一步 | OpenTelemetry、span |

### 12.2 黄金指标

| 指标 | 含义 |
| --- | --- |
| Latency | 延迟（分 P50/P95/P99，别看平均值） |
| Traffic | 请求量 |
| Errors | 错误率（按状态码/业务码分组） |
| Saturation | 饱和度（CPU、连接池、队列长度） |

### 12.3 SLI / SLO / 错误预算

```
SLI：实际测量值（如 99.95% 成功）
SLO：目标（如 99.9%/月）
错误预算：1 - SLO → 每月 43.2 分钟
```

| SLO | 每月不可用 |
| --- | --- |
| 99% | 7.2 小时 |
| 99.9% | 43.2 分钟 |
| 99.95% | 21.6 分钟 |
| 99.99% | 4.32 分钟 |

> 错误预算耗尽 → 冻结发布、优先修稳定性。这是「用数据做取舍」，面试加分。

### 12.4 排障顺序

```
① 看入口错误率与延迟（是全局还是单接口）
② 看下游依赖（DB / Redis / LLM / 第三方）
③ 看资源（连接池、线程池、FD、CPU、内存）
④ 看变更（发布、配置、流量）
⑤ 看单条 trace（最慢 span）
```

## 13. 多租户与成本

| 维度 | 做法 |
| --- | --- |
| 数据隔离 | 行级 `tenant_id` + 强制过滤；大客户独立库 |
| 配额 | 按租户 QPS / token / 存储限额 |

## 14. 面试真题

### Q1. CAP 怎么理解？为什么不能三个同时满足？

**结论**：网络分区不可避免，分区发生时只能在一致性（C）与可用性（A）之间选。

**展开**：CP 拒绝部分请求保一致（支付）；AP 继续服务接受短暂不一致（Feed）。补 PACELC：无分区时在延迟与一致间取舍。

### Q2. 接口幂等怎么做？

**结论**：幂等键 + 唯一约束（或去重表 + 状态机），让重复请求返回同一结果。

**展开**：客户端生成 `Idempotency-Key`；服务端同事务写「请求记录 + 业务数据」；重复键直接返回上次结果。长任务用状态机：已是 `running` 就返回当前状态，不重复启动。

### Q3. 重试怎么设计才安全？

**结论**：只重试幂等操作 + 指数退避加抖动 + 重试预算 + 总 deadline。

**展开**：4xx 不重试（429 除外）；重试次数 2~3 次；用 singleflight 合并相同请求；下游熔断时快速失败。

### Q4. 限流算法怎么选？

**结论**：令牌桶最常用（允许突发），漏桶适合平滑输出，滑动窗口适合精确计数。

**展开**：单机用本地令牌桶；分布式用 Redis + Lua 保证原子；按租户/API Key 维度；拒绝时 429 + `Retry-After`，必要时排队但要有上限。

### Q5. 熔断和降级有什么区别？

**结论**：熔断是「不再调用」，降级是「调用失败后给替代方案」。

**展开**：熔断三态 CLOSED/OPEN/HALF_OPEN；降级如切小模型、用缓存答案、关闭非核心功能；配合舱壁隔离不同下游。

### Q6. 消息队列如何保证不丢消息？

**结论**：生产端确认 + 持久化 + 消费端手动 ACK + 重试/DLQ。

**展开**：生产者 `acks=all`；Broker 多副本；消费者处理成功才 ACK；失败重试后进死信；监控消费 lag。

### Q7. 如何保证消息顺序？

**结论**：同一业务键路由到同一分区/队列，单消费者顺序处理。

**展开**：Kafka 用 key 分区；RabbitMQ 单队列单消费者；多消费者并行会破坏顺序。代价是并行度受限，可只对需要顺序的键串行。

### Q8. 分布式 ID 怎么选？

**结论**：优先趋势递增 + 本地生成——雪花或 UUID v7；简单场景自增/号段。

**展开**：UUID v4 无序会导致 B+ 树页分裂；雪花依赖时钟与 worker id；号段依赖中心服务但性能好。按「是否需要排序、是否暴露规模、是否有中心依赖」选。

### Q9. 分布式事务有哪些方案？

**结论**：2PC、TCC、Saga、本地消息表/Outbox、事务消息。

**展开**：能单库就别分布式；跨服务优先最终一致 + 幂等 + 对账；强一致场景才考虑 TCC/2PC，并接受复杂度与阻塞。

### Q10. 设计一个 Agent 长任务执行系统，怎么保证不丢、不重、可恢复？

**结论**：Run 表状态机 + 事件表 + 租约心跳 + step 幂等键 + 事件重放。

**展开**：
1. 入队写 `queued`，worker 抢租约置 `running`；
2. 每步完成写 checkpoint 与事件；
3. 进程崩溃 → 租约过期 → 其他 worker 从 checkpoint 续跑；
4. 客户端断线 → 带 `Last-Event-ID` 重连补发；
5. 取消 → 安全点检查标志；
6. 重复执行由 step 幂等键兜底。

### Q11. 设计一个流式对话系统？

**结论**：HTTP 入口 → 会话服务 → LLM 网关（限流/重试/降级）→ SSE 输出；消息落库由异步事件完成。

**展开**：
1. SSE 用 `text/event-stream`，事件带 `id` 支持重连；
2. 首 token 延迟是关键指标，可先发 `message_start`；
3. 输出分片落库要防丢（客户端断开也要写完）；
4. 多实例用 Redis Pub/Sub 或事件表广播；
5. 代理层关闭缓冲，心跳防超时。

### Q12. 线上 504 突然增多，怎么排查？

**结论**：先分清是「入口超时」还是「下游变慢」，再定位到具体依赖。

**展开**：
1. 看错误率是否集中在某接口/某地域；
2. 看下游 P99（DB 慢查询、LLM 超时、第三方）；
3. 看连接池/线程池是否打满、FD 是否耗尽；
4. 看最近变更（发布、配置、流量活动）；
5. 临时手段：扩容、限流、熔断、回滚；
6. 复盘：补 deadline、重试预算、SLO 告警。

### Q13. SLO 怎么定？错误预算怎么用？

**结论**：按用户可感知的成功率/延迟定 SLI，设 99.9% 之类的目标，用错误预算决定发布节奏。

**展开**：99.9%/月 ≈ 43.2 分钟不可用；预算充足可以激进发布，耗尽则冻结发布、优先稳定性。SLO 要少而关键，别给每个接口都定。

### Q14. 多租户系统怎么防止「一个租户拖垮所有人」？

**结论**：隔离 + 配额 + 公平调度 + 降级。

**展开**：行级 `tenant_id` + 全局过滤（防越权）；按租户令牌桶；重任务进独立队列/独立 worker；大客户独立库或独立部署；监控按租户拆分指标。

## 15. 速记卡

- **答题框架**：澄清 → 估算 → 接口 → 数据 → 架构 → 瓶颈 → 演进。
- **CAP**：P 必选，实际选 CP 或 AP；补充 PACELC。
- **幂等四件套**：幂等键、唯一约束、状态机、去重表。
- **重试三律**：只重试幂等、指数退避 + 抖动、重试预算 + deadline。
- **限流**：令牌桶（突发）、漏桶（平滑）、滑动窗口（精确）；Redis + Lua 原子。
- **熔断三态**：CLOSED / OPEN / HALF_OPEN；降级给替代方案。
- **MQ**：至少一次 + 消费端幂等；顺序靠分区键；双写用 Outbox。
- **分布式事务**：能单库就单库；否则最终一致 + 幂等 + 对账。
- **ID**：雪花 / UUID v7；锁要配 fencing token。
- **长任务**：状态机 + 事件表 + 租约 + checkpoint + 重放。
- **可观测**：日志带 `trace_id`；看 P95/P99 不看均值；SLO 99.9% ≈ 43 分钟/月。
- **多租户**：`tenant_id` 全局过滤 + 按租户配额 + 重任务隔离。
