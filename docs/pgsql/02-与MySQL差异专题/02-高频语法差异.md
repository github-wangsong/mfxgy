## 3. ON CONFLICT：PG 的 UPSERT（首次教学）

「有就更新、没有就插入」——MySQL 用 `ON DUPLICATE KEY UPDATE`，PG 用 `ON CONFLICT`。

### 3.1 语法骨架

```sql
INSERT INTO 表 (列...) VALUES (值...)
ON CONFLICT (冲突目标) DO UPDATE SET 列 = 新值;
-- 或什么都不做：
ON CONFLICT (冲突目标) DO NOTHING;
```

- **冲突目标** = 一个唯一约束的列或列组合（如 `username`、`(a,b)`）。触发唯一冲突时才走到 `DO UPDATE/NOTHING`。
- `EXCLUDED`：指代「本想让它插入、但因冲突被挡下的那一行」，`EXCLUDED.列` 取它的值。

### 3.2 示例一：有就更新邮箱，没有就插入

```sql
INSERT INTO users (username, email)
VALUES ('alice', 'alice@newmail.com')
ON CONFLICT (username) DO UPDATE
SET email = EXCLUDED.email
RETURNING id, username, email;
```

**预期**：alice 已存在 → 触发冲突 → 把她 `email` 更新成新值，并 `RETURNING` 返回该行。

### 3.3 示例二：有就什么都不做（幂等插入）

```sql
INSERT INTO users (username, email)
VALUES ('alice', 'alice@newmail.com')
ON CONFLICT (username) DO NOTHING;
-- 若 alice 已存在：什么也不发生，不报错
```

### 3.4 与 MySQL 对照

| 维度 | MySQL | PostgreSQL |
| --- | --- | --- |
| 语法 | `INSERT ... ON DUPLICATE KEY UPDATE col = VALUES(col)` | `INSERT ... ON CONFLICT (col) DO UPDATE SET col = EXCLUDED.col` |
| 「不做任何事」 | 无非空对应（需技巧绕） | 原生 `DO NOTHING` |
| 冲突依据 | 任意唯一冲突自动触发 | **显式指定**冲突目标 |
| 取「想插的值」 | `VALUES(col)`（8.0.20 前）/ 新别名 | `EXCLUDED.col` |

> 一句话：**MySQL `ON DUPLICATE KEY` → PG `ON CONFLICT`**；用 `EXCLUDED.列` 取插入值（对应 MySQL 的 `VALUES(列)`）；要「幂等静默跳过」用 `DO NOTHING`。

## 4. RETURNING（引用阶段 0/04）

`INSERT`/`UPDATE`/`DELETE` 后直接拿回结果，已在 `00-认识PostgreSQL与环境上手/04-增删改查.md` 完整教学。这里只提醒与 MySQL 的对照：

| 需求 | MySQL | PostgreSQL |
| --- | --- | --- |
| 插入后拿自增 id | `SELECT LAST_INSERT_ID();` | `INSERT ... RETURNING id;` |
| 更新/删除后拿回行 | 需先查再改，或再查一次 | `UPDATE/DELETE ... RETURNING *;` |

> 第 3.2 节「`ON CONFLICT ... RETURNING`」正是两者结合的典型：冲突更新后一次拿回该行，MySQL 做不到这种一步到位。

## 5. ILIKE 与正则匹配（首次教学正则）

### 5.1 LIKE vs ILIKE

| 写法 | 是否区分大小写 |
| --- | --- |
| `LIKE` | **区分**大小写 |
| `ILIKE` | **不区分**大小写 |

```sql
SELECT * FROM users WHERE email LIKE '%example.com';   -- 精确大小写
SELECT * FROM users WHERE email ILIKE '%EXAMPLE.COM';   -- 忽略大小写
```

### 5.2 正则运算符（PG 独有）

| 运算符 | 含义 |
| --- | --- |
| `~` | 匹配正则（区分大小写） |
| `~*` | 匹配正则（不区分大小写） |
| `!~` | 不匹配（区分大小写） |
| `!~*` | 不匹配（不区分大小写） |

```sql
SELECT * FROM users WHERE email ~ '^[a-z]+@';   -- 正则匹配
SELECT * FROM users WHERE email ~* '^ALICE';    -- 不区分大小写
```

### 5.3 与 MySQL 对照

| 能力 | MySQL | PostgreSQL |
| --- | --- | --- |
| 模糊匹配 | `LIKE`（不区分大小写取决于 collation） | `LIKE` + `ILIKE` |
| 正则 | `REGEXP` / `RLIKE` | `~` / `~*`（`REGEXP` 是 `~` 的同义词） |

> 一句话：**MySQL 的 `REGEXP` → PG 的 `~`**；PG 多一个 `ILIKE` 和 `~*` 处理不区分大小写。

## 6. `||` 字符串拼接（首次教学）

### 6.1 PG：`||` 是拼接

```sql
SELECT 'hello' || ' ' || 'world';   -- hello world
SELECT username || '@' || email FROM users;  -- alice@alice@example.com
```

### 6.2 NULL 传染

```sql
SELECT 'a' || NULL;     -- NULL（拼接遇 NULL 全为 NULL）
SELECT concat('a', NULL);  -- 'a'（concat 忽略 NULL）
```

> 想「拼接时忽略 NULL」用 `concat()`；想「遇 NULL 变 NULL」用 `||`。按需选。

### 6.3 与 MySQL 对照（重雷）

| 写法 | MySQL | PostgreSQL |
| --- | --- | --- |
| `'a' \|\| 'b'` | **逻辑或**（非拼接，返回 0/1） | **字符串拼接**（返回 `ab`） |
| 拼接函数 | `CONCAT('a','b')` | `concat('a','b')` 或 `'a' \|\| 'b'` |

> **重雷**：`||` 在两个库里含义完全不同！MySQL 里它是逻辑 OR，PG 里是拼接。迁移时 MySQL 的拼接必须从「某种习惯」改成 `||`（PG）或 `concat()`；而 MySQL 里写 `a || b` 当逻辑或的代码，到 PG 会变成字符串拼接，语义大改。

## 7. `::` 类型转换（首次教学）

### 7.1 语法

PG 用 `值::类型` 做转换，是 `CAST(值 AS 类型)` 的简写：

```sql
SELECT '123'::integer;         -- 123（文本转整数）
SELECT 123::text;              -- '123'（整数转文本）
SELECT now()::date;            -- 今天的日期（去掉时间）
SELECT '2026-10-21'::date;     -- 字符串转日期
SELECT 100::numeric / 3;       -- 33.333...（整数转 numeric 再做精确除法）
```

### 7.2 与 MySQL 对照

| 写法 | MySQL | PostgreSQL |
| --- | --- | --- |
| 类型转换 | `CAST(x AS type)` / `CONVERT(x, type)` | `CAST(x AS type)` / `x::type`（`::` 是 PG 特色简写） |

> 一句话：**PG 的 `::` 是 `CAST` 的速记**，MySQL 没有 `::` 简写、需写全 `CAST`/`CONVERT`。

## 9. 隐式转换收紧

PG 对**类型转换非常严格**，MySQL 相对宽松（会隐式转换）。

### 9.1 数字 + 字符串

```sql
-- MySQL：SELECT '10' + 5;   → 15（隐式把字符串转数字）
-- PG：报错！operator does not exist: text + integer
SELECT '10'::integer + 5;   -- ✅ 15（显式转换后相加）
```

### 9.2 字符串与数字比较

```sql
-- PG：https 里 'abc' = 1 这类会直接报类型不匹配
-- 必须显式转换；不能像 MySQL 那样隐式把 'abc' 转成 0
```

### 9.3 对照小结

| 行为 | MySQL | PostgreSQL |
| --- | --- | --- |
| `'10' + 5` | 隐式转数字 → 15 | ❌ 报错，需 `'10'::int + 5` |
| 隐式把非法字符串转数字 | `'abc'` → 0 | ❌ 报错 |

> 结论：**PG 要求类型「显式、精确」**。这虽然写起来多打几个字，但换来的是「类型错误早暴露」，不会像 MySQL 那样把 `'abc'` 悄悄当 0 算、埋下难查的 bug。

## 10. 与 MySQL 对照总表

| 场景 | MySQL | PostgreSQL |
| --- | --- | --- |
| UPSERT | `ON DUPLICATE KEY UPDATE` | `ON CONFLICT ... DO UPDATE/NOTHING` |
| 插入/更新后取回 | `LAST_INSERT_ID()` | `RETURNING` |
| 不分大小写模糊 | `LIKE`（collation） | `ILIKE` |
| 正则 | `REGEXP` | `~` / `~*` |
| 字符串拼接 | `CONCAT()` | `\|\|` 或 `concat()` |
| `\|\|` 含义 | 逻辑或 | 拼接 |
| 类型转换 | `CAST` / `CONVERT` | `CAST` / `::` |
| GROUP BY | 可宽松 | 严格 |
| 隐式转换 | 宽松 | 严格 |

## 12. 参考答案与常见坑

**10 条翻译**：

1. `SELECT name FROM users WHERE name ILIKE '%a%';`（`LIKE` 区分大小写 → `ILIKE`）
2. `INSERT INTO users(name) VALUES('x') ON CONFLICT (name) DO UPDATE SET name = EXCLUDED.name;`
3. `SELECT 'a' || 'b';`（PG 里 `||` 是拼接，返回 `ab`；MySQL 里是逻辑或返回 0）
4. `INSERT INTO users(name) VALUES('x') RETURNING id;`（`RETURNING` 一步拿回，替代 `LAST_INSERT_ID`）
5. `SELECT * FROM users WHERE email ~ '^alice';`（`REGEXP` → `~`）
6. `SELECT created_at::date FROM users;`（或 `CAST(created_at AS date)`）
7. `SELECT 10 + '5'::integer;`（PG 不做隐式转换，需 `::int`）
8. `SELECT user_id, COUNT(*) FROM orders GROUP BY user_id;`（去掉非聚合的 `name`，或加进 GROUP BY）
9. `SELECT email FROM users WHERE email ILIKE 'alice@example.com';`（`=` 区分大小写 → `ILIKE`）
10. `UPDATE users SET name='y' WHERE id=1 RETURNING *;`（`RETURNING` 拿改后行）

**常见坑**：

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `ON DUPLICATE KEY` 在 PG 语法错 | 那是 MySQL 语法 | 用 `ON CONFLICT (列) DO UPDATE/NOTHING` |
| `'a' \|\| 'b'` 结果不是 `ab` | 在 MySQL 里 `\|\|` 是逻辑或 | PG 里才是拼接 |
| `SELECT '10' + 5` 报错 | PG 不隐式把字符串转数字 | `'10'::int + 5` |
| `LIKE` 匹配不到但明明有数据 | PG 的 `LIKE` 区分大小写 | 用 `ILIKE` |
| `REGEXP` 报语法错 | MySQL 语法 | 用 `~` 或 `~*` |
| ON CONFLICT 报 `no unique constraint` | 冲突目标不是唯一约束列 | 冲突目标必须是 UNIQUE/PK 列 |

## 13. 本篇小结

- UPSERT：`ON CONFLICT (列) DO UPDATE SET 列 = EXCLUDED.列`（或 `DO NOTHING`）；对应 MySQL `ON DUPLICATE KEY`。
- 字符串三件套：`ILIKE`（不区分大小写）、`||`（拼接，注意 MySQL 里它是逻辑或）、`::`（类型转换）。
- `~`/`~*` 正则对应 MySQL `REGEXP`。
- PG 隐式转换**严格**（需 `::` 显式转），MySQL 宽松（易埋隐式 bug）。
- `RETURNING` 与 `GROUP BY` 严格性已在阶段 0 教学，本篇只引用。
