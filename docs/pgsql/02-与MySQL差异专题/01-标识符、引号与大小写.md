## 3. 先分清两个概念：标识符 vs 字符串

这是所有引号混乱的根源，先立住：

| 概念 | 是什么 | 例子 | 用什么包 |
| --- | --- | --- | --- |
| **标识符** | 表名、列名、类型名、约束名等「对象的名字」 | `users`、`username` | 双引号 `"`（或什么都不加） |
| **字符串字面量** | 一条**数据值**（文本） | `'alice'` | **单引号** `'` |

> 一条 SQL 里常见两者并存：`SELECT "username" FROM "users" WHERE "username" = 'alice';`
> 前三个 `"..."` 是标识符（列/表名），最后的 `'alice'` 是字符串值。

---

## 4. 两条核心规则（PG）

### 4.1 规则一：双引号 = 标识符，单引号 = 字符串

- `"name"` → 被当成**标识符**（列名/表名），**不是**字符串。
- `'name'` → 被当成**字符串**（数据值）。

```sql
-- ✅ 正确：字符串值用单引号
SELECT * FROM users WHERE username = 'alice';

-- ❌ 报错：PG 把 "alice" 当成标识符（列名叫 alice），找不到
-- SELECT * FROM users WHERE username = "alice";
-- 报错：ERROR:  column "alice" does not exist
```

> 这是 MySQL 用户迁移 PG 的**头号踩坑点**（详见第 8 节）：MySQL 里双引号默认也能当字符串用，很多人 `WHERE name = "alice"` 写惯了，到 PG 这里直接炸。

### 4.2 规则二：未加引号的标识符「折叠为小写」

PG 对**不加引号**的标识符，会一律**折叠成小写**（fold to lowercase）。

```sql
CREATE TABLE Teams (id integer);     -- 没加引号：实际建的表叫 teams
\dt                                  -- 看到的是小写 teams
SELECT * FROM teams;                 -- ✅ 小写能查到
SELECT * FROM Teams;                 -- ✅ 大写也能查到（Teams 被折叠成 teams）
SELECT * FROM "Teams";               -- ❌ 报错：不存在叫 Teams 的表（双引号保留大小写）
```

关键点：

| 写法 | PostgreSQL 实际名字 | 引用时 |
| --- | --- | --- |
| `CREATE TABLE Teams ...`（不加引号） | `teams`（折叠小写） | `teams` / `Teams` / `TEAMS` 都能找到 |
| `CREATE TABLE "Teams" ...`（加双引号） | `Teams`（**保留**大小写） | **只能** `"Teams"`，且大小写要精确 |

## 5. 大小写踩坑清单

### 5.1 建了带引号的大写名，之后忘了加引号

```sql
CREATE TABLE "Users" (id integer);   -- 双引号 → 表名是 Users（大写 U）
SELECT * FROM users;                 -- ❌ 报错：users（小写）不存在
SELECT * FROM "Users";               -- ✅ 必须加双引号、且 U 大写
```

> 教训：**要么一开始就全用小写不加引号（推荐），要么从一而终加双引号**。混用必踩坑。

### 5.2 列名同理

```sql
CREATE TABLE t ("Name" text);        -- 列名 Name（保留大写）
INSERT INTO t ("Name") VALUES ('x'); -- 插入也必须 "Name"
SELECT name FROM t;                  -- ❌ 报错（折叠成 name，找不到）
SELECT "Name" FROM t;                -- ✅
```

### 5.3 推荐做法：全小写 + 下划线 + 不加引号

PG 社区惯例是：**标识符一律小写蛇形（snake_case），永不加引号**。这样：
- 不会折叠成意外的大小写；
- 引用时大小写随便写都能命中；
- 代码里 `users`、`created_at` 一眼可读。

```sql
CREATE TABLE user_profiles (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    display_name text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

## 6. 关键字、特殊字符作标识符

偶尔表名/列名撞上了 SQL **关键字**（如 `user`、`order`、`group`），或含空格/特殊字符，就必须加双引号：

```sql
CREATE TABLE "order" (id integer);       -- order 是关键字，必须加引号
CREATE TABLE "My Table" (id integer);    -- 含空格，必须加引号
```

> 但强烈不建议这样命名——埋雷。能改名字就改名字（如 `orders` 而不是 `order`）。实在要用，记得后面**每次引用都加双引号**。

## 7. 与 MySQL 对照速查

| 维度 | MySQL | PostgreSQL |
| --- | --- | --- |
| 标识符引用符 | 反引号 `` `name` `` | 双引号 `"name"` |
| 字符串引用符 | 单引号 `'...'`（双引号**默认也当字符串**） | 单引号 `'...'`，双引号**只是标识符** |
| 未加引号标识符 | 不折叠，是否区分大小写看 OS（Linux 表名区分） | **折叠为小写**，不区分大小写（除非加引号） |
| 建 `CREATE TABLE Users` 后 `SELECT * FROM users` | 可能报错（Linux 区分） | ✅ 能查到（折叠） |
| 建 `CREATE TABLE "Users"` 后 `SELECT * FROM Users` | 反引号语义，无此写法 | ❌ 报错（需 `"Users"`） |

> 一句话：**PG 是「不加引号折小写、加双引号保原样」；MySQL 是「反引号引用、大小写看平台」**。加上「双引号在 MySQL 里能当字符串、PG 里只是标识符」，这三点就是迁移时最常踩的引号坑。

---

## 8. MySQL 迁移过来的三条高频错误

| # | MySQL 惯用写法 | 到 PG 会怎样 | 正确写法 |
| --- | --- | --- | --- |
| 1 | `` WHERE name = "alice" `` | ❌ 报 `column "alice" does not exist` | `WHERE name = 'alice'` |
| 2 | `` CREATE TABLE `Users` `` | ❌ 反引号语法错误 | `CREATE TABLE "Users"`（或干脆小写不加引号） |
| 3 | 表名 `Users` 建好后直接 `SELECT * FROM Users` | ⚠️ 加引号建的表必须加引号查 | 小写建表，或始终 `"Users"` |

> 对照验收第三条：这三点能脱口说出「错在哪、怎么改」，说明本篇核心已掌握。

## 9. 验收自测

### 9.1 验证「折叠 vs 保留」

```sql
CREATE TABLE MiXeD (id integer);      -- 未加引号 → 实际表名 mixed
\dt                                   -- 看到 mixed
SELECT * FROM mixed;                  -- ✅
SELECT * FROM MiXeD;                  -- ✅（折叠）
SELECT * FROM "MiXeD";                -- ❌ 报错

CREATE TABLE "MiXeD2" (id integer);   -- 加引号 → 表名 MiXeD2（保留）
SELECT * FROM mixed2;                 -- ❌ 报错
SELECT * FROM "MiXeD2";               -- ✅
```

### 9.2 验证「双引号不当字符串」

```sql
SELECT * FROM users WHERE username = "alice";
-- ❌ 预期报错：column "alice" does not exist

SELECT * FROM users WHERE username = 'alice';
-- ✅ 正常
```

### 9.3 清理

```sql
DROP TABLE IF EXISTS mixed, "MiXeD2";
```

## 10. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `WHERE name = "alice"` 报 `column "alice" does not exist` | 双引号被当标识符 | 字符串改用单引号 `'alice'` |
| 建了 `Users` 表却查不到 | 建表时加了双引号，表名保留大写，查时未加引号被折叠 | 要么全小写，要么始终 `"Users"` |
| `CREATE TABLE \`Users\`` 报语法错 | 反引号是 MySQL 语法，PG 用双引号 | 换成 `"Users"` 或直接小写 |
| 表名撞关键字 `order`/`user` 报错 | 关键字不能裸用作标识符 | 加双引号 `"order"`，或改名为 `orders` |
| 大小写混用导致代码难以维护 | 折叠规则 + 双引号混用 | 统一 snake_case 小写、不加引号 |

---

## 11. 本篇小结

- 标识符（表/列名）用**双引号**，字符串（数据值）用**单引号**——PG 严格区分。
- 未加引号的标识符**折叠为小写**；加双引号则**保留原样**、且之后引用必须精确匹配。
- 推荐：标识符一律 snake_case 小写、不加引号，从源头规避大小写坑。
- 对照 MySQL：反引号 `` ` `` vs 双引号 `"`；双引号在 MySQL 可当字符串、在 PG 只是标识符；大小写行为 MySQL 看 OS、PG 靠折叠规则。
