## 3. 先建第二张表：外键与关系建模（首次教学 FOREIGN KEY）

到目前为止只有 `users` 一张表。真实系统里数据是**分表**的：用户一张表、订单一张表，用「外键」把订单挂到用户名下。

### 3.1 建 orders 表（带外键）

```sql
CREATE TABLE orders (
    id          integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     integer NOT NULL REFERENCES users(id),  -- 外键：指向 users.id
    amount      numeric(10, 2) NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);
```

`REFERENCES users(id)` 就是**外键约束**：`orders.user_id` 里的值，必须存在于 `users.id` 里。它保证「订单一定属于一个真实存在的用户」。

### 3.2 外键的 ON DELETE 行为

外键可指定「父行被删时，子行怎么办」：

| 写法 | 删除父行时 |
| --- | --- |
| 默认（`NO ACTION`/`RESTRICT`） | **拒绝删除**（有子行引用就不让删） |
| `ON DELETE CASCADE` | **级联删除**子行 |
| `ON DELETE SET NULL` | 子行外键列置为 `NULL` |

```sql
-- 若要「删用户时连订单一起删」，这样写：
-- user_id integer NOT NULL REFERENCES users(id) ON DELETE CASCADE
```

> 本篇用默认行为即可，不必 CASCADE。这是「关系建模 + 引用完整性」的核心：**数据库层面挡住脏引用**，比应用层自己校验可靠得多。

### 3.3 造数据

先清空两张表，再插用户和订单：

```sql
TRUNCATE users RESTART IDENTITY CASCADE;    -- CASCADE 顺带清空引用它的 orders
-- 若上面报错（旧版本），也可手动：TRUNCATE orders RESTART IDENTITY; TRUNCATE users RESTART IDENTITY;

INSERT INTO users (username, email, age) VALUES
    ('alice', 'alice@example.com', 28),
    ('bob',   'bob@example.com',   35),
    ('carol', 'carol@example.com', 22);

INSERT INTO orders (user_id, amount) VALUES
    (1, 100.00),
    (1, 50.00),
    (2, 200.00);
-- carol(id=3) 没有订单，故意留空，用于演示 LEFT JOIN 的 NULL 补位
```

> 数据约定：alice(1) 两单、bob(2) 一单、carol(3) 零单。

## 4. JOIN 的概念：笛卡尔积 + 条件

JOIN 的本质是「**两表的行两两组合**（笛卡尔积），再用 `ON 条件` 过滤掉不匹配的组合」。

```sql
SELECT *
FROM users
JOIN orders ON orders.user_id = users.id;
```

理解 JOin 三要素：

| 元素 | 作用 |
| --- | --- |
| `FROM 表A JOIN 表B` | 决定「谁和谁组合」 |
| `ON 条件` | 决定「哪些组合留下」（通常是外键 = 主键） |
| SELECT 列 | 决定「每行展示什么」 |

> 常见简写：当两表连接列**同名**时，可用 `USING (列名)` 替代 `ON a.列 = b.列`。本篇统一用 `ON` 讲清楚原理。

## 5. INNER JOIN：只保留两边都匹配的行

```sql
SELECT users.username, orders.amount
FROM users
INNER JOIN orders ON orders.user_id = users.id;
```

**预期输出**：

```
 username | amount
----------+--------
 alice    | 100.00
 alice    |  50.00
 bob      | 200.00
```

> `INNER JOIN`（可简写 `JOIN`）返回**交集的组合**：carol 没订单，不出现；没有「悬空订单」也不会出现。用户 1 有两单，就出现两行（一对多展开）。

### 5.1 JOIN + 聚合：每个用户订单总额

```sql
SELECT users.username, SUM(orders.amount) AS total
FROM users
INNER JOIN orders ON orders.user_id = users.id
GROUP BY users.username;
```

**预期输出**：

```
 username | total
----------+--------
 alice    | 150.00
 bob      | 200.00
```

> 注意「JOIN 后聚合」是高频组合拳：先把表拼起来，再 `GROUP BY`。但这样 **carol 会消失**（INNER JOIN 丢弃了没订单的人）。想保留所有人，见 LEFT JOIN。

## 6. LEFT JOIN：保留左表全部行

```sql
SELECT users.username, orders.amount
FROM users
LEFT JOIN orders ON orders.user_id = users.id
ORDER BY users.username, orders.amount;
```

**预期输出**：

```
 username | amount
----------+--------
 alice    | 100.00
 alice    |  50.00
 bob      | 200.00
 carol    |        ← 右表无匹配，amount 为 NULL
```

> `LEFT JOIN`（左连接）语义：**左表行全保留**，右表匹配不上就填 `NULL`。这是「主表 + 可选明细」场景最常用的连接。

### 6.1 用 COALESCE 把 NULL 显示为 0（首次使用）

```sql
SELECT users.username, COALESCE(SUM(orders.amount), 0) AS total
FROM users
LEFT JOIN orders ON orders.user_id = users.id
GROUP BY users.username
ORDER BY total DESC;
```

**预期输出**：

```
 username | total
----------+--------
 alice    | 150.00
 bob      | 200.00
 carol    |   0.00
```

> `COALESCE(值, 默认)`：值为 `NULL` 时返回第二个参数（这里 `0`）。因为 carol 没订单，`SUM` 结果是 `NULL`，被 `COALESCE` 补成 `0`。`COALESCE` 是通用「空值兜底」函数，本篇首次使用，后续常用。

## 7. RIGHT JOIN 与 FULL JOIN

| 连接 | 语义 | 谁可能出现 NULL |
| --- | --- | --- |
| `RIGHT JOIN` | 右表行全保留 | 左表 |
| `FULL JOIN` | **两边都全保留** | 两边 |

```sql
-- FULL JOIN：用户和订单「谁都不落下」
SELECT users.username, orders.amount
FROM users
FULL JOIN orders ON orders.user_id = users.id;
```

> `RIGHT JOIN` 实际等于「`LEFT JOIN` 换边」，用得少；真要用「保左表」就写 `LEFT JOIN` 更符合直觉。
> `FULL JOIN` 在「张榜对账、找两边差异」时有用。

### 7.1 与 MySQL 对照（重要差异）

| 连接类型 | PostgreSQL | MySQL |
| --- | --- | --- |
| `INNER JOIN` | ✅ | ✅ |
| `LEFT JOIN` / `RIGHT JOIN` | ✅ | ✅ |
| `FULL JOIN` | ✅ | ❌ **不支持**（需 `LEFT JOIN UNION RIGHT JOIN` 模拟） |

> 这是两库在 JOIN 上最主要的分歧：**PG 原生支持 FULL JOIN，MySQL 没有**。

## 8. 子查询（首次教学）

子查询 = 一条查询嵌在另一条查询里。按「返回什么」分三类。

### 8.1 标量子查询（返回单个值）

```sql
-- 找出订单金额高于「全体平均订单金额」的订单
SELECT * FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders);
```

> 括号里的内层查询返回**一个值**，外层拿它当比较条件。内层必须只返回一行一列，否则报错。

### 8.2 IN 子查询（返回一个集合）

```sql
-- 找下过单的用户
SELECT username FROM users
WHERE id IN (SELECT user_id FROM orders);
```

**预期输出**：`alice`、`bob`（carol 没下过单，不在）。

### 8.3 EXISTS 子查询（判断「是否存在」）

```sql
SELECT username FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
```

**预期输出**：同样是 `alice`、`bob`。

> `EXISTS(...)` 判断「子查询**有没有返回行**」，有就是真。这里的 `SELECT 1` 是惯例写法（不关心具体列，只关心「存在与否」）；外层表起别名 `u`、内层引 `u.id`，这叫**相关子查询**（内层引用外层）。

### 8.4 EXISTS vs IN 怎么选

| 维度 | `EXISTS` | `IN` |
| --- | --- | --- |
| 语义 | 「是否存在匹配」 | 「值是否在集合里」 |
| NULL 安全 | 天然安全 | 子查询结果若含 NULL 需留意 |
| 大数据量 | 通常更快（找到即停） | 视索引而定 |

> 经验：**判断「有没有」，优先 `EXISTS`**；写起来更直白、多数场景更高效。（性能层面的深入在阶段 6。）

## 9. 与 MySQL 对照速查

| 能力 | MySQL | PostgreSQL | 差异 |
| --- | --- | --- | --- |
| `INNER/LEFT/RIGHT JOIN` | ✅ | ✅ | 语法一致 |
| `FULL JOIN` | ❌ | ✅ | PG 独有 |
| 子查询 `IN` / `EXISTS` | ✅ | ✅ | 语法一致 |
| `COALESCE` | ✅ | ✅ | 一致（MySQL 也有；PG 更常用） |
| 外键 `ON DELETE` | ✅（InnoDB） | ✅ | 语义一致 |

### 10.2 LEFT JOIN 查「用户 + 订单总额（无订单也要出现）」

```sql
SELECT u.username, COALESCE(SUM(o.amount), 0) AS total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id

-- 预期：bob 200.00 / alice 150.00 / carol 0.00
```

### 10.3 EXISTS 子查询找「下过单的用户」

```sql
SELECT username FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
-- 预期：alice、bob
```

### 10.4 验证外键真的「挡脏引用」

```sql
INSERT INTO orders (user_id, amount) VALUES (999, 1.00);
-- 预期：报错 violates foreign key constraint "orders_user_id_fkey"（users 里没有 id=999）
```

> 这条报错证明外键在数据库层挡住了「指向不存在用户」的脏订单，第 3 节的「引用完整性」落地。

## 11. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `LEFT JOIN` 后「无订单用户」消失了 | 用了 `INNER JOIN` 或后面 `WHERE orders.xxx` 把 NULL 行又过滤掉 | 用 `LEFT JOIN`，且条件放 `ON` 里而非 `WHERE` |
| `FULL JOIN` 在 MySQL 里报语法错 | MySQL 不支持 FULL JOIN | 用 `LEFT JOIN UNION RIGHT JOIN` 模拟（PG 直接支持） |
| 标量子查询报「more than one row」 | 内层返回了多行 | 确认内层只返回一行，或改用 `IN` |
| 插入订单指向不存在的用户报错 | 外键约束生效，挡脏引用 | 先插用户，或用存在的 `user_id` |
| `SUM(amount)` 出来是 NULL | LEFT JOIN 下无匹配，聚合结果是 NULL | 用 `COALESCE(SUM(...), 0)` 兜底 |

## 12. 本篇小结

- 外键 `REFERENCES` 把两张表关联起来，保证引用完整性；`ON DELETE CASCADE/SET NULL` 控制删除行为。
- JOIN 本质 = 笛卡尔积 + `ON` 过滤；四类连接按「谁全保谁填 NULL」区分，最常用 `INNER` 与 `LEFT`。
- `FULL JOIN` 是 PG 相对 MySQL 的独有能力。
- 子查询三型：标量（单值）、`IN`（集合）、`EXISTS`（是否存在）；判断「有没有」优先 `EXISTS`。
- `COALESCE` 空值兜底，让 LEFT JOIN 的无匹配行显示为 0 而非 NULL。
