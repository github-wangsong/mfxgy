## 3. PostgreSQL 是什么

### 3.1 一句话定义

PostgreSQL 是一个**开源的对象-关系型数据库管理系统**（ORDBMS，Object-Relational Database Management System）。

拆开这三个词，就是本篇最核心的骨架：

| 关键词 | 含义 | 和 MySQL 对照 |
| --- | --- | --- |
| **数据库管理系统（DBMS）** | 负责「存储 + 检索 + 并发控制 + 崩溃恢复」数据的软件 | 同类：MySQL、SQL Server、Oracle、SQLite |
| **关系型（Relational）** | 数据组织成「表」，用 SQL 操作，强调数据完整性（约束/外键/事务） | 与 MySQL 同为关系型；对照非关系型如 MongoDB、Redis |
| **对象-关系型（OR）** | 在关系模型之上，加入了**可扩展类型系统**：能自定义类型、操作符、索引方法、函数语言（如 PL/pgSQL） | MySQL 更偏「纯关系型」，扩展能力弱一档 |

> 「对象-关系型」不是虚名，它直接长出了 PG 的杀手能力：`jsonb`、数组、`point`/`box` 几何类型、以及 pgvector 的 `vector` 类型——它们都是靠这套扩展机制「外挂」进去的。这点本系列阶段 3（JSONB）和阶段 8（pgvector）会落地。

### 3.2 定位：它与谁同类、和谁对比

在常见数据库版图里，最容易混淆的是这三者的关系，先用一句话划清：

| 数据库 | 一句话定位 | 本篇只关心 |
| --- | --- | --- |
| **PostgreSQL** | 开源对象-关系型，功能最全的「瑞士军刀」，默认持 SQL 标准最严 | ✅ 主角 |
| **MySQL** | 开源关系型，因 LAMP 时代大量网站使用而普及，InnoDB 引擎主流 | 对照对象 |
| **SQLite** | 嵌入式、零配置、单文件库，用于 App 本地/测试 | 不展开 |

> 一句话记忆：**MySQL 胜在「简单普及」，PostgreSQL 胜在「功能与正确性」**。本篇剩余部分都在论证这句话。

### 3.3 开源到什么程度：许可证与「社区」的含义

PostgreSQL 使用 **PostgreSQL License**（类 BSD / MIT 的宽松许可证）。它对使用者的约束极小：

- ✅ 可以自由使用、修改、分发，**商用免费**。
- ✅ 修改后不必开源回馈（对比 GPL）。
- ✅ 可以嵌入到闭源产品里。

因此 PG 没有「社区版 vs 商业企业版」的撕裂（MySQL/Oracle 有 Enterprise 与 Community 之分）；**只有一个版本，由全球贡献者组成的 PGDG（PostgreSQL Global Development Group）统一维护**，背后没有单一商业公司控制。

> 这也是「为什么 PG 几年时间把 MySQL 的差距追平甚至反超」的重要底层原因之一：**方向由社区工程共识决定，而非某家公司的营收压力**。

## 4. 与 MySQL 对照：进程模型（本篇最重要的一节）

> 这是 PG 与 MySQL 心智模型上**最大的、不可调和的分歧点**，务必吃透。后续很多坑（连接数管理、连接池、`work_mem` 调优）都从这儿来。

### 4.1 MySQL：单进程多线程

MySQL 的服务器是 **一个进程（`mysqld`）内开多个线程**：

- 每接受一个客户端连接，就**创建一个线程**（thread）。
- 所有线程共享同一个进程的地址空间，包括 InnoDB 的 **buffer pool**（一块大共享内存缓存）。
- 线程是操作系统里较轻量的调度单元，创建/销毁开销小。

### 4.2 PostgreSQL：多进程

PostgreSQL 的服务器是 **多个进程（process）协作**：

- 一个总管家进程 **`postmaster`**（也常叫 `postgres` 主进程）负责监听端口、接受连接。
- 每接受一个连接，`postmaster` 会 **`fork()`（复制）出一个专门的 backend 进程**来服务这条连接。
- 多个 backend 进程之间，通过**共享内存**（shared memory，存 shared buffers / WAL buffers / 锁表等）交换少量公共状态；但每个 backend 有**自己独立的私有内存**（会话级工作内存，如 `work_mem`、`temp_buffers`）。

### 4.3 对照表

| 维度 | MySQL | PostgreSQL |
| --- | --- | --- |
| 服务器进程数 | 1 个（`mysqld`） | 1 个 `postmaster` + N 个 backend 进程 |
| 每连接对应 | 1 个**线程** | 1 个**进程** |
| 连接的创建开销 | 小（线程轻量） | 大（`fork` 进程较重） |
| 共享内存 | 大块 buffer pool 全局共享 | 共享内存 + 各 backend 独立私有内存 |
| 对连接池的依赖 | 一般 | **强烈建议**（PgBouncer 等），否则连接数一多开销明显 |

### 4.4 这个差异带来什么（三条后果）

1. **高并发长连接场景，PG 要配连接池。** 因为每开一个连接就是 fork 一个进程，成百上千短连接会拖慢。所以生产里 PG 前面常挂 PgBouncer（连接池），MySQL 相对没这么敏感。

2. **`work_mem` 要按「实际并发」算总量。** 因为它是**每进程私有**，N 个进程就是 N 份内存。MySQL 的全局缓冲是「一块大家分」。这点阶段 10 运维调参会再展开，这里先记住「PG 有些内存是按连接翻倍的」。

3. **一个 backend 崩溃不会拖垮整个库。** 进程隔离性更好（线程共享内存，一个线程踩内存可能波及全进程）。这是 PG 稳定性口碑的来源之一。

## 5. 版本号规则：从「两段」到「单段」

### 5.1 规则变化

在 10 之前，PG 用**两段式**版本号：`9.6`、`9.5`、`9.4`…… 其中 `9.x` 里的 `.x` 竟跨越了多个「大版本」，非常反直觉。

从 **PostgreSQL 10（2017 年）起改成单段式**：

| 版本号 | 含义 |
| --- | --- |
| `10` / `11` / `12` … `16` / `17` / `18` | **major 版本号**，每年秋季发布一个 |
| `16.4` / `17.3` | major.minor：`17.3` 表示 major 17 的第 3 个**补丁小版本**（只含 bug/安全修复） |

**记忆口诀**：**10 之前 `9.x`，10 之后一个数；小数点是补丁，不是大版本。**

### 5.2 发布日期与支持期

- 每年 **9–10 月**发布一个新 major（如 16 于 2023-09，17 于 2024-09，18 于 2025-09）。
- 每个 major 官方支持 **5 年**（最终补丁在 5 年后收口）。
- **写作本文时（2026-10）最新 major 为 `18`**；生产保守选择通常用 `17` 或 `18` 这类已发布一阵子的版本。

> 本项目（mini-dify）的 compose 里用的是带 pgvector 的 PG 镜像，具体 major 以 `docker-compose.yml` / `.env` 为准，阶段 0「环境上手」会带你查当前版本。

## 6. 为什么选 PostgreSQL（Why PG 速览）

> 这一节是「速览 + 指路」，每一条都是后续某一阶段的完整主题。这里只给你一个可以放进面试/选型报告里的完整理由清单。

| # | 理由 | 一句话解释 | 本系列在哪展开 |
| --- | --- | --- | --- |
| 1 | **事务性 DDL** | `CREATE TABLE` 也能回滚，迁移崩溃可整体撤销；MySQL 的 DDL 隐式提交、不可回滚 | 阶段 5 |
| 2 | **MVCC（多版本并发控制）** | 读写互不阻塞、一致性快照；MySQL 也做 MVCC 但实现不同（undo log vs 多版本元组 + VACUUM） | 阶段 5 |
| 3 | **强大的类型与扩展** | 原生 `jsonb`、数组、几何类型；`CREATE EXTENSION` 挂载 pgvector/PostGIS/TimescaleDB/Citus | 阶段 3、阶段 8 |
| 4 | **可扩展索引方法** | B-tree / Hash / GIN / GiST / BRIN / SP-GiST，还能做部分索引、表达式索引 | 阶段 6 |
| 5 | **严格贴合 SQL 标准** | 语义严谨：GROUP BY 严格、类型转换严格、`DISTINCT ON`/`LATERAL`/窗口函数等标准特性齐 | 阶段 2、阶段 4 |
| 6 | **开源协议友好 + 社区单一** | BSD 类许可证、无企业版撕裂、方向由社区共识决定 | 本节 3.3 |

> 一句话结论：**要「最省事、生态伙伴最多」可以选 MySQL；要「功能最全、语义最严谨、长期扩展性最好」选 PostgreSQL**。本项目选 PG 的直接理由，正是为了用 `jsonb`（画布两态）与 pgvector（知识库检索）。

## 7. 验收自测

> 目标：在自己起的 PG 上，跑两条 SQL 证明「这是多进程 PostgreSQL」并读出版本。

前提：容器已按 tutorial 阶段 0 启动。先用下面命令确认容器名（不重讲 Docker，仅列命令）：

```powershell
docker ps   # 找 postgres 相关容器的 NAMES，例如 mini-dify-postgres-1
```

### 7.1 查版本号

**完整命令**（把 `<容器名>` 换成实际名字；在 Windows PowerShell 执行）：

```powershell
docker exec -it <容器名> psql -U postgres -c "SELECT version();"
```

**预期输出形如**（关注第一段 `PostgreSQL` 后的版本号）：

```
                                              version
---------------------------------------------------------------------------------------------------
 PostgreSQL 17.x (Debian ...) on x86_64-...
```

> 看到 `x.y` 里的 `.y` 是补丁号；major 是逗号前那个数。对照第 5 节判断它属于哪个大版本。

### 7.2 证明「每连接一个 backend 进程」

**完整命令**（连进去后执行的一条 SQL，观察 `backend_type` 列）：

```powershell
docker exec -it <容器名> psql -U postgres -c "SELECT pid, backend_type, state FROM pg_stat_activity;"
```

**预期解读**：

- 你会看到**多行**，每一行的 `pid`（进程号）都不同。
- `backend_type` 里至少有一个 `client backend`（就是你此刻这条连接对应的 backend **进程**）。
- 再开第二个 `psql` 窗口连一次、重复上面 SQL，会看到多出一个 `client backend` 行、`pid` 也变了——**每连接一个独立进程**，这就是第 4 节说的多进程模型在实例里的直接证据。

> 如果 `pg_stat_activity` 查出来的列你暂时不熟没关系，`pg_*` 系统视图会在阶段 7「体系结构」系统讲，这里只是用它的 `pid`/`backend_type` 做一次「眼见为实」。

## 8. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 连 PG 端口 `3306` 连不上 | PG 默认端口是 **5432**，3306 是 MySQL 的 | 连接串/客户端改用 `5432` |
| `psql` 里表名大写却查不到 | PG 未加引号的标识符会**折叠为小写**（见阶段 2） | 建表命名用小写或规范加双引号 |
| 大量短连接时 PG 明显变慢 | 每连接 fork 一个后端**进程**，开销比 MySQL 线程大 | 上连接池（PgBouncer），或应用层复用连接 |
| 看到 `idle in transaction` 越积越多 | PG 的多版本元组要靠 VACUUM 回收，长事务/空闲事务会阻碍它 | 应用及时提交/回滚；监控长事务（阶段 5 展开） |

## 9. 本篇小结

- PostgreSQL = **开源、社区驱动、对象-关系型**数据库；BSD 类许可证，单一版本、无企业版撕裂。
- 与 MySQL 最核心差异：**PG 多进程（postmaster + 每连接一 backend），MySQL 单进程多线程**；由此 PG 更依赖连接池、`work_mem` 按连接翻倍、进程隔离性更强。
- 版本号：**10 之前 `9.x`，10 之后单段**；写作时最新 major 18。
- Why PG 的六条理由（事务性 DDL / MVCC / 类型扩展 / 可扩展索引 / 标准严格 / 协议友好）各有专属阶段深入。
- 两条验收 SQL 已证明「读出版本号」+「每连接一进程」。
