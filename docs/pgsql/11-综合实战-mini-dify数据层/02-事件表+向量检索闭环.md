## 1. 本篇目标

- 设计一套**可回放、可审计**的运行事件存储：`runs` 表记一次运行，`events` 表记每个 SSE 事件。
- 用 `jsonb` 承载「不同事件 data 结构不同」的异构数据，并说清为什么不用多列。
- 掌握 PG **表分区**（按时间 RANGE 分区），让大表的老数据能快速归档/删除。
- 串起 pgvector 知识库的完整链路：文档上传 → 切分 → 向量化 → 入库 → 检索，以及它如何被引擎的 `retrieval` 事件消费。

**验收标准**

1. 画出 `runs` 与 `events` 的表结构，说明 `events.data` 为什么用 `jsonb`。
2. 写出 `events` 表按月 RANGE 分区的建表 + 子分区 SQL。
3. 用一条 SQL 回放某次 run 的全部事件（按 `seq` 排序）。
4. 口述知识库「写入→检索」闭环，以及检索结果如何变成引擎的 `retrieval` 事件。

## 3. 为什么要持久化事件

项目引擎（阶段 4）通过 SSE 把事件**流式**推给前端：

```
run_started → node_started → token(token) → tool_call → retrieval → node_finished → run_finished
```

问题：**SSE 断了就没了**。要支持：

- **回放**：用户重看一次运行的完整过程；
- **审计**：某次 run 调用了哪些工具、检索了哪些知识块；
- **统计**：每个节点的耗时、token 数、失败率。

所以需要把事件**持久化到数据库**。这就是「事件溯源」思路：把「发生了什么」存下来，而不是只存「最终状态」。

## 4. runs 表：一次运行一行（首次教学建模）

```sql
CREATE TABLE runs (
    id            text PRIMARY KEY,                    -- runId（应用层 uuid）
    app_id        text NOT NULL REFERENCES apps(id) ON DELETE CASCADE,
    status        text NOT NULL DEFAULT 'running',    -- running / succeeded / failed
    started_at    timestamptz NOT NULL DEFAULT now(),
    finished_at   timestamptz,
    error_message text,
    -- 冗余：运行入参快照，便于回放
    input         jsonb
);
CREATE INDEX runs_app_id_idx ON runs(app_id);
CREATE INDEX runs_status_idx ON runs(status);
```

| 设计点 | 理由 |
| --- | --- |
| `status` 用 `text` 而非 PG `ENUM` | 与项目惯例一致（Prisma 用 String），跨 ORM 对齐简单；ENUM 改值需 `ALTER TYPE` 麻烦 |
| `input jsonb` | 入参结构随应用变，jsonb 灵活 |
| `app_id` 外键 + 索引 | 按应用查 run 列表是高频查询 |

> 关于 PG `ENUM`：PG 原生支持 `CREATE TYPE run_status AS ENUM ('running','succeeded','failed')`，比 `text` + CHECK 更严格。但项目为双栈对齐选了 `text`，这是工程取舍（`11-01` §7 提过项目用通用类型降低复杂度）。

## 5. events 表：每个 SSE 事件一行 + jsonb 异构载荷（首次教学）

引擎的 `RunEvent` 有十几种，每种 `data` 结构不同（`token` 是 `{nodeId,text}`，`tool_call` 是 `{nodeId,toolName,args,round}`，`retrieval` 是 `{nodeId,knowledgeBaseId,topK,hits}`…）。给每种事件建一张表或一堆可空列都不现实——用 **`jsonb`** 存 `data`。

```sql
CREATE TABLE events (
    id         bigint GENERATED ALWAYS AS IDENTITY,
    run_id     text NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
    seq        integer NOT NULL,                       -- 事件序号，保证回放顺序
    event      text NOT NULL,                          -- 事件类型：run_started/token/...
    data       jsonb NOT NULL,                         -- 异构载荷
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (run_id, seq)
) PARTITION BY RANGE (created_at);                    -- 按时间分区（见 §6）
```

### 5.1 为什么 jsonb 是对的

| 方案 | 问题 |
| --- | --- |
| 每种事件一张表 | 十几种表，JOIN 回放极复杂 |
| 一张表 + 每字段一列 | 大量可空列，加新事件要 `ALTER TABLE` |
| **`data jsonb`** | **一行搞定，新事件不改结构；可 GIN 索引查特定字段** |

### 5.2 索引

```sql
-- 回放：按 run_id + seq
-- PRIMARY KEY (run_id, seq) 已覆盖

-- 按事件类型过滤（如统计所有 token 事件）
CREATE INDEX events_event_idx ON events(event);

-- 查 data 里的特定字段（如某 run 的 tool_call 调了哪些工具）
CREATE INDEX events_data_gin ON events USING gin (data jsonb_path_ops);
-- 查询：SELECT * FROM events WHERE run_id=? AND data @> '{"toolName":"calculator"}';
```

> `data @> '{"toolName":"calculator"}'` 用 `03-01` 的包含操作符，配合 GIN 索引（`03-02`）快速定位。

## 6. 表分区：按时间 RANGE 分区（首次教学）

`events` 表会快速膨胀（一次 run 几十上百事件，乘上 run 数）。用 PG 表分区把它按**时间切成月表**：

### 6.1 建分区表

```sql
CREATE TABLE events (
    ...
) PARTITION BY RANGE (created_at);
```

### 6.2 建子分区（每月一张）

```sql
CREATE TABLE events_2026_10 PARTITION OF events
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE TABLE events_2026_11 PARTITION OF events
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
-- ... 每月一张
```

> 子分区的列、约束、索引**自动继承**父表。查询时 PG 用**分区裁剪**（constraint_exclusion）只扫相关分区，性能不退化。

### 6.3 老数据归档

```sql
-- 把 2026-10 的分区从主表摘下来（不再参与查询，但数据还在）
ALTER TABLE events DETACH PARTITION events_2026_10;

-- 之后可 DROP 或移到冷存储
DROP TABLE events_2026_10;
```

> 这是 PG 分区表的杀手应用：**删老数据是 `DETACH` + `DROP`，秒级完成**，不用 `DELETE` 扫表（避免膨胀、避免长事务）。

### 6.4 自动创建分区

生产常用 `pg_partman` 扩展自动按月/周建分区，避免手工漏建。项目阶段若上生产可引入。

## 7. 写入：引擎事件 → 数据库

引擎每产生一个 `RunEvent`，除了推 SSE，还异步写库：

```sql
INSERT INTO events (run_id, seq, event, data)
VALUES ($1, $2, $3, $4::jsonb);
```

> 顺序保证：`seq` 由引擎递增分配，`PRIMARY KEY (run_id, seq)` 防重复。回放时 `ORDER BY seq` 即可还原事件流。
> 异步写入：写库不能阻塞 SSE 推送，通常用队列（如项目的事件队列）批量落盘。

## 8. 查询回放与统计

### 8.1 回放某次 run

```sql
SELECT seq, event, data
FROM events
WHERE run_id = $1
ORDER BY seq;
```

### 8.2 统计某 run 各节点 token 数

```sql
SELECT data->>'nodeId' AS node_id,
       sum(length(data->>'text')) AS total_chars
FROM events
WHERE run_id = $1 AND event = 'token'
GROUP BY data->>'nodeId';
```

> `data->>'nodeId'` 取 jsonb 字段（`03-01`）。GIN 索引 `events_data_gin` 加速 `data @>` 类过滤。

### 8.3 用 jsonb 包含查某工具的所有调用

```sql
SELECT run_id, seq, data
FROM events
WHERE event = 'tool_call'
  AND data @> '{"toolName":"calculator"}'
ORDER BY run_id, seq;
```

## 9. pgvector 知识库闭环（首次教学串联）

把阶段 8 的 pgvector 与引擎串起来：

### 9.1 写入侧（文档上传）

```
文档 → splitText 切分 → embedTexts 向量化 → INSERT INTO chunks(content, embedding)
```

项目代码（`kb.service.ts` upload）已实现：切分 → `embedTexts` → 事务写 `documents` + `chunks`（向量走原生 SQL）。

### 9.2 检索侧（knowledge 节点执行）

引擎的 `knowledge` 节点执行时（`knowledge.node.ts`）：

```
用户 query → embedTexts([query]) → searchChunks() 余弦 Top-K → 发 retrieval 事件
```

`searchChunks`（`kb.service.ts`）的核心 SQL（`08-02` §8.3）：

```sql
SELECT c.content, 1 - (c.embedding <=> $1::vector) AS score
FROM chunks c
WHERE c.knowledge_base_id = $2
ORDER BY c.embedding <=> $1::vector
LIMIT $3;
```

### 9.3 闭环：检索结果变成事件

检索返回的 `hits` 通过 `retrieval` 事件（`events.ts` 的 `retrieval()`）进入事件流，再写入 `events.data`：

```json
{
  "event": "retrieval",
  "data": {
    "nodeId": "kb_1",
    "knowledgeBaseId": "...",
    "topK": 4,
    "hits": [{ "content": "...", "score": 0.89, ... }]
  }
}
```

> 这样**一次运行里 knowledge 节点检索了什么**被完整记录在 `events` 表，可审计、可回放。这就是「事件表 + 向量检索」的端到端闭环。

## 10. 综合架构图（文字版）

```
用户运行应用
   │
   ▼
引擎执行图 ──SSE──▶ 前端
   │
   ├─ knowledge 节点 ──▶ pgvector chunks.embedding (cosine Top-K) ──┐
   │                                                               │
   ├─ llm 节点 ──▶ LLM API ──▶ token 事件                          │
   ├─ tool 节点 ──▶ 工具调用 ──▶ tool_call/tool_result 事件         │
   │                                                               │
   ▼                                                               ▼
events 表（run_id, seq, event, data jsonb）◀────────────────────────┘
   │
   ▼
runs 表（status, started_at, finished_at）
```

> PG 在此承担三重角色：**事件持久化**（`events` jsonb + 分区）、**知识库检索**（`chunks` pgvector）、**运行元数据**（`runs`）。这正是「PG 做单库多面手」的体现。

## 11. 与 MySQL 对照

| 能力 | PostgreSQL | MySQL |
| --- | --- | --- |
| 异构事件载荷 | `jsonb` + GIN | `JSON` + 函数索引（较弱） |
| 表分区 | 原生 `PARTITION BY RANGE` | 原生分区（语法不同） |
| 向量检索 | pgvector 内置 | 无原生（外挂） |
| 删老数据 | `DETACH PARTITION` + `DROP`（秒级） | `DROP PARTITION`（类似） |
| 事件统计 | `data->>'字段'` + GIN | `JSON_EXTRACT`（无原生 GIN） |

## 13. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 分区查询没走裁剪、扫了所有分区 | `WHERE created_at` 没加范围条件，或 `constraint_exclusion` 关了 | 查分区表必须带分区键条件；确认 `constraint_exclusion=partition` |
| 插入报「no partition of relation found for row」 | 当前时间没有对应的子分区 | 提前建子分区，或用 `pg_partman` 自动建 |
| `events` 表越来越大、查询变慢 | 没分区 / 老数据没归档 | 按时间分区 + 定期 `DETACH` 老分区 |
| jsonb 字段查询慢 | 没建 GIN 索引，或用了不支持索引的操作符 | 对 `@>`/`?` 建 GIN（`03-02`） |
| 回放事件顺序错乱 | 没按 `seq` 排序，或 seq 有重复 | `ORDER BY seq`，`PRIMARY KEY (run_id, seq)` 保证唯一 |
| 事件写入阻塞 SSE | 同步写库 | 异步批量落盘，不阻塞推送 |

## 14. 本篇小结

- **事件建模**：`runs`（运行元数据）+ `events`（每个 SSE 事件一行，`data jsonb` 存异构载荷）。
- **jsonb 的价值**：不同事件 data 结构不同，jsonb 一行承载 + GIN 可查特定字段，新事件不改表结构。
- **表分区**：`PARTITION BY RANGE (created_at)` 按月切，`DETACH PARTITION` 秒级删老数据，分区裁剪保证查询不退化。
- **pgvector 闭环**：文档→切分→向量化→`chunks` 入库→knowledge 节点余弦 Top-K→`retrieval` 事件写入 `events`。
- PG 同时承担事件持久化、向量检索、运行元数据，是「单库多面手」的综合体现。
