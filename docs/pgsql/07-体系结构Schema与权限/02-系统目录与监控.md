## 1. 本篇目标

- 知道 PG 里**两套系统视图**并存：`pg_catalog`（PG 原生、最全）与 `information_schema`（SQL 标准、只读、跨库）。
- 会用 `pg_stat_activity` 看「现在谁在跑什么」、找出 `idle in transaction`，并会用 `pg_terminate_backend` 安全地结束会话。
- 会用 `pg_locks` 联查 `pg_stat_activity` 锁定「**谁阻塞了谁**」，复现并定位一条被卡住的查询。
- 理解 `pg_settings` 怎么看参数、`SHOW`/`ALTER SYSTEM`/`postgresql.conf` 三者关系。

**验收标准**

1. 用 `information_schema.tables` 列出 `public` schema 的所有表。
2. 用 `pg_stat_activity` 看到当前会话 `pid`，并说出 `state` 的常见取值。
3. 模拟一条阻塞：A 开事务不提交 `UPDATE`，B 同行 `UPDATE` 阻塞；用 `pg_locks` 联查定位阻塞源。
4. 用 `pg_settings` 查到 `work_mem` 的值、单位、修改生效的 `context`。

## 3. 两套系统视图：pg_catalog vs information_schema（首次教学）

PG 把「表有哪些、用户是谁、权限怎样」这类**元数据**保存在一组系统目录里，并对外暴露两套查询入口：

| 维度 | `pg_catalog` | `information_schema` |
| --- | --- | --- |
| 来源 | PG 原生，**真源** | SQL 标准定义的**只读视图**，底层也查 pg_catalog |
| 完整度 | **最全**，含 PG 特有的实现细节（OID、系统列、索引类型…） | 只覆盖标准要求的部分，PG 独有信息查不到 |
| 可移植性 | PG 专有 | 跨 DB 通用（MySQL/SQL Server 也有） |
| 是否可写 | 部分系统表可（**严禁手改**，会损坏库） | 只读 |

> 选型规则：**做跨库工具/标准元数据查询 → `information_schema`**；**深度运维（OID、索引类型、扩展、活动） → `pg_catalog`**。
> 记忆：`pg_catalog.` 前缀带的表是 PG 的「后台账本」；`information_schema.` 是它的「标准对外视图」。

### 3.1 用 information_schema 看「标准元数据」

```sql
-- 列出某 schema 下的表（标准做法，跨库通用）
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public' AND table_type = 'BASE TABLE';

-- 某张表有哪些列
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'orders';

-- 库内所有 schema
SELECT schema_name FROM information_schema.schemata;
```

> 这三条在 MySQL 里**长得几乎一模一样**（MySQL 也有 `information_schema`），是两库对照学习时最容易迁移的部分。

### 3.2 直接查 pg_catalog（PG 独有）

```sql
-- 表的 OID、大小、行数（需要 oid 时只能查 pg_catalog）
SELECT relname, relkind, reltuples::bigint, pg_size_pretty(pg_relation_size(oid))
FROM pg_class
WHERE relname = 'orders';
```

| `pg_class.relkind` | 含义 |
| --- | --- |
| `r` | 普通表 |
| `i` | 索引 |
| `v` | 视图 |
| `m` | 物化视图 |
| `S` | 序列 |
| `f` | 外表 |

> `pg_class` 是最核心的系统表，所有「关系对象」（表/索引/视图/序列…）都在这里挂一条记录。多数元命令（`\d`、`\dt`、`\di`）背后都在查它。

## 4. pg_stat_activity：现在谁在跑什么（首次教学系统化）

`pg_stat_activity` 是一张**每会话一行**的统计视图，是排障的第一站（`05-02` 里用过它查 `idle in transaction`，这里把字段讲透）。

```sql
SELECT pid, usename, state, wait_event_type, wait_event, xact_start, left(query, 80) AS query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY state, xact_start;
```

### 4.1 关键字段

| 字段 | 含义 |
| --- | --- |
| `pid` | 后端进程号（= 操作系统里的 postgres 子进程 PID） |
| `usename` | 登录角色名 |
| `state` | `active`(正在跑)/`idle`(空闲)/`idle in transaction`(事务开着但不干活，危险)/`idle in transaction (aborted)`(事务报错未回滚) |
| `wait_event_type` / `wait_event` | 当前在等什么（`Lock`/`IO`/`Client`/`LWLock`…） |
| `xact_start` | 当前事务开始时间（算「开了多久」） |
| `query` | 当前或最近一条 SQL |

### 4.2 找「开了超过 5 分钟的空闲事务」

```sql
SELECT pid, xact_start, now() - xact_start AS age, left(query, 60)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND now() - xact_start > interval '5 min';
```

> 这是 PG 生产里**最高频的排查动作之一**（`05-02` 解释过它为什么阻碍 VACUUM）。

### 4.3 结束会话（首次教学）

| 函数 | 效果 |
| --- | --- |
| `pg_cancel_backend(pid)` | 取消**当前查询**，会话仍在（事务会回滚） |
| `pg_terminate_backend(pid)` | **终止整个会话**（连接断开） |

```sql
SELECT pg_terminate_backend(12345);
```

> 经验：先 `pg_cancel_backend`（温和），还不动再 `pg_terminate_backend`（断连）。普通角色只能结束**自己**的会话，结束别人需要超管或 `pg_signal_backend` 角色。

## 5. pg_locks：锁持有与等待（首次教学系统化）

`pg_locks` 反映「现在锁的状态」：每个**已持有或等待中的锁**一行。`05-02` 用它查死锁，这里给一个「阻塞链」联查套路。

### 5.1 关键字段

| 字段 | 含义 |
| --- | --- |
| `pid` | 持锁/等锁的会话 PID |
| `relation` | 被锁的对象 OID（表、索引…） |
| `mode` | 锁模式（`AccessShareLock`/`RowExclusiveLock`/`ExclusiveLock`…） |
| `granted` | `true`=已持有，`false`=正在**等待** |
| `waitstart` | 等待开始时间（仅等待的行有） |

### 5.2 经典：谁阻塞了谁（首次教学）

```sql
-- 一条联查：列出「等锁的会话」与其「阻塞它的会话」
SELECT
    w.pid          AS waiting_pid,
    w.mode         AS waiting_mode,
    w.waitstart,
    bl.pid         AS blocking_pid,
    bl.mode        AS blocking_mode,
    now() - w.waitstart AS waited_for,
    left(wq.query, 60)  AS waiting_query,
    left(blq.query, 60) AS blocking_query
FROM pg_locks w
JOIN pg_locks bl
  ON (w.locktype, w.database, w.relation, w.page, w.tuple)
   = (bl.locktype, bl.database, bl.relation, bl.page, bl.tuple)
JOIN pg_stat_activity wq  ON wq.pid  = w.pid
JOIN pg_stat_activity blq ON blq.pid = bl.pid
WHERE NOT w.granted
  AND bl.granted
ORDER BY w.waitstart;
```

> 核心思路：**`granted=false` 的行 = 等锁者**，用（locktype/relation/page/tuple）去匹配 `granted=true` 的行 = 持锁者。这是 PG 排「查询卡住」的标准脚本，背下来。

### 5.3 看某张表当前有哪些锁

```sql
SELECT pid, mode, granted
FROM pg_locks
WHERE relation = 'orders'::regclass
ORDER BY granted DESC, pid;
```

> `'orders'::regclass` 是把表名转成 OID 的 PG 惯用写法，比自己去 `pg_class` 找 OID 方便。

## 6. pg_settings：运行参数与怎么改（首次教学）

`pg_settings` 暴露了 PG 的**全部配置参数**，等价于 `SHOW ALL`，但可筛选。

```sql
-- 查 work_mem 的值、单位、和「改动怎么生效」
SELECT name, setting, unit, context, short_desc
FROM pg_settings
WHERE name = 'work_mem';
```

### 6.1 关键字段

| 字段 | 含义 |
| --- | --- |
| `name` | 参数名 |
| `setting` | 当前值（文本） |
| `unit` | 单位（`kB`/`MB`/`ms`…），部分参数有 |
| `context` | 决定**改动何时生效**（见下表） |
| `short_desc` | 一句话说明 |

### 6.2 context：决定改动生效方式（首次教学）

| `context` | 怎么改才生效 |
| --- | --- |
| `internal` | 只读，编译/初始化时定 |
| `postmaster` | 改 `postgresql.conf` 后**重启服务**才生效 |
| `sighup` | 改配置后 `pg_ctl reload` / `ALTER SYSTEM` + 重载即可（**不用重启**） |
| `superuser` / `user` | 当前会话可 `SET` 改（用户级改完仅本会话生效） |

```sql
-- SHOW / SET（会话级）
SHOW work_mem;
SET work_mem = '64MB';            -- 只对当前会话有效

-- ALTER SYSTEM（写入 postgresql.auto.conf，需 reload/重启看 context）
ALTER SYSTEM SET work_mem = '64MB';
SELECT pg_reload_conf();          -- 让 sighup 级参数立即生效
```

> 三层改法的记忆：**`SET` = 当前会话**、**`ALTER SYSTEM` = 写配置文件 + 按 context 生效**、**直接改 `postgresql.conf` = 手动编辑**。生产推荐用 `ALTER SYSTEM`（可追踪、不手改文件）。
> 对照 MySQL：MySQL 用 `SET GLOBAL`/`SET PERSIST`，重启持久化靠 `mysqld-auto.cnf`；PG 用 `ALTER SYSTEM`（写入 `postgresql.auto.conf`），思路几乎一一对应。

## 7. 常用 pg_stat_* 统计视图（首次教学）

PG 还有一批 `pg_stat_*` 视图统计运行数据，运维高频的有：

| 视图 | 看什么 | 关键字段 |
| --- | --- | --- |
| `pg_stat_database` | 库级汇总（事务数、提交数、死锁数、缓存命中） | `xact_commit`/`xact_rollback`/`deadlocks`/`blk_read_time` |
| `pg_stat_user_tables` | 用户表的扫描/统计 | `seq_scan`/`idx_scan`/`n_live_tup`/`n_dead_tup`/`last_vacuum` |
| `pg_stat_user_indexes` | 索引使用情况 | `idx_scan`/`idx_tup_read`/`idx_tup_fetch` |
| `pg_stat_statements` | **Top-N 慢 SQL**（需扩展，见 `08-01`） | `query`/`calls`/`total_exec_time`/`mean_exec_time` |

### 7.1 看某表「死元组比例」（决定要不要 VACUUM）

```sql
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup::numeric / NULLIF(n_live_tup + n_dead_tup, 0) * 100, 2) AS dead_pct,
       last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

> `n_dead_tup`（死元组）持续高且 `last_autovacuum` 久远，就该手动 `VACUUM` 或查 autovacuum 配置（`05-02` 教过 VACUUM）。

### 7.2 看「某个索引是不是没用」

```sql
SELECT indexrelname, idx_scan, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE relname = 'orders';
```

> `idx_scan` 长期为 0 的索引 = 写时维护却没人用，是删除候选（删前用 `06-02` 的 `EXPLAIN` 再确认一次）。

## 8. 与 MySQL 系统表对照速查

| 目标 | PostgreSQL | MySQL |
| --- | --- | --- |
| 标准元数据 | `information_schema.*` | `information_schema.*`（基本通用） |
| 活动会话 | `pg_stat_activity` | `information_schema.processlist` / `SHOW PROCESSLIST` |
| 锁/等待 | `pg_locks` + `pg_stat_activity` | `performance_schema.data_locks` / `sys.innodb_lock_waits` |
| 运行参数 | `pg_settings` / `SHOW ALL` | `SHOW VARIABLES` |
| 表统计（行数/死元组） | `pg_stat_user_tables` | `information_schema.tables.TABLE_ROWS`（不准）/ `innodb_table_stats` |
| Top-N 慢 SQL | `pg_stat_statements`（扩展） | `performance_schema` / `sys.statement_analysis` |

## 9. 验收自测

### 9.1 information_schema 列表

```sql
SELECT table_name FROM information_schema.tables
WHERE table_schema = 'public';
```

### 9.2 pg_stat_activity 看自己

```sql
SELECT pid, state, wait_event_type, left(query, 40)
FROM pg_stat_activity WHERE pid = pg_backend_pid();
-- 预期：pid 是你当前会话的号，state 为 active
```

### 9.3 复现阻塞并定位阻塞源

```sql
-- 会话 A：开事务改一行，不提交
BEGIN;
UPDATE orders SET amount = 99 WHERE id = 1;
-- （不 COMMIT 不 ROLLBACK）

-- 会话 B：改同一行，会被卡住
BEGIN;
UPDATE orders SET amount = 88 WHERE id = 1;
-- （B 卡住）

-- 会话 C（新终端）：跑第 5.2 节的联查脚本，应看到 waiting_pid=B、blocking_pid=A
SELECT w.pid AS waiting, bl.pid AS blocking
FROM pg_locks w
JOIN pg_locks bl
  ON (w.locktype, w.database, w.relation, w.page, w.tuple)
   = (bl.locktype, bl.database, bl.relation, bl.page, bl.tuple)
WHERE NOT w.granted AND bl.granted;

-- 清理：A 端 ROLLBACK，B 端的 UPDATE 会自动继续或报错，各自 ROLLBACK
```

### 9.4 pg_settings 查 work_mem

```sql
SELECT name, setting, unit, context FROM pg_settings WHERE name = 'work_mem';
-- 说出 setting 的值与单位，以及 context 决定怎么改
```

## 10. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 普通用户查 `pg_stat_activity` 只看到自己 | 缺 `pg_read_all_stats` 角色 / 权限 | 授角色：`GRANT pg_read_all_stats TO 角色`（PG 10+） |
| `pg_locks` 找不到表名 | `relation` 字段存的是 OID | 用 `'表名'::regclass` 或联 `pg_class` 转 |
| `ALTER SYSTEM` 改完没生效 | 参数 `context` 是 `postmaster` | 需要**重启**服务，不是 reload |
| 直接改 `pg_catalog` 把库改坏了 | 系统表是元数据真源，禁止手改 | 用 `ALTER`/`GRANT`/`DROP` 等 DDL，别 `UPDATE pg_class` |
| `pg_stat_user_tables.n_live_tup` 与实际不符 | 统计信息未刷新 | `ANALYZE` 表（`06-02`） |
| 锁排查找不到阻塞源 | 只用了 `pg_locks` 没联活动会话 | 用第 5.2 节的联查脚本把 SQL 也带出来 |

## 11. 本篇小结

- 两套系统视图并存：**`pg_catalog`（PG 原生、最全）** vs **`information_schema`（SQL 标准、只读、跨库通用）**；标准查询用后者，深度运维用前者。
- `pg_stat_activity` 看会话：`pid`/`state`/`query`/`xact_start`；`idle in transaction` 是 VACUUM 大敌；`pg_cancel_backend`/`pg_terminate_backend` 温和到粗暴两级结束会话。
- `pg_locks` 看锁：`granted` 区分持有者/等待者；联 `pg_stat_activity` 按 `(relation, page, tuple)` 配出「谁阻塞了谁」。
- `pg_settings` 看参数：`context` 决定改动是「会话级 / 重载 / 重启」；`ALTER SYSTEM` 是改配置的推荐方式。
- `pg_stat_*` 运维视图：`pg_stat_user_tables` 看死元组比例、`pg_stat_user_indexes` 找无用索引。
