# 01 · 逻辑备份与恢复

> 所属：阶段 10 · 备份、复制与运维（选修）
> 本篇覆盖：`pg_dump`（单库逻辑备份、四种输出格式）、`pg_restore`（恢复、并行、clean/create）、`pg_dumpall`（全实例与全局对象）、恢复演练流程、与 MySQL `mysqldump` 对照

## 1. 本篇目标

- 掌握 PG 逻辑备份三件套：`pg_dump`（单库）、`pg_restore`（恢复）、`pg_dumpall`（全实例/全局对象）。
- 理解四种输出格式的区别，知道**生产用 `custom` 或 `directory`** 的理由。
- 能独立完成一次「**备份 → 建新库 → 恢复 → 验证**」的恢复演练。
- 清楚 PG 逻辑备份为何不阻塞读写（与 MySQL 对照）。

**验收标准**

1. 用 `pg_dump -Fc` 备份 `pg_tutorial` 到一个文件。
2. 用 `pg_restore` 恢复到一个**新库** `pg_tutorial_bak`，验证表与数据齐全。
3. 用 `pg_dumpall --globals-only` 导出全局角色。
4. 说出 PG 逻辑备份不锁表的原理。

## 3. 为什么备份：先立住分类

PG 的备份分两大类：

| 类别 | 工具 | 用途 |
| --- | --- | --- |
| **逻辑备份**（本篇） | `pg_dump` / `pg_restore` / `pg_dumpall` | 导出 SQL/对象，可跨 PG 大版本恢复、可单表恢复、可人类可读 |
| **物理备份**（下一篇） | `pg_basebackup` + WAL | 二进制整库复制，用于 PITR（时间点恢复）和搭建从库 |

> 一句话：**逻辑备份 = 「把数据和结构导出来」**，灵活但慢、且是某一时刻的快照；**物理备份 = 「拷数据文件 + 日志」**，能精确恢复到任意时间点。生产通常**两者都做**（逻辑做日常、物理做灾难恢复）。

## 4. pg_dump：单库逻辑备份（首次教学）

### 4.1 最简单的备份

```bash
# 进容器（项目 PG 容器名通常是 postgres 或 mini-dify-postgres）
docker exec -it <pg容器> bash

# 把 pg_tutorial 库备份成 custom 格式文件
pg_dump -U postgres -Fc -f /tmp/pg_tutorial.dump pg_tutorial
```

| 参数 | 作用 |
| --- | --- |
| `-U postgres` | 连接用户名 |
| `-Fc` | 输出 **custom** 格式（二进制压缩，推荐） |
| `-f /tmp/pg_tutorial.dump` | 输出文件 |
| 最后的 `pg_tutorial` | 要备份的库名 |

### 4.2 四种输出格式（首次教学）

| 格式 | 参数 | 特点 | 适用 |
| --- | --- | --- | --- |
| `plain`（默认） | `-Fp` | 纯 SQL 脚本，可用 `psql -f` 恢复 | 小库、要人工查看/编辑 SQL |
| **`custom`** | **`-Fc`** | 二进制压缩，可恢复单个对象（`pg_restore`） | **生产首选**，体积小、灵活 |
| `directory` | `-Fd` | 每个表一个文件，**可并行备份** | 大库、追求速度 |
| `tar` | `-Ft` | tar 包（注意单文件 ≤ 8GB 限制） | 几乎不用 |

> 关键：只有 `custom`/`directory`/`tar` 能用 `pg_restore` 的「**只恢复某张表**」「**并行恢复**」等高级功能；`plain` 只能整库 `psql -f` 跑 SQL。生产一律 `-Fc`。

### 4.3 常用参数

```bash
# 只备份 public schema
pg_dump -U postgres -Fc -n public -f /tmp/public.dump pg_tutorial

# 只备份 orders 表（含结构+数据）
pg_dump -U postgres -Fc -t orders -f /tmp/orders.dump pg_tutorial

# 只导出结构（不要数据）
pg_dump -U postgres -Fc --schema-only -f /tmp/schema.dump pg_tutorial

# 只导出数据（不要建表语句）
pg_dump -U postgres -Fc --data-only -f /tmp/data.dump pg_tutorial

# directory 格式 + 4 并行备份（大库加速）
pg_dump -U postgres -Fd -j 4 -f /tmp/pg_tutorial_dir pg_tutorial

# 压缩级别 0-9（custom 默认已压缩）
pg_dump -U postgres -Fc -Z 9 -f /tmp/small.dump pg_tutorial
```

### 4.4 PG 逻辑备份不阻塞读写（核心差异）

`pg_dump` 启动时**开启一个事务、取一个一致性快照**，然后读这个快照下的数据。因此：

- 备份期间，**其他会话的写入不被阻塞**；
- 备份出来的是「备份开始时刻」的一致状态（不是备份结束时刻）；
- 长事务会拖慢备份，因为 MVCC 要保留旧版本（呼应 `05-02` 的长事务/VACUUM 问题）。

> 对照 MySQL：`mysqldump` 默认对 InnoDB 表会加锁或用 `--single-transaction`（基于一致性读）才能不锁表；PG 的 `pg_dump` **天然就是一致性快照、默认不锁表**，这是 PG 备份的一大省心之处。

## 5. pg_restore：恢复（首次教学）

`pg_restore` 只用于恢复 `custom`/`directory`/`tar` 格式（`plain` 用 `psql -f`）。

### 5.1 恢复到新库（推荐演练方式）

```bash
# 1. 先建一个空库（pg_restore 不会自动建库，除非加 -C）
psql -U postgres -c "CREATE DATABASE pg_tutorial_bak;"

# 2. 恢复（custom 文件 → 新库）
pg_restore -U postgres -d pg_tutorial_bak /tmp/pg_tutorial.dump
```

### 5.2 常用参数

| 参数 | 作用 |
| --- | --- |
| `-d 库名` | 恢复到哪个库 |
| `-C` | 自动 `CREATE DATABASE`（**先连到一个已有库如 postgres**，由它来建目标库） |
| `-c`（clean） | 恢复前先删除已存在的对象（避免重复键） |
| `--if-exists` | 配合 `-c`，对象不存在时不报错 |
| `-j N` | 并行恢复（对 directory 格式最有效） |
| `-t 表名` | 只恢复指定表 |
| `--schema-only` / `--data-only` | 只恢复结构 / 只恢复数据 |
| `-v` | 打印详细日志 |

```bash
# 恢复时先清理已有对象，再恢复
pg_restore -U postgres -d pg_tutorial_bak -c --if-exists /tmp/pg_tutorial.dump

# 让 pg_restore 自己建库（-C 时 -d 指「连接哪个库来执行 CREATE DATABASE」）
pg_restore -U postgres -d postgres -C /tmp/pg_tutorial.dump

# 并行恢复（directory 格式）
pg_restore -U postgres -d pg_tutorial_bak -j 4 /tmp/pg_tutorial_dir
```

### 5.3 只看备份里有什么（不实际恢复）

```bash
pg_restore -l /tmp/pg_tutorial.dump
# 列出备份内的所有对象（表/索引/函数…），可用列表文件做「选择性恢复」
```

## 6. pg_dumpall：全实例与全局对象（首次教学）

`pg_dump` 一次只备份**一个库**，且**不备份全局对象**（角色 `ROLE`、表空间、`CREATE DATABASE` 语句）。要备份整个实例或全局对象，用 `pg_dumpall`。

```bash
# 备份所有库 + 全局对象（输出纯 SQL）
pg_dumpall -U postgres -f /tmp/all.sql

# 只备份全局对象（角色、表空间）—— 生产常单独做这个
pg_dumpall -U postgres --globals-only -f /tmp/globals.sql

# 只备份角色
pg_dumpall -U postgres --roles-only -f /tmp/roles.sql
```

> 生产惯例：**每个库用 `pg_dump -Fc` 单独备份，全局对象用 `pg_dumpall --globals-only` 单独备份**。这样恢复某个库不影响全局，也避免 `pg_dumpall` 一个超大 SQL 文件难处理。
> 恢复：`psql -U postgres -f /tmp/globals.sql`（`pg_dumpall` 输出是 plain SQL，直接 `psql -f`）。

## 7. 完整恢复演练（验收核心）

这是生产必备技能：**备份了不代表能恢复，必须定期演练**。

```bash
# ① 备份（custom 格式）
pg_dump -U postgres -Fc -f /tmp/pg_tutorial.dump pg_tutorial

# ② 备份全局对象（角色等）
pg_dumpall -U postgres --globals-only -f /tmp/globals.sql

# ③ 建一个空库
psql -U postgres -c "DROP DATABASE IF EXISTS pg_tutorial_bak;"
psql -U postgres -c "CREATE DATABASE pg_tutorial_bak;"

# ④ 先恢复全局对象（让角色存在）
psql -U postgres -d pg_tutorial_bak -f /tmp/globals.sql   # 全局对象通常恢复到 postgres 库更合适

# ⑤ 恢复库数据
pg_restore -U postgres -d pg_tutorial_bak /tmp/pg_tutorial.dump

# ⑥ 验证：表数量、行数、抽查数据
psql -U postgres -d pg_tutorial_bak -c "\dt"
psql -U postgres -d pg_tutorial_bak -c "SELECT count(*) FROM orders;"
psql -U postgres -d pg_tutorial_bak -c "SELECT * FROM orders LIMIT 3;"
```

> 验证要点：**表都在、行数对、抽查几条数据一致**。只有演练通过，备份才算数。

## 8. 与 MySQL 对照速查

| 能力 | PostgreSQL | MySQL |
| --- | --- | --- |
| 单库备份 | `pg_dump -Fc` | `mysqldump` |
| 恢复 | `pg_restore`（custom）/ `psql -f`（plain） | `mysql < 备份.sql` |
| 全实例备份 | `pg_dumpall` | `mysqldump --all-databases` |
| 全局对象（用户） | `pg_dumpall --globals-only` | `mysqldump --all-databases --no-data` 或 `mysql.user` 表 |
| 一致性 | **默认快照，不锁表** | 需 `--single-transaction`（InnoDB）才不锁 |
| 选择性恢复 | `pg_restore -t 表` / `-n schema` | 需从 SQL 里截取（无内建单表恢复） |
| 并行备份 | `pg_dump -Fd -j N` | 无内建并行 |
| 压缩 | `-Fc` 内置压缩 / `-Z` | 需 `gzip` 管道 |

> PG 的 `pg_dump`/`pg_restore` 能力比 `mysqldump` 更完善（格式多、选择性恢复、并行、压缩内置）；MySQL 常用 `mydumper`/`myloader` 第三方工具补这些能力。

## 9. 项目关联：mini-dify 的备份

项目数据在 Docker 卷里，备份策略建议：

- **开发期**：`pg_dump -Fc` 定期导出，方便迁移/分享；
- **生产期**：① 逻辑备份 `pg_dump`（日常）+ ② 物理备份 `pg_basebackup` + WAL 归档（灾难恢复，见 `10-02`）；
- 全局对象（角色）用 `pg_dumpall --globals-only` 单独备份一次。

> 项目当前用 Prisma 迁移建表，逻辑备份也能跨环境恢复结构（Prisma migration 与 `pg_dump` 二选一，生产推荐 `pg_dump` 还原更稳）。

pg_dump -U postgres -Fc -f /tmp/pg_tutorial.dump pg_tutorial

psql -U postgres -c "CREATE DATABASE pg_tutorial_bak;"

### 10.3 全局对象备份

```bash
pg_dumpall -U postgres --globals-only -f /tmp/globals.sql
head -20 /tmp/globals.sql
```

### 10.4 选择性恢复（只恢复一张表到新库）

```bash
psql -U postgres -c "CREATE DATABASE orders_only;"
pg_restore -U postgres -d orders_only -t orders /tmp/pg_tutorial.dump
psql -U postgres -d orders_only -c "\dt"   -- 应只有 orders
```

## 11. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `pg_restore` 报「role does not exist」 | 备份里的对象属主是某角色，但目标库没这个角色 | 先 `pg_dumpall --globals-only` 恢复角色，或 `pg_restore --no-owner` |
| `pg_restore` 报「relation already exists」 | 目标库已有同名对象 | 加 `-c --if-exists` 先删再恢复 |
| 恢复后数据缺失 / 外键报错 | plain 格式恢复顺序不对，或并行恢复时依赖未满足 | 用 custom 格式；必要时去掉 `-j` 串行恢复 |
| `pg_dumpall` 文件巨大难恢复 | 把所有库塞进一个 SQL | 按库 `pg_dump` + 单独 `--globals-only` |
| 备份期间数据库变慢 | 长事务 + 大量写入导致 MVCC 旧版本膨胀 | 避免在大事务/批处理期间跑大库备份 |
| 跨大版本恢复失败 | 旧 PG 备份到新 PG 可能有语法/类型差异 | 先在同版本恢复，再用 `pg_upgrade` 升版本 |

## 12. 本篇小结

- 逻辑备份三件套：`pg_dump`（单库）+ `pg_restore`（恢复 custom/directory）+ `pg_dumpall`（全实例/全局对象）。
- 输出格式：**生产用 `-Fc`（custom）**，大库用 `-Fd -j N`（directory 并行）；`plain` 给小库/人工看。
- `pg_restore`：`-C` 建库、`-c --if-exists` 先清、`-j N` 并行、`-t` 单表。
- PG 逻辑备份**基于一致性快照、默认不锁表**，是相对 MySQL `mysqldump` 的省心点。
- 全局对象（角色）必须用 `pg_dumpall --globals-only` 单独备份；恢复演练比备份本身更重要。
