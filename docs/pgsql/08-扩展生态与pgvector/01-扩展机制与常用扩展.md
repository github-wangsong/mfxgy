- 理解 PG 的**扩展 = 把一批类型/函数/运算符「装」进库里**的机制，能列出「能装什么」和「已装了什么」。

## 3. 扩展机制：把功能「装」进库（首次教学）

### 3.1 扩展是什么

扩展是一组**打包好的 SQL 对象（类型/函数/运算符/视图）**，通过 `CREATE EXTENSION` 一次性导入当前库。本质上它会执行扩展自带的 `.sql` 脚本（创建函数、类型等），并在 `pg_extension` 里登记。

> 关键：**扩展是「库级」的**——同一个 PG 实例里，每个库要**各自 `CREATE EXTENSION`** 才能用；`template1` 装上后新建的库会自动继承。

### 3.2 看「能装什么」与「装了什么」

```sql
-- 已启用的扩展（含版本、schema）
SELECT * FROM pg_extension;

-- 实例里所有可装的扩展（名称/版本/描述）
SELECT name, default_version, installed_version, comment
FROM pg_available_extensions
ORDER BY name;
```

| 字段 | 含义 |
| --- | --- |
| `name` | 扩展名 |
| `default_version` | 默认版本 |
| `installed_version` | 已装版本（没装为 NULL） |
| `comment` | 一句话描述 |

### 3.3 扩展文件从哪来

扩展的脚本（`*.control`、`*.sql`）放在 PG 的 **`sharedir/extension`** 目录：

```bash
pg_config --sharedir/extension
# 示例：/usr/share/postgresql/16/extension
```

> 镜像里打包哪些扩展决定了 `pg_available_extensions` 能看到什么。本项目 mini-dify 用的是 **pgvector 官方镜像**，所以里面有 `pgvector`（下一篇用），其他常用扩展多数也已内置。

### 3.4 装、卸、升级

```sql
-- 装（若扩展脚本不在 sharedir/extension，会报「could not open extension control file」）
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- 卸
DROP EXTENSION IF EXISTS pgcrypto;

-- 升级到新版本（PG 大版本升级时常用）
ALTER EXTENSION pgcrypto UPDATE;
```

> `CREATE EXTENSION` 在阶段 `00-02` 已教过基本语法，这里补「**IF NOT EXISTS**」（幂等，避免重复装报错）与「**升级**」。

### 3.5 默认启用的扩展：plpgsql

`pg_extension` 里默认就有一个 **`plpgsql`**——PL/pgSQL 过程语言。所有 `CREATE FUNCTION ... LANGUAGE plpgsql` 都靠它（项目里 `apps_set_updated_at()` 触发器函数就是 plpgsql，见阶段 5）。它**出厂即装、不能卸载**。

> 对照 MySQL：MySQL 没有「扩展」概念，功能靠**内置函数 / UDF / 存储引擎插件**实现（FULLTEXT、GIS 是引擎内建）。PG 的扩展机制更像「装包」，生态（pgvector、PostGIS、pg_stat_statements…）也因此更发达。

## 4. pgcrypto：UUID 与密码哈希（首次教学）

`pgcrypto` 提供加密相关函数，最常用两个：**生成 UUID** 与 **密码哈希**。

### 4.1 生成 UUID

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- 随机 UUID v4
SELECT gen_random_uuid();
```

> 关于版本的坑：**PG 13 起，`gen_random_uuid()` 已内置（不需装 pgcrypto）**；PG 13 之前必须靠 `pgcrypto`。项目 `schema.prisma` 里的 `@default(uuid())` 最终就是数据库端用 `gen_random_uuid()` 生成（Prisma 会自动选内置或 pgcrypto）。所以**新库直接用内置的就行**，装 `pgcrypto` 是为了它的加密函数。
> 若要 v1/v3/v5（带时间戳/基于名字），用 `uuid-ossp` 扩展的 `uuid_generate_v1()` 等。

### 4.2 密码哈希：crypt()

```sql
-- 注册时：生成加盐哈希（gen_salt 生成随机盐 + 算法标识）
-- crypt() 会把盐和算法编码进结果字符串，所以不用单独存盐
INSERT INTO users (email, password_hash)
VALUES ('alice@example.com', crypt('my-secret', gen_salt('bf')));   -- bf = bcrypt
```

```sql
-- 登录时：用同样的 crypt() 比较（哈希里自带盐，PG 会解析）
SELECT email
FROM users
WHERE email = 'alice@example.com'
  AND password_hash = crypt('my-secret', password_hash);
```

> 关键心智模型：`crypt(明文, 已存哈希)` 会从「已存哈希」里**自动提取盐和算法**再算一次，对比即可。这正是 bcrypt 的标准用法——**盐不用单独存**。
> `gen_salt('bf')` = bcrypt；`'md5'`/`'xdes'`/`'des'` 是更老的算法，**新项目一律用 `bf`**。
> 对照 MySQL：MySQL 有 `PASSWORD()`（8.0 已弃）、`SHA2()`，但**没有内置的 bcrypt**，密码哈希通常在应用层（如 Node 的 `bcryptjs`、Python 的 `passlib`）做。PG 用 `pgcrypto` 可以在数据库层完成，适合「密码不能离开 DB」的合规场景。

## 5. citext：大小写不敏感的文本类型（首次教学）

`citext`（case-insensitive text）是一种**类型级**的大小写不敏感文本。之前用 `ILIKE`（`02-02`）是「操作符级」的不敏感；`citext` 是「列级」的不敏感，所有比较（`=`、`LIKE`、唯一约束）都自动忽略大小写。

```sql
CREATE EXTENSION IF NOT EXISTS citext;

CREATE TABLE members (
    id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email citext NOT NULL UNIQUE      -- 邮箱大小写不敏感且唯一
);

INSERT INTO members (email) VALUES ('Alice@Example.COM');
```

```sql
-- 用任何大小写都能查到
SELECT * FROM members WHERE email = 'alice@example.com';   -- ✅ 命中
SELECT * FROM members WHERE email = 'ALICE@EXAMPLE.COM';   -- ✅ 命中

-- 唯一约束也是大小写不敏感的：
INSERT INTO members (email) VALUES ('aLiCe@example.com');  -- ❌ 唯一冲突
```

> 适用场景：**邮箱、用户名**这类「语义上大小写无所谓」的字段。用 `citext` 比「存时统一 `lower()` + 查时 `lower()`」更省心，也避免表达式索引的维护负担。
> 对照 MySQL：MySQL 默认排序规则 `*_ci`（如 `utf8mb4_general_ci`）本身就是大小写不敏感，所以 `text` 默认就像 PG 的 `citext`；PG 默认 `text` 是**区分大小写**的，需 `ILIKE` 或 `citext`。这是两库文本语义的又一差异。

## 6. pg_stat_statements：Top-N 慢 SQL（首次教学）

`pg_stat_statements` 是**找慢 SQL 的首选工具**，会记录每条 SQL 语句的累计执行时间、调用次数、平均耗时等。它的特殊之处：**必须先在 `shared_preload_libraries` 里加载**，重启后才能用。

### 6.1 启用（配置 + 重启）

```ini
# postgresql.conf
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.track = all      # top / all / none
```

```sql
-- 装扩展（重启后）
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

> 注意：改 `shared_preload_libraries` 后必须**重启 PG**（`context=postmaster`，见 `07-02`）。这是少数不能 `reload` 生效的参数之一。

### 6.2 查 Top-5 慢 SQL

```sql
SELECT
    round(total_exec_time::numeric, 2)        AS total_ms,
    calls,
    round(mean_exec_time::numeric, 2)         AS mean_ms,
    round(total_exec_time / NULLIF(sum(total_exec_time) OVER (), 0) * 100, 2) AS pct,
    left(query, 100)                          AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 5;
```

| 字段 | 含义 |
| --- | --- |
| `total_exec_time` | 该 SQL 累计执行时间（ms） |
| `calls` | 调用次数 |
| `mean_exec_time` | 平均每次耗时 |
| `rows` | 累计返回行数 |
| `query` | SQL 文本（参数已参数化归一） |

> 经验：先按 `total_exec_time` 排（总耗时最多），再看 `mean_exec_time`（单次慢）。**总耗时高的才是真正影响系统的**，哪怕每次只慢一点点。
> 对照 MySQL：MySQL 靠 **慢查询日志**（`slow_query_log` + `long_query_time`）+ `pt-query-digest`，或 8.0+ 的 `sys.schema_statement_analysis`。PG 的 `pg_stat_statements` 是**内存实时统计**，更方便但会占共享内存。

### 6.3 重置统计

```sql
SELECT pg_stat_statements_reset();   -- 清空累计，重新计时
```

## 7. pg_trgm：模糊匹配的「真解」（首次教学）

`06-02` 说过 `LIKE '%abc%'` B-tree 走不了。`pg_trgm` 用**三元组（trigram）**把字符串切成 3 字符片段，建 GIN/GiST 索引，就能加速任意位置的模糊匹配。

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_users_email_trgm ON users USING gin (email gin_trgm_ops);

SELECT * FROM users WHERE email LIKE '%alice%';   -- 现在能命中 GIN 索引
```

| 操作符类 | 索引类型 | 用途 |
| --- | --- | --- |
| `gin_trgm_ops` | GIN | 模糊匹配 / 相似度（推荐默认） |
| `gist_trgm_ops` | GiST | 相似度排序（`ORDER BY 相似度` 时更优） |

> `%` 是 trigram 的「相似度」操作符，可用于「找相似字符串」。中文要先做分词或用 `zhparser`（阶段 9）。

## 8. pgstattuple：检查表膨胀（首次教学）

`05-02` 讲过 VACUUM 与死元组；`pgstattuple` 给你一个**精确的死元组比例**（比 `pg_stat_user_tables.n_dead_tup` 更准，因为后者是统计估算）。

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT tuple_count, dead_tuple_count,
       round(dead_tuple_count::numeric / NULLIF(tuple_count, 0) * 100, 2) AS dead_pct,
       pg_size_pretty(table_len) AS table_size
FROM pgstattuple('orders');
```

> `dead_pct` 很高 → 该 `VACUUM` 了；若 `VACUUM` 后 `table_len` 仍不缩小，说明有「无法回收的死元组」（长事务、复制槽等），排查 `pg_stat_activity` 的 `idle in transaction`（`07-02`）。

## 11. 与 MySQL 生态对照速查

| 能力 | PostgreSQL 扩展 | MySQL 对应 |
| --- | --- | --- |
| 扩展机制 | `CREATE EXTENSION`（库级） | 内置 + UDF + 存储引擎插件 |
| 密码哈希（bcrypt） | `pgcrypto.crypt()` | 应用层（无内置 bcrypt） |
| 大小写不敏感文本 | `citext` | 默认排序规则 `*_ci` |
| 慢 SQL 统计 | `pg_stat_statements`（内存实时） | 慢查询日志 + `pt-query-digest` / `sys` |
| 模糊匹配 | `pg_trgm` + GIN | `LIKE`（无索引）或 FULLTEXT |
| 向量检索 | `pgvector` | 无原生（需外部 ES/向量库） |
| 地理空间 | `PostGIS` | SPATIAL 索引（较弱） |

## 12. 验收自测

### 12.1 列出可装扩展

```sql
SELECT name, default_version FROM pg_available_extensions WHERE name IN ('pgcrypto','citext','pg_trgm');
```

### 12.2 pgcrypto：UUID + 密码哈希

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
SELECT gen_random_uuid();

```

### 12.3 citext：大小写不敏感唯一

```sql
CREATE EXTENSION IF NOT EXISTS citext;
CREATE TABLE t (e citext UNIQUE);
INSERT INTO t VALUES ('Alice@x.com');
SELECT * FROM t WHERE e = 'alice@x.com';       -- ✅ 命中
INSERT INTO t VALUES ('aLiCe@x.com');           -- ❌ 唯一冲突
```

### 12.4 pg_stat_statements（需配置重启后）

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
-- 跑几条 SQL 后：
SELECT calls, round(mean_exec_time::numeric,2) AS ms, left(query,60)
FROM pg_stat_statements ORDER BY calls DESC LIMIT 5;
```

## 13. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `CREATE EXTENSION` 报「could not open extension control file」 | 镜像里没装该扩展的脚本文件 | 换含该扩展的镜像 / 从源码编译 |
| `pg_stat_statements` 装了但视图不存在 / 查不到 | `shared_preload_libraries` 没加或没重启 | 配置后重启 PG（postmaster 级） |
| `crypt()` 比较总是 false | 哈希里没带盐或算法标识不同 | 用 `gen_salt('bf')` 产生哈希，比较时把「已存哈希」当盐传 |
| `citext` 唯一约束没拦住大小写变体 | 没把列声明成 `citext`（仍是 `text`） | 确认列类型是 `citext` |
| `pg_trgm` 索引对中文模糊没用 | 中文按字切，trigram 对多字节字符效果差 | 用 `zhparser` 全文检索（阶段 9） |
| 扩展在库 A 装了，库 B 用不了 | 扩展是**库级**的 | 每个库各自 `CREATE EXTENSION`，或装到 `template1` |

## 14. 本篇小结

- PG 扩展 = 打包的 SQL 对象，`CREATE EXTENSION` 库级导入；`pg_available_extensions` 看能装、`pg_extension` 看已装。
- `pgcrypto`：`gen_random_uuid()`（PG13+ 内置）+ `crypt()`/`gen_salt('bf')` 密码哈希（盐自动编码进哈希）。
- `citext`：大小写不敏感文本类型，邮箱/用户名首选。
- `pg_stat_statements`：Top-N 慢 SQL，需 `shared_preload_libraries` 加载 + 重启；按 `total_exec_time` 排总耗时。
- `pg_trgm`：`LIKE '%x%'` 的索引解（GIN/GiST）；`pgstattuple`：精确死元组比例。
- 对照 MySQL：PG 用「扩展包」机制，功能（向量、全文、加密）更发达；MySQL 靠内置/UDF/存储引擎。
