## 1. 本篇目标

## 3. 索引的本质与代价（先立住心智模型）

索引是一张**独立保存的「排序好的指针表」**：它把被索引列的值排好序，每个值旁边存一个「这行数据在哪」的指针。查某值时，不等值扫描整张表，而是**在排序结构里二分查找**，再顺着指针回表取行。

> 一句话：**索引用「额外空间 + 每次写入都要维护」换「等值/范围查询从 O(N) 降到 O(log N)」**。

它有两面代价，所以**不是越多越好**：

| 代价 | 说明 |
| --- | --- |
| 空间 | 每个索引是一份数据副本（排序后的键 + 指针），大表上可能和表一样大 |
| 写入 | 每次 `INSERT` / `UPDATE` / `DELETE` 都要同步更新所有相关索引，索引越多写入越慢 |

> 设计目标：**为真实高频查询精确建索引，而不是见列就建**。下一节起逐类讲「什么场景该用它」。

## 4. B-tree：默认索引（首次教学）

### 4.1 语法：`CREATE INDEX`（首次教学）

```sql
-- 通用建索引语法（缺省 USING 即 btree）
CREATE INDEX idx_orders_user ON orders (user_id);

-- 唯一索引：既加速又强制列值唯一
CREATE UNIQUE INDEX idx_users_email ON users (email);
```

> 语法骨架：`CREATE [UNIQUE] INDEX 索引名 ON 表名 (列1, 列2, ...)`。
> `idx_表名_列` 是常见命名惯例（项目里 Prisma 生成的索引也类似）。
> 注意：`UNIQUE`/`PRIMARY KEY` 约束底层**就是**一个唯一 B-tree 索引，在 `00-03` 建表时已隐式建好，故主键查询天然走索引。

### 4.2 B-tree 结构：堆表 + 指针（对比 MySQL 关键差异）

PG 的 B-tree 与 MySQL InnoDB 的 B+tree 都能加速等值/范围/排序，但**行数据放在哪**根本不同：

| 维度 | PostgreSQL（堆表） | MySQL InnoDB（聚簇索引） |
| --- | --- | --- |
| 表数据组织 | **堆 heap**：行按插入顺序散放，无默认顺序 | **聚簇**：主键即数据，行按主键物理有序 |
| 索引叶子存什么 | **行位置（TID）指针** | 主键索引叶子存**整行**；二级索引叶子存**主键值** |
| 通过非主键索引找行 | 走索引拿到 TID → **回表取行** | 二级索引拿主键值 → **回表（聚簇）再查主键** |
| 主键的价值 | 只是一个唯一索引，与行物理位置无关 | 决定行的物理存储顺序 |

> 推论：**PG 里「主键」并不等于「物理排好序」**，所以大数据量下按非主键列频繁查询，必须为该列单独建索引；MySQL 里主键顺序会影响插入性能（乱序主键导致页分裂），需要「自增主键」缓解——PG 无此顾虑，`uuid` 主键也无性能惩罚（这是两库主键选型心态的重要差异）。

### 4.3 B-tree 适合什么

| 操作 | 是否命中 | 说明 |
| --- | --- | --- |
| `=` / `<` / `<=` / `>` / `>=` / `BETWEEN` | ✅ | 二分查找 + 顺序扫描区间 |
| `IN (...)` | ✅ | 拆成多次等值 |
| `ORDER BY 索引列` | ✅ | 索引本身有序，直接顺序读 |
| `LIKE 'abc%'`（前缀） | ✅ | 左前缀可走索引 |
| `LIKE '%abc%'`（中缀） | ❌ | 无法定位起点，回退全表（要用全文检索，见阶段 9） |
| 对索引列做函数/运算 | ❌ | `lower(email)`、`age + 1` 都会破坏「按键定位」，需表达式索引（见 §9） |
| `IS NULL` / `IS NOT NULL` | ✅ | 索引里保存 NULL（PG 支持索引 NULL） |

### 4.4 复合索引与最左前缀（首次教学）

多列复合索引 `(a, b, c)` 的键按 `a` 再 `b` 再 `c` 排序，所以**只有「从左往右的连续前缀」能用**：

```sql
CREATE INDEX idx_orders_user_amount ON orders (user_id, amount);
```

| 查询条件 | 是否能用 `(user_id, amount)` |
| --- | --- |
| `WHERE user_id = 1` | ✅ 用 user_id 前缀 |
| `WHERE user_id = 1 AND amount > 10` | ✅ 用两列 |
| `WHERE user_id = 1 ORDER BY amount` | ✅ 一等值 + 一排序，完美 |
| `WHERE amount > 10`（跳过 user_id） | ❌ 最左列缺失，整条索引没用 |
| `WHERE user_id = 1 ORDER BY amount DESC` | ✅（B-tree 支持双向扫描，正反都能走） |

> **最左前缀规则**：复合索引只有最左列参与等值/范围时，右侧列才用得上；跳过最左列直接查右列，索引作废。
> 与 MySQL 对照：规则一致，但 **MySQL 8.0 引入了「索引跳跃扫描」（Index Skip Scan），少数场景能跳过基数很低的最左列；PG 至今（16/17）不支持 skip scan**。所以 PG 里若最左列基数极低（如 `status` 只有两种值）又要按右列查，更该用**部分索引**（§8）或重排复合列顺序。

## 5. Hash 索引：只等值（首次教学）

```sql
-- 显式指定 USING hash
CREATE INDEX idx_users_email_hash ON users USING hash (email);
```

Hash 索引把键做哈希后放进哈希表，**只有 `=` 等值能命中，不支持范围、排序**。

| 特性 | Hash | B-tree（默认） |
| --- | --- | --- |
| 等值 `=` | ✅（且大键值时可能更省空间） | ✅ |
| 范围 / 排序 / 前缀 LIKE | ❌ | ✅ |
| 事务日志（WAL） | PG 10 起才 WAL 化，崩溃安全 | 一直安全 |

> 历史坑：PG 10 之前的 Hash 索引**不写 WAL**，崩溃/复制后会损坏，需重建；10 起已修复、可安全使用。即便如此，**默认选 B-tree 几乎总对**：它既覆盖等值又覆盖范围，Hash 仅在大键等值的特殊场景（如超长字符串主键、UUID 等值）才可能略有优势。

> 与 MySQL 对照：InnoDB **没有**可手工创建且持久化的 Hash 索引（MySQL 的 `USING HASH` 在 InnoDB 上其实仍建的是 B-tree；真正的 HASH 只在 `MEMORY` 引擎）。InnoDB 有个「自适应哈希索引」是**优化器自动**建在内存里、不可控。所以「手写 `USING hash` 获得一个真·哈希索引」是 PG 独有的能力。

## 6. GIN：倒排索引（引用，不重讲）

GIN（Generalized Inverted Index，通用倒排索引）已在 `03-02` 完整教过，这里只归纳「它适用哪些类型」：

| 数据类型 | 典型查询 | 用到的操作符类 |
| --- | --- | --- |
| `jsonb` | `@>` 包含 | `jsonb_ops` / `jsonb_path_ops` |
| 数组 `text[]` / `int[]` | `@>`、`&&`、`?` | 数组操作符类 |
| 全文 `tsvector` | `@@` 匹配 | `tsvector_ops`（阶段 9 用） |

> 记忆：**「一个键值出现在很多行里，要『包含/命中』查询」就用 GIN**。等值用 B-tree，包含/存在用 GIN。

## 7. GiST：可扩展搜索树（首次教学）

GiST（Generalized Search Tree，通用搜索树）是一套**可扩展**的索引框架：任何「能定义区间、能比较交叠」的数据类型，都能挂到 GiST 上。

| 应用 | 说明 |
| --- | --- |
| 范围类型（`int4range`、`tsrange`…） | 支持「区间是否相交/包含」查询（`&&`、`@>`） |
| 几何类型（`point`、`box`…） | PostGIS 空间索引的底层 |
| 全文检索的旧路径 | 未被 GIN 取代前用它；新项目全文用 GIN |

```sql
-- 范围类型演示：给时间区间的「是否有重叠」建 GiST
CREATE TABLE bookings (
    id    integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room  text NOT NULL,
    during tsrange NOT NULL
);
CREATE INDEX idx_bookings_during ON bookings USING gist (during);

-- 查询「与某个时间区间重叠的预订」会命中 GiST
SELECT * FROM bookings
WHERE during && '[2026-01-01 10:00, 2026-01-01 12:00)';
```

> `tsrange`（timestamp range）是 PG 原生范围类型，`&&`表示「相交」。这类「区间交叠」查询 B-tree 无法高效支持，必须 GiST。
> 与 MySQL 对照：MySQL 没有范围类型，也没有 GiST，此类需求只能拆成两个 `BETWEEN` 列或用空间索引近似。这是 PG 类型 + 索引体系更丰富的一个直观例子。

## 8. BRIN：块范围索引（首次教学）

BRIN（Block Range INdex，块范围索引）是 PG 里**最小、最适合超大表**的索引：它不存每个键 → 行的指针，而是**每连续一堆数据块（页）存一个「最小值 ~ 最大值」摘要**。

```sql
-- 对 append-only 的时间递增列建 BRIN（而非 B-tree）
CREATE INDEX idx_orders_created_brin ON orders USING brin (created_at);
```

| 维度 | BRIN | B-tree |
| --- | --- | --- |
| 体积 | 极小（只有若干个块摘要） | 与表同数量级 |
| 适用前提 | 列值**物理上大致有序**（如按时间递增写入） | 任意顺序 |
| 加速效果 | 快速**跳过**「肯定不含目标」的整块 | 精确二分到行 |

> 经典场景：**日志表、时序表、`created_at` 递增的大表**——数据本来就按时间写入，物理上有序，BRIN 能用极小代价快速定位到时间区间。
> 反例：若列值在表里**随机散落**（如随机 `uuid`），BRIN 每块的 min/max 几乎覆盖全域，失去过滤能力，此时回到 B-tree。
> 与 MySQL 对照：MySQL 无 BRIN，超大日志表只能全量 B-tree（体积大）或分表。BRIN 是 PG 处理「海量、自然有序」数据的独门武器。

## 9. 三类精准索引技巧

前三类讲的是「索引类型」，下面三类是**「怎么建更有针对性」**的技巧，跨类型可用（最常配 B-tree）。

### 9.1 表达式索引：在函数结果上建（首次教学）

第 4.3 节说过「对索引列做函数会让索引失效」。解法：**直接在函数结果上建索引**。

```sql
-- 大小写不敏感查询常用 lower(email)；先在 lower 结果上建索引
CREATE INDEX idx_users_email_lower ON users (lower(email));

-- 这条查询因匹配 (lower(email)) 而命中索引
SELECT * FROM users WHERE lower(email) = 'alice@example.com';
```

> 语法：`ON 表名 (表达式)`，表达式与查询里的写法**必须逐字一致**（这里都是 `lower(email)`）才会命中。
> 与 MySQL 对照：MySQL 8.0.13+ 也支持函数索引 `((lower(email)))`（需双括号 + 严格条件），且受「不允许子查询/非确定性函数」等限制；PG 的表达式索引更自由（任意确定性表达式）。

### 9.2 部分索引：只索引一个子集（首次教学）

```sql
-- 只索引「下过单的用户」的 email（未下单用户不占索引、且让其 email 可重复）
CREATE INDEX idx_users_email_active ON users (email)
WHERE age >= 18;
```

```sql
-- 更实际的例子：只对「未删除」行建唯一索引，实现「软删除后同名可重用」
-- CREATE UNIQUE INDEX idx_users_email_active ON users (email) WHERE deleted_at IS NULL;
```

> 语法：在末尾加 `WHERE 条件`，只把满足条件的行放进索引。
> 收益：① 索引更小更快；② 语义更精准——例如「只对 `active` 用户强制 email 唯一」用**部分唯一索引**即可做到（普通 `UNIQUE` 做不到「只在子集上唯一」）。
> 与 MySQL 对照：MySQL 没有真正的部分索引；要用**生成列 + 唯一索引**或应用层校验来近似，不够直接。部分是 PG 的原生杀手锏。

### 9.3 覆盖索引：`INCLUDE` 免回表（首次教学，PG 11+）

回顾第 3 节「回表」：走索引拿到行位置，还要**回到堆表再读一行**。若查询要的列都在索引里，就能**只看索引不碰表**（`Index Only Scan`）。

```sql
-- 普通索引：查「每个用户的订单总额」要回表取 amount
CREATE INDEX idx_orders_user ON orders (user_id);

-- 覆盖索引：把 amount 一并带进索引的非键列，查询可 index-only
CREATE INDEX idx_orders_user_cover ON orders (user_id) INCLUDE (amount);
```

```sql
SELECT user_id, sum(amount) FROM orders WHERE user_id = 1 GROUP BY user_id;
```

> 语法：`INCLUDE (列...)` 里的列**只作「带上」不做索引键**（不参与排序/查找），专为覆盖查询少回表。
> 前提条件：PG 真正走 `Index Only Scan` 还要求表数据页在 **visibility map 里是全可见的**（即经过 `VACUUM`/`autovacuum` 回收过死元组，`05-02` 讲过）。刚 `UPDATE` 过的表要先 `VACUUM` 才能 index-only。
> 与 MySQL 对照：InnoDB 的二级索引**天生覆盖**（叶子存主键，若查询列全在索引+主键内可不回表）；PG 默认索引不存多余列，需显式 `INCLUDE`。两者殊途同归，用法不同。

## 10. 查看索引：`\di` 与 `pg_indexes`（首次教学）

```sql
-- psql 元命令：列出当前库所有索引
\di

-- 看某张表的索引
\d orders

-- 系统目录：按表名查索引定义（indexdef 是完整建索引语句）
SELECT tablename, indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders';
```

> `\di`（+）与 `\di+ 表名` 可看索引大小，判断是否过大。

## 11. 与 MySQL 索引能力对照速查

| 能力 | MySQL（InnoDB） | PostgreSQL | 差异 |
| --- | --- | --- | --- |
| 默认索引 | B+tree（聚簇：行在主键里） | B-tree（非聚簇：堆表 + TID 指针） | 主键物理意义不同 |
| 唯一索引 | ✅ | ✅ | 一致 |
| Hash 索引 | ❌（仅 MEMORY 引擎；InnoDB 自动 AHI 不可控） | ✅（`USING hash`） | PG 有真哈希索引 |
| 复合索引 + 最左前缀 | ✅ | ✅ | PG 无 Skip Scan（8.0 有） |
| 全文索引 | FULLTEXT（ngram/分词） | GIN + `tsvector`（阶段 9） | 体系不同 |
| 空间索引 | SPATIAL（GIS 类型） | GiST + PostGIS | 均需扩展 |
| 范围类型索引 | ❌（无范围类型） | GiST + 范围类型 | PG 独有 |
| 块范围索引 | ❌ | BRIN | PG 独有 |
| 部分索引（WHERE） | ❌（生成列近似） | ✅ | PG 独有 |
| 表达式/函数索引 | ✅（8.0.13+，受严格限制） | ✅（任意确定性表达式） | PG 更自由 |
| 覆盖索引 | 二级索引天然覆盖 | PG 11+ `INCLUDE` | 机制不同，都能少回表 |

## 12. 项目实战：给 mini-dify 的 `apps` 表设计索引

项目 `apps` 表（见 `d:\user\my_project\github\mini-dify\apps\api-ts\prisma\schema.prisma`）已有：

```prisma
model App {
  id          String   @id @default(uuid())
  ownerId     String   @map("owner_id")
  ...
  @@index([ownerId])      // Prisma 已为 ownerId 建 B-tree 索引
  @@map("apps")
}
```

这套设计与本篇知识完全对应，逐条验证心智模型：

| 列 | 现状 / 建议 | 依据 |
| --- | --- | --- |
| `ownerId` | ✅ 已有 `@@index([ownerId])` | `LIST /apps`（查某用户的应用）是高频等值查询，B-tree 命中 |
| `id`（uuid 主键） | ✅ 主键天然唯一索引 | PG uuid 主键无聚簇顾虑，可放心用（§4.2 推论） |
| `graphJson`（jsonb） | 若要「按节点类型过滤画布」，需 **GIN**（`03-02` 已示范） | 包含/存在查询走 GIN |
| `updatedAt` / `createdAt` | 若未来列表按时间排序且数据量大，可考虑 B-tree 或 BRIN | 递增列、Order-by 场景（§8） |

> 结论：项目当前只给外键 `ownerId` 建了索引——这正是「按真实高频查询精准建索引」的正确示范，没有见列就建。将来画布节点检索、时间排序出现时，再按本篇规则补 GIN / B-tree / BRIN。

## 13. 验收自测

### 13.1 建索引并用 `pg_indexes` 查看

```sql
CREATE INDEX idx_orders_created_brin ON orders USING brin (created_at);
CREATE INDEX idx_users_email_lower ON users (lower(email));
CREATE INDEX idx_users_email_active ON users (email) WHERE age >= 18;
CREATE INDEX idx_orders_user_cover ON orders (user_id) INCLUDE (amount);

SELECT tablename, indexname, indexdef
FROM pg_indexes
WHERE tablename IN ('users', 'orders')
ORDER BY tablename, indexname;
-- 预期能看到上面 4 条的 CREATE INDEX 定义原文
```

### 13.2 说明三类技巧各解决的查询

| 索引 | 命中的查询 | 说明 |
| --- | --- | --- |
| `idx_users_email_lower` | `WHERE lower(email)=...` | 函数结果上建索引，绕开「函数使索引失效」 |
| `idx_users_email_active` | `WHERE email=? AND age>=18` | 只索引成年用户，更小且语义精准 |
| `idx_orders_user_cover` | `SELECT user_id, sum(amount)...` | `INCLUDE` 免回表（配合 VACUUM 走 Index Only） |

### 13.3 删掉演示索引（还原）

```sql
DROP INDEX idx_orders_created_brin,
           idx_users_email_lower,
           idx_users_email_active,
           idx_orders_user_cover;
```

## 14. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 建了索引但查询还是全表扫 | 条件对列做了函数/运算，或复合索引漏了最左列 | 用表达式索引、补最左列、或重排复合列顺序 |
| 范围/排序能查、等值反而用 `USING hash` 建不了 | Hash 只支持 `=` | 等值 + 其他都需时用 B-tree |
| 部分索引「没生效」 | 查询的 `WHERE` 与索引 `WHERE` 不一致，优化器不敢用 | 两者条件要能匹配 |
| `INCLUDE` 建的索引没走 Index Only Scan | 表数据页未全可见（有未回收死元组） | 先 `VACUUM` 表再测 |
| 给随机 `uuid` 列建 BRIN 发现更慢 | 列物理无序，BRIN 摘要失去过滤力 | 随机键用 B-tree；仅自然有序列用 BRIN |
| 索引建太多写入变慢 | 每次写都要维护所有索引 | 只为真实高频查询建，定期 `\di+` 看体积 |

## 15. 本篇小结

- 索引 = 「排序的指针表」，用空间与写入代价换查询加速，**按查询建、不按列建**。
- 五类索引：**B-tree**（默认，等值/范围/排序）、**Hash**（仅等值）、**GIN**（包含/存在，jsonb/数组/全文）、**GiST**（可扩展，范围/几何）、**BRIN**（超大且物理有序表）。
- 复合索引遵守**最左前缀**；PG 无 Skip Scan，基数低的最左列场景用部分索引或重排。
- 三类技巧：**表达式索引**（函数结果上）、**部分索引**（`WHERE` 子集）、**覆盖索引**（`INCLUDE` 免回表）。
- 与 MySQL 根差异：PG 是**堆表 + 指针**（非聚簇），MySQL InnoDB 是**聚簇主键**；PG 的主键不决定物理顺序，故 `uuid` 主键无惩罚。
